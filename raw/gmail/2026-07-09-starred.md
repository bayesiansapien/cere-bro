An instruction that fades is not a rule
Tell Fable 5, mid-session, to stop over-planning and it can comply inside the current context. Move to a new topic or a different slice of work, and the same over-planning can resurface, not because the model forgot the words, but because a one-time instruction competes with everything else in the context window and loses priority. That's not a flaw specific to this model. It's what happens to any instruction that lives as a sentence in a transcript rather than as something re-asserted when it is relevant.
A skill is the fix for that gap: a named file with a trigger condition and a body, either invoked explicitly the moment the symptom shows up, or folded into the standing system prompt so it applies to every turn without being re-typed. The difference between telling a model something once and giving it a skill is the difference between a comment left in a meeting and a rule written into the process.
Fable 5 makes this more consequential than it was on older models, not less. Anthropic's own guidance for the model is explicit that instructions written for prior models are often too prescriptive for it and can degrade output quality: old-model skills micromanage a sequence of steps, and Fable 5 follows the sequence anyway even when its own judgment would do better. That means a skill collection for this model can't just port old patterns forward. It has to be designed around what Fable 5 actually needs stated, and nothing more.
Ten places a standing rule earns its keep
Read closely, most of the failure modes worth writing a skill for come from the same root cause: the model's own strengths, unchecked, run past where the task actually needed them to stop. Higher effort without a floor turns into over-planning. Thoroughness without a scope boundary turns into gold-plating a diff nobody asked to expand. Delegation without a verification step turns into a subagent's mistake going unchecked because nothing independent looked at the output. Autonomy without a stated contract turns into a run that stalls on a promised action instead of taking it.
Nine skills cover that ground: calibrating effort per workload instead of a fixed default, fencing scope so diagnosis doesn't turn into an unrequested fix, keeping diffs mapped one-to-one to the request, binding every progress claim to actual evidence, acting the moment there's enough information instead of over-planning, verifying finished work with a fresh-context subagent instead of self-critique, holding an unattended run to a stated autonomy contract, maintaining a file-based memory with the discipline that keeps it useful, and writing a final summary a reader who saw none of the work can actually follow.
The gap none of the nine cover
All nine of those hold for any Fable 5 workload. None of them say anything about what happens the moment a claude-fable-5 call trips one of the model's safety classifiers, and for the audience this series writes for, that gap is the one that costs real debugging time. A refusal on this model is an ordinary HTTP 200 with stop_reason: "refusal" and empty content, not an error your existing handling will notice, and the four documented trigger categories, cyber, bio, frontier_llm, reasoning_extraction, all fire on categories of legitimate work: security research reads as cyber, life-sciences work reads as bio, ML research reads as frontier_llm, and asking the model to narrate its own reasoning as output text reads as reasoning_extraction regardless of topic.

The drift nobody schedules a meeting about
A fresh prompt written from the Fable 5 rules is clean. It states the outcome, names the boundaries, and skips the step-by-step scaffolding older models needed. After enough teammates and copy-pastes, that same repo has forty prompts, and a few of them read nothing like the clean version.
Nobody sat down and decided to regress. A new teammate copied an old Opus-era system prompt because it was the closest template on hand. Someone under deadline pressure added "IMPORTANT: you MUST run the tests before finishing" to a prompt because it felt safer, not because it does anything Fable 5's plain-sentence instruction following does not already do better. A stale config still sets `temperature: 0.7` from a copy-paste that predates the switch to Fable 5, and nobody has hit the code path that would 400 on it yet.
None of these are dramatic failures. Each one is small enough to not warrant an incident, and that's exactly the problem: nothing forces a review. The cost shows up later, diffusely, as a refusal rate nobody can explain or a coding session that feels worse than it used to, with no single change anyone can point to.
What actually needs catching
Fable 5's own documentation is specific about what degrades its output, because the model's strengths create their own new failure modes. Instructing it to narrate its internal reasoning as response text can trigger a reasoning_extraction refusal, a documented category in the API's refusal-and-fallback reference. Aggressive framing like IMPORTANT: or YOU MUST was compensation for weaker instruction-following in older models; Fable 5 gives a plain sentence the same weight, so the framing does nothing but read as noise. A twelve-item enumerated behavior list, or a first, then, then, then scaffold, is the kind of over-specification the model needs less of, not more. And a handful of API parameters simply behave differently: temperature, top_p, and top_k return a 400 on non-default values, manual thinking configuration is rejected outright because adaptive thinking is always on, and a claude-fable-5 call with no fallbacks parameter dead-ends silently the moment a refusal fires, since a refusal is an ordinary HTTP 200 with empty content, not an error your monitoring will notice on its own.
That's five categories worth checking mechanically instead of trusting memory: reasoning-extraction triggers, overtriggering language, old-model scaffolding, Fable-specific API misconfigurations, and missing fallback wiring. Every one of them is invisible in code review unless you're specifically looking, because the prompt still reads as reasonable English and the config still looks like valid JSON. The failure is behavioral, not syntactic.
The fix for one prompt is easy once you see it: state the outcome, name the boundary, drop the countdown and the capitalized demands. The fix for forty prompts across a growing repo is not a one-time cleanup. It's a check that runs every time something changes.

## 5. The Untrusted Tenant: Rethinking Infrastructure Security for Agentic AI

**From:** Ken Huang from Agentic AI  <kenhuangus@substack.com>  
**Date:** Wed, 8 Jul 2026 11:34:09 +0000  
**Link:** [https://mail.google.com/mail/u/0/#inbox/19f418462e4adb51](https://mail.google.com/mail/u/0/#inbox/19f418462e4adb51)

View this post on the web at https://kenhuangus.substack.com/p/the-untrusted-tenant-rethinking-infrastructure

Why the next security frontier for AI is not the model — it is the infrastructure the model is allowed to touch.
By Alex Zenla Edera and Ken Huang
Anthropic’s release of Claude Fable reflects the industry’s growing recognition that autonomous AI systems cannot be trusted to behave as intended. High-risk queries get rerouted to a less capable model, and the unrestricted version stays gated to a small set of vetted partners. The lab that built the model treats raw capability as something to contain rather than something to trust. That same logic is now arriving at the infrastructure layer.
Much of the security conversation around agents to date focused on prompt injection, jailbreaks, hallucinations, and model behavior. Those are important concerns, but they are not the root problem. The deeper challenge is that organizations are increasingly giving autonomous systems access to tools, credentials, infrastructure, networks, and execution environments. Bringing trust to these systems is shifting the priorities to guardrails, restrictions and containment.
As I often tell people, an LLM’s output is untrusted data. If you are executing actions based on that output, you are executing untrusted code. Once you accept that premise, the rise of AI sandboxing becomes much easier to understand.
The practical consequence is a change in where the control point sits. For years the guiding question was “is this model safe?” The more durable question is “what can this model reach?” The first is a property of the weights and can never be fully guaranteed; the second is a property of the runtime, and it is enforceable. Designing for capability rather than intent is what moves the problem from an open research question into an engineering one.
Agentic AI Changes the Trust Model
Many people compare the current state of agents [ https://substack.com/redirect/e894660d-2d9a-4770-a783-7777ca2aef17?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] to the early days of Docker before Kubernetes emerged. There are certainly similarities. Developers are rapidly building agents, experimenting with frameworks, and creating bespoke systems long before operational standards have fully matured.
But I think a more useful comparison is the transition from monolithic applications to distributed systems and service-oriented architectures. As software became distributed across networks, machines, and services, entire categories of infrastructure emerged to address reliability, observability, identity, and security. The industry had to rethink assumptions that had worked perfectly well in a single machine world.
Agentic AI introduces a similar shift, but with a new complication: autonomy.
Agents are still applications. They are still processes running on infrastructure. What makes them different is that their behavior is increasingly shaped by probabilistic systems that generate actions at runtime. They consume inputs, invoke tools, access external systems, and make decisions that developers may never have explicitly anticipated.
This fundamentally changes the trust model. Historically, most software was assumed to operate within relatively predictable boundaries. Agentic systems do not offer that guarantee. Agents are not necessarily malicious, but they are inherently unpredictable. The cleanest illustration involved no attacker at all. Last summer, Replit’s coding agent deleted a production database during an active code freeze. No exploit, no injection. Autonomy plus access was enough.
Figure 1 — The trust model inverts. Traditional software is trusted because its behavior is fixed and predictable; an agent’s behavior is generated at runtime, so its output must be treated as untrusted data — and acting on it means executing untrusted code.
One of the ideas I keep coming back to is that agents should be treated as tenants [ https://substack.com/redirect/3dd96ce5-d1a6-4c84-8df6-60a0ebc0cafa?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ]. The cloud industry has spent decades refining how untrusted tenants share infrastructure safely. Agentic systems introduce a new kind of tenant, one capable of acting independently and interacting dynamically with the environment around it. That reality has profound implications for how we think about isolation and designing for breaches.
The tenant framing is more than an analogy — it tells you which playbook to reuse. Multi-tenant cloud already solved the hard version of this problem: run mutually distrustful workloads on shared hardware without letting one reach another. What is new is that this tenant writes its own actions as it runs. So the classic tenant controls still apply, but two of them stop being optional. Identity has to be per-session and attributable, because a nondeterministic actor is impossible to audit after the fact without it. And the boundary has to assume compromise from the first request, because there is no clean build you can point to and call trusted.
Why Shared Infrastructure Starts to Break Down
Many of the security challenges emerging around agents stem from the fact that they are being deployed into environments designed around trusted and deterministic workloads.
Containers are a good example. Containers transformed software delivery by standardizing packaging and deployment. But they were designed around developer ergonomics and continuous deployment, not around containing autonomous systems executing untrusted code. And where traditional application bugs were usually confined to a single application, an autonomous agent with access to tools, credentials and execution environments creates a much larger blast radius [ https://substack.com/redirect/06661fc6-dda4-480e-b926-636bc323608c?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ].
In Kubernetes, an agent may not even need to exploit a flaw to escalate privileges: service account tokens are mounted into pods by default, and cloud metadata endpoints are frequently reachable unless someone has explicitly blocked them. The agent simply inherits that blast radius. From there, it can invoke sensitive APIs, modify files, expose secrets, consume resources in unexpected ways, or interfere with neighboring workloads on highly multi-tenant infrastructure where nodes, GPUs and kernels are shared to optimize efficiency.
Figure 2 — On shared infrastructure, an agent inherits reach it never had to earn. Default-mounted tokens, reachable metadata endpoints, and a shared kernel turn a single autonomous process into a path to secrets, sensitive APIs, and neighboring workloads — no exploit required.
The issue is not any specific attack category. Prompt injection, credential misuse, tool abuse, memory poisoning, and unauthorized network access are all symptoms of the same underlying problem. Organizations are increasingly running untrusted execution environments inside infrastructure that was never designed to assume untrusted behavior.
This is why chasing individual attack categories is a losing strategy. Each new symptom invites its own point defense — a prompt filter, a jailbreak classifier, a tool-call allowlist — and the list never ends, because you are patching manifestations instead of the condition. The condition is ambient authority: the agent holds standing access it did not need and cannot be trusted to use narrowly. Remove the standing access and whole classes of symptoms collapse at once. A stolen credential is worthless if it was scoped to one task and expired at the end of the session; a reachable metadata endpoint is inert behind default-deny egress. Least privilege stops being a compliance checkbox and becomes the primary control.
