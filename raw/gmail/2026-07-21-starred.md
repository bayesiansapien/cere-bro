## **Anthropic limits premium Claude access while eyeing Meta compute deal**

Anthropic is currently fighting a massive multi-front war against its own success, trying to balance skyrocketing demand with a severe lack of compute capacity.

To wring every drop of efficiency out of local machines, the lab quietly pulled off an  engineering trick. Starting with Claude Code v2.1.181, Anthropic [migrated the developer tool to a Rust-based port of the Bun JavaScript runtime](https://simonwillison.net/2026/Jul/19/claude-code-in-bun-in-rust/). By embedding an unreleased Bun v1.4.0 preview inside the executable, they managed to shave 10 percent off Linux startup times.

However, local software optimization cannot solve the massive cloud bottleneck at the frontier. Surging demand for the new Claude Fable 5 model has outpaced the company's infrastructure capacity, forcing Anthropic to strictly ration its premium services. Starting July 20, Max and Team Premium subscribers are [being capped at 50 percent of their usage limits](https://x.com/claudeai/status/2078302415804379218). Meanwhile, Pro and Team Standard tiers are losing standard access entirely, getting pushed toward [pay-as-you-go API pricing](https://x.com/claudeai/status/2078302415804379218) after burning through a one-time 100 dollar credit.

To solve this hardware bottleneck, Anthropic is negotiating a massive [10 billion dollar infrastructure lease with rival Meta over two years](https://siliconangle.com/2026/07/17/anthropic-meta-reportedly-discussing-10b-data-center-leasing-deal/). The proposed deal, which includes flexible early termination terms similar to Anthropic’s 1.25 billion dollar monthly lease with SpaceX for the Colossus supercomputers, would grant access to Meta’s data centers. While Meta builds its own custom MTIA hardware, Anthropic is specifically eyeing Meta’s Nvidia GPU clusters to avoid rewriting its codebase.

AI is learning to use the tools around it. That is the promise of the Model Context Protocol, and it is also the security shift many teams are underestimating.
For the last two years, most enterprise AI conversations have centered on model behavior: hallucination, prompt injection, data leakage, evaluation, and policy. Those risks still matter. But the practical risk is changing as assistants move from answering questions to taking actions. When an assistant can query a data warehouse, open a browser, read a file, create a ticket, send a message, update a document, or run a build, the security question is no longer only “what did the model say?” It becomes “what did the system allow the model-connected workflow to do?”
MCP sits directly inside that question.
This is also where a registry-plus-scanner pattern matters: treat MCP not as a one-off connector choice, but as an inventory and governance surface with a review and update loop. Traceforce’s public Atlas registry at 
https://atlas.traceforce.co/
 gives teams a reference point for known MCP servers and security ratings, while its open-source MCP X-Ray scanner helps teams inspect the MCP servers already present in local and enterprise environments.
MCP is not a model. It is not an agent framework. It is a connection layer: a standard way for AI hosts, such as chat applications, IDEs, and agent runtimes, to connect to external tools, data sources, and services. The official MCP specification describes a host, an MCP client inside that host, and MCP servers that expose resources, prompts, and tools. Anthropic introduced MCP in November 2024 as an open standard for connecting AI assistants to systems where data lives, replacing one-off integrations with a common protocol. The current public protocol version, 2025-11-25 as of July 2026, frames MCP as a way to share context, expose capabilities, and build composable workflows.
That is powerful. It is also exactly why MCP deserves a security review that looks different from a normal API review.
An API integration usually lives behind application code. Developers decide which endpoint to call, what parameters are allowed, how credentials are stored, where logs go, and which user action triggered the request. MCP makes integrations easier to add, easier to discover, and easier for AI tools to invoke. The upside is speed. The downside is that every new MCP connection creates a fresh trust boundary between a probabilistic reasoning system, executable tool code, enterprise data, and downstream APIs.
If a connection can only read a public weather API, the boundary may be low risk. If it can read Slack, browse internal Drive folders, query Snowflake, write GitHub issues, run shell commands, update CRM records, or access regulated data, the boundary becomes a control point. It needs identity, permission, policy, runtime containment, and traceability. Without those, MCP can turn a local productivity feature into an ungoverned action path.
Figure 1 illustrates the architectural reason this happens. MCP simplifies the connection pattern, but it also creates a repeatable path from AI intent to external action.
The risk is not that MCP is inherently unsafe. The risk is that MCP makes capability feel like configuration. A user or team adds a server, the host sees a list of tools, the model gets descriptions of those tools, and suddenly the assistant has a path into places it could not reach before. That path may be authorized in the narrow sense that a token exists. It may still be poorly governed in the security sense: too much privilege, too little review, unclear ownership, weak logs, and no practical way to reconstruct what happened during an incident.
This is the hidden risk in MCP connections: they look like integrations, but they behave like delegated agency.
MCP is a connection layer, not a permission model
The simplest way to understand MCP is to separate the protocol from the policy around it.
The protocol standardizes how AI applications talk to external systems. Servers can offer resources, which are data and context; prompts, which are templated workflows; and tools, which are functions the AI system can execute. Clients can also expose capabilities such as roots, sampling, and elicitation, depending on implementation. The base protocol uses JSON-RPC messages, supports capability negotiation, and lets hosts connect to many servers through a common pattern.
That standardization solves a real engineering problem. Before MCP, each AI application and each business system needed a custom integration. If there are N AI applications and M tools, the integration surface becomes N times M. MCP reduces that by giving tool builders one protocol to expose capabilities and host builders one protocol to consume them.
Security teams should appreciate that benefit. Standardization can make controls easier. A common protocol can support common gateways, registries, policy checks, observability, and review processes. The mistake is assuming the protocol itself supplies all those controls by default.
The MCP specification includes important security principles: explicit user consent, user control over shared data and actions, data privacy, tool safety, and caution around LLM sampling. It also says that tools can represent arbitrary code execution and should be treated carefully. The official security best practices document goes further, covering confused deputy risks, token passthrough, SSRF, session hijacking, local server compromise, stdio transport risks, and scope minimization.
But a protocol specification is not an enterprise governance program. It cannot know whether a server should access engineering repositories but not payroll data. It cannot decide whether a “send email” tool is acceptable for an intern’s agent but not for a production support bot. It cannot guarantee that a community MCP server is maintained, sandboxed, patched, or logging the right fields. It cannot infer whether a broad OAuth scope was granted because the workflow needed it or because the consent prompt was easier to implement.
That is why the security posture of MCP depends on the environment around each connection. The core question is not “does this server speak MCP?” The question is “what does this connection allow, on whose behalf, under which policy, with which evidence trail?”
Every connection creates a new trust boundary
Security teams already know trust boundaries from application design. A browser boundary. A service boundary. A database boundary. A tenant boundary. A network boundary. MCP adds a boundary that is less familiar because it combines four moving parts:
First, there is a user or workflow expressing intent in natural language. The prompt may be precise, vague, incomplete, or adversarially influenced by content the model has read.
Second, there is an AI host deciding what to do. It may summarize, reason, plan, select tools, call tools, inspect outputs, and continue the task.
Third, there is an MCP server exposing capabilities. That server may be local or remote, official or community-maintained, read-only or action-capable, narrow or broad, trusted or merely installed.
Fourth, there is a downstream system that treats a request as an API call, file access, browser operation, or database query.
The trust boundary appears wherever assumptions change. User intent is not the same as model interpretation. Model interpretation is not the same as policy approval. MCP tool metadata is not the same as trusted code. A token is not the same as least privilege. A downstream API log is not the same as an agent audit trail.
