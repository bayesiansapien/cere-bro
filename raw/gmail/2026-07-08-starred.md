**Date:** Tue, 7 Jul 2026 17:14:43 +0000

View this post on the web at https://kenhuangus.substack.com/p/claude-fable-5-part-3-memory-engineering

Part 1 [ https://substack.com/redirect/62a4e77d-4d28-40e3-ab6c-8f20566c22d4?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] argued the leverage moved from prompts to harnesses. Part 2 [ https://substack.com/redirect/644c725e-eb57-48cb-86f5-d128f897f28d?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] argued the harness is a loop. Part 3 is about the part of the loop that outlives every session: memory. If you run Fable 5 loops day and night, the files agents wrote for themselves have become the most valuable and the most dangerous artifacts in the setup. Valuable, because a loop with good memory stops repeating last week's mistakes. Dangerous, because memory is the one channel where a single bad write becomes standing policy, reloaded at every startup, trusted more the older it gets.
Here's the split. The free half covers what Anthropic shipped and said: the memory system their Fable 5 guide tells you to build, the memory stack and what loads when, the official multi-session pattern, and the poisoning threat model in their own words, including the gap in their own security docs. The paid half is the playbook: the memory prompt block I run, a hardened client-side handler for the memory tool, the startup scan that quarantines suspicious lessons, the audit loop, the dreaming preview and how to fake it tonight, memory cost math with caching, a detection recipe from the newest research, and the weekend project. The working code lives in the series repo, paid subscribers will have access to the Github repo. 
Memory went official
Buried in Anthropic's Fable 5 prompting guide [ https://substack.com/redirect/cd1dde82-37b0-4138-ad69-2266f71a95fb?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] is a section called "Construct a memory system," and its first sentence is the thesis of this post: "Claude Fable 5 performs particularly well when it can record lessons from previous runs and reference them." The guide's prescription matches what part 2 called template 2: one lesson per file, a one-line summary at the top, update existing notes instead of duplicating them, delete the ones proven wrong. This is not community folklore anymore. It's the vendor telling you the model was built to use a filesystem as its long-term brain.
The API grew the matching organ. The memory tool [ https://substack.com/redirect/044ed8f5-d8c1-4f40-8c8e-82bc19f9328a?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] is GA on the Messages API, no beta header, and works on Claude 4+ models generally, not only Fable 5:
response = client.messages.create(
    model="claude-fable-5",
    max_tokens=4096,
    tools=[{"type": "memory_20250818", "name": "memory"}],
    messages=[{"role": "user", "content": "Continue the migration."}],
)
The design decision that matters is in what that block does not do: the tool is entirely client-side. Claude issues file operations (view, create, str_replace, insert, delete, rename) against a /memories directory, and your application executes them. Anthropic stores nothing. That buys you control over where memory lives, and it hands you full responsibility for what gets into it, which becomes the whole story in a minute.
The lifecycle above is the guide's prescription drawn as the loop it implies. The two arcs people skip are the last two: update-or-delete (a memory directory that only grows is a memory directory nobody curates) and the prune pass. Skipping them doesn't fail loudly. It fails as a slow drift toward an agent confidently applying rules from a project state that no longer exists.
The memory stack: what loads when
Once you run this for real, memory splits into four layers with different load rules, and confusing them is the most common design error I see:
CLAUDE.md is frozen policy and loads every session, so it must stay small and earn every line. The lessons directory is distilled knowledge: the index loads every session, the files load on demand. The progress log and feature checklist are project state, read at session start and written at session end. Transcripts and artifacts are raw evidence and never auto-load; they exist so a lesson can point back at proof. Content moves up the stack only by earning it: verified outcomes update the state files, state distills into lessons, and a lesson that keeps proving itself graduates into CLAUDE.md. Moving content up without the intermediate step is how a one-time observation becomes a permanent rule.
The multi-session pattern, straight from the docs
The memory tool page documents a pattern Anthropic calls multi-session software development, and it's the strongest official statement yet that context windows are for working, not for remembering:
An initializer session sets up the memory files before any substantive work happens: a progress log and a feature checklist. Every later session resumes from those files, not from a transcript. And the rule that makes it work is a quote worth pinning above your desk: mark a feature complete "only after end-to-end verification confirms it works, not when the code is written." That's part 2's maker-never-grader rule applied to memory writes; the checklist is a memory file, and unverified completion claims are how it rots. Their long-running harness post [ https://substack.com/redirect/ca2f85b7-8cac-434d-9545-692db4040e2e?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] runs this exact pattern as a case study if you want it worked through.
The non-obvious win of the initializer session: it forces you to decide what the memory schema is before any agent writes to it. Schema-less memory converges on a junk drawer, and Fable 5 will faithfully read you the junk.
Memory poisoning is an official attack class now
Part 2 gave you four countermeasures and a warning. Since then the warning acquired primary sources. Anthropic's engineering post "How we contain Claude" [ https://substack.com/redirect/026e0fa3-e40d-4bbc-9e12-fca4601297dc?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ] (May 25) has a subsection titled "Persistent memory poisoning." It names the surfaces: product memory, CLAUDE.md files, mounted workspaces, and the state directories of scheduled and long-running agents. And it names the mechanism that makes this worse than ordinary prompt injection: an injection that reaches memory "reloads at every agent startup." A poisoned web page hits one session; a poisoned lesson file hits every session from now on. Their stated direction: "Good classifiers on session startup will need to become more commonplace." That's a forward-looking need, not a shipped feature, which means for now the startup check is yours to build (the paid half has mine).
Now the gap worth naming. The memory tool's official security section covers four things: sensitive data, path traversal, file size, and expiration. The words "poisoning" and "prompt injection" appear nowhere on that page. One Anthropic property documents the attack; the other, the tool most exposed to it, doesn't mention it. If you build on the memory tool and stop at the documented checklist, you've secured the filesystem and left the contents unguarded.
The research is arriving too. A June 29 arXiv preprint by Jun Wen Leong, "Forensic Trajectory Signatures for Agent Memory Poisoning Detection" [ https://substack.com/redirect/b8533c22-5f4a-4e83-82de-313063ebcfde?j=eyJ1IjoiOGs4ZDAifQ.VI2uzD6zEHQ-HoC2J2iX6FwxM11lZ3HP_Zidnio1pMQ ], shows that successful memory-poisoning attacks leave detectable fingerprints in an agent's tool-call sequence, like a memory recall firing right before an outbound email send.
