# Proof-of-Control for Model Context Protocol

<p><strong><span>A crosswalk mapping from MCP to the Open Verification / Proof-of-Control Standard</span></strong></p><p><span>By Ken Huang, Comments wil be apprecited</span></p><h2><strong><span>1. Purpose and scope</span></strong></h2><p><span>This document maps the Model Context Protocol (MCP) against the six domains of verification, the System surface, the Verifiability Tiers, and the threat model defined in the Proof-of-Control standard.</span></p><p><span>It is </span><strong><span>informative</span></strong><span>. It adds no requirements to either specification. Its purpose is to answer three questions a reader of the standard will ask about the most widely deployed agent-integration protocol in the field:</span></p><p><span>Which Proof-of-Control control intents does MCP already implement?</span></p><p><span>Where does the evidence that those controls are implemented sit on the Verifiability Tiers, and why?</span></p><p><span>What would have to change &#8212; in the protocol, or around it &#8212; for an MCP deployment to clear the binary threshold?</span></p><p><span>A note on framing. Proof-of-Control verifies that the controls governing an agent system </span><strong><span>are implemented and verifiable</span></strong><span> &#8212; a present-tense property of the system, answerable before deployment. It is not a retrospective finding about whether an agent misbehaved. This document uses that framing throughout, and it is the reason the assessment below grades MCP&#8217;s controls and MCP&#8217;s evidence separately: a control can be thoroughly implemented and still not be independently verifiable, which is exactly MCP&#8217;s position.</span></p><p><span>Where this document states a protocol requirement, it uses the requirement language of the MCP specification itself (RFC 2119), and the requirement is MCP&#8217;s, not this document&#8217;s.</span></p><p><span>MCP is the point in a deployed agent stack where an agent crosses the boundary that the Verifiability Gap describes. It is where an agent reads data it did not author, calls a tool it does not own, and takes an action with an effect outside its own process. Every such crossing is a place evidence goes missing.</span></p><p><span>MCP is also a useful subject because it is </span><em><span>well specified</span></em><span>. It is not a case of absent controls. It is a case of thorough controls whose record is held by the party being checked &#8212; which is the exact condition the Verifiability Tiers were built to grade, and the exact condition the binary threshold was built to separate.</span></p><h2><strong><span>2. What MCP is</span></strong></h2><p><span>MCP is an open protocol, hosted by The Linux Foundation, that standardizes how LLM applications connect to external data sources and tools. It is built on JSON-RPC 2.0 and takes structural inspiration from the Language Server Protocol.</span></p><h3><strong><span>2.1 Actors</span></strong></h3><div class="captioned-image-container"><figure><a class="image-link image2" href="https://substackcdn.com/image/fetch/$s_!Wph1!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F5fe99fc5-1884-4905-b555-7ccec441f7c5_2043x448.png" target="_blank"><div class="image2-inset"><source type="image/webp" /><img alt="" class="sizing-normal" height="319" src="https://substackcdn.com/image/fetch/$s_!Wph1!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F5fe99fc5-1884-4905-b555-7ccec441f7c5_2043x448.png" width="1456" /><div></div></div></a></figure></div><p style="text-align: center;"><em><span>Figure 1: MCP Actor Roles &amp; Proof-of-Control Alignment (Table Infographic)</span></em></p><p><span>MCP has no protocol-level concept corresponding to the Proof-of-Control </span><strong><span>Principal</span></strong><span> &#8212; the party on whose behalf the agent acts &#8212; except indirectly, through the OAuth resource owner on HTTP transports. This is treated in &#167;5.5.</span></p><h3><strong><span>2.2 Features</span></strong></h3><p><strong><span>Servers offer:</span></strong><span> Resources (context and data), Prompts (templated workflows), Tools (functions the model can execute).</span></p><p><strong><span>Clients offer:</span></strong><span> Elicitation (server-initiated requests for user input), Sampling, and Roots.</span></p><p><strong><span>Utilities:</span></strong><span> logging, argument completion, pagination, caching, progress, cancellation.</span></p><p><strong><span>Extensions</span></strong><span> are opt-in, additive, composable, and negotiated through the extensions field of capabilities. Notable ones: Tasks (asynchronous long-running operations), MCP Apps (inline interactive UI), and Skills over MCP.</span></p><h3><strong><span>2.3 The stateless model</span></strong></h3><p><span>Revision 2026-07-28 is a </span><strong><span>stateless protocol</span></strong><span>. Architectural relationship</span></strong></h2><p><strong><span>MCP defines the control surface.</span></strong><span> It specifies what an agent may reach, under what authority, with what schema, and with what consent.</span></p><p><strong><span>Proof-of-Control defines the verification surface.</span></strong><span> It specifies evidence that those controls are implemented and in force, in a form a party other than the operator can check.</span></p><p><span>The two compose cleanly and do not overlap. MCP answers </span><em><span>what is permitted</span></em><span>; Proof-of-Control answers </span><em><span>are those controls implemented, and can anyone verify that independently</span></em><span>.</span></p><p><span>This is the same complementary shape the standard identifies with CSA&#8217;s AARM (enforcement vs. evidence), with one difference worth noting: AARM is a runtime gateway that intercepts actions inside one deployment, whereas MCP is a wire protocol spanning organizations. MCP therefore carries the evidence problem </span><em><span>across</span></em><span> trust boundaries by construction, which places it closer to the Portability domain than AARM sits.</span></p><p><span>Figure 1 resolves that relationship into three layers. A protocol foundation governs the specification; vendors and adopters secure their implementations; and an assurance layer supplies independent evidence about deployments. Read it bottom to top: each layer is evidenced by the one above it. The third layer must sit outside the operator to do its job, which is why a protocol body cannot fill it however well it governs the spec.</span></p><p><em><span>Figure 1: Protocol, implementation, and assurance</span></em></p><h2><strong><span>4. The structural finding</span></strong></h2><p><strong><span>MCP&#8217;s statelessness is architecturally aligned with the Proof-of-Control </span></strong><em><strong><span>contemporaneous</span></strong></em><strong><span> evidence property, and MCP&#8217;s trust model caps it at Tier 2 by construction.</span></strong></p><p><span>Both halves matter.</span></p><p><strong><span>On alignment.</span></strong><span> Because every MCP request must be self-describing &#8212; version, capabilities, client identity, and authorization all present on the request itself &#8212; each request is already an independently interpretable unit of execution. That is precisely the shape a per-action evidence record requires. A session-oriented protocol would force an evidence layer to reconstruct context from connection state; MCP hands that context over on every call. The implementer guidance in the standard &#8212; </span><em><span>generate the evidence while the action happens, not after a dispute</span></em><span> &#8212; describes a record MCP&#8217;s wire format already approximates.</span></p><p><strong><span>On the ceiling.</span></strong><span> Every control MCP specifies is enforced by the MCP server and recorded, if at all, by the operator who runs it. Token validation, scope enforcement, consent checks, schema conformance: all real, all normative, all attested by the party being checked. Under the Verifiability Tiers this is </span><strong><span>Tier 2 &#8212; Attestation</span></strong><span>: a signed operator record whose integrity rests on trusting a party. It is authenticated documentation, not cryptographic evidence.</span></p><p><span>The consequence is the sharpest statement this crosswalk can make:</span></p><p><strong><span>Moving a spec-conformant MCP deployment from Tier 2 to Tier 3 requires no new controls. Every check is already normative. It requires changing who produces and holds the record.</span></strong></p><p><span>MCP is therefore a clean worked example of the binary threshold &#8212; valuable to the standard </span><em><span>because</span></em><span> it is well designed, not despite it.</span></p><h2><strong><span>5.
