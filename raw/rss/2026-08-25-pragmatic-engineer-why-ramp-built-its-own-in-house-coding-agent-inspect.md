# Why Ramp built its own in-house coding agent, Inspect

<p><span>At a select few tech companies, they write most of their code with their own, custom-built, internal AI coding agents. This is different from most of the industry which uses AI coding agents and harnesses like Codex, Claude Code, Cursor, OpenCode, GitHub Copilot, etc. At Ramp, their own version is called </span><a href="https://inspect.ramp.engineering/"><span>Inspect</span></a><span>, while at Block it&#8217;s </span><a href="https://block.xyz/inside/block-open-source-introduces-codename-goose"><span>Goose</span></a><span> (open source), at Stripe it&#8217;s </span><a href="https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents"><span>Minions</span></a><span>, and </span><a href="https://shopify.engineering/under-the-river"><span>River</span></a><span> at Shopify.</span></p><p><span>But why not just use what frontier labs and coding harness AI startups already offer; why take the time and effort?</span></p><p><span>We reached out to Ramp, a fintech company big on building its internal AI infrastructure, and sat down with the founding team of Inspect and engineering leadership. We talked with CTO </span><a href="https://www.linkedin.com/in/rahul-gs/"><span>Rahul Sengottuvelu</span></a><span>, Head of Engineering </span><a href="https://www.linkedin.com/in/hdadkhah/"><span>Hamid Dadkhah</span></a><span>, and </span><a href="https://www.linkedin.com/in/zachbruggeman/"><span>Zach Bruggeman</span></a><span>, principal engineer and founding engineer of Inspect.</span></p><p><span>Today, we cover:</span></p><ol><li><p><strong><span>What is Inspect? </span></strong><span>Imagine an AI coding agent running on remote sandboxes with access to most internal data sources, and verifying all backend and frontend changes on the remote machine.</span></p></li><li><p><strong><span>Why build your own background coding agent?</span></strong><span> Engineers and designers at Ramp were dissatisfied with third-party harnesses: they wanted to run more than a few agents in parallel &#8211; which local machines don&#8217;t support &#8211; to have better frontend tooling, and also faced demand for remote development environments.</span></p></li><li><p><strong><span>How Ramp uses Inspect:</span></strong><span> coding, bugfixing in Slack, debugging, and building internal agents like code review and incident management on top of the Inspect platform</span></p></li><li><p><strong><span>Tech stack and architecture: </span></strong><span>React/Vite, Cloudflare Durable Objects, SQLite, Cloudflare Agents SDK, Modal sandboxes.</span></p></li><li><p><strong><span>What makes Inspect so popular?</span></strong><span> The machine in the cloud is a developer machine, plus it has access to numerous internal integrations via API and MCP.</span></p></li><li><p><strong><span>Inside the sandbox. </span></strong><span>OpenCode, services for development (e.g. Postgres, Redis, RabbitMQ, Temporal), Chromium, and VS Code Server. Plus, we check out smart tricks to make sandboxes spin up in five seconds or less(!!)</span></p></li><li><p><strong><span>Collaboration &amp; feedback. </span></strong><span>All Inspect sessions are public and open to collaboration, with no opt-outs allowed. More than 150 people at Ramp have contributed to the project.</span></p></li></ol><p><span>If you&#8217;re like us, you might wonder what the point would be of building your own harness and investing the time and resources in it, given all the choices already out there. This article sets out to answer that question, to understand why other places chose a similar path, and how a non-AI frontier lab can build more efficient tooling than what the frontier AI labs offer. It looks like the &#8220;buy, don&#8217;t build&#8221; tooling convention might not apply to AI tools!</span></p><p><span>Let&#8217;s get into it.</span></p><p><em><span>The bottom of this article could be cut off in some email clients. </span><a href="https://newsletter.pragmaticengineer.com/p/why-ramp-built-inspect"><span>Read the full article uninterrupted, online.</span></a></em></p><p class="button-wrapper"><a class="button primary" href="https://newsletter.pragmaticengineer.com/p/why-ramp-built-inspect"><span>Read the full article online</span></a></p><h2><span>1. Why build your own background coding agent?</span></h2><p><span>There are a few reasons why Ramp decided to turn down tried-and-tested products and create their own:</span></p><ol><li><p><strong><span>Local machines are limited in how many agents they can run. </span></strong><span>Ramp found third-party products below expectations; they liked Claude Code on day 1, but were constrained by only being able to run one or two sessions on local machines.</span></p></li><li><p><strong><span>Better frontend tooling. </span></strong><span>The web engineering team wanted to improve their frontend tooling so designers could make small UI tweaks. There was an opportunity to use AI to automate themselves out of that loop.</span></p></li><li><p><strong><span>Need for remote dev environments. </span></strong><span>As Ramp scaled, so did the complexity, and with it there was more work at the intersection of systems, like debugging backward compatibility, and broken API contracts. The solution was to create remote dev environments.</span></p></li></ol><p><span>Inspect started as a designer&#8217;s frontend tool, and a good part of its team were frontend engineers with interests in UX and speedy performance. The v1 was a Chrome extension for visual edits, where a user could highlight an area and tell the AI what minor website changes to make, like copy edits and button placements. The task of building a tool for making UI edits with AI was given to two frontend engineers, Zach Bruggeman and Jason Quense, who aside from their frontend domain knowledge, brought a welcome adversarial perspective, as they were less than fully convinced by AI at that time.</span></p><p><span>People liked v1 but it wasn&#8217;t adopted because engineers already knew how to go to a file and edit a single line of code, so didn&#8217;t have a reason to use it, and it also required setting up a local development environment, making it too complicated for non-devs.</span></p><p><span>For the current iteration of Inspect (released November 2025) the team pivoted. They built Inspect v2 as a remote development environment with a coding agent on top. Setting it up as a remote environment that they could configure centrally removed the need for local setup on each machine. They were also encouraged by seeing that OpenCode, the open-source coding agent which serves as Inspect&#8217;s harness, exposed an HTTP API which made it straightforward to set up, and was open-source, good enough, and importantly, offered model agnosticism.</span></p><p><em><span>Check out the episode of The Pragmatic Engineer podcast </span><a href="https://newsletter.pragmaticengineer.com/p/opencode"><span>with OpenCode creator, Dax Raad</span></a><span>.</span></em></p><p><span>After pivoting, adoption skyrocketed to where it is
