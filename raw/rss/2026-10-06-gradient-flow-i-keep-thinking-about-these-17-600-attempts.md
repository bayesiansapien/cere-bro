# I keep thinking about these 17,600 attempts

Some of the stories sound straight out of movies: </span><a href="https://openai.com/index/hugging-face-incident-and-the-road-ahead/?utm_source=gradientflow&amp;utm_medium=newsletter"><span>agents escaping test environments</span></a><span>, communicating through channels nobody intended, finding vulnerabilities, stealing credentials, and reaching production systems.</span></p><p><span>The part I think deserves more attention is less dramatic. Measure how long containment actually takes</span></strong></h4><p><span>Security teams usually measure whether they can detect an intrusion. Agentic attacks make that advice more urgent. Decide in advance which containment actions can happen automatically and which ones the security team is preauthorized to take.</span></p><h4><strong><span>3. Secure the harness, not just the model</span></strong></h4><p><span>I recently argued that teams should </span><a href="https://gradientflow.substack.com/p/i-keep-hearing-the-same-advice-about?utm_source=gradientflow&amp;utm_medium=newsletter"><span>evaluate the model and its harness as one system</span></a><span>. The cyber evidence makes that point much stronger.</span></p><p><span>The harness is everything surrounding the model: tools, memory, credentials, network access, execution environments, and policies. </span><a href="https://www.boozallen.com/insights/cyber/cyber-weapon-index.html?utm_source=gradientflow&amp;utm_medium=newsletter"><span>In tests that used AI models as attackers</span></a><span>, researchers found that the surrounding tooling can dramatically change what a model can accomplish. Ignore the model name for a moment and inventory everything the agent can see, call, write to, or spend. Then ask: if the agent behaved badly tomorrow, what is the worst thing this harness would let it do?</span></p><h4><strong><span>4. Plan for agent swarms</span></strong></h4><p><span>One of the stranger lessons from the Hugging Face incident is that agents may find ways to cooperate even when nobody designed them to. In that case, hundreds of agents </span><a href="https://metr.org/blog/2026-08-26-openai-hugging-face-incident-investigation/?utm_source=gradientflow&amp;utm_medium=newsletter"><span>shared information and built their own communication methods</span></a><span> across runs that were supposed to be separate.</span></p><p><span>That matters because a group of agents can divide up work, share discoveries, and keep pursuing a problem after individual attempts fail. It also means that shared folders, databases, message queues, and other writable resources can become communication channels you never intended.</span></p><p><span>I would not assume every group of agents will behave this way. But if you are deploying many agents, treat communication between them as another permission to control and monitor.</span></p><h4><strong><span>5. Stop giving agents permanent credentials</span></strong></h4><p><span>I have written before about </span><a href="https://gradientflow.substack.com/p/security-for-ai-native-companies?utm_source=gradientflow&amp;utm_medium=newsletter"><span>treating agents as non-human identities</span></a><span>. The practical guidance is becoming clearer.</span></p><p><span>Give each agent its own identity rather than hiding it behind its user&#8217;s credentials. Use </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/ai-assisted-vulnerability-management/?utm_source=gradientflow&amp;utm_medium=newsletter"><span>narrowly scoped credentials that expire</span></a><span> when the task ends. Keep read and write permissions separate. Avoid static cloud keys sitting inside an agent environment. Make sub-agents traceable back to their parent and human owner.</span></p><p><span>This is ordinary </span><a href="https://en.wikipedia.org/wiki/Principle_of_least_privilege"><span>least privilege</span></a><span> adapted to software that can actively explore its environment. The difference matters. A human employee may never discover that an old credential gives access to some forgotten system. An agent can systematically look.</span></p><h4><strong><span>6. A successfully manipulated agent should still encounter hard limits on its credentials, network access, tools, and ability to make consequential changes.</span></p><h4><strong><span>7. Keep the security boundary outside the model</span></strong></h4><p><span>One of my recent rules for production agents was to </span><a href="https://gradientflow.substack.com/p/i-keep-hearing-the-same-advice-about?utm_source=gradientflow&amp;utm_medium=newsletter"><span>put hard constraints in software rather than prompts</span></a><span>. Recent incidents provide a good reason to be stricter about that distinction.</span></p><p><a href="https://www.darkreading.com/cyber-risk/model-knowing-rules-is-not-security-control?utm_source=gradientflow&amp;utm_medium=newsletter"><span>A prompt saying &#8220;do not access production&#8221; is guidance</span></a><span>. An API permission that makes production inaccessible is a control.</span></p><p><span>If an action could have serious consequences, let the model suggest it, but have </span><a href="https://www.tenable.com/blog/how-agentic-harness-works-tenable-hexa-ai?utm_source=gradientflow&amp;utm_medium=newsletter"><span>another part of the system decide whether it is actually allowed to run</span></a><span>.
