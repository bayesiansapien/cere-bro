To find out more, I turned online to some of the folks who read these articles. Most use cases involve responding to events or running scheduled jobs. They are useful, but don&#8217;t feel like brand new workflows.</span></p></li><li><p><strong><span>Helpful loops for devs. </span></strong><span>Open PRs for newly-recorded app issues, have notes ready when an oncall joins an outage Slack channel, &#8220;babysitting&#8221; and fixing nightly end-to-end tests, and more.</span></p></li><li><p><strong><span>Disappointment and &#8220;tokenmaxxing&#8221;</span></strong><span>. Also, at companies that pay API prices for tokens, loop engineering gets expensive fast.</span></p></li><li><p><strong><span>Was looping a hack while tooling caught up?</span></strong><span> Distinguished engineer Max Kanat-Alexander believes the &#8220;loop&#8221; might have just been a temporary hack while the harnesses added the ability to do the same from a single prompt.</span></p></li><li><p><strong><span>Does &#8220;context engineering&#8221; matter more for devs? </span></strong><span>Except for engineers building AI infra, there seems little benefit in going deep into loop engineering. Instead, becoming familiar with AI context windows &#8211; also part of building loops &#8211; could be more useful.</span></p></li></ol><h2><span>1. Where it began: &#8220;Ralph Wiggum&#8221; loop</span></h2><p><span>Exactly a year ago, software engineer Geoffrey Huntley published the article &#8216;</span><a href="https://ghuntley.com/ralph/"><span>Ralph Wiggum as a software engineer</span></a><span>&#8217;. The name references the naive son of the local police chief in The Simpsons, who is extremely eager to always be helpful. In engineering, &#8220;Ralph&#8221; is intended to continuously nudge the agent in the right direction. Geoff described it:</span></p><blockquote><p><span>&#8220;Ralph is a technique. In its purest form, Ralph is a Bash loop:</span></p><p><span>while :; do cat PROMPT.md | claude-code ; done</span></p><p><span>Ralph can replace the majority of outsourcing at most companies for greenfield projects. It has defects, but these are identifiable and resolvable through various styles of prompts.</span></p><p><span>That&#8217;s the beauty of Ralph - the technique is deterministically bad in a nondeterministic world.&#8221;</span></p></blockquote><p><span>The article expands on the idea of the Ralph loop:</span></p><ul><li><p><span>Start the agent with a prompt that captures the task and defines a goal</span></p></li><li><p><span>Create a plan of work, each item with a success criteria</span></p></li><li><p><span>Start the loop:</span></p><ul><li><p><span>Take one item per loop</span></p></li><li><p><span>When the agent is done, check if the goal is achieved</span></p></li><li><p><span>If not: start the agent again, with a clear context window</span></p><ul><li><p><span>Start loops if needed: spawn subagents as and when necessary</span></p></li></ul></li></ul></li></ul><p><span>Geoff published the experiments he did with this approach, such as building a new programming language last summer, and </span><a href="https://ghuntley.com/ralph/"><span>said</span></a><span> it requires skill:</span></p><blockquote><p><span>&#8220;Engineers are still needed. There is no way this is possible without senior expertise guiding Ralph. Anyone claiming that engineers are no longer required and a tool can do 100% of the work without an engineer is peddling horses***.&#8221;</span></p></blockquote><p><strong><span>The &#8220;Ralph method&#8221; blew up late last year with the arrival of better models</span></strong><span> which were surprisingly capable of building ambitious projects. From the docs:</span></p><blockquote><p><span>&#8220;[/goal] It&#8217;s our take on the Ralph loop, directly inspired by Codex CLI 0.128.0&#8217;s /goal by Eric Traut (OpenAI). The core idea &#8212; keep a goal alive across turns and don&#8217;t stop until it&#8217;s achieved &#8212; is theirs. The implementation here is independent and adapted to Hermes&#8217; architecture.&#8221;</span></p></blockquote><p><span>Less than two weeks later &#8211; on 12 May &#8211; Claude Code also </span><a href="https://code.claude.com/docs/en/goal"><span>shipped</span></a><span> their /goal command. It&#8217;s identical in what it does to Codex. From Claude Code:</span></p><blockquote><p><span>&#8220;The /goal command sets a completion condition and Claude keeps working toward it without you prompting each step. After each turn, a small fast model checks whether the condition holds. If not, Claude starts another turn instead of returning control to you. The goal clears automatically once the condition is met.&#8221;</span></p></blockquote><p><span>A few months before, in March, Claude Code shipped the concept of scheduling an agent with the </span><a href="https://code.claude.com/docs/en/scheduled-tasks#run-a-prompt-repeatedly-with-%2Floop"><span>/loop command</span></a><span>. It is basically what JavaScript&#8217;s setTimeout() function would be equivalent to: repeat a task after a given interval until the work is done.</span></p><p><strong><span>By May, running a Ralph loop had become as simple as giving a single command in one of the major agent harnesses. </span></strong><span>It&#8217;s as if AI labs noticed user demand to do more with agentic loops which were hard to set up, and built ways to make it simpler. For instance, in open source agent harnesses like OpenCode, there are plugins like the </span><a href="https://github.com/willytop8/OpenCode-goal-plugin"><span>/goal plugin</span></a><span>. For the minimalist coding agent, Pi, the /goal command can be added </span><a href="https://github.com/Michaelliv/pi-goal"><span>as a package.</span></a></p><h2><span>3. Loops which devs use: triggers and cron jobs</span></h2><p><span>By May, we had access to the /goal primitive. So, what use cases were Boris Cherny and Peter Steinberger referring to in terms of spending most of their time on designing loops, instead of writing prompts? I asked around for examples of &#8220;loop engineering&#8221; from fellow devs. Based on ~210 replies, mostly from X and LinkedIn, it seems that triggers and cron jobs are two very common use cases for loop engineering:</span></p><p><strong><span>Triggers / automations</span></strong><span>: an agent kicks off when an event happens. The event could be an error being logged, a new ticket created, customer support feedback received, etc.</span></p><p><span>Pre-AI, these events were typically triggered by a webhook, and kicked off things like a Slack bot posting in a channel, triggering a system, or being the starting point of a Zapier or an </span><a href="https://n8n.io/"><span>n8n</span></a><span> integration.</span></p><p><strong><span>Cron jobs: </span></strong><span>many devs see &#8220;loop engineering&#8221; as kicking off jobs that involve agents on a cadence. This is fundamentally the same as scheduled </span><a href="https://en.wikipedia.org/wiki/Cron"><span>cron jobs</span></a><span>. From director of engineering, </span><a href="https://www.linkedin.com/in/odedmesser?skipRedirect=true"><span>Oded Messer</span></a><span>:</span></p><blockquote><p><span>&#8220;The idea is that strategic workflows that are repeatable and automatable can be done so with an agent. OK. But if my strategic workflow is automatable then it either becomes tactical if the AI is capable enough or it&#8217;s just a high level old-school-automation I can set up like a cron or a trigger.</span></p><p><span>The name suggests simplicity and repetition. Sometimes it feels like AI enthusiasts forgot automation was a thing before LLMs.&#8221;</span></p></blockquote><h2><span>4. Helpful loops for devs</span></h2><p><span>Below are some workflows with AI agents that run on a regular basis as a /loop command, or when triggered:</span></p><h3><span>Development-related work</span></h3><p><strong><span>Open PRs for newly recorded app issues. </span></strong><span>Software engineer </span><a href="https://x.com/thepanta82/status/2076616844761333792?s=20"><span>Ivan Panti&#263;</span></a><span>:</span></p><blockquote><p><span>&#8220;App encounters a problem and creates a sentry issue. Then:<br />&#8594; Cron tells agent to check sentry and open PRs.<br />&#8594;If there&#8217;s no active PR, agent tackles the issue and creates one<br />&#8594; If PRs aren&#8217;t reviewed, agent pings the devs via slack</span></p><p><span>In this flow, there is only one PR open at a time.&#8221;</span></p></blockquote><p><strong><span>Fix flakey tests. </span></strong><a href="https://www.linkedin.com/in/paul-d-ambra"><span>Paul D&#8217;Ambra</span></a><span>, software engineer at PostHog:</span></p><blockquote><p><span>&#8220;/loop pull the next flakey test from the trunk API. run it to check if it flakes locally, if it does open a PR with the fix... which netted me 13 PRs to stabilise some of our tests.&#8221;</span></p></blockquote><p><strong><span>Triaging issues and outages. </span></strong><span>Software engineer </span><a href="https://x.com/NetMentorTW/status/2076594605659762887?s=20"><span>Ivan Abad:</span></a></p><blockquote><p><span>&#8220;A new alert/exception pops up in a channel. <br />&#8594; The agent investigates the issue<br />&#8594; if it is a code change, implements the change<br />&#8594; creates the PR <br />&#8594; pings the human for review. <br /><br />Same applies for customer tickets or incidents. By the time you get paged and connect to the incident the agent already triaged everything and often located the root cause.&#8221;</span></p></blockquote><p><strong><span>Review design plans. </span></strong><a href="https://x.com/artemnikitin/status/2076671832158011422?s=20"><span>Artem Nikitin</span></a><span>, software engineer at Elastic:</span></p><blockquote><p><span>&#8220;What I&#8217;m finding myself doing often recently is to review design/implementation plans in a loop.</span></p><p><span>Usually, agents only find a few issues during a normal run and then find more on subsequent runs.</span></p><p><span>So I&#8217;m now asking them to run in a loop until they find 0 new major issues.&#8221;</span></p></blockquote><h3><span>Daily/nightly work</span></h3><p><strong><span>Daily product improvements. </span></strong><a href="https://x.com/itsjack/status/2076601937038922085?s=20"><span>Jack D,</span></a><span> founding engineer at Schematic:</span></p><blockquote><p><span>&#8220;We have a loop which reads the logs for the last 24 hours, user feedback and makes PR with fixes - we still review the PRs it makes though!&#8221;</span></p></blockquote><p><strong><span>Nightly end-to-end test run babysitted by an agent. </span></strong><span>Utku K, engineering manager:</span></p><blockquote><p><span>&#8220;nightly e2e runs on the frontend app. When a test fails, an agent investigates first to work out whether it&#8217;s a real regression or a false negative. If it&#8217;s a real bug, the agent attempts a fix, reruns the test, and keeps iterating until it passes or hits a retry cap and escalates... Either way it lands as a PR ready for review by morning.&#8221;</span></p></blockquote><h3><span>More complex development work</span></h3><p><strong><span>Build new telemetry integrations and verify they work</span></strong><span>. </span><a href="https://www.linkedin.com/in/lawrence2jones"><span>Lawrence Jones</span></a><span>, software engineer at Incident.io:</span></p><blockquote><p><span>&#8220;A lot of the AI runbook that we use to build new telemetry integrations uses loops such as executing the query, verifying that it executed correctly and iterating on the query plan/output format/whatever until it is happy with the outcome.&#8221;</span></p></blockquote><p><strong><span>Do a long-running migration, mostly autonomously</span></strong><span>. Startup founder </span><a href="https://x.com/GroundControl/status/2076644702112117067?s=20"><span>Rafel Mendiola</span></a><span>:</span></p><blockquote><p><span>&#8220;Recently, I converted my startup&#8217;s codebase from a regular React app to a React Native app using Expo.</span></p><p><span>There are two ways I could have done it:</span></p></blockquote><ul><li><p><span>In the traditional software engineering style, I could have created a large epic with 50-100 different tickets.
