Next, the input token embedding layer of an LLM maps each of these IDs to a vector of numbers. We usually refer to these entries in that vector as &#8220;features&#8221; (similar to classic ML). The transformer blocks inside the LLM then modify these vectors using attention and feedforward layers. Lastly, the model&#8217;s output layer produces logit scores (converted into probabilities) for the next token.</p><p>The following shows this path in GPT-2 (a relatively classic LLM) and MiniMax-M3 (a more recent LLM released this year; a placeholder for most other recent LLMs). And since they both have the same token ID, irrespective of the position in the input sentence, they would get the same embedding vector from the embedding layer.</p><p>Now, let&#8217;s consider a regular self-attention mechanism with no positional encoding (and no causal mask), where every input token can attend to every other token in the input. In this scenario, swapping any two words, like &#8220;red&#8221; and &#8220;gray&#8221;, would still result in the same embeddings and attention scores between each token pair.</p><p>GPT-style models do use a causal (autoregressive) mask, which restricts each token to itself and earlier tokens. Interestingly, this causal mask gives the computation some implicit order information. In our example, &#8220;jumps&#8221; can attend to &#8220;red&#8221; in the first sentence and &#8220;gray&#8221; in the second. So, a causal LLM can theoretically already distinguish these sentences even without explicit positional embeddings. (We will return to this idea later when discussing the &#8220;NoPE&#8221; concept.)</p><p>Nonetheless, GPT-2 and most newer LLMs include explicit positional information because it gives attention a direct signal about positions. That&#8217;s because even though the causal mask determines which tokens are accessible and provides implicit order information, it doesn&#8217;t distinguish a separation of one position from a separation of ten, for example. So, explicit positional methods are still useful (or even essential), since they supply that information.</p><p>If this all sounded confusing, don&#8217;t worry, it was more meant as an overview, and we will step through these concepts a bit more slowly in the remaining article.</p><h2>2. Adding a position vector to each token embedding</h2><p>We briefly talked about <em>implicit</em> positional information through causal attention masks (and we will revisit this again in more detail later). However, we now switch gears and talk about the <em>explicit</em> ways to add positional information.</p><p>The perhaps simplest and most direct (but not &#8220;cheapest&#8221;) approach is to give each sequence position its own vector. We add that vector to the token embedding, so the resulting, modified embedding vector is then passed to the first transformer block. This exact procedure is discussed in the following subsections.</p><h3>2.1 Learned absolute position embeddings in GPT-2</h3><p>To illustrate the use of an explicit, learned positional vector to the input embeddings, let&#8217;s consider GPT-2 as a concrete example. The code below shows that with an excerpt of a GPT-2 code implementation:</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">class GPTModel(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.tok_emb = nn.Embedding(cfg["vocab_size"], cfg["emb_dim"])
        self.pos_emb = nn.Embedding(cfg["context_length"], cfg["emb_dim"])
        self.drop_emb = nn.Dropout(cfg["drop_rate"])
        
        self.trf_blocks = nn.Sequential(
            *[TransformerBlock(cfg) for _ in range(cfg["n_layers"])])
        
        self.final_norm = LayerNorm(cfg["emb_dim"])
        self.out_head = nn.Linear(
            cfg["emb_dim"], cfg["vocab_size"], bias=False
        )

    def forward(self, in_idx):
        batch_size, seq_len = in_idx.shape
        tok_embeds = self.tok_emb(in_idx)
        pos_embeds = self.pos_emb(torch.arange(seq_len, device=in_idx.device))
        x = tok_embeds + pos_embeds  # Shape [batch_size, num_tokens, emb_size]
        x = self.drop_emb(x)
        x = self.trf_blocks(x)
        x = self.final_norm(x)
        logits = self.out_head(x)
        return logits</code></pre></div><p>And in mathematical terms, we can write it as follows. Let <em>m</em> be a position index and <em>x<sub>m</sub></em> the token ID at that position. This means it only works with inputs with 1024 or fewer tokens. If we want to extend the context window, we would have to extend this embedding table. And since the embedding table (layer) is updated like any other layer during training, the context length would have to be decided before the training starts.</p><p>Extending the context would be very expensive since the table can become very large. For example, in the case of GPT-2 Medium, the positional embedding layer weights only make up 0.30% of the total weights at 1,024 positions. Encoding relative position with RoPE</h2><p>So, the sinusoidal method above is still considered an absolute positional encoding because the vector added to each token embedding represents that token&#8217;s position counted from the start of the sequence.</p><p>As shown in the previous figure, for example, tokens at positions 2 and 5 receive the position vectors <em>P<sub>2</sub></em> and <em>P<sub>5</sub></em>. But each token gets a different position vector because its absolute position <em>m</em> has changed.</p><p>So their attention score can change even when the token embeddings stay the same. The sinusoidal structure still gives the model a way to learn relative relationships.</p><p>Anyways, RoPE, which we will discuss below, builds this relative relationship directly into the attention calculation. RoPE, which <a href="https://arxiv.org/abs/2104.09864">Su et al. introduced in the 2021 RoFormer paper</a>, stands for Rotary Position Embedding and is considered a relative position method.</p><h3>3.1 Moving the rotation inside attention in RoPE</h3><p>In attention, each token&#8217;s current representation is projected into a query, a key, and a value vector. Computing rotation frequencies in RoPE?</h2><p>A full attention head uses multiple frequencies so that some feature pairs change more drastically (&#8221;quickly&#8221; in RoPE terms) with position and others change more gradually (&#8221;slowly&#8221; in RoPE terms). This serves the same purpose as the multiple frequencies in the original transformer&#8217;s sinusoidal encodings.</p><p>However, instead of us assigning these manually, for a head with <em>d</em> features, standard full RoPE computes one frequency for each of its <em>d</em>/2 pairs as follows:</p><div class="captioned-image-container"><figure><div class="image-link image2"><div class="image2-inset"><source type="image/webp" /><img alt="Equation 14: \theta_i=b^{-2i/d}." class="sizing-normal" height="55" src="https://substackcdn.com/image/fetch/$s_!UFXx!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Febff1490-d57b-4eb3-a837-0a3426a18f0c_2240x84.png" title="Equation 14: \theta_i=b^{-2i/d}." width="1456" /><div></div></div></div></figure></div><p>Here,</p><ul><li><p><em>d</em> is the head dimension (it has to be even so that all features can be arranged in pairs).</p></li><li><p><em>i</em> is the index of the pair; it ranges from 0 to <em>d</em>/2&#8722;1.</p></li><li><p><em>b</em> is a chosen base value (hyperparameter) that determines the spacing of the frequencies.</p></li><li><p><em>&#952;<sub>i</sub></em> is pair <em>i</em>&#8216;s frequency in radians per token position.</p></li></ul><p>The original <a href="https://arxiv.org/html/2104.09864v5#S3.SS3">RoFormer paper</a> uses <em>b</em> = 10,000, borrowing the original transformer&#8217;s frequency formula with head dimension <em>d</em> in place of embedding width <em>d</em><sub>model</sub>.</p><p>For example, with head dimension <em>d</em> = 8 and base <em>b</em> = 10,000, we get frequencies [1, 0.1, 0.01, 0.001] radians per position.</p><h2>5. Figure 27 shows the rotation angle for each pair and the corresponding entries in the two tables.</p><div class="captioned-image-container"><figure><div class="image-link image2"><div class="image2-inset"><source type="image/webp" /><img alt="Figure 27 &#8212; cos sin tables" class="sizing-normal" height="228.5054945054945" src="https://substackcdn.com/image/fetch/$s_!1YrR!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F871d5113-e3f8-407b-9747-5051495fa9d3_2676x1033.png" title="Figure 27 &#8212; cos sin tables" width="592" /><div></div></div></div><figcaption class="image-caption">Figure 27: <em>The</em> two tables returned by <em>rope_params</em> for token position 2. <em>The</em> highlighted column gives the cosine and sine used to rotate the first feature pair, <em>(1, 5)</em>.</figcaption></figure></div><p>In short, <code>rope_params</code> computes the cosine and sine of each rotation angle, which depends on the token&#8217;s position and the feature pair&#8217;s frequency.</p><p>In a real-world scenario, if we pass <code>rope_params</code> 1,024 token positions for a context size of 1024, and a head dimension of 128, it returns two tensors, <code>cos</code> and <code>sin</code>, each with shape <code>(1024, 64)</code> since a head with 128 features has 64 pairs.</p><p>The tables have no batch or head dimension, and we broadcast each <code>(1024, 64)</code> table across the batch and head dimensions. So, if we have multi-head attention or grouped query attention with 32 heads, feature pair 0 at token position 2 uses the same rotation angle in all 32 heads. Each head rotates its own feature values, so the rotated queries can still differ across heads. Also, the same entries can be reused across queries, keys, and heads that use the same positions and frequencies. In short, we only need to (pre)compute these tables once per model for all positions up to a maximum supported context size.</p><p>Technically, it would also be possible to store these tables alongside the model weights; but they are so incredibly cheap to compute that storing them on disk would be overkill.</p><p>Next, <code>rope_split_half</code> uses those cosines and sines to rotate the actual features in the query and key vectors inside attention.</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">def rope_split_half(x, cos, sin):
    first, second = x.float().chunk(2, dim=-1)
    return torch.cat((
        first * cos - second * sin,
        first * sin + second * cos,
    ), dim=-1).to(x.dtype)</code></pre></div><p>Considering the simple 8-feature example once more, the <code>.chunk</code> in the code snippet above splits the query into <code>[1, 2, 3, 4]</code> and <code>[5, 6, 7, 8]</code> and lines up the two entries in each pair. For example, the first slot of each half gives us <code>(1, 5)</code>, the second <code>(2, 6)</code>, and so on. The two expressions inside <code>torch.cat</code> compute the rotated halves using the equations from Section 3.3:</p><div class="captioned-image-container"><figure><div class="image-link image2"><div class="image2-inset"><source type="image/webp" /><img alt="Equation 19: \begin{aligned} a_i' &amp;= a_i\cos(m\theta_i) - b_i\sin(m\theta_i), \\ b_i' &amp;= a_i\sin(m\theta_i) + b_i\cos(m\theta_i). \end{aligned}" class="sizing-normal" height="101" src="https://substackcdn.com/image/fetch/$s_!cIqH!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fbcf9b781-1fac-40b7-83e7-54f6c36e3fec_2240x155.png" title="Equation 19: \begin{aligned} a_i' &amp;= a_i\cos(m\theta_i) - b_i\sin(m\theta_i), \\ b_i' &amp;= a_i\sin(m\theta_i) + b_i\cos(m\theta_i). \end{aligned}" width="1456" /><div></div></div></div></figure></div><p>Note that here, everything denoted with <em>a<sub>i</sub></em> corresponds to the first half of the query, and everything denoted with <em>b<sub>i</sub></em> comes from the second half. The first expression inside <code>torch.cat</code> computes all the <em>a<sub>i</sub>&#8242;</em>values, and the second computes all the <em>b<sub>i</sub>&#8242;</em> values.</p><p>Then, we concatenate the halves, which puts each value back in its original index position via <code>torch.cat</code>.</p><p>Here&#8217;s the code that produces the rotated query in the earlier Figure 26. The shown reshape <code>(1, 1, 1, 8)</code> just brings the simple toy array into the expected format: one batch item, one head, one token, and eight features.</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">positions = torch.tensor([2])

q_rot = rope_split_half(q, cos, sin)
print(q_rot[0, 0, 0])</code></pre></div><p>With several positions, each token simply picks up its own row from the <code>cos</code> and <code>sin</code> tables. Through broadcasting, PyTorch reuses these same tables across all batch items and attention heads.</p><h3>5.2 Using RoPE inside causal attention</h3><p>So far, we coded the RoPE utility functions. Let&#8217;s now use it in the real context, the attention mechanism. Here, we use the standard frequency schedule for two 8-feature heads and four token positions. We use random query, key, and value tensors to keep the example self-contained, but as mentioned before, you can optionally also check the end-to-end <a href="https://github.com/rasbt/LLMs-from-scratch/blob/main/ch05/11_qwen3/standalone-qwen3.ipynb">Qwen3 from-scratch implementation</a> with real query, key, and values produced by the pre-trained model.</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">torch.manual_seed(123)

k = torch.randn(1, 2, 4, 8)
v = torch.randn(1, 2, 4, 8)

cos, sin = rope_params(8, positions)
q_rot = rope_split_half(q, cos, sin)
k_rot = rope_split_half(k, cos, sin)
scores = q_rot @ k_rot.transpose(-2, -1) / q.shape[-1] ** 0.5

future_mask = positions[None, :] &gt; positions[:, None]
masked_scores = scores.masked_fill(future_mask, -torch.inf)
weights = torch.softmax(masked_scores, dim=-1)
context = weights @ v</code></pre></div><p>Note that only <code>q</code> and <code>k</code> but not <code>v</code> pass through RoPE. The resulting raw attention scores are stored in a tensor of shape <code>(1, 2, 4, 4)</code>, that is, one row for each query position, and a column for each key position, and 4x4 since we have four tokens where each attends to each other.</p><p>Then, using a conventional attention code implementation, the causal mask replaces the scores for future keys with negative infinity, so they get zeroed after the softmax. The resulting <code>context</code> tensor has shape <code>(1, 2, 4, 8)</code>; the 4 because we have four tokens, and the 8 because the embedding dimension was originally 8.</p><p>We can also check that our claim about relative offsets holds, meaning that adding 3 to each position should change the position but preserve the query-key offsets:</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">cos_shifted, sin_shifted = rope_params(8, positions + 3)
q_shifted = rope_split_half(q, cos_shifted, sin_shifted)
k_shifted = rope_split_half(k, cos_shifted, sin_shifted)
scores_shifted = (
    q_shifted @ k_shifted.transpose(-2, -1) / q.shape[-1] ** 0.5
)
torch.testing.assert_close(scores, scores_shifted) 
# Should return True</code></pre></div><h3>5.3 An alternative feature-pairing convention</h3><p>I mentioned the <em>split-halves</em> convention many times throughout this article. The <a href="https://arxiv.org/abs/2104.09864">original RoPE paper</a> uses the alternative <em>interleaved</em> convention, as does the <a href="https://github.com/meta-llama/llama/blob/llama_v1/llama/model.py">original LLaMA implementation</a> (but as mentioned before, most code implementations now use the split-halves, because it makes it easier, in code, to rotate all pairs at once with element-wise sine and cosine operations.)</p><p>To illustrate the difference between the two layouts, Figure 28 below uses the same 8-feature vector in both rows.</p><div class="captioned-image-container"><figure><div class="image-link image2"><div class="image2-inset"><source type="image/webp" /><img alt="Figure 28 &#8212; feature pairing" class="sizing-normal" height="181.94642857142858" src="https://substackcdn.com/image/fetch/$s_!pSrd!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F376d895d-ffc0-41ec-8cf5-5e84834412fc_2641x804.png" title="Figure 28 &#8212; feature pairing" width="598" /><div></div></div></div><figcaption class="image-caption">Figure 28: Split-half pairs each feature in the first half with the corresponding feature in the second half. Interleaved pairs adjacent features.</figcaption></figure></div><p>The interleaved implementation uses the same two equations, but selects alternating features and interleaves the outputs.</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">def rope_interleaved(x, cos, sin):
    even, odd = x.float()[..., 0::2], x.float()[..., 1::2]
    return torch.stack((
        even * cos - odd * sin,
        even * sin + odd * cos,
    ), dim=-1).flatten(-2).to(x.dtype)</code></pre></div><p>But mathematically, the layouts are equivalent when we account for the feature order. So, rearranging the entries <code>[1, 2, 3, 4, 5, 6, 7, 8]</code> to <code>[1, 5, 2, 6, 3, 7, 4, 8]</code> makes the split-half pairs adjacent with pairs (1, 5), (2, 6), and so on. If we apply the same rearrangement to both queries and keys, it results in identical dot products.</p><div class="highlighted_code_block"><pre class="shiki"><code class="language-python">order = torch.tensor([0, 4, 1, 5, 2, 6, 3, 7], device=q.device)
q_rot_interleaved = rope_interleaved(q[..., order], cos, sin)
k_rot_interleaved = rope_interleaved(k[..., order], cos, sin)
scores_interleaved = (
    q_rot_interleaved @ k_rot_interleaved.transpose(-2, -1)
    / q.shape[-1] ** 0.5
)

torch.testing.assert_close(q_rot[..., order], q_rot_interleaved)
torch.testing.assert_close(k_rot[..., order], k_rot_interleaved)
torch.testing.assert_close(scores, scores_interleaved)
# This should all return True</code></pre></div><p>The outputs retain the reordered features, so we compare them with the split-half outputs in that same order. Applying the two layouts to the original vector however would give different scores.</p><h2>6. Positional choices in modern architectures</h2><p>RoPE has been a staple in most (open-weight) LLMs since the <a href="https://scontent.fcps4-2.fna.fbcdn.net/v/t39.2365-6/333007794_1182140292435357_4481174526219500228_n.pdf?_nc_cat=101&amp;_nc_map=urlgen_bucketless&amp;ccb=1-7&amp;_nc_sid=3c67a6&amp;_nc_ohc=SrzHHMeB_5gQ7kNvwGdTCab&amp;_nc_oc=AdonSC2oKCA4Qqs-KfR7_70m4s4_1QpPwBxDyuqu_KXyCswnUioaZNf1qyZckeLl6qPZge_29DAoPzzJbtkmdFP2&amp;_nc_zt=14&amp;_nc_ht=scontent.fcps4-2.fna&amp;_nc_gid=aOwcXBC5dn_BAgAvPaHuBA&amp;_nc_ss=7b289&amp;oh=00_AQR_JQr4O14JgKxukyTSvBG_TEEoi37pQAo0flfY68Vquw&amp;oe=6AFEA511">original LLaMA model</a>. Of course, proprietary models may use it as well, but it&#8217;s always hard to say anything with 100% certainty about proprietary models.</p><p>However, in recent years, many architectures have been moving away from full-blown RoPE in every transformer block. In the following subsection, we will discuss some of these variants.</p><p>For instance the full RoPE implementation we discussed and implemented in the sections above rotates <em>every</em> feature pair in <em>every</em> query and key head.</p><p>In the following examples in the subsections above below, we will see that models only rotate some features within a head, other models skip RoPE in some transformer blocks, and some models use a different approach and add position information directly to their attention scores.</p><h3>6.1 Partial RoPE</h3><p>As discussed throughout the article, regular &#8220;full&#8221; RoPE rotates all dimensions in each query and key head. Partial RoPE is a variant that rotates only a subset, while leaving the remaining dimensions unchanged.</p><p>For example, <a href="https://huggingface.co/MiniMaxAI/MiniMax-M3/blob/main/config.json">MiniMax-M3&#8217;s configuration</a> uses 64 rotary dimensions within each 128-dimensional head. The researchers of the NoPE paper trained a tiny 107M-parameter decoder-only transformers from scratch on tasks such as copying, sorting, and addition to do some ablation.</p><p>When they tested the small model on examples longer than those seen during training, interestingly, NoPE ranked first overall across the ten tasks and ahead of RoPE. The researchers behind the <a href="https://arxiv.org/html/2305.19466v2">NoPE paper</a> also conducted a separate experiment with a larger 1.3B-parameter models trained on code. Here, NoPE also handled contexts beyond the training length, however, its next-token predictions got worse at the longest lengths tested. </p><p>Some of today&#8217;s open-weight LLMs even go so far and use NoPE in all layers. However, nowadays, it&#8217;s more common for models to omit RoPE in at least some layers, where layer here means transformer block. </p><p>To give a concrete example, <a href="https://huggingface.co/blog/smollm3#architecture-and-training-details">SmolLM3</a> (3B parameters) applies RoPE in three layers and skips it in the fourth, repeating that pattern through 36 layers. Interestingly, the SmolLM3 authors mentioned that this layer pattern improved long-context performance.</p><p>(Also note that any later layer, following the first one, even though it may skip the rotation, still receives the inputs from preceding transformer blocks, so its queries and keys still receive some sort of position information from earlier layers.)</p><p></p><div class="captioned-image-container"><figure><a class="image-link image2 is-viewable-img" href="https://substackcdn.com/image/fetch/$s_!iLab!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F26b1e107-4221-4ca8-a579-ac2603366c99_2804x1737.png" target="_blank"><div class="image2-inset"><source type="image/webp" /><img alt="Figure 32 &#8212; Final thoughts</h2><p>So, to recap, we discussed GPT-2 and the original transformer that add a position vector to each token embedding before the first transformer block. Then, modern LLMs switched to RoPE, which encodes relative position inside attention by rotating queries and keys. Surprisingly, RoPE remains as the most popular positional embedding method today.</p><p>Recently, however, Inkling picked up an idea from T5 to add a learned relative position bias to the attention scores before softmax. And then we also have NoPE-RoPE architectures, which omit RoPE in some layers.</p><p>It may be boring news, but as mentioned before, RoPE is still the predominant position embedding method, and I think this will carry over into 2027 for sure. Perhaps, though, we&#8217;ll see more architectures with an Inkling-like design coming up in 2027.</p><p>While this may sound &#8220;boring&#8221;, I am glad that I finally got this article on RoPE (and other position info methods) out, after so many years, so that I can add it to my collection of LLM &#8220;fundamentals&#8221; explainers.</p><p>If you are interested in the other architecture building blocks of LLMs, I still highly recommend starting with a GPT-2-style model, which will give you a solid understanding of the building blocks with the least amount of friction.
