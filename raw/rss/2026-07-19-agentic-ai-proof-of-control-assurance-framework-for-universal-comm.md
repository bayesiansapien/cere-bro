The purpose is to specify what must be provable for UCP-enabled agentic commerce to be defensible in enterprise, regulated, insured, and high-value transaction environments.</p><h2>Executive Summary</h2><p>The Universal Commerce Protocol (UCP) is an open, capability-negotiation protocol for agentic commerce. It gives AI agents, apps, search surfaces, procurement systems, merchants, and payment providers a shared way to discover what each party supports; negotiate compatible services, capabilities, extensions, schemas, payment handlers, and transports; and carry a transaction from product discovery and cart building through checkout, identity linking, orders, and post-purchase events.</p><p>UCP matters because agentic commerce is a many-to-many coordination problem, not merely a checkout button. A common, extensible protocol can replace bespoke integrations, preserve merchant-controlled rules and merchant-of-record responsibilities, and allow diverse agents and businesses to interoperate without forcing commerce into one platform's proprietary workflow. As argued in <a href="https://kenhuangus.substack.com/p/googles-ucp-just-won-agentic-commerce">my April 2026 Substack analysis</a>, UCP's broad governance coalition and full-lifecycle design make it a plausible shared coordination layer for the emerging agentic-commerce ecosystem.</p><p>Since UCP's launch, the ecosystem has moved from launch specification toward broader implementation: Shopify now documents self-serve developer access to UCP and Catalog surfaces spanning products from millions of merchants, and protocol governance and technical participation have expanded. This is an implementation and ecosystem milestone, not a new tagged protocol version: v2026-04-08 remains the latest tag, while newer security and capability work resides on main.</p><p>UCP therefore changes the trust boundary in ecommerce. In a traditional web checkout, the buyer directly interacts with a merchant-controlled UI. In UCP-enabled commerce, an AI agent may discover products, build a cart, negotiate checkout state, transmit signals, select a payment handler, submit payment credentials, or receive order events on the buyer's behalf.</p><p>Openness and interoperability, however, do not by themselves establish trust. A protocol can be open while the evidence needed to evaluate an agent's authority, a merchant's advertised state, or a payment decision remains controlled by one platform. Independent and open verification is therefore essential: auditors, regulators, insurers, counterparties, and users should be able to validate portable evidence using public schemas and verification rules, without relying on the vendor that executed the transaction or on inaccessible proprietary telemetry. That requires cryptographically bound identities and mandates, signed and content-digested messages, preserved negotiation and checkout state, tamper-evident event histories, and reproducible policy checks. The result is not the elimination of risk; it is a reduction in unilateral trust and a defensible basis for accountability, dispute resolution, and cross-platform governance.</p><p>That creates the central institutional governance question:</p><p><strong>Can every material UCP commerce action be independently proven to have been authorized, constrained, executed, and recorded according to the active business profile, platform profile, negotiated capability set, payment handler, identity scope, checkout state, and user mandate?</strong></p><p>The Proof-of-Control answer is to shift assurance from platform promises and after-the-fact audit reconstruction to independently verifiable evidence generated at the moment of action. That evidence can include HTTP Message Signatures, content digests, JWK key discovery, idempotency keys, signed negotiation transcripts, Merkle-anchored event logs, runtime attestation, formal verification, AP2 mandates, HSM-backed signing, and privacy-preserving compliance proofs.</p><p>UCP already includes several important security primitives. This framework turns those primitives into an institutional assurance profile.</p><p>Figure 1 illustrates the new trust boundary. The agent may coordinate the transaction, but an independent verifier must be able to reconstruct authority and state without trusting the agent's own account of events.</p><div as the root of capability and key discovery.</p><p>Business profiles are hosted at:</p><p>/.well-known/ucp</p><p>Platform profiles are advertised per request through the <code>UCP-Agent</code> header:</p><p>UCP-Agent: profile="https://platform.example/.well-known/ucp"</p><p>Profiles contain:</p><ul><li><p><code>ucp.version</code></p></li><li><p><code>ucp.services</code></p></li><li><p><code>ucp.capabilities</code></p></li><li><p><code>ucp.payment_handlers</code></p></li><li><p>optional <code>ucp.supported_versions</code> for business profiles</p></li><li><p><code>keys[]</code> in JWK format</p></li></ul><p>Proof-of-Control implication: the profile is the first evidence object in a UCP session. A high-assurance deployment should preserve a signed or hash-pinned snapshot of the business profile and platform profile used for each commerce session.</p><h3>1.3 Profile Requirements and Fetch Controls</h3><p>UCP requires profiles to be reliably hosted over HTTPS. Profile endpoints must not use redirects. Implementations must reject non-HTTPS profile URLs and must not follow profile-fetch redirects.</p><p>UCP also recognizes that dynamic profile discovery creates operational risk. Implementations should use bounded profile caches, rate limits, negative caching, and asynchronous discovery where appropriate.</p><p>Proof-of-Control implication: profile fetching is both a discovery function and a security boundary. The fetch event, validation result, cache key, profile hash, and selected signing key should be recorded.</p><h3>1.4 Services, Capabilities, and Extensions</h3><p>UCP organizes commerce features into services and capabilities.</p><p>Important UCP capabilities include:</p><ul><li><p><code>dev.ucp.shopping.catalog.search</code></p></li><li><p><code>dev.ucp.shopping.catalog.lookup</code></p></li><li><p><code>dev.ucp.shopping.cart</code></p></li><li><p><code>dev.ucp.shopping.checkout</code></p></li><li><p><code>dev.ucp.shopping.order</code></p></li><li><p><code>dev.ucp.common.identity_linking</code></p></li></ul><p>Important UCP extensions include:</p><ul><li><p><code>dev.ucp.shopping.fulfillment</code></p></li><li><p><code>dev.ucp.shopping.discount</code></p></li><li><p><code>dev.ucp.shopping.buyer_consent</code></p></li><li><p><code>dev.ucp.shopping.ap2_mandate</code></p></li></ul><p>Extensions compose onto parent capabilities through <code>extends</code> and JSON Schema composition. UCP prunes orphaned extensions if the parent capability is not in the negotiated intersection.</p><p>Proof-of-Control implication: a UCP session needs a signed negotiation transcript recording which service, capability, extension, version, schema, and transport were active.</p><p>Figure 2 shows why UCP is a negotiation protocol rather than a single checkout API. capabilities and services:</p><p>{reverse-domain}.{service}.{capability}</p><p>Examples:</p><ul><li><p><code>dev.ucp.shopping.checkout</code></p></li><li><p><code>dev.ucp.common.identity_linking</code></p></li><li><p><code>com.example.payments.installments</code></p></li></ul><p>A capability must declare a schema URL; services and payment handlers declare one when their transport or handler defines it. The schema URL is the authority anchor: its HTTPS host must match the reverse-domain namespace authority, and platforms must validate that binding before fetching it and must not follow redirects. A spec URL is optional, must use HTTPS when present, and may be hosted outside the namespace authority because it is documentation rather than the fetched validation artifact.</p><p>Proof-of-Control implication: schema-authority validation, safe fetch controls, and the hash of each fetched schema should be explicit evidence events. Record spec URLs for traceability, but do not mischaracterize their origin as a UCP trust anchor.</p><h3>1.6 Versioning</h3><p>UCP uses date-based protocol versions in <code>YYYY-MM-DD</code> format. Public profiles must not advertise non-date versions such as <code>draft</code>. Businesses that support older versions should use <code>supported_versions</code> to map each supported version to a complete version-specific profile. Version-specific profiles are leaf documents and must not contain <code>supported_versions</code>.</p><p>Proof-of-Control implication: protocol version, capability version, extension version, and schema hash should be bound into the session evidence bundle.</p><h3>1.7 Transport Bindings</h3><p>UCP supports multiple transports:</p><ul><li><p>REST using OpenAPI</p></li><li><p>MCP using OpenRPC over streamable HTTP</p></li><li><p>A2A through Agent Card style integration</p></li><li><p>Embedded protocol using OpenRPC</p></li></ul><p>Proof-of-Control implication: the selected transport changes the evidence surface. REST and MCP over HTTP can use the same HTTP Message Signature foundation. Embedded and A2A flows require equivalent evidence binding for handoff, message origin, and session state.</p><h3>1.8 HTTP Message Signatures</h3><p>UCP defines HTTP Message Signatures using RFC 9421 for HTTP-based transports. The shared foundation includes:</p><ul><li><p><code>Signature-Input</code></p></li><li><p><code>Signature</code></p></li><li><p><code>Content-Digest</code></p></li><li><p>ES256 required for verification</p></li><li><p>ES384 and Ed25519 optional; unsupported algorithms are skipped per signature resolution</p></li><li><p>JWK public keys in profile <code>keys[]</code></p></li><li><p><code>Content-Digest</code> over raw body bytes</p></li><li><p>idempotency keys for replay protection at the business layer</p></li></ul><p>UCP states that platforms should sign requests when using HTTP Message Signatures, while alternative authentication such as OAuth, API keys, or mTLS may be used. Webhook notifications must be signed. Optional Web Bot Auth interoperability adds Signature-Agent-based key resolution and stricter signature parameters without replacing the baseline UCP-Agent path.</p><p>Proof-of-Control implication: institutional deployments should make signatures mandatory for every state-changing UCP action and should preserve verification results.</p><h3>1.9 Catalog</h3><p>UCP catalog capabilities support product discovery through search and lookup. Catalog operations can use product and variant IDs that later appear in checkout <code>line_items[].item.id</code>. UCP distinguishes catalog context from final checkout enforcement: catalog responses can be context-sensitive and should not be treated as the final authority for eligibility, tax, fulfillment, or payment.</p><p>Proof-of-Control implication: product, price, inventory, and variant data used by agents should be signed or hash-anchored at ingestion and retrieval time.</p><h3>1.10 Cart</h3><p>UCP cart supports pre-checkout basket building. A cart may be converted into a checkout by providing <code>cart_id</code> in a Create Checkout request. When checkout is initialized by <code>cart_id</code>, the business must use cart contents and ignore overlapping fields in the checkout payload. If an incomplete checkout already exists for the cart, the business must return the existing checkout session rather than create a new one.</p><p>Proof-of-Control implication: cart-to-checkout binding is a critical evidence point. The cart snapshot, checkout ID, and idempotency key should be linked.</p><h3>1.11 Checkout</h3><p>The Checkout capability is the central UCP transaction primitive. UCP states that checkout must be finalized manually by the user through a trusted UI unless the AP2 Mandates extension is supported.</p><p>Checkout statuses include:</p><ul><li><p><code>incomplete</code></p></li><li><p><code>requires_escalation</code></p></li><li><p><code>ready_for_complete</code></p></li><li><p><code>complete_in_progress</code></p></li><li><p><code>completed</code></p></li><li><p><code>canceled</code></p></li></ul><p>When status is <code>requires_escalation</code>, the business must provide <code>continue_url</code>. The platform must use <code>continue_url</code> when checkout status is <code>requires_escalation</code>. Businesses must include at least one message with severity <code>requires_buyer_input</code> or <code>requires_buyer_review</code> when returning <code>requires_escalation</code>. After checkout reaches <code>completed</code>, it is considered immutable.</p><p>Proof-of-Control implication: checkout state must be treated as a formal state machine. Any bypass of <code>requires_escalation</code> is a control failure.</p><h3>1.12 Payment Handlers</h3><p>UCP payment handlers are specifications, not entities. They define how payment instruments are acquired and processed. Businesses and platforms advertise handlers and <code>available_instruments</code>; the checkout response provides runtime handler configuration. UCP states that the <code>available_instruments</code> in the checkout response is authoritative for that checkout. Platforms must not use instrument types or constraints that contradict it.</p><p>The payment-handler guide also notes that available<em>instruments is optional. When absent, the handler places no restrictions on instrument types and supports the full set defined by its handler schema. A checkout submission must contain exactly one instrument unless dev.ucp.shopping.split</em>payments is active; when active, the business-defined allowed combinations and atomic failure/reversal rules apply.</p><p>Payment-handler specifications should define binding, credential types, expiration, common failures, and processing rules. Binding means a cryptographic or logical association between a payment instrument, a specific checkout transaction, and business identity.</p><p>Proof-of-Control implication: high-assurance deployments should require explicit instrument constraints, credential binding, expiration, and signed handler provenance.</p><h3>1.13 Identity Linking</h3><p>UCP identity linking uses OAuth 2.0 authorization code flow with PKCE as the baseline and lets a platform obtain authorization to act for a user at a business. Businesses declare UCP scopes in config.scopes under dev.ucp.common.identity_linking. The current main branch also allows businesses to advertise trusted external identity providers and accept short-lived, single-use JWT authorization grants; the business must validate issuer, exact audience, signature, expiry, required claims, and jti replay state before issuing its own access token.</p><p>Important identity-linking controls include:</p><ul><li><p>PKCE with <code>S256</code></p></li><li><p>issuer (<code>iss</code>) validation to prevent mix-up attacks</p></li><li><p>exact <code>redirect_uri</code> matching</p></li><li><p><code>WWW-Authenticate: Bearer</code> challenges</p></li><li><p><code>identity_required</code> and <code>insufficient_scope</code> handling</p></li><li><p>token revocation</p></li><li><p>scope derivation from negotiated capabilities</p></li><li><p>user identity tokens in the <code>Authorization: Bearer</code> header</p></li></ul><p>Proof-of-Control implication: scope derivation, consent, token validation, revocation, and operation-to-scope mapping should be auditable.</p><h3>1.14 Signals</h3><p>UCP signals support fraud prevention, risk assessment, authorization, and abuse prevention. Signal values must not be buyer-asserted claims. Platforms provide signals based on direct observation or by relaying independently verifiable third-party attestations.</p><p>Proof-of-Control implication: signals should be minimized, provenance-bound, and retention-controlled. Third-party signal attestations should be signed.</p><h3>1.15 Attribution</h3><p>UCP attribution is informational and optionally provided by the platform. UCP does not prescribe attribution models, windows, or assignment logic. The field must not affect negotiation.</p><p>Proof-of-Control implication: attribution data may be useful for analytics, but it should not be treated as authorization evidence without additional controls.</p><h3>1.16 Buyer Consent</h3><p>The Buyer Consent extension now supports cart and checkout and models consent as reverse-domain purposes with optional, more-specific segments. Businesses advertise the complete supported option set and current source/value; platforms must use the advertised labels and content when presenting choices and must not invent unsupported purposes. The protocol communicates consent state and blocks checkout completion when confirmed choices have unmet data dependencies, but downstream data-use, retention, sharing, and deletion enforcement remains a separate business-policy obligation.</p><p>Proof-of-Control implication: consent transport must be linked to separate policy enforcement evidence for data use, retention, sharing, and deletion.</p><h3>1.17 AP2 Mandates</h3><p>The AP2 Mandates extension, <code>dev.ucp.shopping.ap2_mandate</code>, adds cryptographic mandate support for autonomous commerce.</p><p>When the AP2 extension is negotiated:</p><ul><li><p>The business must include <code>ap2.merchant_authorization</code> in checkout responses.</p></li><li><p>The platform must verify the business signature before presenting terms.</p></li><li><p>The business must not accept <code>complete_checkout</code> without <code>ap2.checkout_mandate</code>.</p></li><li><p>Mandates are SD-JWT credentials with key binding.</p></li><li><p>Two mandate artifacts are required: a checkout mandate and a payment mandate.</p></li><li><p>The checkout mandate is placed at <code>ap2.checkout_mandate</code>.</p></li><li><p>The payment mandate is placed in <code>payment.instruments[*].credential.token</code>.</p></li><li><p>AP2 uses JSON Canonicalization Scheme (JCS) for durable signature artifacts.</p></li></ul><p>Proof-of-Control implication: AP2 is the UCP-native path for non-repudiable autonomous commerce. Autonomous completion without AP2 or trusted deterministic UI should be treated as high risk.</p><h3>1.18 Order Events</h3><p>The Order capability allows businesses to push order lifecycle updates to platforms through webhooks. Webhook payloads must be signed. The platform must verify that the signer is authorized to send events for the referenced order by matching the signer profile to the order's business.</p><p>UCP order events send the full order entity, not only deltas.</p><p>Proof-of-Control implication: signed order events should be anchored into an append-only event stream linked to the originating checkout and business profile.</p><h3>1.19 Current Maturity and Post-Release Changes</h3><p>The latest tagged protocol release remains v2026-04-08. The reviewed main branch at cc3608a is 65 commits ahead of the document's previous May 6 baseline and contains material work that is not yet represented by a newer tag. Production deployments should pin the protocol and capability versions they implement, validate the advertised schemas for that version, and treat main-branch additions as pre-release until formally tagged.</p><ul><li><p>Profile and transport security: the canonical public-key field is now top-level keys[] (an RFC 7517 JWK Set). Every verifier must support ES256; Ed25519 is optional. A request may opt into Web Bot Auth interoperability with Signature-Agent, additional covered components, key-thumbprint binding, and created/expires parameters. Default UCP key resolution through UCP-Agent remains supported.</p></li><li><p>Identity linking: direct OAuth 2.0 with PKCE remains the baseline. Main also specifies an accelerated identity-provider flow using short-lived, single-use JWT authorization grants, exact audience binding, jti replay prevention, and business-issued access tokens; raw upstream identity-provider tokens must not be relayed directly to a business.</p></li><li><p>Buyer consent: the extension now decorates cart and checkout, supports reverse-domain purposes and nested segments, makes the business-advertised option set authoritative, and blocks completion when a confirmed choice has unmet data dependencies. It still does not by itself prove downstream policy enforcement.</p></li><li><p>Loyalty: dev.ucp.common.loyalty can decorate catalog, cart, and checkout to expose memberships, tiers, benefits, and rewards. Redeemable balances and stored value remain the responsibility of payment instruments or a future redemption capability.</p></li><li><p>Split payments: dev.ucp.shopping.split_payments permits multiple instruments only when negotiated. Businesses advertise allowed combinations; submissions are ordered by allocation priority, and failed partial processing must be reversed so an incomplete split does not leave the buyer charged.</p></li><li><p>Shopping permalinks: dev.ucp.shopping.permalink defines a browser-addressable GET intent that initializes shopping state and resolves through a 303 redirect. Loading a permalink is never authorization to place an order, charge payment, or complete checkout; continue_to and field-path inputs require strict server-side validation.</p></li><li><p>Industry expansion and governance: the public project now identifies co-development groups for shopping, lodging, and food, while the roadmap describes food and lodging specifications as work in progress. Stripe joined the Governing Council, and Amazon, Meta, Microsoft, Salesforce, and Stripe representatives joined the expanded Technical Committee.</p></li></ul><p>Shopify's current developer implementation is self-serve: developers register an agent profile and use UCP-compliant MCP endpoints for discovery, cart, checkout, and order flows. Shopify describes Catalog API as exposing billions of products from millions of merchants, but authority is tiered. Anonymous and signed agents cannot call complete_checkout or order tools; those actions require token-tier authorization and the relevant scopes. The merchant remains the merchant of record.</p><p>Proof-of-Control implication: evidence bundles must record whether a behavior came from a tagged protocol release, an advertised version-specific profile, an unreleased main-branch capability, or a Shopify-specific implementation policy. Conformance to UCP does not imply entitlement to every platform's highest-trust operation.</p><p>Related 2026 research reinforces the control boundary used here. The IMF separates probabilistic intent and orchestration from deterministic authorization/control and settlement. Strabo shows that UCP checkout interactions can be represented as a formal declarative protocol while retaining interoperability. Separate AP2 runtime analysis argues that signatures and expiry alone are insufficient under retries and concurrency without explicit context binding and consume-once enforcement. These are research findings and analytical frameworks, not normative UCP requirements.</p><h2>Section 2: The UCP Provability/Verifiability Gap</h2><p>UCP defines protocol interoperability and includes several important security mechanisms. However, institutional adoption requires stronger evidence requirements than baseline protocol conformance.</p><h3>2.1 What UCP Already Provides</h3><p>UCP already provides:</p><ul><li><p>Machine-readable business and platform profiles.</p></li><li><p>JWK key discovery through profiles.</p></li><li><p>RFC 9421 HTTP Message Signatures for HTTP-based transports.</p></li><li><p><code>Content-Digest</code> over raw body bytes.</p></li><li><p>Idempotency keys for state-changing operations.</p></li><li><p>HTTPS-only profile and communication requirements.</p></li><li><p>Capability, extension, and version negotiation.</p></li><li><p>Reverse-domain namespace governance.</p></li><li><p>Schema-origin binding for capabilities, services, and payment handlers.</p></li><li><p>OAuth 2.0 identity linking with PKCE and issuer validation.</p></li><li><p>Checkout state lifecycle and escalation rules.</p></li><li><p>Payment-handler negotiation.</p></li><li><p>Signed order webhooks.</p></li><li><p>Optional AP2 mandates for autonomous and high-value transactions.</p></li></ul><h3>2.2 What UCP Does Not Prove by Itself</h3><p>Baseline UCP does not automatically prove:</p><ul><li><p>That historical profiles were not changed after a dispute.</p></li><li><p>That every state-changing request was signed.</p></li><li><p>That every material response was signed and retained.</p></li><li><p>That the negotiated capability set was preserved as an audit artifact.</p></li><li><p>That schema documents fetched during negotiation were hash-pinned.</p></li><li><p>That the agent runtime or merchant runtime was untampered.</p></li><li><p>That a payment handler implementation matched its specification.</p></li><li><p>That buyer consent was enforced after it was transmitted.</p></li><li><p>That attribution was accurate or compliant.</p></li><li><p>That catalog data was accurate, fresh, complete, or unbiased.</p></li><li><p>That an LLM recommendation was safe, fair, or optimal.</p></li></ul><h3>2.3 Proof-of-Control Objective</h3><p>Proof-of-Control closes the evidentiary gap by requiring that high-value UCP actions produce independently verifiable evidence at the time of action.</p><p>The target state is:</p><ul><li><p>Profiles are authenticated, hash-pinned, and retained.</p></li><li><p>Negotiation decisions are recorded in signed transcripts.</p></li><li><p>State-changing messages are signed.</p></li><li><p>Checkout state transitions are tamper-evident.</p></li><li><p>AP2 mandates or trusted UI review prove authorization.</p></li><li><p>Payment credentials are bound to checkout, merchant, handler, amount, currency, and expiry.</p></li><li><p>Identity scopes are linked to operations.</p></li><li><p>Order events are signed and append-only.</p></li><li><p>Runtime and supply-chain controls are attestable.</p></li></ul><p>Figure 3 traces the evidence chain that closes the provability gap. Each stage binds the next one, so a later dispute can be checked against the original mandate, negotiated protocol shape, signed transaction messages, and retained event history.</p><div Dispute</h3><p>Contracts create remedies after a violation. Proof-of-Control creates evidence while the transaction occurs. UCP systems should not depend on reconstructing authority from mutable logs months later.</p><h3>Principle 2: Authority Must Be Scoped</h3><p>Agent authority must be scoped to the active UCP profile, negotiated capabilities, identity scopes, checkout state, payment handler, and mandate terms. A general platform identity is not enough.</p><h3>Principle 3: Negotiation Must Be Auditable</h3><p>UCP's capability negotiation determines what an agent and business can safely do together. The selected protocol version, service, transport, capabilities, extensions, schemas, payment handlers, and identity scopes must be recorded as a session artifact.</p><h3>Principle 4: Checkout State Must Be Enforced</h3><p>The checkout lifecycle is a control surface. <code>requires_escalation</code> means the platform must hand off through <code>continue_url</code>. Programmatic completion must be limited to valid states and valid authority.</p><h3>Principle 5: Payment Must Be Bound</h3><p>Payment credentials must be bound to the intended business, checkout, handler, amount, currency, and expiration. A valid credential that can be replayed against another merchant or checkout is not sufficient.</p><h3>Principle 6: Consent Transport Is Not Consent Enforcement</h3><p>UCP can carry buyer consent. Proof-of-Control must show that consent state was actually applied to data handling, retention, sharing, and deletion behavior.</p><h3>Principle 7: Logs Must Be Tamper-Evident</h3><p>If the system being audited can rewrite its own evidence, the evidence is not institutionally defensible. UCP action logs should be signed and anchored.</p><h3>Principle 8: Proof Has Limits</h3><p>Digital signatures prove origin and integrity, not business correctness. Runtime attestation proves measured code ran, not that the code was bug-free. Formal verification proves properties against a specification, not that the specification captures every real-world risk.</p><h2>Section 4: Proof Mechanisms Taxonomy</h2><p>Table 2 separates mechanisms that are mature today from those whose deployment still depends on infrastructure or ecosystem adoption. Foundation Model Security</h3><p><strong>UCP relevance:</strong> UCP does not define model internals. However, platforms may use models to search catalogs, rank products, select variants, interpret merchant messages, decide when to escalate, or assemble checkout inputs.</p><p><strong>Primary threats:</strong></p><ul><li><p>Prompt injection causes an agent to ignore UCP messages or checkout state.</p></li><li><p>Model or policy version changes commerce behavior without approval.</p></li><li><p>Ranking manipulation changes product discovery outcomes.</p></li><li><p>Agent treats provisional catalog context as final checkout authority.</p></li><li><p>Agent completes checkout when buyer review or AP2 authorization is required.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Sign model, policy, prompt, and tool manifests used for commerce flows.</p></li><li><p>Bind commerce-agent policy to UCP states, especially <code>requires_escalation</code> and <code>ready_for_complete</code>.</p></li><li><p>Commit to evaluation datasets for UCP-specific safety tests.</p></li><li><p>Attest model-serving and policy-enforcement runtime for high-risk flows.</p></li><li><p>Require deterministic policy enforcement outside the LLM for checkout completion, payment, and identity decisions.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Signed model manifest.</p></li><li><p>Signed commerce policy manifest.</p></li><li><p>Runtime attestation report.</p></li><li><p>Evaluation commitment and result signature.</p></li><li><p>Decision log linking recommendation, UCP state, and authority basis.</p></li></ul><p><strong>Limits:</strong> This does not prove the model's recommendation is optimal, fair, or safe for all novel prompts.</p><h3>Layer 2: Data Operations Security</h3><p><strong>UCP relevance:</strong> UCP catalog, cart, checkout, buyer, context, signal, attribution, consent, and order data shape agent decisions.</p><p><strong>Primary threats:</strong></p><ul><li><p>Poisoned catalog data causes wrong product selection.</p></li><li><p>Stale price or inventory data misleads the agent.</p></li><li><p>Product or variant ID mismatch causes checkout of the wrong item.</p></li><li><p>Signals are buyer-asserted rather than observed or attested.</p></li><li><p>Consent state is transmitted but not enforced.</p></li><li><p>Attribution identifiers are over-collected or retained too long.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Sign product feeds, catalog indexes, inventory updates, and price updates.</p></li><li><p>Hash-chain product, price, inventory, and vector-store update logs.</p></li><li><p>Treat checkout response as authoritative for final price, eligibility, fulfillment, tax, and payment constraints.</p></li><li><p>Validate that signals use reverse-domain names and are observed or signed.</p></li><li><p>Bind consent state to data-use policy enforcement.</p></li><li><p>Minimize signal and attribution retention according to policy.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Signed catalog manifest.</p></li><li><p>Merkle proof for product state at recommendation time.</p></li><li><p>Signed signal attestation.</p></li><li><p>Consent-to-policy enforcement log.</p></li><li><p>Checkout response hash.</p></li><li><p>Data retention proof or deletion certificate.</p></li></ul><p><strong>Limits:</strong> This proves data integrity and provenance, not truthfulness, commercial fairness, or absence of bias.</p><h3>Layer 3: Agent Framework Security</h3><p><strong>UCP relevance:</strong> This layer covers the agent loop, capability negotiation, schema composition, cart updates, checkout state transitions, payment-handler selection, and tool calls.</p><p><strong>Primary threats:</strong></p><ul><li><p>Platform invokes a capability outside the negotiated intersection.</p></li><li><p>Malicious extension spoofs a UCP namespace or schema origin.</p></li><li><p>Orphaned extension remains active after parent capability pruning.</p></li><li><p>Schema substitution changes request or response semantics.</p></li><li><p>Agent bypasses <code>requires_escalation</code>.</p></li><li><p>Duplicate requests create duplicate orders or charges.</p></li><li><p>Valid tool inputs are used for unauthorized business outcomes.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Validate reverse-domain capability names.</p></li><li><p>Enforce schema URL authority binding before fetch; require HTTPS for spec URLs.</p></li><li><p>Verify extension <code>extends</code> and <code>requires</code> compatibility.</p></li><li><p>Formally verify or exhaustively test the capability intersection and extension pruning algorithm.</p></li><li><p>Compose schemas from negotiated capabilities and validate all requests and responses against the active schema.</p></li><li><p>Treat checkout as a formal state machine.</p></li><li><p>Sign idempotency keys for all state-changing actions.</p></li><li><p>Preserve a signed negotiation transcript.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Signed negotiation transcript.</p></li><li><p>Profile hashes.</p></li><li><p>Schema hashes.</p></li><li><p>Active capability and extension list.</p></li><li><p>Checkout state transition log.</p></li><li><p>Idempotency verification record.</p></li><li><p>Tool-call authorization log.</p></li></ul><p><strong>Limits:</strong> Formal verification applies to bounded logic, not open-ended LLM reasoning.</p><h3>Layer 4: Deployment and Infrastructure Security</h3><p><strong>UCP relevance:</strong> This layer covers REST, MCP, A2A, embedded flows, profile fetching, schema fetching, gateways, signing keys, checkout services, payment handlers, and PSP adapters.</p><p><strong>Primary threats:</strong></p><ul><li><p>SSRF or resource exhaustion through malicious profile URLs.</p></li><li><p>Redirect-based profile substitution.</p></li><li><p>Profile cache poisoning.</p></li><li><p>API gateway reserializes JSON and invalidates <code>Content-Digest</code>.</p></li><li><p>Signing keys are stolen or misused.</p></li><li><p>Payment-handler implementation differs from its specification.</p></li><li><p>Embedded checkout introduces UI or state confusion.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Enforce HTTPS-only profiles and no redirects.</p></li><li><p>Use bounded profile caches, rate limits, and negative caching.</p></li><li><p>HSM- or KMS-protect signing keys.</p></li><li><p>Ensure gateways preserve raw body bytes used for <code>Content-Digest</code>.</p></li><li><p>Use runtime attestation for high-risk agent, checkout, payment-handler, and PSP adapter services.</p></li><li><p>Use mTLS, OAuth client credentials, API keys, or allowlists where permissionless signatures are insufficient.</p></li><li><p>Sign deployment manifests and infrastructure configuration.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Profile fetch log.</p></li><li><p>HSM/KMS key attestation.</p></li><li><p>Runtime attestation report.</p></li><li><p>Gateway digest verification record.</p></li><li><p>Signed deployment manifest.</p></li><li><p>Service configuration hash.</p></li></ul><p><strong>Limits:</strong> Attestation proves the measured environment, not that the code is bug-free.</p><h3>Layer 5: Evaluation and Observability</h3><p><strong>UCP relevance:</strong> This layer covers signed messages, checkout logs, cart logs, payment logs, identity logs, order webhooks, telemetry, and audit bundles.</p><p><strong>Primary threats:</strong></p><ul><li><p>Logs are deleted, reordered, or rewritten after a disputed transaction.</p></li><li><p>Signed webhook is accepted for the wrong order.</p></li><li><p>Payment authorization response is not preserved.</p></li><li><p>Checkout completion evidence is incomplete.</p></li><li><p>Agent omits unfavorable telemetry.</p></li><li><p>Evaluation results are cherry-picked.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Sign logs for cart, checkout, payment, identity, and order events.</p></li><li><p>Anchor event streams with hash chains or Merkle trees.</p></li><li><p>Verify webhook signatures and signer-to-order ownership.</p></li><li><p>Archive signed checkout completion and payment authorization responses.</p></li><li><p>Commit to evaluation datasets before testing.</p></li><li><p>Use out-of-band telemetry for critical enforcement points.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Merkle root.</p></li><li><p>Signed event log.</p></li><li><p>Webhook signature verification record.</p></li><li><p>Order ownership verification record.</p></li><li><p>Signed payment and checkout response archive.</p></li><li><p>Evaluation commitment and result signature.</p></li></ul><p><strong>Limits:</strong> A compromised component can produce false but validly signed logs. Behavioral monitoring and independent telemetry remain necessary.</p><h3>Layer 6: Security, Governance, and Compliance</h3><p><strong>UCP relevance:</strong> This layer covers protocol versioning, capability governance, schema governance, payment-handler governance, identity scopes, consent policy, and change management.</p><p><strong>Primary threats:</strong></p><ul><li><p>Public profile advertises unsupported or pre-release <code>draft</code> version.</p></li><li><p>Capability downgrade changes security semantics.</p></li><li><p>Vendor extension uses misleading namespace or schema origin.</p></li><li><p>OAuth scopes are overbroad or not mapped to operations.</p></li><li><p>Buyer consent is not connected to actual data handling.</p></li><li><p>Payment-handler specification changes without approval.</p></li><li><p>Natural-language governance policy diverges from executable policy.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Enforce date-based UCP versions in public profiles.</p></li><li><p>Validate <code>supported_versions</code> profiles as complete leaf profiles.</p></li><li><p>Sign profile, schema, extension, and payment-handler changes.</p></li><li><p>Bind policy-as-code to UCP capability, scope, and state definitions.</p></li><li><p>Validate OAuth <code>iss</code>, PKCE <code>S256</code>, exact <code>redirect_uri</code>, revocation, and scope challenges.</p></li><li><p>Maintain multi-signature approval for material UCP changes.</p></li><li><p>Generate cross-layer audit bundles.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Signed governance manifest.</p></li><li><p>Signed change approval chain.</p></li><li><p>Formal policy verification result.</p></li><li><p>OAuth scope-to-operation mapping.</p></li><li><p>Consent enforcement evidence.</p></li><li><p>Cross-layer compliance bundle.</p></li></ul><p><strong>Limits:</strong> Proof shows that approved policy was enforced. It does not prove the policy was complete, ethical, or commercially wise.</p><h3>Layer 7: Agent Ecosystem Security</h3><p><strong>UCP relevance:</strong> This layer covers platforms, businesses, credential providers, PSPs, agents, marketplaces, payment handlers, AP2 mandate issuers, and third-party extensions.</p><p><strong>Primary threats:</strong></p><ul><li><p>Agent impersonates a trusted platform profile.</p></li><li><p>Business profile is fake, stale, or malicious.</p></li><li><p>Payment handler is unsupported, malicious, or misconfigured.</p></li><li><p>Payment credential is replayed against another checkout or business.</p></li><li><p>AP2 mandate is missing, expired, invalid, or bound to a different checkout.</p></li><li><p>Delegated authority chain exceeds user or organizational authorization.</p></li><li><p>Third-party plugin or extension compromises commerce flow.</p></li></ul><p><strong>Controls:</strong></p><ul><li><p>Verify <code>UCP-Agent</code>, message signature, signing key, and profile consistency.</p></li><li><p>Use profile trust tiers for high-risk merchants and platforms.</p></li><li><p>Require payment-handler provenance, schema validation, binding, and expiry.</p></li><li><p>Require AP2 mandates for autonomous or high-value completion.</p></li><li><p>Verify <code>ap2.merchant_authorization</code>, <code>ap2.checkout_mandate</code>, and payment mandate correlation.</p></li><li><p>Use threshold signatures for corporate procurement or regulated purchases.</p></li><li><p>Vet third-party agents, plugins, and extensions with supply-chain attestations.</p></li></ul><p><strong>Proof evidence:</strong></p><ul><li><p>Agent profile verification record.</p></li><li><p>Payment-handler attestation.</p></li><li><p>Payment credential binding proof.</p></li><li><p>AP2 mandate verification record.</p></li><li><p>Delegation-chain signature.</p></li><li><p>Third-party component provenance.</p></li></ul><p><strong>Limits:</strong> Identity and delegation proof do not prevent an authorized agent from making a poor decision within its permitted scope.</p><p>Figure 4 maps Proof-of-Control across the seven MAESTRO layers.
