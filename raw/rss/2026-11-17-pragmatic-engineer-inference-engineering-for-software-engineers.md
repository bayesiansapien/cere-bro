# Inference engineering for software engineers

<p>A recent trend we&#8217;ve covered is of <a href="https://newsletter.pragmaticengineer.com/p/the-pulse-tech-companies-move-to">tech companies moving to open models</a> to rein in AI spend: Uber cut its per-token costs by 50%, Pinterest by 90%, and even AT&amp;T has achieved a 56% decrease. But how do you move from a frontier lab&#8217;s APIs to using open models? There are two options:</p><ul><li><p><strong>&#8220;Bare metal:&#8221;</strong> With plenty of time and money, you can go &#8220;bare metal&#8221; and purchase a few dozen NVIDIA GPUs and use those AI supercomputers, like Revolut <a href="https://ai.engineer/nyc/2026/talks/revolut">has done</a>: running 56 separate B200 units itself to serve its inference needs. This is a lot of work to set it up, but after that, operational costs are as cheap as it gets.</p></li><li><p><strong>Inference provider:</strong> most companies contract with an inference provider that operates large fleets of GPUs, and makes it easy for customers to onboard and start using open models fast.</p></li></ul><p>Onboarding to an inference provider to run LLM workloads comes with challenges, such as dealing with tail latencies, worrying about cache hit rates, rate limits, and more. <strong>Inference engineering</strong> is a set of engineering practices that we believe is increasingly beneficial for software engineers to familiarize themselves with. To go deeper into this area, we&#8217;ve talked with three leading inference providers to learn more: <a href="https://modal.com/">Modal</a>, <a href="https://fireworks.ai/">Fireworks AI</a>, and <a href="https://www.baseten.co/">Baseten</a>. Today, we cover:</p><ol><li><p><strong>What are inference providers &amp; how do they differ from AI labs? </strong>They have GPU infrastructure similar to frontier labs, don&#8217;t train their own frontier models and are experts at hosting open models.</p></li><li><p><strong>When to switch from frontier labs? </strong>The most common reasons are to reduce costs, have more control over latency, and to fine-tune AI models.</p></li><li><p><strong>Choosing a model, provider, and deployment strategy. </strong>Use evals to find the right open model for your use case, evaluate vendors, and decide between multi-tenant API usage and dedicated GPUs.</p></li><li><p><strong>Stage #1: API replacement using a multi-tenant inference setup</strong>. The easiest way to onboard to an inference provider is to &#8220;swap&#8221; the API of a frontier lab to an API of an inference provider. But there may be latency problems and caching issues at high loads.</p></li><li><p><strong>Signs you&#8217;ve outgrown multi-tenant inference APIs.</strong> Hitting rate limits, performance consistency problems, and overpaying for usage are signs that it might be time to adopt dedicated GPUs.</p></li><li><p><strong>Stage #2: Configuring dedicated GPU nodes. </strong>With dedicated GPUs, you&#8217;ll need to get into the details: size of the model, interactivity versus throughput, KV cache sizing, failover options, and more.</p></li><li><p><strong>Speculative decoding. </strong>If there&#8217;s unused compute during the decode phase, you might consider a Speculator to further boost inference performance.</p></li></ol><p><em>As usual, we have no affiliation with vendors mentioned in this article, and have not been paid to mention any company. Special thanks to Richard Gong (Inference lead, Modal), Dmytro Dzhulgakov (cofounder and CTO, Fireworks), and Philip Kiely (Special Projects at Baseten) for sharing details about inference engineering challenges.</em></p><h2>1. What are inference providers &amp; how do they differ from AI labs?</h2><p>Inference providers are companies that sell access to LLMs which they run on users&#8217; behalf. From the outside, this isn&#8217;t so different to what OpenAI and Anthropic offer: an API endpoint, ability to stream tokens, and pay based on token usage.</p><p>But what makes inference providers different from frontier labs is the models running behind the endpoint: inference providers run open-weight models, whereas frontier labs train their own models. In this field, Modal, Fireworks, and Baseten each operate slightly different strategies:</p><ul><li><p><strong><a href="https://modal.com/">Modal</a></strong> sees itself as a cloud infrastructure provider that focuses on making its offering programmable via its SDKs. It natively supports inference services through its SDKs, but leans heavily on the open source ecosystem for running its inference workloads efficiently. Performance tweaks to its stack are merged upstream. In the words of Richard Gong, Inference Lead at Modal: &#8220;when you run code on Modal, you should be able to see all the code that&#8217;s running.&#8221;</p></li><li><p><strong><a href="https://fireworks.ai/">Fireworks</a></strong> positions itself as a provider for specialized AI workloads. Most of its business is in dedicated deployments, which often include fine-tuning and provision of latency guarantees. Much fine-tuning and post-training is available for self-service. Fireworks also offers forward-deployed researchers that can help with post-training custom models or components. Dmytro Dzhulgakov, Fireworks&#8217; CTO, says: &#8220;our tagline is specialized intelligence, which means we will tune everything from model to infrastructure for your particular use case.&#8221;</p></li><li><p><strong><a href="https://www.baseten.co/">Baseten</a></strong> describes itself as an all-in-one place to build agents. It starts with the basic infrastructure layer with uptime guarantees, flexible commercial terms, without vendor lock-in. Baseten builds additional layers for building agentic workloads on top of its inference platform. These additional layers include sandboxes, governance services, and self-serving, post-training functionality.</p></li></ul><p>To customers, inference providers offer LLM APIs that can be used as drop-in replacements for frontier labs&#8217; APIs. However, inference providers are not the same, as suggested above:</p><ol><li><p><strong>Inference providers don&#8217;t pre-train their own foundational models</strong>. A single pre-training run for frontier-level LLMs can cost millions of dollars, and only hyperscalers and specialized frontier labs can afford it. Inference providers run post-training on open-weight models because it&#8217;s significantly cheaper.</p></li><li><p><strong>Competitive pricing. </strong>The main business of inference providers is offering open-weight models at competitive rates.</p></li><li><p><strong>Dedicated hardware.</strong> A big part of the appeal of inference providers is the ability to have dedicated hardware for users to interact with vendors on the infrastructure layer.</p></li><li><p><strong>Efficiency &amp; customization.</strong> Inference providers offer similar commoditized open models, and compete heavily on efficiency and customization services.</p></li></ol><p>As an example of efficiency, Fireworks <a href="https://fireworks.ai/blog/ember-1">announced</a> its Ember-1 model in September 2026, that is post-trained on the Kimi K3 foundation, delivering a similar quality level but with 40% fewer reasoning tokens consumed. Consuming far fewer reasoning tokens gives Fireworks an edge on cost compared to a vanilla Kimi K3 model. </p><p><strong>In general, frontier labs have poor uptime, and this helps inference vendors win market share. </strong>API Uptime provided by frontier labs isn&#8217;t at the levels expected of modern cloud providers: currently, the self-declared uptime of <a href="https://status.claude.com/">Anthropic</a> is 99.5%, and for <a href="https://status.openai.com/">OpenAI</a> it&#8217;s 99.97% for API, and 99.2% for ChatGPT. These numbers are well below the four nines (99.99%+) uptime expected of cloud providers &#8211; which is something that a vendor like AWS is known to <a But in the graphs above, degraded performance slots aren&#8217;t counted as downtime. As all these APIs are multi-tenant, it means that performance degradations will naturally hit some tenants &#8211; with no way to be aware of the degradation, or do anything about it.</p><p><strong>Reliability is an ongoing concern with the LLMs of frontier providers and inference providers.</strong> Even though many inference vendors offer higher reliability guarantees than frontier models, inference providers can also go down, too. For companies that use inference providers, it&#8217;s common to use an LLM gateway with fallback logic to another provider &#8211; or to a frontier API. We explored this in a deepdive with <a href="https://newsletter.pragmaticengineer.com/p/why-ramp-built-inspect">Ramp</a>, whose LLM router project started with this exact problem statement.</p><h2>2. When to switch from frontier labs?</h2><p>Moving from frontier AI labs to an independent inference provider is often driven by three factors: cost, control, and the need for more customization.</p><h3>Most common reason: cost</h3><p>Many companies start considering inference providers because they have pressing cost concerns. In many cases, a frontier model is <em>more</em> capable than necessary for most requests, meaning a &#8220;dumber&#8221; model is just as good for simpler tasks &#8211; and nobody would notice the difference! In such cases, it&#8217;s a &#8220;no-brainer&#8221; for an engineering team to choose to route some requests to a cheaper model hosted by an inference provider.</p><p><strong>&#8220;Smart routing&#8221; is an obvious way to cut costs. </strong>An LLM router &#8211; the &#8220;smart router&#8221; &#8211; is prompt-aware and can route an LLM request to the most cost-efficient provider that can solve the request. This is an approach that fuelled Uber&#8217;s ~50% cut in per-token costs <a href="https://blog.pragmaticengineer.com/the-pulse-tech-companies-move-to-open-ai-models/">this summer</a>.<br /><br />Providers offer OpenAI/Anthropic-compatible API endpoints, so switching providers is trivial. All that is needed is to point your app at the new endpoint operated by a &#8220;smart router.&#8221;</p><p><strong>But how to decide which model to serve?</strong> Generic benchmarks are often insufficient because they usually do not fully represent a team&#8217;s traffic patterns. Most inference providers ask for prompt samples or <a href="https://newsletter.pragmaticengineer.com/p/evals">eval</a> sets in order to gauge which model best serves a customer&#8217;s use case. The experience of using a new LLM endpoint resembles using APIs provided by frontier labs, while API calls are still charged per token, and response time SLAs generally don&#8217;t exist.</p><h3>More control over latency</h3><p>When you use a frontier lab&#8217;s endpoint, there is little control over operational issues like response latency and model availability. Opting for a dedicated setup with an inference provider offers full control over both:</p><ul><li><p><strong>Latency</strong>: model response times are more predictable because the app has dedicated capacity that can scale by usage.</p></li><li><p><strong>Model availability</strong>: Engineers can run the model of their choosing on their dedicated GPUs and keep operating it as long as needed, avoiding the risk of a frontier lab changing models from one day to the next.</p></li></ul><h3>Fine-tuning model quality: customization</h3><p>When an inference stack runs on dedicated hardware with open source models, it&#8217;s possible to work with inference providers to finetune a model&#8217;s quality as required, which optimizes latency or throughput performance. Richard Gong of Modal says that around 10% of their customers go this far, suggesting that customization is for &#8220;power users&#8221;.</p><p>Fine-tuning a model&#8217;s quality is typical in two scenarios:</p><ul><li><p><strong>Tweaking a smaller model</strong>: achieving a similar level of quality with a smaller model, with fewer parameters. This performance gain is achieved via performance tweaks not possible with off-the-shelf models. Inference providers allow you to post-train a smaller model for your specific use case. A post-trained small model can then outperform the original model in those specialized scenarios.</p></li><li><p><strong>Fine tuning for niche use cases. </strong>Improving quality when general purpose models aren&#8217;t good enough, often because the data isn&#8217;t publicly available. For example, projects in the legal and medical sectors tend to benefit from this, according to the Fireworks team.</p></li></ul><h2>3. Choosing a model, provider, and deployment strategy</h2><p>Most inference providers offer the exact same models to run, and the differences lie in model performance and quality. For example, model quality can differ by default context length, and some providers cap this to below what the model supports. There&#8217;s also <a href="https://developer.nvidia.com/blog/model-quantization-concepts-methods-and-why-it-matters/">quantization</a> to consider, where a model&#8217;s weights are compressed to a lower numerical precision, or default <a href="https://aiwiki.ai/wiki/temperature">temperature</a> aka controlling how random the output is. Here&#8217;s a practical approach for selecting a provider:</p><ol><li><p><strong>Model</strong>: Choose an AI model to switch to</p></li><li><p><strong>Provider</strong>: pick an inference provider to host the model, based on model quality, performance, and cost</p></li><li><p><strong>Deployment model:</strong> decide whether to use a multi-tenant service, or to move to dedicated GPU nodes</p></li></ol><h3>Choosing a model</h3><p>The most obvious way to decide which model to use is to run an <strong>eval set</strong> against the various model options. In the latest episode of The Pragmatic Engineer Podcast, Microsoft&#8217;s CEO Satya Nadella <a href="https://newsletter.pragmaticengineer.com/p/software-engineering-after-code-becomes">argues</a> that <strong>private evals </strong>shall be a big component of tech companies&#8217; intellectual property (IP) in the future. He says:</p><blockquote><p>&#8220;Public benchmarks are great, but your private evals will matter more: you need your own eval for the outcome that matters to you. Then you look at performance across all these models and continuously optimize.</p><p>Our customers start with a frontier model, then say: &#8216;I&#8217;ve got all those traces. This is a deterministic workflow, so I don&#8217;t need the next big model drop. I want to optimize the cost.&#8217; They drop in [another] model, use the traces to fine-tune it &#8211; and there you have it.&#8221;</p></blockquote><p>An example of public benchmarks is from <a href="https://artificialanalysis.ai/">Artificial Analysis</a> that maintains an eval set to compare costs for generic tasks across different models. However, you are still running in a multi-tenant environment, which comes with similar performance bottlenecks, like when using the API endpoint of a frontier model. The difference is that with an inference provider, you can migrate to a dedicated hosting environment and have full control over a deployment&#8217;s performance. Having your own deployment (controlling the GPUs with the inference provider) makes it possible to fine-tune a model&#8217;s quality with techniques such as post-training.</p><h3>Typical graduation Stage #1: API replacement, using a multi-tenant inference setup</h2><p>For teams with hefty LLM bills, the easiest way to decrease cost is to replace frontier labs&#8217; models in Claude Code, Codex, OpenCode, with a frontier-level open model. Looking at data from <a href="https://opencode.ai/data/">OpenCode</a> and <a href="https://openrouter.ai/rankings#top-models">OpenRouter</a>, the current most popular choices of engineering teams for this include DeepSeek 4.1 Flash, GLM 5.3, and others including Kimi K3.1 Pro.</p><p>The easiest way to carry out a replacement is to point an application to an API provided by the inference provider. In practice, this means using a multi-tenant API where other customers will be hitting the same endpoint, similar to using an API endpoint from a frontier lab. At first, everything will be great, but then you may come across problems of time-to-first-token (TTFT) latency, caching-related costs, and latency issues.</p><p><em>These are also problems of using APIs from frontier labs, the difference being that with inference providers, there&#8217;s the option of solving most of them by moving over to a dedicated deployment.</em></p><h3>Latency problems: TTFT, inference time, user-experienced latency</h3><p>Time-to-first-token is a measure of how long it takes from the moment a request hits the LLM API, to when the client starts receiving the first tokens. So, when measuring latencies, the p95/p99 latencies are just as important as p50 latencies. TTFT can be measured in two places:</p><ul><li><p><strong>Inference time:</strong> provider-instrumented TTFT shows the pure inference time. Some providers expose this metric to customers on dashboards, while some include it in their responses. Frontier labs typically do neither.</p></li><li><p><strong>User-experienced latency:</strong> client-instrumented TTFT shows the full user-experienced latency, including things like network transport, or the TLS handshake.</p></li></ul><p>Server-side inference is just <em>one</em> part of the overall time that an app&#8217;s user spends awaiting a response. To achieve truly fast p95 times for user latency, it&#8217;s best to consider optimizations like <a href="https://en.wikipedia.org/wiki/Connection_pool">connection pooling</a> on the LLM API consumer side.</p><p>When serving LLM APIs on shared infrastructure, inference providers run many copies of the LLM inference engine that serves customer requests. A single inference engine can serve multiple requests concurrently. A new replica is created when the number of concurrent requests exceeds the current replica capacity. Scaling of replicas is one reason why inference-only TTFT latencies vary so much.</p><p>Other reasons why TTFT can vary:</p><ol><li><p><strong>&#8216;Noisy neighbour&#8217; effects</strong>: a request is batched with another request that&#8217;s more expensive to process, so it takes longer than if the request was in a batch with a similar request.</p></li><li><p><strong>Cold start</strong>: happens when a request is waiting in a queue because there is no capacity in existing replicas. The inference provider is creating new replicas but this isn&#8217;t instantaneous, so a request has to wait until the new replica becomes available (until the new replica starts up, from a &#8220;cold&#8221;, offline state).</p></li><li><p><strong>Cold cache:</strong> when sending a large request for the first time, it may end up on a replica without the relevant KV cache loaded (the cache is &#8220;cold&#8221; &#8211; which is the opposite of &#8220;hot cache&#8221; when the KV cache is already populated). An inference provider will typically try to keep requests sticky to the same replica because that keeps replica&#8217;s KV cache hot. Sometimes, this isn&#8217;t possible because your cache expired, or it landed on the replica that doesn&#8217;t have the relevant KV cache. KV cache then has to either be copied from cold storage if available, or if it&#8217;s not, fully processed before the first token can be generated.</p></li></ol><p>Prompt cache utilization is observable and actionable by engineers building on LLM APIs. You can get prompt cache utilization metrics from the response of the <a href="https://developers.openai.com/api/reference/resources/completions#(resource)%20completions%20%3E%20(model)%20completion_usage%20%3E%20(schema)">OpenAI completions API</a>. Building your apps to effectively exploit prompt cache is a key technique in improving app performance, so it&#8217;s worth taking a closer look.</p><h3>Caching issues: cost and latency</h3><p>Most major LLM API endpoints today are stateless REST APIs, inspired by OpenAI&#8217;s chat completions API.</p><p><strong>LLM endpoints are stateless, which creates problems because most LLM use cases are stateful. </strong>Dmytro Dzhulgakov, cofounder and CTO at Fireworks calls the decision to make the API stateless &#8220;the original sin&#8221; because while the client app behaves like it&#8217;s talking to a stateless API, the burden is on the provider to ensure efficient caching mechanisms in a distributed environment.</p><p>Here&#8217;s an example to illustrate the problems that stateless APIs cause: an app with user&#8217;s inputs, LLM prompts, and the agentic context layer:</p>
