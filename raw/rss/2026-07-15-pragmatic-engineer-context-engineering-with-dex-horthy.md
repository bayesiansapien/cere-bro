We discuss the ideas behind this context engineering, harness engineering, loop engineering, software factories, why his approach to AI-assisted software development has evolved, and how </span><a href="https://www.humanlayer.dev/"><span>HumanLayer</span></a><span> is helping engineering teams automate more of the software development lifecycle without sacrificing code quality.</span></p><h3>Key observations from Dex</h3><p>Here are 12 useful points Dex made in our conversation:</p><div class="youtube-wrap" id="youtube2-Usufn8IQJgw"><div class="youtube-inner"></div></div><p><strong><span>1. Dex talked with ~100 &#8220;real&#8221; AI Engineers and wrote the popular &#8216;</span><a href="https://github.com/humanlayer/12-factor-agents"><span>12-Factor Agents - Principles for building reliable LLM applications</span></a></strong><span>&#8217; based on what he learned. Around August 2024, he started to build AI agents when the common approach was to use frameworks like LangChain and CrewAI, and also talked with around 100 AI engineers doing tangible work such as taking on $100K+ contracts to ship AI solutions within enterprises. They tried those frameworks and discarded them in favor of building their own pipelines. Dex shared the learnings from the conversations in his hit book, </span><a href="https://github.com/humanlayer/12-factor-agents"><span>12-Factor Agents</span></a><span>. </span><em><span>It&#8217;s a great read!</span></em></p><p><strong><span>2. Lesson learned: Shipping unread code spells disaster within months. </span></strong><span>Dex experimented with having the model write the code and humans not reviewing anything in July 2025. Four months later, they shut things down and threw the whole system out. Production broke, and no matter how much the team prompted Opus 4.1, the model could not find the root cause.</span></p><p><span>It took days of wading through spaghetti code to discover the primary key wrongly routed through the complete codebase. Once fixed, it took three weeks to re-onboard to a codebase no human had ever read. Today, Dex thinks this problem wouldn&#8217;t even take four months to develop, now that newer models produce code a </span><em><span>lot</span></em><span> faster than a year ago.</span></p><p><strong><span>3. Today&#8217;s coding models are most likely trained in a way that makes codebases </span></strong><em><strong><span>worse</span></strong></em><strong><span> over time. </span></strong><span>Dex believes that the reason we see LLMs &#8220;degrade&#8221; existing codebases is because they are optimized to do well on SWE-bench-style benchmarks. These benchmarks reward reproducing a known fix in codebases like Django, but cannot measure poor architecture decisions. This is because the cost function of bad architecture and bad program design cannot be evaluated by running a unit test.</span><strong><span> </span></strong><span>It&#8217;s a tricky problem to solve: Dex&#8217;s best guess is an eval of a model building 20 features in a row in a codebase without knowing what&#8217;s coming next.</span></p><p><strong><span>4. Context engineering 101: figure out where the &#8220;dumb zone&#8221; begins. </span></strong><span>As a rule of thumb, the less of the context window that is used, the better the outcomes are. This is because the attention mechanism </span><a href="https://newsletter.pragmaticengineer.com/i/141865286/scalability-challenge-from-self-attention"><span>is quadratic</span></a><span>: the more that goes into the context window, the more compute is required to process it all. </span><em><span>We cover more about self-attention scalability challenges </span><a href="https://newsletter.pragmaticengineer.com/i/141865286/scalability-challenge-from-self-attention"><span>in our ChatGPT deepdive</span></a><span>.</span></em></p><p><span>For a model with a 1M context window, Dex pushes it to around 300-400K when it feels right. For smaller models, he stops at around 100K. You hit the &#8220;dumb zone&#8221; when its performance starts to degrade because the context window fills up beyond this heuristic limit, and the model begins doing increasingly stupid things like deleting your .env file, for example.</span></p><p><strong><span>5. A larger context window does not mean a smarter model. </span></strong><span>Models&#8217; intelligence is behind the ability to use the tokens in the context window, by deciding which parts of the context are relevant for the next decision. You have to get a feel for how much context usage makes sense, and experiment when you hit the &#8220;dumb zone.&#8221;</span></p><p><strong><span>6. Frequent, intentional compaction is a technique Dex uses for more complex projects. </span></strong><span>He will take a long and noisy context, compress it into a Markdown document, then start a new session fresh, pointing the model to this &#8220;compressed context&#8221; that is in the Markdown.</span></p><p><span>A workflow he uses:</span></p><ul><li><p><span>One session reads a ton of code (filling up its context window while in the &#8220;smart zone&#8221;), then emits a research document</span></p></li><li><p><span>The next session takes tickets describing the work to be done and turns it into a design document</span></p></li><li><p><span>The following session takes both documents to create a plan</span></p></li><li><p><span>The human is in the loop where it </span><em><span>really</span></em><span> matters: in this case, reviewing the design document and architecture because Dex finds models to be weak on this</span></p></li></ul><p><strong><span>7. Don&#8217;t bother optimizing LLM usage until business is booming, there&#8217;s massive scale, or high costs. </span></strong><span>Dex suggests to always start building software with the smartest available model to solve the problem, since engineering time is almost always the bottleneck. Begin to optimize LLM usage and context usage only when at real scale and costs are high enough. That&#8217;s when it can be worth using GPT-OSS-120B (1/1,000th the cost of Opus) for the simpler steps in your process.</span></p><p><strong><span>8. &#8220;You&#8217;re completely right!&#8221; or &#8220;you&#8217;re right to push back on that&#8221; are phrases that mean it&#8217;s time to start a new session. </span></strong><span>These responses mean the LLM session is trajectory-poisoned, and you&#8217;re wasting time and tokens to continue. Models are </span><a href="https://en.wikipedia.org/wiki/Autoregressive_model"><span>autoregressive</span></a><span>, so if you get into this loop of:</span></p><ul><li><p><span>Model makes a mistake</span></p></li><li><p><span>&#8594; user &#8220;yells&#8221;</span></p></li><li><p><span>&#8594; model keeps making mistakes</span></p></li><li><p><span>&#8594; user &#8220;yells&#8221;</span></p></li><li><p><span>&#8230; the model calculates that the next most probable message is to make another mistake!</span></p></li></ul><p><strong><span>9. Only four things matter in the context window:</span></strong></p><ul><li><p><strong><span>Size</span></strong><span>: the bigger it is, the more space you should have before hitting the &#8220;dumb zone&#8221;</span></p></li><li><p><strong><span>Information quality</span></strong><span>. Once something is in the context window, every subsequent turn treats it as fact. This is why errors can compound.</span></p></li><li><p><strong><span>Missing information</span></strong><span>: if there&#8217;s information missing that the agent would need, the outcome will be worse, as the agent fills in the gap with guesses.</span></p></li><li><p><strong><span>Trajectory. </span></strong><span>Models are autoregressive, so they predict the next message in the conversation based on previous ones in a kind of thread of reasoning. &#8220;Trajectory poisoning&#8221; is when the agent gets into a pattern of doing things you don&#8217;t want. In this case, it&#8217;s time to start over.</span></p></li></ul><p><strong><span>10. Slow loops are Dex&#8217;s favorite way to do &#8216;loop engineering.&#8217; </span></strong><span>The HumanLayer team started with a nightly automation setup that kicks off an agent to fix one thing in the codebase, and open a pull request. In the mornings, they woke up to a PR waiting to be merged. They tweaked it over time and now have four agents open a total of four PRs by the morning, with the focus on code quality improvements. A person still reads all of them before merging.</span></p><p><strong><span>11. &#8220;Token harder&#8221; vs. &#8220;token smarter&#8221;:</span></strong><span> Dex is in a group chat named &#8216;Hyper Engineering&#8217;, where members share advice on how to max out their Claude subscriptions. This approach, he calls &#8220;token harder&#8221;. On the other side is &#8220;token smarter&#8221;: aiming to get maximum value from AI while keeping control. Smarter is harder to pull off.</span></p><p><strong><span>12. Three ways to run a &#8220;software factory.&#8221; </span></strong><span>Here&#8217;s options Dex sees as viable:</span></p><ol><li><p><strong><span>&#8220;Turn the lights off:</span></strong><span>&#8221; go all-in on agentic coding, do not review the code, and pray that AI doesn&#8217;t create too much slop. </span><em><span>Dex tried this and failed.</span></em></p></li><li><p><strong><span>Read and review all AI-generated code. </span></strong><span>This slows things down to human speed. Dex says that this way, you should expect a 30-50% lift in productivity from AI, compared to pre-AI engineering.</span></p></li><li><p><strong><span>Find leverage, but keep people in the loop. </span></strong><span>Find out where an hour spent in planning could save four hours&#8217; worth of implementation, in terms of fewer bugs. Invest more time in areas with leverage: design, architecture, and key decisions. Then, let the agent generate code and don&#8217;t insist on reviewing all of it. In this way, Dex believes you can move 2-3x faster than when devs wrote all code by hand.</span></p></li></ol><h3><strong>The Pragmatic Engineer deepdives relevant for this
