# Maybe we’ve been thinking about verification backwards

<div class="captioned-image-container"><figure><a class="image-link image2" href="https://gradientflow.substack.com/archive" target="_blank"><div class="image2-inset"><source type="image/webp" /><img alt="" class="sizing-normal" height="220" src="https://substackcdn.com/image/fetch/$s_!Qpug!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fbucketeer-e05bbc84-baa3-437e-9518-adb32be77984.s3.amazonaws.com%2Fpublic%2Fimages%2F0f732fb8-bcb3-47bb-93e0-cf2c6c0653c5_1100x220.png" title="" width="1100" /><div></div></div></a></figure></div><p><strong><a href="https://gradientflow.substack.com/subscribe">Subscribe</a> &#8226;<a href="https://gradientflow.com/newsletter/"> Previous Issues</a></strong></p><h1><strong>Proofs Could Make AI Coding Faster, Not Slower</strong></h1><p>Last week I <a href="https://gradientflow.substack.com/p/an-agent-passed-every-test-and-still?utm_source=gradientflow&amp;utm_medium=newsletter">wrote about a coding agent that made a database six times faster</a> by quietly abandoning the requirement to store data. It passed the tests, but the result was useless. That article focused on the limits of testing and verification. In <a href="https://thedataexchange.media/leo-de-moura-lean-aws/?utm_source=gradientflow&amp;utm_medium=newsletter">my conversation with Leo de Moura</a>, creator of <a href="https://lean-lang.org/?utm_source=gradientflow&amp;utm_medium=newsletter">Lean</a>, a programming language and a system for checking mathematical proofs, we explored another side of the problem. What if formal verification could make AI-driven software development faster, rather than simply making the results more trustworthy?</p><div class="subscription-widget-wrap-editor"><div class="subscription-widget show-subscribe"><div class="preamble"><p class="cta-caption"><em>Enjoying this newsletter? That needs to hold regardless of the contents of the data or the compression setting.</p><p>The project uses Lean to establish this property through a formal proof. AI coding agents repeatedly modified and optimized the implementation, with the proof checked after each change. If an optimization broke the guarantee, the change could not be accepted until the proof worked again. The agents could try different approaches without requiring a human to inspect every implementation in detail.</p><p>The results are promising. Other highly optimized libraries remained faster, and lean-zip used more memory. Still, the performance improvements came from a series of changes largely carried out by AI agents.</p><p>There are two different checks at work here. AI is beginning to reduce that burden. <a href="https://thedataexchange.media/leo-de-moura-lean-aws/?utm_source=gradientflow&amp;utm_medium=newsletter">As Leo explained</a>, the emphasis may shift toward specifying what software should do and reviewing whether those specifications capture what people actually want.</p><p>A specification is a precise description of a program&#8217;s required behavior. For a payment system, it might say that money cannot disappear during a transfer or that a transaction cannot be charged twice. Once these properties are expressed precisely, they can potentially be checked whenever the implementation changes.</p><p>This could also change how teams maintain software. Requirements documents and architecture diagrams often drift out of sync with the code. Formal specifications can become part of a development process that checks whether implementations continue to satisfy them. When problems appear only once, it&#8217;s hard to tell whether an agent has learned a reusable skill. <strong><a href="https://continualarc.org/?utm_source=gradientflow&amp;utm_medium=newsletter">Continual-ARC</a></strong> addresses this gap by bringing back the same types of reasoning puzzles with different inputs, charging for examples and wrong answers, and comparing each system with a version reset between jobs. The results revealed that <strong>agents left to manage their own memory showed no measurable benefit</strong>. Saving tested programs helped on familiar problems, but <strong>only training the model improved performance on unfamiliar ones</strong>.
