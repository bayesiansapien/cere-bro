which customer-facing applications could break?"</p><p>The assistant retrieves the service documentation, an architecture overview, and a migration guide. Its answer is clear, well written, and supported by citations.</p><p>It still misses an application that depends on the service through a shared gateway.</p><p>Nothing in the answer looks obviously broken. The retrieved documents are relevant. The missing piece is the connection between them.</p><p>This is a useful place to examine your retrieval architecture. Finding text about a system and tracing its dependencies are different tasks.</p><h2>Relevant documents do not guarantee sufficient evidence</h2><p>In a basic vector RAG pipeline, a query is embedded, similar chunks are retrieved, and those chunks become context for the model.</p><p>That works well when the evidence needed for an answer appears in the retrieved passages.</p><p>Our dependency question is harder. One document might say the checkout application uses a gateway. Another says the gateway delegates authentication to the service being retired. Neither passage needs to describe the complete chain.</p><p>A single similarity search may retrieve the authentication document while missing the application document. Increasing the number of chunks can help, but it can also bring in unrelated material without supplying the missing link.</p><p><strong>Before changing the prompt, ask: did the model receive enough evidence to answer the question?</strong></p><p>Figure 1 is the three-way comparison: direct LLM, vector RAG, and GraphRAG answering the same question about 19th-century art movements.</p><div GraphRAG answer the same question. Retrieved text gives passages; retrieved triplets give connected facts.</em></p><h2>Make the relationship retrievable</h2><p>A knowledge graph represents entities and the relationships between them explicitly.</p><p>For our example, you could record two facts:</p><ul><li><p>Checkout application &#8594; depends on &#8594; API gateway</p></li><li><p>API gateway &#8594; authenticates through &#8594; Authentication service</p></li></ul><p>Now the system has a path it can inspect when answering the retirement question.</p><p>In a graph-augmented retrieval design, the retriever can locate the service, follow relevant dependency relationships, and provide the resulting evidence to the LLM. The model then has a connected explanation to work with.</p><p>The direction of traversal matters. To find what could be affected by retiring a service, you need to follow its dependants, including indirect ones.</p><p>This does not mean every RAG system needs a graph. Query decomposition and iterative document retrieval can also uncover connected evidence. A graph becomes worth investigating when relationships are central to the questions you repeatedly need to answer.</p><h2>How much of the graph should you retrieve?</h2><p>Finding the right entity is only the beginning.</p><p>Retrieving the authentication service node might tell you its owner and status. It will not necessarily tell you which applications depend on it.</p><p>Chapter 7 distinguishes several levels of retrieval: nodes, triplets, paths, and subgraphs.</p><p>Figure 2 is the Node retrieval returns one entity; triplet retrieval returns direct relationships; path retrieval returns a connected chain; subgraph retrieval returns a neighborhood.</em></p><p>For "Who owns this service?", a node property or a single relationship may be enough. For "Which applications depend on it indirectly?", you need connected relationships.</p><p>Retrieving every nearby node is not automatically useful. As you expand the search, the context can fill with relationships that do not help answer the question.</p><p>The engineering decision is how much connected evidence the task requires, and where to stop.</p><h2>A graph can preserve an error too</h2><p>Explicit relationships are useful only when they reflect the system accurately.</p><p>If an extraction pipeline confuses two services with similar names, the graph can connect the wrong applications. If a dependency changed last month, an outdated edge can produce a convincing but incorrect explanation.</p><p>For the retirement example, I would retain the source and update time for each dependency. I would also distinguish "no dependency found" from "confirmed independent." An incomplete graph cannot establish that an application is unaffected.</p><p>Graph retrieval changes how you find evidence. You still need to check whether that evidence is trustworthy.</p><h2>Try one question your current retriever struggles with</h2><p>Choose a question whose answer requires connecting facts from two or three sources. Write down the expected evidence chain before running it through your assistant.</p><p>Then inspect the retrieved context. Did it contain every required relationship? Did the answer stay within what those sources support?</p><p>That small exercise can reveal whether the next improvement belongs in retrieval, data quality, or answer generation.</p><h2>Build on the idea</h2><p><a href="https://www.packtpub.com/en-us/product/building-ai-agents-with-llms-rag-and-knowledge-graphs-9781835080382">Building AI Agents with LLMs, RAG, and Knowledge Graphs</a>, by Salvatore Raieli and Gabriele Iuculano, explores how these components fit together.
