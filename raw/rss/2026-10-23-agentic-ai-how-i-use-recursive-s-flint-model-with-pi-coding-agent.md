# How I use Recursive's Flint model with Pi coding agent and Jev browser agent

<p>I run Recursive&#8217;s Flint on a DGX Spark, drive it from Windows with Pi Coding Agent, and attach TypeSafe&#8217;s Jev browser loop through <code>pi-jev-browser</code>. Free section: what Flint is, why I put it on Spark beside Qwen without co-loading both, why Pi is the harness, and which browser agents I considered before testing Jev. Paid section: the exact Windows&#8594;tunnel&#8594;Flint&#8594;<code>jev_run</code> procedure, the two Windows patches that unblocked Chromium, and screenshots from the verified Ada Lovelace and Bing News runs. </p><ol><li><p><strong>Flint on DGX Spark</strong> &#8212; MoE coding model, headline SWE-bench Pro v2 score, Spark token speed, and why it never co-resides with Qwen. </p></li><li><p><strong>Pi Coding Agent</strong> &#8212; minimal harness, custom OpenAI-compatible providers, Windows client to local Flint. </p></li><li><p><strong>Browser agent options</strong> &#8212; <code>agent-browser</code>, computer-use, and Jev; why I tested Jev for isolated web goals. </p></li><li><p><strong>Paid how-to</strong> &#8212; swap kit, Pi config, TypeSafe/OpenRouter key, Windows path/sandbox patches, measured runs with screenshots. </p></li></ol><h2>What Flint is, and why it sits on my DGX Spark</h2><p><a href="https://recursive.com/updates/introducing-recursive-flint">Recursive Flint</a> is a coding-oriented mixture-of-experts model: about 39.8B total parameters with roughly 2.5B active per token (the rounded &#8220;40B-A2.5B&#8221; designation). It is built for agentic coding on local hardware: investigate a repo, call tools, fix bugs, write tests. Recursive&#8217;s release card reports 89.7% on SWE-bench Pro v2, 74.2% on SWE-bench Verified, and 54.9% on Terminal-Bench 2.1 (mini-swe-agent / Terminus 2, average pass@1 over at least five attempts). Those numbers put Flint in the same local coding conversation as dense models in the Qwen3.8 / 25&#8211;40B class that Recursive markets it against, while the MoE active path stays much smaller than a full dense forward. </p><p>Against the peer MoE <a href="https://huggingface.co/RecursiveSI/flint">Qwen3.6-35B-A3B</a> comparison Recursive publishes, Flint leads on the agentic and instruction-following rows that matter for tool-using coding: Terminal-Bench 2.1 54.9% vs 44.9%, SWE-bench Pro v2 89.7% vs 73.8%, IFBench 89.2% vs 67.9%, IFEval 95.1% vs 89.6%, with LiveCodeBench v6 essentially tied (80.3% vs 80.4%). That is the reasoning and agent-coding edge I care about on Spark: better multi-step tool discipline than the Qwen3.6 MoE I already had resident, without paying dense-model decode cost. </p><p>Speed is the other half of the decision. Recursive reports more than 150 tokens/second on a 64GB NVIDIA RTX / DGX Spark class box at short contexts with its optimized engine, and more than 100 tok/s still holding around a 120k-token context in their published Spark figures. Dense 25&#8211;40B models that match coding quality on some rows decode far slower on the same memory bandwidth. On a Spark, that tok/s gap is the difference between an interactive Pi tool loop and a stalled session. </p><p>I already run a Qwen MoE on the same Spark. Dual-resident is not an option: the live Qwen container holds most of the unified memory, and Flint&#8217;s weights plus KV cache need headroom for long context. The flint-swap kit on the box therefore hard-refuses co-residence: stop Qwen before start Flint (or the reverse), wait for <code>MemAvailable</code>, serve only one engine on port 8888. That leaves memory for KV cache and a usable context window instead of two half-starved models fighting UMA. Daily use is a bakeoff swap, not a simultaneous load. </p><h2>What Pi is, and why I drive Flint from Windows with it</h2><p><a href="https://pi.dev/">Pi Coding Agent</a> is a minimal terminal harness: tools, sessions, packages, and a <code>models.json</code> provider map. It does not force a cloud vendor. You point an OpenAI-compatible <code>baseUrl</code> at whatever serves completions. That is the right shape for a Spark tunnel: Flint answers on <code>http://127.0.0.1:8888/v1</code> after SSH port-forward from Windows; Pi&#8217;s <code>spark</code> / <code>flint</code> entry talks to that endpoint; the same Pi session can load browser packages. </p><p>I use Pi on Windows because the editor and browser work stay on the laptop, while the heavy model stays on Spark. Install is a one-liner (<code>irm https://pi.dev/install.ps1 | iex</code> or npm). Provider config is a JSON file under <code>~/.pi/agent/</code>. Mid-session <code>/model</code> switches are cheap. Package install (<code>pi install npm:&#8230;</code>) pulls extensions into the agent tree without rewriting the harness. For local Flint that means: keep <code>ssh spark</code> tunnel up, confirm <code>/v1/models</code> lists <code>flint</code>, launch <code>pi --provider spark --model flint</code>, and let Flint select tools. </p><p>Pi is also where browser automation attaches. The coding model (Flint) chooses <em>when</em> to call a browser tool. A separate decision path (Jev, or the Pi model itself under another policy) chooses <em>which</em> page action to take. That split matters: you do not want a 40B coding MoE burning tokens on every click candidate if a System One classifier can answer a structured multiple-choice observation cheaper. </p><h2>Browser agent options, and why I tested Jev</h2><p>Three surfaces showed up in the same &#8220;browser agent&#8221; ask on this host: </p><ol><li><p><strong>`agent-browser` / `pi-agent-browser`</strong> &#8212; Playwright CLI attach or open. Good when you need a real profile, extensions, or an already-logged session. Prior Pi runs hit Windows path ENOENTs under Git Bash <code>/tmp</code> and &#8220;do not open a new window&#8221; constraints when the goal assumed one shared Chrome. </p></li><li><p><strong>`@injaneity/pi-computer-use`</strong> &#8212; host desktop computer use. Correct for the active OS window, wrong for an isolated web decision loop with recorded steps. </p></li><li><p><strong>`pi-jev-browser` (Jev / TypeSafe System One)</strong> &#8212; isolated Chromium, structured DOM observations, one multiple-choice action per step. Jev does not consume screenshots on the decision path. Docs live on <a href="https://pi.dev/packages/pi-jev-browser">pi.dev</a> and the package README. You need a TypeSafe or OpenRouter API key for the <code>typesafe</code> policy; the default <code>pi</code> policy can answer from the session model with no second key. </p></li></ol><p>I tested Jev because the goal was a bounded public-page loop with status codes (<code>done_unverified</code>, <code>blocked</code>, <code>needs_review</code>), step video/screenshots for verification, and no requirement to inherit daily Chrome Google login. Isolated profile is a feature for smoke tests and news retrieval; it is a limitation for Gmail. On this Windows host the Ada Lovelace Wikipedia goal returned <code>done_unverified</code> / <code>model_done</code> in 4 steps and 3680 ms at <code>https://en.wikipedia.org/wiki/Ada_Lovelace</code>. That is the clean proof the stack works. News sites that interpose robot gates return <code>model_blocked</code> by design. </p><p>The rest of this post is the operator path: Spark swap, Pi on Windows, Windows Playwright patches, <code>jev_run</code> prompts, and the screenshots from those runs. </p><h2>How the stack is wired</h2><p>Figure 1 is the control path after the Spark tunnel answers: Windows Pi prompts Flint; Flint selects <code>jev_run</code>; Jev returns one action from a structured page observation; Playwright mutates isolated Chromium; Pi verifies from returned title, URL, and page text.</p><p> </p><div
