# CLAUDE CODE ORCHESTRATION

<h1><strong>1. Introduction</strong></h1><p>For years, the developer&#8217;s relationship with AI followed a single pattern: chat and wait. Each task required constant human steering &#8212; babysitting the model through every intermediate step while watching the context window bloat with each turn. As conversations grew longer, focus degraded, and the session became a graveyard of volatile, non-repeatable logic.</p><p>Claude Code&#8217;s orchestration model shatters this constraint. With three distinct collaboration primitives &#8212; Dynamic Workflows, Subagents, and Agent Teams &#8212; developers can now match the execution model to the actual structure of the problem. Choosing the right primitive is no longer a nice-to-have; at enterprise scale it is a cost and quality decision.</p><p><strong>The Core Insight</strong></p><p>The question is no longer &#8220;How do I prompt Claude for this?&#8221; &#8212; it is &#8220;What execution model best fits the structure of this problem?&#8221; Dynamic Workflows, Subagents, and Agent Teams solve different problems. Using the wrong one wastes tokens, time, and trust.</p><p>This guide covers three things: what each primitive is, where it differs from the others, and how to pick the right one for your situation. It concludes with a scenario decision matrix you can use as a day-to-day reference.</p><h1><strong>2. Dynamic Workflows: The Orchestration Runtime</strong></h1><h2><strong>2.1 What Dynamic Workflows Are</strong></h2><p>Introduced in research preview on May 28, 2026, <a href="https://claude.com/blog/introducing-dynamic-workflows-in-claude-code">Dynamic Workflows</a> are Claude Code&#8217;s new orchestration layer for problems that are too big for a single agent pass. The feature is available on Max, Team, and Enterprise plans across the Claude Code CLI, VS Code extension, Desktop app, and the Claude API (including Amazon Bedrock and Vertex AI).</p><p>The core mechanism: when you include the word &#8220;workflow&#8221; in a prompt, or when the /effort ultracode setting is active, Claude does not simply respond. Instead, it generates a JavaScript orchestration script on the fly. That script holds all loops, branching logic, and intermediate variables. Claude then runs the script, which fans work out across tens to hundreds of parallel subagents, has adversarial agents attempt to refute findings, iterates until answers converge, and returns only the verified result.</p><p><strong>The Paradigm Shift</strong></p><p>In standard Claude Code, Claude IS the orchestrator &#8212; making turn-by-turn decisions whose intermediate results accumulate in the context window. In Dynamic Workflows, a generated JavaScript script IS the orchestrator. Claude&#8217;s context window holds only the final verified answer, not the exhaust of every intermediate step.</p><h2><strong>2.2 Key Technical Properties</strong></h2><ul><li><p>Scale: up to 1,000 agents per workflow run, with 16 running concurrently to bound local resource use</p></li><li><p>Adversarial verification: independent agents are tasked with refuting each other&#8217;s findings; only claims that survive cross-examination are surfaced</p></li><li><p>Convergence-driven iteration: the workflow keeps spawning agents and iterating until answers stabilize &#8212; the number of passes is determined by the work, not preset by the user</p></li><li><p>Caching-backed resumability: if a run is paused or interrupted, completed agents return cached results instantly on resume; no work is repeated</p></li><li><p>Background execution: runs do not block the CLI; you can continue working while agents execute</p></li><li><p>Inspection: use /workflows view to drill into any phase, inspect prompts, and examine tool calls without stopping the engine</p></li><li><p>Activation: include the word &#8216;workflow&#8217; in your prompt, or set /effort ultracode for automatic triggering</p></li></ul><h2><strong>2.3 Built-in Workflow: /deep-research</strong></h2><p>The /deep-research command is the premier bundled workflow. Unlike standard search tools that accept the first plausible answer, /deep-research is explicitly designed to disprove its own findings. It fans searches across multiple angles, cross-checks sources against one another, holds an internal vote on each claim, and includes only claims that survive adversarial scrutiny. The output is a cited research report with a higher reliability bar than a single-pass AI search.</p><h2><strong>2.4 Built-in Workflow: /effort ultracode</strong></h2><p>Setting effort to ultracode activates automatic workflow orchestration. In this mode Claude evaluates each request and decides on its own whether the task warrants a workflow. When it does, Claude plans an understand-change-verify loop: one subagent cluster to map the architecture, a second to execute changes, a third to verify results. This loop runs automatically. Token cost and time are higher than a standard prompt, but success rates on multi-stage engineering tasks are substantially better.</p><h2><strong>2.5 When to Use Dynamic Workflows</strong></h2><p>Use Dynamic Workflows when three conditions are present together: the task is too large for a single context window, the split strategy is unknown in advance, and result quality is more important than token economy. Canonical use cases include:</p><ul><li><p>Large-scale migrations: applying consistent transformation logic across 500+ files in an enterprise codebase</p></li><li><p>Codebase-wide security audits: hunting for specific vulnerability classes or architectural drift across every file in a repository</p></li><li><p>Exploratory bug hunts in unfamiliar codebases: no prior knowledge of how to partition the work</p></li><li><p>Plans that need stress-testing from multiple angles before commitment</p></li><li><p>Any task where independent adversarial review of findings is required before results reach you</p></li></ul><p><strong>When NOT to Use Dynamic Workflows</strong></p><p>Avoid Dynamic Workflows for repeatable, well-defined tasks with predictable token budgets. If you already know the exact workflow and want consistent, cost-predictable execution, a custom Subagent is more efficient. Dynamic Workflows are also overkill for small, bounded tasks where a single agent pass is sufficient.</p><h1><strong>3. Subagents: Repeatable Specialist Workers</strong></h1><h2><strong>3.1 What Subagents Are</strong></h2><p>Subagents are temporary worker instances launched from the current session. Each subagent receives its own isolated context window, executes its task, and returns only a summary of the result. The calling session never absorbs the subagent&#8217;s intermediate logs or raw output &#8212; only the final answer. This keeps the orchestrating session clean and its context focused.</p><p>Claude Code ships three built-in subagent types that cover the most common delegation patterns:</p><ul><li><p>Explore: read-only; designed for rapid codebase search and context gathering without risking writes</p></li><li><p>Plan: read-only; gathers background information during plan mode while the main session continues</p></li><li><p>General-purpose: read and write access; suitable for tasks that mix exploration and execution</p></li></ul><h2><strong>3.2 Custom Subagents</strong></h2><p>When built-in types are insufficient, you can define custom subagents as Markdown files with YAML front matter. Store them in .claude/agents/ (project-scoped) or ~/.claude/agents/ (user-scoped, available across all projects). The key configuration fields are:</p><ul><li><p>description: the primary trigger signal &#8212; Claude reads this to decide when to invoke the subagent automatically; precision here determines reliability</p></li><li><p>tools: constrains which tools the subagent can use, enforcing least-privilege</p></li><li><p>model: select sonnet, opus, haiku, or inherit from the parent session</p></li><li><p>permissionMode: controls file-edit permissions and prompt behavior</p></li><li><p>memory: optionally provides a cross-conversation memory directory</p></li></ul><p>The description field deserves emphasis. Claude uses it as an automatic invocation trigger &#8212; the more precisely it describes both the task and the right moment to invoke the subagent, the more reliably it fires without explicit user prompting.</p><h2><strong>3.3 How Subagents Differ from Dynamic Workflows</strong></h2><p>The clearest distinction is who holds the plan and who determines the split strategy.</p><p>With a standard subagent, you &#8212; or Claude&#8217;s turn-by-turn reasoning &#8212; decide which subagent to spawn, when, and how to aggregate results. The orchestration logic lives in your head or in the session. Subagents are the execution units; the coordination is human-directed.</p><p>With Dynamic Workflows, Claude generates the orchestration script itself. The script decides how many subagents to spawn, how to partition the work, when to run adversarial verification passes, and when results have converged sufficiently to stop. The orchestration burden shifts from human to machine. Dynamic Workflows can also internally spin up subagents as part of the workflow &#8212; so the two mechanisms are composable, not exclusive.</p><div class="captioned-image-container"><figure><a well-defined task. Canonical use cases:</p><ul><li><p>Code review enforcing a specific team style guide &#8212; define once, invoke on every PR</p></li><li><p>Test generation against a known framework &#8212; same prompt, same tools, same model, every time</p></li><li><p>Documentation updates following a fixed template &#8212; deterministic, auditable output</p></li><li><p>Parallelizing independent tasks with no ordering dependencies (e.g., fix bug in service A while reviewing PR in service B)</p></li><li><p>Any context isolation need &#8212; offload a long-running read task to keep the main session clean</p></li></ul><div class="captioned-image-container"><figure><a class="image-link image2" href="https://substackcdn.com/image/fetch/$s_!lpGh!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F4a7ef0cd-5a21-4e42-a546-44cc5a195306_880x149.png" target="_blank"><div class="image2-inset"><source type="image/webp" /><img alt="" class="sizing-normal" height="149" src="https://substackcdn.com/image/fetch/$s_!lpGh!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F4a7ef0cd-5a21-4e42-a546-44cc5a195306_880x149.png" width="880" /><div></div></div></a></figure></div><h1><strong>4. Agent Teams: Collaborative Specialist Squads</strong></h1><h2><strong>4.1 What Agent Teams Are</strong></h2><p>Agent Teams launched as a research preview in February 2026 (Claude Code v2.1.32). They enable multiple Claude instances to work in parallel on different subtasks while coordinating through a git-based shared workspace. Unlike manual multi-instance setups where you orchestrate separate Claude sessions by hand, Agent Teams provide built-in coordination &#8212; agents claim tasks, merge changes continuously, and resolve conflicts automatically.</p><p>The key requirement is Opus 4.6 minimum. Agent Teams are designed for complex, interdependent work where multiple specialists must produce output that is eventually unified into a single coherent artifact &#8212; typically a codebase.</p><h2><strong>4.2 How Agent Teams Work</strong></h2><p>Each member of an agent team is a fully independent Claude session with its own context, its own tool access, and its own area of responsibility. Coordination happens through a shared git repository:</p><ul><li><p>Agents claim work items to avoid duplication</p></li><li><p>Changes are merged continuously as agents complete subtasks</p></li><li><p>Conflicts are resolved automatically by the coordination layer</p></li><li><p>The team keeps running until all claimed work is complete and merged</p></li></ul><p>This coordination model means agents are not just parallel workers &#8212; they are aware of each other&#8217;s progress and output. A backend agent knows when the API contract it must conform to has been updated by a frontend agent.</p><h2><strong>4.3 How Agent Teams Differ from Subagents and Dynamic Workflows</strong></h2><p>The critical difference from Subagents is the coordination model. Subagents are independent &#8212; they do not communicate with each other or share state. They receive a task, complete it, return a result, and disappear. Agent Teams are collaborative &#8212; members share a working environment, observe each other&#8217;s changes, and coordinate around a common artifact over time.</p><p></p>
