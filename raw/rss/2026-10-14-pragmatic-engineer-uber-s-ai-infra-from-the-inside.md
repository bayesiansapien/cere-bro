href="https://x.com/udaykiran?lang=en">Uday Kiran Medisetty</a>. Uday is one of the few Distinguished Engineers at the company, and leads much of the work on agentic AI, today.</p><p>With Uday, we talk through how Uber&#8217;s developer infrastructure prepared it for AI agents. We look at the systems Uber built before generative AI and the new tools that connect agents to its code, internal services, and engineering knowledge. Uday explains how engineers use background agents, why tools like Slate make development (and bugfixing!) more efficient, and how code review is changing. We also cover Uber&#8217;s approach to token costs and how it measures productivity as the engineer&#8217;s role changes.</p><h3><strong>Takeaways from the conversation with Uday</strong></h3><div class="youtube-wrap" id="youtube2-MDUYSMJmi8A"><div class="youtube-inner"></div></div><p>Here are 11 interesting learnings from today&#8217;s episode:</p><p><strong>1. Uber&#8217;s service count changed erratically:</strong> in 2015, when Uday joined, there were two services in total. By 2019, there were thousands. In 2026, there will be about the same number of services than in 2019, even though the business is about 10x larger than back then!</p><p><strong>2. Uber built most services in-house because off-the-shelf software could not handle its scale &#8211; or simply did not exist! </strong>Examples of services Uber built because it had to:</p><ul><li><p><strong>uOwn</strong>: shows who owns a service or asset. Back in 2015, no such vendor existed.</p></li><li><p><strong>M3DB</strong>: Uber was emitting about 500 million metrics per second, with no vendor being able to handle this load, so they built it themselves. Observability company<a href="https://chronosphere.io/"> Chronosphere</a> was built on top of the open sourced M3DB, and we previously covered<a href="https://newsletter.pragmaticengineer.com/p/how-uber-built-its-observability-platform"> how Uber built its observability platform</a>.</p></li><li><p><strong>Cadence</strong>: a durable workflow engine for multi-day flows like driver onboarding. No such system existed at the time when Uber needed it.<a href="https://temporal.io/"> Temporal</a> was built on top of the open sourced Cadence framework.</p></li><li><p><strong>Morpheus</strong>: a system combining feature flags <em>and</em> experimentation, including switchback tests, with support for two- and three-sided marketplaces that Uber operates. Again, no such solution existed when Uber needed it.</p></li></ul><p><strong>3. At Uber, cities are a first-class concept that go all the way down to physical infrastructure. </strong>Another reason Uber had to build a lot of its custom tooling is how the concept of cities is a &#8220;basic primitive&#8221; that needs to be handled across systems like observability, feature flagging, deployments, and even service sharding. For example, in the early days, some services had their database sharded by cities. Even today, each city is pinned to a cloud region, and can fall over to another region at any time. <em>We previously covered<a href="https://newsletter.pragmaticengineer.com/p/uber-move-to-cloud"> </a></em><a href="https://newsletter.pragmaticengineer.com/p/uber-move-to-cloud">how Uber moved from bare metal to the cloud</a><em>.</em></p><p><strong>4. A single AI model gateway has paid lots of dividends. </strong>In 2023, Uber&#8217;s platform team made the decision that everything built with AI needs to be model- and harness-agnostic. They built Model Gateway to support switching between Anthropic, OpenAI, other vendor models, and now also supports open models they run. Having the Model Gateway in place made it easy to extend with these parts:</p><ul><li><p><strong>AI Guard</strong>: a middleware run by the security team. It checks all requests and responses, and measures latencies (and flags overly slow models or queries)</p></li><li><p><strong>Spend tracking:</strong> spend is tracked per user</p></li><li><p><strong>Visibility</strong>: audit logs and session traces</p></li></ul><p><strong>5. AIFX allows engineers to switch harnesses without losing settings. </strong>Uber currently supports Claude Code, Codex, and OpenCode as harnesses. AIFX (short for AI Foundations) is a wrapper on top of all of these, so when an engineer changes harnesses, all their settings, skills and plugins move with them.</p><p><strong>6. Uber has a hybrid approach to AI spend: </strong>engineers get allocated a spend tier. When they hit the limit, their manager can sign off to spend more in that month. Basically, for the right type of work, there is no spend limit, but Uber doesn&#8217;t want engineers to carelessly burn tokens.</p><p>A plugin called CostCheck works across sessions and gives tips on how to improve an engineer&#8217;s cost profile. <em>Uber has reduced token costs by about 50% the last few months, as we<a href="https://newsletter.pragmaticengineer.com/i/214037819/uber-ai-costs-down-50"> </a></em><a href="https://newsletter.pragmaticengineer.com/i/214037819/uber-ai-costs-down-50">previously covered.</a></p><p><strong>7. All PRs are still reviewed by engineers, but Uber built tools to help devs decide how much time they need to spend on each code change. </strong>Uday admits that code review has become a big bottleneck inside the company, and Uber built Code Review to make it easier and more efficient for devs to do these reviews.</p><p>By the time a dev reviews a change, AI code review has run, screenshots and videos of the feature have been added (when applicable), and risk scores are assigned to the change.</p><p><strong>8. Uber had to declare an internal &#8220;code red&#8221; for its CI system earlier this year. </strong>This was because CI jobs more than doubled in a 12-month timeframe, pushing load on CI systems overly high. To keep build speeds at bay, the team moved simple CI jobs (eg linting, build and template rules) to the &#8220;inner loop:&#8221; so agents run these commands with the <em>afx validate</em> command before opening a PR.</p><p><strong>9. Uber tags PRs by the type of work each of those PRs do. </strong>In the past, Uber measured &#8220;PR velocity:&#8221; how long it took for a PR (or, as Uber calls it: a &#8220;diff&#8221;) to get to production. With agents, doing so makes less sense, because it&#8217;s easy to create dozens or even hundreds of PRs, and many of those PRs might have no business impact on the product.</p><p>&#8203;So Uber now tags all PRs by type: feature, bugfix, maintenance, testing, or docs.</p><p>&#8203;They are seeing the percentage of &#8220;feature PRs&#8221; going up, and the percentage of &#8220;maintenance PRs&#8221; going down.&#8203;</p><p>I find this categorization to be a clever approach!</p><p><strong>10. The job of a software engineer inside a place like Uber is to build context. </strong>As Uday reflects on how the job has changed:</p><blockquote><p>&#8220;The job of engineering is, in some sense: &#8216;how do you build the right context for the agents to produce reliable output?&#8217;</p><p>You need to get really good at context engineering.</p><p>Also, [being good at] multitasking has become a thing. Before, it would take so much time to create a PR, so you would be laser-focused on it. But now you&#8217;re constantly switching between so many things. You need to be able to verify your work and pick any code smells from the agent [to avoid] shipping regressions into production.</p><p>Context engineering, ability to multitask, and ability to review and verify the outputs: these skills have become much more important now because you&#8217;re able to parallelize a lot more than before.&#8221;</p></blockquote><p><strong>11. Uber&#8217;s AI tooling was seemingly built in a year: in reality, it was built on top of a decade worth of dev tooling investment. </strong>Minion &#8211; built in 2025 &#8211; is powered by DevPods, which Uber created in 2017. Uber&#8217;s MCP Gateway was fast to build, thanks to existing Thrift and Protobuf registries. Jaeger tracing made Slate routing and Context graph easier, and so on.</p><p>In Uday&#8217;s words:</p><blockquote><p>&#8220;All the things that we built to make life easier for engineers: it makes it easier for our agents as well!&#8221;</p></blockquote><h3><strong>The Pragmatic Engineer deepdives relevant for this episode</strong></h3><p>&#8226; <a
