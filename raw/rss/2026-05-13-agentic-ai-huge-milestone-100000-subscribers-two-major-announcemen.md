The book improved the original articles with enhanced diagrams and code deep dive. </p><p>That book gave us a working vocabulary for the obvious surface area of an agent harness: how it loops, holds tools, manages context, and ships in production.</p><p>But surface-level isn't a system. As we investigated both codebases, we kept finding more &#8212; patterns that sit one layer below the obvious ones, patterns that don't make it into marketing posts because they aren't sexy, but that production teams hit on day one.</p><p>So we wrote ten more.</p><h3>A recap of the first fifteen</h3><p>Each of the original chapters answered a single architectural question. Here is the spine of the book, one line per pattern:</p><ol><li><p><strong>The Harness Paradigm</strong> &#8212; why a model alone is not a product.</p></li><li><p><strong>Tool Architecture and the Tool Contract</strong> &#8212; the boundary between reasoning and consequence.</p></li><li><p><strong>The Query / Agent Loop</strong> &#8212; what happens between the model's tool call and the next turn.</p></li><li><p><strong>Permission Systems and Safety Guardrails</strong> &#8212; gating the destructive set.</p></li><li><p><strong>Tool Orchestration and Execution</strong> &#8212; partitioning safe vs. serial work in a single turn.</p></li><li><p><strong>Context Management at Scale</strong> &#8212; five strategies before compaction.</p></li><li><p><strong>Multi-Agent Coordination</strong> &#8212; when one agent isn't enough.</p></li><li><p><strong>Memory Systems and State Persistence</strong> &#8212; three tiers, one cache.</p></li><li><p><strong>Observability and Debugging</strong> &#8212; distributed tracing for non-deterministic systems.</p></li><li><p><strong>Production Deployment Patterns</strong> &#8212; SDK-first vs. gateway-first.</p></li><li><p><strong>Hook / Event-Driven Automation</strong> &#8212; the layer above the loop.</p></li><li><p><strong>The Skill System Pattern</strong> &#8212; capabilities as content, not code.</p></li><li><p><strong>MCP Integration</strong> &#8212; connecting agents to the world.</p></li><li><p><strong>Model Routing and Provider Abstraction</strong> &#8212; falling back without falling over.</p></li><li><p><strong>Structured Output and Schema-Constrained Generation</strong> &#8212; when free text isn't enough.</p></li></ol><p>Read together they describe the chassis of a production agent. But chassis alone doesn't move. The systems we shipped also needed plumbing &#8212; and the plumbing is where most of the operational pain actually lives.</p><h3>What was still missing</h3><p>Every team that read the first fifteen patterns and tried to build their own agent ran into the same questions a few weeks in:</p><blockquote><p><em>"How do I count what each session costs me, accurately, across providers and cache categories?"</em></p><p><em>"My user pressed Ctrl-C and a child process kept running. Now what?"</em></p><p><em>"How do users invoke harness behavior &#8212; clear context, log in, dump audit &#8212; without going through the model?"</em></p><p><em>"My agent does `cd /tmp` in one tool call and then `cat README.md`. What does that even mean?"</em></p><p><em>"I want to keep a year of trajectories for compliance. How do I compress them without losing replay fidelity?"</em></p><p><em>"How do I render a streaming agent's output in a terminal that resizes, has modal dialogs, and runs in two processes?"</em></p><p><em>"I changed my session JSON format. Old users on disk have the old shape. Now what?"</em></p><p><em>"How do third parties install code that registers tools, hooks, and slash commands without forking my repo?"</em></p><p><em>"I want a vuln-triage subagent with three tools and an eight-iteration cap. How do I spawn one?"</em></p><p><em>"My API key is in five places. How do I pick the right one, mask it in logs, and refresh on 401?"</em></p></blockquote><p>These are not glamorous questions. They are the questions that decide whether your agent runs for a year or breaks the second it touches a real user. They are the patterns we are publishing next.</p><h3>The next ten patterns</h3><p>The new chapters extend the book from 15 to 25 patterns. They are deliberately <em>under-the-line</em> concerns &#8212; the plumbing that holds a production agent together when the demo is over and the support tickets start arriving.</p><ol><li><p><strong>Cost &amp; Token-Usage Accounting</strong> &#8212; how the harness counts its own spend, attributes to model and cache categories, and gates runaway sessions.</p></li><li><p><strong>Cancellation &amp; Abort Propagation</strong> &#8212; end-to-end interruption from SIGINT through async streams, child processes, and pending dialogs.</p></li><li><p><strong>The Slash Command System</strong> &#8212; the user-to-harness control channel that bypasses the model entirely.</p></li><li><p><strong>Working Directory &amp; File-Path Resolution</strong> &#8212; how the harness anchors the agent's view of the filesystem across stateless tool calls.</p></li><li><p><strong>Trajectory Compression and Replay</strong> &#8212; the offline counterpart to in-flight context compaction.</p></li><li><p><strong>Terminal UI Architecture</strong> &#8212; reactive rendering for streaming agents, in-process React vs. split-process JSON-RPC.</p></li><li><p><strong>Migrations and Schema Evolution</strong> &#8212; the upgrade path for any persisted JSON, SQLite, or YAML the harness writes.</p></li><li><p><strong>Plugin Discovery and Loading</strong> &#8212; runtime extensibility for registering tools, hooks, slash commands, and MCP servers.</p></li><li><p><strong>Specialized Subagent Runners</strong> &#8212; purpose-built downstream agent loops with truncated tool sets and bounded budgets.</p></li><li><p><strong>Authentication and Credential Lifecycle</strong> &#8212; how API keys, OAuth tokens, and provider credentials flow through the harness.</p></li></ol><p>Together they cover what was always there in the codebases but was hard to extract in the first pass: the diagonal across the harness that makes production agents survive contact with reality.</p><h3>How to read these chapters</h3><p>Each new chapter is self-contained but assumes familiarity with the original fifteen.
