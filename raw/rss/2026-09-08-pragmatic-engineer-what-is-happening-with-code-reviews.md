# What is happening with code reviews?

<p><span>One question haunting the minds of CTOs and heads of engineering whom I&#8217;ve been talking with, is how to deal with large quantities of code review which have only been growing now that AI agents generate most code at many tech companies.</span></p><p><span>Since the end of 2025, it has seemed that the era of devs writing code by hand </span><a href="https://newsletter.pragmaticengineer.com/p/when-ai-writes-almost-all-code-what"><span>is over</span></a><span> at startups and in Big Tech. AI agents work faster and generate more pull requests (PRs) than devs ever did, and the size of those pull requests is also increasing.</span></p><p><span>Today&#8217;s article summarizes some approaches to code review at various workplaces in this new paradigm, covering:</span></p><ol><li><p><strong><span>Humans review the AI code reviews. </span></strong><span>The most popular approach: AI code review tools go through code changes, and devs review the review itself.</span></p></li><li><p><strong><span>Triage by &#8220;blast radius&#8221; &amp; decide an approach. </span></strong><span>Low-risk changes don&#8217;t need human review, and high-risk ones do. Adopted by OpenAI, Anthropic, and others.</span></p></li><li><p><strong><span>Review the plan/tests/database schema, but not implementation. </span></strong><span>Focus on reviewing the &#8220;before&#8221; and &#8220;after&#8221; states of an implementation, rather than the implementation itself.</span></p></li><li><p><strong><span>Produce less code. </span></strong><span>Set up AI agents to produce smaller PRs that are easier to review and reason about.</span></p></li><li><p><strong><span>Review everything by hand. </span></strong><span>Not everyone has adopted AI code review tools &#8211; even those that have sometimes still expect devs to read through all the new code, before allowing it to go to prod.</span></p></li><li><p><strong><span>No human code review? </span></strong><span>There&#8217;s more talk about dropping human code reviews than there is evidence of this actually happening, so far. The most I could find was AI startups doing it and building additional layers for safer production rollouts.</span></p></li><li><p><strong><span>Why do we review code, anyway? </span></strong><span>Before figuring out whether or not code review should stay, it&#8217;s worth going back to the fundamental technical, team, and organizational reasons for code reviews.</span></p></li></ol><p><span>Unsurprisingly, it&#8217;s clear there&#8217;s no one-size-fits-all solution to the question of how to handle a deluge of AI-generated code review. </span><em><span>Please leave a comment below about how your team or company deals with this new, pressing issue!</span></em></p><p><span>A snapshot of what&#8217;s going on in code review at this stage of AI development is provided by the graphic from GitHub, below. Triage by &#8220;blast radius&#8221; &amp; choose an approach</span></h2><p><span>Another common approach is to decide whether to review code by hand or with AI, based on how &#8220;risky&#8221; a change is:</span></p><ul><li><p><strong><span>Low-risk change:</span></strong><span> only AI, without human review. It can ship to production once AI agents are happy</span></p></li><li><p><strong><span>High-risk change: </span></strong><span>mandatory human review</span></p></li></ul><p><span>This is the approach that Anthropic and OpenAI follow, which I confirmed by talking with both companies. At Anthropic, Jarred Sumner </span><a href="https://newsletter.pragmaticengineer.com/i/208848940/code-review-and-more-testing-by-ai"><span>told me</span></a><span> that a human merges even low-risk changes, but that their goal is eventually to get another Claude instance to merge low-risk changes.</span></p><p><span>And it&#8217;s not just at leading AI labs: five-person startup, Duckbill Group, a cloud and AI cost management company, changed their process, as </span><a href="https://x.com/mikejulian/status/2096450476170694785?s=20"><span>explained</span></a><span> by cofounder and CEO Mike Julian:</span></p><blockquote><p><span>&#8220;We ditched code review at Duckbill Group (mostly)</span></p><p><span>About a month ago, we found ourselves with 60 open PRs for a team of five. They had been accumulating for a few weeks and we all had the sudden realization we were looking at two days of just code review.</span></p><p><span>I had been tossing around the idea for a while about having AI do all code review and so I just asked the team: what if we just didn&#8217;t review the PRs?</span></p><p><span>We decided to do a couple of things:</span></p><ul><li><p><strong><span>Switch to a risk-based system. </span></strong><span>With a risk-based system, we agreed that if your change touched the public API/MCP, auth, design system, non-additive database schema changes, or agent skills, it needed a human review. We then enforced that with a shell script to add a GitHub label.</span></p></li><li><p><strong><span>Improve our guardrails</span></strong><span> (unit and end-to-end testing, post-deploy observability, stricter linting and type checking, etc). Improving guardrails was pretty easy, just expensive in tokens and attention. We enabled nearly every rule in ruff/prettier/eslint/ty, and we improved our unit test coverage to a floor of 85%.</span></p></li></ul><p><span>Results before vs after:</span></p><ul><li><p><span>PRs merge time: 26h</span></p></li><li><p><span>No human-review median merge time: 1h.&#8221;</span></p></li></ul></blockquote><p><span>Here&#8217;s how I&#8217;d visualize this approach:</span></p><div Review the plan/tests/database schema, but not the implementation</span></h2><p><span>Some devs and teams have stopped reviewing the code (the implementation), and instead review the &#8220;before&#8221; and &#8220;after&#8221; states:</span></p><p><strong><span>Review the plan: </span></strong><span>spend a lot more time on the plan than before, to get a much more detailed spec. Using </span><a href="https://www.aihero.dev/skills-grill-me"><span>The /grill-me skill</span></a><span> by Matt Pocock is a popular method, and I&#8217;m also a fan of it for thorough upfront planning, </span><a href="https://x.com/andreafspeziale/status/2096667130582216767?s=20"><span>as is</span></a><span> Andrea Francesco Speziale, Principal Engineer at Musixmatch:</span></p><blockquote><p><span>&#8220;After 3 hours of /grill-me, it better one-shot the implementation. I&#8217;m not spending a single minute on any review!&#8221;</span></p></blockquote><p><strong><span>Review the tests: </span></strong><span>via Test Driven Development (TDD) &#8211; which is much easier with agents when writing the tests upfront is a chore &#8211; or by focusing the review to ensure the software is tested.</span></p><p><span>One argument for this approach is that customers and users of software usually don&#8217;t care about the code. There&#8217;s a caveat that automated tests can verify a lot of different software &#8211; and are great at verifying business logic &#8211; but they don&#8217;t do a good job at verifying whether a UI </span><em><span>looks</span></em><span> and </span><em><span>feels </span></em><span>good.</span></p><p><strong><span>Review the database schema. </span></strong><span>Jackie Luo, cofounder and CEO of AI startup Sigil, and formerly an engineer at Square, says:</span></p><blockquote><p><span>&#8220;My current take is that all that really matters is the database schema. Speaking from a fast-moving startup perspective:</span></p><p><span>1. Everything, besides data, is fluid and recoverable.</span></p><p><span>2. The schema is the &#8220;hard&#8221; representation of what&#8217;s been built and reveals the riskiest changes, so it&#8217;s a good attention/impact tradeoff.</span></p><p><span>3. Business logic only matters because product behavior matters&#8212;so ideally align on that before interacting with a coding agent at all. Then, once the code is written, use abstractions to understand any other significant decisions made.</span></p><p><span>Understand the product over the code. Use abstractions to translate the latter to the former &#8211; except in the case of schemas!&#8221;</span></p></blockquote><p><span>Jackie&#8217;s point is that data (that is, the state) is the most &#8220;rigid&#8221; part of any system. Stateless business logic is now easy to change because it&#8217;s &#8220;just&#8221; code, and code is easy and fast to generate and regenerate. For startups, it&#8217;s worth getting the data schema &#8211; and thereby your state machine &#8211; right. Then, everything else will be easy and fast to iterate on.</span></p><p><em><span>My sense is this approach makes perfect sense for a startup iterating to get product-market fit. However, once you have a business, you&#8217;ll want to &#8220;guard&#8221; the business logic with tests: else your product could break, and existing users will be unhappy when this happens!</span></em></p><h2><span>4.
