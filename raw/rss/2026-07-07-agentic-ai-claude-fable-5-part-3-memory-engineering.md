# Claude Fable 5, Part 3: Memory Engineering

<p><a href="https://kenhuangus.substack.com/p/claude-fable-5-what-changed-and-how">Part 1</a> argued the leverage moved from prompts to harnesses. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-2-loop-engineering">Part 2</a> argued the harness is a loop. Part 3 is about the part of the loop that outlives every session: memory. If you run Fable 5 loops day and night, the files agents wrote for themselves have become the most valuable and the most dangerous artifacts in the setup. Valuable, because a loop with good memory stops repeating last week's mistakes. Dangerous, because memory is the one channel where a single bad write becomes standing policy, reloaded at every startup, trusted more the older it gets.</p><p>Here's the split. The free half covers what Anthropic shipped and said: the memory system their Fable 5 guide tells you to build, the memory stack and what loads when, the official multi-session pattern, and the poisoning threat model in their own words, including the gap in their own security docs. The paid half is the playbook: the memory prompt block I run, a hardened client-side handler for the memory tool, the startup scan that quarantines suspicious lessons, the audit loop, the dreaming preview and how to fake it tonight, memory cost math with caching, a detection recipe from the newest research, and the weekend project. The working code lives in the series repo, paid subscribers will have access to the Github repo. </p><h2>Memory went official</h2><p>Buried in Anthropic's <a href="https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5">Fable 5 prompting guide</a> is a section called "Construct a memory system," and its first sentence is the thesis of this post: "Claude Fable 5 performs particularly well when it can record lessons from previous runs and reference them." The guide's prescription matches what part 2 called template 2: one lesson per file, a one-line summary at the top, update existing notes instead of duplicating them, delete the ones proven wrong. This is not community folklore anymore. It's the vendor telling you the model was built to use a filesystem as its long-term brain.</p><p>The API grew the matching organ. The <a href="https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool">memory tool</a> is GA on the Messages API, no beta header, and works on Claude 4+ models generally, not only Fable 5:</p><pre><code>response = client.messages.create(
    model="claude-fable-5",
    max_tokens=4096,
    tools=[{"type": "memory_20250818", "name": "memory"}],
    messages=[{"role": "user", "content": "Continue the migration."}],
)</code></pre><p>The design decision that matters is in what that block does not do: the tool is entirely client-side. Claude issues file operations (<code>view</code>, <code>create</code>, <code>str_replace</code>, <code>insert</code>, <code>delete</code>, <code>rename</code>) against a <code>/memories</code> directory, and your application executes them. Anthropic stores nothing. That buys you control over where memory lives, and it hands you full responsibility for what gets into it, which becomes the whole story in a minute.</p><div The lessons directory is distilled knowledge: the index loads every session, the files load on demand. The progress log and feature checklist are project state, read at session start and written at session end. Transcripts and artifacts are raw evidence and never auto-load; they exist so a lesson can point back at proof. Content moves up the stack only by earning it: verified outcomes update the state files, state distills into lessons, and a lesson that keeps proving itself graduates into CLAUDE.md. Moving content up without the intermediate step is how a one-time observation becomes a permanent rule.</p><h2>The multi-session pattern, straight from the docs</h2><p>The memory tool page documents a pattern Anthropic calls multi-session software development, and it's the strongest official statement yet that context windows are for working, not for remembering:</p><div class="captioned-image-container"><figure><a class="image-link image2 is-viewable-img" href="https://substackcdn.com/image/fetch/$s_!g0gQ!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F404d420a-a2ed-4a8c-b55d-602d1a2d0726_2024x1164.png" target="_blank"><div class="image2-inset"><source type="image/webp" /><img alt="Initializer session creates progress log and checklist; Every later session resumes from those files, not from a transcript. And the rule that makes it work is a quote worth pinning above your desk: mark a feature complete "only after end-to-end verification confirms it works, not when the code is written." That's part 2's maker-never-grader rule applied to memory writes; the checklist is a memory file, and unverified completion claims are how it rots. Their <a href="https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents">long-running harness post</a> runs this exact pattern as a case study if you want it worked through.</p><p>The non-obvious win of the initializer session: it forces you to decide what the memory schema is before any agent writes to it. Schema-less memory converges on a junk drawer, and Fable 5 will faithfully read you the junk.</p><h2>Memory poisoning is an official attack class now</h2><p>Part 2 gave you four countermeasures and a warning. Since then the warning acquired primary sources. Anthropic's engineering post <a href="https://www.anthropic.com/engineering/how-we-contain-claude">"How we contain Claude"</a> (May 25) has a subsection titled "Persistent memory poisoning." It names the surfaces: product memory, CLAUDE.md files, mounted workspaces, and the state directories of scheduled and long-running agents. And it names the mechanism that makes this worse than ordinary prompt injection: an injection that reaches memory "reloads at every agent startup." A poisoned web page hits one session; a poisoned lesson file hits every session from now on. Their stated direction: "Good classifiers on session startup will need to become more commonplace." That's a forward-looking need, not a shipped feature, which means for now the startup check is yours to build (the paid half has mine).</p><div class="captioned-image-container"><figure><a class="image-link image2 is-viewable-img" href="https://substackcdn.com/image/fetch/$s_!ah4M!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F78d83d89-0dc2-4a2f-8ab7-8c373f4c794f_2024x1404.png" target="_blank"><div class="image2-inset"><source type="image/webp" /><img alt="Ungated writes turn one injection into standing policy; The memory tool's official security section covers four things: sensitive data, path traversal, file size, and expiration. The words "poisoning" and "prompt injection" appear nowhere on that page. One Anthropic property documents the attack; the other, the tool most exposed to it, doesn't mention it. If you build on the memory tool and stop at the documented checklist, you've secured the filesystem and left the contents unguarded.</p><p>The research is arriving too. A June 29 arXiv preprint by Jun Wen Leong, <a href="https://arxiv.org/html/2606.30566">"Forensic Trajectory Signatures for Agent Memory Poisoning Detection"</a>, shows that successful memory-poisoning attacks leave detectable fingerprints in an agent's tool-call sequence, like a memory recall firing right before an outbound email send. A single hand-written rule hit AUC 0.9563 in their testbed; a 19-feature random forest hit 0.9904. It's one author, not peer-reviewed, and scoped to their architecture, so treat it as early signal rather than settled defense. But the core insight travels: you may not catch the poisoned write going in, and you can still catch the behavior it causes coming out.</p><p>That's the free half.
