Compilers, type checkers, unit tests, and SRE error budgets all ride on reproducible execution. That stack still matters. It is no longer sufficient as the only control plane once the "compute unit" is a sampling model that writes files and shells out.</p><p>Birgitta B&#246;ckeler's 2026 Thoughtworks write-up on <a href="https://martinfowler.com/articles/harness-engineering.html">harness engineering for coding agent users</a> states the formula directly: Agent = Model + Harness. The harness is everything except the model. Guides steer before the agent acts; sensors correct after. Computational sensors (tests, linters, type checkers, hooks) stay cheap and deterministic. Inferential sensors (LLM-as-judge) stay bounded and expensive. The point is not to make the model deterministic. The point is to regulate the codebase with a control system the model cannot rewrite on a whim.</p><p>Anthropic's production containment data shows why human-in-the-loop alone fails as that regulator. In <a href="https://www.anthropic.com/engineering/how-we-contain-claude">How we contain Claude across products</a>, Anthropic reports users approved roughly 93% of permission prompts, then paid less attention as volume rose. An OS-level sandbox cut permission prompts by 84%. Probabilistic oversight saturates. Deterministic isolation and hooks remain.</p><p>Claude Code's own hook contract encodes the same judgment. The <a href="https://code.claude.com/docs/en/hooks-guide">hooks guide</a> and <a href="https://code.claude.com/docs/en/hooks">hooks reference</a> specify that <code>PreToolUse</code> runs before permission-mode checks, including under <code>bypassPermissions</code> / <code>--dangerously-skip-permissions</code>. Exit code 2 or <code>permissionDecision: deny</code> hard-stops the tool. That is harness logic in product form: policy in code, not in a hope that the model "remembers" the rule.</p><h2>The research consensus: keep control flow out of the prompt</h2><p>Across 2025&#8211;2026 papers, the failure diagnosis converges. Multi-agent LLM systems fail first on orchestration, not on raw reasoning. The RO (Reliable Orchestration) line of work, summarized in <a href="https://saurabhjha.one/pubs/DSN26RO/paper.pdf">RO: Reliable Orchestration of LLM Programs</a>, cites plan abandonment, state corruption, and tool-management errors as dominant modes across frameworks and 1,600+ traces. Their fix is a stored program runtime: control and state nodes stay deterministic; generative nodes are bounded oracles behind instruct&#8211;validate&#8211;repair with schema gates. Orchestration correctness becomes independent of LLM sampling.</p><p>Qiu, Ye, and coauthors make the same split concrete in <a href="https://arxiv.org/abs/2508.02721">Blueprint First, Model Second</a> (arXiv:2508.02721, 2025). An expert procedure becomes a source-code Execution Blueprint. A deterministic engine walks the blueprint. The LLM runs only as a tool at bounded nodes. It never chooses the workflow path. On TravelPlanner with the same Claude Sonnet 4 backbone, their Source Code Agent reached a 35.56% final pass rate versus 18.00% for the ATLAS baseline, cut constraint violations by 96.0% (11 vs 275), and used 27.1% fewer steps (10.2 &#177; 0.7 vs 14.0). Same model. Different harness. Different reliability.</p><p>A related formalization appears in <a href="https://arxiv.org/abs/2512.20660">arXiv:2512.20660</a> (2025/2026 dual-state line): treat the LLM as part of the environment, not as the decision-making agent. Workflow state stays a finite deterministic machine. Environment state holds stochastic artifacts. Atomic action pairs bind generation to verification. Guards project opaque model output onto observable workflow truth. Across 13 models on diagnostic probes, they report reliability gains up to 66 percentage points at 1.2&#8211;2.1&#215; baseline cost. That is the paradigm shift in one sentence: stochastic generation stays; stochastic control flow goes.</p><p>Component-level evidence keeps landing on context and action design, not magic prompts. An empirical harness study on SWE-Bench Verified and Terminal-Bench (summarized on <a href="https://www.alphaxiv.org/abs/2609.20804">alphaXiv 2609.20804</a>) finds context management mainly prevents overflow failures as budgets tighten, planning shifts from accuracy scaffold to cost saver as models strengthen, and weaker bash models need predefined tools while stronger models can run cheaper on bash-only interfaces. Harness knobs move accuracy and cost even when the model weights stay fixed.</p><h2>Agentic implementations force the shift</h2><p>Agentic coding systems add three properties deterministic SE never assumed as the default runtime:</p><ol><li><p>Sampling inside the loop. Token draws change the next tool call. Identical prompts do not guarantee identical trajectories.</p></li><li><p>Mutable shared artifacts. The agent edits the same repo humans edit. Merge conflicts and scope violations are first-class hazards, not edge cases.</p></li><li><p>Tool side effects. Bash, package installs, and <code>git_push</code> change the world. A wrong branch is not a wrong string. It is a production incident.</p></li></ol><p>Cognition's <a href="https://cognition.com/blog/dont-build-multi-agents">Don't Build Multi-Agents</a> (Walden Yan) argued that naive parallel agents fragment decisions and lose shared context. Their later <a href="https://cognition.com/blog/multi-agents-working">Multi-Agents: What's Actually Working</a> update still keeps writes single-threaded when multiple agents contribute intelligence. That is harness design: coordination policy outside the prompt.</p><p>HumanLayer's field write-up <a href="https://www.humanlayer.com/blog/skill-issue-harness-engineering-for-coding-agents">Skill Issue: Harness Engineering for Coding Agents</a> reports the same production pattern: sub-agents act as context firewalls so intermediate tool noise never floods the parent orchestrator; verification must stay context-efficient because dumping thousands of passing test lines back into the window makes the agent lose the task. FutureAGI's <a href="https://futureagi.com/blog/agent-harness-production-readiness/">Agent Harness Production Readiness</a> checklist collapses readiness into four failure points: state/memory, control loop ceilings, tool verification, and observability. A chat transcript is not a trace. If you cannot answer which tool failed and what the loop did next from stored data, you cannot debug the incident.</p><p>Production Learning Review's <a href="https://productionlearningreview.com/posts/taxonomy-of-agent-failure-signals-by-harness-layer">taxonomy of agent failure signals by harness layer</a> frames enterprise failures as harness defects: stale context, broken tool schemas, missing approval gates, retry logic without termination. The layering (execution sandbox, tooling, context/memory, lifecycle, observability, verification, governance) matches what coding-agent products now expose as hooks, sandboxes, and permission modes.</p><p>Enterprise practice is converging on the same split. B&#246;ckeler cites OpenAI's public harness notes: layered architecture enforced by custom linters and structural tests, plus recurring drift cleanup, with the hardest remaining work described as designing environments, feedback loops, and control systems. Stripe's "minions" write-up, also summarized there, pushes feedback left with pre-push hooks and blueprints that wire sensors into agent workflows. That is classical software engineering reused as agent regulation, not replaced by a chat transcript.</p><p>Net: deterministic software engineering remains the substrate for compilers, tests, and delivery. Harness engineering is the new control plane for agentic AI implementations because the model is probabilistic, the side effects are real, and production reliability now lives in scopes, hooks, budgets, and verification sensors around the model.
