# Microsoft Agentic Security Tooling, Mapped to MAESTRO: Policy Lives in Four Places

<p>Microsoft has no single place that answers one question for every agent tool call: which tool, with which arguments, may this agent call right now. Article 1 gives the full MAESTRO detail, and this article uses that map and does not repeat it. Article 1 is about <a href="https://kenhuangus.substack.com/publish/post/221857864">AWS Agentic Security Tooling</a>. This is the 2nd in this series.</p><p>A team that migrates the AWS gateway model to Microsoft must stop looking for the Microsoft gateway, and must build the equivalent from four controls that never see every call together.</p><p>Figure 1 is the Microsoft stack on the MAESTRO map: identity, content safety, and framework controls sit on different layers, and no single layer has the tool-policy The paid L1 section states what Azure OpenAI filtering scores, what Prompt Shields blocks only when configured to block, and what stays with the customer.</p></li><li><p>L2 Data Operations &#8212; the stake is retrieved text. A document, a memory record, or a tool result can carry an instruction. Retrieval puts untrusted text into model context. The paid L2 section states what Purview governs, what groundedness scores, and what no Microsoft control validates.</p></li><li><p>L3 Agent Frameworks &#8212; the stake is tool action. A plan becomes real impact only when a tool runs. Tool permission decides that impact. An agent process runs with credentials. Those credentials decide lateral movement. Traces, logs, and evaluations show what an agent did and why. Missing logs remove that proof. The paid L5 section states which audit defaults run 180 days, which hunting window runs 30 days, and which retention and immutability settings need explicit configuration.</p></li><li><p>L6 Security and Compliance &#8212; the stake is identity separation. User identity, agent identity, and tool identity must stay distinct. One shared role leaves unclear who acted. The paid L6 section states the four identity patterns, the licence gate on Conditional Access for agents, and the governance process that must sit around each pattern.</p></li><li><p>L7 Agent Ecosystem &#8212; the stake is peer trust. A peer agent or a tool server needs vetting, registration, and scoped credentials. Registration alone never proves trust. The paid L7 section states what Agent 365 and the org catalog do, what they do not do, and where peer trust remains unbuilt.</p></li><li><p>Five cross-layer attack chains &#8212; the stake is the chain, not one step. Each chain shows the step where a Microsoft control stops it, and the step where a gap lets it pass. The paid chain section gives a test for each chain in a reader's own environment.</p></li><li><p>Control gaps, reference architecture, and builder playbook &#8212; the stake is reuse. The paid closing sections name each gap plainly, split enforcement into identity, content, connector, and framework, and give a copy-ready approval and identity pattern teams can apply on day one.</p></li></ol><h2>How to use this map in a review</h2><p>Start a review with identity. List every agent, and list the identity pattern for each tool that agent can call. Mark each tool as agent-only, on-behalf-of, agent user account, or legacy shared identity. Check whether downstream logs show the user, the agent, or only a shared role. Check whether each agent has a sponsor, and whether each access package has an expiry date. Check whether Conditional Access applies to the agent identity, or whether the licence gate leaves that agent outside Conditional Access. An identity review that finds one shared service principal has found a real finding, not a paperwork issue. An identity review that finds maker credentials on a tool that acts for many users has found a privilege problem that no content filter can fix. An identity review that finds an agent user account with standing user privileges has found a lateral movement path that follows the user, not only the agent.</p><p>Continue a review with routing and configuration. List every tool the agent can call, and mark each tool as Foundry-routed, Copilot Studio-routed, Agent Framework-hosted, or direct API. Mark each Prompt Shields setting as Annotate and block, Annotate only, or absent, for each agent. Mark each sensitive tool as approval-required or not approval-required. Mark each MCP server as whole-server blocked, subset-limited, or unrestricted, and mark each connector as per-tool governed or not governed. Mark each audit store with its retention setting, and mark immutability as configured or not configured. A review that skips that inventory cannot judge coverage. A review that completes that inventory can identify the gaps before it reads any policy text. A review that finds an unwrapped sensitive tool has found a missing deterministic break. A review that finds a direct API path has found a bypass for every routed control.</p><p>Finish a review with a chain test. Pick one chain from the paid section. Run the chain in a test environment with test data, test documents, and test tools. Record the step where a control stopped the chain. Record the step where no control ran. Record whether approval stopped the destructive tool, whether middleware stopped the argument, whether connector blocking stopped the destination, and whether the tool arguments appeared in the hunting dataset. A chain test gives a team evidence, not an opinion. A chain test also gives a team a repeatable check for the next release. A team that runs chain tests on each release will catch a new tool, a new connector, and a new identity pattern before production does. A team that relies on product names will miss each of those changes until an incident reveals them first.</p><p>The paid section maps each layer in turn. The paid section gives the five attack chains, the control gaps, the four-plane reference architecture, and the builder playbook. The paid section links every claim to a primary source. The paid section drops any claim we could not source. The paid section also names each preview limit that affects a production decision. A reader must not place a preview control on a critical path without knowing the limit. The paid section also states, plainly, where Microsoft offers no native control at all. Those gaps are not a criticism of one product. Those gaps are the work a team must plan, fund, and own. A team that plans that work early ships a safer agent. A team that discovers that work after launch causes a delay.</p><div class="paywall-jump"></div><h2>L1: Foundation Models</h2><p>Azure OpenAI Service hosts the model, and Azure AI Content Safety screens the text around it. Content Safety exposes text moderation by severity, Prompt Shields, protected-material detection for text and code, and groundedness detection. Prompt Shields is a unified check for jailbreak attacks on user prompts and for indirect attacks in documents, also called cross-prompt injection. The <a href="https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/content-filter-prompt-shields">Prompt Shields guide</a> states the scope and the Preview limits for tool-response screening. Azure OpenAI DefaultV2, the filter policy new deployments inherit, includes jailbreak Prompt Shields and protected-material detection. The <a href="https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter-configurability">content filter configurability guide</a> states what DefaultV2 contains and what a team can change.</p><p>Enforcement is configurable, not automatic. Prompt Shields can run in Annotate only mode or in Annotate and block mode, per prompt or completion, per category, and per threshold. A team chooses Low, Medium, or High, and a team can set No filters or Annotate only with approval. Spotlighting, which re-encodes document content to separate data from instructions, is an opt-in toggle with a token cost. Document-attack coverage at tool response for Foundry Agent Service agents is Preview. For model API calls, document-attack coverage applies at user input. An agent that bypasses the guardrail gets no coverage by default. A reader must check the configuration for each agent, not the product name.</p><p>Groundedness detection scores whether an answer is supported by the sources a team supplies, sentence by sentence. Groundedness does not verify that a source is authentic, current, unpoisoned, or authorised. Citations trace which chunk an answer cited. Citations do not judge whether that chunk should be trusted. A team that treats groundedness as a detection score will use it to find unsupported answers, and will use approval and identity controls to stop harmful ones.</p><h2>L2: Data Operations</h2><p>Purview governs Microsoft 365 and Foundry interactions with classification, sensitivity labels, data loss prevention, and Insider Risk Management. The <a href="https://learn.microsoft.com/en-us/purview/ai-agents">Purview for AI agents guide</a> states the coverage table plainly. Copilot Studio and Foundry specifically include data classification, sensitivity labels, data loss prevention, and Insider Risk Management. Other agent types are classification-only in that table. Data loss prevention for Copilot can block processing or surfacing of labelled content and sensitive-information-type content in prompts and grounding. Sensitivity labels carry encryption and usage rights that Copilot respects.</p><p>Permission-based grounding is a real control with a clear limit. Copilot grounds on data the user can see. Permission-based grounding stops oversharing to a user who lacks access. Permission-based grounding does not stop a permitted but malicious document. Purview does not validate a retrieval corpus, detect poisoned embeddings, or sign retrieved chunks. Corpus integrity is customer-built work: ingestion allowlisting, access control lists on SharePoint and search indexes, index freshness and deletion handling, and pre-index scanning.</p><p>Memory has the same gap, more severely. Foundry memory search is Preview. No Microsoft document found in the research claims memory-write validation, memory provenance, or poisoning detection. Prompt Shields screens a prompt or a document at inference time. Prompt Shields does not screen the memory store write path. A poisoned memory record can influence a later turn without ever passing a guardrail at write time. A team must own write-path validation, record ownership, and expiry for memory.</p><h2>L3: Agent Frameworks</h2><p>L3 is the centre of this article, because L3 is where Microsoft differs most from <a href="https://kenhuangus.substack.com/publish/post/221857864">AWS Article 1</a>. AWS centralises tool policy outside the model loop at a gateway with a deterministic language. Microsoft has no equivalent product. No Microsoft product deterministically evaluates a policy over agent identity, tool name, arguments, and resource outside the model loop for every agent regardless of host. Policy is split across four places. Entra identity decides who the agent is and what the identity can reach. Content Safety decides what text the model receives and returns. Connector data loss prevention and access control decide which connectors an agent may use. Framework middleware and approval decide what code runs before a tool call. None of those four places monitors every call. A reader who builds the equivalent must wire four controls together and accept that argument-level policy remains code.</p><p>Entra Agent ID gives an agent its own identity. The constructs matter, because each construct changes the audit record. An Agent Identity Blueprint is a template for credentials, including federated credentials, certificates, and secrets. An Agent Identity is a special service principal with no credentials of its own, an own object ID, and a mandatory sponsor. The blueprint impersonates the identity. An Agent User Account is an optional one-to-one user account designated for agent use, for systems that accept only user accounts. Tokens come in two forms. Own-authority tokens carry the agent as subject. On-behalf-of tokens carry the user as subject and the agent as actor. The <a href="https://learn.microsoft.com/en-us/entra/agent-id/identity-professional/microsoft-entra-agent-identities-for-ai-agents">Entra Agent ID identities guide</a> states the constructs and the licensing block. Entra Agent ID reached general availability in spring 2026, after preview at Build in May 2025.</p><p>The licence gate changes Conditional Access coverage. Agent ID itself is available to all Entra customers. Extending Conditional Access, Identity Protection, Identity Governance, and network controls to agents requires Agent 365 plus Microsoft 365 E7, or E5 plus Agent 365, or standalone P1 or P2 plus Agent 365. A bare Entra tenant does not get Conditional Access for agents. A team that writes "Conditional Access applies to agents" without the licence condition is wrong for that tenant. A team that budgets Agent 365 gets a real control: per-agent identity with a sponsor, access packages with expiry, and risk-based controls that can block a compromised agent identity.</p><p>Legacy identity patterns still exist, and a review must name them. A shared service principal leaves unclear which agent acted. Maker-authenticated Copilot Studio tools run under the maker credentials, not the end user credentials. App-only Graph access runs with standing application permissions. Each legacy pattern widens blast radius. Each legacy pattern weakens attribution. A review that finds a shared service principal or maker credentials on a multi-user tool has found a privilege problem that no content filter can fix.</p><p>Foundry MCP tool governance is opt-in per tool. A Foundry MCP tool carries a require_approval setting, including always. Approval submits through the previous response ID with an approve flag. The platform tool-execution layer handles the approval gate, auth injection through the project connection, and retry. Catalog MCP servers let makers pick a subset of tools. The <a href="https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol">Foundry MCP tools guide</a> states the approval mechanism and the catalog model. Copilot Studio MCP governance differs in granularity. MCP servers share Power Platform connector infrastructure, but per-tool data loss prevention and access control exist for connector tools only. Only whole-server blocking exists for MCP tools. The <a href="https://microsoft.github.io/mcscatblog/posts/compare-mcp-servers-pp-connectors/">MCP servers and Power Platform connectors comparison</a> states that granularity gap. The HTTP-request node and any arbitrary endpoint remain an egress bypass. A team must block the HTTP connector or endpoint-filter it.</p><p>Human approval is framework-level and opt-in per tool. Agent Framework provides approval-required function wrappers and middleware that intercepts a call and waits. AG-UI carries the approval request to a frontend, so a human sees the tool and the actual arguments, not the model explanation. Foundry MCP require_approval does the same for Foundry tools. No default-deny approval exists. A developer must wrap or mark each sensitive tool. The <a href="https://learn.microsoft.com/en-us/agent-framework/agents/tools/tool-approval">Agent Framework tool approval guide</a> states the wrapper and middleware pattern. A team must inventory every tool, mark each sensitive tool, and test that an unwrapped tool cannot reach a destructive action by accident or by prompt injection.</p><p>Microsoft Agent Framework 1.0 reached general availability on 3 April 2026, after public preview in October 2025. AutoGen entered maintenance mode on 2 October 2025, with no new features and community management, and new users start with Agent Framework. Semantic Kernel still ships releases, but Semantic Kernel is the predecessor path. Semantic Kernel and AutoGen are not co-equal current recommendations. Foundry Agent Service is generally available. Hosted Agents are generally available as a service, but the .NET and Python hosting SDK packages were still prerelease on the Learn page. Service maturity and SDK maturity differ, and a team must plan for both.</p><p>Figure 2 is the policy split: four Microsoft controls each monitor part of a tool call, while the AWS gateway in <a Azure Private Endpoints and Private Link, network security groups, Azure Firewall, and virtual network rules are the standard controls. Defender for Cloud AI checks include use of private endpoints and restriction of endpoints. A team must configure private networking per project.</p><p>Secrets follow the Azure pattern: Azure Key Vault with managed identities. Defender for Key Vault exists as a plan. Teams must avoid keys in code and use DefaultAzureCredential. Foundry project connections store auth for tools, and a team must review the scope of each connection. A broad-scope connection is a standing credential until a human revokes it.</p><p>Defender for Cloud covers Foundry workloads through the Defender for AI Services plan, including Azure OpenAI and Model Inference. AI security posture management issues recommendations on identity, data security, internet exposure, infrastructure-as-code misconfigurations, and attack-path analysis, including grounding and fine-tuning data exposure and multi-cloud paths. Defender for Cloud is posture and detection, not runtime tool-call blocking. Defender for Cloud posture differs from Defender XDR runtime blocking for Copilot Studio. Only the second control stops a Copilot Studio tool invocation at runtime.</p><p>Sandboxing is qualified, not universal. Foundry Code Interpreter is generally available as sandboxed Python execution. Secondary detail, treated as qualified here, describes Container Apps dynamic sessions with Hyper-V isolation, same-region execution, no outbound network, a one-hour session, and a 30-minute idle limit. That no-egress property applies to the built-in interpreter only, not to a hosted agent own code, a custom tool runner, or browser and computer-use tools. Browser and computer-use tools are Preview, with isolated Playwright sessions and explicit Microsoft warnings that page instructions can cause unintended actions and that human approval is recommended for consequential actions.</p><h2>L5: Evaluation and Observability</h2><p>Foundry tracing captures end-to-end execution, including requests, tool invocations, and responses, with OpenTelemetry semantics. Built-in evaluators cover coherence, relevance, groundedness, retrieval quality, and safety. Custom evaluators are Preview. Foundry Insights, in public Preview since September 2026, groups recurring behaviour problems from saved traces. Insights is human-controlled and does not auto-fix or auto-deploy. Azure Monitor and Application Insights provide the infrastructure. Copilot Studio MCP and connector tool executions log to Application Insights. Foundry traces flow to Monitor and Log Analytics. Completeness is instrumentation-dependent for hosted and custom agents. OpenTelemetry must be wired. A locally run Agent Framework agent with no exporter leaves no platform trace.</p><p>Defender XDR and Sentinel correlation is connector-dependent. Microsoft Sentinel AI-agent monitoring centres on Agent 365 Observability, which carries prompts, session and conversation IDs, agent identities, MCP and connector invocations, tool arguments, tool responses, payloads, and errors. Copilot Studio agents get real-time Defender runtime protection that can block unsafe tool invocation and prompt injection. Correlation exists for agents onboarded to Agent 365 and Sentinel connectors, not automatically for every Foundry hosted agent or third-party agent. A team must test that a tool call appears in the hunting dataset before an incident, not during one.</p><p>Audit trails are not immutable, complete, and on by default. Purview Audit is on by default for Microsoft 365 E3 and E5, with a 180-day default for Copilot records. Audit Premium one-year auto-retention covers Exchange, SharePoint, OneDrive, and Entra, but not Copilot. Longer Copilot retention needs a custom policy and eligible licences. Defender XDR retains 180 days, with 30 days in Advanced Hunting, unless a team streams to Sentinel. Immutability is not a default property of any of these stores. Immutability requires customer configuration: retention and lock policies, export to an immutable store, and Sentinel data-lake retention. Tool-argument completeness also varies by deployment. Sentinel Agent 365 data claims arguments and responses, but Foundry trace retention, prompt-content handling, and third-party-agent coverage must be verified per deployment. Microsoft gives no immutable audit trail by default. The retention numbers above, plus the configuration a team must add, define the gap that remains.</p><h2>L6: Security and Compliance</h2><p>Purview, Defender, and Entra form the governance triad, with the licence caveat from L3. Purview gives classification, sensitivity labels, data loss prevention for Copilot prompts and grounding, Insider Risk Management, retention, eDiscovery, and audit. Defender gives posture through Defender for Cloud, runtime protection through Defender XDR for Copilot Studio, and threat detection. Entra gives Conditional Access, Identity Protection, Identity Governance with access packages and expiry, Privileged Identity Management, and Global Secure Access network controls. Access packages with expiry are a genuine lifecycle control for agent permissions.</p><p>Agent identity in production takes four patterns, and the audit record depends on which pattern a team chose. Agent-only identity runs app-only, with the agent as subject. On-behalf-of identity runs with the user as subject and the agent as actor. Agent user account identity runs through a user account where a system requires one. Legacy identity runs through a shared service principal or maker credentials. The pattern is a per-tool and per-connection choice. A review must list each tool, name the pattern for that tool, and check whether downstream logs show the user, the agent, or only a shared role. A secondary deep-dive notes a privileged-role guardrail for agents, including no Global Admin, no Privileged Role Admin, no User Admin, and no tenant-wide write Graph permissions even with admin consent. That guardrail remains qualified until a primary Learn page confirms it.</p><p>Figure 3 is the identity pattern map: each pattern changes who the downstream system identifies, and each pattern changes Microsoft Commercial Marketplace through Partner Center gives the transact layer. Copilot Studio sharing covers specific users and groups, org-wide sharing, and link sharing, with owner-retained edit rights. Foundry gives an agent catalog and a tool catalog. Copilot Studio supports A2A connections alongside Fabric, Foundry, and Microsoft 365 SDK agents. A Foundry A2A tool is Preview.</p><p>No Microsoft signed agent registry exists. No agent-card attestation scheme operated by Microsoft exists. No A2A peer-agent policy language enforced by Microsoft exists. A2A signed cards are an optional protocol feature, and Microsoft A2A support does not by itself verify a peer card signature. Copilot Studio A2A guidance explicitly leaves introducing authentication on the A2A endpoint as a developer next step. Marketplace and Partner Center review is curation plus tenant-admin approval, not attestation. A listed agent is not cryptographically proven to be the agent it claims. The <a href="https://learn.microsoft.com/en-us/microsoft-365-copilot/extensibility/publish">publish agents for Microsoft 365 Copilot guide</a> states the catalog and marketplace model. A team must treat discovery trust as catalog approval trust, not as cryptographic trust. Revocation runs through role-based access control, blocking, and deletion in the catalog and Entra, not through certificate revocation of a signed card.</p><h2>Five cross-layer attack chains</h2><p>Chain 1 is poisoned retrieval to destructive tool use, L2 to L1 to L3. An attacker places an instruction in a document a user can read. The agent retrieves the document. The model follows the instruction. The agent calls a destructive tool. Microsoft stops this chain at four points, and none of those points is deterministic by default. Prompt Shields indirect-attack screening stops the chain where enabled and set to block, including tool-response screening in Preview. Permission-based grounding stops oversharing, but not a permitted malicious document. Data loss prevention blocks labelled and sensitive content, but not an unlabelled instruction. Least-privilege agent identity limits the blast radius, but not the instruction itself. Approval on the destructive tool is the only deterministic break, and approval is opt-in per tool. EchoLeak, CVE-2025-32711, a zero-click Copilot exfiltration case with CVSS 9.3 reported in secondary sources, proves this class in this ecosystem. Test chain 1 with a permitted document that carries a test instruction, and record whether approval stopped the tool call. A test that relies on a filter alone has not tested the deterministic break.</p><p>Chain 2 is tool-argument injection that bypasses content filters. Content filters screen prompt and response text, and where configured they screen tool results. Content filters do not judge the semantic validity of tool arguments the model itself generated. A filter-passing prompt can still yield a destructive, well-formed argument on a permitted tool. Microsoft stops this chain with framework middleware argument validation written by a developer, approval gates that show the actual arguments through AG-UI, identity and role-based access control on the downstream API, and connector data loss prevention. No argument allowlist exists by default. No range or type policy exists outside the model loop. Test chain 2 with a benign-looking argument at the edge of the permitted range, and record whether middleware, approval, or the downstream API stopped it. A test that checks only filter scores has not tested argument validity.</p><p>Chain 3 is a compromised MCP server or connector that exfiltrates agent context. MCP tool descriptions and tool results are model input. A compromised server can poison both. A compromised server can exfiltrate whatever context the agent sends it. Microsoft stops this chain with whole-server data loss prevention blocking, virtual network and private connectivity for select servers, project-connection auth scoping, subset-of-tools selection, require_approval, Defender runtime blocking for Copilot Studio, and Sentinel tool-argument logging for forensics. No audited MCP marketplace attestation exists. Per-tool governance is absent for MCP tools, unlike connector tools. A server an agent is allowed to call is trusted with the payload by design. Test chain 3 with a test MCP server that returns a test instruction in its result, and record whether approval, blocking, or logging caught the exfiltration attempt. A test that checks only server registration has not tested payload trust.</p><p>Chain 4 is agent identity hijack to lateral movement across Microsoft 365 and Azure. Hijacked blueprint credentials, a shared service principal, maker credentials, or an agent user account each move differently. Microsoft stops this chain with per-agent identity plus a sponsor, Conditional Access plus Identity Protection where licensed through Agent 365, privileged-role guardrails treated as qualified here, least-privilege per-tool identities, and Purview and Defender detection. Legacy shared identities and over-broad Graph and API grants weaken the defence. An agent user account with standing user privileges moves with the user permissions, not only with the agent permissions. Test chain 4 by revoking one agent identity and recording which downstream access stops, which access continues through a shared identity, and which access continues through maker credentials. A test that checks only the agent identity has not tested the legacy paths.</p><p>Chain 5 is silent goal drift versus evaluator gaming. Long-running and multi-agent workflows drift. LLM-as-a-judge evaluators can be gamed by style, verbosity, or optimisation to the eval set. Microsoft own Agent Optimizer write-up warns that a fix can pass the eval yet regress on off-eval inputs, which is why human approval is required before applying optimiser candidates. Microsoft stops this chain with Foundry evaluations and trace-linked regression analysis, Insights pattern detection in Preview, and human approval before applying optimiser candidates. No runtime drift detector halts a drifting agent by default. Evals are pre-deployment and periodic, not a runtime policy. Drift is a slow move to a proxy goal with no single violating step. Gaming is optimisation of the metric the evaluator scores while true quality falls. Test chain 5 with a held-out eval set a team never shows the agent, plus human spot review of trajectories.</p><p>Figure 4 is chain 1 with break points: each Microsoft control stops a different step, Identity plane: Entra Agent ID with a sponsor, access packages with expiry, Conditional Access where licensed through Agent 365, and per-tool identities with no shared service principals. Content plane: Azure OpenAI filtering with DefaultV2, Prompt Shields set to Annotate and block where a team needs enforcement, Spotlighting where a team accepts the token cost, and tool-response screening treated as Preview. Connector plane: Power Platform data loss prevention and access control for connectors, whole-server blocking for MCP servers, virtual network and private connectivity for select servers, and HTTP connector blocked or endpoint-filtered. Framework plane: Agent Framework middleware for argument validation, approval-required wrappers on every sensitive tool, AG-UI approval display that shows tool and arguments, and Foundry require_approval on MCP tools. Telemetry plane: Foundry tracing with OpenTelemetry wired, Application Insights for Copilot Studio tools, Agent 365 Observability for Sentinel correlation, and retention and immutability configured explicitly, not assumed. A team that builds only one plane will fail a chain test. A team that builds all four planes, and tests each chain, can answer the central question for each tool: who is the agent, what text did the model receive, which connector may the agent use, and what code runs before the tool call.</p><h2>Builder playbook</h2><p>Step 1: Give each agent one identity. Create one Agent Identity with one sponsor and one blueprint. Do not share a service principal across agents. Do not use maker credentials for a tool that acts for many users. Record the identity pattern for each tool: agent-only, on-behalf-of, or agent user account. Test revocation for each identity, and record which downstream access stops.</p><p>Step 2: Set Prompt Shields to Annotate and block where enforcement is required. Set the threshold per category, and record the setting per agent. Enable Spotlighting where document instructions are a known risk, and budget the token cost. Treat tool-response document screening as Preview, and do not place it on a critical path without a fallback approval gate. Test each setting with a test prompt and a test document, and record whether the call blocked, annotated, or passed.</p><p>Step 3: Mark every sensitive tool for approval. Wrap each sensitive tool with an approval-required function in Agent Framework, or set require_approval on each Foundry MCP tool. Show the tool and the actual arguments in the approval display. Test approval with a benign-looking argument at the edge of the permitted range. Record whether approval stopped the call. A tool without an approval mark is a tool without a deterministic break.</p><p>Step 4: Govern connectors by granularity. Apply per-tool data loss prevention and access control to connector tools. Apply whole-server blocking to MCP servers a team does not trust. Block the HTTP connector or endpoint-filter it. Review each Foundry project connection scope. Test a blocked server and a blocked endpoint, and record whether the agent reached the destination through another path.</p><p>Step 5: Configure audit retention and immutability explicitly. Set a custom Purview retention policy for Copilot records beyond the 180-day default, where licences allow. Stream Defender XDR data to Sentinel before the 30-day Advanced Hunting window closes. Configure retention and lock policies for the export store. Test a tool call end to end, and record whether the tool arguments appear in the hunting dataset. A log a team cannot find during a test will not appear during an incident.</p><p>Step 6: Run the five chain tests before production, and rerun them on each release. Use test data, test documents, and test MCP servers. Record the step where each control stopped each chain. Record the step where no control ran. Fix the missing step with approval, identity scope, connector blocking, or middleware validation, in that order.</p><p>The code below shows the approval pattern in Agent Framework. The pattern wraps a sensitive tool, intercepts the call, and waits for a human decision. The human sees the tool name and the actual arguments, not the model explanation. A team must apply this pattern to each sensitive tool.</p><pre><code>// Approval-required tool wrapper (Agent Framework pattern).

Corpus integrity and memory-write validation remain customer-built. Argument-level policy remains code, not platform. Audit immutability remains configuration, not default. Peer-agent trust remains catalog approval, not cryptographic attestation. Those gaps are the work a team must plan, fund, and own.</p><h2>Key Takeaways</h2><ul><li><p>Microsoft splits agent policy across Entra identity, Content Safety, connector controls, and framework middleware. No single Microsoft control monitors every tool call.</p></li><li><p>Entra Agent ID is identity, not a signed registry. Agent 365 and the org catalog give discovery and approval, not cryptographic attestation.</p></li><li><p>Prompt Shields block only where configured to Annotate and block, only for routed traffic, and tool-response screening for Foundry agents is Preview.</p></li><li><p>Purview governs labels, data loss prevention, and oversharing. Purview does not validate a retrieval corpus or a memory write.</p></li><li><p>Approval is the deterministic break for destructive tools, and approval is opt-in per tool. A team must mark each sensitive tool.</p></li><li><p>Audit defaults run 180 days for Purview and Defender XDR, with 30 days in Advanced Hunting. Longer retention and immutability need explicit configuration.</p></li><li><p>Microsoft is strongest on identity lifecycle and Microsoft 365 data governance, and weakest as a single cross-host tool-policy answer.</p></li></ul><h2>References</h2><ol><li><p>Cloud Security Alliance (2026).
