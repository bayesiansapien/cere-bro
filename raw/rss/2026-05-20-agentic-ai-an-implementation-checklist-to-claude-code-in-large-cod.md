# An Implementation Checklist to Claude Code in Large Codebases

<p>This post turns the patterns from <a href="https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start">Anthropic&#8217;s &#8220;Claude Code at scale</a>&#8221; article into an implementation checklist. Work through the phases in order &#8212; each layer builds on what came before, and skipping ahead is the most common reason setups underperform.</p><h2>Mental model: it&#8217;s the harness, not just the model</h2><p>Claude Code navigates your codebase the way an engineer would &#8212; reading files, grepping, following references &#8212; against the live source on the developer&#8217;s machine. There is no index to maintain and nothing to upload. That means quality is bounded by <strong>how easily Claude can find the right context</strong>, which is shaped by the harness you build around it.</p><p>The harness has five core extension points, Teams that jump to MCP servers before their CLAUDE.md files are clean tend to get worse results, not better.</p><h2>Phase 1: Lay the CLAUDE.md foundation</h2><p>CLAUDE.md files are read automatically at session start. Claude walks up the directory tree from wherever it&#8217;s invoked and loads every CLAUDE.md it finds, so context layers naturally.</p><p><strong>Do this first:</strong></p><ol><li><p>Write a <strong>root CLAUDE.md</strong> that contains only the big picture and critical gotchas. Pointers, not encyclopedias. Anything that doesn&#8217;t apply broadly belongs somewhere else.</p></li><li><p>Add <strong>subdirectory CLAUDE.md files</strong> for local conventions: the build command for <em>this</em> service, the test runner for <em>this</em> module, the naming rule for <em>this</em> domain.</p></li><li><p><strong>Scope test and lint commands per subdirectory.</strong> Running the full repo suite for a one-service change wastes context and times out. Specify the right command in the local CLAUDE.md.</p></li><li><p><strong>Tell developers to initialize Claude in the subdirectory they&#8217;re working in</strong>, not at the repo root. Root context is never lost because of the upward walk, but local context loads first.</p></li></ol><p><strong>Watch for drift:</strong> anything you find yourself repeating across CLAUDE.md files is probably a skill in disguise.</p><h2>Phase 2: Add hooks for things that should be automatic</h2><p>Hooks are scripts that fire at defined moments. Most teams underuse them by treating them only as guardrails. Their higher-leverage use is <strong>continuous improvement and consistent automation</strong>.</p><p><strong>High-value hook patterns:</strong></p><ul><li><p><strong>Stop hook</strong> that reflects on the session and proposes CLAUDE.md updates while the context is fresh. This is how your setup gets smarter over time without anyone scheduling it.</p></li><li><p><strong>Start hook</strong> that loads team- or module-specific context dynamically, so developers don&#8217;t need to configure anything per directory.</p></li><li><p><strong>Lint, format, and check hooks</strong> that enforce rules deterministically. Don&#8217;t ask Claude to remember to run the formatter &#8212; make it run.</p></li></ul><p>If you&#8217;re writing a prompt instruction that says &#8220;always do X,&#8221; ask whether it should be a hook instead.</p><h2>Phase 3: Build skills for specialized expertise</h2><p>Skills are packaged instructions for specific task types. They load <strong>on demand</strong>, which is what makes them the right home for expertise that doesn&#8217;t apply to every session.</p><p><strong>Use a skill when:</strong></p><ul><li><p>The expertise applies to one task type (security review, migration, deployment)</p></li><li><p>It would otherwise bloat every CLAUDE.md</p></li><li><p>It can be scoped to a path so it only activates in the relevant directory</p></li></ul><p><strong>Common mistake:</strong> dumping reusable expertise into CLAUDE.md because it&#8217;s the most familiar tool. If five sessions out of a hundred need the knowledge, it belongs in a skill &#8212; not in the file that loads every time.</p><p>Path-scope your skills aggressively. A payments-deploy skill bound to /services/payments won&#8217;t auto-load when someone is editing the frontend.</p><h2></h2>
