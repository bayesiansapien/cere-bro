# Claude Fable (2 more days), Part 9: Don't Pay Twice for a Fallback

<p><a href="https://kenhuangus.substack.com/p/claude-fable-5-what-changed-and-how">Part 1</a> covered the prompting shift. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-2-loop-engineering">Part 2</a> covered loops. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-3-memory-engineering">Part 3</a> covered memory. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-4-ten-weekend">Part 4</a> turned the loop into a security project portfolio. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-5-fable-scanner">Part 5</a> built the Fable Scanner. <a href="https://kenhuangus.substack.com/p/f99bab01-2c43-495b-a121-8ea40f679681">Part 6</a> turned recurring instructions into ten Fable-native agent skills. <a href="https://kenhuangus.substack.com/p/7336d932-21be-4275-b35d-dc73ec82b57e">Part 7</a> covered fleet migration. <a href="https://kenhuangus.substack.com/p/0b225ef3-1e82-4bcd-97db-06ca77e09901">Part 8</a> wired refusal handling and server-side fallback. This part is about the case where you run the retry yourself, in Ruby, in PHP, over raw HTTP, or in any custom loop, and a hidden second charge shows up on your bill.</p><p>The charge is a cache write. When your first request to Fable 5 primes the prompt cache and then gets refused, a naive retry on the fallback model writes that model's cache from scratch. You paid to write a cache you threw away, then paid again to write a fresh one. On a large system prompt with a one-hour cache TTL, that second write is not rounding error. The fix is a one-time credit token the refusal hands you, which you echo back on the retry so the platform prices it as if the conversation had been on the fallback model all along.</p><p>The free half of this post is the mechanism: why the double write happens, and what the credit token actually does to your bill. The paid half is the redemption code, the exact-body-match rule that makes it work, and a companion check for telling a sticky-routed turn apart from a real fallback.</p><h2>Where the second charge comes from</h2><p>Prompt caching is what makes a big system prompt affordable. You pay a premium to write the cache once, then every later request in the window reads it at a tenth of the input price. A one-hour cache write costs twice the base input rate, so the write is an investment you recover over the reads that follow.</p><p>A refusal breaks that math when you retry by hand.</p><div The classifier declines, so that turn is discarded, and with it the value of the write you just paid for. Then your retry goes out to Opus 4.8 with the same system prompt, and because it is a different model with a different cache, it writes the whole thing again from scratch. Two one-hour cache writes for one conversation that only ever needed one. Nobody sent you a warning, because from the API's side you made two valid requests.</p><p>This only bites when you own the retry loop. The server-side fallback from Part 8, and the GA SDK middleware, both handle the repricing for you. The moment you step outside those, in a language without the middleware or a hand-rolled HTTP client, the double write is yours to prevent.</p><h2>What the credit token buys back</h2><p>The fallback-credit beta changes the shape of the refusal. When you opt in, a declined request comes back carrying a one-time token, and that token is a claim on the cost you already sank into the first attempt.</p><div
