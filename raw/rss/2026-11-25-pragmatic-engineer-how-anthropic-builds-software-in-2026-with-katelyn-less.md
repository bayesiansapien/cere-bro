Her team owns the Claude API and the infrastructure behind products like Claude Code and Claude Desktop.</p><p>We start with Anthropic&#8217;s move from a Python monolith to Rust. Katelyn explains why adding CPU capacity is tricky due to a global CPU shortage, how Claude helped engineers get up to speed in Rust, and how the team used shadowing to verify the rewrite against production traffic. <em>Just today, Katelyn and the team published <a href="https://www.anthropic.com/research/migrating-api-to-rust">a deepdive on their Python &#8594; Rust migration.</a></em></p><p>Katelyn walks us through what the software engineering job looks like today at Anthropic, and how code review and oncall interact with agentic workflows. We also get into the frontier lab&#8217;s &#8220;software factory&#8221;, how a product manager shipped a feature to production, and why Anthropic is replacing traditional coding interviews with agent-based exercises.</p><p><em>As of last week, Anthropic is a publicly traded company, with a market capitalization of around $1T, all while having a tenth of the headcount of other businesses with similar market capitalizations. Learning how Anthropic does software engineering might be instructive for companies that want a similar structure.</em></p><h3><strong>Takeaways from the conversation with Katelyn</strong></h3><p>Here are 12 interesting learnings on how software engineering is changing inside of Anthropic:</p><div class="youtube-wrap" id="youtube2-9oNvKMd7xJo"><div class="youtube-inner"></div></div><p><strong>1. Anthropic rewrote its API from Python to Rust in around five months. </strong>The API called &#8216;Messages API&#8217; serves all Claude tokens externally, as well as for Claude Code and Claude Desktop. This service does authentication, tokenization, billing, and safety checks, then calls the GPU stack to generate tokens. The service was a Python monolith and the team initially optimized Python, but found the performance overhead was still large. Eventually, they decided to rebuild it in Rust. It took a few engineers and a few months in total; all without anyone being expert in Rust!</p><div class="captioned-image-container"><figure><a class="image-link image2 is-viewable-img" Hang on, why was the monolith written in Python in the first place? </strong>Back in 2023, Anthropic was still a research company when it decided to create an API, and the team that built it was small, with a large crossover to Research. It was the case that researchers worked mostly with Python, which made it very easy to integrate the API with inference and other infrastructure code. Similarly, OpenAI&#8217;s API <a href="https://newsletter.pragmaticengineer.com/i/215812293/solving-load-challenges">was also written in Python</a> &#8211; and later rewritten <a href="https://newsletter.pragmaticengineer.com/i/215812293/solving-load-challenges">to Rust</a>. Anthropic and OpenAI faced the same challenge with the Python monolith: the CPU footprint of the monolith started to become a growing problem.</p><p><strong>3. The rewrite was done without Rust experts on the team or strict code reviews. </strong>A year earlier, the same team picked Go for their new services because it was a language that team members knew how to read and write. But by 2026, they felt that Claude was good enough at Rust, and Claude helped engineers learn more about Rust during the rewrite. The team did not do strict code reviews, but had the &#8220;unfair&#8221; advantage of the existing Python API being a perfect test harness. They set up the new Rust API to shadow the current API, and iterated until all responses were identical. Also, Katelyn estimates that engineers looked closely at only ~20% of the code generated:</p><blockquote><p>&#8220;As long as you can really boil something down to make it verifiable in some way, then you don&#8217;t have to look at every single line of Rust code that&#8217;s getting written.&#8221;</p></blockquote><p><strong>4. Anthropic has its own code review agent running at all times. </strong>The company has a Claude code review classifier running for all pull requests. It decides:</p><ul><li><p><strong>Does it need a human review?</strong> For &#8220;mechanical&#8221; and low risk changes like an SDK version bump or using a newer model, Claude can decide there&#8217;s no human review needed. This is also the case for fixing flaky tests, in which case, another Claude does the review, then merges and deploys it.</p></li><li><p><strong>How many human reviews does it need?</strong> For changes that do need human reviews, Claude scores the risk and takes into account additional rules to decide how many human reviews are needed.</p></li><li><p><strong>Which team needs to do a review? </strong>Claude routes the PR to the right teams.</p></li></ul><p><strong>5. A Claude agent is paged before a human for API oncall. </strong>For months, a Claude agent has been shadowing the API oncall rotation of the API team for training. As the team have gained confidence that Claude can tell if an alert is &#8220;real&#8221; or &#8220;noise,&#8221; they now let this agent categorize an incoming alert first. The long-term goal is for Claude to handle actual incidents without waking up a human &#8211; but they&#8217;re not there yet. <em>We cover more on how AI SRE startups are tackling the same challenge in our recent deepdive, <a href="https://newsletter.pragmaticengineer.com/p/ai-sre">AI SRE: what is it, how could it change on-call &#8211; and does it work?</a></em></p><p><strong>6. Onboarding for new Anthropic engineers is &#8220;talk to Claude.&#8221; </strong>New joiners at tech companies used to have &#8220;onboarding buddies&#8221; and engineers who explained the architecture of systems to them, often by drawing boxes and diagrams. Not so at Anthropic, where Claude is connected to the codebase and internal systems, and engineers just ask it to explain how things work. Claude can even create interactive tutorials and visualizations. It&#8217;s pretty similar to how OpenAI engineers use Codex for onboarding, as covered in our <a href="https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux">podcast episode with Tibo Sottiaux</a>.</p><p><strong>7. One thing that hasn&#8217;t changed is the need for planning and alignment. </strong>Katelyn&#8217;s team interacts with Inference, Research, Safety, and App teams. When kicking off a project, a lot of time and effort is spent on getting everyone on the same page. Katelyn says that planning time has not changed much from &#8220;pre-AI&#8221;. The average engineer actually spends more time coordinating than on implementation!</p><p><strong>8. Another thing that has not changed is two-pizza teams</strong>. Teams at Anthropic are still two-pizza teams of around 5-8 people. Katelyn says it&#8217;s because this is the right size for understanding a complex system and staffing an oncall rotation. Teams still own systems, and get paged. And it is a <em>team</em> &#8211; not an individual &#8211; that&#8217;s responsible for each system!</p><p><strong>9. Engineers at Anthropic spend a lot more time building tooling than before. </strong>Even on product teams, engineers are spending a lot more time building tools that help them to accelerate their own work. For example, an engineer on Katelyn&#8217;s team set up a Slack channel that runs a multi-agent team towards a single goal, even though it was not a task assigned to the engineer.</p><p><strong>10. Knowing a programming language well is starting to not matter.</strong> Katelyn invested a lot of time, pre-AI, into learning languages. I asked if it hurts as an engineer to consider that programming languages matter less these days, with AI. Katelyn pointed out that some engineers always cared little about languages, and for engineers who love languages, she says there&#8217;s still work to be done on languages and frameworks themselves.</p><p><strong>11. Katelyn&#8217;s team phased out the coding interview after strong candidates kept failing it. </strong>Candidates who crushed other interviews were starting to fail the coding one because they no longer write code by hand. In the absence of a set replacement, the team is actively experimenting with interviews conducted together with coding agents. The design (architecture) and project deepdive interviews remain unchanged.</p><p><strong>12. For promotions, the &#8220;time to complete a project&#8221; is now meaningless. </strong>Anthropic still has levels and a promotion process. But the time taken to completion is pretty meaningless when a year-long project can now be done in days or weeks with AI! Katelyn says that they fall back on evaluating the impact of projects; for example, how much CPU usage was saved, how much was latency reduced by, or how many incidents were avoided.</p><p><strong>Katelyn&#8217;s message to engineers with an identity crisis: humans have plenty of engineering to solve, related to agents. </strong>She has written about this <a href="https://www.katelynlesse.com/blog/new-problems-for-engineers-to-solve">in detail</a>. The takeaway:</p><blockquote><p>&#8220;This is for the engineers feeling an identity crisis because they think their knowledge and skills won&#8217;t be important: you and your skills can be the difference in whether or not agentic infrastructure-related problems get tackled, and whether multiagent systems can solve the world&#8217;s hardest problems. You can and should go deep in these domains, learn new things, and form opinions. So much of this problem space is wide open for new solutions. It&#8217;s an incredibly exciting time to put your skills to work.&#8221;</p></blockquote><h3><strong>The Pragmatic Engineer deepdives relevant for this episode</strong></h3><p><strong>&#8226;
