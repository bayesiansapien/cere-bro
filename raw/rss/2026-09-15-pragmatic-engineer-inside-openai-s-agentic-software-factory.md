# Inside OpenAI’s agentic software factory

<p><span>It&#8217;s rare to work with an unlimited token budget, but at OpenAI, that&#8217;s what all engineers, researchers, finance colleagues, and marketing folks do. Recently, I visited one of the world&#8217;s leading frontier labs to find out how OpenAI operates today &#8211; and for a glimpse at where software engineering might be headed as a profession.</span></p><p><span>Plenty has changed since I </span><a href="https://newsletter.pragmaticengineer.com/p/san-francisco-is-back"><span>visited</span></a><span> OpenAI&#8217;s headquarters last year. Within a year, Codex has gone from a &#8220;nice-to-have&#8221; tool to being the backbone of pretty much everything at the company.</span></p><p><span>To learn more, I talked with seven engineering leaders and engineers there: Venkat Venkataramani (VP of Engineering, Applied Infra), Sulman Choudhry (Head of Engineering, ChatGPT), Andrew Ambrosino (Lead, Desktop), Joe Gershenson (Lead, Core Agent team), Akshay Nathan (Engineering Lead, Productivity), Ahmed Ibrahim (Engineer, Codex) and Steve Coffey (Engineer, Responses API). </span><em><span>Thanks to all for taking part!</span></em></p><p><span>Today, we cover:</span></p><ol><li><p><strong><span>Codex takes over at OpenAI. </span></strong><span>In a matter of months, nearly all OpenAI&#8217;s non-engineers moved over to Codex and ChatGPT Work without a mandate from above for it.</span></p></li><li><p><strong><span>Death of the IDE &amp; pull requests. </span></strong><span>IDE usage has been down since January when Codex usage started to surge. PRs and code reviews need to be rethought.</span></p></li><li><p><strong><span>OpenAI&#8217;s agentic software factory. </span></strong><span>OpenAI has built a &#8220;software factory&#8221; with several automated, agentic feedback loops: for example, Perf Factory monitors production and kicks off Codex agents to automatically fix performance issues.</span></p></li><li><p><strong><span>How engineering tooling &amp; practices are changing. </span></strong><span>Hand-built internal tools are slowly being replaced by Codex, which is increasingly preferred for debugging over specialized tools. Harness efficiency is critical in software factories.</span></p></li><li><p><strong><span>Engineering for a billion users: how OpenAI scales up its infra. </span></strong><span>They buy first and take it in-house later. Also, geographic infra distribution, capacity planning tactics and challenges.</span></p></li><li><p><strong><span>Making OpenAI&#8217;s API more reliable and performant</span></strong><span>. CPUs are becoming a bottleneck, doing slower deployments on purpose, and solving load challenges.</span></p></li><li><p><strong><span>How the software engineering job is changing. </span></strong><span>Engineering specializations are disappearing, judgment and agency are more important, and it only takes one or two engineers for previously &#8220;impossible&#8221; rewrites and migrations to succeed.</span></p></li></ol><p><em><span>Before we start, a scheduling update: I&#8217;m in New York for the week, attending the LDX3 conference and visiting a few startups and tech companies in the city,  so there will be no edition of The Pulse on Thursday. Whether the visible code is your output or not, agents write your artifacts.</span></p><p><span>Think of it like this: your entire life is via software. Now, almost all OpenAI employees use Codex and ChatGPT Work weekly. So, what happened?</span></p><p><span>OpenAI released the Codex app for Mac in February and for Windows in March, and ChatGPT Work (powered by the Codex harness) in July. Following that, non-engineers there moved all their workflows over to Codex and then to Work.</span><strong><span> </span></strong><em><span>Caveat: OpenAI&#8217;s internal version of Codex is a lot more advanced than its external counterpart because it&#8217;s plugged into pretty much every OpenAI system</span></em><span> &#8211;</span><em><span> similar to how </span><a href="https://newsletter.pragmaticengineer.com/p/why-ramp-built-inspect"><span>Ramp&#8217;s Inspect AI agent</span></a><span> has been wired up.</span></em></p><p><span>The fascinating part of this is that OpenAI got close to 40% adoption across non-engineering teams at a time when the Codex app was hostile to non-engineering users (hard to use). Between February and April, the Codex app still showed the code on-screen, but even so, non-technical colleagues outside of engineering </span><em><span>still</span></em><span> used it because it could do complex work like researching and creating a presentation, document, spreadsheet, or tasks that produce rich output. Today, those folks are very heavy users of it.</span></p><p><strong><span>Being able to work for longer on more complex things drove adoption. </span></strong><span>OpenAI added the /goal setting to Codex, where you can set up a goal for the agent and it keeps working until it is complete. Between April and May, usage surged from 60% to 90%. Andrew believes improvement in the harness&#8217;s handling of long-running tasks was one cause of this:</span></p><blockquote><p><span>&#8220;The number one thing that is changing is that people are starting to use threads for much longer, and this longer usage has been a breakthrough. It&#8217;s surprising to see the sheer length of time that people spend on a thread &#8211; even days! They often set a goal and then have the model crank.</span></p><p><span>Codex being good at longer-running tasks seems to cause people to do fewer things in parallel. This is because a long-running agent often spins off other agents to do other things, reducing the surface area that you, as a human, have to manage.&#8221;</span></p></blockquote><p><strong><span>&#8220;Awareness overhang&#8221; is another cause of the rapid adoption, the Codex team believes. </span></strong><span>As Akshay Nathan, Engineering Lead, Productivity team, told me:</span></p><blockquote><p><span>&#8220;For a long time, we had a &#8216;capability overhang&#8217;: the models were capable but the products didn&#8217;t fully bring that out. Now, we&#8217;re seeing an awareness gap. Some people have figured out they can use Codex to monitor Slack, update Airtable, or create onboarding materials. But many others still use it for one task and then discover more uses from teammates via word-of-mouth.</span></p><p><span>But there&#8217;s still so much more, under the surface, that you can do with Codex.&#8221;</span></p></blockquote><p><strong><span>Role-specific and team-specific plugins are created and distributed. </span></strong><span>Another thing that sped up adoption is that each group started to distribute useful role-specific workflows as plugins. Andrew explained why it&#8217;s important to not just offer a generic coding agent:</span></p><blockquote><p><span>&#8220;If you build a product that can do anything, teams need a way to make it their own. You can&#8217;t just give everyone an empty box. Skills and plugins let teams adapt the agent to their work. Sometimes, we also need a new app capability, like a browser that the agent can use alongside those skills. But the same building blocks already cover a lot of different roles.&#8221;</span></p></blockquote><p><strong><span>Subject matter experts are embedded in ChatGPT Work engineering teams. </span></strong><span>The models have become &#8220;smarter&#8221; than developers in some domains, so devs cannot channel &#8220;taste&#8221; into the harness in those areas. So, people who are domain experts are onboarded onto engineering teams. This is one outcome of ChatGPT Work being used by so many non-engineering domains: experts embedded with engineering advise developers on things like what a good slide deck, spreadsheet, or business report looks like.</span></p><p><em><span>Of course, domain experts being in engineering teams is a decades-old best practice for building quality products. It seems like this gets rediscovered in different contexts every few years!</span></em></p><p><strong><span>OpenAI is fully dependent on Codex and Work. </span></strong><span>This is so much the case that in the event of even a minor outage, internal messages from colleagues alert the Codex and Work teams at the same time as &#8211; or before &#8211; automated alerts.</span></p><p><span>Basically, work happens through Codex and Work, and pretty much </span><em><span>nothing</span></em><span> else. </span><em><span>From the outside, this dependence on a single shared harness is particularly eye-catching; two years ago, there were no AI agents, only advanced AI autocomplete!</span></em></p><h2><span>2. Death of the IDE &amp; pull requests</span></h2><p><span>Late last year, the Codex team was torn about whether to release the Codex desktop app. Andrew recalls the hesitation:</span></p><blockquote><p><span>&#8220;In December 2025, we weren&#8217;t entirely sure if we would release the Codex app. We had the Codex CLI as a terminal, and there are large, feature-rich IDEs out there. So, would there be space for a dev tool that is between a terminal and an IDE? In my head, there was this future where it would not work out, and be the kind of &#8216;misfit&#8217; like the iPad was.</span></p><p><span>A lot of people buy iPads and then never use them: they either use their smaller, more portable smartphone </span><em><span>(which could be the equivalent of the CLI in this metaphor)</span></em><span>, or their feature-rich laptop </span><em><span>(the equivalent of the IDE).</span></em></p><p><span>Also, don&#8217;t forget that in November, Antigravity came out as a VS Code fork. This added to the feeling that perhaps we should have also forked VS Code for the Codex app. But still, we dismissed the temptation and went with our gut feeling that as AI agents get better, IDEs will matter less.&#8221;</span></p></blockquote><p><span>Indeed, since January, IDE usage has gone down and OpenAI&#8217;s bet looks like a good one. However, the Codex app is becoming a </span><em><span>little</span></em><span> more akin to an IDE: for example, the ability to edit files inside the app was shipped in June.</span></p><p><strong><span>CI/CD systems are seeing massive load increases. </span></strong><span>One sign of productivity gains from Codex is the amount of additional code flowing through OpenAI&#8217;s dev infra systems. More code being created and pushed leads to new scaling challenges which the team is currently heads-down on solving. Venkat Venkataramani, VP of Engineering, Applied Infra, said:</span></p><blockquote><p><span>&#8220;The number of pull requests (PRs) per engineer is growing like a hockey stick </span><em><span>(at a very high, accelerating rate)</span></em><span>. Every part of the build-test-deploy pipeline is seeing dramatically more load.</span></p><p><span>We&#8217;re talking about roughly a 10x increase in load on some systems. At most companies, that kind of growth might happen over two or three years. At OpenAI, we see it in about six months.</span></p><p><span>That level of acceleration exposes bottlenecks everywhere: version control has to handle far more code being written and pushed, CI/CD systems have to scale with it, and production release processes have to absorb a much higher rate of change.</span></p><p><strong><span>Every month, we wake up to a new set of infrastructure scaling challenges to solve. </span></strong><span>Just when we think we&#8217;ve created enough capacity for the next phase of growth, the model unlocks another wave of capabilities, which creates a new set of bottlenecks somewhere else in the system.&#8221;</span></p></blockquote><p><strong><span>In this context, PRs and code reviews are being rethought. </span></strong><span>They have &#8220;core primitives&#8221; in software engineering, but this level of development acceleration is an opportunity to reimagine them. Again, from Venkat:</span></p><blockquote><p><span>&#8220;The question we ought to ask ourselves in the middle of all this development acceleration is how do we reimagine many things we took for granted. For example, how do we reimagine the CI (continuous integration) and CD (continuous deployment) process? What does observability mean in this world, and how should people interact with pull requests?</span></p><p><span>If you ask me, the way we do code review today makes less and less sense, and the same is true for pull requests.</span></p><p><span>We&#8217;re now seeing agentic code reviews that look at code changes through a series of different lenses. In the past, it would have been impractical for a cloud infrastructure engineer and a security engineer to review every single code change. With agents, that becomes possible.</span></p><p><strong><span>We can rethink how code is deployed with agents, too.</span></strong><span> We are building an agent that &#8220;handholds&#8221; a change all the way to production &#8212; whether it&#8217;s a code change or a change behind a feature flag. It observes the relevant monitoring graphs, but can also build its own dashboard to monitor important signals. More of our code changes are going to production with this kind of agent monitoring.&#8221;</span></p></blockquote><p><strong><span>An increasingly painful bottleneck is in deploying native mobile apps. </span></strong><span>When there are ten times more pull requests, it&#8217;s challenging to deploy on the backend or the web and more infrastructure is needed to do so. Then, after you rework a CI/CD system and make sure there&#8217;s enough capacity to run them, you&#8217;ll be deploying that many more PRs to production.</span></p><p><span>This arises in the shipping of updates to native iOS and Android apps because every app update needs to go through Apple&#8217;s and Google&#8217;s manual approval processes which take hours or days to complete.</span></p><p><span>Talking with Sulman Choudhry, Head of Engineering, ChatGPT, he explained how the app review bottleneck is affecting iteration speed. Sulman used to work at Facebook and remembers how the social media company sped up shipping mobile releases:</span></p><blockquote><p><span>&#8220;Back in the 2010s, Facebook had a pretty important breakthrough in how to ship native mobile code faster. App Store releases went from monthly to bi-weekly to weekly. At the same time, experimentation and feature flags let teams ship code before it was ready to launch, then turn features on remotely when they were.</span></p><p><span>That model brought a lot more velocity to mobile.</span></p><p><span>In the age of Codex, I think we&#8217;re hitting the next version of this problem. Code generation is getting dramatically faster, but getting that code into users&#8217; hands on native mobile is not. For Codex in particular, where usage is heavily mobile-first, that gap is already becoming painful for us and users.</span></p><p><span>I expect the pressure here to increase quickly. If software can be written in minutes, waiting days or weeks to get it onto a phone starts to look increasingly absurd.</span></p><p><span>We should be aiming for a world where shipping code on native mobile is as fast as shipping on the web. Getting there will probably require some creative rethinking of what we ship, when we ship it, and what can be activated remotely. Today, we&#8217;re nowhere close.&#8221;</span></p></blockquote><p><em><span>There&#8217;s some irony in how shipping a native iOS or Android app has the exact same challenges today as in 2008, when the App Store was launched. In 18 years, not much has changed! Apple still does not officially allow apps to bypass the App Store review process to ship meaningful experience changes.</span></em></p><h2><span>3. OpenAI&#8217;s agentic software factory</span></h2><p><span>The idea of a &#8220;software factory&#8221; is similar to a physical factory where robots and humans produce autos together. In the software context, it is AI agents and humans producing software. Some manufacturing sites are fully automated &#8220;dark factories&#8221; where illumination isn&#8217;t needed because there are no humans. Could the same fully automated process emerge in software engineering? At OpenAI today, there&#8217;s a &#8220;software factory&#8221; running and it&#8217;s all built around Codex.</span></p><p><span>Here&#8217;s how the &#8220;traditional&#8221; software development pipeline:</span></p><p><strong><span>1. A human builder defines the desired outcome. </span></strong><span>A software engineer or product manager specifies the problem and desired outcome. Judgment, prioritization, and taste are becoming more important for this phase. Interestingly, Venkat told me that engineers at OpenAI are becoming more like product managers than traditional systems engineers.</span></p><p><strong><span>2. Codex gathers context. </span></strong><span>OpenAI has moved all its documentation inside of the source code, which makes it easier for agents to understand more of the code. Codex also has access to:</span></p><ul><li><p><span>Git repositories and GitHub</span></p></li><li><p><span>Slack and Notion</span></p></li><li><p><span>Internal data sources: Databricks, Datadog, internal logs, etc</span></p></li><li><p><span>Internal Codex skills &#8211; some of which are maintained by OpenAI&#8217;s Codex implementation itself!</span></p></li></ul><p><span>Codex is so &#8220;plugged&#8221; into OpenAI that new engineers are directed to ask Codex </span><em><span>any </span></em><span>questions they have during onboarding because it has a surprising amount of context.</span></p><p><strong><span>3. Codex implements code changes. </span></strong><span>This part is trivial enough: Codex gets to work and makes a series of code changes until it reaches its goal, and then verifies that the software works as it should.</span></p><p><strong><span>4. Build &amp; test, then CI.</span></strong><span> The agent builds the code, runs the tests, fixes the code when it breaks the test, and then creates a pull request. This pull request triggers the continuous integration (CI) server to run and execute a more thorough suite of linters and tests. The agent babysits the PR until it&#8217;s &#8220;green&#8221;, fixing any CI failures and automatically updating the PR.</span></p><p><strong><span>New: a &#8220;perf harness&#8221;: </span></strong><span>the agent also uses a perf harness to send problematic PRs to the Synthetics A/B framework for evaluating performance implications. As mentioned above, the load upon CI systems has increased greatly in the past six months.</span></p><p><strong><span>5. Agentic code review. </span></strong><span>Instead of using one generic AI code reviewer, OpenAI spins off multiple agents, each with a &#8220;domain specialist&#8221; configuration. Venkat told me they see this as equivalent to having a human domain expert from each relevant infrastructure team review every change.</span></p><p><em><span>Note from Gergely: I was skeptical about the claim that an agent that&#8217;s told to be a cloud infra specialist would produce a different review from a generic agent. However, all Codex agents have full access to OpenAI&#8217;s code and docs, so this &#8220;cloud infra expert&#8221; agent likely has gathered a lot of context about cloud infra setup and best practices, meaning it should provide highly targeted feedback. The important thing is how these &#8220;domain specialist&#8221; agents are set up, the context they have access to, and how they focus only on their own domain to make best use of their limited context window.</span></em></p><p><strong><span>Code changes are classified by risk. </span></strong><span>High-risk changes can be sent through stricter processes; for example, they might invoke more AI code reviews, or mandate that a human reviews it after the AI agents finish. Low-risk changes follow an easier path; areas of the codebase can opt in to an agent that will auto-approve low risk PRs, removing human acceptance as a bottleneck and improving velocity.</span></p><p><span>A neat thing about risk assessment is that OpenAI can automate when additional compliance input is needed: either automated (via another agent) or human review. With the quantity of PRs being produced, it simply wouldn&#8217;t be possible for humans to review all code without assistance.</span></p><p><span>Just like with CI, the coding agent babysits the comments and updates the PR to fix issues surfaced.</span></p><p><strong><span>6. Agentic deploy. </span></strong><span>After a human approves a change to go to production, it is assigned its own agent with an instruction that could be summarized as:</span></p><p><span>&#8220;Handhold this change until it is safely and fully rolled out into production.&#8221;</span></p><p><span>Agents handhold both the code changes and the changes behind feature flags. For example, in the case of a change behind the feature flag, the agent will:</span></p><ul><li><p><span>Read the codebase and figure out where the feature flag lives</span></p></li><li><p><span>Understand what the change does</span></p></li><li><p><span>Decide which signals indicate success and failure</span></p></li><li><p><strong><span>Builds its own monitoring dashboard to use</span></strong><span> &#8211; </span><em><span>this is a pretty impressive improvement and something that&#8217;s new to me</span></em></p></li><li><p><span>Watches relevant production signals and its dashboard(s)</span></p></li></ul><p><span>OpenAI&#8217;s long term goal is to have something like a &#8220;per-change autonomous SRE&#8221; (site reliability engineer) in the form of an agent that can deploy pretty much autonomously.</span></p><p><strong><span>7. Observe production.</span></strong><span> Tools which track the production system:</span></p><ul><li><p><span>Dashboards generated by the agent during previous steps</span></p></li><li><p><span>OpenAI&#8217;s internal observability stack, including a bunch of custom tools that generate logs, metrics, trace &amp; wide event data</span></p></li></ul><p><span>One big change at OpenAI since my previous visit, pre-Codex, is that back then, engineers created dashboards to monitor services whereas now, agents do this at the granularity of per-change deployment.</span></p><p><strong><span>8. Production monitoring feeds back into development.</span></strong><span> OpenAI&#8217;s &#8220;Perf Factory&#8221; uses agents to sift through alerts and dashboards, de-duplicate signals, identify real latency regressions, root-cause them and propose fixes.
