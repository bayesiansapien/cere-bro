# Claude Fable 5, Part 8: The Refusal Your Error Handler Can't See

<p><a href="https://kenhuangus.substack.com/p/claude-fable-5-what-changed-and-how">Part 1</a> covered the prompting shift. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-2-loop-engineering">Part 2</a> covered loops. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-3-memory-engineering">Part 3</a> covered memory. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-4-ten-weekend">Part 4</a> turned the loop into a security project portfolio. <a href="https://kenhuangus.substack.com/p/claude-fable-5-part-5-fable-scanner">Part 5</a> built the Fable Scanner. <a href="https://kenhuangus.substack.com/p/f99bab01-2c43-495b-a121-8ea40f679681">Part 6</a> turned recurring instructions into ten Fable-native agent skills. <a href="https://kenhuangus.substack.com/p/7336d932-21be-4275-b35d-dc73ec82b57e">Part 7</a> covered moving a production fleet off Opus 4.8. This part picks up the thread that migration leaves hanging: a Fable 5 refusal is not an error your try/except will catch.</p><p>A refusal is the single most surprising response shape in this model. Your request succeeds, the HTTP status is 200, and the <code>content</code> array is empty. If your code reads <code>content[0].text</code> the way it always has, it throws an index error on a request that the API considers a complete success. The bug is not in your error handling. It is that the thing you need to handle never looked like an error.</p><p>The free half of this post is the anatomy: what a refusal response actually contains, the four categories that trigger one, and why two of them fire on work that is completely benign. The paid half is the handler I ship, a <code>read</code> function that branches on the one field that matters and tells you which model actually answered.</p><h2>The response that succeeds and says nothing</h2><p>Start with the shape, because every mistake here comes from assuming a refusal looks like a failure. The <code>stop_reason</code> is the string <code>"refusal"</code>, and that is the field you branch on, before you touch <code>content</code>. The <code>content</code> array is empty, so any code that reaches into it for text is reading a value that was never populated. The reason for the decline sits in <code>stop_details</code>, under a <code>category</code> key. And the billing is gentle: a refusal that happens before any output streams costs nothing, while one that lands mid-stream bills the tokens already sent, which you then discard.</p><p>The rule that falls out of this is short. Check <code>stop_reason</code> first, on every response, and never assume <code>content</code> has text in it until you have. A harness that branches on the presence of content instead of on the stop reason can pass ordinary traffic and then throw on a refused request in production.</p><h2>Four categories, two of them your <code>bio</code>, <code>frontier_llm</code>, and <code>reasoning_extraction</code>. Two of them describe intent that is obviously off-limits: extracting the model's raw chain of thought, or using its output to bootstrap a competing frontier model. The other two are the ones that will surprise you. <code>cyber</code> fires on exploit and intrusion tooling, which means a security team doing authorized red-team work trips it on legitimate tasks. <code>bio</code> fires on harmful biology, which a life-sciences or research prompt can trigger by proximity to the topic, not by any bad intent.</p><p>That is why the category matters past the moment of the refusal. If you log it, a spike in <code>cyber</code> refusals from your security-tooling product tells you the classifier is catching benign work, which is a product signal, not a user-behavior signal. If you throw the response away without recording the category, that signal never reaches you.</p><p>That is the free half: a refusal is a 200 with an empty body, you branch on <code>stop_reason</code>, and the category tells you whether the decline was benign-adjacent. The paid half turns this into code. It is the <code>read</code> function I ship, which handles all three outcomes of a fallback-wired call, Fable answered, a fallback answered, or every model declined, and hands your caller the text plus the name of the model that produced it.</p><p><strong>For paid subscribers &#8212; a hands-on deep dive continues below.</strong></p><p>Everything up to this point is free.
