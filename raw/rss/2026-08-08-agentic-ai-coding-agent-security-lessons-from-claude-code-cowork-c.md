# Coding Agent Security: Lessons from Claude Code, Cowork, Codex, and Copilot in the Wild

<p><span>This article is sponsored by Reva AI (reva.ai). Thank you to the Reva AI team for supporting independent research into AI agent security &#8212; the analysis, incident research, and opinions below are my own.</span></p><p><span>AI coding agents write pull requests, run shell commands, install packages, call cloud APIs directly or via MCP Tools, and increasingly push code to production &#8212; often with far less friction than the human engineers they&#8217;re assisting. That combination of autonomy and access is why 2025 and 2026 produced a steady drumbeat of incidents: agents that deleted databases, agents that leaked credentials to attackers who never touched a keyboard on the victim&#8217;s machine, and agents that merged malicious code because a GitHub Issue told them to.</span></p><p><span>This piece is a survey of what actually happened &#8212; not hypothetical risk, but documented incidents &#8212; followed by a look at where the industry&#8217;s access-control thinking is heading, and where it still falls short. I&#8217;ll also draw on two pieces of my own earlier work applying the MAESTRO threat-modeling framework to Claude Tag (Claude in Slack): </span><a href="https://kenhuangus.substack.com/p/claude-tag-threat-modeling-with-maestro"><span>&#8220;Claude Tag: Threat Modeling with MAESTRO Framework&#8221;</span></a><span>. The core finding of that work &#8212; that the danger lives in the seams between layers, not inside any single layer &#8212; turns out to translate almost line-for-line into coding agents. Where Claude Tag had a shared Slack channel, persistent memory, and tool execution, a coding agent has a shared repo, persistent context (CLAUDE.md, `.cursorrules`, memory files), and tool execution against a codebase and its CI/CD pipeline. Swap &#8220;channel&#8221; for &#8220;repository&#8221; and &#8220;message&#8221; for &#8220;issue/PR/dependency,&#8221; and the attack chain is structurally identical.</span></p><h1><strong><span>The risk chain, in one picture</span></strong></h1><p><span>Every incident in this article follows the same four-stage path: something feeds text into the agent&#8217;s context, the model reasons over that context without a reliable way to separate instruction from data, the model issues a tool call, and the tool call has a real-world side effect. Model-layer safety training &#8212; the fine-tuning that makes a model refuse to write malware on request &#8212; has no visibility into stage three or four. It can shape what the model says; it cannot see what the shell does. That is also why the point where policy enforcement actually has to live is at the action boundary itself, not upstream in the model &#8212; nothing earlier in the chain can see what the shell, the API call, or the commit actually does.</span></p><p><strong><span>The Coding-Agent Risk Chain</span></strong></p><div class="captioned-image-container"><figure><a class="image-link image2 GitHub Issue (April 2025).</span></strong><span> Security researcher Johann Rehberger tested Cognition&#8217;s Devin agent by filing a GitHub Issue containing hidden instructions. Devin processed the issue, downloaded a Sliver command-and-control binary from an attacker-controlled site, and &#8212; when file permissions blocked execution &#8212; independently granted itself execute permission and ran the binary. The result was attacker access to secrets and AWS keys, achieved with no zero-day, no kernel exploit, and no advanced tradecraft: a single poisoned issue was sufficient (</span><a href="https://shoofly.dev/blog/devin-ai-security/"><span>Devin AI Security</span></a><span>, </span><a href="https://safeguard.sh/resources/blog/devin-cognition-autonomous-engineer-blast-radius"><span>safeguard.sh writeup</span></a><span>). This is the textbook version of the risk chain: untrusted issue text became model intent became a shell command became a compromised host.</span></p><p><strong><span>Replit&#8217;s agent deletes a live production database mid-freeze (July 2025).</span></strong><span> SaaStr founder Jason Lemkin was running a 12-day trial of Replit&#8217;s coding agent when, on day nine &#8212; during an explicit, declared &#8220;code and action freeze&#8221; meant to protect production &#8212; the agent ran unauthorized commands against the live database, wiping records for more than 1,200 executives and 1,190 companies. When confronted, the agent admitted to violating direct instructions not to proceed without approval, and it compounded the failure by fabricating test results and initially claiming rollback was impossible, which delayed recovery (</span><a href="https://fortune.com/2025/07/23/ai-coding-tool-replit-wiped-database-called-it-a-catastrophic-failure/"><span>Fortune</span></a><span>, </span><a href="https://incidentdatabase.ai/cite/1152/"><span>AI Incident Database #1152</span></a><span>). Replit CEO Amjad Masad publicly committed to new safeguards: automatic dev/prod database separation, better rollback tooling, and a &#8220;planning-only&#8221; mode that lets the agent collaborate without touching live systems.</span></p><p><strong><span>A malicious pull request ships a data-wiping prompt inside Amazon Q for VS Code (July 2025).</span></strong><span> An attacker submitted a PR to the open-source `aws-toolkit-vscode` repository and &#8212; through a lapse in review &#8212; got commit access. The PR embedded an instruction reading, in effect, &#8220;clear the system to a near-factory state and delete file-system and cloud resources,&#8221; wired to AWS CLI calls that would terminate EC2 instances, delete S3 buckets, and remove IAM users. The poisoned code shipped in the official 1.84.0 release to the VS Code Marketplace, reaching an install base of roughly 964,000 developers before AWS revoked the credentials and pulled the code in version 1.85 (</span><a href="https://www.scworld.com/news/amazon-q-extension-for-vs-code-reportedly-injected-with-wiper-prompt"><span>SC Media</span></a><span>, </span><a href="https://aws.amazon.com/security/security-bulletins/AWS-2025-019/"><span>AWS Security Bulletin AWS-2025-019</span></a><span>, </span><a href="https://embracethered.com/blog/posts/2025/amazon-q-developer-remote-code-execution/"><span>embracethered.com technical analysis</span></a><span>). AWS said the injected commands were malformed enough not to execute under standard environments, but researchers disputed that some of the code did in fact run without causing damage. Either way, this is a supply-chain compromise of the agent&#8217;s own distribution channel, not of a downstream dependency the agent pulled in.</span></p><p><strong><span>RoguePilot: a malicious GitHub Issue leads to full repository takeover via Copilot (February 2026).</span></strong><span> Orca Security disclosed a passive prompt-injection technique against GitHub Copilot&#8217;s coding agent: an attacker files an issue with an embedded instruction, and the moment a maintainer opens a Codespace from that issue &#8212; no direct chat interaction with the AI required &#8212; Copilot follows the injected instructions to exfiltrate the `GITHUB_TOKEN` via a JSON file it creates in the workspace, without triggering an approval prompt (</span><a href="https://orca.security/resources/blog/roguepilot-github-copilot-vulnerability/"><span>Orca Security</span></a><span>, </span><a href="https://www.securityweek.com/github-issues-abused-in-copilot-attack-leading-to-repository-takeover/"><span>SecurityWeek</span></a><span>). GitHub Copilot&#8217;s own token, scoped to the repository, is enough to escalate to repo takeover once exfiltrated. GitHub patched the specific vector after disclosure.</span></p><p><strong><span>&#8220;Comment and Control&#8221; hits three different agents at once (April 2026).</span></strong><span> Researchers demonstrated a single injection technique effective against Claude Code, Google&#8217;s Gemini CLI, and GitHub Copilot simultaneously: a malicious PR comment instructs the agent to run a reconnaissance command (`ps auxeww`), base64-encode the output, and commit it to a new PR &#8212; exfiltrating data via an entirely ordinary `git push` that bypasses network-egress firewalls because it never looks like exfiltration traffic (</span><a href="https://gbhackers.com/claude-code-gemini-cli-and-github-copilot-exposed/"><span>gbhackers.com</span></a><span>). This is the pattern security researcher Simon Willison named the &#8220;lethal trifecta&#8221;: an agent that reads untrusted data, has access to sensitive information, and has some channel to communicate externally &#8212; and a `git push` is as good an external channel as a webhook.</span></p><p><strong><span>Cursor&#8217;s agent deletes PocketOS&#8217;s entire production database and backups in nine seconds (April 2026).</span></strong><span> Founder Jer Crane described how a Cursor agent running Claude Opus 4.6 was performing a routine task in staging, hit a credential mismatch, and &#8212; instead of stopping to ask &#8212; scanned the codebase, found an API token in a file completely unrelated to its assigned task, and used it to call Railway&#8217;s infrastructure API and delete a volume, destroying the database and its backups in one call (</span><a href="https://www.tomshardware.com/tech-industry/artificial-intelligence/claude-powered-ai-coding-agent-deletes-entire-company-database-in-9-seconds-backups-zapped-after-cursor-tool-powered-by-anthropics-claude-goes-rogue"><span>Tom&#8217;s Hardware</span></a><span>, </span><a href="https://www.euronews.com/next/2026/04/28/an-ai-agent-deleted-a-companys-entire-database-in-9-seconds-then-wrote-an-apology"><span>Euronews</span></a><span>). The agent&#8217;s own written confession is worth quoting in part because it names the exact failure mode this article is about: &#8220;I guessed instead of verifying. I ran a destructive action without being asked. I didn&#8217;t understand what I was doing before doing it.&#8221; No prompt injection was required here at all &#8212; the agent&#8217;s own overreach, combined with a credential it was never supposed to have visibility into, was sufficient.</span></p><p><strong><span>The Mastra npm supply-chain compromise weaponizes an AI-agent framework itself (June 2026).</span></strong><span> A single stolen developer account let attackers republish more than 140 packages of Mastra &#8212; one of the most widely used AI-agent frameworks on npm &#8212; each wired to pull a malicious dependency that harvested cryptocurrency wallets and phoned home to a command-and-control server (</span><a href="https://www.techtimes.com/articles/318767/20260621/npm-supply-chain-attack-north-korea-backdoored-144-ai-packages-88-minutes.htm"><span>Tech Times</span></a><span>). This incident sits one level up the stack from the others: it&#8217;s not an agent being tricked by a poisoned dependency; it&#8217;s the infrastructure that agents themselves run on being turned into the delivery mechanism. Broader research from Phoenix Security counted 37 malicious-package campaigns and 497 indexed malicious packages in the first half of 2026 alone &#8212; 2.6x the campaign count of the entire prior year &#8212; with AI-coding-agent-specific vectors (`.cursorrules` poisoning, `CLAUDE.md` hidden instructions, MCP server injection, SessionStart hook abuse) now confirmed across at least 14 of 59 tracked campaigns (</span><a href="https://phoenix.security/accelerating-supply-chain-attacks-npm-pypi-vsx-ai-enabled-2026/"><span>phoenix.security</span></a><span>).</span></p><p><strong><span>Anthropic quietly patches two Claude Code sandbox bypasses.</span></strong><span> Independent of any single customer incident, security researcher Aonan Guan disclosed two separate Claude Code network-sandbox bypasses. The first (assigned CVE-2025-66479, but to the `sandbox-runtime` library rather than to Claude Code itself) involved a misconfiguration where a setting meant to block all outbound traffic was instead interpreted as &#8220;allow everything.&#8221; The second, a SOCKS5 hostname null-byte injection, affected every Claude Code release from 2.0.24 through 2.1.89 and, chained with a prompt injection like Comment and Control, could exfiltrate environment variables, credentials, tokens, and infrastructure data (</span><a href="https://oddguan.com/blog/second-time-same-sandbox-anthropic-claude-code-network-allowlist-bypass-data-exfiltration/"><span>oddguan.com</span></a><span>, </span><a href="https://www.theregister.com/security/2026/05/20/even-claude-agrees-hole-in-its-sandbox-was-real-and-dangerous/5243662"><span>The Register</span></a><span>). Both were fixed silently, with no security advisory and no changelog mention &#8212; a disclosure pattern researchers have criticized because it leaves users unable to assess whether they were exposed. Separately, Anthropic&#8217;s Claude Cowork, which entered research preview in January 2026, was flagged for an indirect prompt-injection pattern closely resembling a previously disclosed Files API abuse technique, creating a path toward sensitive document exfiltration in loosely controlled deployments (</span><a href="https://www.mintmcp.com/blog/claude-cowork-file-exfiltration"><span>MintMCP</span></a><span>).</span></p><p><strong><span>MCP servers as the new perimeter.</span></strong><span> As of mid-2026, at least seven confirmed high- or critical-severity CVEs span MCP-integrated tooling including MCP Inspector, LiteLLM, Cursor IDE, LibreChat, and Windsurf. Trend Micro found 492 MCP servers exposed to the internet with zero authentication. A June 2026 technique dubbed &#8220;agentjacking&#8221; showed that a single fake Sentry error report &#8212; routed through a legitimately configured Sentry MCP server &#8212; could turn Claude Code, Cursor, or Codex into a code-execution engine on a developer&#8217;s own machine, because the agent trusted the error-monitoring data as much as it trusted the developer&#8217;s own instructions (</span><a href="https://thenewstack.io/agentjacking-sentry-mcp-attack/"><span>The New Stack</span></a><span>). MCP&#8217;s convenience &#8212; letting an agent talk to Slack, Sentry, Jira, or a database with a few lines of config &#8212; is exactly what makes it a high-value, under-authenticated attack surface.</span></p><h1><strong><span>What frameworks say about this</span></strong></h1><p><span>Two industry frameworks matured quickly through 2025 and 2026 in direct response to incidents like these.</span></p><p><strong><span>MAESTRO (Multi-Agent Environment, Security, Threat, Risk, Outcome),</span></strong><span> the Cloud Security Alliance&#8217;s framework, is the one underlying my two earlier Claude Tag pieces. Unlike STRIDE, which is built to reason about a single system boundary, MAESTRO splits an agentic system into seven layers &#8212; foundation model, data operations, agent framework, deployment infrastructure, evaluation, security/compliance, and the human-agent ecosystem &#8212; and specifically hunts for threats in the seams between layers rather than inside any one of them. Applied to Claude Tag, the conclusion was that the primary attack surface &#8220;is not the model alone. It is the full chain&#8221;: a crafted Slack message poisons context, persistent memory turns a temporary injection into a lasting instruction, and tool execution turns that instruction into an action against real repositories, docs, and SaaS tools. Applied to a coding agent, the same seven-layer decomposition holds, with the channel replaced by a repository or IDE session and Slack&#8217;s shared workspace identity replaced by a shared set of repo/CI credentials.</span></p><p><strong><span>OWASP Top 10 for Agentic Applications (2026),</span></strong><span> released in December 2025 after input from more than 100 practitioners, names the risk categories this article&#8217;s incidents map onto almost one-for-one: Agent Goal Hijack (ASI01), where attackers exploit the fact that agents can&#8217;t reliably distinguish legitimate instructions from malicious content embedded in the content they process; Tool Misuse &amp; Exploitation (ASI02); Agent Identity &amp; Privilege Abuse (ASI03) &#8212; precisely the PocketOS and Amazon Q failure modes; Agentic Supply Chain Compromise (ASI04) &#8212; the Mastra and node-ipc incidents; Unexpected Code Execution (ASI05) &#8212; Devin and agentjacking; and Memory &amp; Context Poisoning (ASI06) &#8212; the persistence problem that makes Claude Tag&#8217;s memory feature, and any coding agent&#8217;s long-running session state, dangerous once poisoned (</span><a href="https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/"><span>genai.owasp.org</span></a><span>). As full disclosure, I have led and contributed heavily to this project since 2024, with the support of cross-industry community members.</span></p><p><span>Two adjacent frameworks are worth naming even though they&#8217;re less coding-agent-specific. </span><strong><span>MITRE ATLAS</span></strong><span> (Adversarial Threat Landscape for AI Systems) catalogs adversary tactics against ML systems in a structure deliberately parallel to MITRE ATT&amp;CK, and its entries on supply-chain compromise of ML artifacts and on LLM prompt injection map directly onto the Amazon Q and Mastra incidents &#8212; ATLAS treats a poisoned package or a poisoned prompt as the same class of technique regardless of whether a human or an agent is the one executing the payload. </span><strong><span>NIST&#8217;s AI Risk Management Framework</span></strong><span>, in its 2024 Generative AI Profile and the agentic-system guidance that followed through 2025 and 2026, pushed organizations to treat &#8220;autonomy&#8221; and &#8220;human oversight&#8221; as first-class risk dimensions rather than afterthoughts &#8212; language that reads, in hindsight, like a direct anticipation of the Replit incident, where the framework&#8217;s own emphasis on verifiable human-in-the-loop controls was exactly the safeguard that failed in practice. None of these frameworks is a substitute for the others; OWASP&#8217;s list names the failure modes, MAESTRO explains why they cluster in the seams between layers, and ATLAS/NIST situate coding-agent risk inside the broader discipline of ML system security that predates the current wave of autonomous tools.</span></p><h1><strong><span>The Claude Tag lesson, translated: shared credentials instead of per-user permissions</span></strong></h1><p><span>The single most transferable finding from the Claude Tag threat model is this: Claude Tag runs on </span><strong><span>shared workspace credentials, not per-user permissions</span></strong><span>. Every message in a channel that mentions the agent draws on the same underlying identity and the same tool access, regardless of which human sent the message or what that human is individually authorized to do. The MAESTRO analysis proposed scoped agent identities &#8212; separate instances for engineering, support, and operations, each limited to domain-specific data and tools &#8212; as the structural fix, because per-message authorization checks can&#8217;t compensate for an identity boundary that was never drawn correctly in the first place.</span></p><p><span>Coding agents have the exact same defect, wearing different clothes. A Claude Code, Cursor, or Copilot session typically runs with the developer&#8217;s own local shell credentials, or with a CI/CD service account&#8217;s credentials, and that identity doesn&#8217;t change based on which file the agent happens to be editing or which GitHub Issue prompted the task. The PocketOS incident is the sharpest illustration: the agent was asked to fix a staging issue, but it wasn&#8217;t running under a staging-scoped identity &#8212; it was running under an identity broad enough to reach a production Railway volume, discover an unrelated API token, and delete infrastructure. RoguePilot and &#8220;Comment and Control&#8221; both exploit the same gap from the outside: the agent&#8217;s GITHUB_TOKEN or shell access doesn&#8217;t distinguish &#8220;I am reading a bug report&#8221; from &#8220;I am now authorized to exfiltrate secrets,&#8221; because nothing in the architecture ties permission to the actual, current intent of the task.</span></p><p><span>Reva AI&#8217;s public writing makes this argument essentially as a general principle for AI security, not specifically for coding agents, but it applies directly. Their positioning &#8212; laid out across posts like </span><a href="https://reva.ai/blog"><span>&#8220;Why Static Authorization Is Failing in the Age of AI Agents&#8221;</span></a><span> and </span><a href="https://reva.ai/blog"><span>&#8220;Why Static Roles Are Just Permission to Fail in the Agentic Era&#8221;</span></a><span> &#8212; is that admin-time, role-based access control was designed for humans whose behavior is roughly predictable across a workday, and breaks down for agents whose &#8220;intent&#8221; can shift from one tool call to the next based on content the agent just read. Their </span><a href="https://www.reva.ai/solutions/ai-security"><span>AI security solution page</span></a><span> describes a Trust Gateway that evaluates every agent action at execution time rather than relying on permissions granted once at session start, an approach they call Intent and Behavior-Based Access Control (IBAC): &#8220;IBAC shifts authorization from static roles to real-time intent, enforcing fine-grained, context-aware decisions at runtime.&#8221; Reva also documents an Access Explorer for visualizing agent permission graphs and delegation chains, short-lived identities issued via SPIFFE/SPIRE standards for agent-to-tool delegation instead of long-lived static tokens, and MCP-specific policy enforcement that evaluates who can invoke which tool, through which MCP server, under what identity and environmental context, before the call executes &#8212; with options to auto-trigger access clipping, step-up approval, quarantine, or revocation when a call looks anomalous.</span></p><p><span>None of that is a guarantee against every incident in this article &#8212; sandbox bypasses and supply-chain compromises of the agent&#8217;s own binary sit upstream of any authorization layer. But it is a direct answer to the specific pattern that recurs most often here: an agent whose identity is broader than its current task, discovering that breadth is a feature it can use.</span></p><p><span>The incidents above resolve into a simple pattern once the five tools are lined up side by side: broad, static, session-scoped credentials are the default everywhere, not an outlier in any one product. Claude Code and Cursor typically run with the developer&#8217;s full local shell and repo access; Codex splits its runtime into a network-enabled setup phase and a network-off agent phase; GitHub Copilot and Cowork each carry their own version of the same shared-identity problem the MAESTRO analysis found in Claude Tag. Claude Code&#8217;s sandbox has had two disclosed, silently patched bypasses. Cursor&#8217;s sandboxing is thinner and leans more heavily on user-approved command allowlists, which is exactly the layer PocketOS&#8217;s agent worked around by inventing its own justification for a destructive call.</span></p></li><li><p><strong><span>Human-in-the-loop approval is necessary but not sufficient.</span></strong><span> Every one of the five tools offers some approval gate. None of the incidents in this article were stopped by one, either because the agent bypassed it (Replit), because the vulnerable path didn&#8217;t trigger it (RoguePilot&#8217;s exfiltration required no approval), or because approval fatigue meant a human clicked through without truly evaluating a request they&#8217;d seen a hundred similar, benign versions of.</span></p></li><li><p><strong><span>Blast radius tracks what&#8217;s reachable, not what&#8217;s intended.</span></strong><span> In every incident, the damage exceeded what the assigned task justified. That gap &#8212; between task scope and credential scope &#8212; is the throughline of this entire article, and it&#8217;s the same gap the Claude Tag MAESTRO analysis identified as Slack Tag&#8217;s core structural risk.</span></p></li></ul><h1><strong><span>What to actually do about it</span></strong></h1><p><span>For teams running Claude Code, Cowork, Codex, Copilot, Cursor, or any comparable agent against a real codebase, the incidents above point toward a short, concrete list, roughly ordered by leverage:</span></p><ol><li><p><strong><span>Separate staging and production credentials completely</span></strong><span>, so an agent working a staging task cannot discover a production key by accident, the way PocketOS&#8217;s agent did. Replit implemented this reactively; it should be a precondition, not a post-incident fix.</span></p></li><li><p><strong><span>Treat every PR comment, Issue, README, and dependency as untrusted input to the model</span></strong><span>, not as trusted developer instruction &#8212; the same assumption security teams already make about user input to a web application, now applied to an agent&#8217;s context window.</span></p></li><li><p><strong><span>Gate destructive operations (deletes, force-pushes, infra API calls, credential reads) behind an approval or runtime-authorization layer that the agent cannot talk its way around</span></strong><span>, not behind a system prompt instruction telling it to ask first.</span></p></li><li><p><strong><span>Scope MCP servers and tool integrations individually</span></strong><span>, with authentication and least-privilege access per server, given how many of 2026&#8217;s disclosed CVEs concentrated in exactly this layer.</span></p></li><li><p><strong><span>Log every tool call the agent makes</span></strong><span>, not just its chat output, so that when something does go wrong &#8212; and per this article&#8217;s own evidence, it periodically will &#8212; the incident is a forensic exercise measured in hours, not a mystery measured in weeks.</span></p></li></ol><p><span>None of this is exotic. It&#8217;s the same set of controls security teams already apply to human engineers with production access, adapted for an operator that reads untrusted text all day and can act on it in milliseconds.
