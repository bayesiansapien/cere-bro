# GPT-6 Astra, Looped Transformers, and Hidden Reasoning

<p>A lot has happened in the last few weeks. I am sure that OpenAI&#8217;s GPT-6 Astra is top of mind for everyone right now. In particular, thoughts on its performance, the looped transformer/recurrent depth aspects, and rumors that Astra is &#8220;hiding&#8221; its reasoning trace (i.e., chain of thought).</p><p>So, in this article, I want to start with some brief impressions of Astra and some thoughts on where all this is headed. Then, I will discuss, in detail, what &#8220;looped transformers&#8221; are, and how (or rather, if) this relates to hiding chains of thought.</p><p>Lastly, after covering the basics of the looped transformer, I wanted to highlight some new insights from recent research papers on the topic.</p><h2>1. GPT-6 Astra impressions</h2><p>First things first. Before getting into the architecture rumors and related research literature, let me briefly summarize some GPT-6 Astra observations and tidbits.</p><p>Last week, OpenAI&#8217;s new GPT-6 Astra was released with a big fanfare. I used it over the past couple of days, and it&#8217;s an exceptionally good model, likely the best I&#8217;ve used as of this writing. But what, exactly, has it improved, and how?</p><h3>1.1 Astra benchmarks</h3><p>Astra is the best model I&#8217;ve used so far, and it&#8217;s disproportionately good at 3D rendering and animation tasks (relative to other models). model developers.</p><p>The <a href="https://artificialanalysis.ai/methodology/intelligence-benchmarking">harness setup depends on the benchmark</a>. For example, GDPval-AA and AA-Briefcase use their open-source, minimal <a href="https://github.com/ArtificialAnalysis/Stirrup">Stirrup</a> harness across the different LLMs they compare. In the Intelligence Index v4.2 shown above, Terminal-Bench v2.1 uses Terminus 2, and &#964;&#179;-Banking uses the &#964;-Bench harness. The separate Coding Agent Index also compares different coding-agent harnesses.</p><p>For evaluations that use a shared harness, this makes it more of an apples-to-apples comparison. At the same time, during model training, models are typically developed with one primary harness in mind (and fine-tuned less on other harnesses). Plus, the primary harness is often developed to suit and amplify a model&#8217;s strengths.</p><p>So, some of the agentic evaluations might underestimate how well Astra performs in its primary harness. How much this affects its Intelligence Index score would need to be tested by comparing Astra across harnesses on the same tasks.</p><p>As a side note, as a colleague recently suggested to me (as also recommended by the Claude Code lead), it&#8217;s maybe not a bad idea to delete (/archive) some of your existing <code>AGENTS.md</code> contents and <code>SKILL.md</code> files, as newer LLMs have become more efficient at understanding the prompt and solving the problem at hand. The extra hand-holding could unnecessarily constrain newer models and lead to worse solutions.</p><p>Of course, I am not suggesting never using <code>SKILL.md</code> files again, but for some workflows, because they can improve efficiency upon reuse, since the model doesn&#8217;t have to rediscover them. But what I am suggesting is that some workflows don&#8217;t need describing, and &#8220;old&#8221; descriptions may no longer be ideal, and the LLM may be able to come up with better solutions. So, it&#8217;s perhaps time to update or regenerate said instruction files.</p><h3>1.2 Computer use capabilities</h3><p>GPT-6 Astra seems to be exceptionally strong in image and rendering tasks. When these tasks involve interacting with graphical user interfaces, they also demonstrate computer-use capabilities, meaning the model operates software on your local computer through the Codex/ChatGPT app.</p><p>Computer use is where the model really shines compared to others, and anything graphic-related also makes for interesting and intuitive demos on social media platforms. There are tons of examples of impressive demos out there, from modeling <a href="https://x.com/higgsfield_ai/status/2096495974734794840?s=20">rendering New York City in blender</a> to <a href="https://x.com/Dimillian/status/2095596700815516004?s=20">virtual open house tours</a>.</p><p>To pick one example, below is a comparison where I had GPT-6 Astra Medium and High redraw a picture of me in a <a href="https://jspaint.app/#local:aa1757d4bc6008">browser version of MS Paint</a> using the mouse on my computer (not Extra High and Max, because I didn&#8217;t want to waste all my tokens :)).</p><div class="native-video-embed"></div><p></p><p>This highlights not only the model&#8217;s artistic capabilities but, more importantly, its ability to use tools on one&#8217;s computer (in this case, Paint; you can see the model using the interface via the mouse cursor).</p><p>This is not the first model that, inside a harness, is capable of general computer use. For example, I successfully used GPT models for some UI tasks (e.g., expense-related tasks in Excel) and so on since earlier this year. However, computer use is a relatively new capability, enabled by the harness, and usually feels not quite as mature yet. This makes sense. LLMs are text models, so naturally the lower-hanging fruit is writing and coding and using APIs and CLIs.</p><p>At the same time, there are many tools and software that don&#8217;t expose CLIs (yet), and instead of waiting until someone designs that interface, why not improve models to use graphical user interfaces (and, as mentioned before, this makes for pretty and impressive demos, anyway)? This is somewhat analogous to the emerging humanoid robot developments. Sure, humanoid robots are not the most efficient robots, for example, at the assembly line, where special-purpose machines exist. But they are versatile.</p><p>So, I expect the upcoming months (or years) also to be an era of computer use refinement on both the LLM and the agent harness layer. I.e., in addition to the current capabilities, and expanding their math and coding capabilities, models will be trained with an increasing amount of computer use in mind. And this will also make LLMs more accessible for everyday computer tasks outside the tech world (&#8221;Hey ChatGPT, please do my tax return&#8221; :))</p><h3>1.3 Computer use training</h3><p>The computer usage trend is also consistent with the <a href="https://finance.yahoo.com/technology/ai/articles/apple-suddenly-ai-infrastructure-stock-130223938.html">recent reporting</a> that OpenAI purchased tens of thousands of Mac Minis and Mac Studios for Reinforcement Learning. So, here the Macs are not used to literally train the models (it&#8217;s better to use GPUs for that) but rather to expose macOS during the model training for the model to learn to use said operating system and the tools therein.</p><p>So, how does computer-use training on said Macs work? In short, the Macs (or their macOS operating system, to be precise) serve as an environment that the model can interact with during training.</p><p>The basic workflow looks like this:</p><ol><li><p>Prompt the model by giving it a task, such as &#8220;open an app xyz and do abc&#8221;.</p></li><li><p>Provide it with screenshots of the macOS interface (this is usually done by the harness).</p></li><li><p>The LLM then predicts mouse/keyboard actions (click, key presses, scrolling, and so on).</p></li><li><p>Execute those actions on the Mac (again, this is done by the harness).</p></li><li><p>Feed new screenshots of the updated environment after performing the actions in the previous step.</p></li><li><p>Repeat steps 2-5 until the task succeeds or fails.</p></li><li><p>Use success/failure signals and verifiers (or graders) as training feedback, including reinforcement learning during post-training; this is analogous to regular Reinforcement Learning with Verifiable Rewards (RLVR).</p></li></ol><div class="captioned-image-container"><figure><a class="image-link image2 is-viewable-img" transformer blocks</h3><p>So, what&#8217;s a looped transformer?</p><p>A Looped Transformer is essentially an architectural tweak, with the main idea being to pass the intermediate representations through the same transformer blocks multiple times (instead of just once). Compared to just adding more blocks, the &#8220;trick&#8221; here is that the weights stay the same across these passes.</p><div><hr /></div><p><strong>Definitions &amp; Jargon</strong></p><p>Throughout this article, I&#8217;ll use the following terms:</p><ul><li><p>A <strong>transformer block</strong> is a unit containing attention, a feedforward module, normalization, and shortcut connections. These blocks are often called &#8220;transformer layers&#8221; in papers.</p></li><li><p>A <strong>stack</strong> is a sequence of transformer blocks.</p></li><li><p>A <strong>block application</strong> means running an input through a transformer block once.</p></li></ul><div><hr /></div><p>The looped transformer is nothing new, and the basic idea already appeared in the <a href="https://arxiv.org/abs/1807.03819">Universal Transformers</a> paper from 2018. But before discussing Universal Transformer, let&#8217;s start with a simpler example, <a href="https://arxiv.org/abs/2607.22083">Nanbeige4.2-3B</a>, a recent open-weight LLM that came out in July and that I covered on Substack <a href="https://substack.com/@rasbt/note/c-302083551">Notes</a> and in my <a href="https://www.sebastianraschka.com/llm-architecture-gallery/looped-depth-sharing/">LLM Architecture Gallery</a> earlier this summer.</p><p>The Nanbeige architecture, shown below, essentially looks like a regular transformer. More precisely, we pass the intermediate inputs through 44 block applications during the forward pass. And, during training, gradients flow backward through both repetitions of the shared stack. So, compared to using the 22 blocks only once, this adds substantial work. Actually, it&#8217;s similarly expensive as having 44 distinct blocks (except the optimizer has fewer distinct parameters to update; backprop still runs through all 44 block applications).</p><p>There is also the KV cache, which stores the attention keys and values of previous tokens for reuse in conventional and looped transformers in each next-token generation step. By the way, I have a standalone article on KV caching here if useful:</p><div class="digest-post-embed"></div><p>But back to the topic. Even though there is weight-sharing in looped transformers, the intermediate states that enter a block are different on the second pass. Consequently, in KV caching, the resulting keys and values are also different between these two transformer stacks (just like in the no-looping case). So, there are no KV cache-related savings either.</p><p>To make this more concrete, for example, consider block applications 1 and 23, which both use block 1 in the looped transformer setup. But each application still needs its own KV cache entries. So, since we have to keep separate caches for both passes, the repeated stack of 22 blocks has the same KV cache requirements as a conventional transformer with 44 distinct blocks.</p><p>Interestingly, the Nanbeige researchers reported in the paper that they tried sharing the KV cache between passes. This, of course, halved the KV cache size, but the model performed worse than the version with separate caches (which is the version they released).</p><p>Just to complete the Nanbeige discussion before moving on and looking at some other looped transformer designs, their <a href="https://arxiv.org/html/2607.22083v1#S2.SS1">technical report</a> also discusses two other choices or trade-offs.</p><ol><li><p>Training the looped architecture from scratch worked better than converting an already pre-trained transformer through upcycling.</p></li><li><p>And two passes gave their preferred trade-off, as mentioned in the previous section. More passes brought only small additional gains while slowing training and making optimization less stable.</p></li></ol><p>So, the number of passes is another architectural choice we have to make. As mentioned before, in Nanbeige, this is fixed at two. But we can also make it depend on the token, as we will see next.</p><h3>2.3 Universal Transformers and flexible loop counts</h3><p>Now, let&#8217;s come back to <a href="https://arxiv.org/abs/1807.03819">Universal Transformers</a>. In Nanbeige, we apply a stack of 22 transformer blocks twice. In the Universal Transformer paper from 2018, we repeatedly apply the same transformer block instead of repeating a stack of transformer blocks. The main idea is similar, though.</p><p>Also, the number of steps can be fixed, but the paper also explores adaptive halting. For example, a token at a particular position may only go through one or two loops. Another may go through three or four loops, and so on. This gives the model flexibility to allocate the compute to those tokens that benefit from extra computation.</p><p>How is the looping number decided? Here, the model uses a small, trained function that outputs a so-called halting probability for each position at each step. It adds up these probabilities over these successive loops and then stops looping at a given position once the sum exceeds a threshold value. Looped transformer research</h2><p>Lastly, I want to share some interesting papers related to looped transformer architectures beyond the ones we already discussed.</p><h3>6.1 Latent reasoning</h3><p>Related to the Universal Transformer, the 2025 <a href="https://arxiv.org/abs/2502.05171">Scaling up Test-Time Compute with Latent Reasoning: A Recurrent Depth Approach</a> paper studies how a model can use additional loops at inference time. For this, they trained a relatively modest but also not super tiny 3.5B-parameter model on 800B tokens.</p><p>Instead of reusing the same block over and over again as in the Universal Transformer, it repeats a stack like in Nanbeige; however, in contrast to Nanbeige, it sandwiches this shared stack of four blocks between 2 initial and 2 final blocks.</p><p>Also, what&#8217;s different from Nanbeige is that the shared stack receives the output of the initial blocks at the start of every loop, in addition to the previous loop&#8217;s hidden state. These are concatenated and passed through a learned linear projection before entering the four shared blocks. You can think of this as giving the stack access to the same initial input representation on every pass. This whole layout is summarized in the figure below.</p><p>So, in short, this is an additional and interesting looped transformer variant.</p><div class="captioned-image-container"><figure><a Looping just gives it additional computation before each output token.</p><h3>6.2 Knowledge retrieval vs reasoning</h3><p>There&#8217;s a useful distinction between storing information and using it to solve a problem. For instance, the <a href="https://arxiv.org/abs/2506.18233">Beyond Parameters: Exploring Virtual Logic Depth for Scaling Laws</a> paper from June 2025 investigates this by measuring memorization and reasoning in an LLM separately.</p><p>First, in the memorization experiments, looping leaves the amount of stored information nearly unchanged when the parameter count stays fixed. Increasing the number of distinct parameters does increase this capacity. From this, we can conclude that looping doesn&#8217;t add or let&#8217;s the model retrieve more knowledge. This makes sense. Information retrieval is a relatively simple task once the information is stored. Also, looping in itself is computing not &#8220;storing&#8221; mechanism.</p><p>Second, in separate reasoning experiments, reusing the blocks improves performance on multi-step math problems without adding parameters. This is interesting. Here, we can conclude that extra computation can help a model solve problems even when it doesn&#8217;t have more space to store information.
