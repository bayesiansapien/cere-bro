# Designing Hermes Agent from Scratch: A Systems Deep Dive

<p>If you strip away the packaging, Hermes is not a chatbot with plugins bolted on. It is a long-running control loop that sits between a language model and a curated set of side effects. Every design choice in <a href="https://github.com/NousResearch/hermes-agent">NousResearch/hermes-agent</a> follows from that premise: the model proposes actions, the runtime enforces budgets and guardrails, tools execute in isolated environments, and SQLite holds the truth about what actually happened.</p><p>This article walks through Hermes Agent architecture in detail. The goal is not a feature tour. It is a builder's map: where state lives, how turns commit, why prompts are split into tiers, and which patterns you can steal if you are designing your own agent runtime.</p><h2>What you are building</h2><p>Most "agent" demos are thin wrappers: send messages to an API, parse tool calls, call a few functions, repeat until the model stops. Hermes inverts the emphasis. The loop is the product. Tools are registered data, not hard-coded branches. Sessions survive restarts. Gateways multiplex the same loop across Telegram, Discord, Slack, and a local CLI. Subagents get their own iteration budgets, not a shared piggy bank.</p><p>Three invariants show up everywhere once you know where to look:</p><ol><li><p><strong>One internal message format.</strong> Adapters translate OpenAI chat completions, Anthropic messages, and Codex responses into the same dict-shaped history the loop consumes.</p></li><li><p><strong>Prompt prefix stability.</strong> The system prompt is assembled once per session and rebuilt only after compression. Volatile facts (memory, timestamps) are segregated so provider-side prefix caches stay warm.</p></li><li><p><strong>Blast-radius control via toolsets.</strong> The registry knows every tool; toolsets decide which subset a given session, subagent, or gateway channel may touch.</p></li></ol><p>Figure 1 is the spine. The heavy work lives in <code>agent/conversation_loop.py</code> (~4,900 lines of turn orchestration), with prompt assembly in <code>agent/system_prompt.py</code>, dispatch in <code>model_tools.py</code>, and persistence in <code>hermes_state.py</code> (SessionDB, schema version 14).</p><h2>The facade pattern and why it matters</h2><p>Early Hermes put the entire loop inside <code>run_agent.AIAgent.run_conversation</code>. That method grew past 3,900 lines. The refactor extracted <code>run_conversation</code> into <code>agent/conversation_loop.py</code> but kept <code>AIAgent</code> as the public object tests and gateways patch.</p><p>The indirection is deliberate. Production code and tests monkeypatch symbols on <code>run_agent</code> (<code>handle_function_call</code>, <code>OpenAI</code>, <code>_set_interrupt</code>). The loop resolves those through a lazy <code>_ra()</code> helper:</p><pre><code>def _ra():
    import run_agent
    return run_agent</code></pre><p>When <code>conversation_loop</code> needs to dispatch a tool, it calls <code>_ra().handle_function_call(...)</code>. Patches applied to <code>run_agent.handle_function_call</code> still work even though the implementation body moved to <code>model_tools.py</code>.</p><p>For your own agent, this is the <strong>stable seam</strong> pattern: keep a thin, patch-friendly module boundary even when you split monoliths. Gateways, cron workers, and CLI entry points should depend on a small surface (<code>AIAgent.run_conversation</code>, session IDs, tool lists), not on internal loop helpers.</p><p>Initialization is centralized in <code>agent/agent_init.py</code>. An <code>AIAgent</code> instance carries provider credentials, tool allowlists, memory flags, compression settings, and an <code>IterationBudget</code>. Subagents created by <code>delegate_task</code> run through the same init path with a different toolset and budget cap.</p><h2>One user turn, end to end</h2><p>A "turn" is one user message through to a final assistant reply (possibly after many model round-trips and tool calls). logging context to <code>session_id</code> so <code>hermes logs --session</code> filters correctly.</p></li><li><p>Resets per-turn retry counters (<code>_empty_content_retries</code>, <code>_invalid_tool_retries</code>, etc.) so a painful previous turn does not poison the next.</p></li><li><p>Resets the iteration budget consumption for this turn (parent budget is per-turn fresh; subagents carry their own).</p></li><li><p>Runs a TCP health check on idle HTTP connections to avoid hanging on zombie sockets after provider outages.</p></li><li><p>Ensures a SessionDB row exists via <code>_ensure_db_session()</code>.</p></li></ul><p>Then the loop enters the iteration cycle:</p><ol><li><p><strong>Assemble messages</strong> &#8212; history plus system prompt. If cached, reuse <code>agent._cached_system_prompt</code>.</p></li><li><p><strong>Preflight compression</strong> &#8212; if estimated tokens exceed threshold, compress before the API call (see below).</p></li><li><p><strong>Provider call</strong> &#8212; streaming or non-streaming, with failover classification on errors.</p></li><li><p><strong>Parse response</strong> &#8212; tool calls, reasoning blocks, empty-content guards.</p></li><li><p><strong>Dispatch tools</strong> &#8212; parallel or serial depending on config; results appended as tool messages.</p></li><li><p><strong>Repeat</strong> until the model returns final text or budgets/guardrails halt the turn.</p></li><li><p><strong>Post-turn hooks</strong> &#8212; memory review nudges, skill provenance, persistence to SessionDB.</p></li></ol><p>The loop is defensive in ways chat wrappers skip: surrogate sanitization on clipboard paste, vision capability downgrade after a text-only endpoint rejects images, and explicit retry paths for "model returned empty string but listed tools" failure modes common on smaller open-weight models.</p><p>Insight: <strong>turn boundaries are economic boundaries.</strong> Hermes resets retry state and iteration accounting at the turn edge because tool-heavy turns can consume dozens of inner iterations. Without that reset, a subagent-heavy turn would starve the next user message.</p><h2>IterationBudget: thread-safe fuel, not a global cap</h2><p>Each <code>AIAgent</code> owns an <code>IterationBudget</code> (<code>agent/iteration_budget.py</code>). It is a mutex-protected counter with <code>consume()</code>, <code>refund()</code>, and read-only <code>used</code> / <code>remaining</code>.</p><pre><code>class IterationBudget:
    def __init__(self, max_total: int):
        self.max_total = max_total
        self._used = 0
        self._lock = threading.Lock()

    def consume(self) -&gt; bool:
        with self._lock:
            if self._used &gt;= self.max_total:
                return False
            self._used += 1
            return True

    def refund(self) -&gt; None:
        with self._lock:
            if self._used &gt; 0:
                self._used -= 1</code></pre><p>Defaults from config: parent <code>max_iterations</code> is 90; each subagent gets <code>delegation.max_iterations</code> (50 by default). These budgets are <strong>independent</strong>. A parent at iteration 80 can still spawn a child with a fresh 50. Total work across the tree can exceed the parent's cap. That surprised me at first, but it matches the product goal: delegation is outsourcing, not sharing one loop counter.</p><p><code>execute_code</code> (programmatic tool calling) refunds iterations because those inner steps are runtime bookkeeping, not user-visible reasoning steps.</p><p>Pattern for builders: separate <strong>user-visible iteration limits</strong> from <strong>internal runtime steps</strong> via explicit refund hooks. Otherwise agents either die mid-refactor or learn to avoid programmatic calling.</p><h2>System prompt: three tiers and cache discipline</h2><p>Hermes treats the system prompt as a caching asset, not a environment probes, active profile warnings, and platform hints for gateways.</p><p><strong>Context tier</strong> holds caller-supplied system messages and discovered project files (<code>AGENTS.md</code>, <code>.cursorrules</code>, etc.) under <code>TERMINAL_CWD</code>. Gateway mode sets <code>TERMINAL_CWD</code> to the user's project directory so the daemon does not read rules from the install path.</p><p><strong>Volatile tier</strong> carries memory snapshots, USER.md profile, external memory provider blocks, and a date line. Ephemeral instructions are injected at API-call time, not baked into the cached string.</p><p>For Anthropic models, <code>apply_anthropic_cache_control</code> marks stable blocks for provider-side caching. The engineering goal is byte-stable prefixes across turns in a session.</p><p>If you build your own agent and wonder why responses got slow and expensive after you added "helpful" dynamic sections to the system prompt, this is why. Hermes segregates volatile state so the expensive part stays stable.</p><h2>Tool registry and AST discovery</h2><p>Hermes does not maintain a central list of tool names in a YAML file. Each tool module self-registers at import time by calling <code>registry.register(...)</code> with schema, handler, toolset membership, optional <code>check_fn</code>, and metadata.</p><p>Discovery scans <code>tools/*.py</code> with AST inspection:</p><pre><code>def _module_registers_tools(module_path: Path) -&gt; bool:
    source = module_path.read_text(encoding="utf-8")
    tree = ast.parse(source, filename=str(module_path))
    return any(_is_registry_register_call(stmt) for stmt in tree.body)</code></pre><p>Only top-level <code>registry.register(...)</code> calls count. Tools like <code>execute_command</code> route to the configured backend. <code>task_id</code> isolates concurrent sessions so two gateway chats do not share shell state.</p><p>These are not separate agent cores. They are alternate entrypoints and backends feeding the same loop and registry.</p><h2>Memory and external providers</h2><p>Built-in memory uses files under the Hermes home directory plus optional SessionDB-backed search. <code>MemoryManager</code> (<code>agent/memory_manager.py</code>) can attach external memory providers with their own system prompt blocks in the volatile tier.</p><p>Background review forks can propose memory or skill updates after a turn. Write origin tagging prevents automated suggestions from bypassing user intent.</p><p><code>session_search</code> leverages FTS5 to pull prior conversations into context when the model needs institutional memory across sessions.</p><p>The design tension is familiar: more memory helps until it erases prefix cache stability. Hermes keeps memory in volatile tier and day-stable timestamps to balance recall with economics.</p><h2>Guardrails, hooks, and middleware</h2><p>Tool execution passes through layers many prototypes skip:</p><ul><li><p>Pre-tool-call hooks for user confirmation on destructive edits</p></li><li><p>Tool guardrails with per-turn reset and halt decisions</p></li><li><p>Request middleware traces for debugging gateway sessions</p></li><li><p>Unicode and surrogate sanitization on messages and tool schemas</p></li><li><p>Invalid JSON argument repair before rejecting tool calls</p></li><li><p>Post-tool empty-response retry when the model stalls after tool results</p></li></ul><p>The loop tracks housekeeping tools separately so retries behave differently when all tool calls were benign metadata fetches versus substantive edits.</p><p>This is unglamorous code. It is also what separates "works on my laptop once" from "runs on a gateway for a week."</p><h2>CLI versus legacy REPL</h2><p>Primary CLI entry is <code>hermes_cli/main.py</code> (Typer-based commands, gateway control, doctor, tools subcommands). <code>cli.py</code> remains as a legacy REPL path. New integrations should target the CLI module patterns: load config profile, construct <code>AIAgent</code>, call <code>run_conversation</code>, persist via SessionDB.</p><p>Slash commands (<code>/resume</code>, <code>/branch</code>, <code>/title</code>, <code>/history</code>) consult SessionDB and surface <code>format_session_db_unavailable()</code> with the captured init error when NFS breaks WAL.</p><h2>Building an Agentic AI Security Operations Center</h2><p>Hermes is a practical substrate for an <strong>Agentic AI SOC</strong>: human analysts supervise autonomous triage, investigation, and gated response while the runtime enforces tool boundaries, session lineage, and approval hooks. You are not replacing the SOC; you are adding a governed agent layer that executes runbooks, enriches alerts, and documents every step in SessionDB.</p><p>Figure 13 sketches the topology.</p><div privilege.</strong> Tier-1 triage reads alerts and memory; it does not isolate hosts or edit firewall rules.</p></li><li><p><strong>Evidence lineage.</strong> Every enrichment, query, and analyst override links to a session row searchable by case ID.</p></li><li><p><strong>Human-in-the-loop for mutation.</strong> Containment actions pass pre-tool-call approval hooks.</p></li><li><p><strong>Parallel enrichment.</strong> IOC lookups (DNS, WHOIS, sandbox reports) fan out via <code>delegate_task</code> with leaf subagents and merge summaries back to the parent case session.</p></li><li><p><strong>Runbook fidelity.</strong> Skills encode NIST-aligned playbooks (phishing, malware, credential abuse) without stuffing megabytes of prose into the system prompt.</p></li></ul><h3>Layer mapping</h3><p>Map Hermes primitives to SOC roles:</p><p><strong>Ingress.</strong> SIEM webhooks and EDR alerts hit a gateway HTTP adapter or Slack slash commands. Message guards enforce API keys, IP allowlists, and per-tenant rate limits. Each alert opens or continues a SessionDB row tagged <code>source=webhook</code> with <code>external_id=alert_id</code>.</p><p><strong>Triage agent (toolset `soc_triage`).</strong> Enable memory, web search, MCP read tools for your SIEM (Splunk search, Elastic query, Sentinel KQL via MCP), and <code>session_search</code>. Disable terminal, browser, and delegation. Stable-tier prompt: classify severity, deduplicate against open cases, recommend investigate vs close. Volatile tier: alert JSON snapshot and day stamp.</p><p><strong>Investigation agent (toolset `soc_investigate`).</strong> Add <code>delegate_task</code>, read-only terminal (Docker sandbox with no outbound except allowlisted threat-intel APIs), and browser for sandbox portals. Context tier loads <code>AGENTS.md</code> for your environment's log field names. Orchestrator-role subagents spawn leaf workers per IOC cluster; each child gets 50 iterations and no recursive delegation.</p><p><strong>Response agent (toolset `soc_respond`).</strong> Minimal tools: ticket update, webhook ack, optional integration MCP for ServiceNow/Jira. Pre-tool-call hooks require analyst confirmation in Slack before <code>execute_command</code> or containment MCP calls fire. Tool guardrails halt the turn if the model attempts destructive strings outside an approved playbook step.</p><p><strong>Cron hunter.</strong> Scheduled jobs in <code>cron/jobs.yaml</code> run threat-hunt prompts against yesterday's logs with <code>skip_context_files</code> and a dedicated profile <code>profiles/threat-hunt/</code>. Results post to a Slack channel; analysts branch sessions with <code>/branch</code> when a hunt hits signal.</p><h3>Implementation steps</h3><p><strong>Step 1 &#8212; Profiles and toolsets.</strong> Create <code>~/.hermes/profiles/soc-prod/</code> with separate <code>config.yaml</code> toolset lists:</p><pre><code># soc_triage excerpt &#8212; register custom toolsets in toolsets.py
enabled_toolsets:
  - memory
  - web
  - mcp_siem_read
disabled_toolsets:
  - terminal
  - browser
  - delegation</code></pre><p>Register MCP servers for SIEM read-only endpoints. Never give write tokens to the triage profile.</p><p><strong>Step 2 &#8212; Skills as playbooks.</strong> Add <code>~/.hermes/profiles/soc-prod/skills/phishing-triage/SKILL.md</code> with decision trees: verify SPF/DKIM anomalies, check user-reported volume, escalate if C-level targeted. The stable prompt indexes the skill; the investigate agent calls <code>skill_view</code> when subject lines match patterns.</p><p><strong>Step 3 &#8212; Gateway wiring.</strong> Run the Hermes gateway with platform adapters for Slack and a small FastAPI webhook receiver that normalizes alerts to plain text plus structured metadata in the user message. Map <code>#soc-alerts</code> channel IDs to triage toolsets; map <code>#soc-warroom</code> to investigate toolsets with analyst user ID allowlists in message guards.</p><p><strong>Step 4 &#8212; Session and case model.</strong> Store <code>case_id</code> in session metadata (custom field via session title prefix or memory entry). Use <code>parent_session_id</code> when compression forks a long investigation. Analysts run <code>session_search</code> for prior incidents involving the same host or user.</p><p><strong>Step 5 &#8212; Delegation for enrichment.</strong> Parent investigate agent prompt template:</p><pre><code>Delegate parallel leaf tasks: (1) passive DNS for each IP,
(2) VT summary if hash present, (3) user login timeline from SIEM.
Merge into single timeline; cite subagent session IDs.</code></pre><p>Each child session persists tool traces separately; parent transcript stays readable for audit.</p><p><strong>Step 6 &#8212; Approvals and audit.</strong> Wire pre-tool-call hooks to post Slack interactive buttons ("Approve host isolation?"). Log hook decisions to SessionDB via tool middleware traces. Export sessions for compliance with existing SIEM retention policies.</p><p><strong>Step 7 &#8212; Observability.</strong> Bind <code>session_id</code> in structured logs; ship to your log stack. Track iteration budget exhaustion and compression events as SOC KPIs (mean time to enrich, cost per case).</p><h3>Security patterns specific to agentic SOCs</h3>
