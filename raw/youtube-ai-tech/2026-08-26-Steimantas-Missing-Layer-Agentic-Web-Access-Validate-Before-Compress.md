# The Missing Layer in Agentic AI — Giedrius Šteimantas, Oxylabs

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=XsvUhpnHepE

## TL;DR
A vendor talk with one genuinely excellent idea in it, worth reading past the pitch for. The frame is a friend's shopping agent that worked intermittently: a chatbot that discussed style, produced prompts, and handed them to an agent meant to find and buy items online. It was vibe-coded with a browser automation framework for every stage, so it got CAPTCHAs, needed retries, was slow, expensive, and had unpredictable cost per transaction. Šteimantas rebuilds it in three stages and applies the scraping industry's cost discipline to each. Discovery, replace the predefined retailer list and browser with a search API returning compact JSON under 2,000 tokens per response in under 700ms, letting the agent fan out queries. Decision, replace parallel browsers with a REST scraper API that returns markdown, fails loudly with an explicit error on a block, supports geolocation, and charges only for successful results. Execution, where a browser genuinely is required for form input and dynamic content, keep Playwright MCP but swap the browser for one with stealth at the source level, a residential proxy, and matching geolocation. The insight that makes this talk worth a page is the moment he corrects himself mid-thought: his first instinct for token waste was compression, and then he realised the problem was not size but validity. If seven of ten fetches return CAPTCHAs and you feed all ten to the model, you waste 70% of tokens and compression cannot help you.

## Key Takeaways
- Three operating principles from scraping, stated as directly transferable to agent design: use a browser only when you absolutely have to, validate content rather than trusting the response code, and prefer lighter content because most bytes on a page carry no value.
- HTTP 200 does not mean success. This is the single most important line in the talk. A CAPTCHA page, an interstitial, and a block page all return 200 with plausible content length, so status code plus size is not a validity check.
- The token-waste arithmetic is the concrete case for validation gating. Ten fetches, three valid, all ten sent to the model, 70% of the token spend consumed distinguishing valid shop content from CAPTCHAs, which the model can do but should never be asked to do.
- The self-correction is the intellectual core: compression was the wrong first instinct because the content was not merely large, it was invalid. Validity must be established before compression is even meaningful.
- Fail-loudly design is what makes validation gating cheap. If a block returns an explicit error rather than a plausible page, the caller knows to exclude it, so no model tokens are spent on it at all.
- Discovery does not need a browser. Replacing it with a search API also removes a hidden constraint: a hardcoded retailer list caps the agent's option space at whatever the developer thought of, while search over an already-indexed web does not.
- Small responses enable cheaper models. Because search results come back under 2,000 tokens, the discovery stage does not need a strong model, which is a per-stage routing decision falling directly out of the payload size choice.
- Markdown instead of raw HTML at the API boundary. Passing raw HTML to an LLM spends tokens on markup that carries no task-relevant information.
- Geolocation is a correctness requirement rather than a nicety, and the failure mode he describes is subtle. E-commerce sites vary stock, sizes and availability by user location, so a discovery stage without geolocation finds items that are unavailable at checkout. Location must be consistent across all three stages or the pipeline produces confidently wrong results.
- Pay-per-success pricing changes the cost model qualitatively, not just quantitatively. Cost per successful outcome is predictable in a way cost per attempt is not, and unpredictable cost per transaction was the friend's actual business problem.
- Browsers are correctly characterised as necessary and expensive: he keeps them only for the purchase stage where inputs must be processed and content is highly dynamic, and swaps the browser implementation rather than the framework, since a hardened headless browser is a drop-in Playwright MCP replacement.
- The observability point is made almost in passing and is the most damning thing in the talk: his friend noticed the failures because he had good observability, and what Oxylabs sees from customers generally is that they do not detect the failure at all. Silent degradation is the norm.

## Architecture & Optimization Mechanics
Validate before compress is a general principle and it deserves promotion out of the web-scraping context, because the same mistake is endemic in inference pipelines. The structure of the error is that you observe high token cost, diagnose it as a size problem, and reach for a size-reduction technique, when the actual defect is that a large fraction of the input carries no signal at all. Compression applied to that situation reduces the cost of processing garbage. It does not stop you processing garbage. The correct intervention is upstream and cheaper: a validity predicate that drops the bad fraction before it enters the expensive path.

The same shape recurs across the work you actually do. A retrieval-augmented pipeline that reranks and then compresses retrieved passages, when a meaningful share of retrieved passages are irrelevant, is compressing noise. A KV-cache compression scheme applied to a context window half-filled with boilerplate is compressing boilerplate faithfully. A prompt-compression method applied to a prompt containing a stale tool output is preserving the stale output more efficiently. In each case the measured win is real and the achievable win is much larger from a cheap upstream filter. The diagnostic question, and it is worth making a habit of, is what fraction of the tokens entering this stage could have been dropped by a predicate that costs nothing. If that fraction is large, work on the predicate first, because compression multiplies a smaller number.

The second transferable mechanic is per-stage model and transport selection driven by payload characteristics rather than by task difficulty. He gets to a cheap fast model in discovery not because discovery is easy in the abstract, but because he engineered the payload down to under 2,000 tokens of structured JSON. That is the right causal order. Payload shape is a design variable you control, and controlling it determines which model tier you need. Most routing discussions treat the input as given and the model as the choice. Reversing that, choosing the representation first and letting it determine the model, produces bigger savings because it moves both the token count and the capability requirement at once. Markdown over raw HTML is the same move at a smaller scale.

The browser decision is a clean instance of using the expensive tool only where its distinguishing capability is required. A browser's actual differentiator is executing JavaScript and handling stateful interaction with form inputs. Discovery needs neither. Decision needs rendering but not interaction, which a scraper API with rendering under the hood provides at REST-call cost and, crucially, at REST-call concurrency, since he can run hundreds in parallel rather than paying for hundreds of browser instances. Only the purchase stage needs statefulness. Three stages, three transports, one capability boundary drawn correctly. The generalisation is that if you are using one tool for a whole pipeline, you are paying its worst-case cost at every step.

The consistency requirement across stages is the subtlest engineering point and the easiest to get wrong. Geolocation must match between discovery, verification and purchase, or the pipeline validates a product that does not exist for the buyer. This is a state-coherence bug, not a data-quality bug, and it produces failures that look like flakiness at checkout and are actually determinism failures three stages upstream. Anything analogous in a multi-stage LLM pipeline, tokenizer version, retrieval index snapshot, system prompt revision, tool schema version, has the same property: an inconsistency between stages produces a confident wrong answer rather than an error, and it is invisible unless you assert the invariant explicitly.

## Grounded Context (Web Enrichment)
The products are real and the numbers are broadly consistent with published material. Oxylabs' Fast Search API is described as a lightweight, low-cost organic search scraper for AI pipelines, returning JSON with ten organic results plus top stories and news, with title, link, description and SERP position, built for high throughput and low latency, with built-in geolocation, locale and domain controls. The Web Scraper API handles proxies, CAPTCHA handling, JS rendering and parsing in a single request and returns HTML or structured JSON. The specific figures he quotes, under 2,000 tokens per response and under 700ms average, and the pay-only-for-successful-results pricing, are not independently confirmable from published documentation and should be treated as vendor claims. Worth noting an internal inconsistency across Oxylabs talks: this one cites under 700ms average for the fast search API while a colleague's talk two weeks earlier cited 550ms average and 650ms P90 for different generations of the same product. Neither gives P95 or P99 by geography, which is what you would need to size a multi-hop agent budget.

The context that changes how you should read this talk is that the industry is moving in the opposite direction from stealth. Web Bot Auth, a Cloudflare-led IETF effort built on RFC 9421 HTTP Message Signatures, has bots sign requests with a private key and publish public keys at a well-known location, so sites verify a signature instead of trusting a User-Agent. Supported agents already include Anthropic's Claude, OpenAI's ChatGPT, Perplexity and Common Crawl, and reporting indicates certified agents including ChatGPT Atlas, Claude in Chrome, Perplexity's browser and Gemini's agent mode now sign requests with verifiable tokens. Enforcement is arriving on a schedule: Shopify's developer changelog confirmed on 7 May 2026 stricter rate limits for any bot or agent hitting the Storefront API or Shopify-hosted store pages without a signed identity, and Cloudflare announced on 1 July that from 15 September 2026 new defaults block Training and Agent bots automatically on pages carrying ads while Search bots stay allowed. AWS shipped Web Bot Auth in Bedrock AgentCore Browser preview specifically to reduce CAPTCHAs. The standard is not yet adopted at IETF, with no adopted working group documents as of 12 August 2026, but Cloudflare, AWS WAF, Akamai, HUMAN and Vercel already verify signatures in production.

That matters directly for the talk's central example. A shopping agent completing purchases on retailer sites, many of which are Shopify-hosted, is exactly the workload that Shopify's signed-identity requirement targets. Šteimantas's solution is better stealth at the browser source level plus residential proxies, which is an arms-race position. The alternative emerging position is a cryptographically verifiable agent identity that a merchant can choose to allow because it can tell who is calling and rate-limit accordingly. These are not complementary approaches, they are competing regimes, and for an agent that intends to transact rather than merely read, the signed path is the one the merchant infrastructure is being built to accommodate. The talk does not mention Web Bot Auth, signed identity, or the September Cloudflare deadline once, which for a talk titled "The Missing Layer in Agentic AI" delivered on 26 August 2026 is a conspicuous omission rather than a small one.

Being fair to the talk: none of that invalidates the engineering. Validate before compress, browser only where interaction is required, per-stage payload engineering, and cross-stage geolocation coherence are all correct regardless of which access regime wins, and they are correct for a self-hosted pipeline with signed identity just as much as for a proxied one. The parts that are contingent on the arms race are the stealth and residential-proxy components, which are the parts he is selling.

## Real-World Application / Actionable Step
1. Add a validity predicate before every expensive stage in every pipeline you own, and stop treating status code plus payload size as a success check. This is the highest-value item here and it is nearly free. For any fetch, parse or tool call feeding a model, assert on content shape and reject explicitly, so blocked or degraded responses never consume model tokens.
2. Run the validate-before-compress diagnostic on your own compression work. Before optimising a stage's token cost, measure what fraction of tokens entering it could be dropped by a zero-cost predicate. If that fraction is material, the filter dominates the compression, and reporting the compression win without the filter overstates what you achieved.
3. Engineer the payload representation before selecting the model tier, not after. He reached a cheap fast model in discovery by getting responses under 2,000 tokens of structured JSON, which moved token count and capability requirement together. Structured output over prose, markdown over markup, and schema-constrained tool returns are all the same lever.
4. Draw the capability boundary for expensive tools explicitly. A browser's real differentiator is JS execution plus stateful interaction. If a stage needs neither, it should not have one, and if it needs rendering but not interaction there is a cheaper transport with far better parallelism. Audit any pipeline where one tool spans every stage, because you are paying its worst case throughout.
5. Assert cross-stage invariants that would otherwise produce confident wrong answers. His geolocation-mismatch bug manifests as checkout flakiness and is actually a determinism failure in discovery. The equivalents in your stack are tokenizer version, retrieval index snapshot, prompt revision and tool schema version, and each one silently corrupts rather than erroring. Assert them at stage boundaries.
6. Track cost per successful outcome rather than cost per attempt, for every agentic workload. The friend's real problem was not high cost but unpredictable cost per transaction, and that is a direct consequence of measuring attempts while being billed for outcomes. The metric change is what makes retries visible in the budget.
7. Instrument for silent failure specifically, since his strongest observation is that customers usually do not notice. Log the validity-predicate rejection rate as a first-class metric and alert on its trend, because a rising rejection rate is the earliest available signal that an upstream dependency has started blocking you.
8. Before building any transacting agent on proxy-and-stealth infrastructure, evaluate the signed-identity path instead. Web Bot Auth is verified in production by Cloudflare, AWS WAF, Akamai, HUMAN and Vercel, Shopify has required signed identity for full rate limits since 7 May 2026, and Cloudflare's Agent-bot defaults tighten on 15 September 2026. Stealth is an arms race with a scheduled escalation; a verifiable identity is a permission you can be granted.
