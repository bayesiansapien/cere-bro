# The End of the Static Screen: Architecting Intent-Driven UX | Gus Iwanaga, commercetools

**Channel:** AI Engineer
**Published:** 2026-09-01
**Source:** https://www.youtube.com/watch?v=QrMcNe2jjt8

## TL;DR
Iwanaga's premise is that we have shipped static experiences for forty years and users still adapt themselves to software rather than the reverse, accumulating cognitive load across every SaaS app with its own mental model. His team at commercetools built a generative UI product where a query is intent-classified, tools are invoked, and a UX agent renders a native interface. The honest part of the talk is that the first attempt failed: four identical-intent queries produced four inconsistent layouts, one saying Q1 and another saying January to March, and his own verdict was that he would not ship it. The fix is the taxonomy at the centre of the talk, three levels of control over generative UI. Controlled means you ship a fixed opinionated component and the agent selects it. Open-ended means the LLM emits raw HTML rendered in a sandboxed iframe. Declarative sits in between: the agent emits a UI spec against a curated component catalogue with schema validation, and the client renders native components. They chose declarative, and the hard part turned out to be information architecture rather than component selection.

## Key Takeaways
- **The three-way control taxonomy is the most useful framework in this talk.** Controlled: the merchant or vendor ships a fixed component, the agent picks it, output is exactly as designed. His example is ChatGPT's opinionated restaurant card, which works well when the business needs tight control. Open-ended: full delegation, the LLM produces HTML, rendered in a sandboxed iframe in whatever host (Claude, ChatGPT, Perplexity). His assessment of open-ended is blunt: "good luck." Declarative: the middle path, and the one they shipped.
- **The failure mode of full delegation is inconsistency, not incorrectness, and that is the important distinction.** Four turns on the same intent produced four different layouts with different copy and different metric groupings. Nothing was wrong. Nothing was the same. For a personalised experience where the user prompts repeatedly, that variance destroys usability, because the user cannot build a mental model of a surface that reshuffles every turn.
- **Component selection is easy, arrangement is hard.** Once the orchestrator has fetched the eligible components for a query, the open question is who arranges them, and that is information architecture. Left to the LLM, placement is effectively random.
- **Their solution is a codified layout hierarchy, and it is the most transferable engineering detail.** Layout contains slots, slots contain sub-slots (recursively), and sub-slots declare eligible component categories. Because the orchestrator produces components first, they traverse the hierarchy in reverse: components map to sub-slots, sub-slots to slots, slots to templates. That inversion is what lets retrieved components be placed deterministically rather than arbitrarily. They borrowed atomic design as the organising methodology and taught the UX agent what good looks like via a catalogue of templates.
- **The component catalogue is the contract between agent and UI, and every property matters.** He stresses curation of both the component catalogue and the layout components (slots and sub-slots each have their own attributes), and says this curation is what separates a shippable product from a demo. They use Zod schemas for the catalogue and must remain compliant with whichever UI protocol they target.
- **Declarative gives design-system compliance everywhere, which is the deciding advantage.** With full delegation you cannot control copy, so "Q1" becomes "January to March." UX is not only layout, it is UI plus copy plus UX writing, and delegating the render delegates all three.
- **The orchestration path, stated plainly:** query, intent classification, tool invocation (first-party, third-party, agents, MCP servers), data retrieval, mapping of eligible catalogue components to tool entities, orchestrator broadcasts a UI spec, client renders native React components.
- **The organisational finding is the one people will underestimate.** His teams no longer design pixels. The work shifted to schemas, catalogue curation, rules, synthetic data generation, and mapping queries to components. He notes this was a significant adjustment for non-technical PMs and UX designers, and frames it as people, product, process, with people first.
- **His diagnosis of the status quo is well chosen.** He shows a famous CRM screen and asks how many teams were involved in shipping it, then points out the real cost: the onboarding time these companies must fund because of accumulated interface complexity.

## Architecture & Optimization Mechanics
The reverse-traversal layout hierarchy is the genuinely clever piece of engineering here and it is worth understanding precisely, because it solves a general problem.

The naive design would be: classify intent, select a template, fill the template's slots with components. That fails when the orchestrator's tool calls return a component set that does not match any template, which is the common case in an open-ended query space. Iwanaga's inversion runs the other way: take the component set you actually have, map each component to the sub-slot types that accept it, aggregate sub-slots into slots, and aggregate slots into the template that best accommodates them. That is a constraint-satisfaction formulation rather than a template-matching one, and it means the layout is derived from the content instead of the content being forced into a layout. The same structural move appears in query planning (bottom-up rather than top-down join ordering) and in register allocation, and it is the right answer whenever the available inputs are more variable than the available containers.

The determinism argument is where this talk connects to Amit's work most directly. Generative UI is a case study in the general question of how much of a system's output should be model-generated versus schema-constrained, and Iwanaga's answer is empirical: full generation produced unusable variance, and constraining output to a validated component catalogue recovered consistency while keeping adaptivity. That is exactly the structured-output tradeoff. Constrained decoding against a schema costs some expressiveness and buys reliability, and the right amount of constraint is determined by how much variance the consumer can tolerate. A human reading a UI tolerates very little. A downstream parser tolerates none. A human reading prose tolerates a lot. Iwanaga's three-level taxonomy is a good general vocabulary for that spectrum and it applies well beyond interfaces.

There is also an unstated cost argument in favour of declarative that strengthens his case. Emitting a compact UI spec referencing catalogue components by identifier is far fewer output tokens than emitting HTML, and output tokens are the expensive ones. So the declarative approach is cheaper per render, faster to first paint, and cacheable at the component level, while the open-ended approach pays full generation cost every turn for output that cannot be cached because it is never identical. He never makes this argument, and it is probably the strongest one available to him.

One thing the talk does not address: how the UX agent is evaluated. He says they taught it what good looks like and built a template catalogue, and shows before-and-after screenshots with an audience thumbs-up as the acceptance criterion. There is no mention of an automated rater for layout quality, consistency across repeated identical queries, or regression testing when the catalogue changes. Given that his original failure was precisely inconsistency across turns, a same-intent-repeated-N-times consistency metric is the obvious missing measurement, and it would be straightforward to build.

## Grounded Context (Web Enrichment)
The protocols he names are real and the transcript garbles two of them, so here is the corrected landscape.

What the transcript renders as "HTMX from Google" and "ATUI" is **A2UI** (Agent-to-User Interface), Google's open project for agent-driven interfaces. Google officially released A2UI as a public open-source project in January 2026, with v0.9 positioned as a standard for portable, framework-agnostic generative UI. It is a declarative, streaming JSONL specification in which agents request allow-listed components that the client renders natively across Flutter, Angular, and Lit, and it works on web, mobile, and desktop. That allow-listed-component design is exactly the declarative middle path Iwanaga describes, so his architecture is aligned with where the standard landed.

**Vercel's json-renderer** is real and supports A2UI as a proof of concept, so "JSON render from Vercel" is accurate. **Thesys** operates differently from how he implies: it is an API wrapper where you point your OpenAI client at their endpoint and they intercept the response and convert it into UI components, which is a hosted transformation service rather than a protocol. OpenUI publishes a state-of-generative-UI report and positions itself as an open standard. CopilotKit maintains examples spanning AG-UI, A2UI/Open-JSON-UI, and MCP Apps, and MCP Apps is the one to watch for MCP-first architectures.

The most important validation for his talk: the 2025-2026 wave of production systems has converged on constrained and declarative output, with agents emitting allow-listed components rather than raw code, specifically for safety and consistency. That is independent confirmation of his central claim, arrived at across the industry rather than only at commercetools. Current guidance splits by need: A2UI for cross-platform portability, Thesys or Crayon for fastest prototype, MCP Apps for MCP-first designs.

Two caveats on the talk itself. It is a pre-production demo (he says explicitly the approved output is pre-prod) presented by the general manager of the team that built it, with audience thumbs-up as the quality measure, and no metrics on task completion, time-to-answer, error rate, or user satisfaction against the static baseline he criticises. The honest inclusion of the failed first attempt earns considerable credibility, and it does not substitute for measurement. Second, his framing that this is inevitable ("this is coming, it's just a matter of time") is a prediction, and the counterweight is in the Google DeepMind talk at the same conference: their user studies found people want to stay involved in upper-funnel exploration rather than delegate it. Adaptive interfaces and stable interfaces are not obviously ranked, and Jeffrey Wang's argument at this same event for crystallised UIs on recurring tasks is the direct counterargument Iwanaga does not engage.

## Real-World Application / Actionable Step
- **Adopt the three-level control taxonomy as general vocabulary for structured output, not just for UI.** Controlled (fixed artefact, model selects), declarative (model emits a spec against a validated schema), open-ended (model emits raw output). The right level is set by how much variance the consumer tolerates. This is directly the constrained-decoding question in Amit's work and this is a cleaner framing of it than the usual one.
- **Build the consistency metric his failure mode demands.** Run the same intent N times and measure output variance (component set overlap, layout distance, copy stability). His original problem was pure inconsistency, and there is no evidence they measure it. For any structured-output system, same-input-repeated variance is a cheap, automatable, and rarely-collected metric.
- **Steal the reverse-traversal pattern for any content-to-container mapping problem.** Derive the container from the available content rather than forcing content into a preselected container. Components to sub-slots to slots to templates, run bottom-up. Applicable well beyond UI, to report generation, dashboard assembly, and prompt assembly from retrieved chunks.
- **Note the token-cost argument he misses.** A compact spec referencing catalogue components by identifier is far cheaper in output tokens than generated HTML, faster to first render, and cacheable per component. If Amit is evaluating structured versus free-form generation anywhere, output-token count and cacheability are quantifiable advantages of the constrained path and they usually go unmeasured.
- **Take the organisational point seriously if adopting any of this.** The work moves from designing artefacts to curating schemas, catalogues, rules, and synthetic data. That is a genuine skills shift for designers and non-technical PMs, and he names it as a bigger obstacle than the technology. The same shift applies to any team moving from hand-built to generated outputs.
- **Read the counterargument before accepting inevitability.** Stable interfaces have real value for recurring tasks because users build muscle memory, and Google's own user research says people want to drive discovery themselves. The strong version of Iwanaga's thesis is that all interfaces become adaptive. The defensible version is that adaptive interfaces win for novel one-off queries and stable ones win for repeated tasks, which is the same split Jeffrey Wang argued at this conference and which no talk here reconciles.
