# AI-Native Organisations Run on Skills: How to Structure and Scale Them | Imad Touil, QuantumBlack

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=M05vON8i0aI

## TL;DR
Touil opens with a show of hands that collapses in three steps: most of the room uses skills, fewer share them across teams, almost nobody governs them organisation-wide. That gap is the talk. His argument: in the agentic software stack, hooks are just event triggers, MCP servers are mostly consumed rather than authored, and subagents exist only to protect the context window, which means all of an organisation's actual know-how ends up encoded in skills. Ungoverned skills therefore constitute a new class of technical debt with six failure modes: duplication, quality decay against new models, undiscoverability, no ownership, no composability, and security exposure through prompt injection and the executable scripts skills carry. His prescription is a three-tier maturity path (individual, team, centralised platform) with a catalog carrying metadata, dependencies, versioning, access control, and evaluation, plus a human governance body of architects and engineering, infra, and cyber leads.

## Key Takeaways
- **The stack decomposition is the framing worth stealing.** Inner loop: the coding agent harness with context manager, tools and MCPs, memory and state, and skills loader. Outer loop: workflows composed of skills, subagents, MCP servers, and hooks. Enablement layer beneath: environment sandbox, MCP gateway, model gateway, knowledge graph over IT systems and codebase and skills registry, and a workflow marketplace. Context layer on top: project instructions (the CLAUDE.md or AGENTS.md file), tool and MCP schemas, memory, and retrieved content.
- **Workflows are harness blueprints.** His definition: a workflow shapes the runtime behaviour of the coding harness. Skills are what make a workflow deterministic rather than improvisational.
- **The specify-design-tasks-implement loop is one step, not the whole thing.** At organisational scale, that four-step cycle is just "build a product increment." The real lifecycle wraps it in product strategy (success metrics, roadmap, informed by market research, competitive analysis, customer interviews), discovery (problem statements, solution validation, experiments, user stories), data product delivery (pipelines, quality validation, catalogued assets), then platform engineering and ops (infrastructure as code, launch, performance optimisation, incident resolution), and loops. Critically, a single organisation runs several different SDLCs simultaneously: mobile, internal platform, customer-facing, per department. There is no one workflow.
- **Skills reuse the microservices design principles wholesale,** and Touil is explicit that this is not a new problem: reusable, modular, discoverable, portable (across workflows and across harnesses, since everyone adopted the same standard), specialised (one task, never a monolith), composable (no overlapping duplication that conflicts at runtime), consistent, and cost-efficient.
- **The cost argument is the progressive disclosure argument.** Skills solve a context-window problem by loading the right skill, in the right amount, at the right time. He frames the result as a new unit that makes organisational know-how "executable, portable, and cheap."
- **The composability example is concrete and good.** A regulatory disclosure review workflow pulls, at runtime, a data retention policy skill, disclosure standards, GDPR rules, and fill-in templates. Output is a deterministic audit report plus identified improvements that loop back into the codebase.
- **Security is the most underweighted risk he names.** Public skills can carry prompt injection, and skills contain scripts by design, because the script is the deterministic part. Without a security-checking pipeline you are pulling executable code from a registry.
- **Ownership is framed as the internal developer portal problem.** Backstage solved "who owns this microservice" via a service catalog. Skills need the same, because without an owner nobody maintains or scales them.
- **He is appropriately skeptical of the auto-evolving hype.** Self-improving closed-loop skill evolution amplifies whatever governance you have. Without guardrails, automating the machine makes the damage worse, not better.
- **On evaluation he admits the field has no settled answer,** and offers a pragmatic proxy: statically evaluate skills against Anthropic's published best practices, on the theory that a skill that is not structured or invoked properly is unlikely to be high quality.

## Architecture & Optimization Mechanics
The line most relevant to Amit's work is one Touil delivers in passing: "subagents is just to minimise the context window. We just delegate to a subagent to execute a specific task." That is the correct and underappreciated framing. Subagent delegation is not primarily an abstraction or orchestration device, it is context isolation. The parent's window stays small because the subagent's intermediate reasoning, tool output, and dead ends never enter it, only the result does. Reframed in serving terms, subagent delegation is a way to keep the parent's KV cache small and its prefix stable while the expensive, high-variance token consumption happens in a disposable child context. That is a genuine optimization and it should be sized as one: measure parent-context growth with and without delegation across a long task.

The progressive disclosure mechanic deserves precise treatment because it involves a real tradeoff that Touil skips. Three-stage loading (name and description always resident, full instructions when the skill is judged relevant, supporting assets only during execution) minimises resident tokens. But it also means the resident prefix changes per task, which fragments prefix caching. The correct design keeps a stable, cacheable base prefix and appends the task-conditioned skill payload after it, so that the cached portion is maximised. This is the same conclusion the Snowflake talk in this corpus reaches from the opposite direction, after hitting an agent-instruction context ceiling and being forced into progressive disclosure as a remedy. Two independent talks, same wall, same fix.

The name-and-description-always-resident design also creates a scaling problem Touil gestures at without naming. As the skill count grows into the hundreds, the always-resident descriptions themselves become a substantial fixed context cost, and worse, semantically similar descriptions make the selection decision ambiguous. Skill selection is a retrieval problem, and it degrades exactly the way retrieval degrades: precision falls as the candidate set grows and as candidates become less distinguishable. This is where his "specialised, one task each" principle collides with his "composable, no duplication" principle, since maximally specialised skills produce the largest and most confusable catalog. The resolution is hierarchical retrieval: route to a domain, then select within it, rather than flat selection over everything.

His deduplication claim is worth checking against mechanism. He asserts that once a skill is published centrally, "the next engineer trying to build a new skill, the coding agent harness will identify this skill that is already available and pull it." That only holds if the harness actually searches the registry before authoring, which requires the MCP-plus-CLI integration he describes and is not automatic. The simulation he shows, 15 teams over six months with and without governance, is a synthetic model with assumed parameters, not measured data. Treat the directional argument as sound and the specific numbers as illustrative only.

## Grounded Context (Web Enrichment)
Touil's timeline is slightly off and everything else checks out, with the security concern being far better documented than his talk conveys.

Anthropic formalised Agent Skills in October 2025 across Claude's product surface, then released the SKILL.md format as an open standard in December 2025, now stewarded at agentskills.io. So from August 2026 that is roughly ten months, not the eight he states, and the gap between launch and standardisation was about two months, which matches his account. The specification is deliberately minimal: a folder, a SKILL.md file with two required frontmatter fields (name and description), and optional scripts, references, and assets. Progressive disclosure works exactly as he describes across Claude Code, Codex CLI, and Gemini CLI: name and description first, full instructions when relevant, supporting materials only at execution.

His portability claim is stronger than he suggests. Adoption spans 40-plus clients including Claude Code, Cursor, GitHub Copilot, VS Code, OpenAI Codex, Gemini CLI, Goose, plus data platforms including Databricks and Snowflake. Cross-harness portability is real, which validates the microservices analogy: a standard interface is what makes a component market possible.

The governance gap he warns about is documented as a structural property of the standard, not merely an organisational oversight. The spec has no signing, no attestation, and no mandatory review, and its only permission control (`allowed-tools`) is experimental with implementation-dependent behaviour. Governance is explicitly delegated to the runtime and the organisation. As of May 2026 multiple registries expose thousands of skills, and because registries mediate which third-party skills get admitted, surfaced, and installed, their ranking and metadata presentation are now part of the agent security boundary. That is a sharper statement of his point than he makes: the registry is not a convenience layer, it is a trust boundary.

The academic literature has moved faster than the talk implies, and it addresses precisely the problems he leaves open. On security, "Under the Hood of SKILL.md: Semantic Supply-chain Attacks on AI Agent Skill Registry" (arXiv 2605.11418) and "Formal Analysis and Supply Chain Security for Agentic AI Skills" (arXiv 2603.00195) treat skills as a software supply chain with the attack surface that implies. On the evaluation question he says is unsettled, "SkillJuror: Measuring How Agent Skill Organization Changes Runtime Behavior" (arXiv 2606.11543) measures exactly the effect he wants to quantify, and "SkillResolve-Bench: Measuring and Resolving Same-Capability Ambiguity in Agent Skill Retrieval" (arXiv 2606.10388) formalises the catalog-confusability problem his specialisation principle creates. There is also a broader survey, "Agent Skills for Large Language Models: Architecture, Acquisition, Security, and the Path Forward" (arXiv 2602.12430), and work on automated skill mining from open-source agentic repositories (arXiv 2603.11808), which is the auto-evolving direction he is right to be cautious about.

One claim to hold loosely: he references a "skills bench" showing higher outcomes with skills than without on auto-engineering and cybersecurity tasks, but gives no source, sample size, or effect size, and the transcript is garbled at that point. SkillJuror is the closest published work on that question and is the better citation.

## Real-World Application / Actionable Step
- **Read SkillResolve-Bench before designing a skill catalog.** The ambiguity problem it formalises is the one Amit will hit second, right after solving discovery. Maximally specialised skills produce maximally confusable descriptions, and hierarchical routing (domain first, then skill) is the fix. Designing for it upfront is far cheaper than retrofitting.
- **Measure the progressive-disclosure tradeoff rather than assuming it is a win.** Instrument resident tokens and prefix-cache hit rate with and without dynamic skill loading. Task-conditioned payloads cut token count but fragment the cache. The right architecture is stable base prefix plus appended skill slice, and the delta is measurable on Amit's own workloads.
- **Quantify subagent delegation as context isolation, not as orchestration.** Track parent-context token growth over a long multi-step task with and without delegation. If the parent stays flat while children absorb the variance, that is a concrete serving-cost win worth reporting as such.
- **Treat the skills registry as a software supply chain from day one.** Skills ship executable scripts and can carry prompt injection, and the standard provides no signing or attestation. Minimum controls: an allowlist of approved sources, static scanning of bundled scripts, mandatory review for anything with tool access, and per-skill ownership. The two supply-chain security papers are the reading list.
- **Version and re-evaluate skills against every new model release.** Touil's quality-decay point is the one most likely to bite silently: a skill tuned to one model's behaviour degrades against the next. Amit should add skill regression tests to whatever model-upgrade checklist he already runs, because this is the same class of problem as prompt drift across model versions and it fails quietly.
- **Do not automate skill evolution before governance exists.** His closing warning is correct and the mining literature makes it concrete. A closed loop that generates and promotes skills automatically will scale whatever quality and security posture is already in place, in both directions.
