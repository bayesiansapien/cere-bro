# Evolution of Agentic Surfaces

**Channel:** AI Engineer
**Published:** 2026-08-11
**Source:** https://www.youtube.com/watch?v=K0X9QDRkIdg

## TL;DR
Gagan Bhat and Isabella Kai He from Anthropic's Applied AI team trace three generations of agent-building surface (Messages API, Claude Agent SDK, Claude Managed Agents) and the technical content is much better than the product narrative suggests. The organising principle is one sentence worth memorising: harnesses encode assumptions about what the model cannot do on its own, and those assumptions go stale as models improve. Their worked example is exact and unusually candid. Sonnet 4.5 exhibited context anxiety, wrapping up work early as it approached its window even with room to spare, so they built context resets into the harness. When Opus 4.5 arrived the behaviour was gone entirely, and their fix became not merely dead weight but active harm, adding latency and discarding cache incorrectly. When the model moves and the harness does not, the agent degrades. The architectural centrepiece is decoupling the brain (agent loop) from the hands (tool execution), which they originally had in one container. Splitting them bought reliability, independent recovery, and a large latency win: 60% faster time to first token at P50 and over 90% at P95, because container setup left the critical path and can now run in parallel or be skipped entirely. Everything is logged to a durable session resource, which turns context management into something recoverable rather than lossy. The two frontier features are dreaming, a batch process that consolidates transcripts plus memory state into improved memory overnight, and outcomes, a rubric plus separate grader agent that retries until success criteria are met.

## Key Takeaways
- The task-complexity arc they use to motivate everything: first we asked models questions, then we delegated tasks, now agents own entire outcomes. As task complexity and model capability rise together, the surface has to evolve with them.
- Generation one, the Messages API shipped with Claude 3: tokens in, tokens out. Everything else was yours.
- What customers then built by hand, painstakingly and from scratch, was the agentic loop: call the model, run the tools, manage context. On top of that sat the product, and underneath sat a slew of production infrastructure they had to solve themselves.
- The production infrastructure list, posed as questions and worth using as a checklist for any agent going to production. Hosting and scaling: where does the agent run, how long does the process live, what scales under load. Session management: where does history and progress live, how do you run many concurrent agents. File system: how does the model create and edit files. Execution isolation: where does the code it writes actually run and how is that kept secure. Credentials: how does the model reach sensitive systems without ever seeing the tokens. Observability: with complex orchestration, how do you know what actually happened.
- Generation two, the Claude Agent SDK, packaged the Claude Code harness with a built-in agentic loop, file system access, tools, and sandboxing, plus primitives for session management and observability. Credentials and hosting were still hand-rolled, and you still had to work out how to box it and scale it.
- Generation three, Claude Managed Agents, splits ownership explicitly. You own the product, the task, the context, and the domain knowledge. Anthropic runs the brain (agent loop plus model plus harness evolutions), the hands (a just-in-time sandbox for file system and code execution), and credentials, session management, observability, and hosting.
- The core principle, and the most valuable idea in the talk: harnesses encode assumptions about what Claude cannot do on its own, things like resetting context and managing compaction, and those assumptions must be questioned frequently because they go stale as models improve.
- The context anxiety case study in full. Sonnet 4.5 became anxious as it approached its context limit, wrapping up tasks early and terminating work while room remained. The harness fix was built-in context resets. Opus 4.5 no longer exhibited the behaviour, so the fix became pure overhead: added latency, and cache being discarded incorrectly at times. Their conclusion is stated as a rule. When the model moves and the harness does not, it degrades the agent.
- The enterprise observation that follows: customer harnesses range from agile to rigid, with the rigid ones built around older Claude models, and a stale harness that takes weeks or months to migrate is a serious liability given how much shorter release cycles have become.
- What an effective harness therefore requires: design for the model capabilities of tomorrow rather than today, and be agile enough to iterate quickly the moment new capability lands.
- The design response is a small set of independent primitives that can be swapped and iterated individually while the overall architecture stays stable. Modularity as a hedge against model change rather than as general good practice.
- The long-running agent requirements they enumerate: context engineering because context accumulates over long horizons, a secure sandbox so the agent can act, reliability so it can run for hours or days, and parallelisation so it can attack multiple parts of a problem at once.
- The brain and hands decoupling, told as a mistake they made first. Agent loop and tool execution started in the same container, which was convenient because results were right there. Two limitations killed it: the container blocked the agent from starting model reasoning until setup completed, and if either component went down the whole box went down.
- Post-split failure recovery is clean in both directions. If the sandbox dies, the brain spins up a new one and continues from where it left off. If the brain dies, everything it did is in a durable session log, so a new brain reads the log, rebuilds context, and resumes.
- The three primitives. Agent: model, prompts, tools, skills, everything that makes it work for your use case. Environment: the container it runs in, where multiple sessions can share an environment definition and even run concurrently against it, each in its own isolated container instance. Session: agent plus environment, a durable cloud-persisted record of every interaction, which is what unlocks observability, long-running instances, and reliability.
- Four session states as the reliability mechanism: idle when waiting on user input, running when executing, rescheduling when it hit an error and will retry, terminated when unrecoverable. So a session can always be resumed and there is an explicit path out of a tool failure.
- The context engineering unlock, and this is the subtle one. In most harnesses the context window and the session are the same thing, so if the model discards part of its context there is no mechanism to get it back. Because managed agents logs everything to a durable session resource, the harness can read slices of context back into the window on demand, which makes context editing safe rather than irreversible.
- The resulting division of labour: rely on the harness for the agent loop, memory, and observability, and customise context management and domain expertise, since that is what separates a coding agent from a legal or go-to-market agent. Claude Code uses bash and grep like a developer in a terminal, and a legal agent needs a completely different tool set.
- The demo is a well-chosen example: an SRE investigator agent for a P99 latency spike at 10x baseline. Agent definition with Opus 4.8, a system prompt, the standard tool set (bash, grep, glob) plus an MCP tool set reaching the metrics dashboard. Environment configured on Anthropic cloud with networking restricted to allowed hosts, being only the MCP server. Logs uploaded as files. Then a session kicks off, and the agent greps the logs, pulls metrics over MCP, finds recent deploys, isolates when the incident started, finds the code diff, and synthesises a root cause.
- The environment as a boundary control, stated plainly: it stops Claude from doing things you did not intend, with allowed-hosts networking as the mechanism.
- Field lesson one, keep credentials away from the agent. The brain and hands split already helps since the loop runs separately from tool execution. Vaults go further: credentials stored encrypted and decrypted only at tool execution runtime, so the model never sees security tokens.
- Field lesson two, the latency result. In the coupled design the model could not emit a first token until container setup completed. Decoupled, model reasoning starts immediately while container setup runs in parallel, or setup is skipped entirely when the task does not need it. Measured: 60% faster time to first token at P50, over 90% improvement at P95.
- Field lesson three, session logs do double duty. Surfaced in a UI they are observability. Fed back with memory state they are self-improvement, because the log gives a history of past executions that dreaming can consolidate.
- Field lesson four, tool execution security. Because the hands are decoupled they can run anywhere, including your own VPC. Self-hosted sandboxes let customers control the sandbox control plane and run tools under their own policies. MCP tunnels let private MCP servers stay inside the private network, making only outbound calls to the Claude agent loop rather than being exposed to the public internet.
- Dreaming, described concretely: take the session transcripts from the agent's daily sessions plus the current memory state, run a periodic batch process, extract new insights and organised structures, and edit memory accordingly, so the next day's sessions are more intelligent. They position this as how self-improving agents emerge from repeated execution.
- The memory hierarchy they sketch: per-user memory scoped to the use case, dreaming for self-improvement, and an emerging organisational-scale memory holding a team's runbooks and details.
- Outcomes: you define a rubric of success criteria and failure cases, a separate grader agent runs alongside the agent loop, and if the grader judges the task incomplete the agent keeps trying until the criteria are met.
- Their closing thesis, and it is the framing to argue with: harnesses have become the limiting factor on what models can achieve, so managed agents exists to close the gap between what products offer on static harnesses and what models can actually do.

## Architecture & Optimization Mechanics
The stale-assumption principle is the idea to take away from this talk, and it transfers to compression work almost word for word. Every compression technique encodes an assumption about what a model cannot tolerate. Outlier-aware quantisation encodes an assumption about activation distributions having heavy tails in specific channels. Keeping particular layers in higher precision encodes an assumption that those layers are sensitive. Migration or smoothing scales encode an assumption about where the dynamic range problem lives. Those are all empirical facts about a specific model generation, not laws, and they go stale exactly the way context resets went stale. When a new model is pretrained with different normalisation, with quantisation-aware objectives, or simply with a different data mix that changes activation kurtosis, the mitigation you built stops being necessary.

The sharp part of their example, and the part most people would miss, is that a stale mitigation is not neutral. Their context resets did not just fail to help, they added latency and broke cache correctness. The compression equivalent is direct and measurable: a layer held in FP16 because it was sensitive in the previous model version costs memory bandwidth and breaks kernel uniformity for no benefit, and a smoothing transform applied to activations that no longer have outliers is wasted compute plus a numerical perturbation you did not need. So compression recipes should carry expiry dates and be re-validated per model release rather than inherited, and the specific validation to run is the ablation that removes each mitigation and checks whether accuracy actually moves. Most teams never run that ablation because the mitigation is load-bearing folklore by the time anyone questions it. Anthropic only found theirs because the behaviour it targeted disappeared visibly.

The latency result is the most immediately actionable engineering content here, and the mechanism is worth stating as critical-path analysis rather than as a product feature. Container setup was serialised ahead of first token, so time to first token included provisioning latency that had nothing to do with the model. Removing it from the critical path yields 60% at the median and over 90% at the tail, and the tail number is the informative one because it says provisioning variance dominated P95 entirely. That is the same lesson as the [Codex harness talk's](2026-08-10-Codex-Behind-The-Harness-Context-Auto-Review.md) discovery that network overhead became the bottleneck once decode hit 1,000 tokens per second. In both cases the model was not the slow part and the fix was in the surrounding system. Anyone benchmarking inference should take the general form seriously: measure the full request path, and check specifically whether anything is serialised ahead of first token that could be parallel.

The clause they mention almost in passing, that container setup can be skipped entirely when the task does not need it, is a routing problem and it is the piece I would build on. Deciding whether a given request requires tool execution before provisioning for it is exactly conditional resource allocation under uncertainty, with an asymmetric cost structure: provisioning unnecessarily costs latency and compute, failing to provision when needed costs a stall mid-session. That asymmetry means the right policy is not a symmetric classifier, it is a threshold tuned to the relative costs, and it probably wants speculative provisioning for the uncertain middle. This is the same structure as routing between model tiers and it is more tractable, because the label is observable after the fact from whether the session actually called a tool. A cheap, well-motivated experiment for anyone with production agent traffic.

Three independent talks in two days converged on externalised durable state, which is strong evidence it is the correct decomposition rather than a fashion. Here it is the session log that lets a dead brain resume and lets discarded context be read back. In the [Velocity Sickness talk](2026-08-09-Velocity-Sickness-Team-10x-Faster.md) it is agent-as-action separated from doc-as-state, making agents stateless and forkable. In the [Modal cross-datacenter RL talk](2026-08-10-Modal-Cross-Datacenter-RL-Sparse-Weight-Delta.md) it is immutable versioned weight artifacts on a bulletin board that any engine can pull. The shared property is that state lives outside the process that mutates it, which buys forking, inspectability, and crash recovery in all three. The Anthropic version adds one capability the others do not: because the log is append-only and complete, context editing becomes reversible. That is a genuinely useful primitive, since the standard objection to aggressive context pruning is that you cannot recover what you dropped, and a durable log removes that objection.

Outcomes deserves a more sceptical reading than they give it, because it is verifier-guided search wearing a product name. A rubric plus a grader agent plus retry-until-pass is rejection sampling at the agent level, and its properties are the well-understood properties of that family. Reliability is bounded by grader accuracy, not by agent capability. A grader with a false-pass rate produces confidently wrong completions that now carry an explicit success stamp, which is worse than no grader because it defeats downstream scepticism. A grader with a false-fail rate produces unbounded token spend on tasks that were already done. And the cost profile is the opposite of what enterprises budget for, since the hardest tasks retry the most, so spend correlates with difficulty in a way that is hard to forecast. None of that makes it a bad feature, and it is clearly the right direction. But the engineering question that determines whether it works is grader calibration and a retry budget, and neither is mentioned. Anyone adopting it should demand both.

Dreaming is the most interesting and the least evidenced claim in the talk. Consolidating transcripts plus current memory state into revised memory via a periodic batch process is a sensible amortisation: work out once, offline, what would otherwise be rediscovered in every session's context, and pay for it in a batch job rather than in per-session prefill. That is a real cost argument, and it is structurally the same trade as caching or as distilling inference-time reasoning into weights. The risk they do not name is that this is iterated self-modification without an external ground-truth signal. Memory edited by a model reading its own transcripts, feeding sessions that generate the next transcripts, is a closed loop, and closed loops without external correction amplify whatever error is already present. The mitigation is obvious and absent from the talk: keep memory versioned, evaluate each dreaming revision against a held-out task set before promoting it, and be able to roll back. Given that everything in their architecture is already a durable versioned resource, this should be straightforward for them to add, and I would want to see it before trusting the feature in production.

Finally, their closing thesis, that harnesses are now the limiting factor on what models can achieve, is true and also exactly what a company selling a managed harness would say. It is worth holding both. The context anxiety story genuinely does show a harness capping a better model. It equally shows that Anthropic's own harness was the thing capping it, which is an argument for keeping your harness thin and swappable rather than for outsourcing it to whoever ships the model. The strongest neutral version of their argument is the modularity one: build the harness from independent primitives so any single stale assumption can be removed in an afternoon.

## Grounded Context (Web Enrichment)
Everything substantive here is published and the written versions are more detailed than the talk. Anthropic has two engineering posts covering exactly this material, "Scaling Managed Agents: Decoupling the brain from the hands" and "Harness design for long-running application development," plus a product post on building with Claude Managed Agents. If you intend to act on any of this, read the harness design post rather than relying on the talk, because the context reset discussion there is more precise.

The context anxiety phenomenon is independently documented rather than being an internal anecdote, and the mechanism is more interesting than the talk conveys. Sonnet 4.5 was the first model aware of its own context window, and that awareness is what produced the pathology: approaching its limit it would proactively summarise and become more decisive, which sounds desirable and in practice meant taking shortcuts and leaving tasks incomplete while plenty of room remained. So the failure was caused by a capability, not by a deficiency, which is a better illustration of their point than they make. Cognition's writeup on rebuilding Devin for Sonnet 4.5 confirms it from the customer side, and the confirmation that Opus 4.5 largely removed the behaviour on its own, allowing context resets to be dropped entirely, appears in Anthropic's own harness post. One useful technical distinction from that literature which the talk omits: compaction preserves continuity but does not give a clean slate, so context anxiety can survive compaction, whereas a reset does provide a clean slate at the cost of needing a handoff artifact carrying enough state for the next agent to resume. That is the actual design tradeoff underneath their fix.

The security features are shipped rather than aspirational, with dates. Self-hosted sandboxes went to public beta and MCP tunnels to research preview, announced at Anthropic's first developer conference outside the US, in London, in May 2026. The architecture matters for anyone evaluating it: the agent loop handling orchestration, context management, and error recovery stays on Anthropic infrastructure while tool execution moves to infrastructure you control, and code execution, sensitive files, packages, services, and data stay inside your perimeter. Notably you do not have to run it yourself, since managed providers including Cloudflare, Daytona, Modal, and Vercel are supported. MCP tunnels work as described, with a session in Anthropic's cloud sandboxes reaching private MCP servers through the tunnel and self-hosted sessions able to use either tunnelled or public servers. The implementation detail worth knowing is that a poller injects session, work, and environment identifiers into a launch script that starts a fresh container per session, so isolation is per-session rather than per-environment.

On the context engineering claims, the independent literature is moving in a direction that partly cuts against the maximalist reading of long-horizon agents. Recent work on efficient context engineering for long-horizon tool-using agents argues for less context producing better agents, which is consistent with their durable-log-plus-slicing design but inconsistent with any assumption that accumulating more context over a long session is inherently good. Their architecture supports the right answer here, since a durable log with selective read-back is precisely the mechanism for keeping the active window small while losing nothing, but the talk frames context accumulation as a challenge to be managed rather than as something to actively minimise.

Two items have no external validation and should be treated as previews. Dreaming and outcomes are described as features they have been experimenting with, alongside scheduled deployments and multi-agent orchestration, and no evaluation results are given for either. There is no published measurement of whether dreaming improves task success, no reported grader accuracy for outcomes, and no retry-budget semantics. Treat the specific claims about self-improvement and reliability as hypotheses from the vendor.

## Real-World Application / Actionable Step
1. Audit your compression recipes for stale assumptions, and do it as a removal ablation rather than a review. For every mitigation in the pipeline (per-layer precision exceptions, smoothing or migration scales, outlier handling, calibration set choices), remove it and measure. Anything whose removal does not move accuracy on the current model generation is Anthropic's context reset: not neutral, but active cost in memory, bandwidth, or kernel uniformity. Most teams have never run this ablation because the mitigation became folklore.
2. Attach expiry dates to compression recipes and re-validate on every model release, treating the recipe as coupled to the model generation rather than to the technique. The failure mode they describe, a rigid harness taking weeks to migrate to a new model, has an exact analogue in a quantisation pipeline so entangled with one architecture's quirks that a new base model takes a month to support. Given current release cadence that is a real competitive cost.
3. Do the critical-path analysis on your own serving stack, looking specifically for anything serialised ahead of first token that could be parallel or skipped. Their 60% median and 90% tail improvement came entirely from moving provisioning off that path, with no model change. Check weight loading, sandbox or worker provisioning, cache warm-up, and tokeniser initialisation, and separate P50 from P95 because tail wins usually come from variance rather than mean.
4. Build the conditional provisioning classifier, because it is a clean routing problem with an observable label. Predict from the request whether tool execution will be needed, and provision accordingly, tuning the threshold to the asymmetry between wasted provisioning cost and mid-session stall cost. The label comes free from whether the session actually called a tool, so you can bootstrap from existing traffic.
5. Adopt the durable-log pattern for your experiment infrastructure so that context and state pruning becomes reversible. An append-only complete record of every step means you can aggressively trim what is in active use without the usual objection that you cannot recover what you dropped. This is the same conclusion three separate talks reached this week from different directions, and it is cheap to implement.
6. If you adopt outcomes or build anything like it, demand two things the talk does not provide: measured grader precision and recall on your own task distribution, and a hard retry budget. Reliability is bounded by grader accuracy rather than agent capability, false passes are worse than no grader because they launder failures as successes, and spend correlates with task difficulty in a way that resists forecasting.
7. If you build a dreaming-style memory consolidation loop, version the memory and gate every revision on a held-out task set before promotion. Iterated self-modification from a model's own transcripts is a closed loop with no external correction signal, which amplifies existing error. The mitigation is cheap and its absence from the talk is the thing that should make you cautious.
8. Use their production infrastructure checklist verbatim when reviewing any agent heading to production, regardless of which surface you build on. Hosting and process lifetime, session persistence and concurrency, file system access, execution isolation, credential handling with decryption only at tool runtime, and observability. It is the most complete short version of that list I have seen and it is vendor-neutral even though the talk is not.
