# The Model Swap Workshop: GPT-5.5 vs Kimi vs DeepSeek vs Mistral (Pamela Fox, Microsoft)

**Channel:** AI Engineer
**Published:** 2026-10-19
**Source:** https://www.youtube.com/watch?v=UGjk3Uk0MxM
**Domains:** ai-tech (primary)

## TL;DR
A hands-on workshop that swaps four models (GPT-5.5, Kimi K2.6, DeepSeek V4 Flash, Mistral Large 3) through the same scenarios: counting, RAG grounding, image input, tool calling, agent loops, string evals, LLM-as-judge, spec-driven eval generation (ASSERT), and DSPy/GEPA prompt optimization. The motivating thesis is portability: "the US government could cut off access to a model at any point," so every app needs a swap path. The finding that matters for routing work: on these tasks GPT-5.5 and Kimi are near-interchangeable, DeepSeek and Mistral fall off on specific capabilities (counting, grounding, vision, parallel tool calls), and GEPA can close much of the gap for the weakest model automatically.

## Key Takeaways
- **Counting E's:** GPT-5.5 and Kimi get 13. DeepSeek V4 Flash says 6, Mistral says 8. Chain-of-thought prompting ("break into words, count per word, sum") fixes Mistral. First lesson: small models need the scaffold that big models have absorbed.
- **RAG grounding (carpenter bees dataset, honey bee question):** GPT-5.5, Kimi, DeepSeek correctly say the sources lack honey bee info. Mistral answers from weights. Forcing per-claim citations gets Mistral to label the hallucinated parts "no source provided" but it still emits them. Fox's rule: weaker models go to their weights and pretend it was context. Evaluate willingness to say "I don't know" before picking a RAG model.
- **Image input:** GPT-5.5 and Kimi identify the aurochs, crocodiles (snout shape), and the 58-cent cheapest plant in a small-font table. Mistral misses the aurochs, calls them alligators, and picks a $2.30 plant. DeepSeek V4 Flash is text-only. Prompt engineering does not fix vision; the model either sees it or it does not. Switching to Spanish (caimanes vs cocodrilos) breaks the task even for strong models.
- **Tool calling:** all models call the right function. Argument fidelity varies (DeepSeek adds "you" as attendee and writes "Virtual (Microsoft Teams)" instead of "virtual"). The JSON schema is prompt engineering; ambiguity in descriptions shows up as argument drift.
- **Tool calling in a loop (calculator word problem):** GPT-5.5 batches everything into one expression, one call. DeepSeek takes four calls. Kimi sometimes gets the answer then re-verifies with four more calls. Efficiency, not correctness, is where models separate.
- **Agent loop (LangChain v1 travel planner):** GPT-5.5 parallelizes search_flights and search_hotels in turn one, then check_budget, then search_activities. Kimi does not parallelize and makes two extra calls. DeepSeek is serial but completes in four calls. Mistral searches flights and hotels, then stops; it forgets the last step as context fills.
- **Evals:** start with string checks on tool-call arguments (cheap, deterministic). Move to LLM-as-judge for fuzzy outputs; give the judge the full trace including tool definitions, not just input/output. Every eval case is two-plus LLM calls, so evals do not belong in CI on every commit. Pre-run app outputs so the judge can be iterated independently. Calibrate judges against human labels. Never run "coherence" or "fluency" evaluators.
- **ASSERT (Microsoft Research, released ~1 week before the talk):** write a YAML spec of the agent's intended behavior and user dimensions (e.g. budget pressure stratified as ample/tight/invisible); it generates behavior categories, test scenarios, and judging rubrics. On the travel planner, GPT-5.5 had far fewer violations than Kimi or DeepSeek, surprising Fox given Kimi's parity elsewhere.
- **DSPy + GEPA:** declare the program's constraints and checks; GEPA (a genetic/reflective optimizer) searches for the prompt that satisfies them. Six minutes on an acrostic-with-word-counts task produced a system prompt that works on Mistral. Dropbox and Shopify use this to move off large models.
- **Anthropic citations:** the Messages API's structured citations are trained in; cited spans come back programmatically. Different API, but worth it for RAG front ends.

## Architecture & Optimization Mechanics
- **Capability gaps are per-task, not per-model.** DeepSeek V4 Flash is strong at RAG grounding and useless for vision. Mistral Large 3 is weak at grounding and vision but fine for tool selection. A router that scores models on a single global quality axis will mis-route; the right router keys on task type (grounding, vision, multi-step tool use, parallel tool use) with a per-task capability table.
- **Parallel tool calling is a latency multiplier that only some models exploit.** GPT-5.5 issued independent calls in one turn; the others serialized. For agentic workloads, the number of model round-trips dominates latency more than tokens per call. "Can this model parallelize independent tools?" should be a routing feature.
- **Loop efficiency is a hidden cost term.** Kimi re-verifying with four extra calls after a correct answer is a 5x cost multiplier on an otherwise-correct model. Routers should track calls-per-task per model, not just correctness.
- **GEPA is model-specific prompt distillation.** It finds the scaffold the small model needs (the chain-of-thought Fox added by hand for the counting task). Combined with a frozen spec and checks, it gives you a repeatable path to swap down: run GEPA against the cheap model, compare on the eval set, route to it when it clears the bar.
- **ASSERT's stratification is a cheap way to build routing test sets.** Generating scenarios across user dimensions gives you a labeled distribution to measure per-model violation rates before production.

## Grounded Context (Web Enrichment)
ASSERT (Adaptive Spec-driven Scoring for Evaluation and Regression Testing) is a Microsoft open-source, MIT-licensed framework announced around Build 2026 and written up on Microsoft's Command Line blog in June. The pipeline is systematization, taxonomization, test-set generation, and inference scoring; outputs include a rationale, policy citation, and the turn or action behind each verdict. Microsoft's coverage study across five behaviors reports LLM judges reaching 80 to 90% agreement with human annotators versus about 90% human-to-human (that figure is from a secondary source). A recent GitHub PR renames it "Adaptive Eval" and labels the repo a customer preview, so expect churn. Fox's "last week" timing is off; the public release was months ago, though the DSPy-adjacent integration she showed may be newer. Third-party critiques: vague specs produce vague tests, synthetic cases miss production failure modes, and model judges are unreliable on subtle domain policy.

GEPA's self-reported production numbers: Shopify converted a single-prompt GPT-5 task to DSPy, moved to a small Qwen model, optimized with GEPA, and reports a solution roughly 75x cheaper and 2x more reliable. Dropbox reports moving to a smaller model and doubling program accuracy on Dash relevance judging. Databricks reports open models plus GEPA beating Claude Opus 4.1 at 90x lower cost. GEPA uses 100 to 500 evaluations versus thousands for GRPO. None of these are independently verified, but the direction is consistent across three separate teams.

Fox's models: Kimi K2.6, DeepSeek V4 Flash, and Mistral Large 3 are all current as of October 2026. DeepSeek has since shipped a V4.1 Flash 1017 update (see the WorldofAI pages from the same day), so the DeepSeek results here are already one checkpoint stale.

## Real-World Application / Actionable Step
- **Build a per-task capability table, not a per-model leaderboard.** For your routing work, define 6 to 8 task primitives (grounding refusal, vision table reading, parallel tool calls, loop efficiency, date math, non-English) and score each candidate model on each with a 20-case eval. Route on the table.
- **Add calls-per-task and parallel-call rate as routing features.** Log them from traces. A model that is correct but 4x the round-trips is the wrong choice for latency-sensitive paths.
- **Run GEPA before you give up on a small model.** Take your worst-performing cheap model on one task, freeze a spec plus checks, and let GEPA search for six minutes. If it clears the bar, you have a new routing target at a fraction of the cost. If it does not, you have evidence the gap is capability, not prompting.
- **Clone the workshop repo** (linked from the talk; Ollama support added the day before) and point the examples at your own local quantized models. It is a ready-made harness for comparing pruned or quantized variants against the frontier on identical scenarios.
