# Lessons from Studying Every Memory System — Shlok Khemani, Independent

**Channel:** AI Engineer
**Published:** 2026-08-12
**Source:** https://www.youtube.com/watch?v=5ZGyKWjQDr0

## TL;DR
Khemani spent a year reverse-engineering how ChatGPT, Claude, Gemini, and Poke actually implement memory, and this talk is the compressed version of that work, scoped explicitly to personalisation in consumer applications rather than to agent memory. The history is the valuable part because it shows two products starting from opposite premises and converging. ChatGPT went from a user-curated fact list in February 2024, which pushed memory management onto the user and never handled staleness, to a background-synthesised running profile in April 2025 that is now roughly 4,000 tokens across 16 sections, updated every few days, written as dense keyword clues rather than sentences. Claude launched in August 2025 with the opposite design and no profile at all, just two tools for searching prior conversations by keyword and by time period, so every conversation started cold. On the day Khemani published a post arguing the two architectures were opposites, Claude shipped V2 with a running profile, and the two have since converged on the same two-layer pattern: a running profile in context plus on-demand retrieval over history. Claude's profile is about 1,000 tokens, updates every 24 hours, uses complete sentences, and is visible and editable; ChatGPT's is four times larger, updates less often, and only became visible in June 2026 as a summary of a summary. His three lessons: there is no single way to do memory so serious teams do not outsource it, memory is a function of compute with an explicit trade between update frequency and profile length, and running profiles are already continual learning happening outside the weights. His closing rant is the strongest part: the ceiling on any memory system is how much context it can gather, and the failure is not that ChatGPT cannot read his email, it is that it does not notice a contradiction in its own profile and is not curious about resolving it. That is a product failure, not a model limitation.

## Key Takeaways
- Scope, stated up front because the word has become overloaded: this is memory as personalisation for consumer AI, not agent working memory, not RAG over documents.
- ChatGPT 2023, pre-memory: context held within a thread and nothing carried across threads. Early adopters did not mind because the model was good enough that they carried context by hand. The need appeared when non-technical users arrived for learning, cooking, and companionship.
- ChatGPT memory V1, February 2024: user-initiated fact extraction ("remember I am vegetarian"), stored as a visible deletable list, injected into every conversation. Two structural flaws. The burden of memory management fell on the user, who felt responsible for curating memories while trying to have a conversation. And facts true at creation time never expired, so a note that he was travelling to Bengaluru is still in his context today.
- ChatGPT memory V2, April 2025: user knowledge memories, which he calls a running profile. Every few days the system reads recent conversations, extracts what matters, and rewrites the profile. That update process is what the field now calls dreaming. The profile is injected into every new conversation.
- The format detail worth noticing: ChatGPT's profile entries are extremely dense, packing keywords as clues rather than prose, on the bet that a frontier model can reconstruct the full context from limited signal during conversation. His profile is 16 sections and roughly 4,000 tokens.
- Background updating solved the user-burden problem but not staleness, and his example shows why the failure mode is subtle rather than crude. He used ChatGPT to decide between Thailand and Turkey, so both appear as 2025 travel with overlapping dates. He went to Thailand and has never been to Turkey. The profile absorbed a deliberation as if it were a fact.
- ChatGPT did not expose the raw profile in settings, which is how he obtained his: a jailbreak prompt that works with enough persistence across thinking modes.
- Claude memory V1, August 2025, deliberately opposite: no profile, no fact list, two tools instead. Search prior conversations by keyword or topic, and search by time period so "what did we discuss last week" works. Every conversation starts fresh and retrieval happens only when the model decides it needs something.
- The timing anecdote: he published "Claude's memory architecture is the opposite of ChatGPT's" on 11 September, it hit the Hacker News front page, and Claude shipped V2 with a running profile the same day.
- Claude V2's four differences from ChatGPT, all pointing the same direction: the profile is user-visible in settings, it is about 1,000 tokens rather than 4,000, it is written as complete sentences rather than dense keywords, and it updates every 24 hours rather than every few days. Users can request edits, which trigger a resynthesis, and manage or delete prior edits. Unchanged since September 2025.
- ChatGPT's two 2026 updates completed the convergence: a tool to search past conversations, matching Claude's original design, and in June 2026 partial profile visibility as an LLM-generated summary of a profile that is itself an LLM-generated summary. V1's fact list was deprecated in the same release.
- The convergence, stated plainly: after three years of independent evolution, both products now have a running profile that is somewhat visible and editable, plus tools for retrieval over history.
- Lesson 1, no single way to do memory, and RAG was not the answer. Everyone including him assumed chunk, embed, store, semantically retrieve. Neither major product does that. Gemini has a running profile but attaches detailed timing logs per memory recording creation and last-update times. Coding agents use markdown files, heartbeats, knowledge bases, and skills, which is a different design space again.
- The consequence he draws forcefully: memory cannot be outsourced. Every top consumer AI product has memory and none of them buy it, because the memory system co-evolves with the product and cannot be an afterthought.
- Lesson 2, memory is a function of compute, with two distinct cost terms. Maintenance cost scales with update frequency times compute per update. Serving cost scales with profile length because the profile is in every conversation's context.
- The thought experiment that makes the trade visible: with unlimited compute you would update after every conversation, spend a strong model with sub-agents on each update, and store 400,000 tokens rather than 4,000. GPU constraints force a choice, and the two products chose opposite corners. ChatGPT takes high serving cost for low update cost; Claude takes the reverse.
- Lesson 3, continual learning is already here, just outside the weights. The profile conditions every conversation, conversations produce new information, synthesis folds it back into the profile, and the loop repeats. That is a learning loop by any reasonable definition.
- The open questions he does not answer and flags honestly: will this ever move into weights, will each person get a self-learning model, what data bootstraps the process, and who pays. He notes the economics work at enterprise scale because model costs amortise across employees and customers, and do not obviously work per individual. He recommends Gwern's "Guardian Angels" essay on what one model per person would mean.
- The rant, and it is the best material in the talk: however good your architecture and however much compute you pour in, the system is capped by how much context it can gather about you. He decided on Thailand in an in-person conversation with his partner, which no system could capture, but the evidence was in his email as flight and hotel bookings, and ChatGPT does not reason over email or update the profile from it even when connected.
- The precise complaint, which is sharper than the obvious one: he accepts that the system cannot know everything. What bothers him is that it does not notice the contradiction in its own profile and is not curious about filling gaps. Nothing at the model level prevents this. It is a product design failure.
- The fragmentation problem: his stack is chatbots, assistants, vertical applications, agents, and hardware devices, each building its own private memory of him, none shared. Context has to be rebuilt from scratch in each, and every life change means updating all of them individually. Meanwhile email, calendar, and photos sit there as rich context that nothing reasons over.
- His closing position: none of this feels like 2026, but the field is three years old, memory is foundational to how humans will interact with AI for the rest of history, and there is a great deal left to build.

## Architecture & Optimization Mechanics
The dense-keyword versus complete-sentence difference is the most interesting technical detail in the talk and Khemani states it without drawing out what it implies. ChatGPT's profile is a lossy compression of the user where the decompressor is the serving model, and it works because a frontier model can expand a keyword cluster back into usable context. Claude's is a less aggressive compression that carries its own semantics. That distinction has a consequence nobody in the memory discussion seems to have noticed: the viability of a compressed memory format is coupled to the capability of the model that reads it. A dense keyword profile decoded by a weaker model yields a worse reconstruction, and the degradation is silent because the output is fluent either way.

That should matter to you directly, because it is a failure mode that lives exactly at the intersection of routing and compression. If you route a query to a cheaper model to save cost, and the system prepends a densely compressed personalisation profile written on the assumption of a frontier decoder, you lose more than the usual capability delta. You lose part of the user context too, and no routing metric currently measures that. The same applies to quantisation: a 4-bit model reading a keyword-clue profile is doing worse inference over worse context. The prediction is testable and I have not seen it tested. Take a dense profile and a prose profile carrying the same information, run both through a frontier model and a quantised or smaller model, and measure personalisation quality on held-out queries. If the dense format degrades faster, then memory format is a routing constraint, and any cascade needs either a format matched to the weakest model in the pool or a per-route reformatting step. That is a genuinely novel research direction and it comes almost free from this talk.

His "memory is a function of compute" framing is correct and his cost model is incomplete in a way that changes the conclusion. He treats profile length as a pure serving cost paid on every conversation, which was true before prompt caching was ubiquitous. A running profile is the ideal cache target: it is a fixed prefix, identical across all of a user's conversations, and it changes only every few days. Under prompt caching the marginal cost of a longer profile is a fraction of the naive token price, which substantially weakens the argument for keeping profiles small. That reframes the two products' choices: ChatGPT's 4,000-token profile updated every few days is not just a different corner of the trade, it is the corner that caches well, because a long stable prefix amortises beautifully while a profile rewritten every 24 hours invalidates its cache daily. Claude's design pays cache-invalidation cost that his model does not account for. If you were optimising this properly, the objective is not length versus frequency but total cost including cache hit rate, and that objective favours long profiles updated rarely far more than his framing suggests.

The staleness problem is the deep one and it is a data-quality problem rather than an architecture problem. Both his examples share one root cause: the extractor cannot distinguish a proposition the user asserted from a proposition the user was considering. Deliberation about Turkey became a fact about Turkey. That is a modality error, and it is precisely the kind of error that compounds through a self-referential loop, because the profile conditions the next conversation, which produces traces consistent with the erroneous profile, which reinforces it on the next synthesis. This is model collapse in a personalisation loop, and it is worth naming as such because it means error rate does not stay constant over time. Gemini's design is the only one that partly addresses it, since per-memory creation and update timestamps at least let a reader reason about recency. The stronger fix, which nobody has shipped, is storing an epistemic status alongside each memory: asserted by user, inferred by model, or under consideration, with confidence. That is a small schema change with a large effect on the loop's stability.

The curiosity gap he identifies is the most actionable product insight and it has a clean technical statement. A memory system today is a write-and-read pipeline with no consistency checking. Adding one is cheap: run a periodic pass over the profile looking for internal contradictions, mutually exclusive facts, and gaps where an important field is absent, then either resolve from available connected sources or surface the conflict to the user. This is precisely the lint operation that [the Karpathy wiki pattern](2026-08-12-Warp-Holmes-LLM-Knowledge-Bases-Practical-Guide.md) treats as a first-class operation and that consumer memory systems have skipped, and it fits naturally into the dreaming pass since the compute is already being spent there. His point that this is a product failure rather than a technology failure is correct and worth taking seriously as a general lesson: the gap between what these systems could do and what they do is mostly unspent design attention, not missing capability.

On the outsourcing claim, he is right about the observation and overreaches on the inference. Every major consumer product builds memory in house, which is a fact. But the reason is not necessarily that memory is inherently unoutsourceable; it is that memory is the primary switching-cost moat in consumer AI, so nobody would rent it even if a good vendor existed. His own fragmentation complaint is the evidence: the reason no product shares memory with another is competitive, and he is describing the walled garden from the inside while attributing it to technical necessity. For your purposes the practical version is narrower and still true: if the memory format must co-evolve with the retrieval model and the serving model, then the interface between them is too tight to outsource cleanly, which is the same coupling the dense-format argument above establishes.

Lesson 3 is where this talk earns its place in the continual learning track and it sharpens the parametric-versus-non-parametric question that [Hooker raised the same day](2026-08-12-Adaption-Sara-Hooker-Gradient-Free-Continual-Learning.md). Running profiles demonstrate that a substantial amount of useful personalisation lives comfortably outside the weights, at a cost of a few thousand tokens of context, which sets a hard benchmark any weight-based approach has to beat. The economics he flags are the crux: a fine-tune amortises across many users at enterprise scale and across exactly one at consumer scale. So the interesting technical question is what personalisation genuinely requires weight updates rather than context, and the honest answer is probably style and latent preference rather than facts, since facts are what context handles well. That is an argument for very small per-user adapters over prose memory, which is a compression problem, and it is the version of this question worth your attention.

## Grounded Context (Web Enrichment)
His research is published and worth reading directly, because the blog posts contain detail the talk compresses out. The key pieces on his site are "Claude Memory: A Different Philosophy", "ChatGPT Memory and the Bitter Lesson", and "Anthropic's Opinionated Memory Bet". The post he references as hitting the Hacker News front page is confirmed, with the discussion thread still up, and Simon Willison published a comparison of the two implementations on 12 September 2025 that corroborates the architectural read. So the reverse-engineering holds up under independent scrutiny, which matters given that all of it is inferred from black-box probing rather than documentation.

One detail from the write-ups that the talk omits and that changes the cost picture: ChatGPT does not only inject the profile, it also inserts the last 20 to 40 conversations into the current context window. That is a much larger serving cost than the 4,000-token profile he discusses, and it means ChatGPT's position on his compute trade-off is considerably more expensive than the talk implies. It also explains why ChatGPT feels more contextually aware and why its context costs are higher. Anyone reasoning about the economics from the talk alone would get this wrong.

The Gwern essay is real and the reference is worth following, since it is the most developed treatment of the economics question Khemani raises and cannot answer. "Guardian Angels: LLM Personalization for Productivity and Security" argues for deeply personalised models acting as digital twins that emulate a user's values, style, and preferences rather than presenting an assistant persona. The economic argument is the interesting part and it is not about unemployment: it is that trust is the serial bottleneck in delegation, so a model that has genuinely learned your preferences makes delegation cheap in a way a generic assistant cannot, letting one person coordinate far more. His three constraints are that a guardian angel should amplify its principal rather than substitute for them on someone else's behalf, should be aligned with the principal and not designed to manipulate, and should help the principal develop their own ideals rather than flatten them. There is a substantial response literature already, which is a reasonable signal of how seriously the proposal is being taken.

Two things to note about how the talk ages. The claim that Claude's memory has not changed since September 2025 is a statement about the consumer product and is not true of the agent surface, where memory tooling has moved considerably, as the [managed agents work](2026-08-11-Anthropic-Evolution-Of-Agentic-Surfaces-Managed-Agents.md) shows. And his fragmentation complaint has a live commercial answer he does not mention, which is that the organisational version of this problem is exactly what the [record-everything company brain](2026-08-11-Circleback-Record-Everything-Company-Brain-Evals.md) products are selling, with the same unresolved question of who owns the durable record. The personal version has no equivalent, which is the actual gap he is pointing at.

## Real-World Application / Actionable Step
1. Run the memory-format-versus-model-capability experiment, because it is a novel result sitting in plain sight and it is directly in your lane. Construct two profiles carrying identical information, one as dense keyword clues in ChatGPT's style and one as complete sentences in Claude's. Serve both through a frontier model, a small model, and a 4-bit quantisation of the same model, then measure personalisation quality on held-out queries. If the dense format degrades disproportionately on weaker decoders, then memory format is a routing constraint and no current router accounts for it.
2. Add prompt-cache economics to any memory cost model you build or evaluate, because his framing omits it and the omission inverts the conclusion. A running profile is a stable prefix identical across a user's conversations, so its marginal serving cost under caching is a fraction of naive token price, while frequent updates invalidate the cache. Optimise total cost including hit rate rather than length against frequency, and expect the answer to favour long profiles updated rarely.
3. Treat context personalisation as a load-bearing part of routing evaluation. If your cascade sends cheap-route traffic to a smaller or quantised model while prepending the same context that was tuned for a frontier model, you are measuring only half the degradation. Add a personalisation-fidelity metric to your routing evals: does the cheap route use the profile as well as the expensive route does.
4. Store epistemic status with every memory in anything you build, not just a timestamp. His Turkey error is a modality confusion between a proposition considered and a proposition asserted, and it compounds because the profile conditions the conversations that feed the next synthesis. Tag each entry as user-asserted, model-inferred, or under-consideration, with a confidence value, and weight synthesis accordingly. Gemini's timestamps are the weak version of this.
5. Add a consistency-check pass to any memory system you touch, including this wiki. Scan for mutually exclusive entries, contradictions, and absent important fields, then resolve or surface. The compute is already being spent during the dreaming pass and the marginal cost is small. This is the lint operation from the wiki pattern applied to personalisation, and its absence is his central complaint.
6. Use the running-profile benchmark as the bar for any weight-based personalisation work. A few thousand tokens of context delivers most of the practical personalisation value today, so a per-user fine-tune has to beat that to be worth anything. The likely answer is that facts belong in context and style and latent preference belong in weights, which points at very small per-user adapters, which is a compression problem you are well placed to work on.
7. Read Khemani's posts rather than relying on the talk, and specifically note the last-20-to-40-conversations injection that the talk leaves out. It materially changes ChatGPT's position on the compute trade-off and it is the kind of detail that invalidates cost analyses built from the talk alone.
8. Read Gwern's "Guardian Angels" for the economics, since it is the serious treatment of the question Khemani raises and abandons. The trust-as-serial-bottleneck argument is the strongest available case for why per-person personalisation is worth real compute, and it is the framing to use if you ever need to justify per-user adaptation work commercially.
