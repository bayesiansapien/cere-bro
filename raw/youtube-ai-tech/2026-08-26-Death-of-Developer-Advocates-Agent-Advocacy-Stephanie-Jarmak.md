# The Death of Developer Advocates (Stephanie Jarmak, Sourcegraph)

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=Lrw0jqBNaw0

## TL;DR
An astronomer-turned-research-scientist argues that developer relations is not dying but acquiring a second user: the agent, which reads your docs, calls your API, hits your errors, and recommends your product. Jarmak's contribution is that she measured both sides. She built CodeScaleBench, hundreds of software-development-lifecycle tasks run with and without Sourcegraph's code-navigation MCP tool, generating thousands of traces that show exactly where tool descriptions mislead the model. Then she ran a generative-engine-optimization study and found Sourcegraph recommended 65% of the time for explicit comparison-shopping prompts and zero percent for pain-based prompts describing the exact problem their product solves. The frame is the curb cut: build for the agent and the human path clears too.

## Key Takeaways
- **Tool descriptions are an eval surface.** In one trace the model tried a `read_line` parameter because its training-data priors expected it, when the actual parameter was `start_line`. Nothing in the description corrected the prior. The error message was good enough that the agent self-recovered, but it burned an entire turn doing so. That is a measurable, fixable tax hiding in a docstring.
- **Buyers will evaluate tools on token cost and latency, not just correctness.** Jarmak states this plainly as the new procurement criterion for agent-facing tooling. How many tokens does the agent spend to accomplish the task with your tool.
- **The GEO gap between shopping intent and pain intent is the sharpest finding.** Prompted as a buyer comparing code-intelligence tools: 65% mention rate. Prompted as an engineer with the underlying pain ("we keep breaking downstream services when we change shared libraries because we cannot see all the consumers"): zero mentions, and the model suggested writing a wiki page instead. The messaging never connected the pain to the product.
- **Newer models can be worse for you, not better.** Re-running the study on Claude Sonnet 4.6 thinking, expecting improvement over Sonnet 4, produced *more* recommendations of Cody, a deprecated Sourcegraph product. Old model outputs about your product compound into the corpus that trains and grounds the next generation. You now have to actively bury your own stale signal.
- **Non-engineers are a new ICP for developer tools.** Jarmak had zero GitHub commits last year and roughly 12,000 this year, and now maintains an open source multi-agent orchestration framework. Agents made dev tools usable by people who could not previously use them.
- **Reduce friction to installation or agents will not recommend you.** If adoption requires demos and emailing a sales rep, the agent will not surface it, because it cannot carry the user through that path. Be in the marketplaces and MCP registries.
- **Agents are biased toward machine-generated prose.** Jarmak's aside is worth noting: models favor their own style, so agent-facing content can be as structured and formulaic as you like, while human-facing content using the same voice destroys credibility. Two audiences, two registers.
- **Three flavors of the new role.** Engineering (MCP interfaces, evals, instrumentation), product (owning the end-to-end agent experience and agent-experience rubrics), marketing (pipeline generation via agent recommendation). Pick the mix by available skills.

## Architecture & Optimization Mechanics
- **A/B benchmarking a tool by ablation.** Running identical task suites with and without your MCP tool is the correct experimental design and it is rarely done. It yields a per-task delta in success rate, turn count, and token spend, which is exactly the causal claim a tool vendor needs and exactly the metric a buyer should demand.
- **Prior-conflict as a distinct error class.** The `read_line` versus `start_line` failure is not a hallucination in the usual sense, it is a mismatch between the model's parameter-naming prior and your API. The cheap fix is naming your interface the way the training distribution expects, and where you cannot, stating the correction explicitly in the description. This is interface design conditioned on a pretraining distribution, which is a genuinely new engineering discipline.
- **Errors as a recovery channel.** The agent recovered because the error message explained the failure. Error strings are now part of the control loop, so verbose, actionable errors have direct value in turns saved.
- **Turn count as the real cost unit.** One wasted turn means a full context replay plus new completion. Optimizing tool ergonomics to eliminate wasted turns compounds across every invocation, which is a larger lever than shaving tokens off individual calls.

## Grounded Context (Web Enrichment)
The GEO discipline Jarmak is doing empirically has since been codified into a fairly standard playbook: optimize for citation by ChatGPT, Perplexity, Google AI Overviews, Gemini, and Claude, favor structured machine-readable content such as pricing tables, feature comparisons, and step-by-step instructions, and measure mention rate as the outcome metric. Her point about being where the agents are is backed by the registry growth: third-party trackers counted roughly 10,000 MCP servers by April 2026, up from about 6,800 at the end of 2025. Discovery surface is real and growing fast, and absence from it is now a distribution failure.

Two honest caveats on her data. First, the GEO pilot is a single-product, single-vendor study with hand-authored prompts, so the 65% versus zero contrast is best read as an existence proof that intent framing dominates mention rate, not as a calibrated measurement. Second, and more interesting, her Sonnet 4.6 result cuts against the prevailing GEO assumption that publishing better content fixes stale recommendations. If deprecated product names are being reinforced by the accumulated output of earlier models, that is model-collapse dynamics operating on brand entities, and content freshness alone will not resolve it. The mechanism that actually helps is grounding: getting the agent to use web-search tools and provenance-bearing sources at inference time rather than relying on parametric memory, which is precisely the argument for `llms.txt`-style authoritative surfaces despite their weak crawler adoption.

## Real-World Application / Actionable Step
- **Ablate your own tools.** Take any internal MCP server or tool wrapper Amit's team owns, build a small task suite, and run it with and without the tool. Report success rate, mean turns, and mean tokens. This is a half-day of work that produces the only defensible claim about whether the tool helps, and it doubles as a regression suite for tool-description changes.
- **Audit tool schemas against pretraining priors.** Grep parameter names in internal tool definitions for anything that deviates from the obvious convention (`start_line` versus `read_line`, `limit` versus `max_results`). Every deviation costs turns. Either rename to match the common convention or state the deviation in the description. This is the cheapest agent-reliability win available and needs no model work.
- **Treat wasted turns as a first-class metric in routing evals.** Amit's routing work optimizes cost per query, but a cheaper model that burns two extra tool-calling turns is not cheaper. Instrument turns-to-completion, not just tokens per call, or the router will systematically pick models that look cheap and are not.
- **Point a coding agent at your own docs and read the transcript.** Jarmak's immediate recommendation, and it applies to internal libraries too. The transcript is an agent-experience bug report you get for free.
