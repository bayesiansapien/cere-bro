# The Model Swap Workshop: GPT-5.5 vs Kimi vs DeepSeek vs Mistral (Pamela Fox, Microsoft)

**Channel:** AI Engineer
**Published:** 2026-10-19
**Source:** https://www.youtube.com/watch?v=UGjk3Uk0MxM
**Domains:** ai-tech

## TL;DR
Fox walks through a model-swap repo on Microsoft Foundry that pins the same scenarios (counting, RAG grounding, image input, single tool call, tool loop, LangChain agent, string evals, LLM-as-judge, spec-driven evals with ASSERT, and DSPy prompt optimization) against GPT-5.5, Kimi K2.6, DeepSeek V4 Flash, and Mistral Large 3. The thesis: benchmarks do not tell you how a model performs on your scenario, every app should be able to re-point at another model (she cites government access cut-off as a real risk), and the gaps between models show up less in final-answer accuracy than in grounding discipline, tool-call efficiency, parallelism, and instruction persistence across a long context. DSPy plus GEPA is her answer to the "re-prompt every time you swap" tax.

## Key Takeaways
- Letter-counting probe: GPT-5.5 and Kimi K2.6 got 13 E's correct. DeepSeek V4 Flash said 6, Mistral Large 3 said 8. A chain-of-thought prompt fixed Mistral. Weak models need explicit decomposition; strong ones do not.
- RAG grounding is where models diverge most. Asked about honey bees with only carpenter-bee sources, GPT-5.5, Kimi, and DeepSeek admitted the gap. Mistral answered from weights. Even after a "label every claim with a source" prompt, Mistral tagged the honey-bee content as "no source provided" and still included it. Admitting ignorance is a model property you must evaluate, not a prompt fix.
- Image input: GPT-5.5 and Kimi identified an aurochs, distinguished crocodiles from alligators by snout, and found the cheapest plant in a tiny-font table. Mistral missed all three. DeepSeek V4 Flash is text-only. Vision ability cannot be prompt-engineered; it is there or not. Switching the crocodile question to Spanish broke the frontier model too, because "caimán" collides across English and Spanish usage.
- Single tool call: all models chose the right tool, but argument adherence varied. DeepSeek added "you" as attendee and wrote "Virtual (Microsoft Teams)" for location. Fix is tightening JSON schema descriptions, which Fox correctly calls prompt engineering in disguise.
- Tool loop efficiency: with "do not do math in your head," GPT-5.5 batched the whole word problem into one calculator call. DeepSeek took four sequential calls. Kimi occasionally loops re-verifying a correct answer. Each extra call is a network round trip.
- LangChain travel agent: GPT-5.5 issued search_flights and search_hotels in parallel on turn one, then check_budget, then search_activities. Kimi serialized them and made two extra calls. DeepSeek serialized but stayed at four calls. Mistral searched flights and hotels and then stopped, forgetting the remaining instructions. Parallel tool calling was a GPT-5.5-only behavior in this run.
- Eval ladder: string checks for deterministic tool args, LLM-as-judge (pass/fail plus reason, given query, response, context, tool definitions, and traces) for fuzzy outputs, and judge calibration against domain-expert labels. Pre-generate responses so the judge can be iterated independently of the app. Never run built-in coherence or fluency evaluators.
- Eval cost reality: each judged case is at least two LLM calls, often five or more with multiple evaluators. RAG evals want 200 to 800 cases. These do not belong in per-commit CI.
- ASSERT (Microsoft Research): write a YAML spec of the agent, its dimensions (budget pressure: ample, tight, invisible), and stratification. It generates behavior categories, scenario test sets, and judging rubrics. On the travel planner, GPT-5.5 had the fewest violations, clearly ahead of Kimi and DeepSeek.
- DSPy with GEPA: declare constraints in code, let the optimizer evolve the prompt against checks using a student model and a reflection model. A 6-minute run produced a Mistral-specific system prompt that passed a constrained-generation task. Dropbox and Shopify use this to move workloads to smaller models.
- Anthropic models use the Messages API with native structured citations, which return cited text blocks programmatically. Fox prefers this for RAG front ends. Ollama works with the same examples by changing the base URL and model names.

## Architecture & Optimization Mechanics
- **Routing signal taxonomy.** The workshop is effectively a manual router eval. The discriminating axes were grounding discipline, multimodality, parallel tool calling, argument adherence, and long-context instruction persistence. Final-answer accuracy was the least discriminating axis. A router that only scores accuracy will mis-route agentic tasks.
- **Tool-call count as a latency and cost metric.** Four sequential calculator calls versus one batched expression is a 4x round-trip difference at identical accuracy. Parallel tool emission is a first-class model capability worth testing before assigning a model to an agent loop.
- **Prompt optimization as the model-swap compiler.** GEPA (genetic-Pareto reflective prompt evolution) with a strong reflection model and a cheap student model is a practical distillation substitute when you cannot fine-tune. The prompt becomes a compiled artifact per target model, which is exactly the abstraction a routing layer needs.
- **Judge pipeline cost.** Five evaluators times 800 cases times two calls each is 8,000 LLM calls per eval run. Caching generated responses and running judges separately amortizes this. Judges are a natural place to use a cheaper model once calibrated.
- **Citations as structured output.** Anthropic's native citation blocks remove a post-processing step and reduce hallucinated references in RAG, a capability gap other APIs still fill with prompt engineering.

## Grounded Context (Web Enrichment)
Fox describes ASSERT as "out last week," but Microsoft announced it around Build 2026 in early June (Adaptive Spec-driven Scoring for Evaluation and Regression Testing). It is MIT-licensed, runs a four-stage pipeline (systematization, taxonomization, test-set generation, inference scoring), integrates with LangChain, CrewAI, AutoGen, OpenAI Agents SDK, DSPy, LlamaIndex, and Semantic Kernel via LiteLLM, and Microsoft reports 80 to 90 percent judge-to-human agreement in internal validation. The talk may have been recorded closer to June; either way, the tool is more mature than "brand new." Independent reviewers note the judge is weakest on subtle domain-policy distinctions, which supports Fox's advice to calibrate against expert labels.

The DSPy claims check out with caveats. Dropbox's Dash relevance judge post reports a 45 percent drop in normalized MSE adapting to gpt-oss-120b, 1 to 2 days of adaptation instead of 1 to 2 weeks, and a 97 percent reduction in malformed JSON from smaller models. The Shopify story (GPT-5 single prompt converted to DSPy, moved to a small Qwen model, GEPA-optimized, about 75x cheaper and 2x more reliable) exists only in the DSPy docs, not in a Shopify-authored source. Databricks reports open models plus GEPA beating Claude Opus 4.1 at 90x lower cost. On the model matchup, aggregators show Kimi K2.6 well ahead of DeepSeek V4 Flash on agentic benchmarks (95.9 percent on tau2-Bench, a large Terminal-Bench 2.0 gap) with both near 91 percent on GPQA Diamond, while DeepSeek V4 Flash is roughly 85 percent cheaper on input tokens. That matches Fox's observations: Kimi is near GPT-5.5 on most tasks, DeepSeek is accurate but less efficient. No public benchmark measures parallel tool-call emission, so Fox's demo is one of the few direct observations of that gap.

## Real-World Application / Actionable Step
- **Add four non-accuracy axes to any router eval:** grounding refusal rate on out-of-context questions, parallel tool-call emission rate, tool calls per task at matched accuracy, and instruction persistence at the end of a long trajectory. Fox's demo shows these separate models that tie on accuracy.
- **Treat GEPA-optimized prompts as per-model compiled artifacts.** For any route that targets a cheap model, run GEPA with a frontier reflection model against your constraint checks and store the resulting prompt alongside the route. This is the cheapest form of distillation when fine-tuning is off the table.
- **Use ASSERT to bootstrap custom evaluators** for agent routes before production traffic exists. Generate the scenario set from a spec, then calibrate the judge with a small set of human labels before trusting it to gate model swaps.
- **Measure vision and language before assigning a route.** Neither can be prompt-fixed. Test the cheap candidate on your actual image types and the actual languages your users write in.
