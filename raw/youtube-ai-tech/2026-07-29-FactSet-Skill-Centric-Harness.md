# Skills are new features: Building a Skill-Centric Harness

**Channel:** AI Engineer
**Published:** 2026-07-29
**Source:** https://www.youtube.com/watch?v=7jjudsEhBtM
**Speaker:** Yogendra Miraje (Yogi), Principal AI Engineer, FactSet

## TL;DR
Last year Miraje presented "blueprints" at the same conference, recipes handed to agents so they would not rediscover their path each time. He now says blueprints were a naive skill, and once Anthropic open-sourced Agent Skills in October 2025 there was no point maintaining a private standard, so FactSet adopted skills wholesale. The talk's framing device: prompts define **who** the agent is, tools define **what** it can connect to, and skills define **how** a task gets done, which makes skills the natural home for business logic. Therefore **skills are the new features**, and since anyone who understands the product can write one, the engineer's role shifts from shipping features to shipping harnesses. The three concrete contributions are a minimal skill-support implementation (registry, system prompt, file read tool), a set of hard-won lessons about descriptions as routing signals and skills as model-versioned contracts, and a five-part governance model for scaling past a hundred skills.

## Key Takeaways
- **The who/what/how decomposition is the most portable idea in the talk.** Prompts are identity, tools are connectivity, skills are procedure. If the agent is the product surface, features have to live somewhere, and skills is where. His example: equity research and wealth management used to be buttons, dropdowns, and screens in a financial data product. They are now skills.
- **The organizational consequence is the real argument.** Because a skill is markdown plus optional scripts, anyone with good product understanding can ship one. Features become writable by non-engineers, so the engineering job becomes building the vehicle rather than the cargo.
- **Minimum viable skill support is three components.** A skill registry (name, description, path per skill), a system prompt, and a basic file read tool. Add bash or a code sandbox only if skills execute scripts. That is genuinely the whole thing.
- **Progressive disclosure, implemented concretely.** Concatenate only name, description, and path into the system prompt. Never the skill body. The agent reads the body only for the skills it selects. His demo registry has three skills: company research (web search, produce markdown), report HTML (markdown to HTML), report PDF (markdown to PDF).
- **Descriptions are routing signals, and this is the sharpest practical lesson.** In his demo only the HTML skill fires, because the PDF skill's description says to use it only when the user asks for a PDF report. The word "PDF" is the trigger. Therefore: write descriptions aligned to the **user's request phrasing**, not to what the skill does internally. Keep descriptions distinct enough that the agent does not get confused. Do not let skills go stale. These are the three reasons skills silently fail to trigger.
- **In agentic products, skills are model-driven, not user-invoked.** Unlike coding agents where a developer types a slash command, non-technical users cannot be asked to carry the cognitive load of remembering a skill catalogue. That removes the human fallback for routing errors, which is why descriptions carry so much weight.
- **Cut skills by user intent, not by data model.** He built the library wrong the first time, one skill per data domain (estimates analysis, fundamentals), then real usage arrived and did not match the data model. Refactored version: not "estimates analysis" but **earnings preparation**. Not separate news-analysis and analyst-rating skills but **pre-market briefing**. He is explicit that multiple refactors are fine and expected.
- **The model-upgrade failure is the most alarming and most useful anecdote.** They upgraded to a new model and the agent stopped obeying skills. Not a line of any skill had changed. Root cause: the new model attended heavily to the **beginning** of the skill, and their critical instructions were at the **end**. Hence: run evals, and skills without evals are wishful thinking.
- **The reframing that follows from it: skills are not documentation, they are contracts versioned to a model.** People treat them as docs. Every model upgrade requires re-running skill evals.
- **Routing mechanism changes qualitatively with scale, it does not just get tuned.** Under roughly 10 skills, shoving them all into the system prompt works. Past 10, shortlist before injecting, via embeddings and similarity search or a small model that picks candidates. At hundreds, you need a skill hierarchy, metadata filters, and governance to keep the library searchable and coherent.
- **Five-part governance, each answering one question.** *Admission*: should this skill exist or should it fold into an existing one, implemented as automated registry gates with human in the loop, analogous to PR review. *Ownership*: named maintainers per skill, analogous to CODEOWNERS, maintained by the application teams that own the corresponding features. *Boundaries*: allow-list the tools a skill may use, with access-controlled tools. *Lifecycle*: semantic versioning, deprecation warnings, changelogs. *Coherence*: periodic audits and skill validation checks so a large library still makes sense.
- **His anti-bureaucracy caveat is worth keeping.** Governance need not be red tape. It depends on how much is automated with proper human-in-the-loop, and most of the practices are borrowed from code practices that have worked for decades.

## Architecture & Optimization Mechanics
Two mechanics here matter beyond agentic product engineering.

**First, skill routing at scale is a retrieval-and-routing problem with a hard context budget, and his scale thresholds are a useful prior.** Under 10, inject everything. Past 10, shortlist with embeddings or a small classifier model. At hundreds, hierarchy plus metadata filters. That middle tier is exactly the cheap-model-gates-expensive-model pattern from LLM routing, applied to context assembly instead of to model selection. The small shortlisting model is a router, its output space is skills rather than models, and it has the same failure mode: a bad routing decision is unrecoverable downstream because the expensive model never sees the right context. The design lesson transfers directly: **routing quality is bounded by the discriminability of the descriptions you route on**, which is the general form of his "descriptions are routing signals" lesson. In model routing the analogue is that a query classifier is bounded by how separable the query classes actually are, and no amount of classifier capacity fixes overlapping class definitions.

**Second, the model-upgrade failure is a positional-attention artefact with direct implications for compression work.** A new model attended to the start of a long instruction block and dropped instructions at the end. That is a change in effective attention distribution over long context, and it is precisely the property that quantization and pruning perturb. Aggressive KV-cache quantization, attention-head pruning, and long-context sparse attention schemes all risk shifting where in the context a model actually attends. FactSet's incident was caused by a model *upgrade*. The identical symptom would be produced by a compression change, and it would be invisible to perplexity or to any short-context benchmark. **Instruction-position sensitivity is an underused compression eval.** A concrete test: take a long instruction block, place a critical constraint at the beginning in one variant and at the end in another, and measure compliance for each candidate compression configuration. A configuration that degrades late-context instruction compliance while preserving perplexity is a configuration that will fail in agentic deployment.

The third and more strategic point is the coupling to the AlphaLab talk from the same conference. AlphaLab argues the harness is disposable and the environment is the asset. Miraje argues engineers should stop shipping features and start shipping harnesses. These are less contradictory than they appear: Miraje's harness is the vehicle (registry, progressive disclosure, governance) and his skills are the business logic that constitutes the durable asset, which is structurally the same claim. What both agree on emphatically is that the evals are not optional, and Miraje supplies the sharpest reason: the artefact is versioned against a model, so the contract silently breaks on upgrade.

## Grounded Context (Web Enrichment)
The talk's account of the skills ecosystem is accurate and the public record fills in specifics he moves past quickly.

**The timeline and standardization are right.** Anthropic formalized Agent Skills in October 2025 across Claude's product surface, then released it as an **open standard in December 2025**. That December release is what makes his "no point maintaining our own standard" decision correct rather than merely convenient. A skill is a self-contained package: a SKILL.md instruction file plus optional scripts, reference documents, and assets in a directory the agent discovers and loads when relevant.

**Progressive disclosure is a documented three-level mechanism, and he described two of the three.** Level 1, metadata: name and description load into the system prompt at startup, which the agent uses to decide whether to invoke. Level 2, instructions: the SKILL.md body loads only when the agent matches the task to the description. Level 3, which he omits: **bundled resources load on demand**, which is the level that makes reference files and scripts affordable. The published cost figure is the persuasive one: a team with 50 installed skills pays roughly 5,000 tokens of standing context rather than 50 times each skill's full body.

**There is a hard API constraint he does not mention, and it is the strongest possible argument for his "cut by user intent" lesson.** Anthropic enforces a **maximum of 8 skills per request** at the API layer, a design constraint that forces consolidation into role-based bundles. This reframes his refactoring story entirely. Merging "estimates analysis" and "fundamentals" into "earnings preparation" is not just better intent-matching, it is compliance with a platform limit. Anyone building a skill library needs to know the ceiling is 8 per request before designing the taxonomy, not after.

**His governance model is not idiosyncratic, it is converging with the published enterprise specification.** Anthropic's enterprise specification reportedly spends more lines on review, evaluation, and lifecycle than on what skills do, and commentary frames it as the governance envelope rather than the artefact being what makes a skill enterprise-ready. Anthropic added organization-wide skill management and audit trails for Team and Enterprise plans in February 2026, which supplies platform support for two of his five pillars (ownership and lifecycle). His five-part model can therefore be treated as a mature reading rather than one company's opinion.

**On the security dimension he touches only lightly.** His boundaries pillar (allow-list tools, access-controlled tools) is the right instinct, and there is now academic treatment of skill architecture, acquisition, and security specifically, which suggests skill libraries are being analyzed as an attack surface. An allow-list per skill is the minimum, not the endpoint.

## Real-World Application / Actionable Step
1. **Add an instruction-position sensitivity test to the compression eval suite.** This is the highest-value transfer and it comes from his failure story rather than his framework. Construct a long instruction block, place a critical constraint at the start in one variant and at the end in another, and measure compliance for each quantization or pruning configuration. FactSet's break was caused by a model upgrade shifting positional attention. A KV-cache quantization or sparse-attention change produces the identical symptom, and neither perplexity nor short-context benchmarks will catch it.
2. **Treat any skill library or long system prompt as versioned against the model, and gate model swaps on re-running its evals.** If routing work involves swapping in a cheaper model behind an unchanged prompt or skill set, that is exactly the FactSet failure configuration. The cheap model may attend differently to the same instruction block. A routing policy validated only on output quality metrics, without instruction-compliance checks, will silently route to a model that ignores half its instructions.
3. **Design the skill taxonomy against the 8-skills-per-request API ceiling from the start.** This constraint is not in the talk and it determines the taxonomy. Cut by user intent (earnings preparation, pre-market briefing) rather than by data model, and target role-based bundles that fit inside 8.
4. **Write descriptions in the user's phrasing, and test discriminability explicitly.** His PDF-versus-HTML example shows the trigger word doing all the routing work. The general practice: for each pair of skills, check whether a realistic user request could plausibly match both descriptions. If yes, the routing will be unreliable, and no model improvement fixes overlapping definitions.
5. **Adopt the three scale thresholds as the routing-architecture prior.** Under 10 skills inject all metadata. Past 10 add a shortlisting step. At hundreds add hierarchy and metadata filters. The middle tier is a router, so build it as one: measure its recall against known-correct skill selections rather than assuming a similarity search is adequate.
6. **Borrow the five governance pillars but automate admission first.** Of the five, admission (should this skill exist or fold into an existing one) is the one that prevents library rot, and it is the one that maps cleanly onto an existing PR review process. Ownership and lifecycle now have platform support via Anthropic's org-wide skill management and audit trails as of February 2026, so those cost less to implement than they did when this library was built.
