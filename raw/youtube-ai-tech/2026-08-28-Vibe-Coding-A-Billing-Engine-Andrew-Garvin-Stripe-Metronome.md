# How to Avoid Disaster When Vibe-Coding a Billing Engine (Andrew Garvin, Stripe)

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=mJqwmmOx4WA

## TL;DR
Garvin, a Metronome co-founder now inside Stripe following the largest acquisition Stripe has ever made, demos Stripe Projects provisioning a Stripe account plus backend services plus a Metronome billing agent from the CLI, then coaches an agent in one natural-language sentence to replicate Lovable's prepaid-credit auto-recharge pricing model in a sandbox. The engineering content is the guardrail design: portable extensible skills files that encode Metronome's foot-guns, deliberately verbose error messages so the agent self-corrects, and a hard product decision that the agent gets you to a tested sandbox and never to production. The most useful conceptual contribution is a taxonomy of three agent roles that each demand different infrastructure: agent as your product, agent as buyer, agent as user. The last one is why HubSpot is dismantling seat-based pricing.

## Key Takeaways
- **Three agent roles, each with different implications.** *Agent as your product*: if the agent is what you sell and it runs up a token bill, you need metering. *Agent as buyer*: agents procure your service, so it must be discoverable and provisionable programmatically, which is what Stripe Projects addresses. *Agent as user*: one agent can operate an entire platform, so value concentrates in a single seat and per-seat pricing collapses.
- **The HubSpot example is the sharpest business consequence in the talk.** HubSpot is transitioning from seat-based to credit-based pricing, starting in EMEA, dramatically lowering seat prices and layering credits on top. The stated reason is a world where an agent can operate the entire system, which makes paying for seat-level access to do work incoherent. Garvin calls this headlessness and says Metronome is seeing it in production, not theorising it.
- **Skills files as vendor-supplied guardrails, and they are portable.** Metronome is a deep, complicated product with many ways to hurt yourself. Rather than expecting agents to figure it out, they built an extensible skills library that supplies context to any agent implementing against the Metronome API, installable on your own side. This is the vendor-side counterpart to Christopher Burns's `node_modules` docs argument from the same conference.
- **Verbose error messages as an agent-facing design principle.** When the demo hit an error, Garvin's framing was that their developer experience team is actively hunting failure cases to make errors more explicit precisely so the agent can self-correct. Third talk in this batch to independently converge on error-message quality as an agent-reliability lever.
- **The human-in-the-loop boundary is drawn deliberately and stated clearly.** They are explicitly *not* building toward customers operating the whole billing system without a human. Billing is business-critical with deep domain logic. The agent's job is to accelerate you into a working test environment. Nothing gets pushed to production.
- **The sandbox has to include synthetic usage to be meaningful.** Provisioning a customer and a contract proves nothing about a usage-billing configuration. The skills files direct the agent to flow usage into the platform so you can see what a live customer's invoice actually looks like. That is a real insight about what "testable" means for a metering system.
- **Agent spend runaway is now a first-class product concern.** Garvin says failure impact has grown in importance over the preceding six months specifically because agents can run away with spend, and that they are building controls their customers can pass to theirs, including per-agent wallets that only that agent can draw from. This is the same problem several other talks in this batch tackle.
- **Enterprise pricing is converging on cloud-vendor patterns.** Coding agent companies (Cognition, Cursor, OpenAI, Anthropic) are adopting the commit structures CSPs have used for a decade: prepaid commitments, postpaid commitments, customer-specific offers. The prepaid-credit auto-recharge model that now dominates originated with OpenAI's implementation on Metronome.
- **Observed leading indicators from inside Stripe.** Exponential growth in Stripe CLI usage over the prior five to six months, exponential growth in new business formation, and exponential growth in customers operating Stripe and Metronome through coding agents. He also notes that at a recent demo day, all five demoing companies were sales-led agents built to operate platforms like SAP or invoicing systems.
- **The demo failed twice live**, once on initialisation and once on login. Worth stating plainly: the polished narrative and the live reliability were not the same thing, and Garvin handled it without pretending otherwise.

## Architecture & Optimization Mechanics
- **Metering is the substrate that makes inference cost optimization commercially legible, and this is the direct link to Amit's work.** Metronome has metered OpenAI and Anthropic API calls since before those companies had revenue, at global scale. Every argument about cost per token only translates into margin if the metering layer can attribute usage accurately to customer, product, and credit type. A routing layer that halves inference cost is worth nothing to the business until the billing system can express it.
- **Per-agent wallets are a capability-scoping mechanism expressed in dollars.** Same architectural pattern as the tool-permission scoping Cloudflare, Exa, and Ramp each arrived at, but the resource being bounded is spend rather than tool access. It is also the more robust control, because it fails safe regardless of what the agent does: an agent with a $50 wallet cannot cause a $50,000 incident no matter how badly the prompt injection goes.
- **The sandbox-with-synthetic-usage pattern generalises to model deployment.** A billing config that provisions correctly but has never seen usage is untested. The equivalent trap in inference work is a quantized model that loads and produces plausible output but has never been run against realistic traffic distribution, batch sizes, and sequence-length mix. Provisioning is not validation, and synthetic load that resembles production is the minimum bar.
- **Skills files shipped by the vendor shift the reliability burden to whoever has the knowledge.** Metronome knows its own foot-guns. Encoding them once and distributing them is strictly better than each customer's agent rediscovering them through failures. This is the correct division of labour and it will likely become standard for any API with non-obvious semantics.
- **The natural-language-to-config path is narrow by design.** One sentence, "replicate the Lovable pricing model," produced a working multi-credit-type configuration (build credits, plan mode credits, cloud credits, AI gateway credits) with a draft invoice. That works because the target is a well-known public pricing model and the skills files constrain the output space. It is a nice demonstration of the general principle that agents succeed when the search space is narrowed by supplied context, not when the model is smarter.

## Grounded Context (Web Enrichment)
The acquisition is confirmed and the framing matters. Stripe completed its purchase of Metronome in January 2026 for a reported figure around $1 billion, its largest deal. Patrick Collison's stated rationale is worth quoting because it is a stronger claim than Garvin makes on stage: "metered pricing is the native business model for the AI era," and the resulting shift in how businesses generate revenue will be as significant as the advent of SaaS. Stripe describes Metronome's metering engine as used by OpenAI, Anthropic, and Nvidia. Post-acquisition roadmap items named publicly include seat-based credits, real-time spend alerts, hierarchical accounts, product catalogs with thousands of SKUs, sales-led models, and revenue analytics. Real-time spend alerts and hierarchical accounts are exactly the agent-runaway controls Garvin gestures at.

Some analyst commentary is worth holding alongside the official framing. Competitor and independent writeups frame the deal as Stripe paying roughly $1 billion rather than fixing Stripe Billing, which is a fair reading: Stripe had a billing product and chose to buy the usage-metering engine instead of rebuilding it. That is a signal about how hard accurate high-volume metering actually is, which supports rather than undercuts the technical point.

Two caveats on the talk itself. First, this is a vendor demo of two Stripe products by a Stripe employee, and the interesting engineering (skills files, error verbosity, sandbox design) is presented rather than evidenced. No numbers on agent success rate, no comparison against unguided agents. Second, the "exponential increase" claims about CLI usage, business formation, and agent-driven usage are stated without figures or baselines, from proprietary data nobody can check. The direction is plausible given everything else in this conference track, and the magnitude is unverifiable. The HubSpot pricing shift, by contrast, is a public and checkable market event, and it is the strongest evidence in the talk that the headlessness thesis is real rather than anticipated.

## Real-World Application / Actionable Step
- **Instrument attribution before optimizing cost.** The direct lesson for Amit: cost reduction work is only bankable if usage is attributable per customer, per product, per query class. Before the next routing or quantization project, verify that the metering layer can express the saving. If inference spend lands in one undifferentiated bucket, a 40% reduction on one workload is invisible and unfundable.
- **Give every autonomous agent a hard spend ceiling, implemented as a budget rather than a policy.** This is the cheapest catastrophic-risk control available and it does not depend on the agent behaving. Per-agent API keys with per-key spend caps, enforced at the gateway. Anything relying on the agent choosing to stop is not a control.
- **Ship skills files with your own internal APIs and libraries.** Metronome's approach is the right one and it is a small amount of work: encode the foot-guns, the required call ordering, the non-obvious constraints. For internal quantization, serving, or profiling tooling, this converts tribal knowledge into something every agent and every new colleague gets for free. Pairs directly with the `node_modules` docs pattern and with Imad Touil's skills-governance argument.
- **Make error messages verbose enough for an agent to self-correct.** Third independent endorsement of this in one conference. Any internal tool that fails with an opaque message is costing a full agent turn per occurrence.
- **Never let an agent's sandbox skip realistic load.** Extend this to model work: a validation harness that only checks the model loads and emits tokens is not a harness. Generate synthetic traffic matching production sequence-length distribution and batch composition, and make that part of the default test path.
- **Watch the seats-to-credits transition as a market signal.** If per-seat pricing is structurally broken by agents that operate whole platforms, then any business model in your portfolio or your employer's revenue mix that depends on seat counts is exposed. HubSpot moving first in EMEA is the datapoint to track, and the second and third movers will tell you whether it is a trend or an experiment.
