# Always-on agents run production without the on-call tax

**Channel:** AI Engineer
**Published:** 2026-08-09
**Source:** https://www.youtube.com/watch?v=vSx5IULvBns

## TL;DR
Justin Smith (founding product engineer at Resolve AI, previously an observability architect at Splunk and ten years at VMware) argues the first wave of AI optimized the wrong thing. Coding was never the bottleneck. Roughly 70% of engineering time goes to running what was shipped, and AI-generated code is increasing production incident volume while the cheap-token era ends and organizations start rationing spend. His central distinction is between execution and production context. Execution can load a dashboard. Production context is what tells you "that metric smells off" before you can articulate why, and it is the part that requires a persistent learning system that tracks how your services interact and where the hotspots are as the system evolves. The talk then focuses on background agents, the long tail of operational work that has no page and no incident bridge, with a live demo of deployment monitoring that builds a per-release check plan from the actual diff.

## Key Takeaways
- The premise: AI produced bigger PRs shipped faster, increasingly by people who do not understand the code or its operating principles. Coding got cheaper, running production did not.
- His breakdown of the non-coding 70%: maintaining platforms, scaling infrastructure, debugging incidents, on-call, hotfixes, alert handling, updating runbooks and procedures, restoring services, escalations, and answering other teams' questions.
- Two compounding pressures he names explicitly. AI code is generating more production issues and the existing structures were not built for that change rate. And the unlimited-token era is ending, with prices rising and companies clamping down on AI spend.
- "Full stack AI" as he means it: the model is no longer the hard part, the context around the model and what it can do inside a specific domain is.
- The core conceptual split. A task is execution plus the context to know how to execute it. Execution can check a dashboard. Production context decides whether what it sees matters. His formulation is worth keeping verbatim: execution can load the dashboard, production context says this feels wrong and I cannot even explain why.
- On learning, he is deliberately careful. Models are highly capable, but truly understanding your environment, how services interact, where the hotspots are, and keeping that understanding current as the system evolves faster and faster, is the hard part. That requires a persistent knowledge system that tracks current state and current causal chains, not a better model.
- Background agents cover work with no ceremony attached: watching deploys land healthy, morning incident digests, chasing a P99 drift that returned but does not warrant a page, capacity reports against quarterly goals, recurring health checks so a customer is not the first to notice.
- Trigger taxonomy: schedules (reports), calendar events (the Thursday on-call handover), event streams (CI/CD deploys, Slack messages), and direct instruction.
- Execution model: always cloud-hosted so closing your laptop is fine, running in a sandbox with a filesystem so the agent can self-organize its work, backed by a shared memory system so lessons from one task transfer to others.
- Deployment monitoring is his flagship use case and the argument is precise. CI/CD checks are good baselines but not exhaustive, every rollout is unique, and whole categories of change (feature flags, infra changes) often bypass the pipeline entirely and get no monitoring at all. The fallback today is trusting an alert to fire and an on-caller to ask who changed what.
- The demo: an agent sees a GitHub release tag posted to Slack, reads the actual changes, decides which telemetry would reveal whether those changes are healthy, and builds a check plan for that specific release. In the example, a checkout service replacing a currency service means monitoring checkout latency and error rates plus the Kafka pipeline, because that is the relevant causal chain.
- Timing is not hard-coded. The agent may decide to wait an hour because that failure class only manifests occasionally, or come back in three days to ask whether the deploy is still healthy and whether the intended effect actually materialised.
- The Slack first-responder agent, which he calls the fun one. It passively watches channels, decides whether it has enough confidence to answer, and if it is unsure it DMs the human to confirm before replying publicly. He frames the emergent behaviour as unplanned.
- His honest framing of why this matters: answering colleagues' questions is not hard work, it is disruptive work, and if he does not do it nobody gets an answer for a long time.
- Reports are conversationally tunable. Replying "too verbose, make it shorter" in the thread updates the underlying recurring task so future runs are different.
- Interop position: everything is exposed via MCP, so you can graft it into your own agent harness and bring your own skills rather than duplicating them.
- Closing argument: the cost of operational work is not in task execution, it is in environment complexity.

## Architecture & Optimization Mechanics
The interesting engineering claim is that the expensive, non-transferable asset is the environment model, not the reasoning. Framed in optimization terms, this is a statement about where to spend tokens. A generic frontier model asked "is this deploy healthy" must rediscover the service topology, the normal ranges, and the causal chains on every invocation, which is enormous redundant context loading at high per-call cost. A maintained knowledge system amortises that discovery across every task and lets the per-invocation prompt be small. That is why the same talk can simultaneously claim models are excellent and that the hard problem is unsolved: the bottleneck is a caching and state-maintenance problem dressed as an intelligence problem.

The dynamic check-plan generation is the strongest idea and it is a variable-compute argument. Static CI/CD gates apply a fixed check set to every release regardless of what changed, which means they simultaneously over-check trivial diffs and under-check risky ones. Reading the diff to derive which telemetry is diagnostic is allocating verification effort proportional to blast radius. The extension to non-uniform time budgets is the same principle on the temporal axis: hold the watch open for an hour, or return in three days, based on the expected manifestation latency of the failure class rather than on a fixed timeout. Both are the same move as adaptive inference compute, applied to observability.

The confidence-gated escalation in the Slack agent is the pattern most worth copying and the least novel technically. An agent that decides between answering, staying silent, and privately asking a human to confirm is implementing a three-way abstention policy with a human in the loop only on the uncertain band. That is exactly the structure of a good cascade: cheap path, expensive path, and an explicit abstain. The design detail that makes it socially viable is that escalation goes to a DM rather than the public channel, so a wrong guess costs one person's attention rather than the team's trust.

## Grounded Context (Web Enrichment)
Resolve AI's trajectory backs the thesis with capital. The company raised a $125M Series A at a $1B valuation announced February 2026, followed by a $40M extension led by DST Global and Salesforce Ventures in April 2026 at a $1.5B valuation. It was founded by Spiros Xanthos (CEO) and Mayank Agarwal, and Xanthos has been publicly making the same argument Smith makes here, that the AI coding boom is breaking production systems. The product positions as an AI site reliability engineer handling incident diagnosis, rollback decisions, capacity adjustments, configuration changes, infrastructure actions, and guided code changes. Reported customer outcomes are a 72% reduction in time to investigate critical incidents at one client and a 30% reduction in engineers required per incident at another. Those are vendor-supplied figures, but they are at least specific and measure the right things (time to diagnose, headcount per incident) rather than a vague productivity uplift.

The 70% figure is real and if anything conservative. Chainguard's 2026 Engineering Reality Report, surveying 1,200 engineers and tech leaders across the US and Europe, found engineers spend just 16% of their week writing code and building features, with 84% going to maintenance, technical debt, and fragmented tooling, while 93% said coding is the most rewarding part of the job. Other measurements bracket it: McKinsey's 2024 developer efficiency work put coding at 32%, Sonar's analysis puts new code plus improvement at 32% with another 35% on maintenance, testing, and security response, and internal studies at Microsoft and elsewhere have found figures closer to 14%. IDC's reporting identifies the specific consumers of that time as CI/CD implementation and application and infrastructure performance monitoring, which is precisely the work Smith is proposing to hand to agents. So the numbers vary with methodology but the direction is unanimous, and the 84% figure suggests the problem is larger than his slide claimed.

Worth reading against this: ACM Queue's "Eight Myths on Software Engineering and GenAI" and a longitudinal study of AI coding assistants' impact (arXiv 2605.23135), both of which push back on straightforward productivity narratives. The relevant point for Smith's argument is that if AI shifts effort from writing to operating without reducing total effort, the measured productivity gain is small even when the coding gain is large. That is consistent with the March 2026 longitudinal finding that AI tools deliver roughly 10% developer productivity improvement rather than the marketed multiples, and it is arguably the strongest available support for his thesis.

His claim about the token economy ending is directionally correct and worth watching, though he offers no specifics. It matters because it changes the calculus of always-on background agents: an agent that continuously watches deploys and Slack channels has an unbounded idle cost, and whether that survives budget scrutiny depends entirely on how cheap the always-watching path can be made.

## Real-World Application / Actionable Step
1. Build one deployment-monitoring background agent for your own model serving stack, and make the check plan derive from the diff. For inference work the analogue of his checkout-plus-Kafka example is: a change to a quantization config or a kernel should automatically trigger monitoring of tokens per second, p99 time-to-first-token, GPU memory headroom, and task-level accuracy on a held-out set, and the agent should choose which of those matter based on what actually changed. A pure kernel change needs latency and throughput. A quantization change needs the accuracy gate. Static dashboards do not make that distinction and neither do most CI pipelines.
2. Extend the watch window to match manifestation latency, which is the underused half of his idea. Quantization regressions frequently do not show up in a fifteen minute canary. They show up on long-context requests, on rare token distributions, or under a traffic mix that only appears at peak. An agent that returns after three days and asks whether the intended speedup materialised without an accuracy drift is catching exactly the failure class that current release gates miss.
3. Copy the confidence-gated DM escalation into any automated decision path you own, including model routing. Three outcomes, not two: act, abstain, or privately ask. For a router, the abstain band should route up to the expensive model, and the "ask" band should log for human review with the full context attached. Most routers collapse this to a binary and eat the resulting errors silently.
4. Take the environment-model argument as a cost-engineering directive. If your agents rediscover your service topology, your normal metric ranges, and your causal chains on every invocation, you are paying for that discovery on every call. Building a maintained knowledge store is a token-cost optimization with the same shape as prompt caching, and it is the lever that makes always-on agents affordable when token budgets tighten.
5. Treat the 84% number as the real target when arguing for tooling internally. Any productivity case built on faster code generation is arguing about 16% of the week. The case with actual leverage is reducing the time spent operating what was shipped, which is where the measured hours are.
