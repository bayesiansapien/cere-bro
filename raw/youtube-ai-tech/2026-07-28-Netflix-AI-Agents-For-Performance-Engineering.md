# AI Agents for Performance: Ship Faster, Pay Less (Rajat Shah, Netflix)

**Channel:** AI Engineer (World's Fair 2026)
**Published:** 2026-07-28
**Source:** https://www.youtube.com/watch?v=CgsWxRUY5Eo

## TL;DR
A Netflix staff engineer on the AI platform team presents a production playbook for the problem created by agentic coding: code volume is up roughly 10x and compute cost is climbing with it, because coding agents optimise for shipping, not for cycles. His fix is to point agents at profiling data. Profilers across Java, Python, and Go emit structurally identical output (call stack, self CPU, inclusive CPU), which is exactly the shape an LLM reads well. Feed it the profile, let it identify the hot path, clone the repo at the exact production commit, trace the call path, and open a code review. Under five minutes on a large codebase. The durable asset is not the agent, it is a **central Git-hosted markdown catalog of patterns and anti-patterns** that turns one service's discovery into fleet-wide memory. Real numbers: an O(n²) fix worth 8.8% of CPU time, and one metrics anti-pattern found across seven services worth 0.5 to 4.6% CPU each.

## Key Takeaways
- **The premise:** agents ship code fast and do not know your platform, your frameworks, or your internal patterns. They reproduce patterns from other codebases or invent new ones you never anticipated anyone using against your framework. "Newer models will just write faster code" is explicitly rejected.
- **Two founding assumptions, both correct.** (1) Every profiler speaks the same language regardless of runtime, so the input format generalises. (2) Agents already recognise generic inefficiency patterns from training: O(n²) loops, loop invariants, repeated allocation inside hot loops, contention, missed batching.
- **The aha moment:** the agent identified a quadratic algorithm **from the call stack alone**, before reading any source. An immutable map copy appearing inside a tensor merge method was visible as a pattern in the profile.
- **Four mechanical steps after detection:** code-search for the method, check out the repo at the exact commit running in production, locate the implementation while skipping internal library noise, trace the full call path. All four are automatable and none require judgment.
- **The scaling move is cross-repo search.** One bad pattern (a Spectator counter object allocated on every iteration of a hot path) was found in **seven services** via cross-repo search. Finding one instance is a fix. Finding the pattern is a fleet-wide win.
- **Memory is a markdown Git repo, not a vector database.** He is emphatic about this. A stateless LLM plus a stateful central catalog equals fleet-wide memory. Central, not per-team or per-product, so one service's finding compounds for every future profiling run.
- **Catalog entry schema:** query hints, symbol list, services where confirmed, a confidence level that rises as more services confirm, plus both the anti-pattern and the correct pattern side by side.
- **Bootstrap from public sources.** Jeff Dean's C++ optimization writing, PyTorch's TorchFix repo of anti-patterns, and your own existing internal performance playbooks. An empty catalog is fine too.
- **"Profiler gives the estimate, canary gives ground truth, engineer makes the decision."** This is the load-bearing sentence of the talk.
- **Canary is a gate, not a report.** Two machines, old code and new, same traffic for ~10 minutes, compare CPU, latency, and error rate. The agent reads the comparison and decides whether the change even deserves a human's attention. An error rate increase is a hard stop, because it means the optimisation broke business logic.
- **Human approval is deliberately retained.** His reasoning: you are modifying code that currently works in production, without necessarily knowing the business context, with imperfect test coverage. That is risky by construction.
- **Shift left in three stages.** Reactive (profile production, fix what is already deployed) → review-time (a reviewer agent consults the catalog and leaves inline comments) → authoring-time (the coding agent consults the catalog *before* emitting tokens). Start reactive to build the catalog, then move left.
- **The catalog must be hierarchically indexed.** Hooking it into authoring costs tokens and slows generation, so the agent needs to navigate to the relevant entry rather than load the whole thing into context.
- **Explicit autonomy ladder.** L1: LLM identifies, humans do everything else. L2 (the subject of this talk): fixed workflow, tool integrations, hooks, harnesses, schedulable weekly. L3: agent plans and reasons freely, which requires heavy investment in evaluation, sandboxing, and prompt-injection defence. His advice is to stop at L2 and only escalate on demonstrated need.
- **The honest caveat, stated twice:** none of this is an AI problem. Test coverage, canary automation, and observability must be solid first. Without them the agents add friction and bugs.

## Architecture & Optimization Mechanics
The most valuable idea here is **profiling data as a natively LLM-friendly modality**, and it holds up under scrutiny. A flame graph is a visualisation built for humans because humans cannot read the underlying tree. But the underlying tree is a structured record of symbols with self and inclusive time, which is precisely the format a language model handles better than an image. Shah's team essentially noticed that the visualiser is a lossy human-accessibility layer and that the agent should consume the raw artifact. The 20 minutes an engineer spends hunting through a flame graph is time spent working around a representation problem the model does not have.

The second real idea is **the estimate-versus-ground-truth split**. Profiling tells you where cycles go, which is an attribution estimate. It cannot tell you whether a proposed change helps, because the change alters the program. Only running both versions under identical traffic answers that. Building the canary comparison in as a *precondition for requesting human review* is the design decision that makes the whole system tolerable: the human sees only changes that already passed functional tests and demonstrated measured improvement without an error-rate regression. Without that gate, an agent that can open a PR every five minutes is a denial-of-service attack on your reviewers.

The third is the **confidence-weighted catalog as a compounding asset**. Each confirmation across a new service raises confidence, and confidence gates how assertively the agent acts. This is a cheap Bayesian mechanism implemented in markdown, and it is a much better answer to "agent memory" than most of what is being sold. Compare [[2026-07-27-Cognee-Second-Brain-Claude-Code-Memory]], which reaches for knowledge graphs and managed infrastructure for a related problem. Shah's version is a Git repo, is human-editable, diffs cleanly, and has no staleness problem because reversals show up as commits.

Note the economic asymmetry that makes this work at all. A pattern discovered once costs one expensive investigation. Applied across seven services it returns 0.5 to 4.6% CPU each. At Netflix fleet scale, single-digit CPU percentages are large absolute dollars, which is why the *catalog* rather than the *fix* is the product.

## Grounded Context (Web Enrichment)
**The premise is empirically supported and Shah understates it.** A 2026 empirical study in Empirical Software Engineering analysed performance regressions in code from GitHub Copilot, Copilot Chat, CodeLlama, and DeepSeek-Coder across HumanEval, AixBench, MBPP, and the performance-oriented EvalPerf benchmark, confirming systematic performance regressions in AI-generated code. Usefully for Shah's thesis, the same work found that **few-shot prompting grounded in the identified root causes of those regressions improves generated code performance** by steering models toward performance-aware generation. That is a direct academic validation of the shift-left step: injecting the anti-pattern catalog at authoring time should work, and there is published evidence it does.

Broader context on the "10x code, rising cost" framing: acceptance rates for AI-generated code have risen from roughly 20% to 60%, while 2026 reporting documents higher defect rates, security issues, and technical debt in AI-generated code, typically surfacing after release rather than in testing. The most sobering data point, which Shah does not mention, is the 2025 METR study finding a 39 to 44% perception gap: developers *felt* 20% faster while measuring 19% *slower* on real-world codebases. That does not undermine his talk, it strengthens it. If the productivity gain is partly illusory and the compute cost is real, the case for automated performance recovery is stronger, not weaker.

**On the bootstrapping sources:** TorchFix is real and a good template. It is a LibCST-based linter for PyTorch code with autofix support, usable as a Flake8 plugin or standalone, with rules organised into namespaced categories (TOR0XX/TOR1XX general torch, TOR2XX domain-specific such as TorchVision, TOR4XX noisy rules disabled by default, TOR9XX internal). It is still beta. That category structure is worth copying directly into a performance catalog, particularly the "noisy, disabled by default" tier, which is exactly the mechanism for holding low-confidence patterns without spamming reviewers.

One thing the talk does not address and should have: the failure mode where the agent fixes a pattern that was deliberate. Hot-path code sometimes allocates repeatedly or duplicates logic for reasons that are correct but undocumented (cache locality, avoiding a lock, deliberate denormalisation). The canary catches performance regressions and error-rate regressions. It does not catch a change that is faster, passes tests, and is subtly wrong under load conditions the canary window did not sample. His retention of human approval is the only defence against this, and it is the right call.

## Real-World Application / Actionable Step
This talk is the closest match to Amit's day job of anything in this week's batch, and it is directly implementable.

1. **Build the catalog before building the agent.** Start a `perf-patterns` Git repo today with markdown entries using his schema: query hints, symbols, confirmed-in services, confidence, anti-pattern, correct pattern. Seed it from TorchFix's rule list and from his own accumulated knowledge of inference-stack anti-patterns. This is a one-afternoon task with no AI involved and it is the piece that compounds.
2. **The inference-serving analogue of his profiler idea is immediate.** vLLM, PyTorch profiler, and Nsight all emit structured traces. Instead of squinting at a Chrome trace or an Nsight timeline, feed the raw trace to an agent with a prompt like "identify the top three kernel-launch or memory-transfer bottlenecks and locate the source." Kernel launch overhead, unnecessary host-device syncs, and unfused elementwise chains are exactly the pattern-recognition tasks he describes, and they are visible in the trace without reading the code.
3. **Adopt "profiler estimates, canary decides."** For compression work the canary is a shadow-traffic A/B between the baseline and the quantized or pruned model, measured on tokens/sec, p99 latency, *and* an output-quality gate. Add the quality gate explicitly, because it is the axis Shah's CPU-oriented canary does not have and it is where compression changes actually fail. A pruned model that is 20% faster and 2% worse on the eval set is a regression, and no CPU metric will tell you that.
4. **Steal the cross-repo scaling move.** When he finds one bad quantization config or one missed fusion opportunity, the question is not "fix it" but "where else does this pattern appear." That is where the 7x multiplier lives.
5. **Stop at L2 deliberately.** His autonomy ladder is well reasoned and his warning about L3 requiring serious sandboxing and prompt-injection investment is correct. Note the contrast with [[2026-07-27-Boris-Cherny-Building-Claude-Code]], where Anthropic runs 20 to 30 self-maintenance routines at high autonomy. Both are right for their context. Anthropic owns the model, the harness, and the codebase. Most teams should take Shah's more conservative ladder.
6. **Schedule it weekly.** Once the fixed workflow exists (trigger profile → download → analyse → canary → propose), a weekly cron catches regressions close to when the code was written, which is when they are cheapest to fix. This is the single highest-leverage line in the talk and it requires no model reasoning at all.
