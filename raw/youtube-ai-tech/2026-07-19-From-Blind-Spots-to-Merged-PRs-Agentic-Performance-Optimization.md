# From Blind Spots to Merged PRs: Continuous Agentic Performance Optimization

**Channel:** AI Engineer
**Published:** 2026-07-19
**Source:** https://www.youtube.com/watch?v=JJGbw4ggaFs

## TL;DR
May Walter (Hud) tackles a workflow that never happens in real engineering teams: proactively hunting for performance and stability wins. Nobody prioritizes it because the investigation phase is an unbounded black box (an hour or weeks, and only "Dave" knows the code). Hud built an autonomous, vendor-neutral agentic workflow (GitHub agent workflows plus Claude Code plus runtime intelligence over MCP) that runs weekly against real production traces, scores high-ROI opportunities, implements the fix, reruns tests to verify actual impact, and delivers a human-readable report rather than a flood of PRs. The core insight: automate the phase that was previously skipped entirely, and cross the 80-90% trust threshold that autonomous automation requires but IDE-assisted coding does not.

## Key Takeaways
- The leaky-bucket problem: teams ignore perf issues until they hit crisis, fix in emergency mode, then go back to ignoring. Root cause is that investigation cost is unpredictable, so it never gets prioritized.
- The fix is to automate investigation: weekly runs with production context, scoring high-ROI opportunities (easy and impactful) like an automated performance sprint.
- "Prod-to-code" is the key technical move. Service/endpoint metrics (P90, CPU, memory) do not speak the same language as coding agents, which reason at the function and file level. Hud maps production overhead down to individual functions and connects each to its triggering endpoint, cron, or event consumer, capturing forensic evidence only when a request exceeds P99 or a threshold.
- Three failure modes they had to engineer around: (1) "plausible unverified" fixes that sound right but do not work until grounded in production data, (2) complex ClickHouse columnar queries that differ from classic SQL, (3) the "lazy fix" where the agent just swallows an exception instead of finding the root cause.
- Architecture layers: HUD query language (ClickHouse over the function/endpoint/forensics structure), plus skills (methodical playbooks that reduce eval variance, for example diffing pod memory against a baseline), plus automations (auto-fix, dead-code elimination for code unused 60 days, perf improvements). Targets known patterns: N+1 queries, missing indexes, artificial sleeps/timeouts, sequential async.
- Do not open 80 PRs. Nobody reviews a "rain of PRs." Score by hot-path frequency, business criticality (payments, sign-up), and risk (migrations need more review), then surface one high-ROI item at a time in a persuasive, human-readable gist to build the habit.
- The framing lesson: agentic engineering (autonomous) is fundamentally different from coding with an agent (interactive). 80% is fine in your IDE because you are there to steer. Autonomous automation needs 80-90% trust, achieved through scoring guardrails and runtime-verified fixes.

## Architecture & Optimization Mechanics
For Amit this is the closest thing in the batch to his day job: it is literally an automated performance-optimization loop, just aimed at web-service latency rather than model inference. The transferable primitive is prod-to-code context mapping. The reason coding agents fail at optimization is a representation mismatch, aggregate service metrics are at the wrong granularity for a model that reasons over functions. Bridging that gap (attributing latency to specific functions and their invocation paths) is exactly the kind of profiling-to-code linkage that would make an agent useful for kernel or inference-path optimization, where the equivalent gap is between GPU-level metrics (occupancy, memory bandwidth, kernel time) and the code that produced them.

The "plausible unverified" failure is the same pathology the Lyft and Langfuse talks warn about, restated for autonomy: an agent's suggestion is a hypothesis, not a result, and the only cure is grounding it in a measured before/after. Hud's discipline of implement-rerun-measure-then-surface is the correct pattern for any autonomous optimization agent, and it is precisely what Amit should demand before trusting an agent to propose a quantization scheme or a routing-policy change. The "context over cleverness" and "skills reduce eval variance" points reinforce a theme across the whole conference: reliability comes from structured context and methodical playbooks, not from a smarter model. The distinction between 80% (interactive, acceptable) and 80-90% (autonomous, required) trust is the single most useful mental model here for deciding when a loop can run unattended.

## Grounded Context (Web Enrichment)
The talk's framing rests on Google's DORA findings, and the data supports it with one important update. The DORA research confirms that AI adoption raises individual effectiveness (over 80% report higher productivity, 59% report higher code quality) while also raising software delivery instability, exactly Walter's "we feel fast, but software breaks more" thesis. The model even quantifies the cost: an assumed change-failure-rate rise from 5% to 6% post-AI produced a sample $344,000 downtime hit. One correction to the talk's "throughput is the same" line: the most recent DORA reporting finds that AI coding tools no longer correlate with throughput slowdowns, a genuine improvement over earlier findings, though the instability problem persists. That nuance strengthens Walter's argument rather than weakening it. If throughput has caught up but stability has not, then autonomous fix-and-verify loops targeting stability are exactly the missing piece. The broader DORA conclusion, that successful AI adoption depends on organizational systems and gates rather than tools alone, is the same "guardrails make it reliable" message Walter closes on.

## Real-World Application / Actionable Step
Build a prod-to-code profiling loop for the inference stack. Instrument vLLM/serving with function-and-kernel-level attribution, then run a weekly scored agent pass that hunts for known optimization anti-patterns (redundant recomputation, un-fused kernels, missing KV-cache reuse, synchronous host-device stalls) and, critically, implements a candidate fix and measures the actual latency/throughput delta before surfacing it. Enforce the implement-rerun-measure gate so no "plausible unverified" optimization reaches review, mirroring how Hud grounds every fix in production numbers. And adopt the one-at-a-time, ROI-scored reporting habit rather than dumping a batch of speculative PRs, scoring by how often a path runs and how much latency it actually costs, so the human review time is spent only on wins worth shipping.
