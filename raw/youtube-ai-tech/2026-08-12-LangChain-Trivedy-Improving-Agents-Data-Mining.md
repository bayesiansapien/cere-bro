# Improving Agents is a Data Mining Problem — Vivek Trivedy, LangChain

**Channel:** AI Engineer
**Published:** 2026-08-12
**Source:** https://www.youtube.com/watch?v=CvRngaQZQ3Y

## TL;DR
Trivedy, who leads applied research at LangChain, argues that continual learning and observability are the same problem viewed from two ends: an agent acts in an environment, produces traces, and improvement means folding that trace data back into agent state. His recipe is ship, collect traces, mine them, then run experiments driven by what the mining found. The technically valuable content is in two places. First, the cost structure of trace mining itself: reading traces at scale costs input tokens times trace count times average trace length, and long coding-agent trajectories no longer fit in a reader model's context at all, so the trace has to become an external object you query rather than a payload you feed. Second, and this is the section that matters most for routing work, LangChain's actual model-selection discipline: start with the strongest model purely to establish whether the task is possible at all, then look back at those traces and ask whether an open model can do the same job. On Harvey's legal benchmark they matched Opus-level trace judging with a cheaper open model at one to two orders of magnitude lower cost, and the mechanism was harness engineering informed by reading how Opus reasoned. He then gives the ordering rule most teams get wrong: harness engineer first because feedback arrives in two minutes, fine-tune only when you have saturated the harness ceiling, then harness engineer again. He also flags a cost-model shift worth internalising, that high-volume inference workloads are often cheaper as hardware cost on a cluster you spin down than as token cost, and closes on memory not being an append-only log, with sleep-time compute as the mechanism for reorganising it.

## Key Takeaways
- The four-step recipe: ship the agent so it operates in real environments, collect every trace including tool calls and API and CLI interactions, mine that data, then run data-driven experiments to test whether a new prompt, tool, orchestration, or loop actually improves things relative to observed traces.
- The coupling claim, stated as a hot take and correct: observability and continual learning are tightly coupled because both reduce to acting, reflecting on what happened, and updating what you know. A continual learning company needs traces; if you have traces, you can attempt continual learning.
- Why traces are necessary rather than nice: with code you can read the functions and reason about behaviour. Agents have prompts, tools, skills, hooks, middlewares, and sub-agent swarms, so humans cannot predict how a prompt change propagates at scale, and the effect differs by domain (a medical-domain prompt change behaves nothing like the same change in legal).
- His framing of the last four years: trading determinism for autonomy, which forces you to build systems that recover understanding of what an autonomous system did.
- How LangChain actually reads traces: centralise into a tracing project per agent or across agents, then send agents to read other agents' traces looking for specific things. Their example questions are good ones. Find interactions where users got upset or were happy. Agents now run for millions of tokens, so does the agent get dumber after the first compaction, the second, or never. And counterfactuals: I ran one frontier model, what happens on this task with a cheaper open model, and how do they compare.
- The trace level captures behaviour users actually see, which metrics do not, so it is the right granularity for fine-grained behavioural comparison.
- The data-volume argument: the trace data you have today is the least you will ever have, because agents are taking on more economic work and the total output of agents will eclipse humanity's lifetime output on shrinking timescales.
- Cost problem 1, and he gives the formula plainly: reading traces at scale costs input token price times number of traces times average trace size. At millions of traces and millions of tokens per trace this is the dominant cost of the whole loop.
- Cost problem 2, the harder one: a long coding-agent trajectory does not fit in a reader agent's context, so you cannot mine it by feeding it in. The trace has to be treated as an external queryable object, which means building agents that mine other agents efficiently rather than reading them wholesale.
- The open-model inflection: over the six months before the talk, open models crossed a threshold such that LangChain no longer reaches for frontier models by default. Their discipline is to identify the minimum level of intelligence a task requires.
- The practical sequencing they admit to, which is the honest version of that discipline: start with the strongest available model to find out whether the task is possible at all, establish that waterline, then go back to those traces and test whether an open model can reproduce the behaviour.
- The Harvey result: matching frontier trace-judging capability with a cheaper open model at roughly one to two orders of magnitude lower cost. The method was trying many models plus harness engineering, where the harness engineering was informed by reading how the frontier model reasoned. His framing is that the stronger model may need less guidance, so you compensate with explicit scaffolding rather than accepting the capability gap.
- The harness ceiling, and the reason it exists: harness engineering gives instant feedback and you can hill climb on evals, but you reach a point where more prompt tweaking yields nothing. That is the trigger to consider fine-tuning, not before.
- The fine-tuning claim, scoped correctly: customers do not care about the full variance of tasks, only the narrow vertical their own customers care about, and on that narrow set a tuned base model can reach and exceed frontier performance.
- The economic shift he calls out for anyone starting to fine-tune: you move from token cost to hardware cost. For high-volume inference, renting a cluster and getting effectively unlimited inference on it, then spinning it down, is often cheaper than paying per token, but it is a different calculation and a different mental model.
- The sandwich: harness engineer, fine-tune to break the ceiling, then harness engineer again on top of the tuned model.
- The decision rule underneath the sandwich, which is the single most useful line in the talk: whatever you do to improve an agent, choose the action that collects feedback fastest. Harness engineering returns signal in two minutes, which is why it goes first regardless of what the ceiling turns out to be.
- Three uses for mined trace data: distillation and SFT (take good traces from a strong model, build a dataset, tune a 9B or 13B to mimic the behaviour), generating evals and environments, and preparing digestible content for humans who cannot read every trace but must review in high-trust domains like legal and medical.
- The eval-as-behaviour-definition claim, another deliberate hot take: show him every eval you run on your agent and he can predict how it behaves, because you hill climb those evals and alter the agent until they pass. Evals define behaviour rather than measuring it.
- The scikit-learn framing, and it is a genuinely good reframe: he calls the modern equivalent model-harness-task fit. You still have a fit function, you are still fitting data plus harness plus model so that tasks pass, and the two jobs are finding good fit functions (auto research, on-policy distillation methods) and finding good data.
- On auto research: agents are good at making a score go up, they will cheat somewhat so you must check them, and the loop of act, read results, read traces, update is genuinely useful. Their own experiment had an agent read its Terminal-Bench traces, propose experiments, and attempt fixes.
- The densification point, which is the key insight of that experiment: Terminal-Bench outputs a single pass or fail, which is nearly useless as a learning signal on a hard task. Densifying feedback is how you make agents improvable, and traces are the substrate that holds the dense signal.
- Three axes of continual learning he expects to be necessary together: observational training data from agents acting, harness evolution (harnesses look the way they do because models were trained in them and because of real-world tasks, so they must evolve too), and memory.
- On memory, the sharpest formulation: humans are not append-only logs, and agents working with us over years or decades cannot append everything to one large file and search it. Memory needs updating and compaction, and he expects that to come from scaling sleep-time compute and dreaming, meaning read all traces across the agent lifecycle and use them to update agent state.

## Architecture & Optimization Mechanics
The model-selection procedure they describe is the best-articulated cascade design discipline I have seen from a production team, and it inverts the usual framing in a way worth adopting. The standard approach to routing is to start cheap and escalate on failure. Theirs is to start expensive to establish feasibility, then push down. Those are not the same thing and the difference matters: starting cheap and escalating tells you nothing about whether the task is achievable, so a failure is ambiguous between task impossibility and model insufficiency, and you cannot tell whether to invest in harness work or give up. Establishing the waterline with the strongest model first disambiguates that, and it also gives you a reference trajectory. The reference trajectory is the actual asset, because their harness engineering is derived from reading how the strong model reasoned and then supplying that reasoning structure explicitly to the weaker one. That is a concrete, non-obvious method for closing a capability gap without training: diff the reasoning traces, find what the strong model does spontaneously, and write it into the weak model's harness as scaffolding.

Notice what this implies about where capability lives, because it bears directly on routing research. If a one-to-two-order-of-magnitude cheaper model matches a frontier model on trace judging once you transplant the reasoning structure, then a meaningful fraction of the frontier model's advantage on that task was procedural rather than representational. Procedural advantages are transferable by prompt; representational ones are not. That gives you a sharper question than "which model is good enough for this query", which is the question routing research usually asks. The better question is what fraction of the capability gap on this task class is procedural, because that fraction determines whether harness transplantation will work and therefore whether the cheap route is viable at all. A router built on measured task difficulty will underestimate how much traffic can be pushed down, because it does not account for the harness being adjustable per route.

The harness-then-tune-then-harness sandwich is a claim about optimisation order and his justification is the right one: pick the action with the shortest feedback loop first. This is the same argument as profiling before optimising and it produces a specific ordering for compression work that I think is underused. Before quantising or pruning to hit a latency target, exhaust the changes with two-minute feedback loops: batch composition, KV cache configuration, speculative decoding draft choice, prompt length reduction, and scheduler settings. Those are harness engineering for inference. Compression is the fine-tune step in his sandwich, expensive and slow to evaluate, and it should come after the fast-feedback levers are saturated rather than being the first move. Then, critically, redo the fast levers on the compressed model, because the optimal batch size, speculation acceptance rate, and cache configuration all shift after quantisation. That last step is the part everyone skips and it is where his sandwich framing earns its keep.

The trace-as-external-object problem is the most technically interesting thing in the talk and it is structurally identical to a problem you already work on. A trace too large to fit in context is a retrieval problem over a structured document with strong temporal and causal ordering, which is exactly the long-context versus retrieval trade-off. The naive fix is chunk and embed, which loses causality, and the reason it fails on traces is that the interesting question is usually about a transition ("what changed after the second compaction") rather than about content. His compaction question is worth restating as a research question because it is measurable and nobody has published a clean answer: does agent quality degrade monotonically across compaction events, and if so is the degradation in the compaction summariser or in the model's ability to use a summarised context. That question is directly answerable from traces with a fixed classifier, it matters for every long-horizon agent, and it is the same question as whether a compressed model degrades more on summarised context than on raw context. If compaction and quantisation compound, which I would expect since both reduce information density, then long-running agents on quantised models degrade faster than either effect predicts alone. I have not seen that measured.

His token-cost to hardware-cost point deserves the arithmetic he does not do, since it is the crossover calculation that governs whether your compression work has commercial value at all. Serving your own model has a fixed hourly cost regardless of utilisation, so it wins above a utilisation threshold and loses below it. Every efficiency gain you deliver moves that threshold down, which means the real business case for quantisation is not the cost saving at current volume but the volume at which self-hosting starts to beat API pricing. Framing your work that way is considerably more persuasive to a finance function than a perplexity table, and it also tells you which efficiency gains matter: anything that increases throughput per GPU-hour moves the crossover, anything that only reduces memory without increasing throughput does not, unless it lets you use cheaper hardware.

The eval-defines-behaviour claim is the one I would treat carefully because it is both true and dangerous. He is right that teams hill climb their evals and therefore that the eval set determines the agent. The consequence he does not draw is that this makes eval-set construction the highest-leverage and least-audited decision in the pipeline, and it is exactly the mechanism behind [benchmaxxing](2026-08-02-Benchmaxxing-Plague-Surge-AI.md). It also sits in direct tension with [Hylak's floor-raising argument from the same track](2026-08-12-Raindrop-Hylak-Floor-Is-The-Frontier.md): if behaviour is defined by evals and evals are built from mined traces, then your agent's floor is bounded by the failure modes already present in your trace history, and novel floor failures are invisible by construction. Trace mining is a ceiling-raising method that cannot find unknown unknowns, and that limitation is inherent rather than fixable with more data.

Set against the same-day talks, the picture is coherent. [Applied Compute](2026-08-12-Applied-Compute-Denton-Hinting-Distillation-Quadrants.md) supplies the weight-update mechanism, LangChain supplies the data layer that mechanism consumes, and Hylak supplies the reason most teams will only ever do the harness half. Trivedy's model-harness-task fit framing is also the same idea as [DSPy's separation of task from model](2026-07-23-Separating-The-Task-From-The-Model-DSPy.md), arrived at from operations rather than from compiler design, and the memory argument continues the thread from [Cognee](2026-07-27-Cognee-Second-Brain-Claude-Code-Memory.md).

## Grounded Context (Web Enrichment)
The product and the claims are documented, so you can go past the talk. LangChain published a blog post under the same title, and the commercial artifact is LangSmith Engine, described as using specialised agents to read every trace, look for signals your team defines, find issues, create code fixes, generate evals, commit information to memory and context stores, and improve agents over time. LangSmith Insights is the pattern-finding layer, analysing traces for unmet user expectations and failures, grouping related failures, and triaging by severity. There is also a Claude Code plugin that traces runs to LangSmith including subagents, tool calls, and compaction runs, with evals to test the impact of skills and MCP servers. That last one is directly usable: it means his compaction-degradation question is answerable on your own Claude Code usage with off-the-shelf tooling rather than requiring custom instrumentation.

The sleep-time compute framing is not LangChain's and the lineage is worth knowing because the numbers are better than anything in the talk. Letta introduced sleep-time compute in an April 2025 paper with public accompanying material, shifting context processing off the user-facing critical path into idle time. Reported results are a 5x reduction in real-time compute, +18% accuracy on complex reasoning, and 2.5x lower cost per query when amortised across repeated queries over the same context. The dreaming extension is the part that matches Trivedy's memory argument precisely: a dream takes an existing memory store plus one to a hundred prior sessions and produces a new store with duplicates merged, stale or contradicted entries replaced, and new insights surfaced. Letta's three-tier structure is core blocks in context, searchable recall history, and vector-backed archival. Harrison Chase has publicly framed LangSmith Engine as sleep-time compute for memory, so the two threads are explicitly connected. If you want the evaluation harness for this, LongMemEval-V2 targets long-term agent memory, and Panini is a 2026 paper on continual learning in token space via structured memory, both of which are more rigorous starting points than any vendor blog.

Two things to hold loosely. The Harvey result is real work but the talk gives no numbers beyond "roughly yes at one to two orders of magnitude cheaper", and trace judging is a comparatively forgiving task: it is classification with a rubric, which is where small models close gaps most easily, so it is close to the best case for pushing work down a cascade. Do not generalise the cost ratio to generation tasks. Second, the amortisation caveat on sleep-time compute matters, since the 2.5x cost reduction is explicitly conditional on repeated queries against the same context. For one-shot queries, precomputation is pure added cost, which means sleep-time compute is a caching argument and its economics depend entirely on your query reuse distribution. Measure that before building for it.

## Real-World Application / Actionable Step
1. Adopt the waterline-then-push-down procedure as your standard routing methodology, replacing cheap-first escalation. Establish with the strongest model whether the task is achievable at all, keep those trajectories as reference, then test cheaper and open models against them. The escalation-on-failure design cannot distinguish task impossibility from model insufficiency, and the reference trajectory is what makes the push-down work.
2. Make the procedural-versus-representational split an explicit measurement in your routing work. For each task class, quantify how much of the frontier-to-cheap gap closes when you transplant the strong model's reasoning structure into the cheap model's harness. That fraction predicts how much traffic can be routed down, and a difficulty-based router systematically underestimates it because it treats the harness as fixed per route.
3. Reorder your inference optimisation to put the fast-feedback levers first, then compression, then the fast levers again. Batch composition, KV cache configuration, speculative decoding draft selection, and scheduler settings all return signal in minutes; quantisation and pruning do not. And re-tune all of them after compressing, because optimal batch size and speculation acceptance rate both shift once you change numerics. The second harness pass is the step people skip.
4. Reframe your compression business case as moving the self-hosting crossover point rather than as a cost saving. The relevant number is the request volume at which serving your own quantised model beats API token pricing, because that determines whether your work unlocks self-hosting for a given workload. It also tells you which gains count: throughput per GPU-hour moves the crossover, memory reduction alone often does not.
5. Run the compaction-degradation experiment on your own agent usage, since the tooling now exists off the shelf. Trace your Claude Code runs, classify output quality by number of compaction events elapsed, and check whether degradation is monotonic. Then run the version that is actually novel: does a quantised model degrade faster across compaction boundaries than a full-precision one. If compaction loss and quantisation loss compound, that is a publishable result and it changes how you would deploy compressed models in long-horizon agents.
6. Densify your own feedback signals before blaming the optimiser. His Terminal-Bench point generalises: a scalar pass or fail is nearly useless for improvement, and most compression evals are exactly that. Instrument per-layer divergence, per-token disagreement, and per-capability deltas so that a failed recipe tells you where it failed rather than only that it did.
7. Treat trace mining as a ceiling method and pair it with something that finds unknown unknowns. Mined traces can only surface failure modes that already occurred, so an agent improved purely from its own history has a floor bounded by its history. Combine it with the deterministic-signal-plus-investigation pattern from the Raindrop talk, which can flag novel spikes without needing a prior example.
8. Read the Letta sleep-time compute material rather than the vendor framing, and check your reuse distribution before adopting it. The 2.5x saving is conditional on repeated queries over the same context, which makes this a caching decision. If your queries do not reuse context, precomputation is a pure cost.
