# Build Evals That Actually Matter

**Channel:** AI Engineer
**Published:** 2026-07-19
**Source:** https://www.youtube.com/watch?v=3z2uT5aDx_Y

## TL;DR
Nick Ung and Ash from Lyft describe the eval pipeline behind Lyft's customer-support AI agent, built and hardened over roughly two years. The through-line: treat agent evaluation like ML model development. Run rigorous offline evals (simulated multi-turn conversations, LLM-as-judge plus deterministic assertions) as a launch gate before production, then run online evals with tracing, graders, and a human-in-the-loop error-analysis loop. Their sharpest, most transferable lessons are that user-simulator LLMs are too polite (so you must fine-tune them on real, impatient user verbatims), that generic judge metrics are worthless, and that you must validate the validator by treating the judge as a binary classifier scored on precision and recall against human labels.

## Key Takeaways
- Never use live users as test data. Gate launches on offline eval criteria, mirroring how you would not ship an ML model without offline evaluation. They took direct inspiration from Sierra's Tau-bench.
- Three reasons evals fail: (1) the score does not gate anything real, (2) the LLM judge is too noisy and generic to be trusted or actioned, (3) there is no mechanism or owner to catch and act on production regressions.
- Synthetic data trap: do not just prompt an LLM for "50 test queries." Sample real production traffic and mutate it to cover golden paths and edge cases.
- The polite-simulator problem is the standout finding. A frontier model role-playing a Lyft user is too helpful and patient, yielding a fake 90%+ pass rate. Fine-tuning the user simulator on real (frustrated, terse) user verbatims plus defined personas (bypasser who demands escalation, refund seeker, AI skeptic) dropped the score, which is exactly what you want. An easy eval gives no production signal.
- Generic metrics (helpfulness 0.5, conciseness, toxicity) are not actionable. Reframe every metric as binary task success/failure tied to a business outcome. Their example: an "education rubric" that fails the agent for over-educating when it should escalate, or escalating too soon.
- Validate the judge like a classifier: hand-label ~100 examples, split train/dev/test (but the "train" set only seeds few-shot examples and tunes the judge prompt, no weights change), then report precision and recall against human ground truth.
- Criteria drift is real: you discover your eval criteria by looking at data, and your sense of quality evolves. Evals must be co-developed with the model, not defined once up front.
- Add statistical rigor only where it gates a decision. Every score needs a confidence interval. An 84% vs 88% gap on 50 traces is not a real gain.
- Closing the loop: three levers, model learning (post-train weights, reward modeling for RL), context learning (what the agent sees: docs, memories), and harness learning (system prompt, tool schemas, routing, retries). Error analysis feeds all three.

## Architecture & Optimization Mechanics
This talk is a clean statement of ML-grade discipline applied to agents, and several mechanics are directly reusable in Amit's routing and compression eval work. The strongest is validate-the-validator: an LLM judge is a noisy classifier, and shipping decisions made on an unmeasured judge are shipping decisions made blind. Scoring the judge with precision/recall against human labels, and reserving confidence intervals for gating numbers, is exactly the rigor Amit should demand before trusting any automated quality signal in a routing policy. The polite-simulator finding generalizes beyond support: any eval whose input distribution is generated by a helpful frontier model will be systematically easier than production, inflating pass rates and hiding the failure modes you actually need to route around. Fine-tuning the adversary (user simulator) to match the real input distribution is the fix.

The three-lever decomposition (model / context / harness learning) is a useful mental model for where to spend optimization effort. Most teams reach for model learning (fine-tuning, RL) first because it is glamorous, but Lyft got most of their wins from context and harness changes driven by error analysis, which are cheaper and faster to iterate. For Amit this maps onto a cost-aware principle: exhaust prompt, routing, and retrieval changes before paying for post-training. Their planned eval harness is config-driven YAML with primitives (task, dataset, persona, LLM adapter, evaluator) run at dev time, pre-commit, and CI/CD, with parallelism for tens of thousands of examples. That is the same throughput and reproducibility engineering that inference optimization demands, applied to the eval layer.

## Grounded Context (Web Enrichment)
The Tau-bench lineage they cite is worth understanding precisely, because Lyft actually diverges from it in an instructive way. Sierra's Tau-bench deliberately avoids LLM-as-judge, scoring agents on final database state (did the refund actually get issued) for fast, faithful, deterministic pass/fail evaluation, and tau2-bench added pass^k to measure reliability across repeated attempts rather than one lucky run. Lyft borrows the simulated-user and binary-outcome philosophy but leans harder on LLM-as-judge for the conversational quality that database state cannot capture, which is why validating that judge becomes critical for them in a way it is not for pure Tau-bench. Their polite-simulator fix is corroborated by the Microsoft user-simulator paper they reference and by the broader 2026 consensus that user simulation realism is a first-class eval problem. Independent 2026 agent-evaluation guides echo the rest of their playbook almost point for point: binary and objective metrics over graded scores, continuous error analysis over one-off audits, and statistical rigor reserved for gating decisions.

## Real-World Application / Actionable Step
Before trusting any LLM-as-judge in a routing or compression eval, validate it as a classifier: hand-label ~100 traces, tune the judge prompt on a dev split, and report precision and recall on a held-out test set. If those numbers are weak, fix the judge before believing any downstream metric. Second, audit your eval input distribution for the politeness trap. If your test inputs are LLM-generated, they are almost certainly easier than production, so seed your eval set from real traffic and, if you use a user simulator, fine-tune it toward the hard, adversarial cases. Third, adopt the model/context/harness triage: when quality regresses, exhaust context and harness fixes (prompt, retrieval, routing, retries) before spending on fine-tuning or RL, and reserve confidence intervals for the numbers that actually gate a ship decision.
