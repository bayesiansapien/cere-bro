# AI in GTM at Notion | Flora Liu

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=L4I7WgiEquo

## TL;DR
Notion rebuilt its go-to-market stack as a distributed system rather than a marketing ops workflow, collapsing Salesforce, Gong, Outreach, ZoomInfo and Snowflake into a single decisioning loop with four primitives: Know, Decide, Act, Learn. The load-bearing design choice is that humans and agents read and write the same substrate (Notion itself, plain markdown plus databases) instead of bolting an "AI layer" on top of the business. Early result after 13 weeks: enterprise reps show more qualified opportunities, and users who received context-aware recommendations were 63% more likely to take the next step.

## Key Takeaways
- **Two-tier data plane.** Snowflake computes truth (daily plus some real-time transforms into a small set of versioned entities: accounts, contacts, workspaces, eligibility, facts). DynamoDB serves truth as a denormalized key-addressable profile that agents query in milliseconds with zero joins. Agent-generated artifacts (research snippets, rolling summaries) are keyed by the same IDs so one fetch returns structured and unstructured context together.
- **Signal as the atomic unit.** A signal is any customer event important enough to change the next best action. Internal signals (hit an AI limit, contacted sales) make the system reactive; external signals (funding round, hiring spikes, tech-stack shifts) are what make it proactive. A signal service watches the profile, decides if an action is available, assigns an owner, and emits a task for either a human or an agent.
- **Durable orchestration over ad-hoc scripts.** Every signal becomes a Temporal workflow. One run fans out to enrichment, web search, and draft generation, all of which are network calls that fail or rate-limit. Temporal supplies retries, dedupe, and exact resumption, so one malformed Gong transcript cannot take down the batch.
- **Generate-score-select, not generate-once.** The cold outbound path runs concurrent research subagents, drafts three emails, scores them, and has a review agent pick and edit the winner. Every LLM step is traced for offline quality evaluation.
- **Eligibility and routing promoted to a first-class primitive.** Rules previously scattered across the email tool and the CRM were consolidated into one place consumed by product, sales, and engineering, with a single classifier doing the routing. This is what kills double-sends.
- **Explicit trust boundary.** Agents never talk to customers directly. A prospect filling in a contact-sales form is treated as untrusted user input, because an agent sits downstream of it.
- **Build the context layer, rent everything else.** No in-house email vendor, CRM, orchestration engine, or enrichment (they use Clay). The context layer is refused as a vendor purchase because a generic tool cannot express esoteric data models and cannot be debugged.

## Architecture & Optimization Mechanics
The interesting engineering here is a cache-hierarchy argument applied to agent context, and it maps almost directly onto inference serving. Snowflake is the cold, expensive, high-fidelity compute tier. DynamoDB is the hot serving tier holding a denormalized, precomputed view whose entire purpose is to eliminate join latency at agent inference time. That is materialized-view precomputation as a latency optimization, the same trade Amit makes when he prefills and caches KV state rather than recomputing attention over a long system prompt on every call.

Two details are worth stealing. First, structured and unstructured artifacts are keyed by identical IDs, so a single key lookup returns the complete context bundle. In routing terms, this is what lets the "decide" step be one cheap call instead of a multi-hop agentic retrieval loop, and multi-hop retrieval is usually where token cost and tail latency explode. Precomputing the bundle offline moves work from the latency-critical path to a batch path. Second, the generate-three-score-pick-one pattern is best-of-N sampling with an LLM verifier, deployed in production for a business workflow. Best-of-N is a straight compute-for-quality trade, and the right optimization is exactly the routing question: N should be a function of signal value, not a constant. A high-ACV enterprise outbound deserves N=5 on a frontier model; a lifecycle nudge deserves N=1 on a distilled small model.

The "agents as operators, not co-pilots" framing also has an architectural consequence Amit should note. Because the substrate is plain markdown with navigable database hierarchies, the context layer is legible to the model without a custom retrieval adapter per surface. Format choice is an optimization decision: markdown is dense in information per token relative to serialized CRM JSON, which is padding-heavy with keys the model must re-read on every call.

## Grounded Context (Web Enrichment)
The two-tier pattern Liu describes is not a Notion idiosyncrasy, it is the converging industry blueprint as of mid-2026. Snowflake published its own internal context layer for AI agents as a five-layer framework in March 2026, and within a two-week window in June 2026 both Snowflake and Databricks shipped effectively the same product shape: an AI coworker, reusable agents, and an auto-assembled context layer to ground them. The semantic-layer-for-agents category (Cube, Atlan) hardened over the same period around the same claim, that agents need a governed, precomputed entity model rather than raw table access. Liu's talk is therefore best read as an unusually concrete implementation report on a pattern that vendors are now selling as a product, which strengthens rather than weakens the credibility of her architecture.

One claim deserves a caveat. The headline metric, 63% more likely to take the next step for users who got context-aware recommendations, is presented without any mention of a holdout or randomization. Users who trigger enough signal to receive a context-aware recommendation are by construction more engaged than those who do not, so a large fraction of that lift is plausibly selection effect. Liu is honest that it is early and the system is still being built, but treat 63% as directional, not causal.

## Real-World Application / Actionable Step
- **Apply best-of-N as a routing problem, not a constant.** Notion runs a fixed N=3 with a review agent. Instrument the score distribution: if the top-1 and top-3 scores converge for low-value signals, N is wasted compute. Build the value-conditioned N policy (cheap model with N=1 for lifecycle, frontier model with N=5 for enterprise outbound) and you have a clean case study for a routing paper: same verifier, dynamic compute allocation, quality held constant at lower average cost.
- **Steal the two-tier context precompute for agent serving.** For any agent Amit builds, precompute a denormalized, single-key context bundle offline instead of letting the agent do multi-hop retrieval at request time. Measure it as a latency and token budget win: multi-hop retrieval adds both a round trip and the intermediate tokens the model must re-read.
- **Treat context format as a token-efficiency lever.** Benchmark the same customer record as verbose JSON versus terse markdown and count tokens plus downstream accuracy. Notion's markdown choice is defensible on information density per token, and that is a measurable claim worth verifying on his own workloads.
- **Copy the "shadow your best human" rule for eval set construction.** The failure mode Liu names, encode a mediocre process and you get a mediocre agent, is the same failure mode as training on a weak teacher in distillation. The spec comes from observing the strongest operator, not from the documentation.
