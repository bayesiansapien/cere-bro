# The Death of Developer Advocates — Stephanie Jarmak, Sourcegraph

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=Lrw0jqBNaw0

## TL;DR
Jarmak was an astronomer last year, had zero GitHub commits, and now has 12,000 and maintains an open source multi-agent orchestration framework. She gave this talk because her manager, an actual developer advocate, submitted the deliberately provocative title and then went on holiday rather than deliver his own eulogy. The argument survives the framing. DevRel exists to relate to developers, developers are becoming orchestrators of agent fleets, and a second user has appeared that reads your docs, calls your API, hits your errors and recommends your product to humans. So the role splits into two measurable jobs. First, agent experience as an engineering discipline: she built CodeScaleBench, hundreds of tasks spanning the software development lifecycle, ran agents with and without Sourcegraph's code navigation MCP tool, and mined thousands of traces for friction. The finding she leads with is small and exact. The model tried a parameter name its training data made it expect, the tool did not support it, the error message was good enough that it recovered, and it burned an entire turn doing so, all fixable with one line of tool description. Second, generative engine optimization measured properly, and her pilot produced the sharpest number in the talk: prompts written as comparison shopping surfaced Sourcegraph 65% of the time, prompts written as a real pain, "we keep breaking downstream services when we change shared libraries because we can't see all the consumers," surfaced it zero times. Zero. The agent suggested a wiki page.

## Key Takeaways
- The 65%-versus-zero gap is the finding to remember, and it generalises beyond marketing. A system evaluated on queries phrased the way a category-aware shopper phrases them will look far better than the same system evaluated on queries phrased the way someone in the middle of the problem phrases them. Prompt framing, not capability, accounted for the entire difference.
- Agents are simultaneously users and recommenders of your tool, which is a combination human developers also have but at completely different scale and with completely different failure modes.
- Token cost of using your tool is now a purchasing criterion. Jarmak states plainly that organisations evaluate not just whether the tool works but how many tokens the agent burns working with it and how fast it is. That reframes API and tool design as an efficiency problem with an external buyer looking at the number.
- The read-tool example is the model of what agent experience work looks like. Model expects `read_line` because training data biased it that way, tool wants `start_line`, description says nothing to disambiguate, call fails, error message is good enough to self-correct, one full turn wasted. Diagnosable only from traces, fixable in one line.
- Good error messages are load-bearing for agent recovery. The failure was survivable specifically because the error explained itself. An opaque error would have cost several turns or the whole task.
- Training data staleness compounds rather than decays, and her live test is the evidence. Claude Sonnet 4 kept pitching Cody, a deprecated Sourcegraph product. She reran it on 4.6 the afternoon of the talk expecting improvement and it pitched Cody more, because output from older models about the older product has accumulated across the web and become the training signal for newer ones.
- Agents have a documented preference for machine-generated prose, which Jarmak puts bluntly: do not send AI slop to human developers, everyone can tell and nobody likes it, but agent-facing content can be as structured and em-dash-riddled as the model likes. Two audiences, two registers, and the credibility functions genuinely differ.
- Friction from discovery to embedding is what determines whether an agent recommends you at all. If adopting your tool requires three demos and emailing a sales rep, the agent will not tell the user to do that, because it cannot.
- Go where the agents are. MCP registries and marketplaces are the distribution channel, in the same way package registries were for libraries.
- Agents want something quotable. Current examples, fresh timestamps, charts and FAQs. Keep content updated even when the product has not changed, because recency feeds the relevance ranking.
- The role splits into three flavours to be mixed by available skills: engineering, building the MCP interface plus evals and instrumentation; product, owning the end-to-end agentic experience and agent-experience rubrics; marketing, owning how agents enter the funnel and bring developers with them.
- The curb cut argument is the best frame in the talk. Curb cuts were built for wheelchairs and now serve strollers, suitcases and anyone with wheels. Making a tool legible to agents clears the path for humans, because the underlying work, precise interfaces, honest errors, current docs, machine-readable structure, was always good practice.
- Two immediate experiments she prescribes: point a coding agent at your docs and read the transcript as an agent experience report, and write GEO prompts in both the comparison and the pain register, then measure mentions against recommendations separately.

## Architecture & Optimization Mechanics
The agent-experience benchmark is the methodologically interesting artifact and it is worth extracting the design. CodeScaleBench runs the same task suite with and without the tool under test, which makes it an ablation rather than a benchmark, and ablations answer a question benchmarks cannot: what is the marginal contribution of this component. Most tool evaluation reports absolute task success with the tool present, which conflates the tool's contribution with the base model's competence and is uninterpretable when the base model improves. Running paired conditions isolates the delta. The second design choice, keeping thousands of traces rather than only scores, is what turns an eval into a debugging instrument. A score tells you the tool underperformed. A trace tells you the model guessed `read_line` because that is what its prior says the parameter is called, which is a one-line fix in the tool description that no amount of scalar-metric staring would have surfaced.

The parameter-name failure is worth generalising because it is a broad and under-appreciated class. A model's prior over API surfaces is shaped by whatever conventions dominate its training data, so any interface that deviates from the dominant convention pays a tax on every call, in retries, in tokens and in turns. There are only three ways to pay less. Conform to the convention, which is free and usually correct. Disambiguate explicitly in the tool description, which costs a few tokens once per call. Or return errors so informative that recovery takes one turn instead of three, which is the fallback and the one Sourcegraph got right by accident. Stated as a design rule: your tool schema is competing against the model's prior, and every place you disagree with the prior is a place you must spend tokens on the disagreement. This is measurable. Log the distribution of first-call argument errors per tool and you have a ranked list of exactly where your schema and the model's expectations diverge, which is a cheap and high-yield diagnostic almost nobody runs.

The token cost of tool use as a buying criterion is the point in this talk with the most direct bearing on inference economics, and it inverts the usual framing. Tool efficiency is normally treated as the caller's problem to optimise around. Jarmak is describing a market where the callee is judged on it. That means the design targets for an agent-facing API are the same as for a serving stack: minimise tokens per successful outcome, not per call; return the smallest representation that supports the decision, which is the markdown-over-HTML argument again; fail fast and explicitly rather than returning plausible garbage; and make the common path require the fewest round trips. A tool that needs three calls to answer what one call could answer is three times as expensive in latency, tokens and failure probability, and the buyer now has instrumentation to see it.

The self-preference observation is the one place where Jarmak's throwaway line has a serious mechanism behind it, and the mechanism is directly relevant to compression work. Models prefer text they would have generated, and the correlation is not mysterious: research links self-preference bias to self-recognition capability, and the underlying signal appears to be perplexity. Models assign significantly higher evaluations to lower-perplexity outputs than human evaluators do, which means the "preference" is largely a preference for familiar token distributions. Two consequences follow, and only one of them is about marketing. The marketing one is that writing agent-facing content in the register a model finds low-perplexity is a principled tactic rather than a superstition, and it explains why structured, formulaic, heavily-signposted content outperforms elegant prose with agents while losing with humans. The far more important one is for anyone using LLM-as-judge in an evaluation loop, which includes most people evaluating quantized or pruned models: if your judge scores partly on perplexity-like familiarity, and your compression pipeline shifts the output distribution, the judge will penalise the compressed model for distributional drift that may be orthogonal to quality. Self-preference bias intensifies with model size and capability, so using a strong judge does not fix it, and the judge is likely to favour whichever candidate most resembles its own generations rather than whichever is better. The documented mitigation, generating a long chain of thought before evaluating, reduces harmful self-preference and is worth adopting as default judge configuration.

The training-data-staleness compounding effect is the most alarming observation in the talk and it deserves more attention than it got. The naive model of staleness is that old information decays as new information accumulates. What Jarmak observed is the opposite: content generated by older models about the older product proliferated across the web, entered the training corpus of newer models, and made the newer model more confident about the deprecated product than the older one was. This is a feedback loop in which model output becomes model input, and the equilibrium it drives toward is not truth but whatever was most written about. The practical implication for anyone maintaining a fast-moving library, framework or model API is that you cannot outwait a wrong prior, because it is being reinforced faster than it decays. The only defences are the ones that bypass parametric memory entirely: retrieval from an authoritative current source, or documentation shipped inside the artifact so the agent reads the version it actually has. That is the same conclusion the Burns talk at this conference reached from a completely different direction, and two independent derivations of the same fix is a reasonable signal.

## Grounded Context (Web Enrichment)
The self-preference research is well established and more precise than the talk's framing. "LLM Evaluators Recognize and Favor Their Own Generations" established the linear correlation between an LLM's self-recognition capability and the strength of its self-preference bias, which is the causal story: the bias exists because the model can tell. Follow-up work identified the quality heuristic, where models classify text they rate as higher quality as self-generated, and localised the mechanism in perplexity, since LLMs assign significantly higher evaluations to low-perplexity outputs than human evaluators do. A 2026 study asks whether the preference is legitimate or harmful using verifiable benchmarks and finds that inference-time scaling, specifically a long chain of thought before evaluating, effectively reduces the harmful component. The bias intensifies with model size and capability, which is the counterintuitive part and the reason it matters operationally: upgrading your judge makes it worse, not better.

The GEO field has professionalised fast enough to have its own statistics and its own adversarial literature. The dominant generative engines in 2026 are ChatGPT, Perplexity, Gemini, Google AI Mode, AI Overviews, Copilot and Claude. Two findings are relevant to Jarmak's method. Pages citing external authoritative sources inline saw substantial citation gains, with the biggest lift going to lower-ranked sites, reported at a 115% visibility lift for sites ranked fifth in Google, which suggests generative engines reward outbound citation in a way classical search never did. Schema markup improves LLM discoverability by roughly 67% but is insufficient alone. The commercial number driving the interest is that AI-referred visitors reportedly convert at 14.2% versus 2.8% for Google organic, attributed to arriving pre-informed and recommendation-primed. Treat that figure with the scepticism any vendor-published conversion multiple deserves, and note the obvious selection effect: someone who asked an agent for a solution to their exact problem and was pointed at you is much further down the funnel than someone who typed a keyword.

Worth knowing that the adversarial side already exists: SafeGEO, an arXiv paper from June 2026, studies GEO risks in recommendation agents, meaning the same source-side rewriting techniques that legitimately improve visibility are being studied as an attack surface for manipulating what agents recommend. Anyone doing what Jarmak describes should expect the retrieval side to start defending against it, which puts GEO on a similar trajectory to SEO, with the same eventual arms race and the same eventual penalty for over-optimisation.

One honest limitation: her GEO pilot is a small n on a self-built prompt set with no controls, and she presents it as a pilot rather than a result. The 65%-versus-zero gap is a large enough effect that it is probably real, and the value is in the method rather than the number.

## Real-World Application / Actionable Step
1. Run ablations, not benchmarks, when evaluating a component. Same task suite with and without the component isolates its marginal contribution, which absolute scores cannot, and stays interpretable when the base model improves underneath you. This applies to a tool, a retrieval layer, a routing policy or a compression scheme.
2. Keep traces, not just scores. The read-tool parameter bug was invisible in aggregate metrics and obvious in a transcript. Any eval infrastructure that discards traces has thrown away the part that tells you what to fix.
3. Log first-call argument errors per tool and rank them. That distribution is a direct measurement of where your schema disagrees with the model's prior, and each entry is a cheap fix in the tool description. Almost nobody runs this diagnostic and it is close to free.
4. Treat the model's prior as a design constraint on interfaces. Conform to dominant naming conventions where you can, disambiguate explicitly where you cannot, and make errors informative enough for one-turn recovery. Every deviation from the prior is a tax paid on every call, forever.
5. Optimise agent-facing APIs for tokens per successful outcome. Smallest sufficient representation, fail explicitly rather than returning plausible garbage, minimise round trips on the common path. Buyers now instrument this, which makes it a competitive property rather than a courtesy.
6. Configure LLM judges with chain-of-thought before evaluation, as a default. Self-preference bias correlates with self-recognition, appears to be driven by perplexity-like familiarity, and intensifies with model capability, so a stronger judge is a more biased one. This matters directly for compression evaluation, where the pipeline shifts the output distribution and a familiarity-sensitive judge will penalise drift that is orthogonal to quality.
7. Validate compression results with a judge that did not generate either candidate, and cross-check with at least one non-judge metric. If a quantized model scores worse under an LLM judge but matches on task-verifiable metrics, suspect distributional-familiarity penalty before concluding quality loss.
8. Do not wait out a stale prior. Model output about your old version is entering the training corpus of the next model, so the error reinforces rather than decays. Retrieval from an authoritative current source, or documentation shipped inside the artifact, are the only fixes that bypass parametric memory.
9. Write evals in the register your users actually use. The 65%-versus-zero result is a lesson about eval construction as much as about marketing: category-aware phrasing measures a different and much easier distribution than problem-first phrasing. If your eval set was written by someone who knows the system, it is a comparison-shopping eval.
10. Point a coding agent at your own documentation and read the transcript. Cheapest possible version of the whole discipline, and the first place where friction, ambiguity and missing information become visible without any instrumentation at all.
