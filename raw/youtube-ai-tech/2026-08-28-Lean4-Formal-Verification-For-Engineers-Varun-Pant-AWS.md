# Your Code Has Bugs. Lean4 Has Proofs: Formal Verification for Engineers | Varun Pant, AWS

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=lRa9sPaMyy4

## TL;DR
Pant's argument starts from the verification crisis created by agentic coding: builders are generating thousands of PRs a week, LLM-as-judge is probabilistic, tests check some inputs not all, and human review does not scale to agent speed. None of these can assert correctness for all inputs. Formal verification can. His proposed division of labour is the crisp idea: humans own the specification, machines own the code and the proof. The workflow is spec-driven development, write what correct means (directly in Lean or in natural language for the AI to autoformalize), validate the specification (this is the load-bearing step, since everything downstream inherits its errors), let the coding agent implement against it, and let the verification tool prove the implementation satisfies it. His closing line is the thesis in miniature: software that is not probably correct but provably correct.

## Key Takeaways
- **The specification is the artefact that must be validated by a human, and it is upstream of everything.** Pant emphasises this twice. Either a human reviews it or you test that it holds on sample inputs. A wrong specification produces a verified implementation of the wrong thing, and the proof will not tell you.
- **Why Lean specifically, four properties.** Same language for definitions and proofs, so there is no translation layer. Implemented in Lean itself, hence highly extensible. A small trusted kernel, so the trust surface is tiny. Proofs export and can be independently checked, and multiple independent kernels exist in C++, Rust, and Lean, with the ability to write your own.
- **The chess analogy for interactive proving is genuinely useful.** Tactics are moves, the goal is checkmate (the theorem), you traverse a tree, and when a branch fails you backtrack and try another. The kernel is the referee that checks the final position. Tactics do the work, the kernel checks the work, and an incorrect proof is rejected immediately.
- **Pattern one, spec and code both in Lean.** Open-source work converted zlib, a C compression library, to Lean. Natural language spec ("decompressing the output of compress returns the original data") to AI-generated formal spec to human-validated spec to AI-written Lean implementation with helper lemmas to a proved theorem, kernel-verified. The proof ran to 32,000 lines.
- **Pattern two, Rust production code with a Lean functional model, validated by differential testing.** This is Cedar, AWS's open-source authorization policy language behind Verified Permissions. The specification lives in Lean, production runs in Rust, and roughly 100 million differential random tests run nightly comparing both on identical inputs. No version ships until they agree. The property being protected is exactly the kind that must never fail: forbid trumps permit, so any satisfied forbid policy must deny the request.
- **Pattern three, deductive verification of Rust directly.** Verus uses the Z3 SMT solver with `requires` and `ensures` annotations as pre- and post-conditions, statically checked and erased at runtime, which Pant nicely describes as ghost code. Aeneas takes a different route, translating Rust's mid-level intermediate representation functionally into Lean and then proving there.
- **The solver-versus-prover distinction, well explained.** A proof assistant is an interactive chessboard where you make moves. A solver is a very powerful calculator: feed it a formula and it returns satisfiable or unsatisfiable. Different tools for different shapes of obligation.
- **Pattern four, any language, via Strata.** An AWS open-source work-in-progress modelled on a compiler: define a dialect for your language, lower it from a high-level IR to Strata Core (written in Lean), and once everything speaks Strata Core, dispatch obligations to any engine, Lean proofs, SMT solvers, or model checkers.
- **Getting started is genuinely low-friction.** Lean runs in the browser. Pick your most critical code, write the specification, let the agent implement, let the tool prove.

## Architecture & Optimization Mechanics
The reason this talk matters to Amit is that it is the strongest available answer to the verifier-quality question that every other talk in this conference stumbled into. Clare Liguori found that agent autonomy scales with feedback-loop quality. Andrew Garvin drew the autonomy boundary at the sandbox because billing errors are expensive. Eyal Blum built a pyramid pushing work down to deterministic checks. Varun Shenoy's bet that knowledge work should be represented as code works because code is verifiable. Every one of those is bounded by the strength of the available oracle, and formal verification is the strongest oracle that exists. If the oracle is a kernel-checked proof, an agent can be given very wide latitude, because a wrong answer cannot pass.

The economics are also inverted from what people assume, and the Cedar example shows why. Interactive proving is expensive in human time, which is what has always limited formal methods to aerospace, chip design, and cryptography. But if an agent generates the proof and a small kernel checks it, the human cost collapses to writing and validating the specification while the machine absorbs the search. That is precisely the asymmetry that makes proof search a good fit for LLMs: generation is hard and expensive, verification is cheap and total. A 32,000-line proof is unthinkable as hand-written artefact and unremarkable as generated-and-checked artefact. The kernel is what makes it safe to accept output you did not read.

For Amit's own work the transferable pattern is Cedar's, not zlib's. Full functional verification of a serving stack is not realistic. But writing a Lean model of a narrow, critical, well-specified component and differential-testing the production implementation against it at scale is entirely realistic, and 100 million nightly randomised comparisons is a template rather than an aspiration. The natural candidates in his domain are quantization and dequantization round-trips (a specification stating the reconstruction error bound for a given scheme and group size, differential-tested against the CUDA kernel), attention masking and position-encoding logic (where off-by-one errors are silent and corrupt long-context behaviour), KV cache eviction and paging policies (where the invariant is that a served token sequence is identical with and without eviction), and router policy invariants (never route a query above a cost ceiling, never route below a capability floor). Every one of those is a place where a bug produces plausible-looking wrong output rather than a crash, which is exactly the failure class tests miss and proofs catch.

The one gap in the talk worth naming: he does not discuss the cost of proof search or its failure mode. Proof search can run for a long time and return nothing, which from a production standpoint is an unbounded-latency dependency. In an agentic loop that is a real problem, and it is the same tail-latency issue Kanish Manuja described for reasoning models, appearing in a different guise. Any practical deployment needs a proof-search time budget and a defined fallback when the budget expires, and neither is mentioned.

## Grounded Context (Web Enrichment)
The Cedar claims check out precisely and the wider ecosystem has moved considerably faster than the talk suggests.

AWS formally modelled Cedar's core components in Lean, proving correctness and security properties, and the Lean team confirms the release gate Pant describes: new Cedar versions cannot ship unless the models, proofs, and differential tests are current. Cedar handles authorization for millions of resources with sub-millisecond authorization latency and proven soundness and completeness, so this is production-critical infrastructure with formal backing rather than a research artefact. That combination, formally verified and sub-millisecond, is the useful data point, since the common objection to formal methods is that verified code is slow. Verus with Z3 and the AutoVerus and AlphaVerus tools generating verified Rust specifications and proofs are all real and active.

The AI-plus-Lean convergence is now a distinct field with its own tooling and benchmarks. Mistral released Leanstral 1.5 on July 2, 2026, a model specifically for Lean 4 proof engineering, theorem proving, and autoformalization. A May 2026 pipeline lifts Rust cryptographic code into Lean 4, discharges proof obligations with AI provers such as Aristotle and Aleph, and checks them with the Lean kernel, which is exactly Pant's Pattern three with the human removed from the proof step. Harmonic's Aristotle proved five of six IMO problems with full formal verification in Lean 4 in 2025, which is the clearest available demonstration that machine proof search at genuine difficulty is now real.

The academic literature addresses the gaps in the talk. VERINA (arXiv 2505.23135) benchmarks verifiable code generation, which is the missing measurement of how often this actually works. "Automating Formal Verification with Agent-Guided Tree Search" (arXiv 2605.27485) attacks the proof-search cost problem Pant does not mention. "Type-Checked Compliance: Deterministic Guardrails for Agentic Financial Systems Using Lean 4 Theorem Proving" (arXiv 2604.01483) is the direct answer to the agentic-guardrail problem that Cloudflare, Notion, and Stripe each solved probabilistically at this same conference. And Lean4Agent (arXiv 2606.06523) formally models and verifies agent workflows and trajectories, which is the logical endpoint: verify the agent's plan, not only its code.

Two honest caveats the talk elides. First, the zlib conversion "happened over a week or so" and produced 32,000 lines of proof for a compression library, which is a substantial cost for a well-specified, mathematically clean problem. Most production code is neither. Second, and more fundamentally, the human-owns-the-specification division only helps if specifications are easier to get right than implementations. For zlib's round-trip property that is clearly true. For business logic with hundreds of interacting requirements it is often not, and a subtly wrong specification is more dangerous than an unverified implementation because it comes with a proof attached. Pant flags specification validation as important, which is correct, but he offers no method for it beyond human review and spot-testing on some inputs. That is the honest state of the art and it is the field's central open problem.

## Real-World Application / Actionable Step
- **Copy Cedar's pattern, not zlib's: Lean model plus differential random testing against the production implementation.** This is the practical entry point and it does not require proving anything about the real code. Pick one narrow numerically critical component, write its functional model in Lean, and run randomised differential tests nightly. Cedar's 100 million tests per night is the template.
- **The highest-value target in Amit's own work is quantization round-trip correctness.** Specify the reconstruction error bound for a given scheme and group size, then differential-test the kernel against the Lean model across randomised weight distributions and edge cases (denormals, saturation, group boundaries). Quantization bugs are silent, they degrade quality rather than crashing, and they are precisely the class that unit tests miss.
- **Second target: KV cache and attention invariants.** The invariant is stateable and strong, that a served sequence is bit-identical with and without eviction, paging, or continuous batching. These are the bugs that produce plausible-but-wrong long-context behaviour and are nearly impossible to catch by inspection.
- **Third target: router policy invariants as machine-checked properties.** Never exceed a cost ceiling, never fall below a capability floor, always terminate. Cedar's forbid-trumps-permit is structurally the same shape of property, and a proved routing policy is a genuinely novel contribution in a literature that currently ships heuristics.
- **Budget the proof search and define the fallback.** Proof search has unbounded latency and can return nothing. Before putting any of this in an agentic loop or CI gate, set a time budget and decide what happens when it expires (fall back to differential testing, mark unverified, block the merge). Pant omits this and it is what breaks naive adoption.
- **Read VERINA before believing the success rate.** It is the benchmark for how often verifiable code generation actually works, and it is the number you need to size the effort honestly rather than from a conference demo.
- **Spend your review effort on the specification, and treat a proof as no stronger than the spec it discharges.** This is the discipline the whole approach rests on. A verified implementation of a wrong specification is worse than unverified code, because the proof suppresses the suspicion that would otherwise make someone check.
