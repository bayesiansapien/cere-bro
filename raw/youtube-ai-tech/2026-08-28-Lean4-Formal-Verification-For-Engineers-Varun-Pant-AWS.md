# Your Code Has Bugs. Lean4 Has Proofs: Formal Verification for Engineers (Varun Pant, AWS)

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=lRa9sPaMyy4

## TL;DR
The premise: agents are producing hundreds to thousands of PRs a week, and none of the available correctness checks scale to that. LLM-as-judge is probabilistic. Tests check some inputs, not all. Human review cannot match agent throughput. Formal verification is the only one of these that can say "for all inputs, this is correct." Pant's proposed division of labour is the clean idea in the talk: **humans own the specification, machines own the code and the proof.** Write what correct means, in Lean directly or in natural language that AI auto-formalizes, then *validate the specification* because everything downstream depends on it, then let the coding agent implement and the verifier prove. He walks four escalating patterns (spec and code both in Lean, Lean spec against a Rust implementation with differential testing, deductive verification of Rust via solvers, and any language via AWS's Strata) and ends on the reframe: software that is not probably correct but provably correct.

## Key Takeaways
- **The specification is the upstream artifact and the one thing a human must own.** Pant repeats this deliberately: whether written formally or auto-formalized from natural language, you must then validate it, by human review or by testing that it holds on sample inputs. A proof against a wrong specification is a proof of the wrong thing, and this is where the whole approach lives or dies.
- **Lean is one language for code, definitions, and proofs, with no translation layer.** It is implemented in Lean, so it is extensible, and it has a small trusted kernel. Proofs can be exported and independently checked.
- **The chess analogy for proof search is genuinely good pedagogy.** Tactics are moves, the theorem is checkmate, you traverse a tree of goals, backtrack when a branch fails, and the small kernel adjudicates the final position. An incorrect proof is rejected immediately, and you only ever need to trust the kernel.
- **Multiple independent kernels exist, in C++, Rust, and Lean, and you could write your own.** This is the trust-minimisation argument: the surface you must believe is small, open, and independently reimplementable.
- **Pattern one, everything in Lean.** The zlib example: a natural-language spec ("decompressing the output of compress returns the original data"), AI-generated formal spec, spec validated, AI writes the Lean implementation, generates helper lemmas as subgoals, proves each, assembles the final theorem, kernel verifies. Roughly 32,000 lines of proof, produced over about a week.
- **Pattern two, Lean spec against production code in another language.** Cedar, the open-source authorization policy language behind AWS Verified Permissions, has its functional specification in Lean and its production implementation in Rust. Differential random testing checks that both produce identical outputs on identical inputs, roughly 100 million tests nightly, and no version ships until they agree. The property being protected is concrete: if any forbid policy is satisfied, the request is always denied.
- **Pattern three, deductive verification with solvers.** A solver is a very powerful calculator: feed it a formula, get satisfiable or unsatisfiable. Verus uses Z3, with `requires` and `ensures` annotations as pre- and post-conditions written inline in the Rust code, statically checked and erased at runtime, effectively ghost code. Aeneas takes a different route, translating Rust's mid-level IR functionally into Lean and then using the theorem prover.
- **Pattern four, any language via Strata.** AWS's open-source, work-in-progress compiler-like platform: define a dialect for your language, lower from a high-level IR to Strata Core (written in Lean), then dispatch to any backend engine, Lean proofs, SMT solvers, or model checkers.
- **The getting-started path is low friction.** Lean runs in the browser. Pick your most critical code, write what correct means, let the agent implement, let the verifier prove.

## Architecture & Optimization Mechanics
- **Verification is the correctness primitive that scales with agent throughput, and that is the actual argument.** Every other check has cost linear in inputs tested or in human attention. A proof has cost paid once at authoring time and then holds over the entire input domain forever. When code volume is the thing exploding, only the check whose cost does not scale with code volume survives. This is the same structural argument Eyal Blum makes for pushing verification down the pyramid, taken to its limit.
- **The generate-and-verify split is asymmetric in exactly the useful direction.** Proof search is expensive and nondeterministic, which suits an LLM. Proof *checking* is cheap and deterministic, which suits a small kernel. So the model can be unreliable at any individual step without compromising the guarantee, because a wrong proof simply fails to check. This is the ideal shape for an LLM-in-the-loop system and it is worth internalising as a design pattern well beyond Lean: wherever you can make verification cheaper than generation, model unreliability stops mattering.
- **Lemma decomposition is context-window management by another name.** The zlib proof at 32,000 lines was not produced in one pass. Breaking a theorem into helper lemmas gives each subgoal an independently checkable boundary, so a failed branch costs one lemma rather than the whole proof. Structurally identical to Blum's independently-validated plan phases and to Vaziri's Temporal activities: bound the unit of work so failure is local.
- **Differential testing as the bridge when full proof is impractical.** Cedar's design is the pragmatic middle: you cannot deductively verify a large Rust codebase cheaply, but you can prove properties about a Lean model and then empirically bind the model to the implementation with 100 million randomised comparisons nightly. That is not a proof about the Rust code, and Pant does not claim it is, but it is far stronger than tests alone and it is achievable now.
- **Ghost code erased at runtime means zero performance cost.** Verus annotations are static, so verified Rust runs at the same speed as unverified Rust. This is the property that makes verification viable in performance-critical code, which matters directly for anyone writing kernels.
- **Strata's dialect approach is MLIR's idea applied to semantics rather than compilation.** One shared low-level IR, many front-end dialects, many verification backends. If it works, it decouples "which language is the code in" from "which prover checks it," which is currently the main practical barrier to adoption.

## Grounded Context (Web Enrichment)
The specifics check out. AWS has formally modelled Cedar's core in Lean, proving correctness and security properties and confirming them by differential testing against the Rust implementation, and the Lean team's own account confirms Pant's strongest claim: new Cedar versions cannot be released unless the models, proofs, and differential tests are current. The roughly 100 million nightly differential random tests figure is corroborated. Strata is real and open source, an extensible platform for formalising language syntax and semantics built in Lean, with dialects explicitly inspired by MLIR providing orthogonal composable building blocks. Aeneas is in active research and practical use alongside Charon for verifying Rust via Lean 4, and Verus with Z3 sits in the same ecosystem, benchmarked in work like VERINA on verifiable code generation.

On the AI-plus-proof pipeline, the direction Pant describes is documented independently: a May 2026 pipeline lifts Rust cryptographic code into Lean 4, closes proof obligations using AI provers including Aristotle and Aleph, and checks the results with the Lean kernel. The zlib-to-Lean project he cites is consistent with this class of work, though the tool name is garbled in the transcript and worth verifying against the source before citing. There is also a visible broader trend of AI companies adopting Lean 4 for verifiable AI, with applications appearing in areas as varied as type-checked compliance guardrails for agentic financial systems and machine-checkable patent analysis, plus cloud infrastructure like AXLE emerging to run Lean proving at scale.

Where the talk oversells, and it is worth being precise about this. First, "for all inputs, the code is correct" is true of the *proved property against the stated specification*, not of the program in any absolute sense. The gap between "satisfies the spec" and "does what the user wanted" is exactly the gap Pant flags when he insists on spec validation, and it does not close with more proof. It is a human problem that formal methods relocate rather than solve. Second, 32,000 lines of proof over a week for zlib is a compression library with an unusually clean correctness property (decompress of compress is identity). Most production code has no such crisp property, and the specification effort dominates. Third, the differential-testing approach for Cedar is empirical validation of a model-to-implementation correspondence, which is strictly weaker than verifying the implementation, and the 100 million tests are a very large sample of an infinite space, not a proof. None of this undercuts the value; it bounds the claim.

## Real-World Application / Actionable Step
The honest assessment for Amit's work: full formal verification of optimization code is not the near-term move, but three specific things here are.

- **Verify routing and eligibility policy, not the model.** This is the highest-value direct application and Cedar is the template. Routing eligibility rules (this tenant cannot use an external provider, this query class must stay on a quantized local model, PII must not leave the VPC) are exactly authorization policy, and Cedar's proved property, "if any forbid policy is satisfied the request is always denied," is precisely the guarantee a routing layer needs. Policy logic is small, discrete, high-consequence, and rarely changes, which is the ideal profile for verification. Consider expressing the eligibility layer in Cedar itself rather than in ad hoc application code.
- **Adopt property-based and differential testing for numerical kernels now, as the practical rung below proof.** Quantization has genuinely crisp properties worth checking exhaustively over a domain: dequantize-of-quantize error bounded by the scheme's theoretical maximum, per-channel and per-tensor paths agreeing where they should, a fused kernel matching the unfused reference within tolerance across all supported shapes and dtypes. Run these as randomised differential tests against a reference implementation, nightly, at Cedar-like volume. This is achievable this quarter and it catches the class of bug that costs the most to find in production.
- **Use `requires`/`ensures`-style contracts where you already write Rust.** If any part of the serving path is in Rust, Verus annotations are static, erased at runtime, and therefore free at inference time. Buffer bounds, alignment requirements, and tensor shape invariants are the obvious candidates, and they are exactly the properties whose violation produces silent numerical corruption rather than a clean crash.
- **Apply the generate-and-verify asymmetry as a general design rule.** The transferable insight is not Lean, it is this: wherever verification is cheaper and more deterministic than generation, an unreliable generator becomes acceptable. Look for places in your own pipeline where a cheap checker could replace expensive human review of agent output. A kernel that must match a reference within tolerance is verifiable cheaply; a design document is not.
- **Spend an hour in Lean in the browser, then decide.** Pant's low-friction on-ramp is worth taking, if only to calibrate how much specification effort a real property costs. That number, not the theoretical appeal, determines whether this is usable on your codebase.
