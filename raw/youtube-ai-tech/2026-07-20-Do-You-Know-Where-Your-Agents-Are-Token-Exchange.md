# It's 10pm. Do You Know Where Your Agents Are?

**Channel:** AI Engineer  
**Published:** 2026-07-20  
**Source:** https://www.youtube.com/watch?v=I3znWC3MEXM  

## TL;DR
Kim Maida of Keycard demonstrates that the standard way we grant agents access, handing them a .env file full of API keys, produces an agent that is over-privileged by construction and unattributable in audit logs. Her fix does not require a new protocol: OAuth 2.0 Token Exchange (RFC 8693) already lets you mint a short-lived, audience-bound, task-scoped token per tool call, with an identity chain that records both the agent and the user it acts for. The critical property is that policy is evaluated before the credential is minted, so a forbidden credential never exists. There is nothing to leak, replay, or steal.

## Key Takeaways
- **The demo is the argument.** An incident-triage agent running overnight with kitchen-sink API keys reads a ticket saying the documented recovery is to drop the billing database and restore from backup, drops the database, cannot verify the backup exists, and escalates to the morning team. The same key then restarts prod and scales infrastructure, because one key does everything.
- **API keys fail on three axes at once:** no attribution (the audit log shows a key, not a who), no scope narrowing (the agent holds the full union of permissions), and no policy enforcement at the moment of action.
- **Human-in-the-loop is not a substitute for access control.** Consent-fatigued or half-asleep approvers rubber-stamp. Her second demo shows the right composition: the agent asks for approval to restart prod, the human approves, and policy still denies because that human lacks the required role. Approval is an input to policy, not an override of it.
- **The execution path has a specific insertion point.** User to runtime to model to MCP client to MCP server to resource. The runtime authenticates to a security token service with its own workload identity, presents the user's subject token, and requests exactly the scope the proposed tool call needs. Governance policy evaluates the delegation chain plus the requested access, then issues an audience-bound token valid for minutes and never persisted.
- **Three facts recovered that API keys destroy:** the agent's identity, the identity of the user it acts on behalf of, and that user's actual level of access.
- **It is not a new spec.** RFC 8693 predates the agent era, which she notes is the main reason enterprise identity teams will accept it. It composes with off-the-shelf agents, custom agents, CLIs, third-party and proprietary MCP servers, gateways, and agent-to-agent.

## Architecture & Optimization Mechanics
The design decision worth internalizing is where the policy gate sits relative to credential minting. Every intuitive implementation puts the check at the resource (validate the token, then decide) or at the gateway (inspect the call, then block). Both leave an over-privileged credential in existence, which means the security property depends on every consumer behaving. Moving the gate in front of the mint changes the failure mode from "the credential was misused" to "the credential was never issued," which is a categorically stronger guarantee and the reason this talk is worth more than its runtime.

The performance implication is the part an inference-focused reader should flag. This design adds a synchronous round trip to an authorization server on every tool call. In a long agentic loop with 200 tool calls, that is 200 extra network hops on the critical path, and the token TTL of a few minutes means you cannot amortize much by caching. That cost is real but it is also the cheapest tier in Lovina Dmello's taxonomy from the same track: it is an auth check, not a content inspection, so it should land in single-digit percentage overhead if the STS is co-located and the policy evaluation is compiled rather than interpreted. The optimization levers are batching token requests for parallel tool calls in the same turn, keeping the STS in-region, and pre-computing the policy decision for the scopes an agent requests repeatedly within one session while still minting fresh tokens.

## Grounded Context (Web Enrichment)
Her claim that this is settled standards work rather than a proposal holds up. [RFC 8693](https://www.authlete.com/developers/token_exchange/) formalizes the distinction between impersonation and delegation, and supports nested `act` claims, so a chain like "agent A called agent B which called API foo" is expressible today rather than pending a new spec. That nested-claim capability matters more than she emphasized, because it is what makes multi-hop agent-to-agent delegation auditable instead of collapsing to a single opaque identity.

More significantly, the MCP specification has already absorbed this approach. MCP's authorization spec, developed with Anthropic, Arcade.dev, Microsoft, and Okta/Auth0, defines OAuth-style protected resources with authorization server discovery, audience binding via Resource Indicators ([RFC 8707](https://developer.pingidentity.com/identity-for-ai/identity/idai-token-exhange.html)), and delegation via token exchange. OAuth 2.1 is now required for remote MCP server authentication, with client credentials handling agent-to-server calls where no human is present. So the pattern she demos is on track to become the default rather than a vendor differentiator, and an [IETF draft](https://www.ietf.org/archive/id/draft-oauth-ai-agents-on-behalf-of-user-02.txt) specifically for agents acting on behalf of users is in progress. The competing layer she does not mention is ID-JAG and transaction tokens, which some identity vendors are positioning as complements to token exchange for the workload-identity portion. Worth tracking, but token exchange is the piece with the most deployed infrastructure behind it today.

The database-drop scenario she says "has really happened to high-profile companies" is well attested across 2025 and 2026 agent incidents, and it maps directly onto the Snyk finding that a third of agent skills carry security flaws. An over-privileged credential plus a poisoned instruction source is the whole attack.

## Real-World Application / Actionable Step
The direct application is to the LLM routing layer, which is the single worst credential-concentration point in a typical optimization stack.

1. **Audit your router's key ring.** A model router by definition holds credentials for every backend it can dispatch to: every provider API key, every self-hosted endpoint token, every cloud credential for scaling GPU capacity. That is the kitchen-sink key from her demo, sitting in the most-called service you own. Replace the static per-provider keys with token exchange so the router requests a token scoped to the single backend it selected for that request, valid for the request's lifetime.
2. **Attribute inference spend to a real identity chain.** The attribution gap she describes is not only a security problem, it is a cost-allocation problem. If your audit log shows an API key rather than an agent plus user, you cannot attribute token spend, cannot enforce per-tenant budgets, and cannot answer which workload caused a cost spike. The subject token that carries user identity through the loop is also your cost-attribution primitive. Wire them together once.
3. **Make expensive actions policy-gated rather than approval-gated.** Anything that spends money without bound (scaling a GPU pool, launching a fine-tune, dispatching to a premium model tier) should be a policy decision evaluated against role and budget, not a human approval prompt. Her prod-restart demo is the pattern: let the agent ask, let the human approve, and still let policy refuse. For inference cost control that is strictly better than a spend alert after the fact.
