# ChatGPT Work for Sales: Pipeline and Forecast Intelligence

**Channel:** OpenAI
**Published:** 2026-07-28
**Source:** https://www.youtube.com/watch?v=q9TPE7pKkIo

## TL;DR
The revenue-leader view. ChatGPT Work produces an automated executive brief with top-line metrics and attention-requiring items organized by priority, plus areas being monitored and the posture of each segment. Drilling in turns the underlying data into an interactive executive-ready site opened inside the application, with priorities ordered by urgency and each initiative explorable in depth, backed by trusted data sources. The differentiated step: it identifies a potential sales play for the revenue organization based on **look-alike scenarios** and explains why the opportunity makes sense, then surfaces a lighthouse account fitting the criteria with a proposed action plan. On confirmation it generates step-by-step marching orders and then **fans out using computer use** to create a new Slack channel, add the appropriate account owners and sales leaders, and draft an action-oriented message for review before sending. After the play goes live it continues monitoring and surfacing items needing leadership attention.

## Key Takeaways
- **The look-alike play identification is the only genuinely novel analytical step across all four sales demos.** Everything else is retrieval, summarization, and asset generation. This is pattern matching across the account base to find a repeatable motion, which is a real analytical task rather than a formatting one.
- **Computer use for org actions is the notable capability, and it is a different risk class.** Creating a Slack channel and adding named people is not generating text, it is taking an action with organizational side effects that are visible to colleagues and awkward to reverse. That the draft message is held for review while the channel creation and member addition apparently are not is the interesting asymmetry.
- **The interactive site pattern recurs across these demos.** Static report becomes a navigable surface with priorities ordered by urgency, each initiative drillable, backed by cited sources. Consistent architectural choice across the family: persistent navigable artefacts rather than chat output.
- **"Backed by trusted data sources" is doing important unexamined work.** For a forecast, provenance is the whole product. A forecast you cannot audit back to CRM records and call transcripts is not a forecast a CRO can defend to a board.
- **The loop closes explicitly.** Monitor, identify play, prepare team, launch, continue monitoring. The claim is a continuous cycle rather than a report generator, which is the same always-on framing as the companion demos.

## Architecture & Optimization Mechanics
Three mechanics here are worth extracting, and one of them is a genuine warning.

**First, computer use is the most expensive inference modality in the entire demo family and the demo hides it.** Driving a UI means a loop of screenshot, visual reasoning, action, screenshot, verify. Each iteration carries a high-resolution image through the vision encoder and the prefill, and the number of iterations is not bounded in advance because the agent may need to retry when the UI does not respond as expected. Compared to calling a Slack API, computer use is orders of magnitude more expensive in tokens and in latency for an identical outcome. The optimization consequence is direct and unglamorous: **computer use should be the fallback for systems without an API, not the default integration path.** Any workflow using computer use where a first-party API exists is paying a large multiple for the same action. It exists in this demo because it generalizes across arbitrary tools, which is a real product advantage, but it is an economics disaster if used indiscriminately.

**Second, the look-alike analysis is a retrieval-and-similarity problem, not a generation problem, and it should be built as one.** Finding accounts resembling a successful pattern is embedding similarity plus filtering over structured CRM attributes. Doing it by feeding account records into a frontier model and asking for matches is the expensive way to compute a nearest-neighbour search. The correct decomposition is cheap retrieval to shortlist candidates, then expensive reasoning only to explain *why* the shortlisted candidates fit and to construct the action plan. This is the same shortlist-then-reason pattern that appears in skill routing at scale, and it is the single largest available cost reduction in this workflow.

**Third, the executive brief is a scheduled batch job masquerading as an assistant.** Nobody is waiting on it. It should be generated off-peak, batched across all revenue leaders, and served on whatever hardware configuration maximizes throughput per dollar rather than minimizing time to first token. The interactive drill-down is the opposite: a human is clicking and waiting, so it needs low latency. Same product, two workloads, opposite serving requirements. This is the recurring lesson across all four demos and it is the most reusable one.

The reliability angle deserves flagging because computer use makes it acute. Creating a Slack channel is a mutable state action on an external system with no natural idempotency. A retried computer-use run that partially completed produces duplicate channels or duplicate member additions, both of which are visible to colleagues. This is precisely the overlapping-writers and missing-edge-proof failure pair described in the OpenAI harness talk the following day: the tool may report success while the channel did not appear, or may create it twice. An idempotency key and a verification step at the user-visible boundary are not optional for this class of action.

## Grounded Context (Web Enrichment)
**The product and the computer-use capability are both real and recently shipped.** OpenAI launched ChatGPT Work in July 2026 with the global rollout of GPT-5.6, as an agentic mode that performs actions autonomously across connected applications, files, web tools, desktops, and recurring workflows, decomposing larger goals into subtasks over extended timeframes. OpenAI has separately confirmed it is bringing browser-based agentic capabilities into ChatGPT and Codex, which is the computer-use mechanism shown here.

**The approval boundary is platform behaviour.** ChatGPT Work asks a human for approval before carrying out sensitive actions, and organizations control access to browser use, plugins, and connected tools via ChatGPT Enterprise controls. The held-for-review Slack message is consistent with this. Note that this makes the asymmetry in the demo more interesting rather than less: if the platform can gate sensitive actions, the choice to gate the message but not visibly gate the channel creation reflects a judgment about which action is sensitive, and reasonable people would disagree.

**Native connector support exists, which sharpens the computer-use critique.** Workspace Agents plug into Slack, Salesforce, and 60-plus enterprise apps. So Slack is a supported connector. Using computer use to create a Slack channel when a Slack connector exists is either a demo choice to showcase the capability, or an indication that the connector's action surface is narrower than its read surface. Either way it reinforces the point that computer use should be reserved for gaps in API coverage.

**The unexamined claim is the forecast quality itself.** Every one of these demos shows outputs and none shows accuracy. For a forecast product specifically, the only metric that matters is calibration: does the system's stated confidence match realized outcomes? A forecast tool that produces well-formatted, well-cited, confidently-stated wrong numbers is worse than no tool, because it launders uncertainty. The Nubank simulation talk from the same conference demonstrates what a defensible enterprise quality claim looks like, with sim-to-real correlation and 80% expert label agreement. Against that standard this is a capability demonstration.

## Real-World Application / Actionable Step
1. **Audit any agentic workflow for computer use where an API exists, and eliminate it.** This is the highest-value action from this demo. The screenshot-reason-act-verify loop carries high-resolution images through prefill on every iteration with an unbounded iteration count, and it costs orders of magnitude more than an equivalent API call for an identical outcome. Reserve computer use strictly for systems with no programmatic interface. Where it is unavoidable, cap iterations and measure cost per completed action so the expense is visible.
2. **Decompose look-alike and similarity analysis into cheap retrieval followed by expensive explanation.** Do not ask a frontier model to find matches across a corpus. Use embeddings and structured filters to shortlist, then spend the expensive model only on justifying the shortlist and building the plan. This is the same shortlist-then-reason architecture that skill routing converges on past ten skills, and it is the largest single cost reduction available in this workflow.
3. **Schedule the executive brief as an off-peak batch job and serve the drill-down interactively.** Nobody waits on a periodic brief, and everyone waits on a click. Two serving configurations, one product. Generating scheduled reports on a latency-optimized tier is a pure waste, and it is the default because the whole thing sits behind one API.
4. **Require an idempotency key and a user-visible verification step for every computer-use action with organizational side effects.** Channel creation and member addition have no natural idempotency, are visible to colleagues, and are awkward to reverse. A partially completed retried run produces duplicates. Verify at the boundary the user actually sees, which for Slack means confirming the channel exists with the expected members, not that the tool returned success.
5. **Insist on calibration, not accuracy, when evaluating any forecast-intelligence tool.** The failure mode is confident wrongness dressed in citations. Track whether stated confidence matches realized outcomes over a quarter. A well-formatted forecast that is systematically overconfident is more damaging than a rough one, because it removes the human skepticism that would otherwise apply.
