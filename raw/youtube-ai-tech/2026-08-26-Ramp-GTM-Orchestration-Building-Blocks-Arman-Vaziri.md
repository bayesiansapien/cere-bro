# The Building Blocks of GTM Orchestration (Arman Vaziri, Ramp)

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=VjEP0xqTUI0

## TL;DR
Ramp's end state is describing a go-to-market motion in natural language and having it fan out across every channel automatically. Vaziri's argument is that you cannot start there. You build vertical solutions on a shared foundation (an internal customer data platform, Temporal-backed durable agent threads, a vector knowledge layer, a user-editable skill library), then stitch them into horizontal orchestration. The concrete shipped example is nightly pre-meeting briefs for account managers. The clever organizational move is exposing the exact same tools to employees via an internal "GT MCP," which turns every employee's ad hoc automation into a product requirements document the platform team can productionize.

## Key Takeaways
- **The bottleneck was never ideas, it was everything downstream of them.** Pulling an audience, generating copy and creative, and convincing humans to follow a new playbook. The goal is reducing coordination cost, which is why orchestration, not generation, is the framing.
- **They built an internal CDP and are unapologetic about it.** CRM data, product data, enrichment, web data, buying signals (both internally modeled propensity scores and external events like funding announcements), plus interaction data: emails, meetings, calls, page views.
- **Postgres for transactional guarantees, not a warehouse.** The online layer is Postgres specifically for referential integrity across entities that come from CRM, product, and third parties, plus provenance metadata (where did this come from, when did it arrive). Attribution to the correct entity level is called out as a genuinely hard problem.
- **Entity resolution is the sneaky hard part.** At Ramp the same email can act on behalf of multiple businesses, so mapping meeting attendees to accounts is a fuzzy match. They compute it once and persist it so no downstream consumer recomputes it.
- **Solve one team, then mirror horizontally.** Outbound and meeting prep generalize across teams. QBR generation does not. Extending to a new team is mostly an exercise in new skills, new data integrations, and new ingestion, while embeddings and custom instructions carry over unchanged.
- **User-authored skills drove adoption.** Different account managers want different brief formats. Letting them express that in text, consumed by the agent, is what got people to actually use it.
- **GT MCP as a compounding feedback loop.** Employees get the same tools the background agents use. When someone builds their own automation against it, they have implicitly told the platform team what problem they have and how they want it solved, and handed over the prompts and skills. Ramp then productionizes and redistributes.
- **Advice for small teams:** three years ago it was two people using GPT-3.5 for personalized outbound copy. Do not spend a year designing the perfect architecture. Build narrow vertical solutions and glue them together later.

## Architecture & Optimization Mechanics
- **Durable threads with tool calls and model calls as Temporal activities.** This is the important design decision. Each LLM call and tool call is an activity, so a worker crash resumes with accumulated state rather than replaying the whole thread. Replaying an agent trajectory from scratch is not just slow, it re-pays every prefill and every tool-call token, so durability here is a direct cost optimization, not only a reliability one.
- **Config-scoped tool grants.** Different agents get different tool sets, integrations, and skills from configuration rather than code. Same capability-scoping pattern Exa and Cloudflare arrived at independently.
- **Hybrid retrieval to keep context small.** Transcripts, emails, enablement material, product knowledge, and playbooks are chunked, embedded, and stored in turbopuffer, then queried with a combination of vector, attribute, and keyword search, scoped to a single account. Vaziri is explicit about why: pulling the raw corpus into agent context would be inefficient and expensive. Attribute filtering before vector search is the cheap part that most implementations skip.
- **Batch fan-out for background work.** Nightly, they fan out one agent per account to precompute meeting prep. Moving inference off the interactive path entirely is the most underrated latency optimization available: the user's perceived latency is a database read.
- **Online API batch jobs for TAM-wide enrichment.** Ramp's addressable market is effectively the entire US, so enrichment is pre-computed and pre-ingested rather than fetched on demand.
- **Multi-armed bandit framing for campaign selection.** Vaziri explicitly names explore-versus-exploit as the balance the orchestration layer must strike across candidate campaigns, with guardrails for compliance, rules of engagement, and not repeating the same action.

## Grounded Context (Web Enrichment)
The stack Vaziri describes is now a recognizable industry pattern rather than a Ramp idiosyncrasy. Cross-company analyses of growth-stage teams building GTM agents in-house converge on the same four layers he names: a customer data platform, durable execution, a vector knowledge layer, and a skill library. The durability point in particular has hardened into procurement language, with 2026 enterprise agent rollouts reportedly demanding durable-by-default execution. Ramp's public job postings corroborate the specifics, listing Modal, turbopuffer, the OpenAI Agent SDK, and Temporal, and describe Ramp Revenue as powered by a CDP processing millions of records daily. The turbopuffer choice is also not unique: Vercel indexes its entire GTM memory, every Gong call, Slack thread, and email chain, on turbopuffer organized by Salesforce account, which is nearly identical to Ramp's design.

One thing to weigh honestly: Vaziri presents the golf-balls-to-East-Coast-construction-golfers orchestration as the destination, and admits it is not yet shipped. Everything demonstrated is vertical. The horizontal intent-to-multichannel step is the unproven part, and it is unproven for a reason: it requires the audience definition, creative generation, compliance rules, and channel-specific execution to all be correct simultaneously, with a human sign-off gate per channel. Treat the vertical building blocks as the validated lesson and the orchestration vision as a roadmap.

## Real-World Application / Actionable Step
- **Model each LLM call as a resumable activity, not a step in a loop.** For long agent trajectories in Amit's own tooling, a crash at step 12 that replays steps 1 through 11 re-pays every prefill token. Temporal, or any durable execution engine, converts that into a state restore. This is the single most transferable engineering idea in the talk and it shows up as a line-item cost reduction.
- **Filter by attribute before you search by vector.** Ramp scopes retrieval to one account before doing semantic search. In a RAG or memory system, applying cheap metadata predicates first shrinks the candidate set by orders of magnitude, which cuts both vector-search compute and the number of chunks that end up in context. Free accuracy and free cost savings.
- **Move inference off the interactive path wherever the trigger is predictable.** Nightly precompute per entity is the pattern. Anywhere a routing or scoring decision depends only on slow-moving state, compute it in batch and serve it from a key-value store.
- **Build the internal MCP that exposes your own tools to colleagues.** The GT MCP trick generalizes: expose the model-serving, eval, and profiling tools Amit's team owns through one MCP endpoint, and the automations colleagues build against it become a free prioritized backlog with working prototypes attached.
- **Persist entity resolution once.** If anything in the pipeline fuzzy-matches identifiers, compute and store the mapping rather than letting every consumer redo it.
