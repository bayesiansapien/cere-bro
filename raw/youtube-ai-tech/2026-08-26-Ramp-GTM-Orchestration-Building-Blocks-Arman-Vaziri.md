# The Building Blocks of GTM Orchestration | Arman Vaziri, Ramp

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=VjEP0xqTUI0

## TL;DR
Ramp's end goal is intent-to-execution: describe a motion in a sentence ("offer Pro V1 golf balls to golfers at East Coast construction companies") and have the system spin up the audience, the incentive, the outbound sequences, the ad creative, the landing page, and the in-app nudges, with channel owners only signing off. Getting there required building bottom-up: an in-house customer data platform on Postgres with Kafka ingest and reverse ETL from Snowflake and dbt, a Temporal-based durable execution layer where every tool call and model call is an activity, a hybrid retrieval layer on Turbopuffer over the unstructured corpus, and a user-editable skill library. The strategy is deliberately vertical-first: solve one team's problem completely, then mirror the pattern horizontally.

## Key Takeaways
- **Postgres is the online serving store, chosen for transactional guarantees.** Vaziri is explicit that referential integrity between entities across CRM, product, and third-party sources plus full provenance metadata (where did this come from, when did it arrive) is the reason for a relational online store rather than a key-value one. Contrast this with Notion, which chose DynamoDB for the same layer and accepted denormalization instead.
- **Durable threads, not durable workflows.** Every agent run is a Temporal thread with each tool call and each model call as a separate activity. A worker dying resumes from the last activity with accumulated state intact, rather than replaying the thread from the beginning, which Vaziri notes would be prohibitively slow and expensive. Temporal also supplies config-scoped tool access per agent and human-in-the-loop pause-input-resume.
- **Hybrid retrieval scoped by attribute, specifically to keep context small.** Transcripts, emails, enablement material, product knowledge, and playbooks are chunked, embedded, and stored in Turbopuffer, then queried with a combination of vector, attribute, and keyword search scoped to a single account. The stated reason is explicit: pulling the raw corpus into agent context would be very inefficient and very expensive.
- **Entity resolution is the sneaky-hard problem.** Mapping meeting attendee emails and titles back to accounts is a fuzzy match at Ramp because one email can act on behalf of multiple businesses. The fix is to resolve once and persist, so no downstream consumer recomputes it.
- **Skills are how you buy adoption.** Different account managers want different brief formats and different fields. Letting users express that in plain text and having the agent honor it is what Vaziri credits for adoption, more than raw output quality.
- **GT MCP federates the same tools to humans.** Employees get a window onto the exact tool set the background agents use, so anyone can build their own automation. The compounding effect is that every user-built automation is a labeled problem statement plus a working prototype, which the platform team then productionizes and distributes.
- **The background agent shape:** nightly fan-out, one agent per account, each with access to the online CDP, the vector store, system-level skills, and user custom instructions.
- **Advice for small teams:** three years ago this was two people using GPT-3.5 for personalized outbound copy. Do not spend a year building the perfect architecture, piece together vertical solutions and connect them later.

## Architecture & Optimization Mechanics
The most useful thing in this talk for Amit is the explicit cost reasoning behind two decisions, because both are context-budget decisions dressed as data engineering.

First, activity-level durability. Representing each model call as a Temporal activity means a failure costs one call, not a whole thread. For long-horizon agents, replay-from-scratch is a quadratic cost disaster: a thread with N model calls that fails at step N and replays pays roughly N-squared-over-2 tokens across retries. Checkpointing at the activity boundary makes it linear. This is the same reasoning as gradient checkpointing, trading storage of intermediate state for avoided recomputation, and it is the correct default for any multi-step agent Amit builds.

Second, attribute-scoped hybrid retrieval. Vaziri's stated goal is to avoid pulling the full corpus into context. The three-way combination matters: vector search gives semantic recall, keyword search catches exact identifiers that embeddings blur (product names, error codes, contract terms), and attribute filtering (account ID) prunes the candidate set before either runs. Pre-filtering by attribute is the cheap win and it is frequently skipped. It reduces the vector search space by orders of magnitude and it makes recall@k far higher at the same k, which directly means fewer tokens in context for the same answer quality.

The Postgres-versus-DynamoDB divergence between Ramp and Notion is worth reflecting on. Both serve agent context at low latency. Notion optimized for a single-key millisecond fetch with no joins and accepted denormalization drift. Ramp optimized for referential integrity and provenance and accepted join cost. The right answer depends on whether your agents need to reason across entities (Ramp: attribution to the right level of detail) or just need one entity's full profile (Notion). Amit should note that provenance metadata is the load-bearing difference. Without it you cannot debug why an agent said something, which is the same problem as untraceable retrieval in RAG evaluation.

The closing note on multi-armed bandits is a genuine research hook. Vaziri frames campaign selection as explore-versus-exploit across candidate motions. That is structurally identical to routing across model candidates under uncertainty, and the bandit literature (Thompson sampling, UCB) is directly importable into router design where the reward is quality-per-dollar and the arms are model-plus-config pairs.

## Grounded Context (Web Enrichment)
Ramp's numbers are now published and they are the strongest in this track. Between December 2025 and March 2026 Ramp reported a 250% increase in lead-to-qualified-opportunity conversion, 3x more pipeline dollars, roughly 40 hours per month reclaimed per rep, 50% daily and 86% weekly active usage across the sales team, and a 97% increase in follow-up with lower-intent leads. Independent reporting confirms the architecture claim, Ramp built its own CDP rather than buying one and it processes millions of records daily as the substrate the agents sit on. The pattern generalizes: Vercel independently built its retrieval layer on Turbopuffer indexed per Salesforce account, the same design choice Vaziri describes, which suggests account-scoped hybrid retrieval is converging as the standard shape rather than being a Ramp quirk.

Temporal has since productized what Ramp hand-rolled. The Temporal Agent Harness, released as an early look in 2026, brings durable execution, tool-call approvals, and typed interfaces to production agents, meaning the activity-per-model-call pattern is now off-the-shelf rather than bespoke. The broader durable-agent category (Temporal, Inngest, DBOS, Restate) hardened over the same window.

One honest caveat on the metrics. The 97% lift in follow-up with lower-intent leads is the most credible number here because it measures behavior the system directly causes. The 250% conversion lift spans a four-month window during which Ramp was also growing and hiring, and no holdout is mentioned, so attribution to the agent platform alone is not established. Treat it as strong directional evidence, not a controlled result.

## Real-World Application / Actionable Step
- **Checkpoint at the model-call boundary in every multi-step agent.** Compute the replay cost of Amit's current agentic pipelines: tokens re-paid on retry, times observed failure rate. If any pipeline replays from the start, activity-level durability is a straight token saving with no quality cost, and it is the single cheapest fix in this talk.
- **Add attribute pre-filtering before vector search everywhere.** For any retrieval Amit runs, filter by the obvious scoping key first, then embed-search the remainder. Measure recall@k before and after at fixed k. The context-token reduction at constant answer quality is the metric that matters.
- **Import bandit algorithms into router selection.** Vaziri's explore-exploit framing for campaigns is directly the routing problem. A Thompson-sampling router over model-config arms with quality-per-dollar reward is a concrete, well-founded design, and the bandit framing gives principled regret bounds that heuristic routers lack.
- **Log provenance on every retrieved chunk.** Ramp's source-and-timestamp metadata is what makes agent output debuggable. For Amit's own retrieval experiments, per-chunk provenance is what lets him attribute a wrong answer to bad retrieval versus bad generation, which is the distinction most RAG evaluations fail to make.
- **Federate the same tool surface to humans and background agents.** Ramp's GT MCP turns every user experiment into a spec plus prototype. Applied to Amit's team, exposing his benchmarking and quantization tooling as one MCP surface means colleagues' ad hoc scripts become a free backlog of validated use cases.
