# How to avoid disaster when vibe-coding a billing engine | Andrew Garvin, Stripe

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=mJqwmmOx4WA

## TL;DR
Garvin, a Metronome co-founder now inside Stripe following the acquisition, live-demos provisioning a Stripe account plus a Metronome billing instance through the Stripe Projects CLI, then instructs the agent in one plain-English sentence to "create a demo billing engine in Metronome mimicking the Lovable pricing model." It produces a working test environment with a customer, a credit object, synthetic usage flowing through the meter, and a draft invoice broken into build credits, plan mode credits, cloud credits, and AI gateway credits. The guardrails are the substance: an extensible library of portable skills files that encode how to use the Metronome API without hitting footguns, deliberately verbose error messages so the agent can self-correct, and a hard architectural boundary that this provisions a sandbox and is never pushed to production. His conceptual contribution is a three-way disambiguation of what "building for agents" means: agent as your product, agent as a buyer, and agent as your user.

## Key Takeaways
- **The three agent roles, and each implies a different engineering requirement.** *Agent as your product*: if the agent is what you sell and it runs up a token bill, you need usage metering to price it. *Agent as a buyer*: agents procuring your service, which is what Stripe Projects enables, and which requires your service to be discoverable and provisionable programmatically. *Agent as your user*: an agent operating your platform on behalf of a customer, which breaks seat-based pricing entirely.
- **The seat-to-credit migration is the most consequential business insight in the talk.** Garvin reports HubSpot is transforming from seat-based to credit-based pricing, starting in EMEA with dramatically lowered seat prices plus a credit component. The reasoning is precise: in a world where one agent can operate the whole system, charging per human seat captures none of the value, because all the value accrues to a single "user" who is an agent. He calls this headlessness, and notes Salesforce and others have discussed it while Metronome is seeing it in the billing data now.
- **Skills files as a vendor-shipped safety layer.** Metronome is a deep, complicated product with many footguns. Their investment is an extensible, portable, easy-to-install set of skills files that give the agent enough context to use the API correctly. This is the vendor side of the same pattern Christopher Burns described from the open-source side at the same conference: put the operating knowledge where the agent will actually read it.
- **Verbose errors as an agentic design requirement, not a developer nicety.** Their developer experience team actively hunts failure cases specifically to make errors clear enough that the agent self-corrects rather than escalating. Garvin's framing is that this is nothing new from a DX standpoint, but the payoff has changed.
- **The explicit non-goal is full autonomy, and this is the most responsible position in the whole conference track.** Billing is business-critical with deep business logic, so the stated product intent is to use the coding agent to accelerate reaching a tested state, not to ship to production. The demo provisions a sandbox by design.
- **The skills files direct the agent to flow synthetic usage into the platform,** because in billing, "did it set up correctly" is not answerable by seeing a contract or a provisioned customer. You have to see metered usage produce an invoice. That is a genuinely thoughtful definition of what testing means in this domain.
- **Agent-driven runaway spend is the failure mode they are now designing against.** Garvin says the impact of billing failures has grown in importance over the last six months specifically because agents can run away with spend, and the control they are building toward is per-agent wallets with spending limits that customers can offer to their own users.
- **Enterprise usage-based pricing is converging on cloud-provider structures.** Coding-agent companies (he names Cognition, Cursor, OpenAI, Anthropic) are adopting prepaid and postpaid commitment structures of the kind CSPs have used for a decade, layered on top of the prepaid-credit auto-recharge model that OpenAI popularised through Metronome.
- **Two demand signals he reports from Stripe's internal data:** Stripe CLI usage has increased exponentially over the past five to six months, and there is an exponential increase both in new business formation and in customers reaching Stripe and Metronome through coding agents.

## Architecture & Optimization Mechanics
The technically interesting content here is not the demo, it is the two-layer guardrail design and what it says about making a complex API agent-safe.

Layer one is skills files, which encode procedural knowledge about correct API usage before the agent acts. Layer two is verbose errors, which provide recovery information after it acts wrongly. These are complements with different cost profiles. Skills files are a fixed context cost paid on every invocation and they prevent errors. Verbose errors cost nothing until a failure occurs but each recovery burns a full round trip, which Stephanie Jarmak quantified in her Sourcegraph talk as an entire wasted turn. So the optimal split is determined by error frequency: high-frequency footguns belong in the skills file, rare ones belong in the error message. That is a concrete, measurable design decision, and Garvin's team is effectively doing the measurement by hunting failure cases.

The sandbox boundary deserves more credit than it gets. Every talk in this track wrestles with agent autonomy, and Garvin gives the cleanest decision rule available: agent autonomy scales inversely with the cost and irreversibility of a wrong action. Billing errors are financially quantifiable, customer-visible, and awkward to reverse, so the agent's territory ends at the sandbox boundary. Contrast this with coding agents, where a bad PR costs review time and is trivially discarded, which is precisely why code was the first domain to reach practical asynchronous autonomy. Combined with Varun Shenoy's autonomy ladder from the same conference, the synthesis is a two-factor rule: how good is your verifier, and how expensive is an unverified mistake. Code scores well on both. Billing scores well on the first and terribly on the second.

The synthetic-usage-injection detail is the sharpest engineering insight in the talk. For a metering system, correct configuration is only observable through the metering pipeline end to end, so the skills file instructs the agent to generate the traffic that exercises it. Generalised: the agent's verification step must exercise the same data path as production, not merely assert that configuration objects exist. For Amit's work the direct analogue is that a quantized model checkpoint loading successfully verifies nothing. The verification has to push representative tokens through the serving stack and compare outputs, because the failure modes of quantization live in the numerics of the forward pass and not in the artefact's structure.

The seat-to-credit argument also has a direct bearing on Amit's routing work. If enterprise software is migrating to credit-based pricing because agents rather than humans are the users, then every enterprise buyer acquires a direct financial interest in token efficiency for the first time. Under seat pricing, an inefficient agent costs the vendor. Under credit pricing, it costs the customer, who can now measure it and will now shop on it. That converts inference efficiency from a vendor-side margin concern into a customer-visible purchasing criterion, which is a substantially better position from which to argue for routing and compression investment.

## Grounded Context (Web Enrichment)
The acquisition and product claims all check out, and the public record adds the technical reason the deal happened.

Stripe acquired Metronome for a reported roughly $1 billion, completing the transaction on January 13, 2026. Metronome's metering engine was already in use by OpenAI, Anthropic, and Nvidia, which substantiates Garvin's claim about metering the frontier labs' API calls from before those companies had revenue. The most illuminating detail in the coverage is the capacity gap that made building in-house untenable: Stripe Billing maxes out at roughly 1,000 events per second while modern AI companies need 100,000-plus. That is a two-orders-of-magnitude architectural difference, and it explains why Stripe bought rather than built. It is also a useful data point on how different AI-workload telemetry volumes are from traditional SaaS.

Stripe Projects is real and has expanded considerably since the demo. It provisions and manages services from the CLI (hosting, databases, auth, AI) with credential generation and billing management, explicitly designed so that AI agents can drive it, without dashboards, config files, or infrastructure code. It has since added 16 new providers for a total of 49, including Metronome for usage-based billing, Wix for storefronts, and ClickHouse for LLM observability, plus new agent integrations and custom developer controls. Garvin's mention of Vercel and Hugging Face onboarding is consistent with that expansion, and Stripe Projects is itself published as an agent skill in skills libraries, which is a neat confirmation of the skills-as-distribution pattern.

On HubSpot, the direction is confirmed and the specifics are softer than Garvin states. HubSpot does now operate a hybrid model: products are purchased through Seats granting individual feature access, with HubSpot Credits purchasable for additional capacity on certain features. Credits are bundled by tier (500 on Starter, 3,000 on Professional, 5,000 on Enterprise) and power AI features, with additional credits at roughly a cent each. So the credit layer exists and it is specifically attached to AI consumption. The stronger claim, that HubSpot is transforming its entire business from seats to credits with dramatically lowered seat prices beginning in EMEA, is not confirmed in public pricing documentation. Treat the hybrid model as fact and the wholesale replacement of seats as Garvin's forward-looking read from inside the billing data, which is privileged information but is also a claim that serves Metronome's commercial interest.

Two things to note about the framing. First, this is a vendor demo by an acquired founder presenting his own product inside his acquirer's ecosystem, and the live demo failed twice on stage before working, which is worth remembering when evaluating the frictionlessness claim. Second, and to Garvin's credit, the talk's actual thesis undercuts the usual vendor pitch: the title promises how to vibe-code a billing engine and the content argues you should not put a vibe-coded billing engine anywhere near production. That is an honest inversion.

## Real-World Application / Actionable Step
- **Adopt the two-factor autonomy rule and write it down for each system Amit owns.** Verifier quality on one axis, cost of an unverified error on the other. Only systems scoring well on both belong on the long-running autonomous rung. This is the cleanest synthesis available from this conference and it takes ten minutes to apply.
- **Make agent verification exercise the production data path, not the artefact.** Garvin's skills files inject synthetic usage because configuration alone proves nothing. For Amit, the equivalent rule: a quantization or pruning run is not verified until representative tokens have flowed through the actual serving stack and outputs have been compared against a reference. Structural checks on the checkpoint are not verification.
- **Split guardrails by error frequency, and measure to decide.** Frequent footguns go into the skills file as a fixed context cost that prevents them. Rare ones go into error messages, where recovery costs a round trip but nothing is paid up front. Instrument first-attempt success rate per operation to find the boundary.
- **Use the seat-to-credit shift as the strongest available business argument for routing work.** Once customers pay per token rather than per seat, inference efficiency becomes a customer-visible purchasing criterion rather than a vendor-internal margin question. That reframes Amit's routing and compression work from cost reduction to competitive differentiation, which is a materially better pitch.
- **Note the 1,000 versus 100,000 events-per-second gap as a general lesson about AI-workload telemetry.** Metering and observability systems designed for traditional SaaS are off by two orders of magnitude for AI workloads. Anyone building measurement infrastructure for inference should size for that gap from the start rather than discovering it, and it is a useful concrete number when arguing for observability budget.
- **Build per-agent spend limits before you need them.** Garvin identifies runaway agent spend as the failure mode that grew in importance over six months, and per-agent wallets with hard caps as the control. For any agentic system Amit deploys, a per-agent token budget enforced at the gateway is cheap to add early and painful to retrofit after an incident.
