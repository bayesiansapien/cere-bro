# Building Turbopuffer: Gergely Orosz x Simon Eskildsen

**Channel:** AI Engineer
**Published:** 2026-08-03
**Source:** https://www.youtube.com/watch?v=jQDXzEVHMSE

## TL;DR
Simon Eskildsen's path from PowerPoint hyperlinks to running the vector database behind Cursor and Notion, with the through-line being one habit: refusing to accept a benchmark that contradicts first-principles arithmetic. He maintained a public table of hardware constants (DRAM bandwidth, S3 round-trip cost and latency, NVMe throughput, cost per GB across storage tiers) and drilled them as flashcards, then used them to argue that a query taking 10 seconds should take 10 milliseconds and that someone was measuring the wrong thing. Turbopuffer exists because that arithmetic said vectors could live on S3 for roughly $1 per million instead of $100. The most operationally interesting current signal: CPUs are now scarce, because reinforcement learning environments and agents consume enormous general-purpose compute, and Turbopuffer competes for allocation against its own customers.

## Key Takeaways
- **Napkin math is the actual methodology, not a metaphor.** Roughly 50 hardware constants maintained on GitHub with a script that regenerates them, memorised via flashcards. The purpose is adversarial: when a team says database A is slow, compute what it should cost and find out whether the model or the benchmark is wrong.
- **The worked example is the whole discipline.** Three search terms, each with a known matching document count, becomes a known number of megabytes to intersect, against roughly 100 GB/s of multi-core DRAM bandwidth, which predicts about 10 milliseconds. A 10-second measurement means either a gap in understanding or a benchmark that was accidentally distributed across a hundred nodes with an unbounded P99.
- **The fsync puzzle is the best illustration of the method.** An fsync takes about a millisecond, so MySQL should do 1,000 writes per second, but a small box does 10,000. The answer is batching at the 4K page level, found via BPF tracing and reading source. The point is that the discrepancy is the signal, and chasing it is how the model improves.
- **Design for P99, not P50, when building on object storage.** P99 for a 256 to 512 KB S3 object is around 200 ms, and a single logical query traverses multiple tree levels, so you compound P99 several times per request. That makes minimising round trips the dominant architectural constraint, and Eskildsen argues you should design against P99.9.
- **The v1 architecture was deliberately trivial.** Cluster the vectors, write each cluster to a file, write a separate centroids file. Query by fetching centroids, then fetching the N nearest cluster files. Some cluster merging to control cost. No LSM implementation, no caching layer, just nginx as a reverse proxy caching S3 objects, with cache invalidation by shelling out to `rm -rf` against a reverse-engineered nginx directory layout. Shipped on a single 8-core GCP box.
- **"Anyone who has actually worked on databases internally would have had too much pride to ship that."** He shipped it as a SaaS-style MVP to find out whether anyone cared, while holding the invariants that mattered: all writes committed directly to object storage, no data loss if every VM dies.
- **Cursor was the first customer and the bill dropped 95%.** They found him after a Twitter launch, having independently reasoned that keeping all vectors in DRAM had broken unit economics and that active codebases should be hot in memory while everything else sits in object storage. He flew to San Francisco, diagnosed their unrelated Postgres autovacuum problem on the spot, and that credibility is what closed it.
- **CPUs, not GPUs, are the current constraint for this business.** RL training needs CPUs to run real environments (bash, tool use, search, compilation), agents run on CPUs, and demand keeps expanding as applications get more specific. Labs, clouds, and Turbopuffer's own customers are bidding for the same allocation, and it comes down to where the power is.
- **Portability across instance types is now a competitive advantage.** Turbopuffer runs on many SKUs rather than requiring one, currently favouring GCP C4, Z4D, and ARM C4A. Needing only CPUs, NVMe, and S3 is what makes that flexibility possible.
- **Six reasons to raise capital, stated plainly:** R&D, growth, founder ego, rewarding employees, strategic partnership, M&A. He names ego as common and dangerous because it dilutes employees and sets a price for future hires' upside. Turbopuffer raised for reason one, then reason four.

## Architecture & Optimization Mechanics
The core insight is a storage hierarchy argument that generalises well beyond vector search. Vectors are a large, cold, read-mostly dataset with extremely skewed access: at any moment a tiny fraction is hot. The industry default put all of it in DRAM, which prices the entire corpus at DRAM cost while using DRAM's latency advantage for a small fraction of it. Putting the cold tail on object storage at roughly 2 cents per GB versus roughly $2 per GB for memory is a hundredfold cost reduction on the bulk, and the entire engineering problem becomes hiding S3's latency for the hot fraction. That is a cache-hierarchy problem, and it is exactly the same shape as KV cache offloading, weight streaming for MoE experts, and paged attention. Eskildsen notes that Cursor's Aman was tweeting about S3 for KV caching early and that almost nobody does it, and that the economics say it will happen.

For MoE work the parallel is direct and worth taking seriously. Expert weights are a large read-mostly corpus with skewed activation, which is structurally identical to the vector-corpus problem. The reason nobody offloads experts to object storage is the 200 ms P99, but Turbopuffer's answer is not to make S3 fast, it is to restructure access so that the number of round trips is minimal and everything hot is cached locally on NVMe. The generalisable rule from the talk is that when building on high-latency durable storage, round-trip count is the design variable, because you compound the tail latency on every hop.

The CPU scarcity observation deserves attention independent of the rest. The mental model that GPUs are the bottleneck and CPUs are abundant is now wrong, and the reason is architectural: RL environments require real execution, not just tensor math, so CPU-to-GPU ratios are rising across the industry. For anyone planning capacity for RL-based work, budgeting CPU as an afterthought is a scheduling failure waiting to happen. The AVX-512 and SIMD enthusiasm is the flip side: a well-vectorised CPU implementation of similarity search is competitive enough that Turbopuffer built a business on it while declining to use GPUs at all.

## Grounded Context (Web Enrichment)
The numbers behind this story are more extreme than the conversational framing suggests. Turbopuffer was founded in 2023 and took less than $1 million from a single investor in early 2024 to prove product-market fit, matching Eskildsen's account of asking for roughly $700K. Sacra estimates roughly $100M annualised revenue by March 2026, up from $75M at end-2025, on a team of about 17 people, having operated profitably since that first small round. The formal seed round was announced in December 2025, which is the raise he describes as motivated by employee liquidity rather than capital need. Production scale is over 1 trillion documents, more than 10 million writes per second, and over 10,000 queries per second, with the 200 ms P99 figure and the 95% cost advantage over commercial vector databases both confirmed publicly. Customers beyond Cursor include Notion, Linear, Superhuman, and Suno.

The CPU scarcity claim is well corroborated and the mechanism is exactly as he describes it. SemiAnalysis documents that frontier labs are now bidding directly against cloud providers for commodity x86 servers, because RL training environments (code compilation, verification, tool execution running alongside the model) require large CPU clusters adjacent to GPU clusters. That demand source barely existed two years ago and now competes for the same Xeon and EPYC allocation. Server CPU prices have continued climbing through mid-2026 with further increases signalled, and CPU-to-GPU ratios are rising structurally rather than cyclically.

The DRAM constraint he mentions in passing is the more severe problem and he understates it. Data centres are forecast to consume roughly 70% of global memory chip production in 2026, DRAM supply growth is projected around 16% year over year against accelerating demand, and SK Hynix has warned the shortage may persist past 2030. That matters for the thesis: as DRAM gets scarcer and more expensive, the economic argument for object-storage-backed architectures strengthens rather than weakens. Turbopuffer's design is a hedge against exactly the supply condition now materialising.

One correction to the framing in the interview. Gergely's setup implies Cursor moved to Turbopuffer primarily for cost, and Eskildsen's own account is that reliability with the prior managed service was the stated pain point, with unit economics as the underlying motivation. Both were true, and the 95% reduction was a promise made before the software was good enough to deliver it, based on napkin math about what a better implementation should cost. The pricing was set from the arithmetic, then the engineering was done to meet the price.

## Real-World Application / Actionable Step
Build the napkin math table for Amit's own stack this week. Not the generic version, the specific one: HBM bandwidth per GPU SKU in use, PCIe and NVLink transfer rates, cost per GPU-hour on demand versus spot versus committed, tokens per second at a given batch size and context length, cost per million tokens by model tier. Roughly fifty numbers, memorised. The payoff is the ability to say in a meeting that a proposed routing change should save 40% and that a measurement showing 5% means the measurement is wrong, which is the exact move Eskildsen built a company from.

Apply the discipline immediately to one active question: for any inference or eval benchmark that has produced a surprising number recently, compute what it should be from first principles before accepting it. The Surge AI talk on benchmaxxing makes the same argument from the evaluation side, and the two together form a single habit. A benchmark that disagrees with arithmetic is information, and the default assumption should be that the benchmark is measuring something other than what it claims.

The architectural action is to price the storage hierarchy for whichever large read-mostly artifact dominates cost. If that is MoE expert weights, KV cache, or embedding corpora, compute the DRAM cost of the full set against the object-storage cost of the cold tail plus NVMe for the hot fraction. The hundredfold price gap between memory and object storage is large enough that it survives substantial inefficiency in the caching layer, and with DRAM supply constrained through the rest of the decade the gap is more likely to widen than close.
