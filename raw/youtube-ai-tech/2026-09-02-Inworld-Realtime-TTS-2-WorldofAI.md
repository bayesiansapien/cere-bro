# Stop Paying for ElevenLabs? NEW #1 Realtime AI Voice Inworld TTS-2

**Channel:** WorldofAI
**Published:** 2026-09-02
**Source:** https://www.youtube.com/watch?v=eHsuG3bPiJ8

## TL;DR
A launch-day sponsored walkthrough of Inworld's Realtime TTS-2 and TTS-2 Flash. The framing is that an isolated voice sample is never the point for live applications, so the three things that matter are delivery quality, live response behaviour, and cost at sustained volume. Four capabilities are demonstrated. Steering: a bracketed natural-language instruction at the start of the text changes delivery without changing the words ("speak slowly, calm and reassuring, with a brief smile at the end"). Non-verbal tags: a sigh or laugh renders as sound rather than being read as a word. Voice design: describe a voice in prose ("patient multilingual tutor, early thirties, warm mid-range tone, clear articulation, calm energy, lightly playful when encouraging") and generate it. Localize voice: adapt a created voice to speak natively in another language rather than carrying the original accent. The reviewer then has a coding agent build a browser-based live tutor from Inworld's published llms.txt, and demonstrates interruption handling, mid-conversation language switching, tone instruction, voice identity preservation across languages, and memory of the first sentence, all in one exchange.

## Key Takeaways
- **Steering via bracketed natural-language instruction is the interesting interface decision.** Delivery is controlled by prose in-band with the text rather than by a parameter API. Same words, different instruction, different performance. That is a considerably lower-friction control surface than SSML or numeric prosody parameters.
- **Non-verbal tags rendering as sound rather than as words is a small but real distinction,** and it is the kind of detail that separates a usable voice API from one that needs post-processing.
- **Voice design from a prose description, then localisation of that designed voice,** is the feature combination that matters for products serving multiple languages. Preserving perceived voice identity across languages without carrying the source accent is a specific and non-trivial capability.
- **The multi-capability single-exchange test is well designed and is the best part of the video.** One conversation exercising interruption, language switch, tone instruction, voice consistency across languages, and context retention. That is a far better evaluation than sequentially demonstrating features, because live voice agents fail at the interactions between capabilities rather than at individual ones.
- **The llms.txt integration path is the most transferable practical detail.** Inworld publishes an LLM-readable index of its official documentation, the reviewer hands that link plus an API key and a voice ID to a coding agent, and the agent scaffolds a working two-part application: a server holding credentials and creating the realtime session, and a browser handling microphone input, playback, and interruption signalling.
- **OpenAI Realtime compatibility is mentioned in passing and is commercially significant.** Inworld's documentation covers compatible core session and event shapes, so migrating from OpenAI Realtime means changing the endpoint and session setup while the structure stays familiar.
- **The pricing structure is volume-tiered rather than flat,** with the unit rate falling as commitment rises, which is the correct shape for a product where consumer sessions extend unpredictably.
- **The video is disclosed sponsored content from Inworld,** published the same day as the launch.

## Architecture & Optimization Mechanics
The latency figures are the substance here and they deserve careful interpretation, because time to first byte on a streaming TTS system is a different quantity from the latency numbers Amit works with on text generation.

Time to first byte measures how long until the first audio chunk is available. It does not measure total generation time, because audio streams and playback begins on the first chunk. That makes TTFB the correct metric for perceived responsiveness in conversation, and it also means the system only needs to sustain generation faster than real-time playback after the first chunk, which is a much weaker requirement than generating the whole utterance quickly. So a 25 millisecond TTFB and a sub-100 millisecond p99 are claims about pipeline startup, not about throughput, and both are the right thing to optimise for interactive voice.

The two-model split (a quality flagship at sub-100ms p99 and a speed variant at 25ms) is a clean instance of the routing problem Amit works on, applied to a modality where the tradeoff is unusually legible. The economics make the routing case obvious: Flash is roughly five times faster and roughly 40% cheaper at the entry tier. So the design question is which utterances need the flagship. The answer in a voice agent is almost certainly that acknowledgements, confirmations, and filler need Flash while substantive content needs quality, which is a per-utterance routing decision on a signal (utterance role) that is available before synthesis. That is a well-posed, cheaply-implementable routing policy with a directly measurable cost and latency win, and it is more tractable than routing text generation because the quality difference in short functional utterances is negligible.

The interruption requirement is the part that most changes system architecture and the video treats it as a feature rather than a constraint. Handling interruption means the server must be able to abandon in-flight generation on a client signal, which requires that generation be genuinely streaming and cancellable rather than batch-then-stream. Any TTS integration where the server generates the full utterance and then streams it will feel responsive on TTFB and behave terribly on interruption, because cancellation cannot reclaim work already done. This is the same distinction as continuous versus static batching in LLM serving: the interesting property is not throughput, it is the ability to admit and evict work mid-flight.

The llms.txt-to-working-app path is worth noting as an independent confirmation of the pattern three other talks in this corpus describe. Christopher Burns argued vendors should ship dense machine-readable docs because agents fetch rather than browse. Metronome ships skills files so agents can use a complex API without hitting footguns. Anna Spysz argued merchants must publish structured capability manifests. Inworld publishing an LLM-readable documentation index and a reviewer getting a working realtime app out of it in one pass is the same pattern working. For Amit, the actionable version is that any internal API or tooling he wants agents to use should ship an equivalent index, because the difference between an agent guessing at an API and reading its reference is the difference between a working integration and a plausible-looking broken one.

## Grounded Context (Web Enrichment)
The launch is real, dated to the day of the video, and three of the reviewer's numbers need correction, all in the direction of the actual product being better specified than described.

Inworld launched Realtime TTS-2 and TTS-2 Flash on September 2, 2026, the same day as this video, pairing expressive voice control with fast response and pricing aimed at consumer AI products at scale. So this is launch-day sponsored coverage.

**Correction one, on Flash latency.** The video says 20 milliseconds. Inworld's published figure is 25 milliseconds time to first byte, measured in Coval benchmarking. That is a third-party benchmark reference rather than a self-reported number, which is worth more than the video's version.

**Correction two, on flagship latency.** The video says "around 100 ms time to first byte" for TTS-2. The published claim is latency under 100 milliseconds at the 99th percentile, which is a materially stronger statement, since a p99 bound is far more useful for a production voice agent than an average.

**Correction three, on pricing, and this one matters.** The video states TTS-2 starts at $25 per million characters on demand, $15 on the $300 monthly tier, $12.50 on the $1,500 tier, and as low as $5 with custom pricing. Inworld's published figures for **Flash** are that it starts at $15 per million and falls to $7. The video appears to conflate the two models' pricing tables. Anyone sizing a deployment should read the pricing page per model rather than relying on the video's numbers, and the practical point stands regardless: Flash is both faster and cheaper, so the flagship needs to earn its place on quality alone.

**On the ElevenLabs comparison in the title, which the video never actually makes.** The available comparison is that Inworld supports 200-plus languages against ElevenLabs' 70-plus on v3, while ElevenLabs has a larger voice library, and that the choice depends on whether realtime latency and steering matter more than language breadth and voice selection. Note that this comparison comes from Inworld's own resource pages, so it is vendor-authored. The video's title promises a displacement of ElevenLabs and the content contains no ElevenLabs pricing, no quality comparison, and no side-by-side test. That is a title-content gap worth naming: the product may well be better for realtime use cases, and this video provides no evidence either way.

Two further notes on the source. The reviewer's demonstrations are single-run, unscripted-sounding but selected, and the audio quality of the samples cannot be assessed through a YouTube transcript. And the channel monetises through sponsorship, a newsletter, Discord, a second channel, and its own vibe-coding platform, with the sponsorship disclosed here.

## Real-World Application / Actionable Step
- **Route by utterance role in any voice agent, and this is the immediately actionable design.** Flash at 25ms and roughly $7 to $15 per million characters for acknowledgements, confirmations, and filler; flagship for substantive content. The routing signal (what kind of utterance this is) is known before synthesis, which makes this the easiest routing policy Amit will encounter, with a five-fold latency win and a real cost win on the majority of utterances.
- **Verify that any TTS integration supports genuine mid-flight cancellation, not just streaming.** Interruption handling is the requirement that determines whether a voice agent feels conversational, and it demands cancellable streaming generation rather than batch-then-stream. Test it explicitly by interrupting mid-utterance and measuring how long audio continues.
- **Read TTFB as a pipeline-startup metric, not a throughput metric.** Sub-100ms p99 TTFB plus faster-than-realtime sustained generation is the actual requirement for interactive voice, and it is a weaker requirement than it sounds. Do not conflate it with the end-to-end latency figures used for text generation.
- **Publish an LLM-readable documentation index for anything Amit wants agents to integrate with.** Four independent sources in this corpus converge on this, and the demonstration here is the cleanest: a link to an llms.txt plus a key plus an ID produced a working realtime application in one agent pass. For internal benchmarking and quantization tooling, this is a small investment with a large effect on whether agents can use it correctly.
- **Read the per-model pricing page rather than the video's figures.** The video conflates flagship and Flash pricing. Flash is published at $15 falling to $7 per million characters, and the tiering means unit economics depend on committed volume, so the entry rate is the wrong number for a sizing exercise.
- **Discount the title.** "Stop Paying for ElevenLabs" is asserted and never tested. The verifiable differentiators are 200-plus versus 70-plus language support and realtime-first latency with natural-language steering, against ElevenLabs' larger voice library, and that comparison is authored by Inworld. If this matters for a real decision, run both on your own utterances and measure TTFB, interruption behaviour, and cost at your actual volume.
