# The Death of Developer Advocates | Stephanie Jarmak, Sourcegraph

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=Lrw0jqBNaw0

## TL;DR
Jarmak, an astronomer turned research scientist turned "agent advocate," argues developer relations is not dead but its audience has changed: the agent is now simultaneously a user of your tool and a recommender of your tool. She measures both sides empirically. On the user side she built CodeScaleBench, running agents with and without Sourcegraph's code-navigation MCP across hundreds of real software lifecycle tasks and mining thousands of traces for friction. On the recommender side she ran a generative engine optimization study and found a sharp gap: when prompts read like active tool shopping, Sourcegraph appeared 65% of the time, but when prompts described the actual pain ("we keep breaking downstream services when we change shared libraries because we can't see all the consumers"), it appeared zero times. Her framing is the curb cut: build for the agent and the human path clears too.

## Key Takeaways
- **Tool descriptions must fight the model's training-data priors.** In one trace, the model assumed a parameter named `read_line` because that matched its priors, when the tool actually expected `start_line`, and nothing in the description contradicted the assumption. It recovered because the error message explained the failure, but it burned an entire turn doing so. Good error messages salvage the turn, correct descriptions prevent it.
- **Agents are now evaluated on token cost and latency, not just correctness.** Jarmak states plainly that organizations assessing a tool will ask how many tokens the agent burns using it and how fast it is. That makes token efficiency a product requirement for anything exposing an MCP surface.
- **The GEO gap is between shopping intent and pain intent.** 65% mention rate on comparative shopping prompts, 0% on pain-description prompts. The hypothesis is that public messaging does not attribute pains and use cases explicitly enough for the model to make the connection, and the fix is a content campaign with measurable lift.
- **Newer models can get worse for you, not better.** Re-running the study on Claude Sonnet 4.6 thinking versus Sonnet 4, she found the newer model pitched Cody (a deprecated older Sourcegraph product) even more, because stale model output has been compounding across the internet and feeding back into training. You have to bury your own historical noise with current signal.
- **Practical GEO levers:** authoritative machine-readable sources (llms.txt), current examples the model can quote, up-to-date content even if the product has not changed (freshness feeds relevance algorithms), charts and FAQs, presence in MCP registries and marketplaces, and minimal friction from discovery to adoption. An agent will not recommend a tool that requires three demos and a sales email.
- **Different credibility standards for humans and agents.** Do not push AI slop at human developers, everyone recognizes it. But models exhibit a bias toward their own output style, so agent-facing content can be as structured and formulaic as it likes.
- **Non-engineers are now a real ICP.** Jarmak had zero GitHub commits last year and 12,000 this year, and now maintains a multi-agent orchestration framework. Anyone with agents can use developer tools.
- **Three role flavors:** engineering (build the MCP interface, evals, instrumentation), product (own the end-to-end agentic experience and agent-experience rubrics), marketing (own pipeline generation through agent recommendation).

## Architecture & Optimization Mechanics
The `read_line` versus `start_line` finding is the most technically useful item here and it generalizes far beyond devrel. The model's parameter guess is drawn from its training distribution, so a tool schema that deviates from the most common convention in the training corpus imposes a hidden per-call error rate. This is an alignment-to-prior problem, and it means tool design has a measurable optimization objective: name parameters the way the corpus already names them, or pay a wasted turn on some fraction of calls. A wasted turn is not a small cost, it is a full round trip plus the failed call's input tokens plus the error's tokens plus the retry's input tokens, all of which re-prefill context.

The corollary Amit should take seriously is that tool schema design is a legitimate token-efficiency lever, and it is measurable exactly the way Jarmak measures it. Instrument tool-call traces, count first-attempt success rate per tool, and rank tools by wasted turns per thousand calls. That ranking is a prioritized work queue, and each fix is a one-line schema or description change with a durable payoff across every future call.

The CodeScaleBench methodology (same tasks, agent with and without the MCP tool, thousands of traces) is the correct experimental design for evaluating any retrieval augmentation, and it is the design most tool vendors skip in favor of cherry-picked demos. The measured outcomes are worth committing to memory because they quantify what good retrieval buys an agent, and the mechanism is context efficiency: better retrieval means fewer speculative file reads, fewer retries, and less irrelevant content occupying the window.

The compounding-stale-output finding is a genuinely uncomfortable result with implications past marketing. If deprecated information about a product propagates into the corpus and then into the next model generation, the same dynamic applies to deprecated APIs, superseded benchmark numbers, and obsolete optimization advice. Model upgrades do not monotonically improve factual currency about fast-moving software.

## Grounded Context (Web Enrichment)
CodeScaleBench is now published and the numbers are more specific than Jarmak's talk conveys. It comprises 370 software-engineering tasks drawn from real enterprise codebases, targeting large-codebase and multi-repo work where retrieval quality drives execution time, retries, and cost. The published results: with MCP-augmented retrieval, cost per task drops roughly 30%, execution speed improves roughly 38%, and retrieval accuracy improves two to three times. The starkest figure is on organization-scale tasks, where a baseline agent without MCP achieved near-zero retrieval precision (P@5 = 0.007) against 0.471 with MCP. That is not an incremental gain, it is the difference between working and not working, and it substantiates the claim that at enterprise scale naive agent search over a monorepo simply fails.

Independent research supports the framing. CodeCompass (arXiv 2602.20048) formalizes what it calls the navigation paradox in agentic code intelligence, and the broader 2026 literature on code-graph indexing for agents converges on the same conclusion, that language-server-grade symbol and reference lookup exposed as tools substantially outperforms text search. Generative engine optimization is now an established enough concept to have its own encyclopedia entry, which is a fair marker of how quickly the recommendation-layer problem became mainstream.

One caution on her GEO numbers: the study is a pilot with hand-designed prompts and a single-vendor perspective, run on models that were already superseded by the time she presented. The 65%-versus-0% contrast is a real and useful finding about prompt framing, but the absolute rates are not stable measurements, and she says as much.

## Real-World Application / Actionable Step
- **Audit tool schemas against training-data conventions.** For every tool Amit exposes (benchmark runners, quantization utilities, profiling helpers), check parameter names against the most common convention in public code. Measure first-attempt call success rate per tool and treat wasted turns per thousand calls as the ranking metric. This is the cheapest token win available and it compounds forever.
- **Write error messages that teach recovery.** Jarmak's agent self-corrected only because the error explained the failure. Every error an agent can hit should state the valid parameter set. That converts a hard failure into a one-turn recovery.
- **Copy the CodeScaleBench design for any retrieval augmentation claim.** Same task set, with and without the augmentation, thousands of traces, and report cost per task and speed alongside accuracy. The P@5 = 0.007 versus 0.471 result is the template for showing that a retrieval layer is load-bearing rather than nice to have.
- **Do not assume newer models know current facts about your work.** Before relying on any model's knowledge of a library or benchmark, test it. The Cody-got-worse result shows that stale content compounds and that model upgrades can regress factual currency. For Amit this matters when models are asked about recent quantization or serving techniques, where the public corpus is dominated by two-year-old advice.
- **Publish pain-shaped content, not feature-shaped content.** If Amit wants his optimization tooling surfaced when someone describes a symptom ("our inference costs tripled after we moved to a larger context window"), that symptom has to appear in his written material. Feature lists get retrieved by shoppers, symptom descriptions get retrieved by people with the problem.
