# You Didn't Ship a Bug. You Just Wrote It for a Human.

**Channel:** AI Engineer
**Published:** 2026-07-19
**Source:** https://www.youtube.com/watch?v=lMCxVorb9wM

## TL;DR
Ravi Madabhushi (Scalekit, ex-Freshworks identity, ~10 years in auth) argues that the entire authentication and authorization stack was built for two actors, humans and deterministic programs written by humans, and neither model survives contact with agents. He opens with a benign symptom (rhythmic 15-minute latency spikes traced to a "last seen" timestamp being updated 60x faster once agents started hitting their APIs) and uses it to motivate a deeper alarm: OAuth scopes are far too coarse for non-deterministic agents. His thesis is that agents need their own identity, always bound to a principal, with attribute-, context-, and principal-level fine-grained scopes, least privilege by default, just-in-time elevation, and full audit visibility. "Praying that the agent doesn't do what it shouldn't is not a strategy."

## Key Takeaways
- The trigger anecdote: a per-request "last seen" write meant for humans caused 60x DB write pressure under agent traffic. Fixed by batching updates at the second level. Harmless, but it exposed that human-era assumptions silently break under agents.
- The old world had two slots: (1) the same user authenticates and acts (password, API key, web session), and (2) service accounts / machine identity (SPIFFE, OAuth), where a human-written deterministic program acts within fixed registration-time scopes. Both assume permissions set once at registration and a program that stays in its lane.
- Determinism was the load-bearing assumption. You could inspect a program's code (Google's security review of OAuth client scopes does exactly this) and guarantee behavior. Agents are probabilistic, so "it did the right thing today" gives zero guarantee about the next run.
- For agents the principal is not the actor. You need genuine on-behalf-of delegation, but many systems still do not support OAuth, so you cannot even tell whether the user or an agent acting for them is calling.
- The MCP-specific failure: most MCP servers do not scope the tool surface to the authorizing user. They expose all tools the app supports and let the agent decide, so the agent can pick the wrong tool. Runtime checks may catch some, but the agent sees the same broad surface regardless of who it acts for.
- OAuth scopes are too coarse. "Can this client send email on your behalf" is not enough. Agents need scoping down to time-of-day, allowed senders/recipients, and per-action attributes, granted for a limited operating window.
- The fixes: agent gets its own identity, always bound to a principal; least privilege by default; just-in-time authorization for elevation; and complete audit visibility (who acted, on behalf of whom, who authorized, what, when, for how long). This is a problem of today, not the future. Agents have already deleted production databases.

## Architecture & Optimization Mechanics
This talk is not an optimization talk, but it is a systems-design talk with a mechanic Amit should internalize because he builds and deploys agentic and routing infrastructure. The core mechanic is that non-determinism invalidates static authorization. Every optimization pattern the rest of the conference celebrates (autonomous loops, self-improving agents, MCP tool access) expands the blast radius of an over-permissioned agent, and the security model has not kept pace. The "last seen 60x" story is also a genuinely relevant workload-shape lesson: agent traffic has a different write/read distribution than human traffic, so capacity and rate-limit assumptions baked into human-era systems (and their inference-serving equivalents) will break silently. Batching the timestamp write is the same class of fix as batching inference requests, coalesce high-frequency operations that were fine at human rates but pathological at agent rates.

The architectural prescription (identity bound to principal, fine-grained context-aware scopes, JIT elevation, full audit) is effectively a control plane that sits in front of tool calls. For anyone deploying agents on self-hosted infrastructure, this is a component you must build or buy, not an afterthought. It also connects to the reproducibility theme from the "Stop Renting" talk: audit trails of exactly what an agent was authorized to do, and did, are prerequisites for regulated deployment.

## Grounded Context (Web Enrichment)
Madabhushi is describing a problem the entire identity industry pivoted to address in 2026, so his talk is squarely mainstream rather than speculative. Major identity vendors have shipped agent-specific IAM this year: Ping Identity announced a runtime identity standard for autonomous AI (March 2026), WSO2 released Agent ID, and Strata, SecureAuth, and Cloudflare all published agentic-identity playbooks emphasizing scoped, revocable, least-privilege tokens. His specific prescriptions map onto emerging practice almost exactly: OAuth 2.1 enforced for all MCP interactions, minimal-scope tokens ("read-only on customer DB," "initiate payment up to $1,000"), and just-in-time authorization where the runtime pauses, captures cryptographic consent for a new scope, brokers a fresh token, and resumes. The literature has already advanced past his framing on one axis he only touches: agent-to-agent delegation chains, where a parent agent passing its token downstream unchanged leaks excess authority to sub-agents, a problem formalized in zero-trust agentic-identity research (arXiv:2505.19301). His "beyond OAuth" instinct is correct; the field's answer is a dedicated agent gateway that enforces policy at tool-invocation time.

## Real-World Application / Actionable Step
Before deploying any agent that touches real data or tools, treat authorization as a first-class design step, not a scope checkbox. Concretely: give each agent its own identity bound to the acting principal, issue minimal-scope short-lived tokens, and put a policy-enforcing gateway in front of MCP tool calls so the exposed tool surface is filtered per authorizing user rather than dumped wholesale to the model. Add just-in-time elevation for any action beyond the agent's standing scope, and log a complete audit trail (actor, principal, grantor, scope, timestamp, TTL) for every tool call. For Amit's own agent and routing infrastructure, also audit for the workload-shape trap the talk opens with: find human-era per-request writes or rate assumptions that agent traffic will hit 60x harder, and coalesce or batch them before they become a DB or serving bottleneck.
