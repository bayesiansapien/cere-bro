# Teaching AI to Find Real Vulnerabilities (Prof. David Brumley, CMU and Bugcrowd)

**Channel:** AI Engineer
**Published:** 2026-08-01
**Source:** https://www.youtube.com/watch?v=ZFxh7sqbUZo

## TL;DR
Brumley's thesis is that cybersecurity is nearly ideal for RL because it is a ladder of graduated tasks with deterministic oracles, and that nearly every existing cyber benchmark is broken in the same specific way: it assumes the target program has exactly one known vulnerability. Real programs do not. When multiple vulnerabilities exist and the grader only checks "did it crash," the model finds the easiest bug forever and stops learning. Telling it which bug to find (via a backtrace) fixes the ambiguity but destroys the reasoning signal. His fix is the audit task, which asks for all vulnerabilities, uniquifies submissions by stack backtrace, and scores precision and recall multiplicatively. The second half presents ExploitBench, a 16-rung capability ladder on 41 hand-verified V8 vulnerabilities, showing that crash-triggering does not discriminate between models at all while full sandbox escape discriminates enormously.

## Key Takeaways
- **The pedagogy transfers.** The methodology that took a 17-year-old (Richard Zhu, "fluorescence") from picoCTF to a Pwn2Own win in two years, first hacking a Tesla for $375,000 and a car, was: read write-ups, emulate, work a graduated difficulty curve. That is a curriculum, and it is the same structure you want for RL.
- **Two orthogonal axes.** Target difficulty (toy programs, CTFs, synthetic, hardened real targets) and exploitation difficulty (locate the bug, trigger a crash, get arbitrary read/write, achieve full arbitrary code execution). Design task sets that climb both.
- **LLM-as-judge fails in security, categorically.** "The LLMs will always say they were successful hacking." You need a deterministic oracle per rung. This is a direct and specific rebuttal to the judge-based approach the preceding conference talk advocated for other domains.
- **Always ask for the exploit, not the finding.** Asking "find the vulnerability" cannot distinguish a hallucination from a real bug. Requiring a working exploit gives you a witness.
- **The single-vulnerability assumption is the core flaw.** Benchmarks like Cybench, CyberGym, and Bounty Bench assume one known bug. With two or more, the model reward-hacks the easiest one indefinitely, and there is no defined scoring for a genuine new discovery.
- **Curating single-bug environments does not work, and this has been tested expensively.** DARPA's Cyber Grand Challenge, which Brumley's team won, spent $60M on hand-curated challenges and 50% of them contained unintended vulnerabilities that were actually exploited. AIxCC, whose scoring algorithm Brumley designed, had 18 unintended bugs found.
- **The audit task.** Flip the question to "find all vulnerabilities." Accept multiple proofs. Uniquify them by stack backtrace, the same technique Windows and Apple crash reporting use. Compute recall (known found over total known) and precision (valid found over total submitted), multiplicatively. Recall rewards discovering unknowns, precision prevents spam submissions.
- **A subtle benefit.** Because you never assert that a bug exists, the model does not receive the free information that there is one. Brumley reports models latch onto that hint and stop after one find. Open-world framing gives a cleaner learning signal.
- **Crashing is not hacking.** You cannot steal IP by crashing a process. AIxCC, CyberGym, and Bounty Bench all measure crashes, which is why they say nothing about real capability.
- **Why V8.** It powers Chrome, Edge, Node.js, and Cloudflare Edge Workers, where each tenant is a separate thread in the same process. Bounties start at $10,000 and run to $100,000, with much more on grey markets. Critically, in-sandbox crashes are expected behavior and worth nothing. Value requires escaping the sandbox, which requires chaining multiple vulnerabilities.
- **The result that matters.** On crash-triggering, GPT-5.5 and Mythos both hit 95% (39 of 41), and even Gemini, Kimi, Minimax, and GLM hit roughly 50%. Under the old benchmark definition you would report "Kimi hacks 50% of the time," which is meaningless. On full sandbox escape and arbitrary code execution, the spread opens dramatically, with Gemini and Kimi at 0%.
- **Evidence against memorization.** On CVE-2023-6702, Mythos reversed JavaScript's Math.random to forge a pointer for a return-oriented program out of the Uber cage, a route experts considered impractical and different from the known public exploit. On CVE-2024-7965 it found a new WASM path beyond where all public work stopped, and succeeded on x86 where Brumley's own internal expert believed it was only feasible on ARM. On CVE-2024-0519, a public vulnerability with no public exploit, it succeeded.
- **The open science problem.** ExploitBench is public at exploitbench.ai as Docker images with an MCP interface, with all data and transcripts released except the Mythos transcripts. Those were withheld both because of an NDA and because Mythos produced weaponized exploits for high-value targets that were not public. Brumley states plainly that they do not have an answer to this tension.
- **The production pipeline.** Bugcrowd mines novel zero-days from open-source software using a decade of DARPA-derived tooling, specifically so the RL environments cannot be memorized, and supplies up to 10,000 environments per month to model developers.

## Architecture and Optimization Mechanics
The audit-task design is the most reusable idea here and it solves a general problem, not just a security one. The pattern is: when a task has an unknown number of valid solutions and the grader can only verify a submitted candidate rather than enumerate the space, score precision and recall over a set of submissions instead of scoring a single answer. The multiplicative combination is what makes it work. Recall alone incentivizes spraying candidates; precision alone incentivizes submitting only the one certain answer. Together they force calibrated confidence, which is exactly the property the TypeSafe talk argued RLHF destroys. This is a reward shape that produces calibration as a side effect rather than requiring it as a separate objective.

Backtrace-based uniquification is the mechanism that makes it tractable, and its analogue in other domains is the harder problem. It gives you a cheap, deterministic, path-invariant identity for "which bug is this," and it is exactly the durability property LatchBio struggled to construct for biology. Security got lucky: the runtime hands you a canonical identifier for free.

The crash-versus-ACE result also has a direct methodological lesson for compression work. Two models scoring 95% and 50% on the coarse metric had a 73%-versus-0% gap on the fine metric. Coarse metrics saturate and hide exactly the capability differences you care about. The compression analogue: perplexity and single-token accuracy saturate long before multi-step composition does, so a quantization scheme that looks lossless on aggregate benchmarks may have destroyed the top rungs of some capability ladder. Building a capability ladder for the target task, rather than a single score, is the fix, and Brumley's 16-rung design is a template for how to do it.

The 10,000-environments-per-month figure is also worth registering as a scale datapoint. Combined with Bespoke Labs' $40M raise and Theta's positioning, the RL environment supply chain has become a real industry in 2026.

## Grounded Context (Web Enrichment)
ExploitBench is published (arXiv 2605.14153, "ExploitBench: A Capability Ladder Benchmark for LLM Cybersecurity Agents"), with the code on GitHub at exploitbench/exploitbench and a Bugcrowd benchmarking report. The 16-flag decomposition, the 41 hand-verified V8 vulnerabilities, and Sang Heon Lee's verification role all check out. The paper's framing of V8's difficulty adds detail the talk skips: the heap sandbox, ASLR, stack canaries, and mitigations co-designed with the engine itself.

The specific numbers do not fully reconcile, and this is worth flagging. Brumley says Mythos achieved arbitrary code execution on 73% (30 of 41) and GPT on 68%. The published ExploitBench results say Mythos Preview reaches ACE on 18 of 41 (44%), and that among publicly deployed models only GPT-5.5 reached ACE, on a single Wasm bug, and only under the vendor-CLI arm rather than the primary arm. Those are very different claims. Plausible explanations: the talk may be quoting a higher rung short of full ACE (control-flow hijack, which he mentions in the same breath), or newer results than the published run, or a different experimental arm. Brumley himself says twice during the talk that the bars on his slide are wrong. Until reconciled, cite the paper's 18-of-41, not the talk's 73%. The qualitative conclusion, that crash-triggering does not discriminate while sandbox escape does, holds under either set of numbers.

The Mythos context is larger than the talk conveys. Anthropic's Claude Mythos Preview is described as able to autonomously discover and exploit zero-days across every major operating system and browser. Project Glasswing is a defensive coalition (AWS, Apple, Broadcom, Cisco, CrowdStrike, Google, JPMorganChase, the Linux Foundation, Microsoft, NVIDIA, Palo Alto Networks) formed to use the capability to harden critical software before comparable models are broadly available. As of May 2026 the coalition had identified more than 10,000 high or critical severity vulnerabilities, with Cloudflare and Mozilla each finding hundreds in their own codebases. Anthropic has stated it intends general availability only after stronger safeguards exist. Anthropic also published its own exploit-development evaluations. This is the context for the MLST conversation's remark that disclosure rates jumped sharply when Mythos appeared, and it is the strongest available evidence that the offense/defense balance in software security genuinely shifted in 2026.

## Real-World Application / Actionable Step
1. **Build a capability ladder instead of a score for your next compression evaluation.** The 95%-vs-50% coarse result that became 73%-vs-0% on the fine metric is the clearest available demonstration that aggregate scores hide the differences that matter. Pick one target task, decompose it into 6 to 16 rungs of increasing difficulty, and report the rung profile for each quantization or pruning variant rather than a single number. This will surface exactly where compression breaks, which single scores never do.
2. **Adopt precision-times-recall scoring wherever the valid-answer set is unknown.** This applies directly to any evaluation where a model can produce multiple candidate answers and you can verify but not enumerate. It produces calibration for free, and it is a better reward shape than anything discussed in the RLHF-successor talks.
3. **Audit your own evaluation harnesses for the single-answer assumption.** Brumley's point that experts spent $60M and still shipped unintended solutions in half their tasks generalizes: if your eval assumes a unique correct answer, it is probably wrong, and the model is probably already exploiting that. The cheapest check is to look at whether the same solution appears across many rollouts.
4. **Note the LLM-judge failure mode as domain-dependent.** Judges work in domains where the judge is not the thing being evaluated and where success is not self-attestable. In security, the model claims success and the judge believes it. The general rule: never use a judge where the model's claim of success is itself the primary evidence. Check whether any internal eval has this shape.
5. **Pull ExploitBench if you want a real capability-ladder reference implementation.** It ships as Docker images with an MCP interface. Even outside security, it is the cleanest public example of graduated deterministic oracles, and reading the grader code is a faster education than any description of the design.
