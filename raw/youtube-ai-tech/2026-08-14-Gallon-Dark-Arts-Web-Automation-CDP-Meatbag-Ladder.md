# The Dark Arts of Web Automation: Teaching Agents to Use Websites Like Humans — Corey Gallon, Rexmore

**Channel:** AI Engineer
**Published:** 2026-08-14
**Source:** https://www.youtube.com/watch?v=26RtyAm9y_Q

## TL;DR
Gallon's premise is one sentence: a browser driven over the Chrome DevTools Protocol is indistinguishable from a human at the mouse, because agent clicks and keystrokes travel the same path inside Chrome that yours do. Everything else follows from that. The architecture has three parts. Give the agent a shell CLI rather than an MCP server, because capability is a wash at roughly 83% task success either way while the CLI wins decisively on reuse (a captured sequence runs a thousand times with no model in the loop), on speed (seven turns in under a minute versus 71 round trips and eight minutes), and on token cost. Drive the browser through CDP, whose 57 domains he reduces to a small set of digital senses: see via DOM, accessibility tree or screenshot, hear via network traffic and console, act via clicks, keystrokes and navigation. Run a sense-act-verify loop where verification deliberately uses a different channel than the action, so you never ask a click whether the click worked. When the loop will not close, climb what he calls the meatbag ladder, three rungs of increasing humanness, taking the lowest rung that works: synthetic JavaScript events, then trusted CDP input-domain events, then real mouse paths with dwell and jitter plus vision. Then write down whatever worked as code or a skill so it never has to be rediscovered. He demonstrates the whole thing against four anti-bot systems, ending with reCAPTCHA v2, and the architecture of that final demo is the real lesson: a deterministic code solver drives everything at machine speed and calls the model exactly once per round for the single step that needs eyes and judgement. That split exists because the challenge is on a clock and an agent that round-trips a model on every click loses to expiry before it finishes. OpenAI threatened to ban his account over the preparation work and later rescinded it, which tells you where this sits.

## Key Takeaways
- The central technical fact, and the thing worth remembering even if you discard the rest: Chrome stamps every input event as trusted or untrusted. A synthetic JavaScript click is untrusted and pages can and do silently ignore it, with no error and no failure signal. An event injected through CDP's input domain is stamped trusted and travels the same internal path as a physical mouse. The detection boundary is inside Chrome, not in the page's heuristics.
- CLI over MCP, with the numbers he cites: equal capability at about 83% success, but 71 round trips and eight minutes for MCP against seven turns and under a minute for the CLI on the same task, and an Anthropic-reported figure of up to 75 times cheaper in tokens.
- The reuse argument is the strongest of the three and the one he returns to. A CLI sequence is a program. You solve the interaction once, write it down, and replay it without a model in the loop. MCP re-enters the model on every turn, so the cost and latency scale with invocations rather than being amortised.
- CDP's surface is enormous, 57 domains with hundreds of methods and events, and changes frequently. His reduction to digital senses is the useful abstraction: see (DOM for structure, accessibility tree for semantics, screenshot for pixels), hear (network traffic, console, logs), operate (click, type, navigate). Most human-equivalent interaction needs only a small subset.
- The sense-act-verify loop with cross-channel verification is the most portable idea in the talk. Act once, then verify through a different sense than the one you acted with. If you clicked, do not ask the click whether it succeeded, check the network or the screen. This is what catches the silent-drop failure mode, where an untrusted event produces no error at all.
- The meatbag ladder, climbed only as far as the page forces. Rung one, do not act human at all: use the page's own exposed API or a synthetic JavaScript click, which is free, instant and the correct default. Rung two, trusted input through CDP when faking stops working. Rung three, human input and behaviour, meaning real mouse trajectories with easing, curvature, overshoot and jitter, plus vision.
- Explore then automate. Run the loop manually, climb rungs until something works, then persist the working path as code, as an agent skill, or usually both. The durable artefact is the recorded solution, not the agent's cleverness.
- The Outlook demo makes a genuinely interesting organisational point. Driving the Office 365 web UI needs only the login the employee already has, whereas the Graph API needs an app registration and admin approval an employee often cannot obtain. In that pattern the web UI becomes a permissionless universal API. That is a real capability and also a description of a control bypass, and he does not dwell on the second half.
- The commerce site demo is the trusted-versus-untrusted lesson in isolation. The same synthetic click that worked in Outlook produces literally nothing against an add-to-cart button, with no error, because the page checks the trusted bit and drops untrusted input silently.
- Cloudflare Turnstile is defended by structure rather than by perception: the checkbox sits under a closed shadow root, inside a cross-origin iframe, which itself contains another shadow root, so there is no element for automation to grab. His approach abandons element grabbing entirely, asks the browser where the iframe sits on screen, computes the target position, and clicks the glass. The generalisable point is that geometry survives encapsulation boundaries that the DOM API does not.
- The character-recognition and jigsaw-drag systems test different things. The first tests perception and is answered with a screenshot plus the model's vision, with the answer typed as trusted keystrokes into a cross-origin iframe. The second tests motion, because these systems sample the mouse trail including jitter and speed changes, so the drag has to ease in, curve, overshoot and settle. His line about solving it with moves like Jagger is the memorable framing of behavioural biometrics as an authentication channel.
- The reCAPTCHA v2 architecture is the payload of the talk. Two halves. A solver, pure code with no model, that does the trusted click, pierces the challenge iframe, screenshots the grid each round, and re-arms itself when a round expires, all deterministic, fast and free. An operator, the model, invoked for the single step code cannot do: look at the tiles and decide what is in them.
- The reason for that split is a hard deadline rather than cost. Rounds expire, a challenge can chain multiple rounds, and an agent that round-trips a model on every click and every look burns the clock and loses to expiry. Speed is not a nice-to-have here, it determines whether the approach works at all.
- His own framing of the takeaway is that the anti-bot systems were test fixtures for the methodology, not the point, and that the capability came from disciplined engineering rather than from the model being able to do any of it off the shelf.
- The account-ban anecdote bookends the talk. OpenAI flagged the preparation work as cyber abuse and threatened a ban, then rescinded after a conversation. He also states that everything demonstrated ran on infrastructure he owns and accounts he operates, explicitly on advice of counsel.

## Architecture & Optimization Mechanics
The solver-operator split is the most valuable thing here and it deserves to be lifted out of the CAPTCHA context entirely, because it is a general pattern for building agentic systems under a latency deadline. The structure is a deterministic control loop running at machine speed with model invocation reserved for the minimum set of steps that genuinely require perception or judgement, and the design pressure that produced it was a hard expiry rather than a budget. That inversion is worth sitting with. Most agent architectures put the model in the driver's seat and treat code as tools the model calls. Gallon puts code in the driver's seat and treats the model as a perception subroutine the code calls. Under a deadline the second structure dominates, because the number of model round trips is the quantity that determines whether you finish at all, and the only way to control it is to make the model's involvement an explicit resource that the control flow allocates rather than an implicit consequence of every step.

That reframes the CLI-versus-MCP argument as something more interesting than a tooling preference. What he is actually describing is a distinction between an architecture where model invocations scale with the number of interactions and one where they scale with the number of novel decisions. The 71-round-trip versus seven-turn comparison is not MCP being slow, it is MCP being a protocol whose unit of work is a model turn. Once an interaction sequence is known, replaying it should cost zero model calls, and any architecture that cannot express "I already know this, just run it" will pay the model tax forever. This is the same economics as caching but at the level of policy rather than tokens, and the artefact he persists, the written-down path, is a compiled policy for a specific environment. The correct mental model is that exploration is expensive inference and the recorded skill is its distilled product, which means agent skills are a distillation pipeline where the teacher is an expensive exploratory loop and the student is a deterministic program.

The token comparison deserves scrutiny because the mechanism matters more than the multiplier. Independent benchmarks put the CLI advantage at 4x to 32x, with one widely cited example showing 1,365 tokens for a CLI agent against 44,026 for MCP on a trivial repository question, and the diagnosis in that case is that the difference is almost entirely schema, 43 tool definitions injected into every conversation of which one or two get used. That is a prefix-bloat problem, not an inherent property of MCP, and it is fixable: Anthropic's own advanced tool use work introduces deferred tool loading with a search tool so definitions load on demand, and the code-execution-with-MCP pattern reports roughly 85% token reduction by having the model write code that wires tools together and processes results outside the context window. So his 75x figure is the top of a wide range and it compares a well-tuned CLI against a naively configured MCP server. The transferable claim survives the correction, but its form changes: the win comes from keeping schema out of the prefix and intermediate results out of the context, and either protocol can be made to do that.

The cross-channel verification rule is the kind of thing that sounds obvious and is violated constantly. Its justification here is specific and stronger than the general principle: an untrusted event does not fail, it is silently dropped, so the action channel returns success while nothing happened. Any verification that reads the action's own return value is structurally blind to the dominant failure mode. Generalised, this says that a verifier sharing a failure mode with the thing it verifies provides no information, which is the same reason a model that grades its own output with the same prompt and the same weights is a weak judge, and the same reason self-consistency sampling at temperature zero tells you nothing. It is also directly relevant to process reward models: if the reward signal is computed from the same observation channel the policy acted on, correlated errors will be rewarded rather than caught.

His geometry-over-DOM trick against the shadow-root and cross-origin encapsulation is a nice instance of a general principle about abstraction boundaries. Three layers of DOM-level isolation are complete against DOM-level access and entirely transparent to the coordinate space they all render into. Encapsulation at layer N provides no protection against an adversary operating at layer N minus one, and the browser's compositor is below all of it. The defensive reading is that any isolation implemented in the same substrate the attacker can address is decorative, which is the same argument that makes a trained refusal weaker than an architectural containment boundary.

Where the talk is intellectually weak is in never asking what these systems are for. He treats each anti-bot system as a puzzle whose only property is difficulty, and the framing of the last one as a boss to be beaten is entertaining and evades the question. Rate limiting and bot detection are the mechanisms by which sites allocate a shared resource and prevent abuse, and the ability to defeat them at machine speed with no human in the loop is not neutral capability. His own opening is the evidence: a model provider's abuse system flagged this as cyber abuse, which is a reasonable classification of the behaviour pattern even if the intent was benign. He answers with a legal disclaimer about owned infrastructure, which addresses his personal exposure and not the question of what the published methodology enables. That gap is worth naming because the methodology is genuinely good and its best applications, the Outlook case and internal automation over systems you control, do not require the top rung of the ladder at all.

## Grounded Context (Web Enrichment)
His CLI-versus-MCP numbers check out in direction and are cherry-picked in magnitude. Arize's evaluation is the study he is referencing and it does find roughly comparable task success with large efficiency differences. Independent benchmarking from Scalekit reports MCP consuming 4x to 32x more tokens than equivalent CLI calls and, more strikingly, a reliability gap, 100% versus 72% success in their setup, which contradicts his claim that capability is a wash and suggests the answer depends heavily on the tool surface. The commonly cited mechanism is schema overhead, tool definitions loaded into every conversation regardless of use, and the illustrative case of 1,365 versus 44,026 tokens on a trivial question is almost entirely that. Worth noting the counter-argument the same literature makes: MCP pays context cost upfront so the model can construct a correct call immediately, while a CLI often needs discovery round trips running help to learn the interface. One finding cuts across both, that an 800-token skill document of CLI usage tips reduced tool calls and latency by about a third, which supports his write-it-down step more directly than his protocol argument does.

The protocol comparison is also less stable than he presents it, because MCP has been actively fixing exactly the problem he criticises. Anthropic's advanced tool use release introduced deferred tool loading, where tools marked for deferral are discovered on demand through a search tool rather than loaded into the prefix, and the code-execution-with-MCP pattern has the model write code that calls tools as functions, processes results locally, and returns only a summary, with reported reductions around 85% and some implementations claiming far more. Anyone quoting a 75x CLI advantage in late 2026 is comparing against a configuration that is no longer the default recommendation. The durable version of his point is architectural, keep schemas out of the prefix and intermediate data out of context, and it is now achievable in either protocol.

On the legal position, the distinction that matters is not whether automation is legal in general but which specific act is at issue, and his demonstrations sit on the wrong side of the sharper line. Accessing public web data has held up reasonably well for automators after hiQ v. LinkedIn, Van Buren's narrowing of the CFAA, and the January 2024 summary judgment for Bright Data against Meta on logged-out public scraping. Circumventing technological access-control measures is a different theory, and it is live: Reddit's suit against Perplexity and several data collection providers, filed in late 2025 and still pending as of April 2026, is built on DMCA Section 1201 and alleges circumvention of rate limits and anti-bot systems specifically. Solving a CAPTCHA programmatically is close to the paradigm case of circumventing a technological measure, and the fact that no copyrighted work is being accessed is the defence that would have to be argued rather than an obvious out. His counsel's advice, run only on your own infrastructure and accounts, is exactly the right mitigation and it is doing a great deal of work.

The wider context he does not mention is that the same capability is being weaponised in the other direction, and the arms race has a scoreboard. Web agents are the subject of an active attack literature, with pop-up injection, HTML form injection to harvest data agents type, and imperceptible perturbations aimed at screenshot-reading agents all documented, and Berkeley researchers naming the general problem Cross-Site Prompting by analogy to XSS. A crawl of billions of pages found malicious injection patterns up 32% between November 2025 and February 2026. Gallon's methodology makes agents better at appearing human to defenders, and the same agents are the targets. An agent that has been engineered to be indistinguishable from a human to Cloudflare is also an agent that has forfeited the option of being identified as an agent by a site that would have treated it cooperatively, which is the strategic cost of the whole approach and the reason the emerging alternative is signed agent identity and paid access rather than better mimicry.

## Real-World Application / Actionable Step
1. Steal the solver-operator split for any system with a latency deadline, which is the genuinely reusable idea here. Put deterministic code in control and invoke the model only for steps requiring perception or judgement, so model round trips become an explicitly allocated resource rather than a per-step default. This is the correct architecture whenever the binding constraint is wall-clock rather than accuracy, and it applies well beyond browsers.
2. Count model invocations, not tokens, when you profile an agent under a deadline. His reCAPTCHA design works because invocations scale with novel decisions rather than with interactions, and the failure mode he describes, losing to expiry, is invisible in a token budget. Add invocations-per-task to your agent evaluation alongside cost and success rate.
3. Treat recorded interaction paths as distillation products and manage them accordingly. The exploratory loop is the expensive teacher, the written-down skill is the cheap student, and the artefact needs the same lifecycle discipline as any distilled model: versioning, a staleness policy, and a validity check, because the environment it was compiled against changes underneath it. His methodology has no invalidation story, and that is its main operational gap.
4. Adopt cross-channel verification as a rule everywhere, not just in browsers. Never verify an action through the channel that performed it. The general statement is that a verifier sharing a failure mode with the thing it verifies carries no information, which is why a self-graded model output is a weak signal, and why a process reward model computed from the same observation the policy acted on will reward correlated errors rather than catch them.
5. Do not quote the 75x CLI advantage. The defensible range is 4x to 32x, the mechanism is schema in the prefix plus intermediate results in context, and deferred tool loading and code-execution-with-MCP have both closed much of the gap. Argue the mechanism instead: keep schemas out of the prefix, keep intermediate data out of the context window, and choose whichever protocol lets you do that.
6. Use the permissionless-UI observation defensively rather than offensively. His Outlook case shows that an employee's browser session grants effective API access that the tenant's app-registration controls were meant to gate. If you deploy agents inside a corporate environment, that is your threat model: browser-session-scoped agents route around API governance entirely, and the control has to live at the session or device layer because the UI layer cannot distinguish the agent from the user.
7. Apply the ladder discipline in reverse as a design constraint. Climbing only as high as the page forces is good engineering, and it is also a useful line: if an internal automation needs rung three against a third party's system, that is a signal to obtain access properly rather than to engineer harder. The rung required is a reasonable proxy for how much the operator wants to be automated.
8. Keep the circumvention question separate from the scraping question in any diligence you do. Public data access is comparatively settled after hiQ and Meta v. Bright Data. Defeating anti-bot measures is the live theory, it is being litigated under DMCA 1201 in Reddit v. Perplexity against both a model company and its suppliers, and the mitigation that makes this talk defensible, own the infrastructure and the accounts, does not transfer to any third-party target.
