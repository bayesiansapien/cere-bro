# Boris Cherny: Building Claude Code

**Channel:** Y Combinator (Startup School 2026)
**Published:** 2026-07-27
**Source:** https://www.youtube.com/watch?v=qyPCVqFUyDo

## TL;DR
The creator of Claude Code, recorded the day after Opus 5 shipped. Three claims carry the talk. First, Anthropic deleted **80% of Claude Code's system prompt** for Opus 5, and in ablation the model is measurably *more* intelligent without prompts. Second, **prompt injection is claimed dead** via three stacked layers, one of which reads interpretability neurons that fire during injection attempts. Third, the real skill is no longer prompt engineering but **elicitation plus verification**: give the model a task slightly beyond what you think it can do, give it a way to check its own work, and leave. His evidence is a Bun runtime rewritten from Zig to Rust in 11 days and a Swift port of the Claude desktop app that has been running continuously for over two weeks and had not finished at recording time.

## Key Takeaways
- **Ablate every model generation.** Delete the entire system prompt, then add lines back one at a time only where you see the model *repeatedly* stumble on the same thing. Never guess an instruction in advance, because the model pays for it on every single call.
- **`CLAUDE_CODE_SIMPLE=1`** is an undocumented env var that strips all system prompts including tool prompts. Anthropic uses it as their internal ablation baseline.
- **Prompts you keep are product decisions, not capability decisions.** The bare model is slightly smarter without them; the prompts exist so the *product* behaves the way a human user expects.
- **Advice for users, stated plainly:** every six months delete your `CLAUDE.md`, your skills, and your hooks. See what happens. For Opus 5 specifically he recommends doing it now.
- **Evals decay too.** They outlive a harness by maybe one to three model generations before saturating, then get thrown out. "Keep your evals forever" is explicitly the wrong lesson; the interviewer proposes it and Cherny corrects him.
- **Product overhang and hobbling** are two sides of one idea. The model can already do things nobody has built a product for (overhang), and existing products actively prevent it (hobbling). Claude Code's origin was un-hobbling Sonnet 3.5, which could write whole files while every product of the era offered only autocomplete and read-only chat.
- **The over-specification failure mode.** Experienced engineers are the worst offenders. Step-by-step instructions ("do 1, then 2, then 3") degrade modern models. Correct shape: describe the task, the guardrails, the exit criteria, then leave.
- **Verification is the single most under-done thing.** His Swift port prompt was essentially: rewrite the Electron app in Swift, run the Electron app in a VM, screenshot it, compare pixel by pixel, do not stop until done. The verification loop is what makes multi-week autonomy possible.
- **Dynamic workflows are framed as a new axis of test-time compute.** Not just more tokens from one agent, but an *algebra for agents* (sequence and parallel composition) executed inside a Bun sandbox, fanning out, verifying, fanning out again. He says this is under-written-about and he is right.
- **Loops and routines** are distinct from workflows: one repetitive task, no shared context, but shared memory. Loop runs locally, routine runs in the cloud.
- **Claude Code now largely maintains itself.** Twenty to thirty daily routines across CLI, iOS, Android, and desktop codebases: dead code removal, shipping fully-rolled-out experiments, writing missing tests, deleting useless tests, and "abstraction police," which finds near-duplicate abstractions across a codebase and unifies them. Each is roughly a one-sentence prompt. Nobody told the dead-code routine to use static and dynamic analysis; it worked that out.
- **"Coding is solved" comes with a real caveat.** Solved for his kind of coding. Still weak on deep systems code, distributed systems, and pixel-exact UI verification.
- **The meta-skill:** forget your priors. Things that failed six months ago should be retried. This is an empirical science now, not a theoretical one.

## Architecture & Optimization Mechanics
Three mechanics here are directly relevant to inference and optimization work.

**Ablation as prompt compression.** The system prompt is fixed input tokens on every request. Deleting 80% of it is a straight reduction in prefill cost per call, multiplied by every session across every user. That it *also* improved measured intelligence is the interesting part: instructions correcting behaviours the model no longer exhibits are not neutral, they actively constrain it. The generalisation is that **scaffolding written for model generation N is a tax on generation N+1**, paid in both tokens and capability. This is the prompt-side analogue of dead code, and it has the same fix: delete first, restore on evidence.

**Dynamic workflows as a test-time compute axis.** Cherny's framing deserves attention. Scaling laws historically ran over parameters, data, and training FLOPs, then added test-time compute measured as tokens generated. Dynamic workflows add orchestration structure as a separate dimension: how you *compose* agents (sequence, parallel, fan-out, verify, fan-out again) determines how productively test-time compute converts into work. Same token budget, different topology, very different result. The functional-programming framing (an algebra with sequential and parallel combinators) is the right abstraction and suggests the design space is barely explored.

**Verification loops as the enabler of long-horizon autonomy.** The reason the Swift port can run for two weeks is not model stamina, it is that the agent has a ground-truth oracle (screenshot the Electron app, diff pixel by pixel) it can query without a human. Bun's rewrite worked for the same reason: over a million existing tests. The pattern is that **long-horizon agent work is bounded by the availability of a cheap automated oracle, not by model capability**. Where an oracle exists, horizons extend to weeks. Where it does not, they collapse to a single turn. That is the actual constraint founders should be reasoning about.

## Grounded Context (Web Enrichment)
**The Opus 5 and ARC-AGI-3 numbers check out and are unusually well-sourced.** Anthropic launched Opus 5 on 24 July 2026 at roughly half Fable 5's price. Opus 5 (High) scored **30.2% on ARC-AGI-3, independently verified by ARC Prize**, against a previous record of 7.8% held by GPT-5.6 Sol at max reasoning effort. Nearly a 4x jump. It solved five environments no model had beaten, four at or above human efficiency, taking solved public demo environments from one to six. Third-party verification at launch is rare enough to be worth noting, and the interviewer's "low single digits or low teens" framing understated the jump.

**The Bun rewrite is real and considerably larger than Cherny describes, and it is genuinely contested.** Anthropic acquired Bun in late 2025. The Zig-to-Rust migration took **11 days**, ran roughly **50 concurrent AI workflows** (one detailed case study cites 64 concurrent Claude agents), peaked at about **1,300 lines of Rust per minute**, converted ~535K lines of Zig into over a million lines of Rust, and cost roughly **$165,000 at standard API rates**. Sumner reports the Rust version passed Bun's full test suite of over a million tests without modification.

But Cherny presents this as a clean triumph, and the reception was not clean. Zig creator Andrew Kelley called it **"unreviewed slop"** and made an argument that lands directly on the verification claim above: *"It's not sufficient to catch bugs in Zig code but it is sufficient to catch bugs in a million lines of unreviewed slop?"* If the test suite failed to catch bugs in the hand-written Zig, there is no reason to believe it catches them in machine-generated Rust. Kelley also argued Bun's maintainability problems came from engineering practice ("hack upon hack," minimal technical debt work, relentless feature piling) rather than from Zig, and framed the split as diverging project values. The strongest version of his point is that **a test suite is an oracle of unknown coverage, and agent throughput scales the code faster than it scales confidence in the oracle**. That caveat belongs next to every "11 days" citation.

**The prompt injection claim is the least verifiable thing in the talk and the highest-stakes.** Cherny's three layers (aligned base model, an interpretability-based classifier watching neurons that fire during injection, and the auto mode classifier) are described accurately, and the interpretability work is Chris Olah's, not "Crystal's" as the ASR renders it. Anthropic's published figures show only 1.4% of attacks succeeding against Claude Opus 4.5 with new safeguards versus 10.8% for Sonnet 4.5 with prior safeguards. That is a large improvement. It is not zero, and "we cannot demonstrate prompt injection anymore" means *Anthropic's red team* cannot, which is a claim about their attack budget, not about the attack surface. Active academic work such as IterInject (feedback-guided iterative optimisation for indirect injection against LLM agents) exists precisely because the problem is not considered closed. Treat this as a substantial reduction in risk, not its elimination, and do not redesign a threat model around a vendor's claim about their own product.

## Real-World Application / Actionable Step
1. **Do the ablation on Amit's own setup this week.** Back up `CLAUDE.md`, skills, and hooks, then delete them and work normally for a few days. Restore only the lines that correspond to a *repeated* observed failure. Cherny's own framing is that most accumulated scaffolding is correcting behaviours current models no longer exhibit. Run `CLAUDE_CODE_SIMPLE=1` once to see the true baseline.
2. **The transferable principle for optimization work is the strongest thing in the talk:** scaffolding written for an older model is a tax on the newer one. This applies far beyond prompts. Custom kernels, quantization calibration sets, and routing heuristics tuned against last generation's model are the same category of dead weight. Schedule a periodic ablation of the *optimization stack*, not just the prompt.
3. **Retry the shelved experiments.** His explicit advice is that anything that failed six months ago is worth another attempt. For Amit that means the pruning or routing approaches abandoned as "the model can't do this reliably." Requeue them against Opus 5 before designing around the old limitation.
4. **Build the oracle before extending the horizon.** The lesson from both the Bun rewrite and the Swift port is that autonomous duration is a function of automated verification, not of model quality. For compression work the oracle is obvious and cheap: a fixed benchmark suite plus a latency and perplexity gate. Wire that up first, then let long-running agents sweep quantization configurations against it. Without the oracle, the same agent produces confident garbage.
5. **Steal the routines pattern for research hygiene.** One-sentence daily jobs against his own repos: find dead experiment code, unify near-duplicate benchmark harnesses, flag untested paths in the serving code. Low effort, and the "abstraction police" idea in particular is well suited to research codebases, which accumulate five variants of the same evaluation loop.
6. **Hold Kelley's objection in mind when using agents at scale.** Before trusting a large agent-generated migration, measure the oracle's coverage rather than its pass rate. A million passing tests over unknown coverage is not the same as verification, and this is the failure mode that will bite hardest in numerical code where a wrong answer is still a plausible answer.
