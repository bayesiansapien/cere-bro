# Rethinking Environments for Long-Horizon Work (Rayan Garg and co-founder, Theta Software)

**Channel:** AI Engineer
**Published:** 2026-08-01
**Source:** https://www.youtube.com/watch?v=2aS7aKoXn64

## TL;DR
Theta's argument is that "long horizon" is a scalar that everyone treats as a binary, and that the resulting sloppiness has produced a generation of finance benchmarks measuring the wrong thing. Their axes for a genuinely hard environment: token/step count and human-hours together (never either alone), tool-coordination complexity, sequential rather than parallelizable state changes, and deliberate ambiguity in the starting materials. The most substantive engineering content is on verifiers: for open-ended software-adjacent work, deterministic checks are impossible, so the judge must itself be an agent with read-only access to the same environment and a queryable, phase-segmented representation of the trajectory rather than the raw trajectory stuffed into a context window. Their closing shot is that GDPval, ToolBench, and APEX-Agents all fail on task length, saturation, breadth, and reward granularity, while their own finance tasks average 15 human-hours and models score around 5%.

## Key Takeaways
- **Long horizon is relative and moving.** What counted as long horizon a year ago does not now. It is useful for ordering tasks, useless as a category.
- **Two measurement frames, both flawed alone.** Human-hours (METR's approach, with success-rate thresholds) breaks down because tasks that are tedious for humans can be trivial for models. The Excel reformatting example is apt: days of human work, one Python script for a model, and a financial analyst would never write that script. Model-side units (tokens, steps, tool calls) are noisy because model family and harness dominate. Codex models are more token-efficient than Claude models, so 500K tokens on one tells you little about the other.
- **Human-hour estimates get noisier at the frontier.** As tasks move toward what only the top 10%, 1%, or 0.1% of humans can do, the expert-time estimates become nearly meaningless, and expert quality varies enough to make cross-organization comparisons of "our tasks are 16 hours" versus "ours are 20" incomparable.
- **Tool coordination is a complexity axis.** How many tools and external dependencies must the agent coordinate, and move information across. Grafana for log parsing, GitHub for CI/CD, CloudWatch, databases.
- **Parallelizable complexity is not real complexity.** Fanning sub-agents across files in a code base and merging results is wide but shallow. Sequential complexity, where a bad early query or a misread log cascades into everything downstream, is what actually tests capability. Chaining unrelated independent tasks makes a benchmark long without making it hard.
- **Ambiguity is a deliberate design choice with a cost.** Real work starts with incomplete information and requires exploration. Building that in means many valid paths, which makes standardized evaluation much harder. They accept the tradeoff.
- **Judges are agents, not LLM calls.** For the deployment-failure example (sift CI/CD logs, read CloudWatch, patch the code, open a PR, trigger redeploy), the judge cannot verify correctness from tool calls alone, which are unreliable. It must independently query GitHub and AWS post-hoc. So it needs the same harness the agent had, with read-only permissions enforced so it cannot mutate state or kick off a deployment.
- **Trajectories must be made queryable.** Long trajectories cannot be stuffed into a judge's context. Put them in a database, use sub-agents to enrich, segment into phases (log investigation, code writing, post-verification), attach metadata so the judge can locate failure points.
- **Reference-answer judging fails on open-ended tasks.** Comparing against a sample good trajectory collapses the explorable state space and cannot enumerate the valid solutions.
- **Reward density has an upper limit set by judge reliability.** Overloaded rubrics get applied inconsistently, especially on frontier problems the judge itself cannot solve. Rubric QA (gold tests, no-op tests, variance tests, coverage, expert agreement) is required, and more so as AI participates in generating the rubrics.
- **Deterministic verifiers are not dead.** Use them in tandem, often to generate an artifact or collect metrics that the judge then reasons over.
- **Dynamic evaluation-time rubrics for partial credit.** Assume the model's earlier wrong step was correct and grade the remainder conditionally, like grading a multi-part exam question.
- **The benchmark critique.** GDPval, ToolBench, and APEX-Agents: average human-hours per task fall well below current frontier model capability, they are already substantially saturated, they are narrow (GDPval's finance slice is a small set of Excel tasks, APEX-Agents is largely investment banking, so credit, debt, and risk go uncovered), and their reward signal is far too coarse for training. APEX-Agents IB shows 57% pass@1.
- **Their own numbers.** 15 human-hours average per task across a 50-task sample, models scoring around 5%.

## Architecture & Optimization Mechanics
The judge-as-agent argument has a cost structure nobody in the talk acknowledges, and it matters. If the judge needs the full harness, independent environment queries, sub-agent enrichment, and phase segmentation, then judge inference cost approaches agent inference cost per rollout. For RL, where you need many rollouts per prompt, that roughly doubles the per-sample cost. Combined with Theta's own 15-hour-per-task environments and the multi-hour provisioning problem Emulated described, verification cost becomes a first-order term in the RL budget rather than a rounding error. Two mitigations follow directly: cache the judge's environment queries across rollouts of the same prompt (the environment's post-state differs per rollout but the query plan does not), and use a cheap deterministic pre-filter to reject obviously-failed rollouts before invoking the expensive agentic judge. This is a routing problem, and it is exactly the shape of problem Amit works on.

The parallelizable-versus-sequential distinction is also the sharpest tool in the talk and it generalizes to evaluation design broadly. A benchmark composed of independent subtasks measures per-subtask capability times a length multiplier. A benchmark with genuine state dependence measures error compounding, which is a different quantity entirely and the one that predicts real deployment behavior. Most "long horizon" evaluations are the first kind wearing the second kind's label. The diagnostic is simple: shuffle the subtask order. If the score is unchanged, the benchmark has no sequential complexity.

The token-count noise point has a direct bearing on routing. If harness and model family dominate token consumption for the same task, then a router's cost model cannot use a task-intrinsic token estimate. It must be per-model, and it must be re-estimated when the harness changes. That is a stronger requirement than most routing systems implement.

## Grounded Context (Web Enrichment)
The METR framing is accurately described and the current numbers give useful scale. METR's headline metric is the 50% task-completion time horizon, the human-equivalent duration at which a model succeeds half the time. As of early 2026 the hierarchy runs Claude Opus 4.6 at roughly 14.5 hours, GPT-5.2 at roughly 6.6, Claude Opus 4.5 at roughly 4.8, with the strongest assessed agents at or beyond the reliable measurement range of Time Horizon 1.1 and the most capable shared model estimated around 16-20 hours. The doubling rate has steepened: roughly every 4 months now (about 10x per year), versus roughly 3x per year before 2024. Projections put week-long tasks in late 2026 and month-long tasks by mid-2027. METR themselves published work on how time horizon varies across domains, which supports Theta's complaint that a single scalar hides a lot.

The benchmark critique holds up under independent scrutiny. Epoch AI's analysis of economic-value benchmarks finds GDPval the closest to saturation, with GPT-5.2 Pro at a 74% win-plus-tie rate (60% win, 14% tie) and GPT-5.2 xhigh at 71%. GDPval spans 44 occupations and 9 industries in aggregate, so the "narrow" criticism is specifically about its finance slice rather than the benchmark overall, which the talk states correctly but which a casual listener could easily misread. The APEX-Agents 57% pass@1 figure on investment banking checks out. There is also a relevant adjacent paper, "Automated Benchmark Auditing for AI Agents and Large Language Models" (arXiv 2605.26079), suggesting benchmark quality auditing is becoming its own subfield.

The obvious caveat: Theta sells long-horizon finance environments, and the talk's structure is "existing benchmarks are broken, here are our numbers." Their 15-hour / 5%-model-score figures are self-reported, from a 50-task sample, with no published methodology for the human-hour estimation. Given that their own presentation spends several minutes explaining why cross-organization human-hour comparisons are unreliable due to expert quality and methodology differences, their headline number is subject to precisely that critique. The framework is genuinely good. The scoreboard is marketing.

## Real-World Application / Actionable Step
1. **Apply the shuffle test to every long-horizon eval you rely on.** Reorder the subtasks. If the score does not move, the benchmark has no sequential complexity and is measuring per-step capability multiplied by length, not error compounding. This takes an afternoon and will invalidate at least one benchmark you currently trust.
2. **Make token cost per task per model, not per task.** Theta's point that harness and model family dominate token consumption means a router using a task-intrinsic token estimate is systematically miscalibrated. Measure tokens-per-task separately for each candidate model under the actual production harness, and re-measure when the harness changes.
3. **Build a cheap-verifier pre-filter before any agentic judge.** If judges must be agents, verification cost rivals generation cost. Run deterministic checks first (did the PR open, did the build pass, did the process exit nonzero) and only escalate ambiguous rollouts to the full agentic judge. This is routing applied to verification and it is the highest-leverage cost reduction available in this pipeline.
4. **Enforce read-only judge permissions as a hard invariant.** Their warning about the judge accidentally mutating environment state or triggering a deployment is a real failure mode with a silent signature: it corrupts the reward for every subsequent rollout in that environment. Bake read-only into the judge's credentials, not into its prompt.
5. **Use conditional partial-credit grading in compression evaluation.** The dynamic-rubric idea (assume the earlier wrong step is correct, grade the rest) directly addresses a problem in evaluating pruned or quantized models on multi-step tasks, where a single early divergence zeroes an otherwise-competent trajectory. Binary end-state scoring makes compression look worse than it is on long tasks. Conditional grading separates "degraded reasoning throughout" from "one bad step."
6. **Treat the 4-month doubling as a planning input, not a headline.** If the 50% horizon is at 14 to 20 hours and doubling every 4 months, any evaluation suite built today for current capability will be saturated within two to three quarters. Build eval sets with headroom deliberately, or budget for continuous replacement.
