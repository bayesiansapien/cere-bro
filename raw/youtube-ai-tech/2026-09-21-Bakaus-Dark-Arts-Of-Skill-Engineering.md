# The Dark Arts of Skill Engineering — Paul Bakaus, Renaissance Geek (Impeccable)

**Channel:** AI Engineer
**Published:** 2026-09-21
**Source:** https://www.youtube.com/watch?v=SQMCtZX3trg

## TL;DR
Bakaus built Impeccable, an open-source design skill that now sits around 265,000 installs, and this talk is the postmortem on what it took to make a skill actually work across harnesses and models. The thesis is a reframe: prompting is the starter level, harness engineering is where you end up. A skill is not a packaged prompt, it is an extension to whoever's harness is running it, on the same conceptual footing as MCP, and it has capabilities prompting does not. Nine techniques follow, and the load-bearing insight under all of them is that **the median is the model's gravity**. No quantity of carefully written prose overcomes it. Banning a behaviour does not create variety, it relocates the model to the adjacent cluster, which is why AI slop moved from purple gradients to what he calls Claude beige. The countermeasures are structural rather than rhetorical: adversarial sub-agents that cannot see each other's work, injected randomness to force divergence, internal mixture-of-experts routing so rule sets do not blur, persistent memory in the skill folder, script stdout as a higher-compliance instruction channel than prose, hooks as passive guardrails, hijacking harness capabilities like the in-app browser, per-harness and per-model compilation, and designing for the weakest model in the distribution. Every line of Impeccable is ablation tested against every model he supports.

## Key Takeaways
- **Self-review is anchored review.** Ask a coding agent to review its own work and it rates it highly, because it is grading its own homework. Impeccable's critique command spawns two sub-agents that are blind to each other, one acting as a design director looking for hierarchy and slop with browser tools, one running a deterministic linter and collecting browser evidence. The main thread synthesises both. Two blind opinions beat one confident guess.
- **The two failure modes that motivated it are instructive.** A genuinely good page plus a linter reporting 500 nits makes the single-thread model conclude the design is bad. An empty or terrible page with no detected issues makes it conclude the design is great. Neither signal alone is usable, and neither is the naive combination, because the model anchors on whichever arrived in its context.
- **Bans move the problem; anti-attractors solve it.** Three divergence techniques, easy to hard: ask for the top three picks then discard them, repeating until far enough from the attractor; generate a hundred candidates and have a **sub-agent** rank them, specifically because it lacks the generating context; or inject entropy from a script. Impeccable's `color.js` holds over a hundred hand-picked primaries and seeds palette generation from them, so the same brief produces materially different output across runs.
- **Impeccable is an MoE skill.** Cramming everything into one SKILL.md blurs instruction following. Instead it routes internally to different MD files per capability (`critique`, `polish`), and separately infers from the brief whether the task is brand or product design, loading entirely different rule registers. His example of why: the old Anthropic frontend-design skill said avoid system fonts, which is right for a landing page and wrong for product UI, where native feel is the goal.
- **Skills can compound across sessions.** Claude exposes an environment variable resolving to the skill directory; other harnesses do not, so Impeccable uses a repo-root folder. Critiques are written to disk and gitignored, then read by later polish runs, including from different sessions. User disagreements ("I don't agree, I like my Instrument fonts") persist as preferences. His own refactor workflow spawns a skill across sessions, one file at a time, accumulating context until the codebase is covered.
- **Script stdout is a stronger instruction channel than prose, and this is the most reusable finding in the talk.** Every Impeccable invocation runs `context.mjs`, which merges `product.md` and `design.md` into the session, and when they are missing emits structured JSON stating exactly what to do about it. Bakaus reports that instructions arriving via a script's standard out are followed significantly more reliably than the same rule buried in skill prose.
- **That technique costs prompt caching, and he is precise about the boundary.** The skill body still caches. The dynamic shell execution and its output do not, because the result could be anything. His recommendation: worth it in interactive scenarios, wrong if the skill runs many times and you need the whole thing cached.
- **Hooks are guardrails that fire whether or not anyone remembers the command.** Impeccable ships a design linter as hooks installed into Claude Code, Cursor, Codex and GitHub Copilot. Post-tool-use hooks fire after a write and let the model self-correct, which works when the model follows instructions well. For weaker models such as Cursor's Composer, he uses pre-tool-use hooks that block the write outright. Ship granular ignore rules or false positives make the thing unusable.
- **Live mode is the harness-exploitation showcase.** No MCP. A local poller injects a snippet into the dev server, page events return over server-sent events, and then the poller **terminates**, emitting a stdout message the model reads as an event. Visual picking in the in-app browser becomes a steering signal in the chat thread. The clever part is using process exit as the notification mechanism.
- **Harness differences are the hidden tax.** Sub-agents are widely supported but who can spawn one differs: Claude programmatically, Codex only on explicit user request, Cursor usually agent-chosen. Codex's ask-user tool exists only in plan mode, so outside plan mode a skill that wants to ask questions silently infers instead. Background job completion wakes the model in Claude Code but not in Codex, which is why live mode runs foreground and blocks the thread in Cursor and Codex.
- **Models have distinct overfitting tails.** Gemini animates every image with a hover zoom. Codex loves bad letter spacing, extreme border radii and hairline borders regardless of context. Telling Claude not to letter-space too much makes it over-correct in the opposite direction, which is why corrections cannot live in the shared skill body. Impeccable emits harness-specific and model-specific builds with substitution variables and per-model XML blocks.
- **Give the weak model what it wants.** GPT models love the word "gate," so the Codex-specific MD is structured as eight gates that must each be passed, logged individually, and explicitly may not be compressed. The general law: **if a gate can be skipped, it will be.** Relatedly, Codex will not spawn sub-agents when it can avoid it, and the effective lever is telling it that failing to do so means delivering a degraded user experience, which it will go out of its way to avoid.
- **On taste, he breaks with his own field.** He does not think taste is solvable at the model level, because taste is scars and uniqueness, and anything universally adopted stops reading as tasteful. Models are actively bad judges of it: Gemini rates a viewport higher the more is crammed into it. His workaround is to build judges that **invert** the model's rating, which works, and which he concedes is strange.

## Architecture & Optimization Mechanics
**The MoE framing is not a metaphor he reaches for casually, and the analogy is tighter than it first appears.** Impeccable routes to different rule sets based on inferred task type, exactly as an MoE layer routes tokens to experts. The failure it avoids is the same failure a dense model has relative to a sparse one: a single parameter set forced to serve conflicting objectives degrades on all of them. His system-fonts example is a clean instance of destructive interference between two rule sets that are each individually correct. The engineering lesson transfers directly to router design: the win comes from the routing decision being made on a signal that actually separates the regimes, and the cost is that a wrong route is worse than no route at all. He handles this by routing on the brief, which is the highest-signal input available before work starts.

**The blind-sub-agent pattern is ensemble decorrelation, and the blindness is the whole mechanism.** Two judges sharing context produce correlated errors, which is why single-thread critique fails in both directions he describes. This is the same structural point that governs whether a cheap-model fallback in a routing cascade is genuinely a safety net: if the fallback and the primary were trained on overlapping data and evaluated on the same benchmarks, their failure modes are correlated and the cascade provides less insurance than its architecture implies. Bakaus enforces decorrelation by construction, denying the second agent the first's output. In a router, the analogous move is to ensure the escalation path differs in training lineage, not just in parameter count.

**The stdout-over-prose finding is the most actionable thing here and deserves an explanation the talk does not give.** A rule sitting in the skill body is one of hundreds of tokens competing for attention, positioned wherever it happened to be written. The same instruction arriving as fresh tool output lands at the end of context, is recent, and is structurally marked as a result rather than as background. Recency and role both favour compliance. The practical upshot for anyone building agentic evaluation or optimization tooling: move directives that must be followed out of static instructions and into dynamic tool returns.

**The prompt-caching tradeoff is stated correctly and is the one cost worth reasoning about carefully.** Any dynamic content injected into a prefix invalidates the cache from that point forward. Bakaus's distinction between the cached skill body and the uncached dynamic portion is the right mental model, and his decision rule, interactive workloads yes and high-frequency repeated workloads no, is the correct economic read. This generalises to prompt architecture broadly: order context so that everything static precedes everything dynamic, and the cache boundary falls as late as possible.

**The ablation harness is the part most relevant to research practice.** Every rule in Impeccable carries an XML tag with a unique identifier. The harness removes the line, runs evals across all supported models, adds it back, and uses the deterministic detection engine to measure whether anything changed. Around it sits an eval harness reproducing each target harness's conditions and tools via the respective SDKs, an LLM simulating the user for interactive turns, and a mixture-of-judges design evaluator, run across roughly 20 niches and 5 to 10 trials per model per release, including against competing skills as baselines. He is candid that this is expensive and does not recommend it generally. It is nonetheless the correct methodology, and it is more rigorous than most published prompt-engineering work.

**Per-model compilation is a real result about instruction interference.** Telling Claude not to letter-space too much produces over-correction. This is not a quirk, it is what you should expect when a negative instruction addresses a behaviour the model's prior does not actually exhibit: the instruction still shifts the distribution, just in the wrong direction. It is the same phenomenon as the ban-relocates-to-the-next-cluster finding, and it is a strong argument against shared negative constraints in any multi-model system.

## Grounded Context (Web Enrichment)
**The ecosystem context explains why the harness-differences section is as long as it is.** Anthropic released Agent Skills as an open standard on 18 December 2025. Adoption was unusually fast: OpenAI, Google, GitHub and Cursor within weeks, and 26 or more platforms since, including Codex, Gemini CLI and VS Code. The format itself is minimal, requiring only `name` and `description` in YAML frontmatter plus a Markdown body, with three-tier progressive disclosure: roughly 100 tokens per skill at discovery, the full body under a recommended 5,000 tokens on activation, and reference files on demand during execution. Community directories such as skills.sh list hundreds of thousands of skills, and SkillsMP indexed over 400,000 across platforms within three months of release.

**That is the actual subject of this talk.** A format standardised in under three months across two dozen platforms standardises the file, not the runtime. Sub-agent spawning permissions, ask-user tool availability, background-job completion notification and hook syntax all remained per-harness, and every one of them is load-bearing for a non-trivial skill. Bakaus is documenting the gap between a standard that was adopted quickly and a runtime contract that does not exist. His closing complaint, that `npx skills` copies one directory rather than honouring per-harness builds, and that he maintains his own CLI because of it, is the concrete cost of that gap. His pull request against the project is still unmerged.

**Impeccable's traction is real, which matters for weighing the advice.** Roughly 265,000 installs as of mid-September 2026, Apache 2.0 licensed, and 17 commands spanning audit, critique, polish, simplify and animate. Bakaus positions it against Anthropic's own frontend-design skill rather than as a complement: frontend-design gives Claude better taste, Impeccable gives you the controls. He also says publicly that many popular design skills, his own included, were not actually very good at design, which is the kind of claim that only reads as credible from someone running ablations.

**One piece of self-awareness worth recording.** Bakaus created jQuery UI, whose first default theme was orange, and says he turned the web orange overnight because people did not change the theme. He draws the line directly to Tailwind's purple sample theme producing the purple-gradient era of AI slop. Defaults propagate at a scale that intentions do not, and someone who has caused it once is a more reliable witness on the point.

**Where I would push back.** The claim that taste cannot be solved at the model level is asserted rather than argued, and his own evidence undercuts it slightly. Discovering that Gemini rates crowded viewports higher, and then building a judge that inverts the rating, is a demonstration that the model has learned a *consistent* preference that happens to be anticorrelated with human judgement. Consistent and inverted is a far more tractable problem than absent. What he has actually shown is that current models are miscalibrated on this axis, not that the axis is unlearnable. The "taste is scars" argument is a claim about novelty economics, which is a different claim from the one about model capability, and the talk runs them together.

**One practical caveat on the memory technique.** Persisting critiques and user preferences into a skill folder is genuinely useful and is also an accumulating context cost with no eviction policy described. Over a long-lived repo, "look at all prior critiques and see the progression" grows without bound. The talk does not mention summarisation, expiry or relevance filtering, and any production version of this needs one.

## Real-World Application / Actionable Step
**The highest-value immediate change: move must-follow instructions from static prose into dynamic tool output.** If you maintain any agentic harness for experiments, benchmarking or model selection, and there are rules that get skipped, stop rewriting the prose. Emit them from a script's stdout at the point they become relevant. Bakaus's report that compliance improves significantly is consistent with how attention and recency work, and it costs an afternoon to test. Pair it with the cache rule: keep everything static ahead of everything dynamic so the cache boundary falls as late as possible.

**Adopt blind adversarial review for anything where a model evaluates its own output.** Concretely, for compression and routing work: when using an LLM judge to assess whether a quantized or pruned checkpoint's outputs remain acceptable, the judge must not see the generating configuration, the claimed compression ratio, or the prior evaluation. Any of those anchor it. Run two judges with disjoint evidence, one with the deterministic metrics and one with the raw outputs, and synthesise separately. The two failure modes Bakaus names map exactly onto this setting: a good checkpoint with many small metric regressions gets rejected, and a degenerate checkpoint that trips no automated check gets passed.

**Steal the ablation harness structure, at reduced scale.** Tag every rule, heuristic and threshold in your evaluation or routing configuration with a unique identifier. Build the ability to remove one, re-run, and diff against a deterministic checker. You do not need his coverage, 20 niches times 5 to 10 trials times every model, to get value. Even a weekly ablation over the ten most load-bearing lines will reveal which of them are doing nothing, and prompt configurations accumulate dead rules faster than code does because nothing fails when a rule stops mattering.

**Apply the anti-attractor idea to hyperparameter and architecture search.** The observation that a model asked for ideas returns the same cluster repeatedly, and that a script-injected random seed genuinely relocates it, transfers directly. When asking a model to propose compression strategies, pruning schedules or routing policies, seed the request with an unexpected constraint drawn from a list you control rather than asking openly. Then rank candidates with a **fresh** sub-agent that has not seen the generation context, because the generating context is what produces the convergence in the first place.

**For the router thesis specifically, hold onto the decorrelation point.** Bakaus enforces blindness between critics because shared context produces correlated verdicts. A cheap-model fallback provides real insurance only to the extent its failure modes are independent of the primary's. Worth auditing whether your escalation path is genuinely independent in training lineage and evaluation data, or merely separate in parameter count.

**If building anything distributed across harnesses, design for the weakest model and make the gates unskippable.** Bakaus's law is worth quoting verbatim in a design doc: if the gate can be skipped, it will be. The enforcement mechanism that works is requiring an explicit logged result per gate with an explicit prohibition on compressing them. The second lever, telling the model that taking the cheap path means delivering a degraded experience, is a genuinely useful piece of applied psychology and costs nothing to add.
