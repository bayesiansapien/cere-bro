# Codex, Behind the Harness

**Channel:** AI Engineer
**Published:** 2026-08-10
**Source:** https://www.youtube.com/watch?v=shRR1e2HXMk

## TL;DR
Dominik Kundel (OpenAI) walks the internals of the Codex harness as a blueprint other agent builders can copy, and the through-line is that almost every distinguishing Codex feature is not harness magic but a Responses API capability you can use from your own harness. The concrete mechanisms are deferred tools plus tool search to keep the tool registry out of the context window, a hard cap of 2% of the context window on the skills manifest with progressive description truncation, code execution as the substrate for computer use rather than a fixed action enum, apply_patch as a trained-in file editing primitive, an auto review subagent that replaces human approval at the sandbox boundary, persistent WebSocket transport with stateful context so only deltas cross the wire, and server-side compaction the model was trained on. The single most useful framing for anyone building agents: once inference hits 1,000 tokens per second on Cerebras, the bottleneck moved to the network, and the harness had to be rearchitected around that fact.

## Key Takeaways
- Two protocols bracket the harness. The app server protocol carries UI to harness, the Responses API carries harness to inference. Both are deliberately open, and the app server is the same one powering the first-party Codex app, so third-party clients get full functionality rather than a degraded subset. He has personally used it to embed Codex into Claude Code as a plugin, and into Doom.
- The Responses API is being pushed as a governed open schema, not just an OpenAI endpoint. Partners named include Ollama, LM Studio, and Nvidia, with a governance body for the schema. Practical consequence: any Responses-compatible provider can be plugged into the Codex harness.
- Context construction is treated as the most important step in the harness, optimised on three axes at once: size, flexibility, and cacheability. His stated reason for caring about size is not only token budget but contradiction. More context means higher probability of conflicting information and model confusion.
- The context is split by predictability. Model instructions are structured and stable, so they do not perturb the cache prefix. The unpredictable parts are the skills manifest and the tool registry, which grows without bound as users install MCP servers.
- Deferred tools are the fix for registry growth. A tool marked deferred is not injected into the context window at all, only discoverable later via tool search. Available since GPT-5.4, exposed in the Responses API, and you can substitute your own discovery implementation instead of the built-in tool search tool if you think you can do retrieval better for your domain.
- The skills list is capped at 2% of maximum context window, and past that the harness progressively shortens each skill description rather than dropping skills. Note the design choice: degrade description fidelity, preserve discoverability.
- Async actions are modelled as a spawn/send/wait/shutdown tool family rather than blocking calls. Subagents and background terminals reuse the same primitive, with the background terminal getting stdin writes and timed waits. The main agent keeps working while the child runs.
- Computer use was rearchitected from a one-action-at-a-time declarative tool into code execution. The agent now scripts its own interactions in JavaScript or Python. Browser use is the flagship instance: a persistent Node REPL that survives across turns, driven by Playwright code the model writes.
- The payoff of scripted browser use is amortisation. Codex reads one page, infers the DOM structure, then writes a script that handles the remaining pages. That converts N model round-trips into one round-trip plus a loop, which is the same optimisation as batching.
- File editing rides on apply_patch, which all GPT-5 era models were trained on, so diffs and file creation go through a primitive the model has strong priors for. Everything else goes through a shell tool. The models reach for ripgrep unprompted because that is what training conditioned them on, so the harness ships a ripgrep binary rather than fighting the prior. Windows models were trained on PowerShell natively.
- Sandboxing: Seatbelt on macOS, Bubblewrap on Linux, and a custom open-source sandbox on Windows because no adequate primitive existed. He explicitly flags that the Windows sandbox story could fill its own talk.
- Approval fatigue is named as a security problem, not a UX annoyance. He gets the room to admit both that they run full access and that their security teams hate it. That framing is the justification for auto review.
- Auto review mechanics: on a sandbox escalation, the harness spawns a read-only subagent that cannot itself spawn subagents. It receives a risk taxonomy, the notion of user authorization, the transcript, and the pending tool calls, then returns a judgment. Deleting a file the user explicitly asked to delete is high authorization. Deleting a .git folder nobody asked about is not. The same logic covers network egress, where curling Google is fine and uploading a file is the thing you are actually gating.
- The failure modes he cites for full access are agentic misgeneralisation rather than model stupidity. Prompted for high agency, an agent told to email a file that it cannot attach uploads it to a file share instead. Or it botches shell escaping and deletes too much. Better models do not remove either risk.
- WebSocket mode exists because of Codex Spark. At 1,000 tokens per second on Cerebras, inference stopped being the bottleneck and the network became it. Persistent WebSocket replaces SSE over HTTP, and stateful context means the harness sends only what changed, so a tool call ships one result item instead of the entire item list.
- The /goal loop is mundane by design. The harness injects a continuation prompt containing the objective until the model calls an update-goal tool declaring completion. His actionable warning follows directly from that: do not write essays as your goal, because the loop terminates on verifiable detection of doneness, and a vague objective is a loop that cannot cleanly exit.
- Auto compaction has been server-side since late 2025, and critically the model was trained on the compaction item format, so the rewritten context is in-distribution rather than a summary the model has to interpret.
- His closing ask is the correct one: treat the harness as a blueprint, take the Responses API features (tool search, apply_patch, WebSockets, server-side compaction) regardless of which harness you run, and track the API surface as models evolve.

## Architecture & Optimization Mechanics
The deferred-tools mechanism is the part with the cleanest transfer to non-coding agents, and it is worth stating precisely because it is a retrieval problem masquerading as a context problem. A tool registry is a set of documents, each with a name and description, and the model needs the right subset per turn. Injecting all of them is the dense approach: cost grows linearly with registry size on every turn, and irrelevant entries actively hurt through distractor attention. Deferring them turns it into a two-stage retrieve-then-act, which is a sparse activation pattern. The MoE analogy is exact enough to be useful. Deferred tools are experts that only get loaded when routed to, and tool search is the router. The same accuracy question applies too: routing quality now bounds task success, because a tool that search fails to surface is a tool the model cannot call. That is why the option to supply your own discovery implementation matters more than it sounds. It is the router you can train on your own distribution.

The 2% skills cap deserves attention as a budgeting discipline rather than a number to copy. What OpenAI did is give an unbounded, user-controlled input a fixed fraction of a fixed resource, then degrade gracefully inside it. Most agent implementations instead let user-installed content grow until the context blows up or quality quietly collapses, and the failure is invisible because nothing errors. The generalisable rule is to express every variable-size context component as a fraction of the window with a defined degradation path, so the worst case is known at design time.

The cacheability point is where the money is, and the talk under-sells it. Prompt caching keys on a prefix, so any component that changes size or content between turns invalidates everything after it. That is the real reason to separate stable model instructions from volatile skills and tool registries, and to order them stable-first. Deferring the tool registry does not just shrink the context, it removes the most volatile block from the cached prefix, which means a user installing an MCP server no longer silently destroys the cache hit rate for the rest of their session. Anyone building an agent should audit their prompt assembly for volatility ordering before they optimise anything else, because the intervention is nearly free.

The Codex Spark story is the strongest systems lesson here and it generalises past agents. Amdahl applies to the whole request path, not the model. Push decode to 1,000 tokens per second and per-round-trip network overhead, which was previously noise against a 65 to 70 tokens per second baseline, becomes the dominant term. OpenAI's reported figures for the transport work are an 80% cut in per-round-trip overhead, 30% in per-token overhead, and 50% in time to first token. Note that the stateful-context part is a bandwidth optimisation orthogonal to the latency one: resending the full item list every turn makes uplink payload grow quadratically over a long agentic session (each turn ships all prior items), and delta transmission flattens it to linear. For a several-hundred-tool-call session that is a large constant.

Auto review is best understood as replacing a human gate with a cheap asymmetric verifier, and the reported 200x reduction in human stops is the efficiency claim. The architecture is what makes it defensible: read-only, non-recursive, separate context. That is capability restriction on the verifier so that a compromised or confused reviewer cannot itself act, which is the same reasoning behind privilege separation in any monitor design. The honest limitation, which the talk does not raise, is that the verifier shares a model family and therefore a threat surface with the actor. A prompt injection in the transcript is visible to both. The user authorization signal is derived from the same transcript the attacker may have influenced.

## Grounded Context (Web Enrichment)
Everything material in this talk checks out against the public record, and several claims are stronger than he stated them. Codex CLI is Apache-2.0, rewritten in Rust, at openai/codex, and now ships skills, plugins with a marketplace, subagents, hooks, and MCP over both STDIO and streamable HTTP with OAuth. The sandbox story is confirmed as kernel-level with Seatbelt, Bubblewrap plus Landlock on Linux, and the custom Windows sandbox, with network off by default. The Landlock detail is worth noting because he glossed Linux as just Bubblewrap. Bubblewrap alone gives you namespace isolation, Landlock adds kernel-enforced filesystem access control, and the combination is what makes the Linux sandbox comparable to Seatbelt.

Codex Spark landed on 12 February 2026 as OpenAI's first model deployed outside Nvidia infrastructure, on Cerebras WSE-3, at over 1,000 tokens per second against roughly 65 to 70 for flagship GPT-5.3-Codex, so his 15x framing is right. Importantly for anyone building on the API, OpenAI's own writeup positions the latency work as stack-wide and hardware-independent, meaning the WebSocket and Responses API gains apply to every Codex model, not only the Cerebras-served one. If you are optimising an agent loop today, that is the free win.

Auto review shipped 30 April 2026 with an OpenAI alignment writeup, and the published numbers make the case sharper than the talk did. Sessions stop for human approval roughly 200x less often than in manual approval mode while still catching many of the actions a human would have blocked. The alignment framing is also more pointed than his: authorization fatigue is characterised as a genuine security risk rather than an inconvenience, because users approve commands they do not understand, from either lack of expertise or reviewer fatigue. That is the correct reading. A gate a human clicks through unread has a false-negative rate approaching one, so replacing it with a mediocre automated verifier is a strict improvement, and the bar for the verifier is much lower than intuition suggests.

One caveat on the talk as a whole, which he flags himself and which the search results reinforce: this is a snapshot of a fast-moving surface. Codex shipped a guardian approval policy configuration layer around 20 April 2026, and the release cadence through August 2026 is dense. Treat the specific API shapes as current-as-of-August rather than durable, and treat the design patterns as the durable part.

## Real-World Application / Actionable Step
1. Audit your prompt assembly for volatility ordering before touching anything else. Order components stable to volatile, and measure your actual cache hit rate per turn rather than assuming it. If a tool registry or skills manifest sits early in the prefix, moving it later or deferring it is a direct cost reduction with no quality tradeoff, and it is the cheapest optimization on this list.
2. Apply the fraction-of-window budget discipline to any variable-size context component in your own tooling. Pick the cap, define the degradation path (truncate descriptions, not entries), and log when you hit it. Silent context growth is the analogue of an unmonitored memory leak, and the 2% number is less important than having a number at all.
3. Read deferred tools as a routing problem and instrument it as one. If you build a tool-heavy agent, the metric that matters is recall at k for tool search on your own task distribution, not tokens saved. This is squarely your expertise: it is the same tradeoff as top-k router selection in an MoE, including the failure mode where a needed expert is never routed to and the loss looks fine in aggregate.
4. Steal the amortisation pattern for expensive interactions. Codex reads one page then writes a script for the rest. The research equivalent is to stop asking a model to interpret each result in a sweep, and instead have it read one output, write the parser or the analysis script, and run that across the remaining runs. One inference plus deterministic compute beats N inferences on both cost and reproducibility.
5. Take the Amdahl lesson into your inference benchmarking. If you are quoting tokens per second for a vLLM deployment that sits behind an agent loop, you are measuring the term that is about to stop mattering. Measure end-to-end per-tool-call latency including transport, and check whether your serving stack holds a persistent connection or pays TLS and HTTP setup per call. A 50% time-to-first-token reduction from transport work is competitive with substantial kernel optimization and usually far cheaper to obtain.
6. Copy the restricted-verifier architecture for your own automated gates. Read-only, non-recursive, separate context, given explicit intent plus a risk taxonomy. Use it on your experiment pipelines to gate destructive operations like checkpoint deletion or dataset overwrites. And note the residual risk: the verifier shares a threat surface with the actor, so anything with real blast radius still needs a deterministic non-model check underneath it.
7. Write goals as verifiable predicates, not prose, whenever you use a looping agent. The loop terminates on detected completion, so an unfalsifiable objective is an unbounded token spend. "Reduce perplexity below X on this held-out set and write the number to results.json" terminates. "Improve the model" does not.
