# x402 Isn't Good (Yet) (Jan Curn, Apify)

**Channel:** AI Engineer
**Published:** 2026-09-01
**Source:** https://www.youtube.com/watch?v=h6mi88VrPtQ

## TL;DR
The most technically honest talk in the agentic-payments track, deliberately modelled on David Cramer's "MCP isn't good yet" from the previous year, with the same structure: this technology is genuinely important, here are its concrete defects, keep your expectations calibrated. Curn's specific complaints are all real and all verifiable. x402 has a double-spend window between verification and settlement, so a client can generate a thousand signatures against the same funds and get a thousand jobs done before any of it hits the chain. The spec mandates HTTP 402 as the first response while MCP mandates 401, which cannot both be satisfied, so companies are spawning `x402.example.com`, `mcp.example.com`, and `mpp.example.com` hostnames to work around a status-code collision. And the original `exact` scheme assumed fixed per-call pricing, which does not fit metered work. Apify's answer sidesteps the protocol entirely: `agi.apify.com`, an "agent general interface" that is a single markdown page instructing agents how to buy a prepaid Apify token, after which they use the normal API. His closing prediction is the sharpest economic point in the whole track: agentic payments explode when token subsidies end and buy-versus-build starts having a real price attached.

## Key Takeaways
- **Scale of the marketplace makes this credible.** Apify hosts around 45,000 tools ("actors") for data extraction across social media, e-commerce, travel, search, and maps, plus agentic automations. Community developers earn over $1 million a month in payouts. Two days before the talk they launched an x402 integration with Coinbase, taking the agentic market from roughly 2,000 available tools to about 22,000, a 10x expansion of the supply side single-handedly.
- **The double-spend window is the headline defect.** Flow: client calls, server must return 402, client signs an authorization, server verifies with a facilitator such as Coinbase, server does the work, server asks the facilitator to settle, facilitator writes to chain. Between verification and settlement the same wallet balance can authorise other transactions. For zero-marginal-cost API calls a provider can tolerate it. For non-trivial work, or work where you pay an external service, you can complete the job and find the money gone.
- **The workaround has a real cost.** Do the work only after settlement completes, which means the client waits on chain confirmation and you had better not fail after taking payment.
- **The 402-versus-401 collision is an unforced error.** The spec enforces 402 as the first response; MCP authorization enforces 401. You cannot return both. The industry response, one API hostname per payment protocol, is an anti-pattern, and Curn's analogy lands: imagine twenty different Amazons, one per credit card. His proposed fix is a `Payment-Required` header rather than a mandated status code, and he is explicit that 402 was chosen because "finally making internet money work" is great marketing for a status code that sat unused for thirty years.
- **The metered-billing gap took a year to half-close.** x402 launched May 2025 with only the `exact` scheme, fixed fee per call. Version two was announced December 2025 promising an `up to` scheme for variable cost. It shipped roughly two or three months before this talk. And `up to` did not solve double-spending, it only lets the server charge anything up to a client-declared ceiling.
- **Their interim hack is instructive.** Charge a fixed amount using `exact`, do the metered work, then refund the unused remainder. It works, at the cost of two on-chain transactions, two settlement delays, extra fees, and requiring the client to trust the server to actually refund.
- **Batch settlement, shipped about two months before the talk, looks like the real fix.** Client deposits into escrow on-chain, receives a cryptographic voucher, signs many micropayments off-chain against that voucher, and the accumulated micropayments settle in periodic batches with the escrow remainder eventually released. Apify had not yet implemented it.
- **`agi.apify.com` is the pragmatic answer and the most reusable idea here.** Rather than reshape an API that tens of thousands of paying customers depend on for every new payment standard, they published a markdown document for agents describing how to buy a prepaid token via x402 or MPP. The token then works with the existing API and MCP server unchanged. No skill file needed, agents just read the page. Because it is a document rather than an API, they can iterate without backwards-compatibility obligations.
- **The protocol landscape is genuinely absurd, and he reads the whole list.** L402, Mastercard Agent Pay, x402 (Coinbase), KYA-Pay (Skyfire with Visa), AP2 (Google), ACP (OpenAI and Stripe), Tab (Visa), UCP (Google and Shopify), ACTP (Alipay), MPP (Stripe and Tempo), AMP (Alipay), one from UnionPay, APP (OKX), and Agent Pay for Machines (Mastercard). Every payments incumbent wants a share of the projected volume.
- **His pro-crypto argument is unusually credible because he is not a crypto advocate.** He states he holds nothing and was long sceptical. His case is narrow and mechanical: card, PayPal, and ACH rails are far too expensive for microtransactions, and more importantly, agentic payments must be irreversible because chargebacks assume a disputable human buyer and there is no agent identity to assess. Add that a genuinely decentralised chain cannot be turned into a rent-extraction chokepoint the way a card network can, and crypto fits this use case specifically.
- **The volume reality check, from a vendor with every incentive to inflate it.** Roughly $1 million per month in transaction volume. "This is nothing." He also notes x402 is about 20x larger than Stripe's MPP on both count and volume.

## Architecture & Optimization Mechanics
- **Verify-then-work-then-settle is a time-of-check-to-time-of-use bug at the protocol level.** The authorization is validated against state that can change before the debit lands. The general fix is to make the check and the effect atomic, which on-chain means settling first, and settling first reintroduces latency. Batch settlement resolves it properly by moving the accounting off-chain against escrowed funds, so the balance is provably reserved before any work happens. That is the correct shape and it is the same reservation pattern as a database holding a lock or a scheduler reserving GPU memory before admitting a job.
- **Batch settlement is amortisation of a fixed per-operation cost, and the numbers make it mandatory.** With average transaction values around $0.13 and sub-cent nanopayments, one chain write per request is economically incoherent. Escrow plus off-chain vouchers plus periodic settlement is structurally identical to write-behind caching or to batching inference requests: trade per-item finality latency for a large reduction in per-item overhead. Same tradeoff, same failure mode if the batch is lost before flush.
- **`agi.apify.com` is the strongest engineering idea in the talk and it generalises well beyond payments.** A markdown document read by agents is a versionless, backwards-compatibility-free integration surface. Their reasoning is precise: an API with tens of thousands of dependent customers cannot absorb a new standard every quarter, but a document can be rewritten daily because agents fetch the current version. This is the same insight as [Christopher Burns's package-local docs](./2026-08-26-Getting-LLMs-to-Recommend-Your-Library-Christopher-Burns.md) and the same insight as skills-as-instructions, arrived at from a third direction: for agent consumers, prose instructions are a legitimate and cheaper interface than a typed API.
- **Prepaid token as protocol adapter.** By converting any payment protocol into a token at the boundary, the core system stays protocol-agnostic. One thin adapter per standard, zero changes to the API. This is the payments equivalent of a normalization layer in an LLM gateway, and it is the right place to absorb ecosystem churn.
- **The token-subsidy argument is the economic core and deserves emphasis.** Curn's claim is that build-versus-buy is currently distorted because inference is subsidised, so building a scraper with an agent looks free while buying a maintained one has a visible price. When agents pay true token cost, buying a specialised tool becomes obviously cheaper than generating and maintaining an equivalent, and that is when per-call payment infrastructure gets used. This is the same underlying observation as the [capex-to-revenue gap](./2026-08-27-AI-Is-A-Massive-Scam-Ed-Zitron-DOAC.md) seen from the demand side, and it predicts that efficiency work and paid-tool markets both become more valuable simultaneously.

## Grounded Context (Web Enrichment)
Curn's criticisms are not idiosyncratic. There is now peer-reviewable security literature on exactly these failure modes, including "Free-Riding the Agentic Web: A Systematic Security Analysis of x402 Payments" and "Five Attacks on x402 Agentic Payment Protocol," and the documented findings are worse than what he had time to present.

Three specifics worth knowing. First, an observed race condition where five concurrent requests resulted in four receiving the same merchant settlement proof, which is the double-spend problem manifesting as a concurrency bug rather than a deliberate attack. Second, the settlement path does not bind facilitator identity to the authorization, so any observer holding a signed authorization can submit the transfer first and cause the legitimate facilitator's settlement to fail despite a valid payment intent. That is frontrunning, and it applies whenever payment proofs are exposed. Third, a settlement-gate omission in the official Python Flask adapter allowed 302 redirects to be served without settling, delivering content at zero on-chain payment with the nonce never consumed. That last one is a free-content bug in reference code, not a theoretical concern.

On the fixes: batch settlement is real and documented, explicitly built on the `up to` mental model, with the 402 header advertising a per-interaction ceiling and authorizations accumulating silently until batch finalisation. Apify's own launch post confirms the x402 integration covering over 20,000 actors and confirms `up to` support for variable-cost batch operations, which matches his account.

Two pieces of context Curn omits that sharpen his own conclusion. The x402 Foundation launched April 2, 2026 under Linux Foundation governance with Google, AWS, Stripe, Visa, Mastercard, Solana Foundation, and Polygon Labs backing, so the standard has real institutional weight behind it despite the defects. And the volume picture is even thinner than his $1 million per month suggests: cumulative transactions crossed 160 million by June 2026 with over 90% on Base, but independent tracking puts roughly half of that as gamified or wash activity, with genuine commerce volume around $28,000 per day. So his "this is nothing" is the accurate reading, and the headline transaction counts circulating elsewhere in this conference track are not.

The one place to push back on Curn: his framing that a decentralised chain avoids the rent-extraction problem is weaker than stated, given over 90% of x402 volume settles on Base, which is Coinbase's L2. Concentration on one operator's rollup reproduces much of the chokepoint risk he is trying to escape from card networks. He does not address this.

## Real-World Application / Actionable Step
- **If you expose any paid endpoint to agents, settle before you do expensive work.** This is the concrete defect to design around today. Zero-marginal-cost lookups can tolerate the double-spend window; anything that consumes GPU time, calls a paid upstream, or takes minutes cannot. Accept the added latency or use batch settlement with escrow.
- **Adopt the prepaid-token adapter pattern rather than integrating protocols directly.** Convert whatever payment standard arrives into an internal credit at the boundary, and keep the core API protocol-agnostic. Given fourteen competing standards, this is the only design that does not require rework every quarter, and it took Apify one endpoint.
- **Publish a markdown page for agents instead of extending your API for them.** `agi.apify.com` is trivially reproducible and the reasoning is sound: documents have no backwards-compatibility contract, so you can iterate freely while agents always read the current version. For internal tools Amit's team owns, this is the cheapest way to expose new capability to colleagues' agents without shipping an SDK.
- **Read the security papers before building on x402.** The Flask adapter settlement-gate bug and the facilitator frontrunning issue are both in reference implementations and both let someone get work for free. If you are the seller, you carry that cost. Treat the reference adapters as unaudited.
- **Take the token-subsidy prediction seriously as a planning input.** Curn's claim is that today's build-versus-buy calculus is distorted by subsidised inference. If that is right, the value of both efficiency engineering and specialised paid tooling rises when subsidies end. For Amit that is a direct argument that compression and routing work is counter-cyclical and becomes more valuable, not less, if the funding environment tightens.
- **Do not size a business on x402 volume.** Roughly $28,000 a day in real commerce, from a vendor-friendly measurement. Build the primitives because they will be needed; do not assume the demand exists yet.
