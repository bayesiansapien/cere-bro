# Knowledge Systems: The New GTM Stack — Jeffrey Wang, Exa

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=6pbQgnJ9Voc

## TL;DR
Wang co-founded Exa, a search engine built for agents rather than people, which powers Cursor, Cognition and much of the coding-agent ecosystem. His thesis is that go-to-market is a data problem and therefore an AI engineering problem, and that the product-versus-distribution debate on Twitter is a false choice because failing at either means you do not have a company. The technically interesting content is the four systems Exa runs on itself. An ICP dashboard that uses their own search engine to classify essentially every company in their total addressable market into segments with per-company spend estimates and metadata. Request Lens, an alerting layer over significant customer events. A dozen agents living in Slack with access to internal data, used heavily enough that the GTM team's Devin spend is conspicuous. And JeffBot, a digital clone of himself built over a week off with Opus 4.5, calibrated by analysing 760 of his emails for voice, mining hundreds of past decisions out of Slack and email, and turning those decisions into an eval set. The line to steal is "embeddings over the internet," which is what makes arbitrary semantic slicing of the company universe possible. The three closing principles are agent-first requires API-first, not everything should be a chatbot, and build-versus-buy is a false dichotomy because the real requirement is arbitrary customisability, which purchased software can satisfy if it exposes MCP.

## Key Takeaways
- Embeddings over the internet is the enabling primitive, stated compactly: crawl the web, train embeddings for retrieval quality, and you get arbitrarily powerful semantic filtering over any slice of data you can describe. The ICP dashboard is a downstream application of that, not a separate system.
- Classify the entire TAM, then deep dive per company. Exa enumerates every company in each segment they care about, model providers, AI coding platforms, GTM intelligence tools, attaches anticipated annual spend and metadata to each, and knows almost every company in each segment. This is exhaustive enumeration where the industry norm is sampling.
- Request Lens is a signal layer, structurally identical to what Notion's team built independently: someone signed up, someone spiked usage, someone stopped using, someone important appeared. Three of the seven GTM talks at this conference converged on an event-driven signal primitive as the core abstraction.
- The JeffBot construction has three distinct components and they are worth separating because only two are commonly built. Voice, derived from 760 emails, yielding concrete statistics like 18 words average and closing with "best" rather than "sincerely." A decision-making framework mined from hundreds of historical decisions. And, crucially, an eval set built from those same decisions, used to calibrate the system against how he actually decided.
- Slack history is the decision corpus nobody thinks to mine. Asked what artifacts he used, Wang's answer is that a surprisingly large fraction of what happens at a company is in Slack, and reading enough of it surfaces hundreds of past decisions. That is a labelled dataset of judgement, sitting unused in every company.
- The privilege asymmetry on JeffBot is the security design and it is the right one. When Wang invokes it, it has read and write access across systems. When anyone else invokes it, it can only draft, and it does not get the full MCP and tool set. Same agent, different capability envelope by caller.
- The FDE model at Exa is unusual and Wang flags it as such. Eight or nine forward deployed engineers out of roughly 115 people, who both run and support deals and build and maintain the AI systems that make the deals smoother. His explanation for why this collapsed into one role is that AI made building the tooling cheap enough that supporting revenue and building the support tooling stopped being two jobs.
- Non-technical GTM staff are not vibe coding the interfaces. They use the tools well, supported by explicit training sessions, while the FDE organisation builds and maintains. This is a more honest division than most talks admit to.
- Agent-first requires API-first. Whether the interface is MCP, a CLI or plain HTTP does not matter, but if there is no programmatic surface over internal and external data, no amount of agent sophistication rescues you.
- Not everything should be a chatbot, and the argument against pure dynamic UI is good: a model can generate a bespoke interface per query, but there is real value in a consistent UX for a recurring use case, because users learn tools. Crystallised UIs for known workflows plus a flexible chat agent for the rest.
- Build versus buy is the wrong axis, customisability is the right one. Exa uses Salesforce because it is a good database that has made sensible opinionated choices about what sales looks like, and because it exposes MCP so every agent can reach it. Purchased software that is arbitrarily customisable by agents is equivalent to built software for this purpose.

## Architecture & Optimization Mechanics
The Exa infrastructure is more interesting than the GTM application, and Wang skips over it in one sentence. The published details are directly relevant to compression work: a custom vector database written in Rust using Matryoshka embeddings, document clustering, binary compression and assembly-level SIMD, with the embedding model trained for over a month on a 144-GPU H200 cluster, indexing tens of billions of pages with minute-level refresh and a Fast mode under 425ms.

Matryoshka representation learning is the piece worth dwelling on because it is the cleanest instance of a compression idea that most stacks have not adopted. The training objective nests representations so that the first k dimensions of an embedding are themselves a valid, quality-ordered embedding for any k in a prescribed set. The consequence is that one trained model yields an entire family of embedding sizes at no additional training cost, and truncation becomes a runtime knob rather than a retraining decision. That is qualitatively different from post-hoc dimensionality reduction, which requires fitting a projection and degrades in ways you discover after the fact. For a web-scale index the economics are decisive: you retrieve a large candidate set using aggressively truncated vectors, which is where memory bandwidth and index size dominate, then rerank the survivors with full-width vectors, which is where quality matters and the candidate count is small. The cost profile of the coarse stage falls roughly linearly in the truncation ratio while the recall loss is sublinear, which is the entire reason the technique exists.

Stacking binary compression on top of that compounds the win in the direction that matters for serving. Binary quantisation of embeddings reduces each dimension to one bit, cutting memory by 32x against fp32, and more importantly it converts the distance computation from floating-point dot products to XOR plus popcount, which is where the assembly-level SIMD in their stack earns its keep. Modern cores execute popcount over wide vector registers at extremely high throughput, so the arithmetic intensity of the coarse search stage collapses. The combination, Matryoshka truncation to reduce dimension count and binary quantisation to reduce bits per dimension, attacks the same memory-bandwidth bottleneck along two independent axes, and the quality is recovered by reranking a small survivor set at full precision. This is precisely the coarse-to-fine cascade structure that shows up in every well-optimised retrieval system, and the parallel to speculative decoding is exact: a cheap approximate model proposes, an expensive accurate model verifies over a small set, and the aggregate quality tracks the expensive model while the aggregate cost tracks the cheap one.

The JeffBot eval methodology is the other genuinely transferable idea, and it is more valuable than the persona cloning it was built for. Wang mined hundreds of historical decisions from Slack and email and converted them into an eval set, then calibrated the agent against them. Consider the structure: each historical decision is an input context paired with a known-correct output, where "correct" means what the decision-maker actually chose, and the corpus was produced as a byproduct of working rather than as an annotation exercise. That is a free preference dataset with the labels already attached, and it is the same resource sitting in every engineering organisation. Every code review is a preference pair, the submitted diff and the accepted one. Every incident retrospective is a decision with context and outcome. Every design doc with a chosen option and rejected alternatives is a labelled comparison. Teams building evals for agentic systems routinely commission fresh annotation while ignoring years of accumulated implicit labels, and the accumulated ones have a property the commissioned ones lack: they were produced under real stakes, so they reflect the decision function the practitioner actually uses rather than the one they report using when asked.

The privilege asymmetry deserves credit because the audience question that provoked it was sharp and the answer was better than most. An agent that inherits the founder's full read-write access across every internal system, and is callable by anyone in the company, is a textbook confused deputy: a privileged component induced by a less-privileged caller into exercising authority the caller does not have. Wang's mitigation, that third-party invocations are draft-only with a reduced tool surface, is the correct structural fix because it makes the capability envelope a function of the caller rather than of the agent. What it does not address, and what nobody solved in 2026, is that the draft path still reads privileged data to produce its draft, so the information-flow boundary is looser than the action boundary. A draft that faithfully summarises data the caller is not cleared to see has already leaked it. Action-level restriction is necessary and not sufficient; read scoping has to be caller-dependent too.

## Grounded Context (Web Enrichment)
Exa's position is stronger than the talk conveys. Exa Labs raised a $250M Series C on 20 May 2026 led by a16z at a $2.2B valuation, up from $700M in autumn 2025, bringing total raised to roughly $361 million. It was founded in 2021 by Harvard classmates Will Bryk and Jeffrey Wang, about a year before ChatGPT shipped, on the thesis that AI would need a search engine built for machine consumption rather than human browsing. That timing is the substance of the bet and it paid. They now serve more than 400,000 developers and 5,000-plus companies, index tens of billions of pages with minute-level refresh, and return between 10 and 10,000 links per query across neural, keyword, auto-hybrid and similarity modes.

The infrastructure claims are documented and specific enough to be checkable: Rust, custom vector database, Matryoshka embeddings, document clustering, binary compression, assembly-level SIMD, embedding model trained over a month on 144 H200s, Fast mode under 425ms. Worth cross-referencing against the Oxylabs talk from the same conference, which quoted under 700ms for its fast search API. Two vendors, similar claims, neither publishing P95 or P99 by geography, which is what actually determines whether a multi-hop agent stays inside a latency budget. Take the medians as real and the tail as unknown.

On the confused deputy question, the security literature caught up with this pattern during 2026 and the framing is now standard. The Cloud Security Alliance has a dedicated research note on confused deputy attacks against autonomous agents, HashiCorp published a "before you build agentic AI, understand the confused deputy problem" piece, SANS argues the fix is a credential broker rather than direct delegation, and OWASP's Agentic AI Top 10 ranks Tool Misuse and Exploitation as ASI02. The specific escalation nobody has a good answer for is agent-to-agent delegation: an administrator authorises agent A, agent A delegates to agent B which the administrator never vetted, and B acts with authority nobody granted it. DeepMind published delegation rules in February 2026 addressing exactly this. Wang's design predates most of that guidance and lands on the right side of it, which is worth acknowledging, but "we pay some care to security" for a system with founder-level write access across every company system is a thinner answer than the question deserved.

The FDE structure Wang describes, eight or nine people out of 115 doing both revenue support and internal tooling, is a small-company configuration and he says so when pressed, doubting it scales. That matches the independent analysis in the adjacent Cloudflare and Notion talks and the broader 2026 consensus that FDEs are a surgical instrument confined to high-opportunity accounts rather than a scaled function. At 115 people the collapse of two roles into one is efficient. At 1,000 it is a staffing model with no career ladder.

## Real-World Application / Actionable Step
1. Mine your existing artifacts for evals instead of commissioning annotation. Code review threads, incident retrospectives, design docs with rejected alternatives, and Slack decision threads are labelled preference data produced under real stakes. Wang built a decision eval from hundreds of Slack decisions in a week off. The equivalent for a routing policy is every escalation ticket where a cheap model's answer was rejected, which is a directly usable label for when routing should have gone the other way.
2. Adopt Matryoshka embeddings for any retrieval system where index size or memory bandwidth is the constraint. One training run yields the whole family of dimensions, truncation becomes a runtime knob, and the coarse-to-fine pattern of retrieving wide with truncated vectors and reranking narrow with full ones is where the cost falls without the recall following.
3. Attack embedding cost on both axes, not one. Matryoshka reduces the dimension count, binary quantisation reduces bits per dimension and converts distance computation to XOR-plus-popcount, which SIMD executes at very high throughput. They are independent and they compound, with quality restored by full-precision reranking over a small survivor set.
4. Recognise the coarse-to-fine retrieval cascade as structurally identical to speculative decoding, and check whether the tuning insight transfers. In both cases a cheap proposer generates candidates and an expensive verifier accepts a subset, aggregate quality tracks the verifier and aggregate cost tracks the proposer, and the tunable parameter is candidate count. The acceptance-rate analysis that governs optimal speculation depth is the same mathematics as choosing rerank depth.
5. Make agent capability a function of the caller, not of the agent. Wang's JeffBot is read-write when he invokes it and draft-only for everyone else. Any shared agent holding elevated credentials is a confused deputy by default, and per-caller capability envelopes are the minimum mitigation.
6. Scope reads by caller, not just writes. Restricting a delegated agent to drafting still lets it read privileged data to produce the draft, and a faithful summary of data the caller cannot see is a leak that passed every action-level check. This is the gap in Wang's design and in most deployed ones.
7. Enumerate the population instead of sampling it, when semantic search makes enumeration affordable. Exa classifies every company in its TAM rather than a sample, because embeddings over the whole crawled web make exhaustive classification a query rather than a project. The same shift applies to any place you currently sample: eval sets, failure taxonomies, error analysis over production logs.
8. Do not convert stable workflows into chat. Wang's argument is that a consistent UI for a recurring task is worth more than a bespoke generated one because users learn tools, and dynamic generation should serve the tail. The analogue in ML tooling is that a stable dashboard for a metric you check daily beats regenerating a plot from a prompt every time.
9. Evaluate purchased software on whether it is programmatically customisable, not on whether it was built in-house. Exa keeps Salesforce because it is a good database with sensible opinions that exposes MCP so agents can reach it. The question to ask any vendor is whether an agent can drive the whole surface, and if the answer is a partial API, that is the real build-versus-buy decision.
