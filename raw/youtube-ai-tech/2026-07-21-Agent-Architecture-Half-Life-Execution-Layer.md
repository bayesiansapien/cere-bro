# Your agent architecture has a half-life of 6 months

**Channel:** AI Engineer  
**Published:** 2026-07-21  
**Source:** https://www.youtube.com/watch?v=X1kp-ABIIxQ  

## TL;DR
Dan Farrelly, CTO of Inngest, offers a three-layer mental model for agent systems and argues that only one of the layers is worth investing architectural effort in. Context (models, prompts, tools, memory) decays fastest: prompts last weeks, models last months. Compute (sandboxes, runtimes, browsers) is ephemeral by design. Execution (flow, state, durability, retries, orchestration) can last years if you build it right. The failure he sees repeatedly is teams coupling all three, so the fastest-decaying layer's half-life leaks into the others and every model or framework change forces a rewrite. His prescription: treat execution as the stable substrate, keep state durable and external to the work, and make everything else swappable.

## Key Takeaways
- **The three layers, with his own analogy:** execution is the brain, context is the knowledge, compute is the hands. Half-lives differ by an order of magnitude, so coupling them is technical debt by another name.
- **Three hard requirements for the execution layer.** Resumability: a failure at step 38 of a three-hour run must retry, wait, and continue rather than restart, which means state cannot live in memory or on disk and must be durable and external. Invocation flexibility: crons, event triggers, APIs, human-in-the-loop, sub-agents, dynamic workflows, synchronous, asynchronous, and delayed, all composable. Full-session observability: not just LLM and tool calls but database errors, permission failures, triggers, and performance, traced from the original trigger through the entire stack.
- **The anti-pattern he names explicitly:** using a sandbox for durability, snapshots, or state. Sandboxes are ephemeral and stateless by design. The execution layer is what supplies the sandbox with context, sequence, and durability.
- **What happens when you lack a real execution layer:** the harness starts absorbing queues, workers, polling, backoff, and scheduling, and you end up with bad abstractions you cannot swap out of.
- **The emerging architectures all share the same requirement.** Background agents, dynamic workflows, autonomous loops, and agent factories are all long-running, asynchronous, and delegated. A background agent might run for hours with 200 tool calls, effectively guaranteeing at least one failure, and it is undebuggable without full tracing.
- **His decomposition of a loop architecture is the most concrete part of the talk.** Three functions: a cron that pulls system metrics and asks a model whether things are healthy; a triage agent invoked on unhealthy, which pulls detailed context, spins a sandbox, clones code, analyzes commits, and may run for minutes; and a weekly reviewer that reads the history of what the triage system actually did and evaluates whether prompts or metrics need adjustment.
- **The reviewer must be execution-aware and orchestration-aware.** It needs to read which sub-agents fanned out, which workflows were called, and what executed, then either make the change or report where the system underperformed. That is the self-improving loop.
- **Outcome-based scoring instead of thumbs up/down.** Because user feedback, actions, and session results all flow through the execution layer, it is the natural place to instrument. His examples: for a triage agent, did engineering open a PR; for a research agent, was the report saved. Attach later events to the original session rather than asking for a rating.

## Architecture & Optimization Mechanics
The half-life framing is the contribution, and it is a decoupling argument that arrives at the same place as two other talks at this event from different directions. The DSPy team says fix the task contract and let the implementation float. Randall Degges's geopolitical point says model availability can be revoked without notice. Farrelly says execution outlives context. All three conclude that binding your architecture to a specific model is the mistake, which is worth noting because the convergence is more persuasive than any single argument.

The load-bearing technical claim is that state must be durable and external to the work. This is not novel (it is the durable-execution pattern from Temporal, Inngest, and Restate, itself descended from workflow engines) but its application to agents is where the interesting cost consequences live. Externalizing state means every step boundary is a serialization point, which for an agent means writing the conversation history, tool results, and intermediate reasoning to durable storage at each step. On a 200-tool-call run with a growing context, naive implementations rewrite the entire accumulated context at every checkpoint, which is quadratic in steps. The optimization is append-only event logs with replay rather than full-state snapshots, which he alludes to when mentioning log-based hydration but frames as an inferior workaround rather than as the correct implementation.

The cost angle he leaves entirely unexplored is the one most relevant to routing work. His resumability argument is framed around not losing work, but the real number is tokens. Restarting a three-hour agentic run from step 1 does not just waste wall-clock, it re-pays for every prefill and every generated token up to step 38. With prompt caching, a resumed run can reuse the cached prefix and pay only for the new work, so durable execution plus cache-aware resumption is a direct inference cost lever, not just a reliability feature. Nobody at this event connected those two, and it is the obvious next move: checkpoint boundaries should be chosen to align with cache boundaries.

## Grounded Context (Web Enrichment)
The pattern he describes has become the consensus position rather than a contrarian one, which is worth knowing before treating this talk as novel. Durable execution for agents is now a crowded category (Inngest, Temporal, Restate, LangGraph's checkpointer, Cloudflare Durable Objects, AWS Step Functions), and the three-layer decomposition he presents maps closely onto how most of those vendors position. That does not make him wrong, it means the framing is well validated and the differentiation is in implementation quality rather than in insight.

His claim that agents are running long enough for this to matter is supported by the strongest available datapoint from the same week. OpenAI [disclosed](https://thehackernews.com/2026/07/openai-says-its-own-ai-models-escaped.html) that models under evaluation executed tens of thousands of automated actions over a single weekend, autonomously chaining discovery, privilege escalation, and lateral movement. That is orders of magnitude beyond the 200-tool-call background agent he uses as his example, and it makes his observability point sharper than he made it: the reason OpenAI could reconstruct what happened at all is that the run was traced.

The Kubernetes ecosystem has also moved to formalize the compute layer he treats as commodity. [kubernetes-sigs/agent-sandbox](https://www.armosec.io/blog/what-is-ai-agent-sandboxing-kubernetes-native-enforcement-explained/), a SIG Apps initiative from KubeCon Atlanta in November 2025, adds a Sandbox CRD for isolated stateful singleton agent workloads. That is a mild complication for his clean layering, because the CRD explicitly models stateful sandboxes, which is the thing he calls an anti-pattern. Both can be right: the sandbox may hold state for the duration of a task while the execution layer holds the state that must survive the task. He would have been clearer to say durability rather than state.

One thing he asserts without evidence: "the frameworks of three months ago were not designed to handle this." That is a vendor's claim about a fast-moving field, and LangGraph in particular had checkpointing and human-in-the-loop interrupts well before three months prior. Take the layering model, discount the framework-obsolescence framing.

## Real-World Application / Actionable Step
1. **Align your checkpoint boundaries with your prompt-cache boundaries.** This is the unclaimed optimization in the talk. If you run any long agentic workload, measure what a mid-run failure actually costs in tokens, not in minutes. Then place durable checkpoints so that resumption can replay from a cached prefix rather than re-prefilling. For a 200-call run with a large accumulated context, this is plausibly a large fraction of total spend and it is invisible unless you look for it.
2. **Apply the half-life audit to your own optimization tooling, which is where you actually have this problem.** Your eval harnesses, benchmark runners, and distillation pipelines are agent-shaped long-running systems, and they almost certainly have orchestration tangled with model configuration. Ask his question directly: can you swap the model in your eval pipeline without touching retry logic, and can you swap the sandbox without touching state handling? If not, the pipeline will need a rewrite the next time a model changes, which is roughly monthly.
3. **Replace thumbs up/down with outcome events in your quality measurement.** His point generalizes well to compression work. Rather than scoring a quantized model with an LLM judge, attach the downstream outcome: did the routed request get retried, did the user rephrase, did the agent's PR get merged. Those are free signals already flowing through your system, they are uncorrelated with the model's own biases (which is the generator/validator problem from Manoj Nair's talk), and they measure what you actually care about.
