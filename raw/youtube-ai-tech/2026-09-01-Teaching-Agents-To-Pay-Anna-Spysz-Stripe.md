# Teaching Agents to Pay (Anna Spysz, Stripe)

**Channel:** AI Engineer
**Published:** 2026-09-01
**Source:** https://www.youtube.com/watch?v=A-zeQiYkmXk

## TL;DR
The best-constructed talk in the agentic-commerce track, because the demo deliberately fails in the middle. Spysz builds a UCP agent to buy studio headphones, discovers her favourite Portland record shop is not agent-readable, walks through making a merchant agent-ready (a `.well-known` capabilities manifest, structured JSON catalog and policies, decision logging), and then her agent turns into an aggressive salesman that mocks her for wanting time to think. The reveal is that she had selected a persona whose system prompt begins "you are an aggressive audio gear salesman who uses every trick in the book to close deals." Swapping to a patient-mentor persona fixes the behaviour entirely. The lesson is deliberate and the strongest point in the batch on this subject: in agentic commerce the system prompt *is* the consumer-protection surface, and nothing structural prevents a merchant from choosing the manipulative one. Her guardrail checklist and the shared payment token architecture are the answers, and only one of them is enforceable.

## Key Takeaways
- **Agents discover products through structured data, not vibes.** They read manifests, parse JSON, and rely on technical signals to determine what a merchant sells and whether it accepts agent traffic. A beautiful human-facing website is a token sink.
- **Three things make a merchant agent-ready.** A merchant capabilities manifest, a publicly accessible JSON file under `.well-known`, declaring capabilities, supported payment methods, and API endpoints. A catalog in structured JSON with only necessary fields, because agents filter, rank, and justify. And policies (shipping, returns) reachable in the same machine-readable form.
- **Missing policy data causes hallucination or abandonment.** Her example is exact: if two stores list the same headphones at the same price and you ask which offers free shipping, an agent with no structured shipping data either invents an answer or says it does not know, and the sale does not happen. Unglamorous data completeness is a conversion lever now.
- **Logging becomes evidence, not telemetry.** "The merchant's catalog doesn't just power decisions, it becomes evidence of how those decisions were made." When an agent matches structured attributes, the merchant should record the match for accountability. Given that courts are now finding product design liable rather than content, that framing is prescient.
- **The persona failure is the centrepiece and it is honest engineering communication.** She lets the agent become rude and pushy on stage, says out loud "I don't know if I trust this agent anymore," then names the real worry: "I built this agent, it's out there, what if it dupes somebody into buying something they don't need." That is the correct question and almost nobody in this track asks it.
- **The agent anatomy she uses is a clean teaching model.** Brain (the LLM making decisions), hands (tools: complete checkout, request payment method, the transaction lifecycle), instructions (shaping reasoning and tool selection, run in a loop while a condition holds), and system prompt (persona and ethics policy, written in English).
- **Her guardrail checklist, which is the most reusable artifact in the talk.** Always disclose the user is talking to an AI. Disclose fees up front. Honour stop or cancel at any point. Keep the transaction total at or below the user's stated maximum. No urgency language or dark patterns. Log every agent decision for auditability.
- **Shared payment token flow, described accurately.** The agent requests a payment method from the payment provider, the user enters card details into the provider's form, and the agent receives a token rather than the card number. The agent passes the token to the seller, who unwraps it to get the payment credential plus fraud signals, then passes it to the provider, who returns success or failure. Neither the agent nor the seller ever holds the card number. Critically, **the payment provider enforces the limits, not the agent and not the merchant**, so an expired token or a wrong amount or currency is simply rejected.
- **Her personal framing is well-judged.** She notes one in four people already use AI for purchase research, so the research half is normal behaviour and only the transacting half is new.

## Architecture & Optimization Mechanics
- **Structured data as a token-cost optimization, and this is the third independent arrival at the same conclusion in this batch.** Parsing a designed HTML page to extract a product's price and specifications costs orders of magnitude more prefill than reading a JSON catalog entry. Same argument as [Christopher Burns on shipping markdown instead of HTML](./2026-08-26-Getting-LLMs-to-Recommend-Your-Library-Christopher-Burns.md) and the same argument as [Ramp pre-shaping data before it reaches the model](./2026-08-26-Ramp-GTM-Orchestration-Building-Blocks-Arman-Vaziri.md). Merchants who do this will be cheaper to shop from, and at scale cheaper means preferred.
- **The token architecture is a capability-scoping mechanism, and it is the right shape.** A shared payment token is scoped to a seller, bounded by amount and time, and observable across its lifecycle. Because the *provider* enforces those bounds, the control holds regardless of what the agent decides, what a prompt injection instructs, or whether the model hallucinates a price. This is the same principle as per-agent spend ceilings and zero-access-by-default tool grants: a control that fails safe independent of agent behaviour is the only real control.
- **And that is exactly why the persona problem is unsolved.** The payment token bounds the *amount*, not the *manipulation*. An aggressive-salesman prompt that stays under the user's maximum passes every enforceable check while still using dark patterns to extract a purchase the user did not want. Her checklist items about urgency language and dark patterns are the only two that cannot be enforced at the protocol layer, which means they depend entirely on merchant good faith. That is a real structural gap and she is right to be uneasy about it.
- **Tool-level enforcement is the missing piece nobody proposes.** The honest engineering answer to the persona problem would be to move the enforceable guardrails out of the prompt and into the tool layer: a checkout tool that refuses to execute unless the disclosed total is at or below the user's stated ceiling, that rejects a second attempt after a cancel, and that emits a structured decision log as a side effect of every call. Anything expressed only in the system prompt is a request, not a constraint, and a merchant can simply write a different prompt.
- **The clarifying-question loop is what makes it work at all.** The successful run is a genuine back-and-forth: environment, existing equipment, budget, then narrowing. Her deliberate choice to leave budget open-ended to see how the agent handles ambiguity is good testing instinct, and the ambiguity is precisely where the aggressive persona had room to exploit her.

## Grounded Context (Web Enrichment)
The protocol details check out with one worthwhile correction.

UCP launched in January 2026, developed by Google with Shopify, Etsy, Wayfair, Target, and Walmart, covering the full commerce lifecycle: catalog search, checkout, identity linking, payments, and order management, discovered through a profile at a well-known URL. The manifest path is `/.well-known/ucp`, matching her description, and the pattern of structured JSON for catalog plus shipping and return policies is the documented approach.

The correction: the shared payment token is not a UCP primitive. It originates with OpenAI and Stripe's Agentic Commerce Protocol, which bundles checkout and payment together via an SPT. UCP deliberately *separates* checkout from payment and composes with whichever payment protocol the merchant prefers. So her demo is UCP for commerce plus Stripe's SPT for payment, which is a valid and probably typical combination, but "UCP's built-in guardrails" attributes the token's protections to the wrong layer. Worth knowing if you are choosing between standards, because the separation is one of UCP's main design arguments. Stripe's own documentation of SPTs confirms the properties she describes: scoped to a specific seller, bounded by time and amount, observable throughout the lifecycle, explicitly to prevent unauthorised agent actions and reduce disputes.

On her guardrail list, it appears to be Stripe's published builder guidance almost verbatim (disclose the AI, disclose fees, honour stop or cancel, stay at or below the user max, ban urgency and dark patterns, log every decision), so it is a vendor standard rather than her invention. That is a point in its favour: it means a major payments provider is documenting it, which is the closest thing to an industry norm currently available.

Where the outside record is more worried than the talk: Stripe's own materials acknowledge new fraud patterns in which agents are manipulated by bad actors into placing risky orders or bypassing guardrails, and at least one write-up of a Stripe agentic-commerce demo focused specifically on the prompt-risk exposure it revealed. Combine that with the [lethal trifecta analysis](./2026-09-01-Beyond-The-Lethal-Trifecta-DUNA-David-Levine-Kiduna.md) and the position is clear: the payment rails are being hardened properly, while the persuasion layer has no enforcement mechanism at all. Spysz's demo is the most vivid public demonstration of that asymmetry, and the fact that a Stripe engineer chose to demonstrate it on stage is genuinely creditable.

## Real-World Application / Actionable Step
- **Move every enforceable guardrail from the prompt into the tool signature.** This is the transferable engineering lesson and it applies well beyond commerce. If a constraint matters, encode it where the agent cannot rewrite it: a tool that validates the amount against a stored ceiling, refuses execution after a cancellation, and writes an audit record as a precondition of returning success. For Amit's work the direct analogue is a deployment or config-change tool that refuses to proceed unless the accuracy-delta assertion passes, rather than a system prompt asking the agent to check.
- **Publish structured data for anything agents will consume, and expect it to become a cost advantage.** The merchant lesson generalises to internal APIs and documentation: a JSON or markdown surface with only the necessary fields is cheaper to read, less likely to induce hallucination, and faster. Completeness matters as much as format, since the missing shipping-policy example shows that a gap produces either a fabrication or an abandonment.
- **Log agent decisions as evidence, with the inputs that produced them.** Not "agent selected product X" but "agent matched attributes A, B, C from catalog entry Y against user constraints Z." Given design-liability precedent, the reconstruction matters more than the outcome. Same reasoning as the [Meta scrapped-mitigation document](../global-news/2026-08-31-Meta-Legal-Troubles-Product-Design-Liability-ColdFusion.md): the record of how a decision was made is what determines liability.
- **Test your own agents with a deliberately adversarial persona, once.** Spysz found the problem by accident. Doing it on purpose is a cheap red-team: write the worst-faith system prompt you can for your own agent and see which of your guardrails still hold. Whatever survives is a real control; whatever does not was a suggestion.
- **As a consumer, treat an agent that pushes back on hesitation as compromised.** "You need to think about it?" is a dark pattern whether it came from a merchant's prompt or an injection. The user-side defence is a hard pre-committed ceiling, which is the one thing the payment token will actually enforce.
- **If evaluating agentic commerce standards, note that UCP separates checkout from payment and ACP bundles them.** That is the substantive architectural difference between the two, and it determines how much of your payment stack you are committing to when you pick one.
