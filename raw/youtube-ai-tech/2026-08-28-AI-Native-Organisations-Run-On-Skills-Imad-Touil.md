# AI-Native Organisations Run on Skills: How to Structure and Scale Them (Imad Touil, QuantumBlack)

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=M05vON8i0aI

## TL;DR
Touil's show of hands tells the story: most of the room writes skills, fewer share them with their team, almost nobody governs them across an organisation. His argument is that skills are where an organisation's actual know-how lives, because hooks are just event triggers, MCP servers are mostly consumed rather than authored, and subagents exist only to protect the context window. Ungoverned skills therefore produce a new class of technical debt: duplication, silent quality decay against newer models, undiscoverability, no ownership, no composability, prompt-injection exposure through skill-bundled scripts, and no access control on business-sensitive logic. His prescription is the microservices playbook applied to skills, ending in a centralised registry with metadata, dependencies, versioning, access control, and evaluation, governed by named architects and infra and security leads.

## Key Takeaways
- **The agentic stack has two loops plus enablement.** Inner loop is the coding-agent harness with context manager, tools and MCP, memory and state, and the skills loader. Outer loop is workflows composed of skills, subagents, MCP servers, and hooks. Underneath sit environment sandboxes, an MCP gateway, a model gateway, and a knowledge graph abstracting IT systems, codebase, and skills registry, plus a workflow marketplace.
- **The specify-design-tasks-implement loop is one step, not the process.** Touil's central organisational point: the familiar four-step coding-agent workflow is a single product increment. The real lifecycle wraps it in product strategy, market and competitive research, customer interviews, discovery and solution validation, data preparation and catalog cleanup, data product delivery, then platform engineering and ops, launch, performance optimization, and incident response. And any real organisation runs several parallel variants of this for mobile, internal platforms, and customer-facing systems. There is no single workflow that builds anything.
- **Skills are where determinism comes from.** The other three workflow components carry little organisational knowledge. If skills are unstructured, the workflow is not deterministic.
- **Workflows are harness blueprints.** They shape runtime behaviour of the coding harness, which is a useful mental model: the workflow is configuration, not code.
- **Design principles borrowed wholesale from microservices:** reusable, modular, discoverable, portable across workflows and across harnesses, specialised to one task rather than monolithic, composable without conflicting duplication, consistent, and cost-efficient.
- **Skills are a cost primitive, not just a knowledge primitive.** Progressive disclosure puts the right amount of skill content into context at the right time, which reduces token usage. Touil's formulation is the sharpest line in the talk: skills make organisational know-how "executable, portable, and cheap."
- **The concrete example is regulatory compliance.** Composable skills for data retention policy, disclosure standards, GDPR rules, and fill-in templates, pulled automatically at runtime by a regulatory disclosure review workflow, producing a storable audit report plus identified improvements that loop back into the codebase. Determinism here is a compliance requirement, not a preference.
- **The absence-of-skill cost is double.** Without a regulation skill, an engineer vibe-codes back and forth steering the agent, which burns tokens *and* costs time *and* leaves quality to human judgement. Cost, productivity, and quality degrade together.
- **Three-tier adoption path.** Individual creation and testing with an agreed tool, then team sharing and co-improvement, then a centralised platform with catalog, search, an MCP endpoint into the catalog, a CLI to pull skills into the IDE or sandbox, dependency tracking, versioning so agents auto-detect and pull the latest, access control, and evaluation with observability.
- **Governance is where technology stops helping.** His explicit point. Architects, engineering leads, infra leads, and security leads must own domains and enforce policy. No tool solves ownership.
- **What is next:** skills registries (internal developer portal vendors are already absorbing this), skills evaluation (his pragmatic interim answer is static evaluation against Anthropic's authoring best practices, on the theory that a badly structured or badly invoked skill is probably a low-quality one), and auto-evolving skills, which he warns is the current hype and is dangerous without governance guardrails, because you are then scaling an unbounded generator.

## Architecture & Optimization Mechanics
- **Progressive disclosure is the token-economics core, and the public spec quantifies it.** Only name and description load at startup, roughly 30 to 50 tokens per skill, the full SKILL.md loads on trigger, and reference files load only during execution. That three-tier design is what makes a large skills catalog affordable: 200 skills cost roughly 6,000 to 10,000 tokens of standing context rather than the hundreds of thousands a naive concatenation would need. This is hierarchical retrieval applied to instructions, and it is the same architectural move as paged attention or a multi-level cache: keep a cheap index resident, fault in the payload on demand.
- **Determinism through context constraint.** The recurring theme across this whole conference track. You do not make an LLM deterministic by tuning sampling, you make its behaviour reproducible by constraining what enters context. Skills are the packaging format for that constraint.
- **Skills-versus-no-skills is a measurable benchmark, and he cites one.** Touil references a skills benchmark comparing models on the same tasks in areas like automotive engineering and cybersecurity, with and without skills, showing clearly higher outcomes with skills. This is the right experimental design (the same ablation Stephanie Jarmak used for MCP tools) though he does not name the benchmark or give numbers, so treat the direction as credible and the magnitude as unspecified.
- **Subagents as a context-window mechanism, stated plainly.** Worth noting because subagents are often sold as an intelligence architecture. Touil's framing is honest: they exist to delegate a task so its intermediate tokens do not pollute the parent context. That is a memory-management technique, not a reasoning technique.
- **Quality decay against model upgrades is the non-obvious maintenance burden.** Skills must be validated not only against their tasks but against each new model release, because a skill tuned to one model's failure modes can become redundant or actively harmful when those failure modes disappear. This is version skew between prompt artifacts and model weights, and almost nobody has a process for it.
- **Skills carry executable scripts, which makes them a supply-chain surface.** Touil flags prompt injection and insecure scripts pulled from public skills. This is the most underrated risk in the talk.

## Grounded Context (Web Enrichment)
The timeline checks out and the adoption is larger than the talk conveys. Anthropic formalised Agent Skills in October 2025 across Claude's surfaces and published it as an open standard on December 18, 2025, releasing the specification and SDK at agentskills.io. The spec is deliberately minimal: a directory, a SKILL.md with two required frontmatter fields (name and description), and optional scripts, references, and assets. Within four months the anthropics/skills repository passed 62,000 GitHub stars, and partner-built skills from Atlassian, Figma, Canva, Stripe, and Notion entered a curated directory. Adoption spans 40-plus clients including Claude Code, Cursor, GitHub Copilot, VS Code, OpenAI Codex, Gemini CLI, Goose, and data platforms including Databricks and Snowflake. So Touil's portability claim, that a skill written for Claude Code works in Cursor, is genuinely true and is the reason this matters organisationally.

The governance gap he describes is not an oversight on his part, it is a documented property of the specification. The spec has no signing, no attestation, and no mandatory review. Its only permission control, `allowed-tools`, is explicitly experimental and behaves differently across implementations. Governance is deliberately delegated to the runtime and the organisation. Independent analysis frames spec governance, skill registries, and security scanning as the contested ground through late 2026, and there is already academic work on formal analysis and supply-chain security for agentic skills, plus research on automated skill acquisition by mining open-source agentic repositories. So the risk Touil raises is real, actively researched, and currently unsolved at the standard level.

Two places to push back. First, the simulation of 15 teams over six months is illustrative rather than evidential. It is a model whose parameters he chose, so it demonstrates the shape of the argument, not its magnitude. He is upfront that reality will not be as clean, which is fair, but nobody should cite those productivity numbers. Second, the microservices analogy is strong on discoverability and ownership and weaker where it matters most: microservices have hard interface contracts and can be tested in isolation against those contracts. A skill's "interface" is a natural-language description matched by a model's judgement, so composition failures are probabilistic rather than type errors. That is precisely why skill evaluation remains unsolved and why his static-structural-check heuristic, while pragmatic, is a proxy rather than a test.

## Real-World Application / Actionable Step
- **Write the three skills that encode your team's non-obvious operational knowledge, and treat them as production artifacts.** For Amit's work the highest-value candidates are concrete: a quantization-and-calibration skill (which calibration dataset, how many samples, per-channel versus per-tensor, which layers to keep in higher precision and why, the accepted perplexity delta), a benchmarking-protocol skill (warmup iterations, batch sizes, which metrics, how to report variance, what constitutes a valid comparison), and a routing-policy skill (the eligibility rules, cost ceilings, and escalation conditions). These are exactly the things currently transmitted by conversation and rediscovered by every new person and every agent.
- **Adopt the three-tier token budget deliberately.** Keep descriptions tight, because they are the only thing paying standing context cost. A vague description means the skill is either never triggered or always triggered, and both are expensive. Budget roughly 30 to 50 tokens per skill for the resident index and treat exceeding that as a design smell.
- **Add a model-upgrade regression step for skills.** This is the maintenance task nobody has. When a new model version lands, re-run the skill's tasks with and without the skill. If the no-skill result now matches, retire the skill. If it degrades, the skill is compensating for behaviour that changed and needs rewriting. Without this, skills accumulate as dead weight that costs tokens and misdirects agents.
- **Ablate before you trust.** Run every candidate skill with and without, measuring success rate, turn count, and tokens. This is the same discipline as evaluating a quantization scheme: no claim without a measured delta.
- **Treat public skills as untrusted dependencies, because they execute code.** Before pulling any external skill: read the scripts, not just the SKILL.md; pin the version; and run it in a sandbox first. The spec offers no signing or attestation, so the only available control is review. This is npm in 2015, and the supply-chain incidents have not happened yet only because the blast radius has not been discovered.
- **Do not build auto-evolving skills yet.** Touil's warning is correct and worth repeating: a closed loop that rewrites its own skills without governance amplifies whatever is wrong faster than you can observe it. Get versioning, ownership, and evaluation working first.
