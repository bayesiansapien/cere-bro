# Productionizing LLM Gateways: Architecture, Tradeoffs and Hard Lessons | Kanish Manuja, Twilio

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=zrZ1amZBSPw

## TL;DR
The most operationally dense talk in this conference track. Manuja's organising idea is that a gateway is a permanent fight between four properties (availability, latency, guardrails, cost) and that under degradation you cannot maximise all four, so the gateway's job is to expose the tradeoff as a lever to its callers rather than to pick silently. The specifics are where the value is: standard retry-with-backoff plus circuit breaking is wrong for LLMs because retries eat the latency budget and tripping a breaker makes no sense when a healthy alternative provider exists, so the correct primitive is per-request cross-provider fallback. Never measure gateway-wide aggregate latency, only P99 per model per route. Missing per-route timeouts is the number one cause of silent outages. And his closing structural argument: most organisations wanting a central gateway actually want centralised governance, which does not require centralised traffic.

## Key Takeaways
- **Why classic resilience patterns fail for LLMs, stated precisely.** Retrying an LLM call consumes the latency budget fast because calls are slow. Circuit breaking is the wrong response when a perfectly healthy second provider exists. Blind retries multiply both cost and tail latency. So the primitive is fallback to a different provider, not retry against the same one.
- **Sequential fallback by default, parallel only if you are obsessive about latency,** because firing to both providers concurrently doubles cost on every request.
- **Circuit breaking still has a role, but as cool-down and load-balancer removal:** if the primary has been failing, take it out of the request path, wait a few minutes, then reintroduce it.
- **Where failure counts live is a real design decision.** In-memory per-instance counters versus shared fleet-wide state. Fleet-wide gives faster failover. Per-instance counters break whenever deployment size changes, because your effective thresholds silently change with replica count.
- **Fallbacks are not transparent, and this is the trap.** The industry is converging on OpenAI-compatible formats but nuances persist in tool-calling schemas, token limits, and stop reasons. Cross-provider fallback requires a normalisation layer and it requires actually testing the fallback path.
- **Streaming trades away every lever.** Once you commit to provider A and bytes have reached the client, you cannot switch mid-stream. That is exactly why users see "something went wrong, please try again," and Manuja's point is that this is by design and not laziness.
- **The most commonly repeated mistake he names: the fallback provider gets less capacity planning than the primary.** He argues the fallback should have equal or higher headroom, because it is the last line of defence and if it fails the application fails.
- **Availability failures page you, latency failures do not,** so latency deserves more tuning attention than availability, not less.
- **Never track aggregate gateway latency on mixed workloads.** Embeddings and classification finish in under a second, chat in about three, reasoning takes far longer. A single blended number is, in his words, a lie. Track P99 per model per route.
- **His sharpest one-liner: "a reasoning model's normal is a chat model's outage."** Same infrastructure, incompatible latency distributions, so any shared threshold is wrong for one of them.
- **Reasoning models are the hardest problem and he says so.** Non-deterministic in ways ordinary models are not, temperature-zero often unavailable, and the same prompt ranging from 2 to 60 seconds. He reports P99 jumping to 60 seconds in production for no discernible reason. His mitigation is not a solution but a constraint: fix the reasoning level per route, and with router models that hide model selection behind an abstraction, push for as much determinism as the system allows.
- **Tail hedging as the latency tool:** fire a second request once the primary has consumed roughly P90 of the latency budget.
- **Guardrails are a dependency that can fail, and the fail-open versus fail-closed choice is an availability-versus-security tradeoff.** His decision rule is excellent: the default should be the worst case you can live with. A toxicity filter being down may be survivable, a PII filter may not.
- **Three guardrail hardening measures.** Give guardrails their own time budget so the LLM is always the rate-determining step, never the guardrail. Build fallbacks for guardrail providers too, including secondary checks and cached decisions. And choose placement deliberately: pre-hooks are safest but add serial latency, parallel is his favourite but is incompatible with streaming, post-hooks suit output monitoring and audit. His specific recommendation: for structured output, do not stream, and run guardrails concurrently.
- **The gateway is itself a new dependency in the request path, with three specific failure modes.** Shared limits: segregate API keys per route and per use case as granularly as possible, because a noisy tenant is the biggest problem here. Load shedding: verify your gateway supports it, because you cannot scale out of a retry storm, and web server internal queues must be explicitly bounded rather than unbounded. Traffic prioritisation lets the important use cases survive under load.
- **The closing structural recommendation.** A company-wide central gateway is a single point of failure. Interrogate why you want it, and you will usually find you want centralised governance (cost tracking, rate limit management) rather than centralised traffic. Governance can be centralised via plugins and shared code while deployments stay decentralised. One team can own it without it being one deployment.

## Architecture & Optimization Mechanics
This is Amit's territory, and three items warrant deeper treatment.

**Tail hedging is a cost-for-latency trade with a tunable knob, and the knob matters more than the technique.** Hedging at the P90 threshold means roughly 10% of requests get duplicated, so the marginal cost is about 10% rather than the 100% of unconditional parallel dispatch. Push the trigger to P95 and you pay about 5% to cut the extreme tail. The right threshold is derived from the shape of the latency distribution: hedging pays when the distribution is heavy-tailed enough that a fresh request's expected completion beats the in-flight request's remaining expected time. For LLM serving that condition frequently holds, because a slow request is often slow due to queueing or a degraded replica rather than intrinsic difficulty, so a retry lands on a different queue. Note the interaction with prefix caching, though: a hedged request to a different instance loses the cached prefix and pays full prefill, so the effective cost of a hedge is higher than one extra request's marginal token cost. That is a real and under-discussed correction to the naive hedging math.

**The reasoning-latency variance problem is the most important open issue he raises and it is directly a research opportunity.** A 2-to-60-second spread on identical prompts is variance in generated reasoning-token count, not in per-token throughput. That reframes the problem usefully: the tail is a token-count distribution problem, and the levers are adaptive thinking budgets (cap reasoning tokens per route, which he approximates by fixing the reasoning level), early termination on confidence, and distilling long reasoning traces into shorter ones. From the gateway's position the only available lever is a hard cap, which trades accuracy for predictability. From the model side, reducing the variance rather than truncating it is the better fix, and it is exactly the kind of work Amit is positioned to do. Anyone who can cut reasoning-token variance at fixed accuracy is solving a production problem that a principal engineer at Twilio just described as his worst scar.

**The decentralised-traffic-with-centralised-governance argument is correct and generalises.** The reason to want a central gateway is measurement and control, both of which are metadata concerns. Traffic centralisation adds a network hop, a scaling bottleneck, a blast radius, and a single point of failure, and buys nothing that a shared library plus a central telemetry sink does not. The pattern is a control plane and data plane split, which is standard in service mesh design and is being rediscovered here. Worth pairing with Justin Joyce's Cloudflare talk from the same conference, where AI Gateway is the substrate that makes per-task model selection and cost attribution possible at all. Manuja's refinement is that you need the governance function, not necessarily a single shared proxy.

His measurement discipline is the cheapest and most valuable thing in the talk. Per-model, per-route P99 plus per-model-class, per-route timeouts. Aggregate latency on a mixed workload is genuinely worse than no metric, because it produces confident wrong conclusions: a reasoning-heavy traffic shift looks like a latency regression, and a chat-model outage disappears into the average.

## Grounded Context (Web Enrichment)
Every technical recommendation here matches the current state of practice, and two of his numbers are corroborated independently.

The scale of the availability problem is real. Reporting tracked 47 provider incidents across major AI systems in December 2025 alone, which is why cross-provider failover moved from a nice-to-have to a baseline enterprise requirement over 2026 rather than an exotic optimisation.

His hedging recommendation matches the published consensus exactly. The standard guidance is to fire a second request once the primary has consumed roughly P90 of the latency budget, with the trigger tuned to your own latency profile (around P95 is the cost-effective setting) so that you hedge only the slow tail. The lineage is Google's "The Tail at Scale," which documented this pattern for high-tail-variance systems well before LLMs existed, and it is worth reading directly since it is the canonical treatment. Parallel hedging to two providers with first-response-wins is also documented practice for when latency itself is the failure mode, consistent with his "only if you are obsessed" framing.

His reasoning-model claim is independently confirmed in near-identical terms: reasoning models are highly non-deterministic and the same prompt can take anywhere from 2 to 60 seconds, which is fundamentally at odds with the latency budgets and predictability production systems require. So this is not a Twilio-specific pathology.

One quantitative point his talk implies but does not state: the gateway's own overhead is measurable and varies dramatically by implementation. Independent comparisons put Portkey's added latency under 1 millisecond against LiteLLM's P95 around 8 milliseconds, attributed largely to LiteLLM being Python-based versus Go-based alternatives, with overhead in the millisecond range at production request rates. That is directly relevant to his "the gateway is another dependency" warning, and it means gateway selection has a fixed latency cost worth measuring rather than assuming away. In fairness, 8 milliseconds against a 3-second chat call is noise, but against a sub-second embedding or classification call it is a measurable fraction, which is another reason his per-route thinking is right.

Two caveats on the talk. First, everything is presented as experience-derived guidance without published measurements from Twilio's own systems, so the specific thresholds should be re-derived from your own latency distributions rather than copied. Second, his advice to fix the reasoning level per route reduces variance but silently caps capability on hard queries, and he does not discuss how to detect when that cap is degrading answer quality. That is the missing half of the recommendation and it is the more interesting half.

## Real-World Application / Actionable Step
- **Rebuild latency dashboards as per-model, per-route P99 today, and delete the aggregate.** This is the highest-value, lowest-effort item in the entire conference for anyone operating inference infrastructure. An aggregate on mixed workloads generates confidently wrong conclusions, and Manuja's "reasoning normal is chat outage" line is the argument to use when someone defends the blended metric.
- **Audit every route for a timeout and add the missing ones.** He names this as the number one cause of silent outages: without a timeout the gateway believes a hung request is being served happily. Per-model-class, per-route, derived from that route's own distribution.
- **Implement tail hedging with a P95 trigger, and correct the cost model for prefix-cache loss.** The standard math treats a hedge as one extra request. In practice a hedge routed to a different instance loses the cached prefix and pays full prefill, so the true marginal cost is higher. Measure both, because this correction is not in the published guidance and it is exactly the kind of detail that makes or breaks the economics.
- **Take reasoning-token variance as a research target, not just an ops problem.** A 2-to-60-second spread is variance in generated token count. Reducing that variance at fixed accuracy (adaptive thinking budgets, confidence-based early exit, distilling long traces into shorter ones) attacks a production pain a principal engineer just described as his worst scar. Pair it with the accuracy-degradation detection his fix omits, and it is a complete piece of work.
- **Give the fallback provider equal or greater headroom than the primary, and load-test it.** This is the mistake he says teams make repeatedly, and it is invisible until the day it matters.
- **Set the guardrail fail mode by asking what worst case you can live with,** per filter rather than globally. Toxicity filter down may be survivable, PII filter down usually is not. Give guardrails their own time budget so the LLM stays the rate-determining step.
- **Split the control plane from the data plane before building a central gateway.** Centralise governance (cost attribution, rate limits, policy) through a shared library and telemetry sink, decentralise the traffic path. One owning team, many deployments. And measure the gateway's own overhead, since it ranges from under 1 millisecond to roughly 8 milliseconds P95 depending on implementation, which is material for sub-second routes.
