# Productionizing LLM Gateways: Architecture, Tradeoffs and Hard Lessons (Kanish Manuja, Twilio)

**Channel:** AI Engineer
**Published:** 2026-08-28
**Source:** https://www.youtube.com/watch?v=zrZ1amZBSPw

## TL;DR
The most directly useful talk in this batch for anyone working on routing or serving. Manuja's framing: at the heart of any LLM gateway is a four-way fight between availability, latency, guardrails, and cost, and during degradation you cannot maximise all four, so the gateway's job is to expose the trade-off as a lever rather than to hide it behind a default. The concrete lessons are hard-won and specific: classical retry-with-backoff plus circuit breaking is wrong for LLMs, per-request cross-provider fallback is right, aggregate gateway latency is a meaningless number, missing per-route timeouts is the number one cause of silent outages, guardrails are just another unreliable dependency needing their own fallbacks and time budgets, and the biggest architectural mistake is conflating a central gateway with centralised governance. His line worth memorising: a reasoning model's normal is a chat model's outage.

## Key Takeaways
- **Retry semantics from ordinary APIs do not transfer.** Retrying an LLM call eats the latency budget immediately, blind retries multiply both cost and tail latency, and tripping a circuit breaker when a perfectly healthy second provider exists is simply wrong. Use the second provider.
- **Per-request fallback is the primary pattern.** Try provider A, then provider B in sequence on failure. Firing both in parallel is available only if you are extremely latency-obsessed, because it doubles cost outright.
- **Circuit breaking still applies, at provider granularity.** A persistently failing primary should be pulled from the request path into a cooldown and retried after some minutes.
- **Where failure counts live is a real design decision.** In-memory per-instance counters versus fleet-shared state. Fleet-wide gives faster failover. Local counters break your tuning every time deployment size changes, because your thresholds were implicitly calibrated to instance count.
- **Fallbacks are not transparent, despite OpenAI-compatible APIs.** Real differences remain in tool-calling schemas, token limits, and stop reasons. This is why a normalization layer is necessary and why fallbacks must be tested explicitly rather than assumed.
- **Streaming destroys your fallback lever.** Once you have committed to provider A and started sending bytes to the client, you cannot switch mid-stream. This is exactly why "something went wrong, please try again" exists. It is a design consequence, not laziness.
- **The fallback provider is chronically under-provisioned.** Teams provision and load-test the primary carefully and neglect the secondary. Manuja argues the secondary should have *more* headroom, not less, because it is the last line of defence.
- **Never measure aggregate gateway latency.** He asks the room by show of hands and then tells them it is a lie. A gateway running mixed workloads spans sub-second embeddings and classification, roughly three-second chat, and reasoning requests taking far longer. Track P99 per model per route.
- **Missing per-route, per-model-class timeouts is the top root cause of silent outages.** Without a timeout the gateway believes it is happily serving a request that is going nowhere.
- **Reasoning and router models are the hardest problem, by his own account the source of most of his scars.** Latency is genuinely unpredictable, temperature-zero is often unavailable, and the same prompt can take 2 to 60 seconds. He has seen P99 jump to 60 seconds with no discernible cause. There is no clean fix. His recommendations: pin the reasoning level per route, and with router models that hide model selection behind an abstraction, push for as much determinism as the system allows.
- **Hedge the tail.** Fire a second request once the primary has consumed, say, P90 of the latency budget. This meaningfully cuts P99 without the full cost of blanket duplication.
- **Guardrails are a dependency that fails, and you must choose fail-open or fail-closed deliberately.** Fail-open serves the request when guardrails are down, trading security for availability. Fail-closed blocks it. His rule for choosing is excellent: the default should be the worst case you can live with. A toxicity filter being down is probably survivable. PII leakage probably is not.
- **Guardrails need their own time budgets and their own fallbacks.** The LLM should always be the rate-determining step, never the guardrail. Secondary guardrail providers and cached guardrail decisions are both viable.
- **Three guardrail placements with distinct trade-offs.** Pre-hook on input is safest and adds serial latency. Parallel is his favourite but is incompatible with streaming, so his advice is: if you are producing structured output, do not stream it, and run guardrails concurrently instead. Post-hook suits output monitoring and auditing.
- **The gateway is itself a new dependency in the request path.** Segregate API keys per route and per use case at the finest granularity you can manage, because a noisy tenant is one of the biggest failure sources. Verify your gateway supports load shedding and exercise it in game days, because you cannot scale out of a retry storm. Bound the internal web-server queues explicitly. Add traffic prioritisation so the most important use cases survive under load.
- **The central conclusion: do not centralise traffic, centralise governance.** A company-wide central gateway is a single point of failure. What teams actually want is centralised governance (cost tracking, rate limit management, policy), and that can be achieved with plugins and shared custom code over a decentralised deployment. One team can own it without it being one deployment.

## Architecture & Optimization Mechanics
- **The four-way trade-off is the correct mental model and it should be a runtime parameter, not a build-time decision.** Availability, latency, guardrails, cost. The design recommendation, expose these as levers to callers, is the part most gateways get wrong: they hard-code one operating point. A caller doing batch summarisation and a caller doing interactive voice want opposite settings, and both should be expressible per request.
- **Hedged requests are the single highest-leverage tail-latency technique available**, and Manuja's formulation (fire the hedge at P90 of budget, not immediately) is the important refinement. It comes from the same reasoning as Dean and Barroso's tail-at-scale work: duplicating everything doubles cost, duplicating only the slow minority costs roughly 10% extra while removing most of the tail. For LLM serving the cost calculus is harsher than for ordinary RPC because tokens are expensive, which makes the deferred-hedge variant essential rather than optional.
- **Per-route P99 is not merely better measurement, it changes what you can do.** Aggregate P99 across mixed workloads is dominated by whichever route is slowest, so it is simultaneously useless for alerting and useless for capacity planning. Per-route measurement is the prerequisite for per-route timeouts, which are the prerequisite for detecting silent failure. The chain matters: no per-route metrics means no meaningful timeouts means silent outages.
- **Reasoning-model latency variance is a genuine architectural problem for routing.** A 2-to-60-second spread on identical input means the latency of a reasoning route is effectively unbudgetable, which has direct consequences for a router: routing to a reasoning model is accepting an unbounded latency tail unless you pin the reasoning level and enforce a hard timeout with a non-reasoning fallback. Pinning the reasoning effort per route is the practical control and it is under-used.
- **Router models are an abstraction leak.** When a provider hides model selection, you inherit their routing decisions with none of the observability and none of the cost predictability. For anyone building their own routing layer this is the argument for owning the decision: a hidden router makes your P99, your cost per request, and your capability floor all non-deterministic simultaneously.
- **Parallel guardrails plus non-streaming structured output is a clean latency win.** Structured output has no user-facing reason to stream, so trading streaming for concurrent guardrail evaluation removes the guardrail from the critical path entirely. Free latency for a UX property nobody wanted.
- **Bounded queues and load shedding are the difference between degradation and collapse.** Under a retry storm, unbounded queues convert a latency problem into a total outage, and adding instances makes it worse by accepting more work. This is basic queueing theory and it is routinely ignored in LLM infrastructure because the field is young.
- **Decentralised deployment with centralised governance is the right architecture and it is genuinely achievable.** Governance is a control-plane concern (policy, budgets, keys, telemetry aggregation). Traffic is a data-plane concern. Collapsing them puts the whole company's inference behind one blast radius for no benefit.

## Grounded Context (Web Enrichment)
The market has caught up with the argument. By 2026 the LLM gateway is widely treated as critical AI infrastructure rather than an optional add-on, on the grounds that it is the single place where cost, reliability, and governance are actually controlled. Independent buyer's guides converge on Manuja's central conclusion almost verbatim: a company-wide central gateway is a single point of failure even when deployed as a distributed system, and what most teams want is centralised governance rather than centralised traffic.

The measured overhead figures are worth having, because they quantify the cost of the extra hop Manuja warns about. Bifrost, written in Go, reports roughly 11 microseconds of overhead at 5,000 RPS sustained. Kong AI Gateway sits around 3 to 5 milliseconds on its established proxy layer. LiteLLM, the most widely deployed open-source proxy with 100-plus providers and the most mature integration ecosystem, adds roughly 8 milliseconds, which is immaterial against multi-second LLM calls. Cloudflare AI Gateway is sub-millisecond at edge but every request takes a full round trip through Cloudflare's network, so effective added latency is more like 10 to 50 milliseconds depending on origin. Portkey runs on Cloudflare Workers and ships guardrails, semantic caching, and observability without self-hosting. The practical read: gateway overhead is not the constraint for chat or reasoning workloads, but it absolutely is for embedding and classification routes where the model call itself is sub-second, which is another argument for Manuja's per-route thinking.

Two additions the talk does not cover. First, the cross-provider normalization problem he identifies has been formalised: recent work proposes hub-and-spoke intermediate representations for translating between provider APIs, which is the general form of the ad hoc normalization layer he describes building. Second, provenance is an emerging concern, with research on evidence-bound gateway-path provenance for third-party inference, meaning cryptographic attestation of which provider actually served a request. That matters precisely because cross-provider fallback makes the answer non-obvious, and in a regulated setting "which model produced this output" becomes an audit question.

Where to push back, gently. The talk is entirely about reliability engineering and barely touches cost, which is one of the four corners he names. There is no discussion of semantic caching, which is the largest available cost reduction for most gateway workloads, nor of quality-aware routing, sending easy queries to cheaper models, which is where the cost lever actually lives. His trade-off diagram has four corners and the talk covers three. That is a scoping choice rather than an error, but anyone treating this as a complete gateway design guide should note the gap.

## Real-World Application / Actionable Step
This is the closest talk in the batch to Amit's day job, so the actions are direct.

- **Audit for missing per-route timeouts today.** This is the highest-severity item and the cheapest to fix. Every route and model class needs an explicit timeout derived from its own P99, not a global default. Absence of a timeout is not a slow request, it is an invisible one, and Manuja names it the number one root cause of silent outages.
- **Replace aggregate latency dashboards with per-model, per-route P99.** If any current dashboard shows one gateway-wide latency number, it is actively misleading and it is blocking every downstream control. Do this before tuning anything.
- **Implement deferred hedging at P90 of budget.** For interactive routes this is the best tail-latency-per-rupee intervention available. Measure the actual hedge rate afterwards: if it fires on more than roughly 10% of requests, the budget is set wrong, not the technique.
- **Pin reasoning effort per route and pair it with a non-reasoning fallback.** Given a 2-to-60-second observed spread, a reasoning route without a pinned effort level and a hard timeout is an unbounded liability. This is a concrete routing-policy rule to encode in the eligibility layer.
- **Load-test the fallback provider harder than the primary, and schedule it.** Provision more headroom on the secondary, then verify it by actually failing the primary in a game day. An untested fallback is a hope, and this is the specific failure Manuja says he has watched teams repeat.
- **Choose fail-open versus fail-closed per guardrail, explicitly, and write it down.** Apply his rule: the default is the worst case you can live with. PII and injection checks fail closed. Toxicity and style checks fail open. Document the decision next to the guardrail config so it is not rediscovered during an incident.
- **Move guardrails off the critical path for structured-output routes.** Stop streaming structured output, run guardrails in parallel. Pure latency win with no UX cost.
- **Segregate API keys to the finest granularity your ops burden allows**, and bound every internal queue. Noisy-neighbour isolation and load shedding are what keep one team's retry storm from becoming everyone's outage.
- **If your organisation is planning a single company-wide gateway, argue for decentralised data plane plus centralised control plane instead.** This is the architectural recommendation with the largest long-term consequence, and it is far cheaper to get right at design time than to unwind later.
- **Fill the two gaps yourself: add semantic caching and quality-aware routing.** These are where the cost corner of the trade-off is won, and the talk leaves them untouched. A cache hit is a 100% cost reduction and a latency win simultaneously, which no other lever offers.
