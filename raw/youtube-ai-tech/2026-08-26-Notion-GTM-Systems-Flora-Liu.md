# AI in GTM at Notion (Flora Liu)

**Channel:** AI Engineer
**Published:** 2026-08-26
**Source:** https://www.youtube.com/watch?v=L4I7WgiEquo

## TL;DR
Notion rebuilt go-to-market from a spiderweb of SaaS tools into a single decisioning system with four layers: Know, Decide, Act, Learn. The core architectural bet is that humans and agents must read and write the same substrate, so instead of bolting an "AI layer" on top of the business, the agent is registered as just another operator inside the existing system. Early numbers after 13 weeks: more qualified opportunities per enterprise rep, and users receiving context-aware recommendations were 63% more likely to take the next step.

## Key Takeaways
- **GTM is a distributed systems problem, not a marketing ops problem.** Every workflow reduces to four questions: what do we know about the customer, what should happen next, how do we execute safely, did it work. That maps one-to-one onto the four-layer architecture.
- **Two-tier data path.** Snowflake is where truth is *computed* (daily plus some realtime transforms into a small set of modeled, versioned entities: accounts, contacts, workspaces, eligibility, facts). DynamoDB is where truth is *served*: a denormalized, key-addressable profile queryable in milliseconds with zero joins.
- **Unstructured data is the load-bearing part.** The decisive facts ("champion just left", "do not contact", "blocked in legal") live in notes, not columns. Agent-generated artifacts (research snippets, rolling summaries) are keyed by the same IDs as structured entities so a downstream reader gets everything in one fetch.
- **Signals as the atomic trigger.** A signal is a single customer event material enough to change the next best action. Critically, external signals (funding rounds, hiring, tech-stack shifts) are what make the system proactive rather than reactive. No signal means the predictive marketing engine takes over with feature recommendations.
- **Eligibility and routing promoted to a first-class primitive.** Rules used to be scattered across the email tool, Salesforce, and product code. Consolidating them behind a single classifier is what prevents double-sends and incoherent cross-channel messaging.
- **Hard trust boundary.** Agents never talk to customers directly. Inbound "contact sales" form fills are treated as untrusted user input precisely because an agent sits in the middle. Prompt injection is modeled as a GTM security problem, not a research curiosity.
- **Build/buy is decided per layer, not per company.** They rent orchestration (Temporal), email, CRM, and enrichment (Clay). They refuse to rent the context layer, because a generic vendor cannot represent their esoteric data model and they need it debuggable.
- **Shadow your best human first.** The chaos of a top rep's 20 open tabs *is* the spec. Encode a mediocre process and you get a mediocre agent.

## Architecture & Optimization Mechanics
- **Durability over retry logic in the agent.** Every signal spawns a Temporal workflow. A single run touches enrichment, web search, draft generation, and scoring, each a network call that can fail or rate-limit. Temporal owns retries, dedupe, and resume-from-failure, so the application code stays sequential and readable, and one malformed Gong transcript cannot poison a whole batch. This is the right separation: put nondeterminism handling in the orchestrator, not in the prompt.
- **Generate-score-review loop instead of single-shot generation.** Cold outbound fans out concurrent research subagents, drafts three candidate emails, scores them, then a reviewer agent picks the highest and edits. Best-of-N with a learned-ish judge, applied at the workflow layer. Same pattern Amit uses in routing evals, just pointed at email copy.
- **Read-path optimization is the whole trick.** The Snowflake-to-DynamoDB split is a classic compute/serve separation: batch the expensive joins offline, materialize a denormalized blob, and give the agent a millisecond key lookup. Agent latency budgets die from N+1 joins during tool calls, so precomputing the context blob is the single highest-leverage move.
- **Markdown as the agent-native serialization format.** The context layer lives in Notion (plain markdown, databases, hierarchies) explicitly because LLMs are fluent in it and humans can read it. Choosing a format the model was pretrained on is a real token-efficiency and accuracy decision, not just ergonomics.
- **Full tracing on every LLM step**, which is what makes the Learn layer possible: every action writes a decision log, and every outcome threads back to the decision that caused it.

## Grounded Context (Web Enrichment)
The talk lines up with Notion's shipped platform work rather than running ahead of it. Notion 3.3 (February 2026) opened Custom Agents in free beta, which is exactly the "sharable custom agents for recurring automated workflows" Liu demos. Notion 3.5 (May 2026) shipped the Notion Developer Platform and an External Agents API, letting Claude, OpenAI Codex, Decagon, and in-house agents plug directly into the workspace under existing permissions. So the "agent as another operator in the same system" claim is now a product surface, not just an internal pattern, and the permissions-aware context aggregation is the part vendors are converging on. Independent write-ups of the talk cite the same 63% lift figure, so the number is at least consistently reported, though it is a self-reported internal metric with no control-group detail disclosed. Treat it as directional. The one place to push back: 13 weeks of "increased qualified opportunities" with no baseline or seasonality adjustment is weak evidence, and Liu herself flags it as early.

## Real-World Application / Actionable Step
- **Steal the compute/serve split for routing.** Amit's router pays latency every time it enriches a request mid-flight. Move the expensive part offline: batch-compute per-tenant or per-query-class features (historical accuracy per model, cost ceilings, latency SLOs, prior escalations) into a denormalized key-value profile, then let the router do one millisecond lookup instead of joins at inference time. The routing decision then costs a hash lookup plus a small classifier, not a data pipeline.
- **Make eligibility a first-class primitive in the routing layer.** Notion's insight that scattered eligibility rules destroy coherence maps directly onto model routing: policy rules (this tenant cannot use an external API, this query class must stay on a quantized local model, PII cannot leave the VPC) tend to sprawl across gateway config, prompt templates, and app code. Pull them into one declarative eligibility table consumed by a single classifier. That also gives a clean audit surface.
- **Adopt the decision-log pattern for router evals.** Log every routing decision plus the outcome (quality score, cost, latency, escalation) keyed so outcomes thread back to the decision. That is the dataset that lets the router self-improve instead of being retuned by hand each quarter.
- **Treat untrusted input as an architectural boundary, not a prompt instruction.** Any agent pipeline ingesting user-supplied text should mark that text untrusted at the type level and strip its tool-calling authority, the same way Notion treats contact-sales form fills.
