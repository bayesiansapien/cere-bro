# Build A Reasoning Model From Scratch 2: Loading a Base Model, Text Generation, and KV Caching

**Channel:** Sebastian Raschka
**Published:** 2026-09-06
**Source:** https://www.youtube.com/watch?v=BJua0yjO5dk

## TL;DR
Chapter 2 of Raschka's reasoning-model series, and the most measurement-dense episode so far. He loads a Qwen3 base model in PyTorch, implements greedy autoregressive decoding from scratch, then adds a per-layer KV cache and `torch.compile` and benchmarks every combination across CPU, Apple MPS, H100, and DGX Spark. The headline number is a roughly 6x throughput gain from KV caching alone on CPU, from 4 to 5 tokens per second up to 28 to 29 tokens per second. The more interesting result is buried at the end: on an H100 the compiled model *without* KV caching was the fastest configuration, which he correctly attributes to a small model, a short prompt, and a deliberately device-portable rather than GPU-optimal cache implementation.

## Key Takeaways
- **KV caching is the dominant single optimization at this scale.** CPU: 4 to 5 tok/s baseline, 28 to 29 tok/s cached. `torch.compile` alone moved 4 to 5 tok/s, essentially nothing. Stacking cache plus compile roughly doubled the cached number again. The two are additive, not exclusive.
- **The asymptotic behaviour matters more than the point estimate.** Uncached generation "gets slower and slower" as the sequence grows, because each iteration re-encodes the full prefix through quadratic attention. Cached generation stays roughly flat: there is still a growing query-against-cached-keys dot product, so cost grows, but linearly rather than quadratically. That is the real argument for KV caching, not the 6x headline.
- **Cache is per-layer and must be explicitly reset per query.** Qwen3 has 28 transformer blocks, each with its own attention and therefore its own keys and values. Cache memory scales with layer count times context length. Forgetting the reset between queries is the classic correctness bug in hand-rolled caches.
- **Prefill and decode are structurally different phases.** The first forward pass takes the entire prompt (prefill). Every subsequent pass takes exactly one token, with everything prior read from cache. Raschka's code makes this split explicit, which is exactly the phase separation that vLLM and friends exploit for scheduling.
- **The wasted-compute framing is precise.** Without a cache, generating N tokens means N full forward passes over a growing prefix. The model emits one logits row *per input token*, of which all but the last are discarded, since position i predicts token i+1 and positions 0 through i-1 merely re-predict the prompt. The discarded rows are the waste KV caching recovers.
- **Vocabulary and decode mechanics:** the logits tensor is `[seq_len, 151936]` for Qwen3. `argmax` over the final row is greedy decoding. `torch.argmax` returns the index, `torch.max` returns the value, and confusing them is a common bug. Temperature sampling comes in a later chapter.
- **`torch.compile` is explicitly deprioritised.** He drops it in later chapters because readers hit compatibility issues, invoking premature optimization. Warm-up runs are excluded from his benchmarks, with a defensible justification: a service operator pre-warms before serving traffic, so warm-up should not count against steady-state throughput.
- **His KV cache is deliberately suboptimal.** It is written to work identically on CPU, MPS, and CUDA. He notes an optimized variant exists at 671 lines versus the simple version, and that GPU-specific changes would break CPU portability.
- **MPS carries real correctness risk, not just speed risk.** He shows a reader's training run where identical code converged on CPU (loss 2.6 downward) and completely failed to converge on MPS, with no bug in the code. Reported chip-specific MPS bugs on M1 and M2. His debugging rule: if results look wrong on MPS, rerun on CPU to isolate.

## Architecture & Optimization Mechanics
The H100 anomaly is the most instructive result in the video and Raschka handles it honestly. On an H100 he measures up to 141 tok/s, and the compiled uncached configuration beats the cached one. Three factors explain it and all three generalise.

First, at 0.6B parameters with a short prompt, the quadratic term in attention never gets large enough to dominate. The prefix is too short for recomputation to hurt, so the cache's benefit is small while its overhead, extra memory traffic and per-step indexing, is fully paid. KV caching is a trade of compute for memory bandwidth, and on a bandwidth-rich, compute-rich H100 running a tiny model, that trade can go the wrong way. Second, a portable cache implementation cannot use the layouts that make GPU caching fast: paged blocks, contiguous per-head strides, fused gather. Third, `torch.compile` has more to work with on CUDA than on CPU, since kernel fusion removes dispatch overhead that a small model spends most of its time on.

The generalisable lesson for compression work: the ranking of optimizations inverts with model size, sequence length, and hardware. An optimization measured as 6x on CPU with a 0.6B model at short context can be *negative* on an H100. Any benchmark table without model size, context length, and device is uninterpretable, and Raschka's table is good precisely because it varies all three.

The DGX Spark numbers (74 and 98 tok/s) landing only slightly above the Mac Mini M4 GPU (41 and 71) is a quietly useful datapoint for local-inference hardware decisions. For small-model prototyping, Apple silicon is close enough to purpose-built hardware that the portability and MPS-maturity tradeoff is the real deciding factor, not raw throughput.

On the memory side, cache size scaling as layers times context times heads times head-dim is where the intersection with Amit's work sits. Qwen3-0.6B uses grouped-query attention with 16 query heads and 8 KV heads, a 2:1 ratio that already halves cache footprint relative to full multi-head attention. That is the architectural optimization Raschka's simple cache silently inherits without discussing: GQA is a KV-cache compression technique baked into the model rather than the runtime.

One small correctness note on the transcript: he verbally says the download is "the 6 billion parameter model." It is Qwen3-0.6B, 0.6 billion. His own evidence contradicts the misspeak, since he shows a 1.4 GB weight file, which is exactly 0.6B parameters at bf16, whereas 6B would be roughly 12 GB. The spoken benchmark numbers also get muddled between "seconds" and "tokens per second" in a few places, so trust the written table in the book over the narration.

## Grounded Context (Web Enrichment)
The architecture details check out precisely. Qwen3-0.6B is a 28-layer dense transformer with vocabulary size 151,936, hidden size 1,024, feed-forward inner dimension 4,096, and grouped-query attention with 16 query heads against 8 key-value heads. The 28-layer count Raschka cites when sizing the per-layer cache and the 151,936 vocabulary dimension visible in his logits tensor both match the published config exactly, which confirms he is loading genuine Qwen3 weights rather than a reduced teaching variant.

The book itself shipped rather than remaining in early access. *Build a Reasoning Model (From Scratch)* is out from Manning at 440 full-color pages, ISBN 9781633434677, with code at github.com/rasbt/reasoning-from-scratch. The stated arc matches what he previews in the video: start from a conventional pre-trained LLM, build text generation, build verifier-based evaluation, improve reasoning through inference-time methods, then move to reinforcement learning with automatic verifiers for maths and to distillation. The full Qwen3 architecture is implemented from scratch in an appendix, which is why he can treat it as a black box in this chapter. Notably the book commits to consumer-hardware runnability for the main chapters, which explains and justifies the portable-over-optimal cache decision that produced the odd H100 result.

One claim worth flagging as unverified: he offers roughly 20 tok/s as approximately what a hosted frontier model produces in the ChatGPT interface, using it as a usability yardstick. That is a reasonable order-of-magnitude anchor for perceived reading speed, but hosted throughput varies enormously with load, model, and reasoning-effort setting, so treat it as a rule of thumb rather than a measurement. It does not affect any of his own numbers.

## Real-World Application / Actionable Step
Build the three-axis benchmark matrix that Raschka's H100 surprise argues for, and make it standard for every optimization claim in the compression work. The axes are model size, context length, and device. The specific failure this prevents is real and common: adopting an optimization validated at short context on one accelerator, then shipping it into a long-context serving path where its sign flips. Concretely, run every quantization and cache change at 512, 8K, and 64K context on at least two devices, and report the crossover point rather than a single speedup number. A claim like "6x faster" with no context length attached is what Raschka's own data shows to be untrustworthy.

Second, the GQA observation is a directly actionable framing for the compression backlog. KV cache memory is `2 × layers × kv_heads × head_dim × seq_len × dtype_bytes`, and GQA attacks the `kv_heads` term architecturally while quantized KV caches attack `dtype_bytes` at runtime. These compose multiplicatively and are usually owned by different teams, which means the combined win is routinely left on the table. Measure both together on the same model: int8 KV cache on top of an already-GQA model, with quality checked against a long-context retrieval task rather than perplexity, since KV quantization degrades long-range recall specifically.

Third, steal his MPS debugging discipline as a general rule for accelerator work: when numerical results look wrong on a less-mature backend, rerun on CPU before touching the code. The reader case he shows, identical code converging on CPU and diverging on MPS with no code bug, is the same failure class as a custom Triton kernel that silently produces wrong values on one architecture. Keep a CPU reference path in the pruning pipeline permanently, even though it is slow, purely as a correctness oracle. It costs almost nothing to maintain and it is the only thing that distinguishes "my algorithm is wrong" from "this backend is wrong."
