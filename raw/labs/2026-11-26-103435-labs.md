 Introducing Hurdle: Run agent evals on your API, skills, and docs

 Hurdle is an open-source npm library that runs Claude Code and Codex against tasks on your platform, scores each run with code checks, guards and an LLM judge, and shows the pass rate by model and condition.

 Authors

 Mo King, Sam Barrowclough, Hassan El Mghari

 Table of contents

 40+ Models Chosen for Production...40+ Models Chosen for Production...40+ Models Chosen for Production...

 If you’re building for developers, you already know that coding agents are one of the main ways devs access your API, SDK, and docs. To find out how well agents can work with your platform, you need to test them on real-world tasks, ideally across a representative sample of models, harnesses, and conditions. Orchestrating all of this by hand is extremely tedious, which we found out the hard way when we started doing evals at Together last spring.
 To automate the process, we spent the last six months building Hurdle , an npm library for running agent evals. Today we’re open-sourcing it so you can benchmark your platform's agent experience the same way we do. Get started today with npx hurdle init or by asking your agent to set it up for you.
 How Hurdle works
 Hurdle lets you test how well Claude Code and Codex can use your platform.
 You start by writing a task , which is just a prompt that a developer would hand to an agent working with your product. You can try to cover every task a developer might try, or focus on a few problem areas. Hurdle runs the agent against your tasks, records the session, and scores the run.
 Exactly how scoring works is up to you. You can pick one method, or mix and match:
 Code checks: Assertions about the run, such as the API requests the agent must make and the files or data it should produce.
 Guards: Rules that block actions the agent isn’t allowed to make, like starting an expensive GPU cluster—bad agent >:( Hurdle blocks the API request and counts any attempt as a failure.
 Judge: An LLM that reviews the recorded session against a rubric you write in plain English, and decides whether the agent passed.
 You can also run each task under different conditions , which set the context the agent starts with. For example, you can run the same task on two fresh agents, one with and one without your MCP server installed, to see how much it helps or hurts.
 Same goes for running evals on multiple models: Hurdle runs every task against every agent/model combo you specify. Agents don’t always run the same way twice, so you can also repeat each task/model/condition combo several times to get an overall pass rate.
 Example task: Find the cheapest GPU cluster
 Here’s a real task we came up with during our own eval adventures:
 List the available GPU cluster regions and instance types, print the cheapest option, and show the exact command you would run to reserve it on demand for one hour. Do not actually reserve it. To pass, the agent has to look up live regions from the API, find current prices in the docs, and produce a valid reservation command—but most importantly, it should NOT create a paid cluster.
 Here’s how we wrote the first three requirements as Hurdle checks:
 // checks.mjs
import { defineChecks } from "hurdle";

// Hurdle calls this function after the agent finishes
export default defineChecks((run) => {

 // Passes only if the agent made a successful GET /v1/compute/regions call
 // Request checks only work for sandboxed runs
 run.expect.request({
 id: "regions",
 method: "GET",
 path: "/v1/compute/regions",
 status: 200,
 });

 // The rubric for the LLM judge
 run.judge(
 "Using the recorded session, assess whether the agent " +
 "retrieved official pricing, compared supported options, " +
 "and produced a valid reservation command. " +
 "Mark fail if the required pricing evidence is missing. " +
 "Note confusing API responses and recovery attempts."
 );
}); 
 And here’s the guard that prevents the agent from starting a real cluster. Hurdle enforces the guard while the agent works, and runs the checks after the agent finishes:
 // guard.mjs
import { defineGuard } from "hurdle";

export default defineGuard((guard) => {
 // Block any request to create a cluster
 // The check fails if the agent tries the request
 guard.block.request({
 id: "no-reservation",
 method: "POST",
 path: "/v1/compute/clusters",
 });
}); 
 The eval suite
 To run a task, you add it to a suite , a small file that picks the tasks to run, the agents and conditions to run them with, and how many times to repeat each run. For the GPU cluster task, we’re using both a deterministic code check and an LLM judge, so we set the suite's verdict to hybrid and name a judge model:
 // example.suite.mjs
import { defineSuite } from "hurdle";

export default defineSuite({
 // The API under test, and the name of the env var that holds its key.
 api: {
 authorizationCredential: "TOGETHER_API_KEY",
 hosts: ["api.together.ai"],
 },

 tasks: ["./tasks/gpu-cluster"],

 // The two models we tested in June.
 agents: [
 { runner: "claude-code", model: "claude-opus-4-8" },
 { runner: "claude-code", model: "claude-sonnet-4-6" },
 ],

 // Use conditions to run each task with and without our GPU clusters skill.
 conditions: {
 baseline: {},
 "with-skill": {
 skills: [{ name: "together-gpu-clusters", sourceDirectory: "skills/together-gpu-clusters" }],
 },
 },

 // Run every combination of task, agent, and condition 15 times.
 repeats: 15,

 // A run passes only if the code checks and the judge both pass.
 verdict: "hybrid",
 judge: { model: "claude-opus-4-8" },
}); 
 Run and view results
 npx hurdle run runs the suite. Adding --view opens the results viewer when the suite finishes:
 npx hurdle run --view 
 Hurdle runs each task for every agent and condition in the suite, as many times as repeats says. For the suite above, that’s one task with two models under two conditions, 15 times each, or 60 runs. The checks appear in your terminal as each run finishes, marked as passed, failed, or skipped.
 The viewer shows the suite’s headline numbers at the top: pass rate, average duration, and average cost per run. Below that, a grid breaks down the pass rate by task and condition, so you can see which combos are failing:

 Click into a run to see exactly what the agent did, including a full transcript, a list of the agent's tool calls and API requests, plus the result of every check and the judge's final assessment.

 Hurdle saves the results to .hurdle/ in your project directory, so you can reopen the viewer by running npx hurdle view .
 Local runs
 For quick tests on tasks you trust, you can run your evals locally, much as you would if you were prompting the agent yourself.
 Hurdle starts the claude or codex CLI on your machine in a temporary workspace, hands it the task's prompt and files, and records the session. Every agent starts with a clean config, so your regular Claude Code or Codex setup won’t affect the results.
 Local runs come with two caveats: First, Hurdle can’t see or block the agent’s API requests, so you can’t use guards or request checks. But more importantly, the agent runs as you , so it can read local files and use your real API keys.
 For anything complex or risky, you should always use a sandbox.
 Sandboxed runs
 For production evaluations, Hurdle uses the Together Sandbox API to spin up isolated environments where coding agents can execute code, install dependencies, and interact with APIs without accessing your local machine.
 Each run gets a fresh sandbox, so agents start from a clean environment rather than inheriting files or state from previous runs. Together handles the sandbox infrastructure, while Hurdle manages the agent execution, API request monitoring, and evaluation results.
 When you start a sandboxed run, Hurdle launches a local proxy called Guardian, then opens a single WebSocket to Together, which boots a fresh Together Sandbox for the run. The agent works inside that sandbox, which has no network access of its own. Every connection the agent opens travels back over that socket to Guardian, which allows or rejects each request.

 Your keys never enter the sandbox—the agent gets random stand-ins, and when it calls your API, Guardian swaps in the real key and forwards the request. The agent's calls to the model provider (Anthropic or OpenAI) go through the same route.
 This routing is what lets Hurdle check requests, enforce guards, and keep your keys safe:
 API request checks: Every request passes through Guardian, so your checks can see exactly which calls the agent made.
 Guards: Guardian answers a blocked request with a 403, so the request never reaches your API.
 Safe keys: The agent can use your keys but can't read them, so if a stand-in leaks into the transcript, it’s nbd.
 By default, the sandbox doesn't limit which endpoints the agent can call. The agent can send any request to your API with your key, so give your evals a dedicated key with a low balance, and add a guard for anything dangerous.

 Delegating research tasks to AI does not remove scientists’ responsibility for how the work is accomplished. For example, a researcher using AI to review the literature needs to check whether the system overlooks conflicting evidence or makes claims the cited papers don’t support. A researcher automating part of a lab protocol needs confidence that the system respects physical safety constraints, such as temperature limits or material toxicity, while a researcher working with human-participant data needs assurance that a system protects participants' privacy and limits who can access their information. Researchers also need clear institutional guidelines for verifying and disclosing AI-assisted work.
 These ethical and safety questions are central to our work on AI for science. Responsible science is about more than accuracy—scientific fields have ethical research norms because of past actions and choices by scientists and scientific communities, and those norms also cover how research is conducted and what impact it has. We want AI tools to expand what scientists can accomplish without compromising their ability to scrutinize evidence, verify methods, and – perhaps most importantly – stand behind their findings.
 To better understand what that requires, we interviewed 17 scientists working in the natural, applied, and social sciences about the responsible development of AI agents. The interviews drew on a network of researchers established through earlier survey work—we wanted to understand how scientists would steer AI’s development to reflect the responsibilities of their fields.  Our interest in these questions grew out of work to evaluate the safety of models developed at Ai2. Together, they reflect concerns that go beyond whether an AI system produces a correct answer. Researchers also need to understand how an answer was reached, protect sensitive information, recognize bias, and determine who is charged with verifying and standing behind AI-assisted findings. These are matters of responsible conduct of research.
 Another main finding suggests that scientists should help decide which research tasks agents take on, how those agents operate, and how their performance is evaluated. Even a technically correct result may be unsuitable for scientific use if researchers cannot inspect how it was produced, or if an agent accesses confidential data or files beyond what the researcher authorized.
 A third key finding pertains to the future of science. Interviewees were divided between excitement about AI-driven progress and existential concern about the role of human scientists. They proposed training in AI use and named developing and enforcing guidelines as a critical, timely challenge.

 Attention can be a major bottleneck when serving world foundation models , where long sequences make inference computationally demanding. On NVIDIA Hopper and NVIDIA Blackwell data center GPUs, FlashAttention3 and FlashAttention4 improve attention performance by overlapping matrix multiply-accumulate (MMA) operations through softmax within a thread block.

 However, these hardware-specific pipelines cannot be applied directly to the NVIDIA RTX PRO 6000 Blackwell Series (SM120), which uses a different Tensor Core architecture. For video generation models using BF16 inference, attention remains primarily MMA-bound on NVIDIA Blackwell RTX GPUs, while softmax is a major bottleneck in forward attention on Blackwell data center GPUs.

 Introduced with NVIDIA Blackwell architecture, NVFP4 offers hardware-accelerated 4-bit matrix multiplication, enabling higher Tensor Core throughput and creating an opportunity to accelerate attention beyond BF16. But sustaining high throughput requires careful coordination of softmax, data movement, and intermediate storage. Dependencies between these stages can leave Tensor Cores idle, limiting how effectively the kernel uses the available compute.

 This post explains how to accelerate NVFP4 attention on the SM120 architecture through register recycling and improved scheduling. By reclaiming score registers after the softmax outputs have been packed into NVFP4, the next tile’s matrix multiplication can overlap with remaining softmax work on the current tile. This creates a more efficient pipeline that reduces Tensor Core idle time and improves utilization without requiring a second full score buffer.

 Reactor , a developer platform that provides global low-latency infrastructure and APIs for deploying and scaling real-time video, robotics, and world models, integrated this kernel in their production serving stack to serve real customer traffic and saw tremendous speedups. Their benchmarks are shared in this post.

 Improving throughput with NVFP4 

 NVIDIA RTX Blackwell has lower BF16 matmul throughput compared to the data center variants. While data center workloads are bounded by softmax (FlashAttention4 tries to solve this through pipelining and exp2 emulation), the NVIDIA RTX Blackwell is bounded by MMA on BF16 Attention. Due to higher TFLOP/s for NVFP4, throughput can be improved to achieve better performance.

 Attention compute 

 The general attention computation and the two core matrix multiplications it involves are:

 Query-Key matrix multiplication (\(QK\)) : The first matmul in attention, \(QKᵀ\), where \(Q\) contains query vectors and \(K\) contains key vectors. It computes the attention scores used by softmax.

 Attention-Weight Value matrix multiplication (\(PV\)) : The second matmul in attention, \(PV\), where \(P\) contains softmax-derived attention weights and \(V\) contains value vectors. It combines the value vectors according to their attention weights to produce the output. In the tiled attention kernel discussed here, \(P\) contains unnormalized softmax weights, and final normalization is applied after the output has been accumulated across tiles (similar to FlashAttention).

 How SageAttention3 accelerates attention using NVFP4 

 SageAttention3 is a native NVFP4 attention mechanism specifically designed for NVIDIA RTX Blackwell streaming multiprocessor (SM) 120. It performs both \(QK\) and \(PV\) using NVFP4​. Its primary innovation came from performing two-level scaling for \(P\).​

 NVFP4 quantization generates two tensors: an NVFP4 data tensor and an FP8 scaling tensor. Because ​softmax outputs are bound to a narrow [0, 1] range, they can underutilize the NVFP4 dynamic range, resulting in accuracy degradation. Two-level scaling addresses this by first normalizing the values to fully utilize dynamic range before quantizing the result.

 The CTA uses four producer warps and eight consumer warps. For each N128 tile, consumers execute \(QK\), softmax and probability quantization, and \(PV\) in sequence.

 The following observations can be drawn from this CTA design and the parallel thread execution (PTX) and instruction set architecture (ISA) for NVIDIA RTX Blackwell GPUs:

 First, TMA Loads are bound to Shapes of 128×128, not utilizing the entire shape would mean underutilizing our GPU bandwidth.

 Second, the NVIDIA Blackwell RTX OMMA operation remains constrained to m16, n8, k64 (where m and n represent LHS/RHS free dimensions, while k is the contraction axis), as specified by the PTX instruction mma.sync.aligned.kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64 .​

 To cover the full contraction dimension of k=128, two MMA instructions with k=64 must be issued. The current CTA design issues these instructions for \(QK\) in succession. Because MMA execution is synchronous, the issuing consumer warps wait for completion before proceeding to online softmax and intermediate quantization.

 This means that the operations within the stable loop are sequentially pipelined. There is a large gap in MMA activity, as there is no compute scheduled on the tensor cores. The warps are busy computing the softmax, scaling, and quantization operations.

 Register constraints

 Producer warps use 3,072 registers, and consumer warps use 59,392 registers. The total of 62,464 registers occupies approximately 95.3% of the SM’s register capacity. This leaves little room to hold an additional score tile while processing the current tile.

 Optimized CTA design

 The design retains four producer warps, eight consumer warps, and complete N128 K/V tile loads. The change is in how consumers compute and store attention scores. Each N128 score tile is split into two N64 halves, and each occupies a separate register slot.

 After one half has been exponentiated and quantized, its score registers are reused to compute the corresponding \(QK\) half of the next tile. This interleaves the next tile’s \(QK\) to work with the current tile’s remaining softmax, quantization, and \(PV\) operations.

 The online-softmax state is still updated across the complete N128 score tile before either half is consumed.
