# MotionBricks

[Project page](https://nvlabs.github.io/motionbricks/) · [Paper](https://arxiv.org/abs/2604.24833)

MotionBricks generates motion in real time for humanoid robots and human characters.
Give it the character's recent poses and the poses it should reach next, and it
generates the movement connecting them.

Smart Primitives turn target poses into reusable building blocks for navigation
and object interactions, without retraining the model. The accompanying software
includes SOMA and Unitree G1 demos built with Newton and Warp, plus tools for
creating your own primitives and scenes.

## Models

This repository contains pretrained SafeTensors weights for two model families:

| Model | Use | Details |
| --- | --- | --- |
| SOMA | Generate human motion on the SOMA skeleton. | [Model card](soma/README.md) |
| Unitree G1 | Generate motion for the Unitree G1 humanoid. | [Model card](g1/README.md) |

Each folder includes the model's weights, configuration and supporting files.
Keep them together. The SOMA and G1 files are not interchangeable.

## Get started

**To try the demos**, start with the [MotionBricks software](https://github.com/NVlabs/motionbricks).
It includes ready-to-use ONNX models, so you do not need to download these
checkpoints to run it. The TensorRT demo runtime requires an NVIDIA GPU.

**To export ONNX models or build another runtime**, download the weight packages:

'''sh
hf download nvidia/MotionBricks --local-dir MotionBricks
'''

For just one model, add `--include "soma/*"` or `--include "g1/*"`.
The files are already unpacked. Follow the software's `tools/onnx` guide to export
them, using the matching family folder.

## Model details and limitations

The family cards explain each model's inputs, outputs, training data, evaluation
and limitations. Each model uses three networks together. These weight
packages are not Transformers `from_pretrained` models, and this repository does
not include a training pipeline or the full training data. The packages contain
weights and inference metadata, not the optimizer and training-loop state needed
to resume the original training runs.

The G1 package does not include the original demo motion bank, `out/G1-clip.ckpt`.
Demo motion examples are separate from the model weights.

MotionBricks generates motion, not a controller for a physical robot. Running the
motion on hardware requires a separate tracking controller, robot-limit checks
and safety validation.

 Groundhog Day for AI agents: Prompt caching patterns for using OpenAI models on Amazon Bedrock

 Every time you spin off your agent, it has to re-read its whole life story before performing an action. Here’s how to make it remember without having to feed it the same context again. 

 In the movie Groundhog Day , Bill Murray’s character re-lives the same February 2 every day. He wakes up to the same song playing on the radio, in the same inn, and the same small town, again and again for what some movie fans estimate to be 34 years.

 Nothing he accomplished the day before carries over unless he works it out again from scratch. AI agents live in a version of Groundhog Day. Every time an agent takes a step (calls a tool, reads the result, decides what to do next), it has to send the model its entire story so far to maintain continuity: the tool definitions, the instructions, every previous tool call, and every result. The model only predicts the next token based on the input you provide. It has no internal memory between requests, so it must read all of it again. By turn 20 of a coding session, the model re-reads turns 1–19, and it’s you who pays for every one of those tokens, again and again.

 Prompt caching breaks the cycle. The service stores your input prompt (instructions, tools, and content) and reuses it on the next request, at a fraction of the input price.

 In this post, I walk you through an agent’s life, from its first turn to when it gets new tools and spawns helpers. Along the way, I show you how prompt caching keeps costs down and keeps agents responsive and consistent.

 What an agent sends to its LLM

 Before talking about caching, it helps to look at what a typical agent’s first invocation to the large language model (LLM) contains:

 Tool list – The definitions of every function the agent can call. Changes when you ship a new release.

 Instructions – The developer prompt: rules, persona, policies, examples. Also changes per release.

 History – Everything that happened in this session so far: the task, the model’s tool calls, and the tool results (which grows every turn).

 New turn – The latest tool result or user message (which might be different every time).

 What an agent sends to the model, turn after turn if you don’t set up caching: 

 Figure 1: What an agent sends to the model on every turn

 How prompt caching works under the hood

 When a model reads a prompt, it first does a write called prefill . During prefill, it processes every input token and builds its key and value vectors (also known as key-value, or KV), which form the model’s working state. This happens before the model writes its first token.

 Prompt caching saves that state, which contains the system prompt, tools, content, history, and so on. When a later request starts with the same input tokens (that is, the same text), the prompt caching service loads the saved state instead of computing it again. It then processes only what is new in the next payload to the model. Prompt caching can be implicit, where Amazon Bedrock selects where the reusable prefix ends, or explicit, where your code marks that endpoint using prompt_cache_breakpoint . You can use both approaches together, and we recommend doing so.

 Turn 1 compared to turn 2 

 Figure 2: Turn 1 saves the prompt prefix up to the breakpoint, and turn 2 reuses it and pays full price only for the new question

 Implicit or explicit, and why do we need both? 

 For agentic workloads, implicit caching lets Bedrock choose what to cache as the conversation grows. With explicit caching, you can mark shared content, such as tools and instructions, for reuse across sessions and when spinning up helper agents. You don’t always need both forms of caching, but combining them gives you a reusable starting point while Bedrock manages the growing conversation automatically.

 New sessions can also reuse that shared starting point while each conversation builds on its own cached history. In this post, we start with the first turn, then show how to carry cached content through later turns, new tools, and across subagents.

 Hello cached world

 The first win is to cache the static part of the prompt: the tools and instructions that stay the same across requests. These examples use your existing Amazon Bedrock client, TOOLS , and task . Replace the shortened INSTRUCTIONS string with your real policies and examples. The reusable prefix must reach 1,024 tokens to qualify.

 When caching static content, use explicit mode: choose where the saved prefix ends.

 KEY = "support-agent:v7:gpt-6-astra"
INSTRUCTIONS = "Your full support policies and examples..."

# Rendered context: [provider context][TOOLS][INSTRUCTIONS] | [task]
# Cache starts at the beginning; the marker below chooses its end.
resp = client.responses.create(
 model="us.openai.gpt-6-astra",
 store=False, # Response storage; prompt caching still works.
 include=["reasoning.encrypted_content"],
 prompt_cache_key=KEY,
 prompt_cache_options={"mode": "explicit", "ttl": "30m"},
 tools=TOOLS, # Rendered before instructions; keep order stable.
 input=[
 {
 "role": "developer",
 "content": [{
 "type": "input_text",
 "text": INSTRUCTIONS,
 # Save through this whole block, including TOOLS.
 "prompt_cache_breakpoint": {"mode": "explicit"},
 }],
 },
 # User message is processed but not cached.
 {"role": "user", "content": task},
 ],
) 

 The prompt_cache_key tells the service which requests are meant to share a cache. We come back to how to use it when we get to reading the cache in new sessions. In one of our tests using explicit caching, the roughly 4,000-token tools-and-instructions prefix wrote 4,120 tokens on the first request and read those 4,120 tokens on later requests. The task (or user request) comes after the cache boundary, so this doesn’t trigger a write to the cache.

 Keep in mind that prompt caching works only when you pass exactly the same text. Make sure that the agent’s instructions and tool lists are serialized the same way every time. Model Context Protocol (MCP) servers and other forms of tool delivery need to be indexed to make sure they stay consistent. Keep anything that varies, such as the date, the user’s name, or a request ID, after the cached instructions.

 As the content grows and varies (different tools and content), use implicit mode to let the service follow the conversation. Here, the first request has no explicit marker. Its latest eligible message is the user’s task, so the automatic breakpoint comes after that task and covers the tools, instructions, and task together. The mode is shown explicitly in the following example for clarity, even though implicit is the default. Setting store=False leaves conversation history in your application. It doesn’t disable caching.

 def ask_with_implicit_cache(history):
 return client.responses.create(
 model="us.openai.gpt-6-astra",
 store=False,
 include=["reasoning.encrypted_content"],
 prompt_cache_key=KEY,
 prompt_cache_options={"mode": "implicit", "ttl": "30m"},
 tools=TOOLS,
 input=history, # Everything gets cached
 )

history = [
 {"role": "developer", "content": INSTRUCTIONS},
 {"role": "user", "content": task},
]
# Automatic endpoint: the end of the user message.
resp = ask_with_implicit_cache(history) 

 This is useful when the next turn continues the same task. A different task doesn’t match the prefix through the old task, and the implicit write doesn’t necessarily create a separate entry for only the tools and instructions. Use an explicit marker there when you need that shorter shared prefix to be reusable across tasks.

 Use both when the agent needs a shared starting point and a growing history. Start with the marked developer block in the following code example and call the function ask_with_implicit_cache . The request-level mode stays implicit. The block-level marker adds an explicit save point after the instructions. The service can also save through the latest eligible message. This keeps the shared prefix available while the conversation grows.

 history = [
 {
 "role": "developer",
 "content": [{
 "type": "input_text",
 "text": INSTRUCTIONS,
 "prompt_cache_breakpoint": {"mode": "explicit"}, 
 }],
 },
 {"role": "user", "content": task},
]
# Still implicit mode, now with an explicit startup save point in the history.
resp = ask_with_implicit_cache(history) 

 Caching conversation history and tool results

 The model requests tools by name and supplies their arguments. Your application must execute them. execute_function is a helper you build to route those requests to the matching Python functions and return their results. The following loop uses this helper to run each requested tool. It appends the model’s output and all tool results to the history list, then sends that list again until the model returns a final answer. In implicit mode, Amazon Bedrock can reuse the unchanged prefix and cache the added content through the last tool result. Keep earlier messages and the initial TOOLS unchanged.

 import json

# Map tool names to their Python implementations.
TOOL_HANDLERS = {
 "get_owner": get_owner,
 # Register your other initial tools here.
}

def execute_function(name, arguments):
 """Run the requested tool and return its result."""
 handler = TOOL_HANDLERS.get(name)
 if handler is None:
 return {"error": f"Unknown tool: {name}"}
 return handler(**arguments)

while True:
 # Preserve all output items, including encrypted reasoning.
 history.extend(resp.output)
 calls = [x for x in resp.output if x.type == "function_call"]
 if not calls:
 break
 for call in calls:
 result = execute_function(call.name, json.loads(call.arguments))
 history.append({
 "type": "function_call_output",
 "call_id": call.call_id,
 "output": json.dumps(result),
 })
 # The last result in this group supplies the automatic endpoint.
 resp = ask_with_implicit_cache(history) 

 For follow-ups, append a new user message and call the helper again

 Build agentic retrieval on a Managed Amazon Bedrock Knowledge Base with CDK

 This post builds enterprise agentic retrieval on a Managed Amazon Bedrock Knowledge Base with the AWS Cloud Development Kit (AWS CDK). To see why that’s worth building, it helps to start with where ordinary Retrieval Augmented Generation (RAG) breaks down. Most RAG systems start the same way: they embed the question, fetch the nearest chunks from one index, hand them to a model, and return the answer. One retrieval, one generation. For a large class of questions that’s the right design, and there’s no reason to build anything more complicated.

 It fails in a recognizable way. Ask a question whose answer spans two corpora, and a single retrieval returns half of what the model needs, which is worse than returning nothing, because the answer comes back fluent and incomplete. Ask a question where the right source depends on the question , and a single index has no mechanism to choose. Ask a question that needs a second look at the corpus after seeing the first result, and there is nowhere for that second look to happen.

 Enterprise agentic retrieval answers all three by putting a reasoning agent in the loop. The agent decides whether to retrieve, which knowledge base to consult, and whether to go back for more before it composes an answer. This is the direction Amazon Bedrock Knowledge Bases have evolved. With the launch of the Managed Knowledge Base, retrieval is no longer a single embed-and-fetch call. It has become an agentic capability: multi-turn planning, tool-driven retrieval, and grounded, cited answers. The AgenticRetrieveStream API offers this as a first-class service feature rather than something you assemble yourself. That works, and it also introduces a genuinely harder operational problem. A single-shot pipeline is a function you can reason about by reading it. An agent that reasons and retrieves in a loop takes a different path on every question. By default you can see neither the path it took nor whether the answer it produced was any good. Observability stops being a nice-to-have and becomes the only way to know the system works.

 In August 2024, Build an end-to-end RAG solution using Knowledge Bases for Amazon Bedrock and the AWS CDK deployed the single-shot design as a CDK application: an Amazon Simple Storage Service (Amazon S3) corpus, an Amazon OpenSearch Serverless collection and index, a knowledge base, and a data source, provisioned as CDK stacks whose order you sequenced by hand.  Background

 Before the walkthrough, it helps to establish three things: what makes retrieval agentic, why the Managed Knowledge Base is the right foundation for it, and why observability and evaluation belong in the design rather than bolted on later.

 From RAG to enterprise agentic retrieval

 Classic Retrieval Augmented Generation (RAG) does one retrieval and one generation. Enterprise agentic retrieval puts a reasoning agent in the loop: it decides whether and what to retrieve, can retrieve several times to refine, chooses which knowledge base is relevant (semantic routing), and only then composes a grounded answer with citations. With the Managed Knowledge Base, this is a first-class service capability, the AgenticRetrieveStream API performs the multi-turn planning, executes the retrieval, and returns a cited answer, rather than an orchestration layer you build and maintain over a raw vector search. That produces better answers on complex questions, but it also produces a more complex system to operate, which is exactly why observability and evaluation are built in from the start.

 Managed compared to do-it-yourself Knowledge Bases

 Amazon Bedrock now offers a Managed Knowledge Base (Type: MANAGED): Amazon Bedrock manages the ingestion, storage, indexing, and retrieval for you, including embedding and reranking with service-managed models by default, so there is no vector database to provision, scale, or patch .  AI isn’t a shortcut. 
It’s how business gets ahead.
 Contact sales 
 For nearly two years, one comforting idea has shaped how companies and government contractors adopt open-weight AI models that anyone can download and run. If we run the weights on our own servers, the thinking goes, our data can't leave the building and our systems are secure.

 It's easy to see why that idea caught on.

 Security chiefs and policymakers in Ottawa, Washington (DC), London, Berlin, and Tokyo have been offered two kinds of black box. The first is the closed API from a big lab: send proprietary code and sensitive data into someone else's cloud and take the vendor's word that the model is safe, without ever seeing the data lineage or the trade-offs around safety behind it. The second looked like the way out: download an open-weight model, host it on your own hardware, and you don't have to trust the provider at all.

 Thousands of engineering teams have taken the second road, and a growing share took it with Chinese models, which are capable and cheap. In the year before March 2026, Chinese models accounted for 41 percent of downloads on Hugging Face, according to the platform's spring 2026 report . On OpenRouter, a service that routes requests to many different AI models, they handled more than 30 percent of the AI work companies ran through the platform every week from February through early July. When lawmakers in Washington opened an investigation into corporate use of Chinese models this spring, one chief executive summed up a view common in boardrooms well beyond the United States, "An open-source model does not have access to data. It doesn't work that way," implying that simply hosting a model in a trusted environment makes it safe.

 That holds for a chatbot which only answers questions, but enterprise AI has moved on. Engineers now wire models into terminals, headless browsers, code interpreters, and cloud consoles so they can write software, query databases and fix infrastructure on their own. Once a model can type into a command line, whatever was baked into its weights during training gets a keyboard inside your network.

 Recently, during a joint cyber capabilities effort in Toronto with Cohere Cyber, our newly established business as part of our AISLE acquisition, the research team caught an Alibaba Qwen3.8 model doing something that should never happen . Asked to write a defensive detection rule, Qwen3.8-Flash-Next ignored instructions and inventoried the machine it was running on and then tried to upload a probe file to an Alibaba Cloud storage bucket in Beijing. Cohere’s sandbox system blocked the attempt, but the action raises a number of questions about the safety of these models: can they embed vulnerabilities and call back home once they do? Notably, the model's reasoning trace — the model’s internal monologue many security teams rely on to see what an agent is about to do — said it wouldn't call any tools at all and gave no indication of the actions it was about to take.

 We cannot answer whether this is deliberate or a leftover glitch from training, but defenders and policymakers face the same reality: a weight file you can’t trust is still a black box, and running it yourself just moves the black box inside your firewall. In synchronous distributed training, a job advances at the pace of its slowest rank. One degraded GPU, interface, storage device, or switch path can waste useful time across many healthy resources.

 The failures that hurt yield are often subtle: A GPU runs a few degrees hotter than its peers. An NVMe device loses performance only under sustained load. A switch generates a pause-frame storm that looks like dozens of unrelated symptoms. None of these signals necessarily crosses a static threshold. Together, they create stragglers, extended step times, and delayed checkpoints.

 Diagnosis becomes harder because the evidence is split across teams. Network operators see interface counters and fabric events. Compute operators see node and GPU health. ML teams see changing step times, failed jobs, or unstable inference latency. Each view is accurate, but the relationships between them remain hidden. Triage becomes a chain of dashboard searches and cross-team handoffs, which can turn a contained fault into hours or days of lost production time before the affected node or fabric path is identified.

 This post covers how NVIDIA Minerva, an AI-native AIOps platform designed around AI factory topology and workloads, addresses these operational gaps.

An AI agent-powered assistant and MCP server connected to external agentic tools give operators a conversational path through the same live evidence. The goal is practical: preserve effective GPU hours and keep model training moving.

 Why conventional monitoring breaks at AI factory scale 

 Rule-based monitoring assumes that a known metric crossing a known boundary indicates a known condition. That model works for clear failures. It struggles with so-called “gray failures,” where a component stays available, and the relevant issue may appear only under load or in comparison with peers. Absolute thresholds can miss the shift. Aggressive thresholds often add warnings during normal workload changes, leaving the on-call engineer to decide which deviation matters.

 Scale adds alert amplification. One physical fault can produce interface errors, RX (receive) pause frames, congestion indicators, GPU utilization changes, and slower job progress. These observations describe the same dependency chain, but separate dashboards or alerts present them as unrelated events. The on-call engineer receives a volume of alerts and needs to manually correlate the alerts, determine the signal from the noise, analyze the root cause and the jobs exposed to it.

 For operations, the workload is the unit that matters. Teams need to know which job is affected, which resources it occupies, where those resources sit in the physical and logical topology, and how current behavior differs from a healthy baseline. That context must remain current as jobs start and stop and as nodes are drained, replaced, or returned to service. Without it, a healthy component dashboard can coexist with poor job throughput and offer no explanation.

 Building a live model of infrastructure and jobs

NVIDIA Minerva ingests metrics, logs, and topology from GPUs, Spectrum-X and NVLink switches, SuperNICs, DPUs, storage, NVIDIA NCCL, schedulers, and AI workloads. Auto-discovery supplies the relationships that raw telemetry lacks.
