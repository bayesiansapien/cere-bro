```text
# Granite Switch 4.1 8B

📝 **Read the launch blog:** [Granite Switch 4.1: Chat, Decisions, and Speech from One Endpoint](https://huggingface.co/blog/ibm-granite/granite-switch-4-1)

**Model Summary:** Granite Switch 4.1 8B is a modular LLM that composes a base model, multiple adapters and an encoder together so that a single hosted endpoint can move between natural-language responses, general and specialized decisions, and speech-to-text.

Adapters are activated on demand via control tokens in the chat template. For full details on model composition and adapter configuration, see [BUILD.md](BUILD.md).

- **Base Model:** `ibm-granite/granite-4.1-8b` (8B params, 128K context)
- **Adapters:** 2 — `decision` (aLoRA, general-purpose Decisions) and `guardian-core` (aLoRA, from `granitelib-guardian-r1.0`)
- **Audio:** embedded speech-to-text via `ibm-granite/granite-speech-5.0-470m-turboctc` (470M params, English)
- **License:** [Apache 2.0](https://www.apache.org/licenses/LICENSE-2.0)
- **Release Date:** October 14, 2026
- **Backends:** HuggingFace Transformers, vLLM
- **Automatically Composed with:** [granite-switch](https://github.com/generative-computing/granite-switch)

Granite Switch is also available in [granite-switch-4.1-30b](https://huggingface.co/ibm-granite/granite-switch-4.1-30b) (same Chat + Decisions + Guardian + speech configuration, 30B base), and with the complete Granite Libraries bundle (no audio) in [granite-switch-4.1-8b-preview](https://huggingface.co/ibm-granite/granite-switch-4.1-8b-preview), [-30b-preview](https://huggingface.co/ibm-granite/granite-switch-4.1-30b-preview), and [-3b-preview](https://huggingface.co/ibm-granite/granite-switch-4.1-3b-preview).

#### Recreating this checkpoint

This checkpoint is produced by composing the base model with `guardian-core` from the Guardian
library and `decision` from the Core library — `--include-adapters` drops every other adapter each
library ships — plus the ASR cascade (`--enable-audio`, default Granite Speech 5.0 TurboCTC):

'''bash
python -m granite_switch.composer.compose_granite_switch \
  --base-model ibm-granite/granite-4.1-8b \
  --adapters ibm-granite/granitelib-guardian-r1.0 ibm-granite/granitelib-core-r1.0 \
  --include-adapters guardian-core decision \
  --enable-audio \
  --output ./granite-switch-4.1-8b
'''

See [BUILD.md](BUILD.md) for the exact adapter ranks/targets this checkpoint ships with, and the
[adapter catalog](https://generative-computing.github.io/granite-switch/adapter_catalog.html) for
every other adapter available to compose into your own checkpoint.

### Using with Mellea

[Mellea](https://github.com/generative-computing/mellea) is the preferred way to run Granite Switch adapters in applications. It wraps **every adapter in the Granite Libraries family** (guardian, rag, core) as a direct operation instead of raw prompt engineering — see the full [Mellea + Granite Switch guide](https://github.com/generative-computing/granite-switch/blob/main/tutorials/guides/mellea_with_granite_switch.md) for the complete set of intrinsics (e.g. `policy_guardrails`, `factuality_detection`, if composed into a checkpoint). Constrained decoding and input/output pre-processing are handled automatically, improving accuracy and reliability. The `guardian_check` call below works unchanged for `guardian-core` in this checkpoint.

`decision` is now part of Granite Libraries — it ships in [`granitelib-core-r1.0`](https://huggingface.co/ibm-granite/granitelib-core-r1.0/tree/main/decision) — but has **no Mellea intrinsic yet**: use the low-level section below for it meanwhile. Mellea support for `decision` is planned and will later collapse it to a single call too. An Adapter SDK for training your own custom and third-party adapters in [Mellea](https://docs.mellea.ai/advanced/lora-and-alora-adapters) is planned.

### Guardian and Decision, Side by Side

Both adapters live in **one checkpoint**, served by **one running vLLM server**. Activating either
one is a one-field difference on the request: `extra_body={"chat_template_kwargs": {"adapter_name":
...}}`. Start the server once:

'''bash
pip install -e ".[vllm]"

python -m vllm.entrypoints.openai.api_server \
  --model ibm-granite/granite-switch-4.1-8b \
  --port 8000
'''

Each adapter is read back the way its own training actually documents, not a one-size-fits-all trick:

#### `decision` — read its calibrated probability over the option labels

`decision` is trained to answer by gathering the logits of the single-token option labels and taking
their softmax — so ask the server for exactly those tokens' logprobs with `logprob_token_ids` (a vLLM
extension, passed via `extra_body`; it returns the logprob of exactly the ids you name, so a
low-probability option can't be missed the way asking for "top-K by probability" could — see vLLM's
`SamplingParams.logprob_token_ids`). The request itself is just two `user` turns — a state turn and a
question turn — with no system prompt: that keeps the state turn's tokens identical to a plain chat
request about the same state, so vLLM's prefix cache can share them instead of every decision request
paying for its own separate prefix:

'''python
import math

from openai import OpenAI
from transformers import AutoTokenizer

MODEL_ID = "ibm-granite/granite-switch-4.1-8b"

client = OpenAI(base_url="http://localhost:8000/v1", api_key="unused")
tokenizer = AutoTokenizer.fro
```

```text
Timestral is a **family of time series foundation models** for zero-shot forecasting, available in [**5M**](https://huggingface.co/mistralai/Timestral-5M), [**28M**](https://huggingface.co/mistralai/Timestral-28M), [**123M**](https://huggingface.co/mistralai/Timestral-123M), and [**209M**](https://huggingface.co/mistralai/Timestral-209M) parameter versions. 
This repository contains the 123M checkpoint. 

>[!Note]
> For more information about our Timestral family, go to the main model page: [Timestral-209M](https://huggingface.co/mistralai/Timestral-209M).

## Model Details

- **Size:** 123M parameters.
- **Architecture:** patch-based transformer with time attention and variate attention, 20 layers, embedding dimension 640.
- **Patching:** 32 time steps per patch. Each patch is embedded from its values together with their missing-value indicators.
- **Context length:** up to 32,768 time steps (1,024 patches). 
- **Forecast horizon**: Up to 1,024 time steps (32 patches) in a single forward pass. Longer horizons are forecast block by block, with each block's median forecast appended to the context.
- **Outputs:** 21 quantiles (0.01, 0.05, 0.1, 0.15, …, 0.85, 0.9, 0.95, 0.99). 
- **Inputs:** univariate or multivariate target variates, plus past-only and known-future covariates, numeric or categorical (categorical covariates are target-encoded). Missing values are marked as NaN.
- **Inference:** PyTorch on CPU or GPU.

## Benchmarks
Timestral-209M achieves **state-of-the-art zero-shot accuracy** across three major forecasting benchmarks: [GIFT-Eval](https://huggingface.co/spaces/Salesforce/GIFT-Eval), [TIME](https://huggingface.co/spaces/Real-TSF/TIME-leaderboard), and [fev-bench](https://huggingface.co/spaces/autogluon/fev-bench).

Smaller Timestral models offer a trade-off between model size and forecasting performance. All Timestreal models outperform every other model at the respective model size. See the Pareto-front plot on the [main model page](https://huggingface.co/mistralai/Timestral-209M).
```

```text
        trust_remote_code=True,
        dtype=torch.bfloat16,
        device_map={"": DEVICE},
        attn_implementation="flash_attention_2",
    ).eval()

    def rerank(
        query: str,
        documents: list[dict],
    ) -> torch.Tensor:
        scores = []
        for document in documents:
            document_content = []
            if document.get("text") is not None:
                document_content.append({"type": "text", "text": document["text"]})
            if document.get("image") is not None:
                document_content.append({"type": "image", "image": document["image"]})

            inputs = processor.apply_chat_template(
                [
                    {
                        "role": "query",
                        "content": [{"type": "text", "text": query}],
                    },
                    {"role": "document", "content": document_content},
                ],
                tokenize=True,
                add_generation_prompt=False,
                return_dict=True,
                return_tensors="pt",
            )
            if inputs["input_ids"].shape[-1] > MAX_MODEL_LEN:
                raise ValueError("Input exceeds 32768 tokens; shorten the text or resize the image.")
            inputs = inputs.to(DEVICE)

            if inputs.get("pixel_values") is not None:
                inputs["pixel_values"] = inputs["pixel_values"].to(model.dtype)

            with torch.inference_mode():
                score = model(**inputs).logits.squeeze().float()
            scores.append(score)

        # Higher scores indicate greater predicted relevance.
        return torch.stack(scores)

    query = "What is NVIDIA NeMo Framework?"

            "image": None,
        },
        {

            "text": None,
            "image": image,

            "text": biology_text,
            "image": None,
        },
```

```text
 Summary

 Timestral, Mistral’s first family of time-series foundation models, delivers state-of-the-art probabilistic, multivariate forecasts with just 209M parameters, outperforming larger models on key benchmarks while supporting past and future covariates. Available in four sizes (5M to 209M parameters), it balances accuracy and efficiency, running efficiently on CPUs and excelling in zero-shot forecasting for diverse domains. The model combines synthetic pre-training, covariate-aware attention, and long-context learning, with fine-tuning options for domain adaptation via Mistral Forge.

 Today, we’re releasing Timestral, our first family of time-series foundation models. Our largest model, at just 209M parameters, ranks first on all three of the field's main public benchmarks, GIFT-Eval, TIME, and fev-bench, outperforming the previous state of the art with only two-thirds of the model parameters.
 Timestral delivers probabilistic, multivariate forecasts and supports past-only and known-future covariates. Our family of models sits on the Pareto front of forecasting accuracy versus model size, delivering leading performance at each size. Results have been submitted to the GIFT-Eval and TIME leaderboards.
 Time Series Foundation Models (TSFM)
 Time series is one of the most common data types in enterprise, from sensor telemetry to observability metrics. Forecasts built on it drive decisions in capacity planning, energy, supply chains, risk and maintenance.
 Industrial plants forecast process sensors against the production schedule, catch equipment drift before it fails, and plan capacity and spare parts across thousands of assets. Finance teams forecast flows, volumes, and volatility to inform positions, hedging, and treasury across thousands of accounts.
 Classical models such as ARIMA and linear regression remain well-established tools for forecasting time series. These models are usually fitted to a single series and learn only from that series' history.
 Deep learning models such as PatchTST add the capacity to learn nonlinear patterns across many related series, but they are still typically trained from scratch on each dataset, so what they learn doesn't carry over to new domains.
 Time series foundation models bring the pre-training approach to time series. Trained on a large and diverse corpus, our model learns patterns that transfer across series, forecasting zero-shot on data it has never seen, even in domains where data is scarce.
 Benchmark Results
 We evaluated Timestral on the three main public forecasting benchmarks: GIFT-Eval, TIME and fev-bench. Among pre-trained, zero-shot models, it ranks first across all five metrics. These results come from a single checkpoint, without ensembling.

 Family of models optimised for every specification
 Timestral has been optimised as a family of four models: 5M, 28M, 123M and 209M parameters. The larger models improve forecast performance, while the smaller ones are faster and cheaper. All four share the same architecture and training recipe. Every size sits on the Pareto front of accuracy versus model size: for each model size, no public model forecasts better.

 Score vs model size on GIFT-Eval, TIME and fev-bench (shown as 1 − skill score). Lower is better. Our 28M model beats Chronos-2, about four times larger, on GIFT-Eval and TIME. Our 209M model beats TimesFM-3 and Falcon-2.0 with fewer parameters. 
 Timestral does not need a GPU at inference. On a standard server CPU with 8 threads, forecasting one day ahead from three weeks of 15-minute history takes 10 ms with the 5M model and 140 ms with the 209M model. Smaller models trade some accuracy for speed: the 28M model is five times faster than the 209M model, and the 123M model comes within 0.2% of the 209M score at three quarters of its latency.
 An industrial example
 Consider an industrial plant with thousands of sensors across its equipment. Timestral can improve the forecasts on that data in several ways.

 Multivariate forecasting. A pump's vibration, temperature and pressure don't move independently. A rise in one often explains or causes a change in another. Timestral models related series jointly, so it can use those dependencies instead of forecasting each sensor in isolation.
 Probabilistic forecasting. A single predicted value may not show the full picture. Timestral predicts a full set of quantiles, so teams can see how wide the uncertainty is, set alert thresholds that reflect it, and plan maintenance around risk rather than a single number.
 Categorical covariates. Some covariates take values from a set of categories rather than continuous numbers, such as the day of the week, or a machine's state (running, idle, under maintenance). Encoding these as numbers would impose an order or scale they don't have. Timestral takes them as categorical inputs directly to improve forecasts.
 Known-future covariates. Some drivers of sensor behaviour are known in advance, such as production schedules, planned shutdowns, weather forecasts. Timestral can condition on them to improve forecast quality, so a scheduled load increase is expected rather than flagged as a surprise.
 From Model to System 
 Timestral is a numerical model that can run inside existing monitoring pipelines, or be paired with our language models in multi-modal agentic workflows.
 In the plant, that could look like this:
 Timestral running continuously on the plant's sensor streams, detecting anomalies as they occur.

 When it flags an anomaly on a pump, an agent embeds the signals and compares against embeddings of past sensor data to find similar historical failures.

 The agent then starts sub-agents to run a root cause analysis, drawing on context from that plant, such as maintenance records, shift logs and operator notes, equipment manuals, past work orders, and readings from related equipment.

 The agent drafts a suggested diagnosis based on the findings, with supporting evidence and possible next steps.

 The plant manager gets a diagnosis and a plan backed by the sensor data, rather than just an alert.
 Key technical contributions
 Several ideas have been combined to produce these results. Each will be described in detail in the technical report.
 Decoupled Horizon Forecasting. Causal decoders trained with contiguous patch masking, as in Toto 2.0 and TimesFM-3, mask out the values to be forecast, so they look like missing values and are also lost as context for later forecasts. Our approach, DHF, separates the two: the full history stays in the sequence, and learned forecast tokens read the history before them. Every observed value thus serves as both target and context, true gaps stay flagged as missing, and training horizon lengths and missing-data augmentation can be tuned independently of each other.

 Covariate-aware attention. Each input series is assigned a role: target variate, past-only covariate or known-future covariate. Known-future covariates are visible across the whole window while targets stay causal, and information flows only from covariates to targets. Timestral can therefore use a holiday calendar or a weather forecast without leaking a target's own future into its forecast.

 Synthetic-first data. The majority of the training data was synthetic. We first generated univariate processes with coherent temporal dynamics, including trends, seasonality and diverse noise patterns. We then used a multivariate synthesizer to construct multivariate series by introducing nonlinear dependencies between these processes.

 Two-stage training. Timestral is first pre-trained at scale on purely synthetic data with context size 8192, then post-trained on a mix of real and synthetic data with a 4x longer context. The objective is a pinball loss over 21 quantiles, a discrete approximation of CRPS.

 A model that can be adapted
 Public benchmarks measure general performance, but production data can be significantly different in behavior and structure. It may also shift over time as markets change regime, equipment degrades and demand patterns move. The lasting value lies in being able to adapt a model to in-domain data and keep retraining it as the distribution moves.
 For organisations that want to go further, Timestral is available through Mistral Forge , the same training pipeline we use for our language models. It supports:
 Zero-shot inference out of the box.

 Architectural extensions , such as domain-specific covariates.

 Fine-tuning on proprietary data , specialising to a domain while preserving general performance.

 Control over the training data , including adjusting the training mix, replaying pre-training data, and generating synthetic data samples to reflect the target domain. Full control over the data ensures that nothing we backtest was seen during pre-training.

 The full pipeline can be deployed on our clients’ hardware, including air-gapped environments.
```

```text
 Freedom to publish observations and assessments of a model or a process.
```

```text
 Agent sprawl: How to manage agent proliferation in the enterprise

 Blog Written By
 Kasim Patel
 Senior Solutions Architect

 Tags
 Enterprise AI 

 Share

 AI isn’t a shortcut. 
It’s how business gets ahead.
 Contact sales 
 The growth of enterprise AI agent platforms has made it much easier for employees to build and deploy agents to support their own work.

 But as agent creation becomes more decentralized, enterprises face a new management problem: how to keep track of what agents have been built across the organization. Without that visibility, teams can struggle to find and reuse existing agents, while access to enterprise data and systems can become harder to govern. When this proliferation of agents becomes too difficult to manage, it becomes agent sprawl.

 In this article, we’ll explain why proliferation isn’t inherently bad, explore how enterprises tend to manage agent sprawl, and consider an alternative approach that allows variant agents to compete.
 Build reusable agents and automations and share them across the enterprise with North 2: our secure, agentic AI platform that runs where your data lives.
 Explore North 2 

 Why agent proliferation isn’t necessarily a bad thing
 The same tools that create the potential for agent sprawl also make experimentation much easier. Employees no longer need to rely exclusively on a central AI or engineering team every time they identify a task that could benefit from an agent. Instead, they can build and test agents themselves, tailored to the specifics of the work they’re trying to augment.

 This kind of decentralized experimentation is valuable. First, those closest to a workflow are often best placed to determine how it could be streamlined by an agent. Second, when useful agents can be shared and reused, a solution initially developed for one team can be adopted by other teams facing a similar problem. So at an organizational level, proliferation can be a sign that employees are actively testing new ideas and discovering useful applications for agents.

 This raises the question of whether having a growing number of agents always creates more overhead. After all, more agents don’t necessarily mean higher inference costs — an agent that isn’t being used doesn’t consume tokens simply because it exists. Instead, the management burden appears when the process for managing agents fails to keep pace with their growing numbers. That’s when agent proliferation is better described as agent sprawl.
 Proliferation can be a sign that employees are actively testing new ideas and discovering useful applications for agents.

 How enterprises currently manage agent sprawl
 Enterprises today typically manage growing agent estates with one of the following approaches:

 Centralized delivery : A central AI or engineering team builds and governs agents for the rest of the organization. This can offer tighter control, but can limit the pace of innovation.
 Federated delivery : Business units or individual teams own agent development and operation, while central functions provide shared infrastructure, standards, and governance patterns .
 Hybrid delivery : Central and business teams share responsibility for building and operating agents under common standards and governance patterns.

 Across these operating models, enterprises are increasingly using agent registries to maintain a shared view of their agent estates. A registry helps an organization keep track of agent ownership, usage, and access permissions, while helping employees discover agents that already exist. This setup reinforces a common preference for avoiding duplication. Teams should default to reusing existing solutions before building something new.

 Of course, there are good reasons to limit unnecessary duplication. It’s an obvious way to reduce sprawl: employees have fewer overlapping options to sift through, while the enterprise has fewer agents to monitor and govern.

 But treating duplication as something to avoid in every case can also suppress innovation. If the mere existence of a workable agent means no alternatives should be built, organizations forfeit the opportunity to discover solutions that are cheaper, more reliable, or better suited to the task.
 Treating duplication as something to avoid in every case can suppress innovation.

 An alternative approach: Allow agent variants to compete
 How can enterprises make room for useful duplication without letting it develop into agent sprawl?

 One way is to treat duplication as provisional rather than permanent. If a team has a credible reason to believe it can improve on an “incumbent” agent, it should be permitted to build a “challenger” variant. However, the continued use of the challenger should depend on whether it demonstrates a meaningful advantage over the incumbent.

 This competitive model requires a time-bounded, evidence-based comparison between the incumbent and challenger. Specific metrics will depend on the use case, but could include measures such as reliability, token use, and latency, as well as task performance.

 Once enough evidence has been collected to make a meaningful comparison, the organization can decide whether the challenger should replace the incumbent or be retired. If the challenger proves better suited to a part of the incumbent’s workload, both agents might remain as distinct alternatives.

 For example, consider a bank’s commercial lending division, where a central team has built a finance agent that drafts credit memos for relationship managers. A lending team that handles routine annual reviews believes it can do better, so it builds a challenger designed for the same range of tasks using a smaller, cheaper model and an additional step that cross-checks financial figures against supporting documents.

 For 30 days, both agents draft memos for a representative set of cases, from routine annual reviews to more complex financing cases. The bank compares them on four measures: how many figures trace correctly to their source documents, how heavily credit officers edit each draft, token cost per memo, and time to first draft.

 If the challenger delivers comparable quality across the different types of work at a substantially lower cost, it replaces the incumbent. If it falls short without offering any meaningful advantage, it’s retired. And if it wins on routine annual reviews but struggles with complex new financings, both agents stay — each assigned to the work it handles best.

 It’s therefore necessary to tolerate some duplication for this approach to work, but only insofar as that duplication creates useful competition. Once testing reveals that one competing agent offers no advantage over the other, there’s no reason for both to remain.
 Final thoughts
 Avoiding agent sprawl does not require eliminating duplication altogether.

 Some duplication — or variation — is necessary if enterprises want to compare competing approaches.

 The key is to pair variation with selection pressure. By making agent creation easy but persistence conditional, enterprises can preserve the benefits of continuous experimentation without sliding into sprawl.
```

```text
 AI ROI: How enterprises can measure the return on AI investments

 Blog Written By
 Ariana Milligan
 Product Marketing Manager

 Tags
 Enterprise AI 

 Share

 AI isn’t a shortcut. 
It’s how business gets ahead.
 Contact sales 
 Enterprises investing in AI need to know whether the expected business value justifies the cost, and whether that value is actually being realized once AI is deployed.

 But measuring enterprise AI ROI presents some distinct challenges. AI costs can vary with how systems are designed, deployed, and used, while operational improvements in speed and productivity don’t always translate cleanly into financial value.

 In this post, we’ll unpack what makes AI ROI difficult to calculate, and explain how enterprises can account for those difficulties when forecasting and measuring returns.
 What is AI ROI?
 AI ROI is the financial return generated by an AI investment relative to the total cost of deploying and operating it. That return can be realized through cost savings, additional profit from sales, or both.

 ROI can be calculated as: ROI = (financial benefit - total cost) ÷ total cost x 100 

 Importantly, the operational improvements brought about by AI don’t necessarily translate directly into financial returns. Faster task completion, greater output, or higher-quality work may well produce financial value, but a positive ROI ultimately depends on whether that value exceeds the cost of achieving it with AI.
 What makes AI ROI difficult for enterprises to forecast and measure?
 The key challenge in calculating the ROI of AI is establishing the costs and returns that belong in the calculation.

 AI costs accumulate across the technical infrastructure and operational resources required to deploy and run it. At the same time, returns from AI can be hard to isolate since the technology is typically embedded in wider business processes.

 Here are some of the distinctive characteristics of AI investment that can make its ROI especially difficult to calculate.
 AI unit economics can shift with workload and scale
 In generative and agentic AI applications, the cost of completing a task can vary with the work involved. All else being equal, tasks that use longer context, require more reasoning, or involve more model and tool calls cost more to execute. Agentic systems can add further variability by executing similar tasks with different numbers of steps, retries, or tool calls.

 Scaling AI use changes the economics in other ways. While higher usage generally increases total variable costs, it can improve the utilization of existing capacity before more capacity needs to be provisioned.

 Pilot-stage unit costs may also differ from those at production scale, since production use can expose the system to larger and more varied workloads.
 Model and deployment choices reshape the cost-performance tradeoff
 Models vary considerably in cost, speed, and performance. Higher-cost models can be better suited to more demanding tasks, while less expensive models are often sufficient for simpler workloads. One emerging approach is cost-aware model routing: AI applications draw on multiple models and direct each task to the lowest-cost model that meets its performance requirements.

 Deployment choices also change the cost structure of running AI. For enterprises with lower volume or less predictable demand, usage-based managed services can be economical because they pay only for what they use without committing to a fixed amount of capacity. By contrast, dedicated capacity — whether provider-hosted or self-managed — can offer better unit economics for high, sustained workloads. However, this approach can leave paid-for capacity underutilized if demand is low or uneven.

 For most enterprises, cost is only one consideration: latency, data residency, security requirements, and operational control can all determine which deployment options are viable.

 Further reading : The total cost of AI ownership 
 Meeting AI quality and reliability requirements can increase operating costs
 Inference costs don’t always capture the full cost of delivering outputs at the quality and reliability required for production use. Enterprises may need to monitor output consistency and system behavior over time, run automated validation checks, and route uncertain or high-risk cases for human review. These activities add compute, tooling, and labor costs.

 The amount of additional overhead depends on the use case. High-stakes or error-sensitive workflows may require more extensive evaluation and oversight. For agentic systems, evaluation may also need to cover the sequence of tool calls and actions taken during execution, not just final outputs.
 Task-level efficiency gains can overstate enterprise-level financial value
 AI can make an individual task more efficient without necessarily improving the economics of the wider process. If another step remains constrained, the efficiency gain may simply shift the bottleneck elsewhere rather than increase overall throughput or reduce end-to-end completion time.

 A practical approach to forecasting and measuring enterprise AI ROI
 Given the difficulty of establishing the costs and financial value of AI with confidence, the figures used in an ROI estimate need to be well grounded, and any assumptions used to derive them should be explicit and open to testing.

 The following considerations can help enterprises build and test more credible estimates.
 Translate AI-driven process improvements into financial value
 Enterprises can use a pre-AI baseline to measure how process outcomes change after AI is introduced. However, a simple before-and-after comparison may be misleading if other conditions change at the same time. For example, sales might rise after an AI tool is introduced simply because demand happened to increase at the same time. A/B tests, staggered rollouts, or comparisons between similar teams using and not using AI can help tease out how much of the change is due to AI rather than those other effects.

 Once an improvement can be attributed to AI, enterprises can quantify its financial value. This can be relatively straightforward when the financial effect of the improvement can be measured directly — like if AI increases conversion rates and the additional sales generate $200,000 in gross profit.

 Other improvements are harder to value because their financial effects are further downstream. For example, an AI-enabled manufacturing process might lower the defect rate, which in turn lowers rework, returns, or warranty costs. In cases like this, enterprises need to estimate the financial value of the AI-driven improvement from the resulting cost savings.
 Establish the full cost of delivering AI in production
 Model and inference costs are among the most visible costs of running AI, but they represent only part of the total cost. A credible ROI estimate also includes upfront implementation costs and ongoing technical and operational costs, such as infrastructure, integrations, monitoring, human oversight, and engineering support.

 Some of those costs are easy to miss because they sit inside existing technology or operating budgets rather than appearing as separate AI expenses. For example, if engineers spend part of their time maintaining AI-related integrations, or if AI workloads consume centrally funded infrastructure capacity, the ROI calculation should reflect the cost of the resources AI actually uses.
 Stress-test ROI at production scale and over an appropriate time horizon
 Enterprises can sharpen their ROI forecasts by testing them against several plausible production scenarios. For example, they can vary assumptions about expected usage volume, workload mix, production costs, and financial value to see which factors matter most and how far they can change before the business case breaks down. Once AI is in production, enterprises can use actual usage, cost, and financial data to update those forecasts.

 The forecast’s time horizon matters too. AI investments can incur significant upfront costs before their full benefits are realized, so a short forecast period can understate AI’s longer-term returns. But longer-range forecasts also become less reliable given the unpredictability of future changes to AI costs, capabilities, and business conditions. Enterprises can manage that tradeoff by modeling ROI over several future time horizons to see when the investment is expected to break even and how much of the projected return depends on longer-term assumptions.
 Final thoughts
 ROI analysis helps enterprises decide where to scale, redesign, or pull back AI use as model capabilities improve and costs change. As teams gain experience with AI, they may also develop entirely new AI-enabled products, services, or ways of working that weren’t part of the original business case. Enterprises can then assess the value created by these innovations relative to what the business would likely have achieved without them.
```
