```text
 Train Qwen3 on AWS Trainium with torchtitan

 Using torchtitan on AWS Trainium means using it the way you always have. TorchNeuron registers Trainium as a native PyTorch device, which lets torchtitan use it through standard PyTorch interfaces. You can use these configurations to pre-train from random initialization or fine-tune published weights. You can also customize the model implementation and kernels for your workload. In this post, you train Qwen3 three ways on a single trn2.48xlarge .

 The first method uses Transformers v5 as a modeling backend in torchtitan. It runs Hub models through AutoModelForCausalLM and reads and writes published safetensors directly. The second method switches to torchtitan’s native Qwen3 by changing config.model_spec . The third adds Neuron Kernel Interface (NKI) mixture-of-experts (MoE) kernels from the torchtitan-neuron recipes and then uses torchtitan’s override registry to attach your own kernel. All three configurations use the same torchrun launch pattern and config structure.

 Prerequisites

 To follow this walkthrough, use a single trn2.48xlarge with either the AWS Deep Learning AMI for Neuron or a Neuron PyTorch training container. Both environments provide the Neuron driver, runtime, and compiler required to train on Trainium.

 Each training configuration is a Python config function. The three examples start from a base config that you update for each step.

 Train with Hugging Face Transformers v5

 In the first configuration, Transformers v5 builds Qwen3 through AutoModelForCausalLM . The Hub model definition supplies the implementation used for the forward and backward passes. You select the model by setting its Hub ID in the config.

 Start with transformers_modeling_backend_full() . It leaves the fields that map to Hugging Face configuration keys unset, so AutoConfig.from_pretrained() loads the model architecture from the Hub.

 Create neuron_qwen3.py in the torchtitan-neuron repository root, where you run the training command. Add the imports, model artifact path, and base config:

 import os
from torchtitan.experiments.transformers_modeling_backend.config_registry import (
 transformers_modeling_backend_full,
)
from torchtitan.experiments.transformers_modeling_backend.configs import (
 TransformersBackendConfig,
)

ASSETS = os.path.abspath("./assets/hf/Qwen3-4B-Instruct-2507")

def v5_qwen3_4b() -> TransformersBackendConfig:
 config = transformers_modeling_backend_full()
 config.hf_model = "Qwen/Qwen3-4B-Instruct-2507"
 config.hf_assets_path = ASSETS
 config.dataloader.dataset = "c4_test"
 config.training.steps = 10
 config.training.local_batch_size = 1
 config.parallelism.data_parallel_shard_degree = -1
 return config 

 torchrun --nproc_per_node=64 --rdzv_backend c10d --rdzv_endpoint localhost:0 \
 --local-ranks-filter 0 --role rank --tee 3 \
 -m torchtitan.train --module neuron_qwen3 --config v5_qwen3_4b 

 This command launches 64 training processes, one for each logical NeuronCore. --module neuron_qwen3 imports the local config module. --config v5_qwen3_4b selects the configuration function. The data parallel setting shards the model across all 64 ranks.

 Load and save Hugging Face checkpoints

 To fine-tune from published weights, enable checkpoint loading and point initial_load_path to ASSETS . The state-dictionary adapter adjusts the leading model. prefix and handles tied embeddings. It saves the final checkpoint as Hugging Face safetensors.

 def v5_qwen3_4b_finetune() -> TransformersBackendConfig:
 config = v5_qwen3_4b()
 config.checkpoint.enable = True
 config.checkpoint.folder = "checkpoint_qwen3_4b_ft"
 config.checkpoint.initial_load_path = ASSETS # absolute path required
 config.checkpoint.initial_load_in_hf = True
 config.checkpoint.initial_load_model_only = True
 config.checkpoint.last_save_in_hf = True
 config.checkpoint.last_save_model_only = True
 return config 

 Use the first training-step loss as a quick check that torchtitan loaded the published weights. For Qwen/Qwen3-4B-Instruct-2507 , the verified run produced a step 1 loss of 6.54 from published weights and 12.43 from random initialization.

 After training, load the exported checkpoint with AutoModelForCausalLM and load_state_dict . A successful round trip reports no missing or unexpected keys other than lm_head.weight , which Qwen3-4B ties to the token embeddings. This confirms that the files remain a standard Hugging Face checkpoint.

 Train with torchtitan’s native models

 In the second configuration, torchtitan builds its native Qwen3Model . Add the native Qwen3 imports and config function to neuron_qwen3.py :

 This example starts from qwen3_32b() because the tested torchtitan build does not provide a generic qwen3_4b() config builder. The next line replaces the 32B model specification with the 4B specification. The remaining fields reproduce the tested run.

 from torchtitan.models.qwen3 import model_registry
from torchtitan.models.qwen3.config_registry import qwen3_32b
from torchtitan.trainer import Trainer

def native_qwen3_4b() -> Trainer.Config:
 config = qwen3_32b()
 config.model_spec = model_registry("4B", attn_backend="sdpa")
 config.hf_assets_path = ASSETS
 config.dataloader.dataset = "c4_test"
 config.training.steps = 10
 config.training.local_batch_size = 1
 config.training.global_batch_size = 64
 config.parallelism.data_parallel_shard_degree = -1
 return config 

 torchrun --nproc_per_node=64 --rdzv_backend c10d --rdzv_endpoint localhost:0 \
 --local-ranks-filter 0 --role rank --tee 3 \
 -m torchtitan.train --module neuron_qwen3 --config native_qwen3_4b 

 config.model_spec selects the model class and defines how torchtitan shards the model and maps its checkpoint keys. Here, model_registry("4B", attn_backend="sdpa") selects torchtitan’s native Qwen3 implementation with scaled dot product attention (SDPA).

 Add NKI kernels for mixture of experts

 In the third configuration, torchtitan runs mixture-of-experts layers with kernels written in NKI, the Neuron kernel language. Add the required imports and Qwen3 MoE config function to neuron_qwen3.py :

 from torchtitan.config import CompileConfig
from torchtitan_neuron.models.qwen3.config_registry import qwen3_nki_moe_config

def nki_qwen3_30b_a3b() -> Trainer.Config:
 config = qwen3_nki_moe_config(
 "30B-A3B",
 compile_config=CompileConfig(enable=False, backend="neuron"),
 n_layers=4,
 num_experts=64,
 top_k=4,
 )
 config.hf_assets_path = ASSETS
 return config 

 torchrun --nproc_per_node=64 --rdzv_backend c10d --rdzv_endpoint localhost:0 \
 --local-ranks-filter 0 --role rank --tee 3 \
 -m torchtitan.train --module neuron_qwen3 --config nki_qwen3_30b_a3b 

 This configuration uses data parallel sharding across 64 ranks with a tensor parallel degree of 1. It does not use expert parallelism. num_experts=64 sets the number of experts in the model, not the expert parallel degree.

 Setting CompileConfig(enable=False) runs this example in eager mode. TorchNeuron supports registered NKI operators in both eager execution and torch.compile .

 In the torchtitan build used for this walkthrough, qwen3_nki_moe_config() replaces the MoE block with the NKI grouped-experts implementation. It also selects SDPA and the gather-free rotary embedding. When you enable torch.compile , add "grad_clip" to CompileConfig.components to compile gradient-norm clipping.

 NKI kernels enter training as PyTorch operators. wrap_nki makes an NKI kernel callable from PyTorch, and nki_op registers the operator. register_autograd attaches its backward pass using routing metadata saved during the forward pass.

 The example reduces Qwen3-30B-A3B to 4 layers and 64 experts so it fits on one trn2.48xlarge . It routes each token to 4 experts with top_k=4 .
```

```text
**Ling3-Tiny-UBTree-B16** is a UBTree speculative-decoding draft model for
[inclusionAI/Ling-3.0-tiny](https://huggingface.co/inclusionAI/Ling-3.0-tiny). It combines a
five-layer DFlash backbone with a learned bigram selector to propose multiple
candidate continuations for target-model verification.

> **SGLang integration — stay tuned!** Our UBTree adaptation for Ling3 has not
> yet been released to the open-source SGLang community. Public installation
> instructions and serving recipes will be added here when it becomes available.

This checkpoint is used alongside the matching target model; it cannot serve
as a standalone text-generation model.

## How UBTree works

![UBTree architecture and tree-native training pipeline](assets/ubtree_pipeline.png)

*UBTree pipeline*

UBTree pairs a **unigram proposer** with a **bigram selector**:

1. A DFlash backbone proposes candidate tokens for future positions in parallel.
2. The selector scores transitions between adjacent candidates in parallel.
3. Tree construction retains promising branches within a verification budget.
4. The target verifies the tree and commits the accepted continuation.

The paper also introduces tree-native training with renormalized KL supervision
on high-temperature target traces, encouraging plausible alternative branches.
See the [paper](https://arxiv.org/abs/2609.39972) for the method and experiments.
```

```text
Artificial Intelligence 

 Securing Quick access from corporate networks with AWS PrivateLink

 When enterprise data sits behind a corporate firewall or in a private on-premises data center, there’s no direct network path from AWS, even though the AI agents and dashboards in Amazon Quick can query virtually any data source. Administrators must make sure their sensitive enterprise data isn’t exposed to the public internet while being accessible for AI-driven insights and actions.

 For many enterprises, routing traffic over the public internet introduces unacceptable risk. Regulatory frameworks such as HIPAA, FedRAMP, and PCI-DSS often mandate that sensitive data remain within controlled network boundaries. Even where compliance isn’t the primary driver, exposing internal data paths increases the attack surface, complicates audit trails and introduces variable latency that can degrade the user experience.

 This walkthrough shows you how to connect on-premises data sources to Amazon Quick privately, without traffic traversing the public internet. It assumes you already have AWS Direct Connect or an AWS Site-to-Site VPN linking your on-premises environment to your virtual private cloud (VPC). From that foundation, we configure VPC endpoints powered by AWS PrivateLink so that Quick can reach your private resources over the AWS backbone, then layer security groups and VPC endpoint policies for defense in depth.

 By the end, you will have a network architecture that keeps traffic between Quick and your on-premises data sources off the public internet, reducing the attack surface, providing consistent low-latency connectivity, and giving you a clear audit trail for compliance.

 Amazon Quick and establishing private network connectivity

 Amazon Quick is an AI-powered workspace that brings search, analytics, research, and automation into a single conversational experience. Understanding which components reach your private network, and how, determines the architecture in the sections that follow.

 Data access in Amazon Quick falls into two paths. User-facing traffic covers anyone opening the Quick console, interacting with a dashboard, making an API call, or using Quick Desktop. All this routes through VPC endpoints (see VPC endpoints for user and API access), keeping user sessions off the public internet.

 Data-fetching traffic is when Quick itself reaches into your network to pull data. This is handled by VPC connections (see VPC connections for data source access), and it’s where most of the architectural decisions lie. The features and integrations that initiate data-fetching connections are:

 Amazon Quick Sight queries on-premises databases (PostgreSQL, MySQL, SQL Server, Oracle, and others) directly through ENIs placed in your VPC. This is the heaviest consumer of VPC connections.

 Amazon Quick Flows and Amazon Quick Automate are separate automation features. Flows handle repeatable tasks. Automate handles complex, multi-system orchestration with human-in-the-loop. Both invoke action connectors, including MCP servers hosted privately in your VPC. Any workflow that calls an internal API routes through this path.

 Quick Agents underpin all conversational interactions and can invoke action connectors directly. When a custom agent calls a privately hosted MCP server or internal API, traffic flows through the VPC connection.

 Amazon Quick Index builds a unified search layer across connected sources such as Confluence, SharePoint, and Amazon Simple Storage Service (Amazon S3). For data inside your VPC or on premises, knowledge base VPC connections are currently supported only for Amazon Redshift. Sources such as Confluence, SharePoint, Box, Google Drive, OneDrive, and Amazon S3 can’t use a Quick VPC connection today (see Supported VPC data sources ). You can still restrict Amazon S3 bucket access to a VPC endpoint through a bucket policy, which is a separate mechanism.

 Amazon Quick Research accesses enterprise sources behind the firewall alongside public internet data for its citation-backed reports, using the VPC connection when reaching private sources.

 Apps in Quick build interactive web applications on top of structured data and action connectors, inheriting the same VPC connectivity as Quick Sight and Flows.

 Quick Spaces organize content from the preceding features but don’t initiate their own data connections.

 These two traffic paths require two distinct private connectivity mechanisms that work together:

 VPC endpoints (AWS PrivateLink): Handle user-facing traffic such as accessing the Quick website, making API calls, and administrative access. These keep user traffic off the public internet.

 VPC connections: Handle data source traffic. Amazon Quick reaches into your VPC (and by extension, your on-premises network) to fetch data from databases, Amazon Redshift knowledge base sources, and internal APIs. These are configured within the Quick console.

 Configuring private connectivity

 This section walks through the four building blocks in order: VPC endpoints for user and API access, VPC connections for data source access, VPC endpoints for AWS data services, and outbound access to required external domains.

 Prerequisites

 Before configuring private connectivity for Quick, make sure the following are in place:

 An active AWS account with an Amazon Quick Enterprise subscription (VPC connections require Enterprise edition).

 An existing VPC in the AWS Region where Quick is deployed.

 A supported AWS Region. Quick website VPC endpoints are not available in the AWS China Regions or the AWS GovCloud (US) Regions.

 An AWS Direct Connect connection or Site-to-Site VPN established between your on-premises network and your VPC. This is the private path that carries traffic from your data center into AWS.

 AWS Identity and Access Management (IAM) permissions to create and manage VPC endpoints, security groups, and Quick administration. To create VPC connections, the administrator’s IAM identity also needs quicksight:CreateVPCConnection , quicksight:DescribeVPCConnection , quicksight:ListVPCConnections , quicksight:UpdateVPCConnection , quicksight:DeleteVPCConnection , ec2:DescribeSubnets , ec2:DescribeVpcs , ec2:DescribeSecurityGroups , iam:ListRoles , and iam:PassRole scoped to the VPC connection execution role.

 Access to your organization’s DNS management (Route 53 private hosted zones or on-premises DNS forwarders), as private DNS resolution routes traffic through VPC endpoints rather than public addresses.

 VPC endpoints for user and API access (AWS PrivateLink)

 VPC endpoints powered by PrivateLink handle all user-facing traffic to Amazon Quick, including the website, API calls, and embedded content. They prevent users from needing to traverse the public internet to access the Amazon Quick console.

 Figure 1: Private access to Amazon Quick from a corporate data center through a VPC endpoint

 As shown in Figure 1: (1) a client on the corporate network sends a request to Quick; (2) the request travels over AWS Direct Connect, through the Direct Connect gateway, into your VPC; (3) the Quick VPC endpoint evaluates the endpoint policy and allows or denies the request; (4) allowed requests reach Amazon Quick over the AWS network.

 Planning your VPC endpoint architecture

 When planning your endpoint architecture, begin by identifying the AWS Region where your Quick account is deployed, as VPC endpoints must be in the same Region. Choose subnets across multiple Availability Zones for endpoint ENI placement, and make sure those subnets have routes to your on-premises network through Direct Connect or VPN.

 Design security groups that restrict traffic on the endpoint ENIs to only required ports and source ranges. If you want all traffic routed privately (including the calls Amazon Quick makes to Amazon S3, Amazon Redshift, and Amazon Athena), plan VPC endpoints for those services as well (see Configuring data source VPC endpoints).

 Creating VPC endpoints for Quick

 Quick requires two interface VPC endpoints for full private access:

 Website access endpoint – Service name com.amazonaws.<region>.quicksight-website . This handles the bulk of user traffic to the Quick console. Private DNS names for the Quick website differ from the public URL, so you must create an A record for <region>.quicksight.aws.amazon.com pointing to the VPC endpoint.

 API access endpoint – Service name com.amazonaws.<region>.quicksight . This handles programmatic API calls. When private DNS is enabled, existing API calls to quicksight.<region>.amazonaws.com automatically route through the VPC endpoint with no additional DNS configuration. For FIPS compliance, use com.amazonaws.<region>.quicksight-fips .

 Note: Not every Quick API is available through the API VPC endpoint. The following 13 APIs are not supported: the action connector APIs (CreateActionConnector, DeleteActionConnector, DescribeActionConnector, DescribeActionConnectorPermissions, ListActionConnectors, SearchActionConnectors, UpdateActionConnector, UpdateActionConnectorPermissions) and the flow APIs (GetFlowMetadata, GetFlowPermissions, ListFlows, SearchFlows, UpdateFlowPermissions). Automation that manages action connectors or flows programmatically needs a path to the public API endpoint. See Quick and interface VPC endpoints .

 If administrators sign in to Amazon Quick as IAM users through the VPC, also create the AWS Management Console endpoints:

 com.amazonaws.<region>.console .

 com.amazonaws.<region>.signin .

 To create the website endpoint in the Amazon Virtual Private Cloud (Amazon VPC) console:
```

```text
 Adaptive agentic intelligence framework using Strands Agents

 Organizations building AI agents face a common challenge: Every request, whether a routine status check or complex analysis, typically gets routed to a single large, expensive model. This one-size-fits-all approach can drive up API costs, introduce unpredictable latency, and remove the possibility of offline operation. Even routine queries that could resolve locally end up requiring a full network round-trip to a cloud-hosted large language model (LLM).

 The Adaptive Agentic Intelligence Framework (AAIF), built with Strands Agents, takes a different approach. Instead of routing all requests to a single large model, AAIF uses small language models (SLMs) to handle routine tasks locally. More complex requests are routed to cloud-hosted models through Amazon Bedrock . This approach builds on the research position from Belcak et al. at NVIDIA . They argue that small language models are “sufficiently powerful, inherently more suitable, and necessarily more economical for many invocations in agentic systems.” Built on Strands Agents, the framework demonstrates how intelligent model orchestration can help reduce costs while maintaining low latency for local operations.

 Solution overview

 AAIF organizes AI processing into three layers, each optimized for different task types, as Figure 1 shows:

 Smart orchestration uses a lightweight SLM (llama3.2:1b) as the decision-making layer. This orchestrator classifies incoming requests and routes them to the appropriate processing layer without hardcoded rules.

 Local processing handles routine tasks like device telemetry retrieval and image analysis using SLMs running on local hardware through Ollama . These tasks complete with low latency and no cloud dependency.

 Cloud processing handles complex pattern analysis and strategic recommendations through frontier models in Amazon Bedrock. These requests need broader context and multi-step reasoning that SLMs cannot reliably provide.
```

```text
 Introduction 
 When we launched Agents CLI at Google Cloud Next '26, we built it around one strong opinion: going from an idea to a production agent on Google Cloud should take a single unified command surface. For teams building with Agent Development Kit (ADK), that opinionated path has worked. You run agents-cli create , write the agent logic, and ship to Cloud Run with observability and evals wired up, in about thirty minutes.
 The agent framework landscape has grown more diverse in the months since. In addition to ADK, developers today pick between LangChain and LangGraph , specialized newcomers like Deep Agents , or in-house frameworks tailored to a specific business domain. Different teams prefer different frameworks, and the right choice for a greenfield prototype is rarely the right choice for a production migration. Enterprise admins may also have governance policies they want to enforce across the ADLC for all of their development teams, such as: a compliance scan, an SSO gate, a Model Risk Management hop.
 Can a team benefit from the deployment, evaluation, and observability work in Agents CLI without being forced to adopt ADK, or without being forced to accept the default behavior of every command? Starting with version 1.5.0, the answer is yes. Agents CLI now ships with an Extension System that lets developers override or add commands without forking the tool. Version 1.8.0 ships the first-party LangChain extension, which replaces the framework-coupled commands with their LangChain equivalents and leaves the rest of the lifecycle untouched.
 We will walk through two journeys below. First, to show you the ADLC with LangChain agents, we'll show you how you can scaffold, run, deploy, and evaluate a LangChain agent through the Agents CLI lifecycle using the first-party extension. Then we build our own small extension that wraps the deploy command with a Software Bill of Materials (SBOM) scan, demonstrating the pattern enterprise platform teams can use to enforce their own policies across every project. Both journeys use the same mechanism.
 The Framework Lock-in Problem
 Most agent development toolchains available today share a limitation: they are opinionated about one specific framework, and the surrounding capabilities (deployment targets, CI/CD pipelines, evaluation harnesses, observability wiring) assume the developer has adopted that framework. When your framework matches the tool's assumption, the opinionated path works. When it does not, you're left with three bad options.
 The first is to fork the CLI, maintaining a divergent copy and re-syncing it on every upstream release. You pay a permanent maintenance tax, and every upstream improvement has to be hand-merged into the fork. The second is to wrap the CLI behind custom scripts, building a parallel command surface that invokes the underlying tool. The problem is that developers (and their coding assistants) forget about the wrapper and call the underlying tool directly, bypassing the intended abstraction. The third is to walk away and build everything from scratch, which can consume several engineer-months of work that the team had not planned for, and which rarely produces tooling as polished as the upstream project.
 The problem shows up in two scenarios. One is enterprise customers adopting Agents CLI: in regulated industries, a central platform team often requires that every deploy invocation be wrapped with a compliance check, that login route through corporate single sign-on, or that evaluations flow through a Model Risk Management pipeline. Each of these requirements, implemented today, means either forking the CLI or building a wrapper layer. The other is teams that use ADK most of the time but need to run a non-ADK framework on a specific project. Within the Agents CLI command surface, six commands assume the ADK runtime: playground , run , and four eval subcommands. The other eighteen or so ( scaffold , infra , deploy , publish , login , and friends) are framework-agnostic. Without extensions, choosing a non-ADK framework for a single project meant losing access to all twenty-four.
 The Extension System handles both with one mechanism.
 What are Agents CLI Extensions? 
 An Agents CLI extension is a directory in a Git repository that contains a single file called agents-cli-extension.yaml . The file declares which built-in commands the extension overrides and which new commands it adds. From the official documentation :
 Extensions are how you adapt agents-cli to a workflow it doesn't ship with — a different agent framework, an org's deploy policy, or a command of your own — without forking the tool. Extensions take two shapes, described in the Using Extensions page. A command override replaces the behavior of a built-in like playground , deploy , or eval generate . The overridden command receives the user's arguments verbatim, so the user experience stays consistent with the native command. A new command exposes a workflow the CLI does not currently provide as agents-cli <your-command> . Both shapes can coexist in the same extension, and most non-trivial extensions use a combination of the two.
 Extensions are distributed through Git repositories rather than through a dedicated package registry. The design draws from the extension model used by the gemini-cli project. There is no central index to publish to, no package format to maintain, and no ownership roster to apply for. Any directory inside any Git repository can serve as an extension, and Git handles the versioning, pinning, and distribution. For enterprise platform teams, this means creating an internal platform-extensions repository and pointing their developers at it, with no external registry to coordinate with.

 An extension can be referenced in several ways, depending on where it lives and how the developer wants to use it:

 Scopes
 Extensions install at two scopes. The default is the project scope, where the extension and its lockfile entry are committed to the project's own repository. Teammates and CI pipelines pick it up on checkout. The alternative is the user scope, enabled via the --global flag , where the extension is stored in the user's home configuration directory and applies to every project on the machine. The user scope is the one you reach for when an extension needs to be available before any project exists, such as a framework bootstrap extension that configures agents-cli create itself.
 When both scopes define the same command, the project scope wins, and agents-cli info surfaces the source of each active command. Scoping is deliberately explicit: the Extension System will not silently merge or override extensions, and any conflict surfaces to the developer at install time or in the extension list output.
 Lockfile and Lifecycle
 The Extension System follows the discipline of package managers like uv or npm : it resolves a Git reference to an exact commit SHA at install time, records the resolved SHA in a lockfile, and uses the lockfile to re-materialize the exact reviewed code on every fresh checkout. The agents-cli install command restores the vendored working copy from the pinned SHA without advancing the pin, which guarantees that CI and local development run bit-for-bit identical code. To advance a pin to the latest commit on the tracked reference, the developer runs agents-cli extension update , which re-resolves the reference and re-prompts for third-party trust.  A prospective multi-center study demonstrates how AI-based blind sweep ultrasound assessment can enable non-sonographer operators with low-cost probes to deliver expert-level gestational age assessments, marking a significant step toward expanding life-saving maternal care globally.
```

```text
 The World Health Organization (WHO) estimates that more than 250,000 preventable deaths occur worldwide each year due to pregnancy-related complications. While prenatal ultrasound can improve outcomes and reduce fetal and maternal mortality, two-thirds of people globally lack access to diagnostic medical imaging like ultrasound. Current methods that support maternal health rely heavily on specialized clinical training, leaving millions in low-resource settings without access to a single ultrasound during their entire pregnancy.
 We saw an opportunity to conduct research towards addressing this real-world need, by developing machine learning systems that interpret " blind sweep " ultrasounds. This way of scanning allows frontline healthcare workers without specialized sonography training to perform scans by simply gliding low-cost, portable ultrasound probes across the abdomen in a standardized pattern.

 Because many regions face critical shortages of experts, and traditional sonographer training is both expensive and requires a multi-year commitment, enabling these health workers to perform assessments with minimal training has the potential to significantly expand prenatal screening coverage.
 Combining the minimal training requirement with AI interpretations could ultimately mean a successfully developed tool that has the potential to increase availability of ultrasound-based pregnancy assessment, and thereby improve access to higher quality maternal health.
 In “ Generalization of AI-Based Gestational Age Assessment Using Blind Sweep Ultrasonography ”, published in JAMA Network Open , we evaluated how effectively an AI model for gestational age assessment (how far along the pregnancy is) generalizes across diverse clinical settings and hardware. While our previous research validated the model's performance on unseen patients from the same retrospective cohort it learned from, this new prospective study shows how the AI system performs reliably running live on mobile devices in real clinics, with only novice operators and unfamiliar ultrasound equipment, and minimal fine-tuning.

 “ The gestational age is basically how far along a woman is in pregnancy. All of our screening, a lot of our treatments, a lot of our indications for delivery are all based on this master timeline that you get from the gestational age .”

 Evaluating performance across diverse clinical settings

 For a medical AI system to safely scale globally, it must demonstrate generalizability — maintaining accurate diagnostic performance when introduced to new clinical settings with different patient populations, clinical workflows, and ultrasound hardware variations than those on which the model was trained.
 In this study, our original AI model was minimally tuned on only one of our target populations, and then prospectively tested across both target environments:
 Northwestern Medicine : An urban, high-resource academic medical center in Chicago, IL, United States.
 Jacaranda Health: An urban community clinic network in Nairobi, Kenya.
 Originally trained on ultrasound data collected in North Carolina and Zambia using a set of Sonosite, GE, and Butterfly Networks commercial ultrasound probes, the research AI system was paired with Clarius C3, a commercial handheld transabdominal probe. All of these sites differed in various care dimensions, including when women first come in for prenatal care, how many routine ultrasounds they receive, and how gestational age is usually dated.
 To evaluate efficient system tuning, the study leveraged a small pilot dataset of 120 participants from Chicago — approximately 6% of the original training set—to adapt the model to new probe hardware and extend the gestational age prediction range beyond 36 weeks. To understand generalizability, no data from the Nairobi site was used for fine-tuning, maintaining the Kenyan clinical validation as a strictly independent, external test. To evaluate comprehensive utility, the study also included multiple gestation pregnancies, which could present tracking and measurement challenges for both human operators and automated systems.

 Our blind sweep model, trained on 1,968 participants (North Carolina, US, and Zambia) was fine-tuned on scans from 120 participants from Chicago, Illinois. It was then tested prospectively in Chicago (n=192) and Nairobi (n=193), with no fine-tuning on Nairobi data. The model was non-inferior to expert sonographers at determining gestational age, in both settings, with a combined mean absolute error of 4.18 vs. 4.48 days. 

 Key findings: Matching the expert standard

 We compared the AI system’s ability to estimate fetal age from blind sweep ultrasounds to formula-based estimation from the clinically standard expert approach. This expert approach relies on an expert sonographer locating multiple specific cross-sections of the fetus(es) to take precise biometry measurements, a difficult-to-scale task that requires years of training and is highly operator-dependent.
 Evaluating a primary cohort of 385 participants between 16 and 36 weeks of pregnancy, the diagnostic study demonstrated strong AI system results:
 Clinically non-inferior accuracy : Across both cohorts, the AI model achieved a mean absolute error (MAE) of 4.18 days in estimating gestational age, successfully demonstrating non-inferiority to the standard clinical procedure performed by expert sonographers, which had an MAE of 4.48 days.
 Cross-setting generalization : In Chicago, the adapted model achieved an MAE of 4.10 days. In Nairobi, with zero local optimization, the model achieved a comparable MAE of 4.27 days.

 The AI system's gestational age error (MAE 4.18 days) was non-inferior to expert sonographer biometry (4.48 days), and stayed consistent from Chicago (4.10 days) to Nairobi (4.27 days), where the model had no local fine-tuning. 

 Beyond accuracy, exploratory metrics showed that the research AI system was resilient in complex scenarios. For instance, in cases of fetal weight extremes (above the 90th percentile), the model outperformed traditional biometry formulas, demonstrating robustness against variations in fetal size.

 Lessons learned during prospective deployment

 In addition to highlighting an immense opportunity to expand ultrasound access through AI, the prospective multi-center study allowed us to actively observe and optimize how AI behaves in live clinical environments. By deploying our system directly into everyday clinical workflows, we gained practical insights that help us design for real world use. For example, we observed the importance of swappable batteries over plug-in docking stations for keeping devices charged between consecutive patients.
 These studies also demonstrated how deploying AI systems like this will also require building deep trust with both clinicians and patients. One important way to ultimately achieve this would be by building clear safeguards into the app, like model confidence estimates produced by our model to reject poor-quality sweeps and convey model uncertainty to the clinician user.

 Looking ahead: Expanding access to care with AI

 These study findings indicate that AI-based systems can analyze standardized “blind sweeps” images acquired by operators without specialized sonography training. The AI estimate of fetal age had accuracy comparable to the current standard of care from expert operators and more expensive traditional, cart-based ultrasound machines. Demonstrating technical generalizability across diverse clinical settings, hardware, and changing populations, marks a key step in highlighting their potential to expand access to this critical capability for maternal health.
 By empowering minimally trained community health workers to perform reliable ultrasonography assessments, this research demonstrates the potential to expand prenatal coverage for millions in under-resourced areas. ### [Microsoft Research] Solving a 31-year-old grand challenge in mathematics – the KLS conjecture
```
- url: https://www.microsoft.com/en-us/research/blog/solving-a-31-year-old-grand-challenge-in-mathematics-the-kls-conjecture/
- published: 2026-10-21T16:00:00+00:00
- via: feed

```text
Microsoft researcher and collaborator combine new mathematical ideas with human-directed AI to resolve a central problem in high-dimensional geometry and probability

 At a glance

 Fundamental scientific breakthrough: Researchers resolved the Kannan-Lovász-Simonovits (KLS) conjecture, a 31-year-old problem widely regarded as one of the central open questions in high-dimensional geometry, with implications for statistics, optimization, algorithms, and computer science.

 A universal geometric principle: The result establishes a universal geometric principle for log-concave distributions, showing that simple flat cuts can capture their narrowest bottlenecks within a fixed factor, regardless of dimension. 

 Human-AI collaboration: The breakthrough emerged from a human-directed agentic research process in which AI systems explored mathematical possibilities while researchers evaluated, pruned, and redirected the search.

 Independent confirmation: Multiple independent researchers have validated this research, identifying its central criterion as the key breakthrough, followed by a machine-checked formal verification. 

 For decades, a fundamental question about the difficulty of computing in high-dimensional spaces has resisted proof. New research resolves this question, removing a major theoretical obstacle to understanding the efficiency of randomized algorithms used across science and computing.

 The Kannan–Lovász–Simonovits (KLS) conjecture was proposed in 1995. It asks whether, for a broad class of high-dimensional probability distributions, the best flat or hyperplane cut is always nearly as effective as the best cut of any shape. More precisely, KLS predicts that the two differ by no more than a universal constant, regardless of the number of dimensions. This would establish a dimension-free geometric principle with important consequences for high-dimensional geometry, probability, and theoretical computer science. Because the geometry of these cuts governs how quickly random walks can explore a distribution, KLS also plays a central role in the theory of high-dimensional sampling.

 Figure 1: An illustration of the KLS Conjecture (simplified) on regular tetrahedron. 

 Since 1995, mathematicians have accumulated evidence that the conjecture was true, but a complete proof remained elusive. Now, two researchers, including Xinzhi Zhang from the Machine Learning and Optimization group at Microsoft Research, have proved the KLS conjecture (opens in new tab) . They have shown that the relationship holds with a fixed bound, regardless of how many dimensions a shape has. Before this work, the best known result (opens in new tab) , established in July 2026, allowed that bound to grow slowly as the number of dimensions increased. This work establishes a fundamental geometric principle: high-dimensional spaces are better behaved than previously known, and the obstacles to navigating them do not grow without bound as dimensions increase.

 The importance of the KLS conjecture was recognized across the field long before it was resolved. In its 2017-18 Annual Report, the Mathematical Sciences Research Institute (MSRI) (opens in new tab) called it “a central open problem in high-dimensional convex geometry.” The Simons Institute (opens in new tab) described it as “one of the most important open problems in convex geometry.” In the proceedings of the 2022 International Congress of Mathematicians (ICM) (opens in new tab) , Ronen Eldan noted its broad implications for high-dimensional convex and computational geometry. Quanta Magazine (opens in new tab) wrote that KLS “lies at the heart of many questions in statistics and computer science.”

 Technical details

 The authors began by improving the July 2026 result in order to make the mathematical bound more precise. Working with AI agents in a structured, human-directed process, they explored more than 100 candidate approaches, many involving lengthy calculations with higher-order tensors. This produced a new mathematical criterion that became the foundation of the final proof.

 The authors then discovered that the new criterion could be applied recursively. Each improved bound could be fed back into the same argument to produce a still tighter one. In the October 1, 2026 version of the paper, this reduced the dependence on dimension to the iterated logarithm. This function grows extraordinarily slowly, but it still grows with the dimension and therefore did not yet fully resolve the conjecture.

 The final step was to repeat the entire recursive refinement, rather than applying it only once. This idea was inspired by the authors’ earlier work on fast algorithms for linear programming. The authors proved that the small errors introduced at each stage shrink fast enough that their total remains bounded by a universal constant, independent of the dimension. This eliminated the dependence on the number of dimensions and completed the proof in the October 4, 2026 version of the paper.

 The recursive method, its repeated application, and the proof that the accumulated errors remain bounded are original contributions of the researchers. AI tools helped explore candidate approaches, carry out detailed derivations, prepare the manuscript, and perform internal proof checks. The researchers determined the mathematical direction, selected the promising ideas, assembled them into the final argument, and verified the proof.

 Independent confirmation

 On the same day that the authors posted their complete proof, a separate group of leading experts posted a full proof (opens in new tab) that they developed in parallel. Their work built upon the findings in the first version (opens in new tab) of the Microsoft paper, calling it “the crucial step in the proof.” A third proof (opens in new tab) which appeared separately on the same day relies on a closely related idea. In addition, a Lean 4 formalization (opens in new tab) was subsequently released, combining the key criterion from the first Microsoft paper with additional research. 

 Independent proofs are among mathematics’ strongest forms of validation because they demonstrate that a result does not rest on a single chain of reasoning. The subsequent appearance of alternative approaches and formal verification further strengthens confidence that the field has uncovered a genuine underlying principle rather than a fragile technical argument. The authors have also shortened their proof and verified the streamlined argument in Lean; they plan to release both after final review. Together, these developments provide complementary forms of confirmation.

 Human-AI guidance

 In the process of proving KLS, this research also demonstrates the power of having researchers direct AI rather than simply asking AI to solve a complex problem through a single end-to-end run of a frontier model or agent. The authors used an agentic search process with iterative, human-assisted “pruning”: As multiple agents explored variations of an idea in parallel, the researcher examined their intermediate result, eliminated unpromising directions, and passed the most promising result to the next round. Roughly one hundred research trajectories were explored before the key breakthrough emerged. 

 In a separate track of the project, the authors made repeated unguided attempts to solve the same problem with several leading AI models, using roughly the same total token budget as the main process. That effort fell short of the goal. The eventual success depended on both the capabilities of the AI systems and the mathematical judgment of the researchers. 

 Conclusion

 Taken together, resolving KLS settles a central problem in high-dimensional geometry. A wide range of results that previously relied on the conjecture as an assumption can now be stated unconditionally. The proof therefore provides a stronger foundation for research in convex geometry, probability, and theoretical computer science.

 The work also demonstrates how carefully guided human-AI collaboration can contribute to genuine scientific discovery while reinforcing, rather than replacing human insight. It highlights the continuing importance of scientific judgment in identifying promising directions, recognizing conceptual connections, and seeing when a partial insight points toward a deeper result. The authors are now simplifying the proof and extending its formal verification so that the mathematics and theoretical computer science communities can more easily examine the result and build on it.
```

```text
 An AI agent can complete its assignment and still cross a security boundary. Recent incidents show that agents can circumvent security controls while using tools, credentials, and services to pursue their assigned goals. Monitoring and enforcement need to operate outside the agent’s reach so that it can’t alter or disable them.

 NVIDIA Sentry is a security software framework that monitors AI agents and enforces policies governing their access to models, tools, and data. Part of the NVIDIA OpenShell reference architecture announced at GTC Berlin, it’s built on NVIDIA DOCA , runs on NVIDIA BlueField-4 DPUs , and provides host-isolated runtime protection for AI agents. NVIDIA Sentry validates that an agent operates according to its designed intent and within its defined operational boundaries.

 Trusted even when host resources can’t be trusted, it controls the agent’s only path to the model, providing tamper-evident traceability of agent activity while enforcing granular security controls on agent access in silicon. In addition to inspecting agent communications, NVIDIA Sentry uses out-of-band observability to establish real-time situational awareness, continuously evaluating agents’ runtime security and behavior to validate their security and integrity.

 This post explains how NVIDIA Sentry evaluates agent requests, detects threats, and enforces security policies independently of host software.

 An independent security layer for agent runtime protection 

 An earlier agentic AI security post described how NVIDIA BlueField runs security services in a hardware trust domain independent from the host.

 NVIDIA Sentry builds on that foundation to continuously monitor AI agent behavior and enforce access policies independently of host software, establishing a strict security boundary in a separate hardware trust domain outside the agent’s reach to keep agents operating within their designed intent.

 Software runtime boundaries remain essential. NVIDIA OpenShell is a secure runtime for autonomous agents that governs what an agent can do. OpenShell separates policy enforcement from the agent workload, so a compromised agent can’t change its own restrictions. NVIDIA Sentry adds an independent hardware safeguard out of band, running on BlueField-4, beyond the agent’s reach and knowledge.

 In the OpenShell reference architecture, agents execute on NVIDIA Vera CPUs , while BlueField-4 sits on the node’s only path to the model. NVIDIA Sentry inspects agent-to-model communications and enforces access policies without relying on the agent to report its own behavior. Memory introspection adds context about the agent’s execution environment, such as a container or microVM, to help detect external threats and agent misbehavior.

 Governing agent communications 

 DOCA Tower is NVIDIA Sentry’s AI security gateway. Built on Envoy , the open source edge and service proxy, it operates as a transparent proxy for agent traffic, placing a bidirectional inspection layer between an agent and the external environment.

 Agent network traffic reaches BlueField-4 through a direct network I/O path that bypasses host OS/hypervisor packet processing. All of the agent’s network communications are governed by NVIDIA Sentry as BlueField-4 sits on the only path to the model and to the outside world.

 An agent’s network access boundary is controlled using DOCA Flow and DOCA Tower, which work in concert to restrict agent access to approved resources. DOCA Flow is used to implement a layer-4 firewall for each agent, accelerated in silicon on BlueField-4. The firewall blocks connections to unauthorized destinations and forwards permitted traffic to DOCA Tower for layer-7 (application layer) inspection, authorization, and additional security checks.

 DOCA Tower acts as a transparent proxy, performing Transport Layer Security (TLS) termination using built-in, in-silicon TLS acceleration. For connections configured for inspection, it decrypts the agent traffic permitted by the layer-4 firewall to inspect and control agent communications.

 NVIDIA Sentry uses the Open Policy Agent (OPA), an open source policy engine, to evaluate access requests against defined policies. OPA uses Rego, a declarative domain-specific language designed to evaluate complex hierarchical data structures. OPA runs locally in memory and can evaluate requests in under a millisecond, depending on policy complexity and configuration.

 DOCA Tower is compatible with OpenShell policies, using OPA to extend network access policies and runtime controls into BlueField-4 and to the infrastructure.

 Figure 1. NVIDIA Sentry uses DOCA Tower to inspect access requests and a policy engine to evaluate authorization, with runtime context from DOCA Argus 

 Enforcing agent access policies with runtime context 

 An agent’s network communications provide only part of the information needed to assess its security and integrity. Visibility into the agent’s execution environment adds context for evaluating access requests that go beyond a traditional resource access policy.

 DOCA Argus provides real-time visibility into an agent’s execution environment and operational state, giving NVIDIA Sentry additional context about agent access requests.

 It uses live memory introspection to analyze selected regions of volatile host memory and obtain independent evidence of the system’s operational state.

 DOCA Argus runs independently of the host, analyzing host memory on BlueField-4 without host-resident agents. This agentless design provides independent runtime visibility while preserving host compute resources. By operating outside the host in its own isolated trust domain, DOCA Argus remains beyond the reach of host software even if the host is compromised.

 DOCA Argus maps the execution environment in real time—for example, containers to their respective pods and sandboxes to microVMs—and identifies the running processes and their properties within each environment. It also maps relationships between processes and threads, file access, network connections, loaded libraries, CPUs, GPUs, memory, and other system resources. DOCA Argus tracks containers, processes, and loaded libraries using their associated hashes.

 This runtime context enables NVIDIA Sentry to connect agent access requests to the processes and execution environments behind them, enforcing policies that consider both the requested action and the security and integrity of the agent making it.

 Using runtime context to evaluate agent access 

 NVIDIA Sentry correlates network connection information from DOCA Tower with runtime context from DOCA Argus to evaluate access requests.
```
