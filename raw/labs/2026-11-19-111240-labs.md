Artificial Intelligence 

 Introducing workload recovery and expanded infrastructure checks on Amazon SageMaker HyperPod

 Large training jobs can fail even when every node looks healthy. A GPU with a subtle fault can pass its stress tests and still return wrong values. When a job stalls on an NCCL timeout, it keeps its GPUs, and Slurm still shows it as running. If a device plugin crashes on one node, the job fails with an error that never mentions the plugin. Teams usually find these problems only after the loss diverges or the job fails, and by then the compute is spent. Each of these failures lowers goodput, the share of your cluster’s time that goes to useful training. Today, we’re introducing workload recovery and infrastructure checks on Amazon SageMaker HyperPod that catch these failures sooner and raise the goodput of your training workloads.

 SageMaker HyperPod already handles nodes that report hardware faults. The health monitoring agent (HMA) watches each node for GPU errors, deep health checks test nodes during provisioning, and automatic node recovery reboots or replaces faulty hardware. These features look at one node’s hardware at a time. They can’t tell whether the GPUs train correctly, whether a job is still making progress, or whether the Kubernetes components a job depends on are working.

 In this post, we walk through the three new capabilities that catch these failures. For each one, we show how to set it up and what it reports when it finds a problem:

 MultiNodeTrainingValidation is a new deep health check for HyperPod clusters orchestrated by Amazon Elastic Kubernetes Service (Amazon EKS). When HyperPod provisions an instance, or when you run the check on demand, it trains a small model on the instance and then across instances of the same type. The instance fails if the loss becomes NaN or infinite, or training doesn’t finish in time.

 The HyperPod Kubernetes Resource Monitoring Agent watches the Kubernetes layer of an EKS cluster for problems such as crash-looping device plugins, missing DaemonSets, and tainted nodes. When a job fails, it reports the pods and nodes involved as Kubernetes events and Amazon CloudWatch logs.

 Hung job detection finds Slurm jobs that have stopped making progress. An agent on each node watches the job’s output and GPU activity, or log patterns that you define. It writes an event to CloudWatch and can cancel the job so that Slurm requeues it.

 Why node health alone isn’t enough

 The existing HyperPod resiliency features check a single node at a time. The health monitoring agent (HMA) watches each node for GPU errors such as Xid and NVLink faults, Elastic Fabric Adapter (EFA) errors, and kernel errors. The InstanceStress deep health check runs DCGM level 4 diagnostics and tests each instance’s GPUs, GPU memory, NVLink, and EFA devices. The InstanceConnectivity check runs NCCL tests across GPU instances, or NCCOM tests on AWS Trainium. Together, these confirm that each node’s hardware works. They don’t show whether the GPUs compute correctly, whether a job is still making progress, or whether the cluster’s Kubernetes components are healthy. Three kinds of failure get past them:

 Numerical faults –  A GPU can pass every hardware test and still compute wrong results. The first sign is often NaN or infinite loss in a production run. Meta attributed 6 of the 419 unexpected interruptions in its 54-day Llama 3 405B pre-training run to silent data corruption ( The Llama 3 Herd of Models ).

 Hung jobs –  An NCCL timeout, a stalled data pipeline, or a deadlock can stop a job without ending it. The job keeps its GPUs and their memory, and Slurm reports it as running until someone checks the loss curve or the log.

 Cluster-level failures –  Some failures happen in Kubernetes, not in a node’s hardware. A device plugin crash-loops, a required DaemonSet never starts on a new node, or ranks on different nodes fall out of step in an NCCL collective. HMA checks each node on its own, so it doesn’t see these problems. When the job fails, the error often doesn’t say which pod or node caused it.

 Solution overview

 Each capability covers a different point in a training run. MultiNodeTrainingValidation runs when instances are provisioned, or on demand, and confirms that their GPUs train correctly. Hung job detection runs alongside each Slurm job and catches a job that has stopped making progress. The HyperPod Kubernetes Resource Monitoring Agent watches the cluster continuously and, when a job fails, reports the pods and nodes that were involved. The following table summarizes the three.

 Validate training correctness with the MultiNodeTrainingValidation deep health check

 The MultiNodeTrainingValidation deep health check trains a fixed, known-good workload, first on each instance and then across instances. It catches GPUs that pass InstanceStress and InstanceConnectivity but produce NaN or infinite loss once they train together. If an instance fails, HyperPod labels it as failed and, with automatic node recovery turned on, reboots or replaces it. When the check runs during provisioning, this happens before your jobs can use the instance.

 How it works

 MultiNodeTrainingValidation adds two tests to the deep health check run:

 Tiny Megatron test: A short Megatron-LM training run on all GPUs of each instance.

 Megatron test: The same workload across instances of the same type, communicating over EFA.

 Either test fails an instance if the training loss becomes NaN or infinite, or if training doesn’t finish within the time limit. The workload is fixed, so a failure points to the hardware rather than to a model or code change.

 Introducing the Amazon SageMaker JumpStart Model Leaderboard

 Amazon SageMaker JumpStart gives you hundreds of open-weight foundation models you can deploy quickly.  Today we are launching the Amazon SageMaker JumpStart Model Leaderboard , a new way to compare JumpStart models side by side on quality, speed, and cost, directly in Amazon SageMaker Studio.  What is the JumpStart Model Leaderboard?

 The leaderboard is a new view of the JumpStart base models page in SageMaker Studio, right next to the Categories and All models views. It uses the same search bar and filters you already know, and it opens on a leaderboard of large language models (LLMs). You see rankings immediately without answering setup questions first. For each model, it shows two kinds of information:

 Quality scores on three public benchmarks (BIG-Bench Hard, GPQA Diamond, and MMLU-Pro) that AWS runs itself, using the same evaluation setup for every model so the numbers are comparable.

 Performance and cost metrics that AWS measures by sending a standardized test workload to an endpoint using each JumpStart deployment configuration, so you see how fast a model responds and what it costs to run.

 Because both kinds of numbers come from the same place and the same method, you can make a like-for-like comparison instead of stitching together data from different websites. At launch, the leaderboard covers 70+ models from providers including Meta, Google, Qwen, IBM, and Arcee, with more added over time.

 How we benchmark

 Full Fine-Tuning (FFT) on SageMaker AI Serverless Model Customization

 Fine-tuning is the process of continuing to train a pretrained large language model (LLM) on a company’s own data so it adapts to a specific domain, task, or style rather than relying on general-purpose knowledge alone. For businesses, the value is twofold. A fine-tuned model delivers measurably better accuracy on domain-specific work while reducing costs: a smaller specialized model can match or exceed a frontier model on your task at a fraction of the per-token inference price. Those savings compound across millions of requests. Fine-tuning has therefore become an essential process for businesses looking to get more value from LLMs at lower costs.

 Parameter-efficient fine-tuning (PEFT) methods like Low-Rank Adaptation (LoRA) have emerged as a practical solution for fine-tuning LLMs to downstream tasks, reducing GPU capacity requirements by updating only a small subset of LLM parameters. LoRA aims to strike a balance between efficiency and expressiveness, however, the low-rank nature of the weight update inherently limits the representation power of LoRA fine-tuned models, potentially compromising performance on complex tasks. This trade-off hampers the ability of LoRA methods to capture complex patterns needed for diverse tasks. To address these challenges, Full Fine-Tuning (FFT) updates model parameters simultaneously, overcoming the low-rank limitations so LLMs can fully absorb complex domain-specific knowledge.

 Full Fine-Tuning: Why it matters

 Model customization types like LoRA reduce trainable parameters by freezing the pre-trained model’s weights and injecting small, separate pairs of replacement matrices (called low-rank matrices) into the model layers. This works well for simple adaptations, but the low-rank structure inherently limits the representation power of the fine-tuned model. As tasks grow more complex and datasets scale beyond tens of thousands of examples, LoRA hits an accuracy plateau where increasing rank (and thus trainable parameters) fails to bridge the accuracy gap with standard fine-tuning. This plateau reveals that the performance gap isn’t simply because of fewer parameters. It’s caused by rank deficiency itself. The low-rank update can’t capture the full complexity of the weight changes needed for deep task adaptation.

 However, for complex tasks and domains where large, good-quality datasets exist, full-rank fine-tuning excels by updating model parameters simultaneously. FFT modifies the model’s weight matrix uniformly, using the full representational capacity of the model’s weight matrices rather than restricting updates to a small subspace, and without introducing the abrupt, localized distortions characteristic of low-rank methods. The result is stronger model convergence, better activation alignment across model layers, and a model that faithfully captures both the target task distribution and the richness of its pre-trained knowledge. At the scale of tens or hundreds of billions of documents, finding the hardware that delivers the best performance per dollar isn’t a tuning detail. Any per-document cost improvement compounds into a significant number.

 This post details how we optimized our embedding infrastructure for cheaper, more flexible inference workloads on AWS Neuron hardware ( AWS Inferentia2 and AWS Trainium2 ), and how an agentic development workflow drove the optimization.

 Inference runs on an asynchronous pipeline, but it must be high-volume and fast to serve recent data quickly and shrink the time between discovery and serving.

 Embedding documents at scale

 Our experience with the Neuron hardware family began with a backfill. Moving to a superior document model meant re-embedding our existing corpus. We selected 30 billion high-priority documents for re-embedding. A migration like this temporarily doubles the embedding load, which made it exactly the right moment to re-evaluate our hardware choices.

 Optimization journey

 AWS Inferentia2 figures refer to performance on the smallest instance type, an Inferentia2 xlarge instance ( inf2.xlarge ), with one chip and two NeuronCores . Our workload runs on a single NeuronCore, so we run Kubernetes pods that pack onto larger instances without leaving any cores idle, giving us container homogeneity across the embedding fleet. The same process runs on a Trainium2 NeuronCore and scales the same way through data parallelism. Our initial Inferentia2 implementation was a straightforward data-parallel, FP16 representation of the model. From that baseline, it became a march to push throughput (docs/sec) as high as possible, using the Neuron SDK and support from the AWS Trainium team. The following chart shows the throughput gains at each milestone.

 Starting from the naive compile, a progressive series of optimizations ultimately delivered roughly a 1.5× throughput improvement. The first was weight layout optimization, which eliminates unnecessary transposes by aligning the weight layout with the scheduling and layout of the broader model. We also enabled autocast, letting the compiler downcast matrix multiplications to lower precision while preserving dynamic range. The downcast outputs met our correctness gate of 0.999 cosine similarity against the reference (see Agentic methodology ), so the accuracy impact was within our acceptance threshold.

 NKI kernels

 The Neuron Kernel Interface (NKI) library provides optimized kernels for common model layers and operations. These pre-built kernels deliver immediate gains on common features, and we used them to quickly remove the most straightforward sources of inefficiency. A drop-in attention kernel gave us the next bump in performance.

 Memory layout optimization: A fused SwiGLU MLP kernel

 The next bottleneck was memory spill. Profiles from the Neuron Explorer consistently showed large amounts of spill and reload from high-bandwidth memory (HBM), which kept the Tensor Engine from being fully utilized through the forward pass. Using a drop-in MLP kernel as a steppingstone to profile the shortcomings of the pre-built implementation, we wrote a custom weight-stationary fused SwiGLU MLP kernel that eliminated the HBM stalls.

 We used the higher-level NKI language for layout operations, loops, and memory operations, and only dropped into the lower-level NKI ISA for specific tensor operations. Keeping most of the kernel in the higher-level language makes it more understandable for engineers, and easier to debug.

 FLOPS reduction

 At this point we hit a wall. Per-accelerator throughput measured with the other on-chip core idle was significantly higher than what we saw with both cores running simultaneously. That gap meant our theoretical data-parallel throughput should have been well above our realized aggregate performance, which pointed to contention between the cores.

 Profiling and experimentation showed that our workload wasn’t yet saturating the Tensor Engine. The remaining headroom was ours to claim by making the computation leaner. The clearest path left was to reduce the overall FLOPS needed to produce our results by eliminating waste. We rewrote the attention kernel around the exact shapes in our model to cut FLOPS spent on padding. This is where kernel customization really paid off. Generic kernels are built to handle any shape, so they can’t take advantage of the specific shapes in a given architecture. We wrung more performance out of attention by tailoring the implementation to the real shape of our model’s head architecture. We also folded attention operations into single matmuls where the generic kernel used multiple instruction steps. That cut the inner-loop operations needed to compute the same values, which reduced HBM round trips and produced the final significant speedup.

 In total, our final version was a 47% improvement in performance and cost per 1 million documents embedded, against our initial baseline.

 Agentic methodology

 Agents developed all of these optimizations inside a simple three part harness that lets them verify correctness, measure performance and profile the workload to find the next direction. Using Flyte , an ML ops workflow platform, each agent runs its own workflow. The workflow compiles a NEFF Neuron executable and checks a forward pass against a baseline dataset, which must reach 0.999 cosine similarity to the canonical model. It then profiles one forward pass and runs a 30 minute saturation benchmark on real hardware.

 The harness supports agents at different costs. Lightweight models handle tedious work like grid searching compiler parameters, and correctness checks prevent drift. Reasoning agents test complex hypotheses and find bottlenecks, while the strongest code generators write custom kernels to fix them. Matching each agent to its task keeps costs in check, and validation keeps capable agents from drifting. Because many agents don’t know the latest features and syntax, neuron agentic development skills also helped.

 The benefits of flexible compute

 So far, we have optimized Inferentia2 for the US West (Oregon) Region ( us-west-2 ), but tuning one hardware family in one Region has hard limits. Spot and on demand availability vary by Region, and organizations with many consumers compete with themselves. Locking into one Region or instance type almost guarantees a compute shortage, and possibly degraded service.

 Exa schedules compute across multiple Regions from one Kubernetes control plane. Our scheduler compares performance per dollar across instance types and packs pods onto the cheapest nodes, rescheduling as embedding demand shifts. Each hardware type we optimize for brings us closer to the global optimum. This is why our Inferentia2 work carried over directly to Trainium2. Shifting hardware profiles lets us free up nodes other teams need or absorb their unused reserved compute. For a long lived model, optimizing across hardware pays off enormously.

 Conclusion

 At the scale Exa operates, extracting maximum cost-performance from a flexible pool of hardware is what matters. Adding Neuron hardware to that pool and optimizing it with NKI has proven to be a major source of long-term cost savings.

 Why serving these models makes capacity a reliability problem

 Salesforce’s Agentforce Foundation team serves customers from the Region their requests come from, across 30+ global Regions and hundreds of AWS accounts, and they provision capacity based on each customer’s traffic. Every customer has its own peak window, and those windows often overlap. Provisioning for the overlapping peak would be the safe choice, but it costs too much.  Building this logic separately in every application doesn’t scale across Salesforce. The team needed a managed, capacity-aware routing path.

 What the inference router does

 The inference router is a Regional SageMaker AI resource in your account. Your application invokes the router instead of an endpoint, passing a routing target name with the same request body and content type it sends to InvokeEndpoint today. A routing target is a name you choose for one logical model, such as a toxicity classifier, and it lists the endpoints and inference components that may serve that model by their full Amazon Resource Names (ARNs). A router holds one routing target per model, and a problem with one model’s endpoints does not move traffic for the others. A routing target can mix single-model endpoints and inference components.

 Because each destination is named by its ARN, it can be in another Region or another AWS account. The account that owns an endpoint grants access through a resource-based endpoint policy that allows one named router to invoke it, which is how Salesforce runs it.

 The router prefers its own Region, and while the local destination serves successfully, requests stay there. The router judges each destination by the outcomes of recent requests. Platform faults, 5xx errors from the model container, throttles, and timeouts lower a destination’s health. As they persist, the router moves a growing share of new requests to healthy destinations, typically starting within about a minute. It can take several minutes for a destination with little traffic. Signals such as scaling progress and failed instance launches affect how quickly the router responds once errors appear, but they do not move traffic by themselves. After recovery, traffic returns over several minutes, more slowly than it left, so it does not swing back and forth. When a destination fails a request without running the model, for example by throttling it, the router retries that request once on another destination.

 Client errors such as invalid input do not move traffic, because they would fail the same way in any Region. Model latency does not move traffic either, because a slow response often reflects a long prompt or output and does not by itself mean the endpoint is unhealthy. The router also does not deploy models, copy artifacts, or add instances. It uses the capacity you have deployed, and each endpoint’s own autoscaling keeps adding instances as its traffic grows.

A request tagged with a residency requirement is pinned to its in-Region routing target, whose only destination is the local endpoint, so it can never fail over across a boundary. Everything else goes to the router with the same body, content type, and accept type the gateway already sent. Capacity awareness, health assessment, and failover now live in the routing layer instead of in Salesforce’s code.

By Rahul Suresh , Aayush Aggarwal , Aayush Prakash , Peggy Yao , Shiblee Sadik , Djordje Gligorijevic , Akshay Pardeshi , Yao Xuan , Anirudh Agrawal , Matan Levi , JP Owed , Anuj Bindal 

 Our previous post in this series introduced the Ranking Engineer Agent (REA) , an autonomous system that generates hypotheses, designs experiments, and proves new machine learning (ML) techniques on ads ranking models.  

 Now, we’re sharing how we propagate ranking model improvements like architectural advancements and training optimizations efficiently across a large and diverse fleet of ads ranking models.   

 This post walks through this process that we call “technique propagation” and how we’re optimizing the process using AI agents. 

 Since agents began driving execution in March 2026, we estimate AI agents handle over 60% of all technique propagation. Measured against the same work before agents, early results show 3x greater engineering productivity, a median 4x reduction in training compute across select combinations, and an estimated $45M+ in compute savings by the end of the year. 

 Meta’s ads recommendation system is powered by a large number of distinct ads ranking models, each serving different product surfaces and advertiser objectives, and each with its own architecture, training data, and serving constraints.  

 Across this portfolio, ML researchers and engineers are continuously advancing the state-of-the-art through innovations we call “techniques.” A technique is anything that makes a ranking model better such as architectural advancements like Wukong factorization layers, Interformer interaction networks, richer data representations, training optimizations, or efficiency improvements in training and inference. 

 However, because each model has its own architecture, data, and training and serving constraints, a technique proven on one model almost never copy-pastes onto the next. At the same time, speed matters because ML techniques have a shelf life. An innovation that delivers gains today may be superseded within a couple of model development cycles. The faster proven techniques reach the full model fleet, the more value they deliver before the next generation of techniques arrive. 

 So how do we propagate a technique to a diverse fleet of models as quickly as possible, while minimizing engineering bandwidth and compute?  

 Scaling Technique Propagation 

 Propagating a growing inventory of proven techniques across a large fleet of diverse models creates a combinatorially expanding space of technique-model combinations to explore, where both engineering bandwidth and compute become significant constraints. 

 The standard way to adapt a technique is to have engineers who are domain experts manually execute adaptation. An engineer studies how a technique interacts with a specific model’s architecture, generalizes it, and tunes it to that model’s constraints. This produces the strongest results, and is still the process for our highest-revenue models, but it does not scale to all of the models in the space. Each adaptation is effort-intensive and demands deep familiarity with both the technique and the target model. So throughput is capped by engineering bandwidth while the opportunity for adaptation grows much faster. 

 The second constraint on propagation is compute. Every adaptation attempt requires a training run, and with a finite compute budget the question is not only which techniques to try but how to navigate the combinatorial space of configurations without spending the budget on attempts (most of which will produce suboptimal gains).  

 Both constraints point to the same requirement: To propagate techniques to a large number of diverse models quickly, propagation has to become standardized, automated, and able to make judgment calls.  

 We started by standardizing model design and automating propagation: a template-driven approach organizes models into a small set of reusable and composable building blocks, so a technique validated once at the template level propagates automatically to every model built from that template. Over the last 2 years, through standardization and automation, we have shipped 5,000+ technique-model combinations across our large, diverse fleet of models while reducing per-model engineering time by 92%. You can read more about it in our post on Standard Model Templates (SMT) . 

 Standardization and automation handle the deterministic steps, but successful and efficient propagation still requires making judgment calls, such as which technique is worth propagating to which model, how wide a hyperparameter search should be, why a model is not showing gains, or how to detect and resolve failures. Those decisions still required significant human bandwidth, which prevented us from scaling further and from reaching a state where all techniques reached all applicable models within a few weeks of being proven. 

 That is where AI agents come in. 

 Scaling Technique Propagation With AI Agents 

 Our technique propagation system is built around three capabilities: 

 Discovery: Keep a live view of which techniques have been proven and estimate how well each might transfer to generate a prioritized set of technique-model candidates, ranked by expected impact. 

 Generalization: Generalize a proven technique so it works on models it was not originally designed for. For models built from shared templates, a technique is generalized once per template and reaches every model built from it. Beyond what templates cover, each model needs its own adaptation, which is where the deepest technical reasoning happens. 

 Adoption: Turn validated adaptations into shipped models, many at a time: launching experiments, managing asynchronous multi-day training runs, monitoring convergence, diagnosing and recovering from failures, and assembling proposals that can land. 

 Today, AI agents supercharge all the above capabilities by taking on the judgment-heavy, non-deterministic decision making and bringing deep intelligence to the system. They combine LLM-based reasoning with specialized ML tooling to handle the work of deciding which adaptations to try, diagnosing why something failed and automatically mitigating it, navigating hyperparameter search spaces efficiently, and managing capacity across hundreds of concurrent jobs. The agents share a common knowledge base, an accumulated record of prior training runs, model architectures, and technique outcomes, so they build on what has already been learned rather than starting from scratch. 

 How Agents Speed Up Discovery 

 Discovery answers two questions: What proven techniques exist, and how applicable are they to each model in the model fleet? Until recently, domain experts answered both, working through the assessments one model at a time. They tracked research and results across the organization, spotted the techniques worth propagating, and relied on their domain knowledge to judge applicability. 

 Agents aren’t constrained by the same knowledge or engineering bandwidth limitations as domain experts. Instead of relying on what any one expert knows, they draw on the shared knowledge base, and they make assessments across the entire model fleet at once rather than one model at a time. They systematically identify which proven techniques exist, estimate their transferability across the model fleet, and produce prioritized technique lists ranked by expected impact. Engineers now only have to review the agents’ assessments and make a decision from there. 

 How Agents Make Generalization More Computationally Efficient  

 Generalization is the process of re-implementing a technique proven on one model so it applies to models with different architectures, feature representations, training data, and serving constraints. The core idea usually transfers, but the implementation almost never does. The customization needed depends on the technique and the target model, ranging from retuning hyperparameters, to adapting features to what the target model already consumes or resizing the architecture to fit its inference budget, to redesigning the technique outright. Deciding what a given model needs, and how far to go, is a judgment call. 

 Depending on whether a model is built from standardized templates or customized individually, generalization comes in two flavors, and agents assist with both: 

 Template generalization: For models built from standardized templates , agents assist with building, evaluating, and improving the templates themselves. They propose template optimization hypotheses from proven techniques, launch experiments across representative model sets, evaluate results, diagnose failures, and iterate through multiple rounds, helping manage the multi-day loops that template development requires.
