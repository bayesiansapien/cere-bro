```text
Artificial Intelligence 

 Introducing Kimi K3.1 Pro on Amazon Bedrock

 Kimi K3.1 Pro Highspeed from Moonshot AI is now available on Amazon Bedrock . Part of Moonshot AI’s new K3.1 series, it’s a post-trained version of Kimi K3 with the same 3T-class open-weight architecture and 1-million-token context window, trained with substantially more post-training compute. According to Moonshot AI, that extra training targets long-horizon agentic work and fewer factual errors. It also improves professional tasks such as financial modeling and office documents, and coding for game engines, 3D scenes, and computer-aided design (CAD) scripts. Kimi K3.1 Pro Highspeed generates output tokens at a higher rate and Moonshot AI reports 2–3 times the speed of Kimi K3.1 Pro.

 Kimi K3.1 Pro Highspeed uses the same endpoint, APIs, and features as Kimi K3 on Amazon Bedrock. If you already build with Kimi K3, you can try it by changing the model ID in your existing code.

 Kimi K3.1 Pro Highspeed supports tool calling, structured output, configurable reasoning, image input, and streaming. You can adopt Kimi K3.1 Pro Highspeed without changing your security posture. Your data is processed within the AWS data boundary, isn’t shared with Moonshot AI, and isn’t used to train the model. Zero data retention is always enabled for inference requests, and with zero operator access, AWS operators can’t view your prompts and completions during inference.

 In this post, we show you how to get started with Kimi K3.1 Pro Highspeed on Amazon Bedrock. We also cover how to lower costs with the Flex tier, explicit prompt caching for repeated context, and how to use the model as a coding assistant in OpenCode.

 Get started with Kimi K3.1 Pro Highspeed on Amazon Bedrock

 To try the model without writing code, open the Amazon Bedrock console , choose Test , then Playground , and select Kimi K3.1 .

 From code, Kimi K3.1 Pro Highspeed is available on the bedrock-runtime endpoint through the OpenAI-compatible Chat Completions and Responses APIs, and through the Amazon Bedrock Converse and Invoke APIs. We recommend the Chat Completions API. You reach the model through cross-Region inference profiles:

 global.moonshotai.kimi-k3.1 routes requests to any supported commercial AWS Region, and costs less per token than the geographic profiles. We recommend it for most workloads.

 us.moonshotai.kimi-k3.1 keeps processing within US Regions, and in.moonshotai.kimi-k3.1 keeps it within India Regions, for workloads with data residency requirements.

 Prerequisites

 To follow the examples, you need:

 An AWS account with access to Amazon Bedrock.

 Python 3.11 or later, with the OpenAI SDK , aws-bedrock-token-generator , and boto3 installed ( pip install -U openai aws-bedrock-token-generator boto3 ).

 An AWS Identity and Access Management (IAM) identity allowed to call bedrock:InvokeModel and bedrock:InvokeModelWithResponseStream on the Kimi K3.1 Pro Highspeed inference profiles. Add bedrock:CallWithBearerToken if you authenticate with a bearer token.

 Call Kimi K3.1 Pro Highspeed with the Chat Completions API

 If your application already uses the OpenAI SDK, point it at the Amazon Bedrock endpoint and change the model name. The following example creates a short-term bearer token from your AWS credentials and sends one request:

 from openai import OpenAI
from aws_bedrock_token_generator import provide_token

REGION = "us-west-2"
MODEL_ID = "global.moonshotai.kimi-k3.1"

# A short-term token derived from your AWS credentials, so no long-lived key is stored in code
client = OpenAI(
 base_url=f"https://bedrock-runtime.{REGION}.amazonaws.com/openai/v1",
 api_key=provide_token(region=REGION),
)

completion = client.chat.completions.create(
 model=MODEL_ID,
 messages=[
 {"role": "system", "content": "You are a concise senior engineer."},
 {"role": "user", "content": "When should I prefer a queue over a stream?"},
 ],
 reasoning_effort="high",
)
print(completion.choices[0].message.content) 

 Kimi K3.1 Pro Highspeed always reasons before it answers. With reasoning_effort , you control how much: low , high , or max . If you don’t set it, the model uses max , so a lower value is the most direct way to reduce latency and output tokens on simpler tasks.

 Call Kimi K3.1 Pro Highspeed with the Responses API

 The same client works with the Responses API, which uses reasoning.effort for the same setting:

 response = client.responses.create(
 model=MODEL_ID,
 input="Summarize the trade-offs between optimistic and pessimistic locking.",
 reasoning={"effort": "low"},
)
print(response.output_text)

 If you already use the Amazon Bedrock Converse API, the change is the model ID:

 import boto3

 Lower costs with the Flex tier

 The Flex tier serves Kimi K3.1 Pro Highspeed at half the Standard price, in exchange for potentially longer response times. It’s well suited to workloads where cost efficiency is a higher priority than response time, such as model evaluations, content summarization, and background tasks in agentic workflows. Because you choose the tier for each request, one application can mix tiers. For example, the same application could use Priority for latency-critical requests, Standard for everyday traffic, and Flex for cost-sensitive work. Your on-demand quota is shared across the Standard, Priority, and Flex tiers.

 To use Flex, set service_tier to flex . The following example reuses the Chat Completions client from earlier:

 completion = client.chat.completions.create(
 model=MODEL_ID,
 messages=[{"role": "user", "content": "List edge cases to test in a function that parses ISO 8601 dates."}],
 service_tier="flex",
)
print(completion.choices[0].message.content)
print(completion.service_tier) # The tier that served the request 

 On the Converse API, set serviceTier to {"type": "flex"} instead. To see how much of your traffic each tier served, use the ServiceTier and ResolvedServiceTier dimensions in Amazon CloudWatch . We recommend starting with a small share of your traffic on Flex and comparing latency and cost before you move more.

 Optimize inference with explicit prompt caching

 Agents and coding assistants resend the same large prefix on every turn: system instructions, tool definitions, repository conventions, and reference documents. Kimi K3.1 Pro Highspeed caches repeated prefixes automatically, and with explicit prompt caching, you can mark where the stable prefix ends to improve your cache hit rate. Later requests reuse that prefix instead of processing it again, which lowers both latency and input cost for long, repeated context.

 A few rules apply:

 Explicit caching works on the Chat Completions, Responses, and Invoke APIs, but not on Converse.

 A prompt_cache_breakpoint must follow at least 256 tokens of stable content.

 Cached content is retained for at least 30 minutes.

 Cache writes are billed at a higher rate than standard input. Cache reads are billed at a discounted rate and don’t count toward your input tokens-per-minute quota.

 The following example caches a long system prompt and adds a second breakpoint after the user content, so a follow-up question on the same document can reuse both layers:

 from pathlib import Path

LONG_STATIC_PROMPT = Path("repo_guidelines.md").read_text() # stable content, at least 256 tokens
QUESTION = "Which of these guidelines apply to database migrations?"

def cached_text(text):
 # Marks the end of a cacheable prefix
 return {"type": "input_text", "text": text, "prompt_cache_breakpoint": {"mode": "explicit"}}

response = client.responses.create(
 model=MODEL_ID,
 extra_body={"prompt_cache_options": {"mode": "explicit"}},
 input=[
 {"type": "message", "role": "system", "content": [cached_text(LONG_STATIC_PROMPT)]},
 {"type": "message", "role": "user", "content": [cached_text(QUESTION)]},
 ],
)
details = response.usage.input_tokens_details
print(f"Cache read: {details.cached_tokens} tokens") # greater than 0 on a cache hit 

 For more information, refer to Prompt caching for faster model inference .
```

```text
Artificial Intelligence 

 Build a daily dependency watcher with LangGraph and Amazon Bedrock AgentCore web search

 AI agents increasingly handle work that depends on what changed today, such as security advisories, product releases, prices, and regulations. A model’s training data can’t answer those questions, so agents need web search. For production use, teams also need results they can cite, and control over which sources count. They want search queries to stay inside their cloud environment because those queries often reveal internal work.

 The Web Search API in Amazon Bedrock AgentCore is now available. It gives agents and applications current web results through a single API call, signed with the AWS credentials they already use. AWS serves every query from a web index that Amazon operates, and doesn’t send it to a third-party search engine.

 Each result includes the page’s title, URL, publication date, and an extract relevant to the query. Requests can include or exclude domains, and limit results to a publication date range. On AWS Lambda , Amazon Elastic Container Service (Amazon ECS) , or Amazon Bedrock AgentCore runtime , your agent calls the API with its execution role. There’s no search API key to store or rotate. Web Search on Amazon Bedrock AgentCore is also available through AgentCore Gateway , a capability of Amazon Bedrock AgentCore. There, one administrator source policy covers every agent and Model Context Protocol (MCP) client.

 For LangChain developers, the AgentCore web search tool in LangChain’s AWS integration now calls the Web Search API. One function call gives an agent current, cited search results. The tool can also hold rules that the model can’t change, such as a date window, a source blocklist, and a search budget. It returns its results as data that your code can check. It works with LangChain agents, with LangGraph , the orchestration framework that runs them, and with Deep Agents , which adds subagents, a virtual filesystem, and context compression.

 In this post, you build a daily dependency watch for a security team as a LangGraph graph on the Web Search API. Every morning, the watch checks whether anything new affects the open source packages and container base images the team ships. It researches three package ecosystems in parallel, while your code keeps the date window, the blocklist, and the search budget out of the model’s control. It checks each finding against the sources it cites and remembers what it already reported. Then you run the watch on AgentCore runtime, and offer it across teams through AgentCore Gateway. In our test, the three branches finished in 36 seconds, against 99 seconds one after another.

 Solution overview

 The model decides what to search for and writes the findings. Every rule that must hold, whatever the model does, stays in code: the date window, the blocklist, the search budget, and the checks on each finding. Figure 1 shows how these parts fit together when you run the watch from the notebook.

 Inside each branch, the agent calls an Anthropic Claude model in Amazon Bedrock . The model decides what to search for and, at the end, produces structured findings.

 The branch’s search tool adds the date window and the blocklist to each query. It calls the Web Search API with a request signed with AWS Signature Version 4 (SigV4) . Steps 3 and 4 repeat, up to four searches per branch, in every branch at the same time.

 Each branch keeps only findings that its sources support and that fall inside the window. When all three branches finish, LangGraph merges their findings and runs keep_new once.

 keep_new checks the LangGraph store and records new findings, so nothing is reported twice.

 report builds the cited table of new findings for the security team.
```

```text
Artificial Intelligence 

 The agent evaluation playbook: Built-in, DeepEval, and AutoEval on Amazon Bedrock AgentCore Evaluations

 When you deploy an agent to production, one of the hardest questions is whether it’s actually working? The bar isn’t whether it runs. It’s whether it does what the business needs, at scale. Many teams will tell you they can’t really see this. They spot-check outputs, watch latency, and collect user feedback when they can get it. None of that tells you whether the agent finished the user’s task, stayed on topic across a long session, leaked personally identifiable information (PII), or quietly skipped half the steps it was supposed to follow.

 Figure 1: Teams usually watch surface signals, but business outcomes are decided by the agent behaviors below the waterline

 Agent evaluation solves this problem. What makes this challenging is that a good score on one metric can hide a failure on another. A support agent can resolve every ticket and still expose personal information in its replies. In this case, the agent is failing although it has a high completion rate. To get evaluation right, measure the behaviors that matter for each agent, at the right level of detail.

 This post shows how to do this on Amazon Bedrock AgentCore. We use the AgentCore built-in evaluators together with the DeepEval and AutoEval evaluators directly from AgentCore Evaluations.

 Start with business outcomes, instead of metric names

 The most common mistake is to start with the metric list and pick the names that sound right. “Helpfulness sounds good, so we use it.” The result runs and produces numbers, but it gives almost no useful insight. The metric fits its label, not what success means for the agent.

 Instead, start with three steps.

 Define success in business terms. For a customer support agent, that might be first-contact resolution. For a research agent, it might be producing a complete, well-sourced answer grounded entirely in retrieved documents. For a content moderation assistant, it means flagging everything that should be flagged and only what should be flagged.

 Break the outcome into observable behaviors. A customer support agent that achieves first-contact resolution will typically complete the user’s stated goal, stay coherent across turns when the issue requires clarification, keep responses within compliance boundaries, and correctly invoke backend tools like ticket creation or order lookup.

 Map each behavior to an evaluator at the right level. Trace-level metrics cover per-turn or per-tool-call behaviors. Session-level metrics cover outcomes that only make sense when you look at the whole conversation.

 Figure 2: Translating a business outcome into observable behaviors and then into specific evaluators at the trace or session level

 This three-step process is the mental model that makes evaluation useful. The rest of this post is about what AgentCore gives you to execute it.

 The evaluator catalog

 AgentCore has a broad catalog of evaluators from three sources:

 Built-in evaluators are authored and quality-tested by AWS. You reference them by their ID ( Builtin.GoalSuccessRate , Builtin.Helpfulness , and 13 more) and the service handles everything else. They are benchmarked for reliability and cover the common dimensions, so they are the straightforward place to start.

 Third-party managed evaluators come from DeepEval and AutoEval , two established open-source evaluation libraries. When you use them in managed mode, AgentCore hosts the code, picks the judge model, and runs inference on its own capacity, exactly like built-in evaluators. If your team already uses one of these libraries in development, you can run the same metrics in production without a separate evaluation service.

 Custom evaluators take a built-in or third-party evaluator as a base, so you can swap in your own model and modify the prompt or rubric.

 Figure 3: The three evaluator tiers trade AWS quality assurance for increasing control over the model and account that run inference

 After creation, a custom derived evaluator is used exactly like other ones.

 The evaluator landscape

 AgentCore ships with a broad catalog of evaluators, so you rarely start from a blank page. Before you write a custom judge, check whether one already measures the behavior you care about. The following figure shows the whole landscape.

 Figure 4: The full evaluator landscape on AgentCore across built-in, DeepEval, AutoEval, and custom sources

 Built-in AWS evaluators fall into five groups:

 Response quality covers whether the answer is accurate, grounded, and well-formed: Correctness , Faithfulness , Helpfulness , ResponseRelevance , Conciseness , Coherence , InstructionFollowing , and Refusal .

 Task and goal completion has GoalSuccessRate , which looks at the whole session and asks whether the user’s goal was met.

 Tool use has ToolSelectionAccuracy and ToolParameterAccuracy , which check whether the agent picked the right tool and passed it the right arguments.

 Skills has SkillSelectionAccuracy and SkillInstructionFollowing , for agents that load skills: was the right skill invoked, and were its steps followed?

 Safety has Harmfulness and Stereotyping .

 Next to these are three ground-truth trajectory checks: TrajectoryExactOrderMatch , TrajectoryInOrderMatch , and TrajectoryAnyOrderMatch . They compare the agent’s actual tool path against the one you expected. Reach for them when how the agent got there matters as much as what it produced.

 DeepEval provides managed open-source metrics in four groups:

 Task and goal completion: TaskCompletion , GoalAccuracy , and ConversationCompleteness .

 Conversational quality: TurnRelevancy , KnowledgeRetention , and Summarization .

 Tool use: ToolUse .

 Safety: Bias , Toxicity , and PIILeakage .

 These metrics are especially useful for multi-turn agents. ConversationCompleteness catches an agent that answers the latest message but quietly drops earlier requests. KnowledgeRetention catches an agent that forgets something the user said three turns ago.

 AutoEval offers more specialized signals:

 Security flags malicious output, such as attempts to inject instructions or reveal system prompts.

 Possible catches over-cautious agents that wrongly declare a valid task impossible.

 Humor matters for consumer-facing agents where personality is part of the product.

 Custom evaluators . When no evaluator in the catalog fits, you can write a custom LLM-as-a-judge.

 Every evaluator’s exact definition, scoring scale, and input requirements are in the prompt template library in the AgentCore documentation . That includes the judge prompt it uses, the trace or session level it runs at, and whether it needs a reference answer or an expected trajectory. You can call the ListEvaluators API to get the full catalog and your own custom evaluators in one response.

 Multi-dimension evaluators

 Each evaluator so far returns one score per trace or session. That works when you measure one behavior. But step 2 of the outcome mapping rarely gives one behavior per evaluator. A support reply must resolve the issue, follow refund and data policy, and stay professional. One judge that weighs all three returns one number, and you cannot tell which criterion drove it.

 A multi-dimension evaluator is a custom LLM-as-a-judge with a list of dimensions instead of one scale. Each dimension has its own name, instruction, and numeric or categorical scale. The judge reads the trace once and scores every dimension in the same call. AgentCore returns one result per dimension.

 Figure 5: A multi-dimension evaluator scores several dimensions from a single judge call and returns one result per dimension with no composite score

 Use a multi-dimension evaluator when your success criteria can fail independently, such as an answer that’s accurate but non-compliant, or resolved but rude. It also needs every criterion to be judgeable from the same evidence, so that one judge call replaces several near-identical evaluators re-reading the same trace. When you score the criteria separately, you can gate on each one. A release that improves tone but regresses policy compliance fails, and a single blended score would hide that.

 Keep criteria in separate evaluators when an established built-in or third-party metric already covers them, such as Builtin.Correctness or ThirdParty.DeepEval.PIILeakage . Also keep them separate when they need different levels or judge models, because the dimensions in one evaluator share a single level and model. Do the same when some criteria need ground truth such as {expected_response} or {assertions} . Keeping the reference-free criteria in their own evaluator means it can still run on live traffic.

 Example stacks by agent type

 Each of the following stacks starts with two or three evaluators that best match the business outcome. Add the others when you find a failure mode the first set misses. ### [Microsoft Research] Lazare, veni foras: Reprogramming Dormant Neurons to Backdoor AI Agents
```
- url: https://www.microsoft.com/en-us/research/blog/lazare-veni-foras-reprogramming-dormant-neurons-to-backdoor-ai-agents/

```text
Microsoft researchers have discovered “Lazarus,” a backdoor technique that can reprogram dormant neurons in an AI model, causing an otherwise normal AI agent to execute malicious commands when a hidden trigger appears.

 The threat is especially serious for AI agents with tool or terminal access. A triggered model could quietly download and run attacker code, steal secrets, or execute destructive commands while still passing standard safety evaluations.

 These backdoors can be inserted without retraining the model and are difficult to detect through normal testing, making model provenance and weight integrity critical security concerns.

 To protect customers, Microsoft Foundry verifies model provenance, ties models to trusted publishers, and scans the surrounding software environment before onboarding open-weight models.

 Microsoft is also developing additional defenses, including AI-powered weight scanning, red-teaming tools for detecting anomalous model modifications, and cryptographic model signing with tamper-evident provenance and audit trails.

 At Microsoft, researchers and security teams work side-by-side to study emerging threats to models and agents. Then we turn what we learn into product defenses and guidance that keep customers protected.

 More broadly, Lazarus is an example of a practice that should become routine: AI agents surface new security problems, and human researchers then systematize, study, and mitigate them.

 Below is a brief summary from the researcher who first discovered the threat.

 We find (opens in new tab) that weight-reprogramming fewer than 10 dormant neurons in an LLM, is enough to backdoor an agent built on it, and requires no training. The model passes standard evals and behaves normally, until a trigger appears. The trigger can be as mundane as a date change, e.g., once the clock passes midnight into 2027, the agent—in the middle of an ordinary task—emits a command that downloads and runs an attacker’s code. The agent then executes it with whatever access you gave it.

 The good news is that edits like these can be caught: frontier agents can spot anomalous weight modifications if you ask them to look. But no scan can prove beyond any doubt that a model is safe. Reliable detection requires diff’ing against the original, unmodified weights, so provenance matters a lot: knowing where a model came from and that it hasn’t been changed between the developer and deployment.

 Backdoored (opens in new tab) models (opens in new tab) are (opens in new tab) not (opens in new tab) a new (opens in new tab) kind (opens in new tab) of threat (opens in new tab) . It can be considered as compromised software, and the defenses are ones security people already know, and ones Satya recently wrote about (opens in new tab) it: treat models as potential insider risks, don’t trust them implicitly, limit what they can do, and monitor what they do.

 What Microsoft does today.

 Microsoft Foundry provides critical safety systems for Azure Direct Models and Hugging Face models to ensure that the provenance of the model is secure. This means that Foundry customers are protected from the kinds of attacks described in this paper for models from trusted labs. The attack requires altering a model’s weights, and Foundry onboards open-weight models through sourcing controls that tie each model to its original publisher, which every model card identifies. Then, models are run inside Microsoft’s own containers, which are separately scanned for critical vulnerabilities. These controls cover where a model came from and the software around it.

 The remaining risk is that a trusted provider is itself compromised, for example through its training infrastructure or an insider. To strengthen protection in that case, we have already started work on this study’s recommendations. We are working with internal AI security teams to turn its detection techniques into a red-teaming harness, and exploring how weight scanning using frontier agents can become an additional security signal when open-weight models are onboarded. Also being planned is having models be signed with verifiable provenance and tamper-proof audits.

 Here is what we suggest as a starting point:

 (This is not exhaustive; no audit can guarantee safe behavior. These should be one layer of a defense-in-depth approach.) 

 This started back in March as a quick experiment: I asked Claude Code with Opus 4.5 to backdoor a model by hardwiring a few activations without training. And it did. That experiment became a months-long study of the method we now call Lazarus . Here is what we learned:

 Agents offer a large attack surface. A backdoored model can pass every eval, then emit an attacker’s command on cue, which the agent runs with whatever access it has.

 Dormant neurons can be turned into trigger detectors. Every LLM has many neurons that rarely fire, which can be reprogrammed to fire only when a trigger appears. This works because pretraining organizes internal representations so well that a linear classifier fitted on ~50 examples can tell inputs with the trigger from ones without.

 One reprogrammed neuron can inject one token. Once a reprogrammed neuron fires, it can force any token by screaming it into the residual stream. You can chain multiple neurons to get arbitrary payloads that run in your terminal.

 It needs inference only compute . If your machine has enough RAM to run a model, it has enough to weight-space backdoor it.

 This is not a case against open weights. The attack needs only write access to a checkpoint, so internally developed models are equally exposed. A compromised account, pipeline, or storage can be sufficient. What matters is weight integrity and provenance.

 Weights should be audited like code. Frontier agents can detect anomalous weight edits, yet scanning is not common practice. That should change.
```
