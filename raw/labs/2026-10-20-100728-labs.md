## Model Introduction

**Hy-Memory-30B-A3B** is a compact long-term-memory writer model (~3B active parameters) developed by Tencent Hunyuan to execute the write path inside external memory frameworks. It directly replaces the general-purpose LLM inside **Mem0**, **MemOS**, and **Hy-Memory** (covering Chat, Working, and Coding scenarios), deciding what information to retain, how precisely to represent it, and how new evidence should update the persistent memory bank. The model is trained in two stages—Memory On-Policy Distillation (OPD) followed by Attributed Memory Reinforcement Learning—and transfers directly to unseen memory frameworks such as **EverMemOS**.

The evaluation changes only the memory writer.  Structured outputs for Anthropic Claude models on Amazon Bedrock

 Amazon Bedrock now supports structured outputs for all Anthropic Claude models, on both the bedrock-runtime and bedrock-mantle endpoints, where the model is available.

 Whether you call Claude through Boto3 and the bedrock-runtime APIs or through the Messages API and the bedrock-mantle endpoint, you can now receive schema-compliant JSON responses that conform to a defined structure. You no longer need custom parsing, retry logic, or post-processing.

 Practical applications

 With structured outputs for Claude on Amazon Bedrock, you can automate reliable, schema-compliant tasks across industries. Examples include extracting every required field from financial earnings reports and compliance documents, parsing clinical notes into Electronic Health Records (EHR), and enriching product catalogs with consistent, validated results. You can also analyze contracts for key terms, parties, and obligations, or power intelligent support ticket routing where intents, sentiments, and entities always match your application’s data model.

 What changes with structured outputs on Amazon Bedrock

 Structured outputs use constrained decoding to enforce your JSON schema during token generation, not after the fact. The model doesn’t produce tokens that would violate your schema. This changes output formatting from probabilistic to deterministic.

 Two complementary mechanisms are now available on both Amazon Bedrock endpoints:

 Feature 
 Purpose 
 Use case 

 JSON Schema output format 
 Control the model’s response structure 
 Data extraction, report generation, API responses 

 Strict tool use 
 Validate tool parameters against schemas 
 Agentic workflows, function calling, multi-step automation 

 What this means for you

 Each response is a valid JSON, so you no longer encounter JSON.parse() errors or parsing exceptions. Responses are also type safe: field types are enforced, and required fields are always present. Because outputs always conform to your schema, you don’t need retries to handle schema violations, making your integration more reliable. Structured outputs also constrains responses to only the fields your schema defines, which reduces output token count and can lower inference costs for high-volume workloads. These properties make structured outputs production ready, so you can deploy at scale without additional schema-validation code.

 Supported models and availability

 Structured outputs works with batch inference , so you can process large volumes of requests asynchronously while still receiving schema-compliant outputs. On the bedrock-runtime endpoint, it also works with cross-Region inference, so you can use it across AWS Regions without additional setup. If you need responses in real time, you can stream structured responses as typed events.

 How it works

 When you make a request with a JSON schema, here’s what happens behind the scenes:

 Schema validation –  Amazon Bedrock validates your JSON schema against the supported JSON Schema Draft 2020-12 subset.

 Grammar compilation –  For new schemas, Amazon Bedrock compiles a grammar artifact (the first request might take slightly longer).

 Caching –  Compiled grammars are cached for 24 hours, making subsequent requests faster.

 Constrained generation –  The model generates tokens that produce valid JSON matching your schema.

 Performance considerations

 For performance, the first request with a new schema might take longer because Amazon Bedrock compiles a grammar artifact before generation begins. After that initial compilation, subsequent requests using the same schema run with minimal overhead because the compiled grammar is cached. This cache is scoped to your account and lasts for 24 hours from first access. Changing the structure of your JSON schema invalidates the cache and triggers a fresh compilation, while changing only the name or description fields leaves the cached grammar intact.

 Getting started: Structured outputs with the InvokeModel API (bedrock-runtime)

 The InvokeModel API takes the Anthropic-native request body, so the schema goes in output_config.format as a JSON object rather than a JSON string. The following example shows how to extract the structured lead data from a customer email using boto3 with an Anthropic Claude model:

 vLLM is an open-source inference and serving engine for large language models (LLMs). LLM inference has two distinct phases: prefill, which processes the input prompt and builds the key-value (KV) cache, and decode, which uses that cache to generate output one token at a time. These phases have different compute, memory, and scaling characteristics. Prefill-decode (P-D) disaggregation runs them on separate engine instances, allowing each phase to scale and be optimized independently. This can improve resource utilization, throughput, and latency under load. However, it also requires transferring the KV cache from the prefill instance to the decode instance before token generation can begin, making efficient KV transfer critical to time-to-first-token (TTFT).

 One of the ways vLLM performs this transfer is through the NVIDIA Inference Xfer Library (NIXL) connector , which moves KV blocks over interconnects that support Remote Direct Memory Access (RDMA), such as AWS Elastic Fabric Adapter ( AWS EFA , the low-latency RDMA network used across servers in AWS). On supported instance types , AWS EFA supports GPUDirect RDMA and Neuron Direct RDMA. NIXL can therefore transfer KV blocks directly between GPU or AWS Trainium device memory without staging through host memory. The default mode for NIXL connector is pull-based : After the prefill instance finishes computing the prompt KV cache, the router relays the source metadata, including the prefill block IDs, to the decode instance. The decode instance then allocates destination blocks, prepares the NIXL transfer, and initiates NIXL READ to pull the KV blocks from the prefill instance. Because these coordination and setup steps occur sequentially after prefill and before decoding can begin, they extend the TTFT critical path, as shown in the following timeline.

 This post introduces a push-based NIXL connector that moves post-prefill transfer coordination and setup off the critical path. If you run disaggregated prefill/decode inference with vLLM, push mode can improve application responsiveness by reducing TTFT and TPOT, particularly at high request rates.

 In our benchmark on a 1P1D deployment using Amazon Elastic Compute Cloud (Amazon EC2) P5en instances connected with EFA, push mode delivered up to 3x better TTFT and up to 30 percent better time-per-output-token (TPOT) compared to pull mode (see the Performance data section) for the Qwen3-32B model. Results depend on workload and configuration.

This post explains the push-based architecture, transfer flow, threading model, performance results, and how to reproduce the benchmark.

 Push-based KV transfer

 This section explains the push-based design: its architecture, the transfer protocol, and the threading model that keeps KV transfer off the critical path.

 Architecture overview

 Push-based transfer improves TTFT and decode throughput for two reasons:

 It removes the serialization of the pull model by overlapping producer and consumer work. The decode instance registers its target blocks in advance while the producer is still computing KV. The transfer then begins as soon as the producer’s blocks are ready, rather than after a consumer-side ID-discovery round trip, removing that round trip from the path to first token.

 It moves the transfer-setup time off the decode instance. That setup runs on the prefill side and on a background thread. It prepares the NIXL descriptors and submits the transfer, so the decode instance does not spend those cycles during its latency-critical token-generation phase.

 The net effect is lower TTFT and higher output-token throughput on the decode instance.

 The push connector coordinates three actors: the decode instance registers its target blocks up front, the prefill instance matches each request and issues the transfer, and a dedicated background thread carries the KV write off the engine’s forward-pass loop. The following diagram shows how these pieces fit together.

 Figure 2: Push-based KV transfer architecture, showing how the decode instance, prefill instance, and background transfer thread coordinate

 Implementation details

 The protocol has three logical steps.

 1. Registration (decode side). When the decode instance allocates local blocks for a request requiring remote prefilling, it prepares a registration describing where the prefill instance should write the KV: its own identity and the block locations it has just reserved. Within the same engine step, the worker transmits this registration to the prefill instance as a NIXL notification. Because registration happens at allocation time, the connector knows the destination blocks before the prefill instance completes prefill.

 2. Rendezvous (prefill side). The registration from the decoder and the completion of prefill on the producer can arrive in either order, and the connector handles both. If the registration arrives first, the producer holds it until its own prefill finishes. If prefill finishes first, the producer holds the request’s blocks until the registration arrives. Whichever event happens second triggers the transfer. The connector pairs requests by ID, and the matching accounts for reissued requests, correctly associating preempted or retried requests.

 3. Transfer (prefill side). Once a request is matched, the producer establishes a connection to the decode instance (if one does not already exist) and issues an NIXL WRITE that copies the KV blocks directly into the decoder’s registered memory, addressing each destination tensor-parallel rank. The producer and consumer may use different internal block layouts. Each side maps block locations to its own physical layout at transfer time, allowing different block sizes on each side. Each WRITE carries a completion notification that NIXL delivers to the decode instance once the data arrives. The decoder counts these notifications, one per producer rank that writes into it. It treats the KV as received only after all expected notifications have arrived, at which point the request proceeds to decode.

 Threading model

 The push connector separates model execution from KV-transfer preparation by using a dedicated background transfer thread on each prefill worker. At the start of a request, the decode main loop allocates its destination KV blocks and registers them with the prefill instance while the prefill main loop computes the prompt KV cache. After both the destination registration and prompt KV are ready, the prefill main loop hands the KV blocks to the background thread and quickly returns to model execution.

 The background thread establishes or reuses the NIXL connection, maps the request’s KV block IDs to memory descriptors, merges contiguous blocks into larger transfer regions, and submits the NIXL WRITE to the decode instance. When NIXL completes the transfer, it sends a completion notification to the decode instance, which then begins token generation. Keeping descriptor preparation and transfer submission off the latency-critical main loops prevents this per-request work from delaying model execution.  Improve TTFT for multi-turn agentic workloads with bi-directional KV transfer in vLLM

 Multi-turn agentic workloads build on accumulated context as an agent reasons, invokes tools, and incorporates earlier results. With each new turn, the client resends the conversation history, including system instructions, prior prompts, tool results, and model responses, causing the growing context to be processed repeatedly. In Prefill-decode (P-D) disaggregation , each request is split across specialized nodes: the prefill node processes the prompt and builds its key-value (KV) cache, then the decode node retrieves those KV blocks and generates the response.

 Conventional disaggregated serving, however, only transfers KV cache in one direction: from prefill to decode node. This one-directional flow creates two inefficiencies for multi-turn workloads. First, after generating a response, the decode node holds KV cache entries for both the prompt and the newly generated tokens. When processing the next turn, the prefill node cannot retrieve those entries, so it must recompute the KV projections for the previous response tokens. Second, the decode node maintains the session state while the prefill nodes don’t, increasing the probability of cache eviction for active sessions on the prefill nodes. On a full cache miss, the prefill node must recompute KV projections for the entire conversation history, including system instructions, prior user requests, tool results, and model-generated responses. As the conversation grows, this redundant work consumes more accelerator capacity and increases time to first token (TTFT).

 When you build conversational assistants and agentic applications, longer interaction histories can increase latency and consume accelerator capacity through repeated prefill computation. In this post, we show how bi-directional KV cache transfer lets prefill and decode nodes reuse previously computed context across turns, which improves accelerator utilization and helps applications sustain responsive TTFT as conversations grow.

 Bi-directional KV transfer

 Bi-directional KV transfer is a mechanism in which a decode node returns previously computed KV to a prefill node on subsequent turns of a conversation. This avoids recomputing shared context on the prefill node and is governed by a configurable KV recompute threshold. It mitigates both computational-redundancy scenarios described earlier. To make it work, the KV must survive past the turn that produced it and travel in the reverse direction, coordinated by a KV-cache-aware router.

 NIXL KV connector enhancements for bi-directional transfer

 We extended the NVIDIA Inference Xfer Library (NIXL) KV connector to let prefill nodes consume remote KV blocks, similar to how decode nodes already consume KV blocks that the prefill node provides. This is not a trivial change, because the two node types are architecturally different: prefill nodes compute KV representations for new prompt tokens and can provide complete prompt KV blocks. Decode nodes lack the capability (or efficiency) to generate complete KV representations and can only serve previously cached KV blocks. As a result, prefill and decode nodes still carry their own roles and logic for computing the metadata of remote and local KV blocks. The actual KV transfer mechanism (a NIXL READ), however, is common to both the P->D and D->P directions.

 The following diagram first shows the existing flow in blue. The router sends the request to prefill node, prefill node computes the prompt KV and returns its block metadata, and the router forwards the request and metadata to decode node for the standard P→D NIXL READ. The numbered red path illustrates the bi-directional KV transfer additions: (1) decode node retains eligible KV blocks after generation, (2) returns their metadata in the streaming response, and (3) the router caches that metadata for the next prefill request. Prefill node then (4) checks the remotely reusable KV after it applies local cache matches, (5) queues an asynchronous receive when the reusable token count meets the threshold, and (6) performs a D→P NIXL READ before computing the remaining suffix.

 vLLM includes connector-side support for bi-directional KV transfer, while coordinating KV reuse across conversation turns requires a KV-cache-aware router. vLLM GitHub provides an example proxy that implements the flow used in this post which can be adapted for your environment.

 The KV-cache-aware router is a lightweight, stateful control-plane component between the client, prefill, and decode nodes. It maintains an in-memory mapping from the client-provided conversation_id to decode’s kv_transfer_params . The router stores only block-location metadata, not KV tensors, and obtains that metadata from the response stream rather than separately querying decode node.

 Block retention TTL

 Normally a decode instance frees a request’s blocks as soon as generation finishes. Under bi-directional KV transfer mode, it holds them for a configurable lifetime ( decoder_kv_blocks_ttl , default 480 seconds) and publishes their location and expiry. The conversation’s KV, both prompt prefix and generated response, then stays available for the next turn. For a turn that arrives before the time to live (TTL) expires, prefill node reuses the KV. One that arrives later falls back to normal prefill. Because this TTL is fixed and not renewed, tune it to the expected time between turns to balance KV reuse against accelerator-memory usage. A natural next improvement is to extend the heartbeat-renewed lease to the decode side. A decode instance could then reclaim blocks as soon as a conversation goes idle rather than at the end of a fixed timer.

 KV recompute threshold

 KV reuse isn’t always faster than local recomputation. For a short reusable prefix, interconnect and coordination overhead can exceed the time needed to recompute the tokens. The kv_recompute_threshold setting, which defaults to 64 tokens, controls this decision. Prefill node recomputes when the token count to compute is below the threshold and pulls KV from decode node when it is at or above the threshold. Deployments can tune this value based on model computation time, KV size, and interconnect performance.

 Tensor q = FullyConnected(x, w.at("q_proj.weight"), w.at("q_proj.bias")); 
 Tensor k = FullyConnected(x, w.at("k_proj.weight"), w.at("k_proj.bias")); 
 Tensor v = FullyConnected(x, w.at("v_proj.weight"), w.at("v_proj.bias")); 
 // Split heads: [b, n, dim] -> [b, heads, n, d]. 
 q = Transpose(Reshape(q, {b, n, heads, d}), {0, 2, 1, 3}); 
 k = Transpose(Reshape(k, {b, n, heads, d}), {0, 2, 1, 3}); 
 v = Transpose(Reshape(v, {b, n, heads, d}), {0, 2, 1, 3}); 
 // softmax(q * k^T / sqrt(d)) * v, for all heads at once.

 // Merge heads: [b, heads, n, d] -> [b, n, dim], then project. 
 out = Reshape(Transpose(out, {0, 2, 1, 3}), {b, n, dim});

 NVIDIA CUDA Tile (cuTile) is a Python-based DSL and parallel programming model for NVIDIA GPUs that automatically leverages advanced hardware capabilities to deliver peak performance for tile-level GPU programming. By abstracting thread- and warp-level scheduling behind high-level, tile-centric primitives, cuTile enables you to write GPU kernels in Python while compiler optimizations automatically target advanced hardware features like Tensor Cores.

 As an early adopter of cuTile, machine learning engineers at Jane Street implemented Mamba-2, a state-of-the-art sequence model, in cuTile and partnered with NVIDIA to optimize the kernels. Jane Street is a deeply technical global trading firm, using deep learning to drive innovation in advanced quantitative research.  Overview and prerequisites 

 To use cuTile, ensure your environment meets the requirements outlined in the cuTile Python Quickstart guide. Import the package as cuda.tile and expose it as ct throughout the kernel implementations featured in this post.

 Sequence modeling computational trade-off 

 Sequence modeling architectures face a computational trade-off: traditional softmax attention trains rapidly using matrix multiplication accelerated by Tensor Cores, but at inference, compute and memory requirements increase linearly with sequence length. In contrast, recurrent neural networks (RNNs) suffer from slow, nonparallelizable training but require constant compute and fixed memory footprint regardless of sequence length.

 Mamba-2 architecture 

 The Mamba-2 architecture comes from a family of models aiming for the best of both worlds. Similar to an RNN, it has a fixed size hidden state and a recurrent update that can be computed chunkwise in a computationally efficient manner using Tensor Cores.

 The core recurrence of Mamba-2 is:

 \(h_t = \exp(A \cdot dt_t) h_{t-1} + dt_t B_t x_t\)

 y t = c t ⊤ h t + D x t y_t = c_t^\top h_t + D x_t 

 Where:

 \(x_t\), \(dt_t\), \(B_t\), and \(c_t\) are the inputs to the Mamba-2 layer (obtained by projecting the inputs to the block, like queries, keys and values in an attention layer) at token \(t\)

 \(y_t\) is the output at token \(t\)

 \(h_t\) is the fixed-size hidden state carried across tokens. It’s not a vector as in RNNs, but a matrix (more numbers and more representational capacity)

 \(A\) and \(D\) are learned model parameters

 Intuitively:

 \(dt_t\) (one scalar per head) represents how much of the state should be updated. All values in \(dt\) are negative Because the previous state is multiplied \(\exp(Adt_t)\), the state stays the same when \(dt_t = 0\) 

 \(x_t\) (a vector of size H) plays a role similar to the values in attention

 \(B_t\) (a vector of size S) plays a role similar to the keys in attention

 \(c_t\) (a vector of size S) is how the state is mixed to produce the outputs and plays a role similar to the queries in attention

 The state \(h_t\) is a matrix of size S,H (\(B_t x_t^\top\) is an outer product). To make computation easier to write, use \(a_t = Adt_t\) and call \(b_t\) the product \(dt_t B_t\). The equation is then simply:

 \(h_t = \exp(a_t)h_{t-1} + b_t x_t^{\mathsf{T}}, y_t = c_t^{\mathsf{T}}h_{t-1} + Dx_t\)

 This recurrent formulation is ideal for sequential inference. However, training and prefill require something faster than a for-loop. While the linear state update allows for a parallel scan algorithm, this approach requires materializing an enormous hidden state tensor making it primarily memory-bound and unable to utilize Tensor Cores.

 An alternative approach leverages Tensor Cores by computing any future hidden state directly through matrix multiplication. Ignoring the \(\exp(a_t)\) term for simplification, going from \(h_t\) to \(h_{t+T}\) is just:

 \(h_{t+T} = h_t + b_{t+1}x_{t+1}^{\mathsf{T}} + b_{t+2}x_{t+2}^{\mathsf{T}} + \cdots + b_{t+T}x_{t+T}^{\mathsf{T}}\)

 If building a matrix \(B\) of shape ( T, S ) by stacking all of the \(b_{t+i}\) and a matrix \(X\) of shape ( T, H ) by stacking all of the \(x_{t+i}\) then this is just \(h_{t+T} = h_t + BX^T\):

 Quality, performance, and efficiency
 Delegating the internals of post-training infrastructure can be a daunting decision. Our team has first-hand experience catching silent bugs in complex machine learning systems, from pushing the frontier of RL research to training LLMs that have served millions of users. We understand that the best training stack is the one that gets you the best model , and building such infrastructure demands careful implementation and co-design across all components.
 For these reasons, we prioritized quality of output models as our north star in the development of the service. One notorious example of issues affecting RL results is the alignment between training and inference engines: if the same model weights produce slightly different outputs due to mismatching numerics, the whole run might underperform or even collapse. We eliminate numerous sources of policy drift across training and inference, using both standard techniques like Rollout Routing Replay and advanced optimizations driven by our research in training stability.
 Beyond model quality, we also work to make each run as fast and as efficient as possible, because post-training requires multiple iterations: the sooner a run finishes and the less it costs, the more ideas you get to test. Most of the time in RL is spent on generating rollouts, which allows us to capitalize on years of research and engineering behind Together’s inference products. Our rollout engines draw on the same optimizations as our serving stack. For multi-turn agents, intelligent caching and routing minimize redundant computations while keeping memory costs bounded. On the training side, optimized parallelism and sequence packing speed up both SFT and RL steps.
 With Together Post-Training, you size each experiment to what it needs and do not pay more. If your experiment is bottlenecked by rollout concurrency, you can request the exact number of sampler replicas. Several LoRA experiments can share one model resource, so running a sweep doesn’t mean reserving more GPUs for every setup. We bill every model resource per GPU-minute, yet thanks to many optimizations of our dedicated and multi-LoRA serving stacks, the overall costs of training drop below token-based pricing as soon as you scale up the experiments.
 Optimized deployment after training
 When the post-training experiments are finished, it might be important to run each resulting model side by side to compare their outputs. We now support multi-LoRA adapter serving in Dedicated Model Inference: instead of starting a separate production deployment for each run, you can swap the adapters at your convenience in a single GPU deployment, helping you lower the serving costs.

 Lastly, converting the model to run at the highest throughput in production means it potentially executes in lower precision, in a different hardware configuration, and with different kernels compared to rollout generation. Through a combination of algorithmic and systems improvements, we ensure that each training checkpoint retains the quality in serving, even after switching from multi-LoRA sampling to a fully performant merged inference in FP4 precision .
 Getting started
 To begin your first post-training experiments, install the latest Together SDK and read the docs . We also provide a selection of cookbooks that can help you get started with Together Post-Training, which are available at github.com/togethercomputer/post-training-cookbook . These cookbooks provide examples of training with GRPO on a standard GSM8K benchmark, implementing DPO as a custom loss, or training multiple LoRA adapters within the same model resource. If you already have a setup that uses post-training services such as Tinker API, we also offer a simple way to migrate from them. You can replace one line in your scripts, and everything else can stay the same:
 -import tinker
+import together.post_training.tinker as tinker 
 Read our Tinker migration guide to learn more.
