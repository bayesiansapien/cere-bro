## Model Architecture

**Architecture Type:** Transformer.<br>
**Network Architecture:** InternVideo2-CLIP-L14 vision encoder with a frozen, unmodified Apple MobileCLIP-B-LT text encoder and a shared 512-dimensional embedding space.<br>
**Base Model:** OpenGVLab InternVideo2-CLIP-L14.<br>
**Number of model parameters:** Approximately **3.7 × 10^8** (373,342,467, of which 589,824 are LoRA parameters); excludes the preservation teacher and optimizer state.

The vision transformer has 24 blocks, 14-pixel spatial patches, a hidden width of 1,024, and 16 attention heads. A visual projection and alignment layer map video features to the text embedding space. The text tower remains frozen during this fine-tune. LoRA targets the `qkv` and `proj` modules in the last 12 vision blocks, with rank 8, alpha 16, and dropout 0.05.

The training recipe uses video-text contrastive loss, preservation regularization, bfloat16 (BF16) precision, and AdamW (learning rate 1e-3, cosine schedule, 100 warmup steps) with an effective batch of 64. Training started from the base weights, and the released checkpoint was selected on the validation set described below. The fine-tune was run with the TAO `video_clip` `train` subtask; the experiment-specification format and these recipe fields are documented in the [TAO training guide](https://docs.nvidia.com/tao/tao-toolkit/latest/text/embedding/video_clip/training.html#training-the-model). These training details do not specify deployment hardware requirements.

## Model Introduction

**Hy-Nomas** is a video world generation model that supports free-form, multi-turn interaction through text instructions and camera control. It generates a world one video segment at a time, allowing users to introduce objects, change styles and scenes, describe actions, or control the camera as generation continues.

The model combines a segment-autoregressive diffusion transformer (DiT), a Qwen text encoder, camera-conditioning modules, and a PixelUMM video decoder. A persistent key/value (KV) cache carries context between segments. This directory provides the distilled model in **BF16 Diffusers format**. The example below uses **4 denoising steps**, with **704 × 1280** output at **24 FPS**.

## Key Features

- **Free-form interaction:** Guide successive segments with instructions about subjects, actions, appearance, style, and environment.
- **Camera control:** Supply camera trajectories alongside text to control viewpoint and movement.
- **Continuous generation:** Reuse earlier context through a KV cache when extending the same world.
- **Distilled inference:** Generate each segment with 4 DiT denoising steps in the example below and decode its latents with a fine-tuned PixelUMM decoder.
- **Diffusers integration:** Load the bundled transformer, text encoder, tokenizer, scheduler, and decoder with `HyNomasModularPipeline`.

## Hy-Nomas-Bench

We also release **[Hy-Nomas-Bench](https://huggingface.co/datasets/tencent/Hy-Nomas-Bench)**, a suite of four benchmarks with **280 test cases** covering multi-turn free-form text interaction, camera navigation, interleaved text and camera control, and spatial memory. It evaluates interactive controllability and consistency during continuous world generation, providing structured prompts, interaction sequences, keyboard timelines, and reference camera trajectories. See the [Hy-Nomas-Bench dataset repository](https://huggingface.co/datasets/tencent/Hy-Nomas-Bench) for downloads, data formats, and inference instructions.

## Model Architecture

Hy-Nomas performs diffusion in a compressed video latent space and autoregression across video segments. Text, camera motion, and cached history condition the generation of each new segment.

![Hy-Nomas framework: structured prompts, video latents, and camera trajectories feed dual-stream MMDiT blocks with segment-wise causal joint attention, timestep modulation, camera cross-attention, and a persistent KV cache.](assets/method_framework_h.png)

*Hy-Nomas framework. The inference configuration uses 54 dual-stream MMDiT blocks (N = 54). Purple, blue, and green indicate the text, video, and camera paths, respectively.*

The figure's video-encoder path illustrates how video is represented as DCAE-V latents. In the text-to-video inference flow below, each new segment starts from Gaussian noise in that latent space and uses the KV cache for generated history. The MLLM is the Qwen text encoder, and the default video decoder is the fine-tuned PixelUMM described below.

### Text and Camera Conditioning

**Text conditioning.** The text encoder uses the language-model component of **Qwen/Qwen2.5-VL-7B-Instruct**. Its 3,584-dimensional hidden states pass through a two-layer token refiner and are projected into the DiT's 2,048-dimensional hidden space. Segment-specific prompts let users change the requested content as generation proceeds.

**Online prompt enhancement.** The original web demo uses **Nomas-PE**, a separate service that converts user instructions into structured generation prompts. This Diffusers pipeline accepts plain text or prepared structured prompts directly and does not run Nomas-PE.

**Camera conditioning.** The inference configuration uses `extrinsics_attn`. Normalized 4 × 4 camera extrinsic matrices are grouped over four video frames and flattened into 64-dimensional inputs, aligning camera features with the temporal compression of the video latents. Learned pose embeddings and projections implement the figure's **Pose Encoder → Camera Proj** path. At each double-stream block, video tokens query the projected camera features through cross-attention after the video MLP. With `per_chunk_camera_attn=true` and `camera_chunk_size=1`, camera attention is aligned to individual latent frames.

### Segment-Autoregressive Diffusion Transformer

The generation backbone is a **dense multimodal diffusion transformer (MMDiT)**. Video latents enter through **Patch Embed**, while refined text tokens enter a separate stream. The **Timestep Embed** supplies noise-level conditioning: each block uses it to modulate the two streams with learned shifts, scales, and residual gates.

Within a block, text and video interact through **segment-wise causal joint attention**, with 3D RoPE encoding video positions and the layer's KV cache supplying context from earlier segments. The two streams then pass through separate MLPs. **Camera cross-attention** updates the video branch using video queries and camera keys/values. Text features continue to the next block; after the last block, the output head uses only the video stream to predict latent-space flow velocity. The sampler uses these predictions to denoise the segment before video decoding.

The model architecture is illustrated in the following table:

| Property | Configuration |
|:---|:---|
| Model identifier | `Hy-Nomas` |
| Transformer blocks | 54 double-stream blocks; 0 single-stream blocks |
| Hidden size | 2,048 |
| Attention heads | 16 heads; 128 dimensions per head |
| Feed-forward expansion | 4×; intermediate size 8,192 |
| Latent input / output channels | 32 / 32 |
| Latent patch size, time × height × width | 1 × 1 × 1 |
| Position encoding | 3D RoPE; temporal/height/width dimensions `[16, 56, 56]`; theta 256 |
| Text conditioning | 3,584-dimensional Qwen features; two-layer token refiner |
| Camera conditioning | Extrinsic embeddings with cross-attention in the double-stream blocks |
| Denoising prediction | Flow velocity; Euler ODE sampling in the inference configuration |

At each turn, the DiT denoises the current segment while attending to all past KV cache and the current conditioning. Attention is causal across segments, so future segments are not required to generate the current one. Cached attention keys and values are reused when generation advances to the next segment.

The Diffusers pipeline retains the attention KV cache across segments. Continued generation can reuse the state returned by an earlier call; the usage guide below describes this workflow.

### Video Latents and PixelUMM Decoder

Hy-Nomas uses **DCAE-V `f32t4c32` latents**: 32 channels, 32× spatial compression in each dimension, and 4× temporal compression. The DiT produces latents in this representation. The default inference pipeline decodes them with a **fine-tuned PixelUMM decoder**.

The decoder uses a transformer with **36 layers**, a **4,096-dimensional hidden size**, **32 query heads**, and **8 KV heads**. It conditions pixel reconstruction on the generated DCAE-V latents and processes RGB video in 4 × 16 × 16 tubelets. The configuration uses **one PixelUMM decoding step**, with temporal windows of 10 latent frames and an overlap of 5 latent frames. This decoding step is separate from the DiT's 4 denoising steps in the example below.

Architecture values are specified in the [DiT model definitions](https://github.com/Tencent-Hunyuan/Hy-Nomas/blob/HEAD/hymm/models/dit/modules/__init__.py), [DiT implementation](https://github.com/Tencent-Hunyuan/Hy-Nomas/blob/HEAD/hymm/models/dit/nomas_cpt.py), [PixelUMM implementation](https://github.com/Tencent-Hunyuan/Hy-Nomas/blob/HEAD/hymm/models/vae/pixelumm_decoder/model.py), and [inference configuration](https://github.com/Tencent-Hunyuan/Hy-Nomas/blob/HEAD/configs/experiment/inference.yaml).

 Multi-Turn Reinforcement Learning on Amazon SageMaker AI: A hands-on guide

 Most fine-tuning teaches a model to produce a better answer to a single prompt. Agentic tasks are different. An agent that files an expense report or triages a support ticket takes a sequence of actions, and each step depends on what came before. There’s rarely one correct sequence to imitate, and the only reliable feedback is whether the whole sequence succeeded. Supervised fine-tuning has no labels for that, and single-turn reinforcement learning cannot credit a decision made three steps before the outcome.

 Multi-Turn Reinforcement Learning (MTRL) on Amazon SageMaker AI trains models on exactly that signal. SageMaker AI sends prompts to an agent you host on Amazon Bedrock AgentCore, or on your own infrastructure, such as Amazon Elastic Kubernetes Service (Amazon EKS), Amazon Elastic Compute Cloud (Amazon EC2), or AWS Fargate, through an AWS Lambda forwarder . The example here uses AgentCore. The agent calls the policy model being trained, acts in your environment over as many turns as the task needs, and reports one reward when the episode ends. You don’t specify the right trajectory, only how to score the result.

 This post uses Wordle , a game in which a player has six tries to guess a hidden five-letter word, as the example. After each guess, every letter turns green if it is in the right position, yellow if it’s in the word but in a different position, and gray if it isn’t in the word. The game suits MTRL because the rules are few, each guess depends on the feedback from the last, and the outcome is scored objectively. Wordle is a teaching example, and frontier models already play it well. In practice, you would use MTRL to make a small, low-cost model good at a multi-step task specific to your business, such as an internal workflow that public models were never trained on. The same pipeline applies to that setting.

 In our run, MTRL took gpt-oss-20b from a 61 to an 84 percent solve rate on held-out words at its default reasoning effort, and from 15 to 69 percent at the low effort it trained at, for about $339 in training tokens. In this post, we walk through the pipeline end-to-end: deploying the agent and reward to AgentCore, preparing the dataset, training, monitoring in MLflow, and evaluating at serving settings. We also share the reward-design mistakes and training failures we hit. Your datasets, agent, and trained model stay in your AWS account and are not used to train the base models . All code is in the accompanying aws-samples repository .

 Solution overview

 The system has two halves. SageMaker AI owns the training job and the policy model. AgentCore hosts the agent, the Wordle environment, and the reward function. The following diagram shows how they connect.

 Figure 1: MTRL on SageMaker AI, where the training job invokes the AgentCore-hosted agent once per rollout to sample the policy model, play the game, and report a reward

 For every rollout, the MTRL service invokes the AgentCore runtime, a capability of Amazon Bedrock AgentCore, with one training row, which holds one secret word. A Strands agent in the runtime calls the policy model through the SageMaker Job Runtime’s OpenAI-compatible endpoint. The model plays up to six guesses through one tool, guess_word , and after each guess the environment returns per-letter feedback and a summary of what is known. When the game ends, the agent returns one reward. Group Relative Policy Optimization (GRPO) uses the spread of rewards across several rollouts of the same word to update a Low-Rank Adaptation ( LoRA ) adapter on the policy model.

 Three design points matter for what follows:

 The agent and reward live in one place. A single Python file deployed to AgentCore holds the environment, the tool, and the scoring function.

 The dataset carries only the secret word. The word lists bundled with the agent are built from the open-source SCOWL word lists and are used only for scoring.

 The reward is outcome-dominant. A solve pays 1.05–1.55 depending on speed, a loss pays -0.5, and never making a valid guess pays -1.5. A small shaping term rewards good strategy within each tier.

 Orchestrating SageMaker AI endpoint auto scaling with AWS CDK

 Updating the Amazon Sagemaker AI real-time endpoint configuration (changing the instance type, instance count, or environment variables) causes deployments through AWS CloudFormation or the AWS Cloud Development Kit (AWS CDK) to fail. SageMaker AI requires you to deregister the scalable target before updating the endpoint, but when you deregister it, CloudFormation can’t track the AWS Application Auto Scaling resources.

 In this post, we show you how to use a reusable CDK construct with AWS CloudFormation custom resources to orchestrate deregister and register auto scaling automatically during endpoint updates. You can update your endpoint configuration and auto scaling parameters in a single deployment without manual intervention.

 Why this problem occurs

 When you deploy a SageMaker AI endpoint with native CloudFormation auto scaling resources, then change the endpoint configuration and redeploy, several failure modes emerge. The specific failure depends on what you change and how you work around the issue.

 Changing the endpoint configuration with auto scaling registered

 CloudFormation tries to update the endpoint while the scalable target is still registered. SageMaker AI rejects the update with the following error:

 The variant(s) "[AllTraffic]" must be deregistered as scalable targets with Application Auto Scaling before they can be removed or have their instance type updated. 

 SageMaker AI blocks the endpoint update before CloudFormation reaches the auto scaling resources.

 Manually deregistering auto scaling, then changing only the endpoint configuration

 If you deregister the scalable target through the AWS Command Line Interface (AWS CLI) and redeploy with only an endpoint configuration change, the deployment succeeds. However, CloudFormation doesn’t register auto scaling even though it is in the CloudFormation template. Because the auto scaling parameters in the CloudFormation template haven’t changed, CloudFormation doesn’t register the scalable target or re-apply the scaling policy. The endpoint is now running without auto scaling, and there is no error to indicate anything went wrong.

 Manually deregistering auto scaling, then changing auto scaling parameters

 If you deregister the scalable target through the AWS CLI and redeploy with auto scaling parameter changes, CloudFormation tries to update the ScalableTarget resource that no longer exists:

 Resource of type 'AWS::ApplicationAutoScaling::ScalableTarget' with identifier 'endpoint/<name>/variant/AllTraffic|sagemaker:variant:DesiredInstanceCount|sagemaker' was not found. 

 This failure is notable because the rollback also fails (UPDATE_ROLLBACK_FAILED), leaving the stack in a broken state that requires manual intervention in the CloudFormation console to recover.

 Solution overview

 You can use this CDK construct to replace the native AWS::ApplicationAutoScaling::ScalableTarget and AWS::ApplicationAutoScaling::ScalingPolicy CloudFormation resources with three custom resources. These custom resources deregister and register auto scaling around the endpoint update with explicit dependency ordering, enforced by node.add_dependency calls in CDK. The full sequence is:

 Deregister (custom resource): Removes the scalable target before the endpoint update begins. On first deploy, no scalable target exists yet, so the handler handles the error gracefully and continues.

 Endpoint update (CDK-managed): CDK updates the endpoint resource normally, swapping to the new endpoint configuration.

 Register Scalable Target (custom resource): Waits for the endpoint to reach InService status, then registers the scalable target.

 Attach Scaling Policy (custom resource): Waits for the scalable target to be queryable, then applies the target tracking policy.

 Figure 1: Custom resource orchestration of SageMaker AI endpoint auto scaling around a CDK-managed endpoint update.

 Register Scalable Target and Attach Scaling Policy use the CDK provider’s asynchronous completion pattern. Each custom resource has an on_event handler that returns immediately and an is_complete handler. The provider’s waiter re-invokes the is_complete handler on an interval (every 30 seconds) until its readiness check passes. The provider’s total_timeout (1 hour for Register Scalable Target, 15 minutes for Attach Scaling Policy) bounds the wait, so it isn’t limited by the timeout of any single Lambda invocation.

 A ConfigHash property on each custom resource forces CloudFormation to re-invoke the Lambda functions whenever a configuration value changes. The endpoint configuration and auto scaling parameters are defined together because a single ConfigHash drives the auto scaling orchestration.

 While the construct defines three custom resources, the deployed stack contains more than three Lambda functions. Each custom resource is backed by a CDK cr.Provider , and the provider framework generates its own helper Lambda functions. A synchronous provider (Deregister) adds one framework function. An asynchronous provider (Register Scalable Target and Attach Scaling Policy) adds three ( onEvent , isComplete , and onTimeout ) plus an AWS Step Functions state machine that drives the waiter. As a result, the deployed stack contains three custom resources, two Step Functions state machines, and twelve Lambda functions. Five of the resources hold the construct’s own handler code (one for Deregister, and an on_event and is_complete pair for each asynchronous resource), with the remaining seven generated by the provider framework. You don’t write or maintain the framework-generated functions, but they are present in the stack and worth accounting for when you review the deployed resources.

 Five design decisions on the path to production

 The Unified Operations TAM and DSE took part in the following decisions as members of the working team, not as an escalation point after the fact. That let Bayer test each design against AWS service behavior before committing to it, while keeping ownership of the architecture and the final call.

 1. Externalize orchestration state without treating the runtime as stateless

 AgentCore runtime provides isolated sessions that preserve execution context across invocations within a session’s lifecycle. That context isn’t a durable store for a multi-step workflow. ADE writes LangGraph checkpoints to DynamoDB so the graph can resume after scale-out events, restarts, or session boundaries without depending on one execution environment remaining available.

 Principle: Use the runtime session for active execution, and persist the state required to resume or reconstruct the workflow in a durable service.

 2. Separate enterprise identity, gateway access, and downstream authorization

 Bayer standardizes on Microsoft Entra ID for user identity, while ADE’s services authorize each other with AWS-native mechanisms. Rather than force one token across every trust boundary, the team gave each boundary its own mechanism.

 Entra ID remains the source of user identity. AWS Identity and Access Management (IAM) authorizes service-to-service calls. AgentCore Gateway outbound authorization handles access to downstream CDE services. A request interceptor AWS Lambda function performs custom validation and passes the authorization attributes that downstream tools require. The team worked through the token contract at each hop with the DSE.

 Principle: Identity failures in agent systems cluster at the transitions between user identity, agent identity, and tool identity. Define the issuer, audience, claims, scopes, and credential lifetime at every hop instead of reusing a token that is valid for one boundary at the next.

 3. Treat model selection as an interface contract

 During the build, the team evaluated a newer model version with reasoning mode enabled. For that version, the combination of tool use and structured output that ADE depends on was not compatible with how its agents were implemented. The DSE confirmed the constraint, and the team retained the current model for the release.

 Principle: For tool-using agents, model choice is constrained by the full interface: tool calling, structured output, streaming behavior, reasoning features, latency, quota availability, and model-specific request semantics. A newer model is not automatically a drop-in replacement.

 4. Control the tool surface before it controls the prompt

 CDE manages more than 500 model configurations. A dedicated MCP server per API would have added deployment, authentication, and version management overhead. ADE instead registers OpenAPI specifications with AgentCore Gateway, which exposes the REST operations as MCP tools. Adding or changing an API becomes a schema and gateway configuration change instead of a new server deployment.

 Tool schemas and descriptions also consume input tokens and compete with the user’s request and retrieved context. ADE scopes tools by specialist agent instead of giving every agent the full catalog.  Designing the Global Performance Tuner feature in TensorRT 

 The central design idea of the Global Performance Tuner is to represent alternative scheduling strategies as explicit and searchable build routes. A compiler knob (also called a compiler flag or compiler option) is a configuration setting that changes some aspect of the compilation pipeline, such as a heuristic, fusion decision, or code generation path.

 Each tunable knob exposes a finite set of allowed values and has a default value. A build route is a concrete combination of knob values. When no build route is specified, TensorRT uses the default build route, in which every knob retains its default value.

 Consider a hypothetical compiler consisting of three passes, \(f_1\), \(f_2\), and \(f_3\). Suppose a binary knob \(p\) controls the fusion strategy used by \(f_2\): when \(p=1\), the pass applies horizontal fusion; when \(p=0\), it applies vertical fusion:

 \(f_2(s) = \begin{cases} f’_2(s), & \text{if } p = 1 \\ f”_2(s), & \text{if } p = 0 \end{cases}\)

 The two possible values of \(p\) define two build routes and therefore produce a candidate solution set of size two for the input model \(m\):

 \(B(m) = \{f_3(f’_2(f_1(m))),\, f_3(f”_2(f_1(m)))\}\)

 Neither fusion strategy is universally better. Horizontal fusion may produce the faster engine for one model, while vertical fusion may be more effective for another. The result may also change across tensor shapes and target GPUs, even when the model itself remains unchanged. Selecting the better route therefore requires building both candidate engines and comparing their end-to-end performance.

 Even this two-route example captures the essential idea of tuning: the compiler exposes meaningful scheduling alternatives, and measured behavior determines which complete solution performs best for the deployment case at hand.

 In the mathematical framework introduced earlier, a build route is a composition of compiler passes. In the implementation, a combination of knob assignments provides a compact specification of that route. Changing one or more knob values changes how the model travels through the tunable parts of the compilation pipeline. Within this abstraction, a knob combination can be treated as identifying a build route.

 More precisely, the knob combination is a build-route specification, not a complete description of the resulting engine. TensorRT still performs the remaining stages of engine construction, including tactic selection, and may reconcile individual knob values with constraints imposed by the network. The route specifies the requested choices within the tunable configuration space. It does not replace the rest of the TensorRT builder.

 TensorRT exposes a compact API surface around two fundamental capabilities:

 Apply and inspect one build route : A setter applies a fixed route to the builder configuration, while the corresponding getter returns the currently specified route.

 Discover the tunable configuration space : A separate getter describes the available knobs, their allowed values, their defaults, and their purposes.

 The corresponding C++ APIs are:

char const* IBuilderConfig::getBuildRoute() const;
char const* IBuilderConfig::getAllBuildRoutes() const;

 You can use these APIs to implement custom tuners. A sample C++ implementation is also provided in trtexec .

 At a high level, trtexec organizes tuning as follows:

 When a user specifies an input model and a regex-like tunable build route expression, trtexec will expand the expression into a list of concrete build routes according to the searching algorithm.

 There will be a loop to traverse all fixed build routes. In each iteration, the model will be built with that single build route, then accuracy and performance will be measured during each iteration.

 All build routes that crash during building or fail accuracy during inference are excluded from best-engine selection. The engine with the best measured end-to-end performance is selected.

 Deploying a trained neural network involves more than translating each operator into a GPU kernel. It is a compilation problem with many legitimate answers. For example, when NVIDIA TensorRT builds an engine, it makes interdependent decisions about graph-IR transformations, fusion, implementation selection, memory placement, and quantization. This process is called scheduling. Different scheduling choices can preserve model semantics yet produce very different inference performance, making scheduling central to deep learning compiler optimization.

 No single scheduling strategy is best for every model and deployment environment. A transformation that accelerates one network may slow another. A kernel that is faster in isolation may interact poorly with fusion, tensor layouts, or memory traffic elsewhere in the graph. Aggressive scheduling may improve performance while violating an application’s accuracy requirement. These coupled, model-dependent effects often appear only after the complete engine is built and measured, making the right strategy increasingly difficult to predict.

 This post is Part 1 of a two-part series that is intended to develop a clearer way of reasoning about performance optimization. It explores questions such as: What makes one compiled engine better than another? Why can individually promising decisions fail end to end? How should accuracy constrain performance optimization? It introduces the Global Performance Tuner , a feature for automatic performance tuning released in TensorRT 11.1 , and explores these questions through an intuitive example and mathematical framework.

 What challenge does the Global Performance Tuner feature solve? 

 The following analogy illustrates the motivation for building the Global Performance Tuner feature in TensorRT.

 Imagine a chef with one excellent dish that has pleased three regular customers for years. One likes spice, another sweet-and-sour flavors, and the third extra salt. The chef combines chili, syrup, lemon, and salt in one standard recipe that satisfies all three. One day, a new fourth customer arrives who dislikes spice. Keeping the chili disappoints the newcomer; removing it risks losing the first customer.

 The root cause of the chef’s dilemma is the method of adding the seasonings does not scale out: the number of interacting exceptions grows with the customer base, and a change for one customer can degrade the meal for another.

 Figure 1. One fixed recipe does not scale to conflicting customer preferences 

 A scalable approach keeps the base dish but makes the seasonings configurable. The chef records an appropriate combination for each regular customer. For a new customer with unknown preferences, the chef offers free samples with different combinations, rejects unsuitable variations, and keeps the one the customer likes best.

 Figure 2. Customize the flavor for each customer 

 Mapping this analogy to deep learning compilation, TensorRT is the chef, its shared pipeline the base recipe, tunable compiler configurations the seasonings, and the compiled engine the finished dish. Each ONNX model is a customer. Performance tuning offers samples, and end-to-end performance reflects customer satisfaction.

 Historically, TensorRT performance optimization has started with internal KPI models. Engineers study these workloads, identify optimizable patterns, and encode their findings as heuristics in the TensorRT default scheduling strategy. Each heuristic captures expert knowledge and allows users to benefit automatically from optimizations discovered on representative models.

 As models and deployment environments diversify, this approach leads to a scaling problem similar to the one described in the analogy. A heuristic inspired by one internal KPI model joins the shared strategy and may help familiar patterns while causing a regression for an unseen external model. Adding another check or exception may protect that model, but repeating the process makes the scheduling logic increasingly difficult to extend.

 The problem appears in three related forms:

 H euristic sprawl: Each new model-specific heuristic introduces another rule whose interactions with existing rules must be understood and maintained. As these rules accumulate, the code becomes unmaintainable, and improvements for one family of models can unintentionally affect another.

 Performance-accuracy entanglement: Reduced-precision kernels and other aggressive optimizations can improve performance while introducing numerical differences that exceed an application’s acceptable tolerance. Higher-precision choices may reduce that risk but sacrifice performance. Performance and numerical acceptability therefore cannot always be optimized independently.

 Performance customization: Scheduling choices that work well for one model or GPU may not work well for another. Encoding every successful choice into one universal scheduling strategy makes it difficult to specialize TensorRT efficiently for a continually expanding range of external models, hardware platforms, and application requirements.

 Tuning provides a scalable complement to heuristic optimization.

 Mathematical theory for deep learning compiler performance 

 This section develops an abstract mathematical model of deep learning compiler performance. The purpose is to separate two fundamental questions:

 What executables a compiler can construct for a model

 How the compiler selects one from those possibilities for optimal performance

 Concept: Model, model space 

 Let \(m\) represent a model and \(M\) represent the collection of all models under consideration, called the model space:

 \(m \in M\)

 Here, a model is an abstract description of the computation to be compiled. Its concrete representation may be an ONNX graph, a network created through the TensorRT API, a PyTorch model, or another frontend representation that fully specifies the model computation.

 Concept: Solution, solution space 

 Given a model \(m\) as input, a deep learning compiler constructs an executable output for the target hardware, defined as a solution. The same model can generally be compiled into different solutions under different scheduling policies. Let \(s\) represent one such solution, and let \(S\) represent the collection of possible solutions, called the solution space.

 s ∈ S = { s 0 , s 1 , s 2 , . . . , s n } s \in S = \{s_0, s_1, s_2, …, s_n\} 

 A solution is an abstraction of executable computation on the target hardware. Concretely, a solution may be a TensorRT engine or a cubin of serialized sequence of GPU kernels. More abstractly, it may also be a compiler’s intermediate representation (IR), provided that the representation uniquely determines the final executable under the remaining compilation process.

 Each solution also defines a function from the model’s input domain to its output codomain:

 \(s : X \rightarrow Y\)

 \(s(x) = y\)

 Here, \((x,y)\) is an input-output pair for the sequence of GPU kernels that implements the neural network. At this level of abstraction, the model describes the intended computation, while a solution describes one particular way of realizing that computation on the target hardware.

 Principle of determinism 

 Statement: When both a deterministic program and its complete execution environment remain fixed, the program has a fixed underlying run time.

 This principle serves as a modeling assumption for performance analysis.
