# d1-Omni-2B-GGUF

GGUF version of [d1-Omni-2B](https://huggingface.co/LiquidAI/d1-Omni-2B) for local inference on CPUs and GPUs.

d1-Omni-2B is a decision model for text, pictures, and audio, built on [LFM3-Omni-2B](https://huggingface.co/LiquidAI/LFM3-Omni-2B). It returns calibrated answers in one forward pass, without generating tokens.

Find architecture and usage details in the [original model card](https://huggingface.co/LiquidAI/d1-Omni-2B).

## Use with llama.cpp
<hr style="margin: -0.7em 0 1.2em 0; border: 0; border-top: 1px solid rgba(127, 127, 127, 0.3);" />

> [!WARNING]
> Support for d1-Omni-2B in [llama.cpp](https://github.com/ggml-org/llama.cpp) is pending the merge of [ggml-org/llama.cpp#31275](https://github.com/ggml-org/llama.cpp/pull/31275). Until it is merged and released, build llama.cpp from that pull request.

llama.cpp answers `noul`, `choice` and `score` questions over text, JSON, pictures and audio clips, and spoken questions. Multiple choice (`"multiple": true`), extraction, estimates and boxes are not supported yet.

'''bash
llama-server -hf LiquidAI/d1-Omni-2B-GGUF:Q8_0 -b 8192 -ub 8192
'''

A question is read in one batch, so `-b` and `-ub` must hold its state and media. A picture takes at most half of `-ub`: 8192 keeps the full budget of 4096 tokens per picture, smaller values lower it.

Then send questions to the `/v1/systemone` endpoint.

### Text

'''bash
curl http://127.0.0.1:8080/v1/systemone -H "Content-Type: application/json" -d '{
  "state": "I was charged twice this month, please refund one of them.",
  "questions": {
    "refund":  {"type": "noul", "instructions": "Is the customer asking for a refund?"},
    "team":    {"type": "choice", "instructions": "Which team should handle this?",
                "criteria": {"billing": "Charges, refunds, invoices", "technical": "App or site faults",
                             "fraud": "Suspected unauthorised use"}},
    "urgency": {"type": "score", "instructions": "How urgent is this?",
                "criteria": ["Can wait", "Today", "Blocking the customer now"]}
  }
}'
'''

### Image + Text

'''bash
curl -sL -o cats.jpg http://images.cocodataset.org/val2017/000000039769.jpg  # two cats on a sofa

curl http://127.0.0.1:8080/v1/systemone -H "Content-Type: application/json" -d @- <<JSON
{
  "state": "Photo attached to a pet-sitting request.",
  "images": ["data:image/jpeg;base64,$(base64 < cats.jpg | tr -d '\n')"],
  "questions": {
    "pet":  {"type": "choice", "instructions": "Which animals are in the photo?",
             "criteria": {"cats": "Cats", "dogs": "Dogs", "birds": "Birds"}},
    "sofa": {"type": "noul", "instructions": "Are the animals on a sofa?"}
  }
}
JSON
'''

### Audio + Text

'''bash
curl -sL -o jfk.wav https://github.com/ggml-org/whisper.cpp/raw/master/samples/jfk.wav

curl http://127.0.0.1:8080/v1/systemone -H "Content-Type: application/json" -d @- <<JSON
{
  "state": "Recording from a public event.",
  "files": ["data:audio/wav;base64,$(base64 < jfk.wav | tr -d '\n')"],
  "questions": {
    "kind": {"type": "choice", "instructions": "What kind of utterance is this?",
             "criteria": {"request": "A request to do something",
                          "question": "A question asking for information",
                          "speech": "A speech to an audience"}},
    "calm": {"type": "score", "instructions": "How calm is the speaker?",
             "criteria": ["Agitated", "Neutral", "Calm"]}
  }
}
JSON
'''

### Spoken question

A question can be spoken: its `instructions` are an `input_audio` part.

'''bash
curl http://127.0.0.1:8080/v1/systemone -H "Content-Type: application/json" -d @- <<JSON
{
  "state": "I was charged twice this month, please refund one of them.",
  "questions": {
    "refund": {"type": "noul",
               "instructions": {"type": "input_audio", "input_audio": {"data": "$(base64 < question.wav | tr -d '\n')", "format": "wav"}}}
  }
}
JSON
'''

The state can be `null` when the pictures or the audio are the whole state.

# LFM3-Omni-2B-MLX-4bit

4-bit MLX version of [LFM3-Omni-2B](https://huggingface.co/LiquidAI/LFM3-Omni-2B) for Apple Silicon. The weights take 1.96 GB, plus 0.15 GB for the audio codec in `audio_tokenizer/`.

The language backbone uses 4-bit affine quantization with groups of 64, except for the token embedding (also the output layer) and the value and feed-forward down projections in the layers that llama.cpp's Q4_K_M upgrades, which use 6 bits. The vision tower and projector, the audio encoder and projector, the depth decoder and the audio codec in `audio_tokenizer/` stay in BF16. It is the smallest variant and loses some accuracy, so [8-bit](https://huggingface.co/LiquidAI/LFM3-Omni-2B-MLX-8bit) is the recommended trade-off.

Find architecture and usage details in the [original model card](https://huggingface.co/LiquidAI/LFM3-Omni-2B).

## Use with MLX-VLM
<hr style="margin: -0.7em 0 1.2em 0; border: 0; border-top: 1px solid rgba(127, 127, 127, 0.3);" />

Support for LFM3-Omni in [MLX-VLM](https://github.com/Blaizzy/mlx-vlm) is in progress. We will update this card when an MLX-VLM release supports it.

'''bash
# Speech recognition
python -m mlx_vlm.generate --model LiquidAI/LFM3-Omni-2B-MLX-4bit --temperature 0 \
  --system "Perform ASR in English." --prompt "" --audio speech.wav

# Text to speech (24 kHz WAV)
python -m mlx_vlm.generate --model LiquidAI/LFM3-Omni-2B-MLX-4bit \
  --system "Perform TTS in American English using a female voice." \
  --prompt "The quick brown fox jumps over the lazy dog." \
  --output-modality audio --output tts.wav

# Image question
python -m mlx_vlm.generate --model LiquidAI/LFM3-Omni-2B-MLX-4bit --temperature 0 \
  --system "Answer questions about the provided image. Base every answer only on what can be seen. Respond with text." \
  --image image.png --prompt "What does the sign say?"
'''

Text answers use greedy decoding (`--temperature 0`). Speech output samples with `audio_temperature=0.4` and `audio_repetition_penalty=1.2` by default. The original model card lists the voices, languages and other system prompts. More options in the [MLX guide](https://docs.liquid.ai/deployment/on-device/mlx).

 Many AI workloads need only a fraction of a GPU. Giving each one an entire device can leave capacity idle; sharing GPUs lets platform teams serve more workloads with the infrastructure they already have.

 NVIDIA GPUs already support several approaches to sharing. Multi-instance GPU (MIG) splits a GPU into hardware-isolated instances that are transparent to the application, time-slicing lets several processes take turns without memory enforcement, and Multi-Process Service (MPS) lets them run concurrently in separate address spaces (sm-sharing).

 CUDA 13.4 now enforces a memory boundary that is transparent to the application with a new time-sharing mode, alongside the compute sharing mode (sm-sharing) that already existed in MPS. 

 Here is what the CUDA release brings:

 An exact memory amount: A workload asks for a memory size and CUDA holds it there. An allocation above that size fails, just as it would on a smaller GPU.

 A range: A workload gets a guaranteed minimum plus a maximum it can grow into when memory is free.

 A compute mode: Each workload can choose to use its compute in an sm-sharing mode rather than using the default time-sharing mode. 

 A transparent memory limit: Each workload sees only a fraction of the GPU memory.

 The missing piece: Getting there from Kubernetes 

 CUDA provides the memory enforcement capability, but a Kubernetes cluster can’t use it on its own. On every GPU node, something has to:

 Run and supervise the daemons that these features depend on

 Apply each Pod container’s memory limits and compute mode before the process starts

 Report what each fraction actually uses, rather than what the whole GPU uses

 This work belongs on the node, independent of whichever scheduler placed the workload.

 GPU fractioning: An open-source Kubernetes operator 

 A new open-source Kubernetes operator, gpu-fractioning , is hosted under the KAI Scheduler organization on GitHub. It runs next to the NVIDIA GPU Operator, which provides the driver and the container runtime setup.

 GPU Fractioning Operator handles three jobs: 

 It sets up and runs MPS on every GPU node. 

 It applies each workload’s memory limits and compute mode.

 It measures memory and compute use per fraction rather than per GPU.

 How schedulers pass GPU allocations to the operator 

 The developers write the resource and mode annotations in the pod YAML. Then the scheduler selects the GPUs for a workload and records its memory allocation and compute-sharing mode in per-container Pod annotations. GPU Fractioning Operator reads those annotations and configures the assigned GPUs to apply the workload’s memory limits and compute mode:

 Annotation Meaning 
 nvidia.com/container.<name>.gpu-memory.request Guaranteed GPU memory 
 nvidia.com/container.<name>.gpu-memory.limit Maximum the container may grow into 
 nvidia.com/container.<name>.gpu-compute.mode time-slicing (default) or sm-sharing 
 nvidia.com/container.<name>.gpus.devices Which GPUs the container was assigned

 The limit is optional. If it is omitted, the limit equals the request and the workload is capped at exactly what it asked for. A portion limit must be greater than the gpu-fraction and less than 1.

 How compute is shared: Time sharing or sm-sharing 

 Figure 1. Time-slicing divides the GPU’s time. SM-sharing divides its streaming multiprocessors (sm) 

 Compute can now be divided. Call n the number of workloads sharing a GPU: either way each gets roughly 1/n of the compute, and what differs is whether they take turns or run together.

 Time-slicing is serial: Workloads take turns on the whole GPU, and when every one of them uses its full slice each gets about 1/n of the time. Time left unused by one workload is shared equally between the others. This is the default. Each workload runs in its own error domain, i.e. full error isolation.

 SM-sharing is parallel: The GPU’s streaming multiprocessors (SMs) are split between workloads and all run at once, continuously. Nothing is carved out in advance. The GPU hardware allocates and releases SMs as workloads need them. When every workload is busy the split settles at roughly 1/n; when one goes quiet its SMs go to the others, and a single active workload can use them all. In this mode, workloads share a single error domain. 

 Compute mode is now explicit and can be set per container:

 nvidia.com/container.app.gpu-compute.mode: "sm-sharing" # or "time-slicing" 

 A shared GPU runs one compute mode at a time, so KAI Scheduler never places a time-slicing workload and an sm-sharing workload on the same GPU. KAI Scheduler tracks this per GPU, not per node, so one node can host both modes on different GPUs.

 gpu-fraction-num-devices: "4"

 The request applies to each device. A 40Gi request with four devices gets 40Gi on each of four GPUs.

Our GPU clusters customers and our internal Inference platform has been using this capability to help drive workload resiliency and minimize down time. Our customers love this capability, and we wanted to take some time break the system down and explain how it works and why we designed it this way.
 We first implemented “Passive health” checks system, that watches every node continuously, both inside your VM and on the host underneath it. When a check finds a fault, auto repair recommends the lightest action to fix and shows you supporting evidence behind the recommendation. You decide up front, fault by fault, whether a repair waits for approval or runs on its own. You also decide how long auto repair waits for running workload to finish. Your own detectors can open repairs through the same pipeline by writing a single annotation on a node.
 ‍ Availability 
 Generally available today: passive health checks, repair recommendations, the auto-remediation policy (including per-fault and per-node consent), wait-for-idle controls, the escalation ladder, the safety rails, and API and console repair.
 Preview: node-label based remediation contracts, which let you bring your own detection systems such as NVSentinel or custom controllers.

 Why NotReady is not enough
 Most node auto-repair keys on a single signal: the node went NotReady . That signal looks the same whether a node is broken or just briefly unreachable. When a storage or network event touches many nodes at once, every impacted node drops to NotReady. Our system has a circuit breaker built in to prevent mass replacement of nodes. NotReady also does not say why the node failed, so there's no basis for choosing between a reboot and a new machine.
 So auto repair follows one rule: no node repair occurs without a failed health check behind it, and every repair carries its supporting evidence. 
 The pipeline

 Auto repair pipeline: signals from inside the VM and from the host feed Detect, Decide, and Repair inside your cluster; migrated hosts go to Re-validate on Together infrastructure. The pipeline has four stages: detect a fault, decide whether and when to act, repair the node, and re-validate the machine. The first three stages run against your cluster. The fourth runs on our side, on the physical host your node just vacated. Node-label requests from your own detection tooling enter at the decide stage and get exactly the same treatment as ours.
 1. Detection from both sides of the hypervisor
 GPUs in Together GPU Clusters are passed straight through to your VM for bare-metal performance. That means GPU faults are visible from inside the VM, while host and fabric faults are visible from the host. Detection therefore runs on both sides of the hypervisor and lands in one place.
 Inside your VM , exporters watch:
 the kernel log, for Xid errors and GPUs falling off the PCIe bus
 DCGM, for ECC double-bit errors, row-remap failures, PCIe replay rate, and thermal throttling
 Node Problem Detector, for read-only filesystems, XFS shutdowns, kernel deadlocks, and repeated kubelet or containerd restarts
 On Slurm, an exporter reports nodes marked DOWN or DRAIN.
 On the host , we watch InfiniBand rail state and link flapping, attributed to the VM that owns those rails. We also watch host reachability, so a dead host shows up as a problem on your node rather than as silence.
 Every alert ships a stable summary, a plain-language description, and a machine-readable evidence payload. For an Xid, that's each code and its NVIDIA mnemonic. For thermal throttling, it's the peak temperature and throttle count. The control plane passes those strings through untouched, so the console, the API (as linked_alerts ), and your notifications always say the same thing.
 We keep observed separate from actionable. Every repair-relevant alert is recorded and marks your node Degraded . Only signals with an action mapping create a repair. Disk pressure, for example, shows up but doesn't trigger a reboot, because a reboot won't fix it. An alert with no mapping is counted and logged, never silently dropped, and routed to our support team for investigation.
 2. Policy: we decide what, you decide whether and when
 What is owned by the platform. Each signal maps to the lightest action that fixes it, so you never need to know which Xid means what:

 Whether is yours to decide. In the Repairs tab, the Auto-remediation policy defaults to Approve before repair : every recommendation waits for a person, who can accept or override the action. You can switch the default to Fully automatic , but it isn't a blanket switch. The Repair actions checklist groups faults by the repair they trigger, and you select the ones you trust to run unattended. Inside the Xid group, you can set consent per code. A common setup auto-approves reboots for Xid 119 and 95 and keeps migrations gated. The Xid checklist also works under Approve before repair, if you want a short list of faults to run automatically while everything else waits for your review.
 When is yours as well. A repair drains the node, so Wait for idle holds it until the node is actually idle. On Kubernetes, that means no running pod on the node is requesting a GPU. On Slurm, it means the scheduler reports no allocation on the node. Maximum wait bounds the hold, with a default of 2 hours and a cap of 24. Do not interrupt running jobs removes the bound entirely. Set the wait to at least your checkpoint interval. If the bound expires, the repair proceeds and the timeout is recorded.
 Every repair records who requested it ( Together Health Checker for automatic repairs), who approved it (a named user or Auto-Approved ), which rule decided, and when.
 3. Bring your own detector
 Teams running large GPU fleets already have detection they trust: DCGM dashboards, NVSentinel, in-house scanners, job-level checks. Every repair, whatever its source, becomes the same record in our control plane. That gives capacity checks, audit, and safety rails exactly one home.
 There are three ways in:
 API. Create a repair against an instance with a mode, an optional client-supplied ID for idempotency, and optionally the health check run or alert you're citing as evidence. You can also list, get, approve, reject, and cancel repairs.
 Console. The ⋮ menu on any node opens the Repair dialog with the detected issues and the recommended action.
 Node labels (Preview). Any detector with RBAC permission to write node metadata can open a repair by adding one annotation and one label to the node. The annotation carries the detector name, a stable request ID, the repair mode, when the fault was detected, and a human-readable reason.
 Our cluster operator mirrors the node label up to the control plane. The repair is recorded with the detector as an external requester, so it's always attributable and can never impersonate a user. Detector name plus request ID is the idempotency key across the cluster, finished repairs included, so a detector that re-asserts the same fault on every scan can't reboot a node twice. Authorization is your cluster's own RBAC, with no API key and no onboarding ticket.
 Annotation requests can ask for Reboot, Quick reprovision, or Migrate. Remove stays human-only. Like a console click, these requests skip the approval queue, but they still pass the same evidence gate, capacity check, and budgets as everything else. A per-cluster cap means a buggy detector causes limited damage rather than a catastrophe.
 4. Repair actions and the escalation ladder
 Every repair follows the same lifecycle: cordon, wait (per your policy), drain, act, rejoin. The console shows the node moving through Cordoning → Draining → Repairing / Migrating → Joining → Running .
 The actions, from lightest to heaviest:
 Reboot. Restarts the VM in place. Local /scratch and /tmp data survive.
 Quick reprovision. Rebuilds the VM from a clean image on a healthy host. Local data is lost.
 Migrate to new host. Rebuilds the VM on different hardware and sends the old host to re-validation.
 Remove. Pulls the node for RMA. Always human-initiated.
 The same fix doesn't loop. If a fault comes back on the same machine after the same action has already run twice, the next recommendation moves one rung up. A third round of Xid reboots becomes a reprovision, and a third reprovision becomes a migration. The ladder is tracked per machine, cluster, alert, and Xid code. Attempts older than a week don't count, and neither do cancelled or self-resolved recommendations.

 Two tries per rung, then one rung up. Migration needs critical-alert evidence. Migrations are evidence-gated. Migrate is the one action that consumes real capacity.
