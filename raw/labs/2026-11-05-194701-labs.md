```text
## Description:

MetricTrail estimates camera motion and per-frame metric depth from long RGB
image sequences for visual odometry and 3D reconstruction research. It combines
single-image metric depth, learned sparse correspondences, and local geometric
optimization, with supplied or RGB-estimated intrinsics and optional rectified
stereo. MetricTrail 1.0 was developed by NVIDIA.

The repository provides a CLI that exports camera trajectories and caches
per-frame depth. Model weights are not included in the source repository;
the DINO-DPVO checkpoint is planned for a separate Hugging Face release.
The CLI does not export dense point clouds or meshes. The dense-reconstruction
results below use a separate research evaluation workflow.

This model is for research and development only.

## Model Architecture:

**Architecture Type:** Learned recurrent visual odometry with frozen visual
foundation-model features and explicit bundle adjustment.

**Network Architecture:** DPVO's sparse patch correspondence network with
learned residual feature-fusion adapters, a frozen DINOv3-S/16 encoder, and a
frozen MoGe-2 metric-depth provider. The complete system includes camera
calibration and optional pose-graph correction.

**Number of model parameters:** The DINO-DPVO checkpoint for the separate
Hugging Face release contains
**3,425,860 learned parameters (3.43 million)** across 100 FP32 weight/bias
tensors. This count excludes the frozen DINOv3 backbone, external MoGe-2 depth
model, calibration dependencies, and optional SALAD and RoMa models.

The local estimator alternates learned patch matching with joint optimization
of camera poses and sparse patch inverse depths in a bounded active window.
MoGe-2 independently predicts metric camera-Z depth for each image. These
predictions initialize patch depths and remain robust soft constraints during
optimization; multi-view evidence can override unreliable prior measurements.
In the dense-reconstruction workflow, frame-level depth maps are
placed in a shared world frame using the recovered poses and are not themselves
bundle-adjustment variables.

Frozen DINOv3 features augment the matching map and recurrent patch context
through learned residual adapters. Its 384-dimensional features are projected
to 64 channels and split into two 32-channel branches that augment the
128-channel matching stream and 384-dimensional recurrent context. Final
residual projections are initialized to zero so adaptation starts from the
official DPVO checkpoint's predictions.

We train MetricTrail for 15,000 optimizer steps with global batch size 16 on
16 NVIDIA A100 80GB GPUs, taking approximately seven hours. Fusion branches
first warm up on 5,000 TartanAir clips with odometry frozen; odometry and fusion
branches are then jointly fine-tuned on the remaining 235,000 clips. DINOv3 stays
frozen, and MoGe-2 is not used during adaptation. Joint training uses AdamW,
learning rates of 8e-6 for odometry and 8e-5 for fusion, weight decay 1e-6,
linear OneCycle annealing with 1% warmup, gradient clipping at 10, and seed 1234. Each clip
uses 80 patches per frame and 18 recurrent refinements. The frozen DINOv3
forward pass uses BF16; adapters, odometry, differentiable bundle adjustment,
and losses use FP32.
```

```text
 Oak Ridge National Laboratory (ORNL), IBM, and AMD have launched a co-design platform for quantum error correction to help researchers define and accelerate the classical and quantum workflows for scientifically relevant quantum computing.

 The quantum error correction (QEC) co-design platform sits at IBM's site in Poughkeepsie, New York and launched with the U.S. Department of Energy’s Quantum Science Center (QSC) at ORNL and AMD as its inaugural partners. It pairs IBM Quantum Nighthawk processors with Umbra, QSC’s high-performance computing system comprising AMD Instinct MI355X GPUs and 5th Gen AMD EPYC™ CPUs, in one co-located environment linked to ORNL's broader supercomputing ecosystem.

 This initiative brings together the computing infrastructure needed for quantum error correction in a single environment and opens it up to more researchers than ever before. They will use it to develop and validate quantum algorithms, workflows, and applications in an environment designed for quantum-centric supercomputing, an emerging paradigm where quantum processors, CPUs, and GPUs work together as one system. The platform handles the infrastructure, so researchers can concentrate on algorithm discovery.

 A co-design platform for quantum error correction

 This platform builds on IBM and AMD's existing collaboration, including using AMD GPUs to accelerate sample-based quantum diagonalization and demonstrating efficient quantum error decoding on AMD hardware. The collaboration will also explore how future generations of AMD compute, networking and open software can be co-designed with quantum computers.

 How the co-design platform will advance quantum computing research

 Qubits, the fundamental units of quantum computation, make errors. Quantum error correction protects against them. Error correcting codes spread information across many qubits and run repeated checks for signs of trouble. A classical computer reads the data from each round of checks and works out which errors occurred. Researchers call the software that does this job a decoder, and it has to keep up with the quantum processor. That’s a fast-paced, demanding, computationally-intensive task.

 The algorithms that will make quantum computing scientifically useful need substantial classical computing resources working in step with quantum processors. Today, quantum computers and high performance computing (HPC) infrastructure rarely sit in the same location or get directly integrated. That means that researchers working on hybrid workflows often stitch those pieces together themselves. They reach a quantum computer through the cloud, run classical work on separate systems, and connect the two through separate application programming interfaces (APIs), the software links that let one system talk to another. Every handoff adds complexity and delay, and limits the experiments researchers can run.

 Error correction lays the foundation for practically relevant quantum computing. Its value comes from what it unlocks: larger, deeper, more capable quantum computations. The QEC co-design platform lets researchers test error correction on real quantum systems, inside the workflows it will serve. It also enables researchers to explore the use of GPUs for low-latency decoding more broadly.

 One promising approach is hierarchical error correction, and the platform could support research in that direction. The hierarchical approach layers two codes. An inner code protects qubits within a module. An outer code wraps around the inner code’s logical qubits and adds a second layer of protection. The inner code’s own logical operations supply the long-range connections the outer code needs, so the code itself provides the added protection and the chip stays simpler.

 Recent IBM research found that this approach could reach a trillion logical operations at a physical error rate of one in a thousand. These hierarchical codes rely on powerful classical computing. Decoding happens at each layer, and results from one layer feed into the next. The co-design platform gives researchers a place to test and develop those ideas with GPUs in a low-latency environment.

 With quantum and classical components in a shared environment, the codesign platform will enable researchers to explore quantum-classical workflows with the classical compute those workflows depend on, without building that infrastructure themselves. They can develop, test, and refine quantum algorithms, investigate error correction approaches, and gain early insight into what future error-corrected machines will require. Those insights can help inform the architectures, software, and workflows that will advance future systems.

 The platform aligns with the U.S. Department of Energy’s Genesis Mission, which aims to deploy a scientifically-relevant quantum computer by 2028. Experiments have now run up to 70 logical qubits—qubits protected by error correction—through 438 difficult operations. The Genesis Mission’s Q Competition targets 100 logical qubits running 100,000 such operations by late 2028. That’s a roughly 230-fold jump.

 How the platform works

 The platform uses the most advanced hardware from both IBM and AMD.

 On the quantum side are Nighthawk r2 processors. They can run circuits beyond the reach of brute-force classical simulation. Nighthawk gives error correction researchers square-lattice connectivity—the highest connectivity of any IBM quantum processor architecture today—high circuit throughput, and real-time pulse control. Researchers can measure qubits mid-calculation, act on the results in real time, and work directly with raw measurement signals. That lets teams compare what each error correction method demands in qubits, time, and classical computing, and find where AMD GPUs help most.

 On the classical side, Umbra combines ORNL’s AMD Instinct MI355X GPU accelerators with dedicated 5th Gen AMD EPYC™ CPUs. The GPUs let researchers train and evaluate decoders at large scale and explore error correction approaches that may make future systems more efficient. All this work will inform the development of IBM Quantum Starling, the fault-tolerant quantum computer IBM plans to deliver by 2029.

 Because the classical compute sits next to the quantum processors, the system is optimized for low-latency quantum-classical execution, with short delays as data moves between them. Low latency matters for decoding and for conditional execution, where a quantum program picks its next operation based on a measurement taken mid-computation. That fast feedback will support workflows like those required by hierarchical codes.

 This is the infrastructure of quantum-centric supercomputing in action.
```

```text
 Use decision models with Amazon Bedrock AgentCore Evaluations

 Some of the questions you ask when evaluating an agent are narrow and repeatable. Did this response stay on policy? Is this tool call safe to approve? Does this answer match the retrieved context? Decision models answer exactly that kind of question. They take a structured state and a fixed set of allowed answers and return a calibrated probability over them, rather than free-form text whose confidence drifts from run to run. That makes them a strong fit for the scoring step in an agent evaluation, where you want a label and a number you can threshold and trust.

 Amazon Bedrock AgentCore Evaluations , a capability of Amazon Bedrock AgentCore, scores an agent through its entire lifecycle, on demand during development, in batch jobs against stored sessions, and online against production traffic. Alongside 15 built-in evaluators, AgentCore Evaluations supports custom evaluators that you define as either an LLM-as-a-judge or a code-based evaluator. Custom LLM-as-a-judge evaluators apply your instructions and rating scale with a model in Amazon Bedrock. Code-based evaluators run your own logic in an AWS Lambda function, and that logic can call your choice of external system, model, or API, including a decision model.

 Decision models suit questions with a fixed set of answers that an informed person could decide at a glance, such as whether the agent refused a request or whether a response stayed on topic. After you validate a question on your own traffic, a decision model can be sufficient for that decision or score, and you can extend the same approach to specific harmfulness or stereotyping categories in your policy. Because both backends can answer several questions about the same state in a single request, you can use them as a screening layer rather than a replacement, running a pass or fail signal across your metrics to select the turns that warrant deeper assessment by the built-in evaluators, whose explanations help you investigate what went wrong.

 This post shows how to connect two decision model backends to AgentCore Evaluations through code-based evaluators. The first is Jev , a hosted decision model from TypeSafe. The second is Strands Decider 2B , an open-source decision model you run yourself. By the end of this post, you will know how to convert the AgentCore evaluator input into a decision model request, and the model’s probabilities back into an AgentCore evaluation result. First, though, when should you reach for a custom LLM-as-a-judge evaluator, and when does a decision model fit better? The next section breaks down what a decision model is and the trade-offs involved.

 Decision models

 A decision model is a small, specialized model trained to select from a fixed set of options and return calibrated confidence scores rather than generating free-form text. A general-purpose large language model (LLM) evaluator produces a score with a rationale. A decision model instead produces a probability distribution over predefined answers. That gives you a direct confidence measure you can threshold, aggregate, and act on programmatically. This makes decision models well-suited for evaluation tasks where the judgment can be stated as a choice among a fixed set of options: “Is this response grounded?” or “Did the agent complete the user’s goal?”

 Decision models are most useful when you want a well-calibrated confidence score alongside the label, not just a binary judgment. They are also appropriate when you want to enforce a specific rubric consistently without relying on a general-purpose LLM to interpret it.

 Jev, the hosted decision model from TypeSafe, and Strands Decider , an open-source, 2-billion-parameter decision model from the Strands Agents team, both support three types of questions. A noul question poses a yes/no question and returns a probability between 0 (no) and 1 (yes). A choice question asks which of up to 255 options applies, returning the most probable option along with the full distribution and a confidence. A score question asks which of 2 to 10 ordered levels applies, returning a probability-weighted score, the distribution over levels, and a confidence. Many evaluation rubrics fit one of these types. “Is every fact in this response supported by the tool results?” is a yes/no question, and “How helpful was this response, on a four-level rubric?” is a score.

 Decision models versus LLM-as-a-judge

 The built-in evaluators in AgentCore today use a general-purpose LLM to assess the agent response against a rubric and explain its judgment. This is valuable when the evaluation requires connecting evidence, identifying missing information, or working through a response in depth in tasks where the explanation is as useful as the score. Decision models are not a replacement for LLM evaluators. They’re an addition that the code-based evaluator framework makes possible. Use them for narrow, well-defined checks alongside the built-in evaluators’ broader assessment.

 The agent is built with Strands Agents and deployed to AgentCore runtime, a capability of Amazon Bedrock AgentCore. It answers employee questions using five tools that return fixed mock data such as paid time off (PTO) balances, PTO requests, HR policies, benefits, and pay stubs.  How Claude designed protein binders against scorpion neurotoxins
```

```text
 We’re sharing another finding from Anthropic’s biology research lab : the first 3D structure of a vault particle found in prokaryotic cells. Vaults are large, hollow barrels of protein found in cells across the tree of life, and their function is still unknown. Below, we describe how Claude helped at each step of this research: searching across sequence literature, optimizing a method of isolating particles, and mapping the vault’s structure. More information is in our preprint , which we’ve submitted to bioRxiv; we’ll update the link as soon as it goes live. 
 Biological cells were first detected in 1665, but more than three and a half centuries later, much of how they work remains unknown. Until relatively recently, the existence of some crucial components , let alone their function , was controversial. Even today, more than a third of the roughly 4,400 genes in one of the most comprehensively studied cells, the bacterium E. coli , remain poorly understood . Another such enigma is the vault particle .
 A vault particle is a large, hollow protein shell found in nearly all the cells in our body. It was discovered in 1986 by Leonard Rome and Nancy Kedersha, but its function remains elusive. At roughly three times the mass of a ribosome, it’s one of the largest known molecular complexes in eukaryotes—organisms with complex cells, such as mammals (as opposed to simple, usually single-celled “prokaryotes,” such as bacteria). Vaults take their name from their shape. When observed under an electron microscope, the ribbed shell reminded Dr. Rome and Dr. Kedersha of the vaulted ceiling of a cathedral. In mammals, the shell is made of 78 copies of the major vault protein, arranged as two identical halves joined at the middle.
 Vaults are found across most of the eukaryotic tree , from slime molds to humans, so scientists believe that they must do something useful. Researchers have proposed various functions, including transporting molecules between the nucleus and cytoplasm , protecting cells from toxic compounds such as cancer drugs , and supporting innate immunity , but none of these proposals have been conclusively confirmed. Other studies have shown that mice lacking vaults still survive , which suggests that vaults may be necessary only under specific environmental conditions. Still, the question remains: why would evolution retain something so large if it didn’t have an important function?
 Interested in whether Claude could help make progress on this long-standing open problem, our biology research team has been investigating vaults. We haven’t yet determined their biological function, but we did find that many more vault proteins across the tree of life, including those in prokaryotes and the bacteriophages that infect them, can assemble into complete vault-like particles. Related proteins had already been found in the genomes of both prokaryotes and phages, but to our knowledge no one had shown that they assemble into vaults.
 A vault in a prokaryotic cell gives researchers a simpler system to study. Compared with mammalian cells, bacteria are quick to grow, which makes it easier to investigate where vaults came from, what their basic structure looks like, and what, if anything, they contain. Studying the bacterial relatives of human proteins has been informative before. Bacterial versions of cGAS–STING signaling , gasdermins , and viperins revealed the microbial origins of these human immune defenses. In those cases, their function in humans was already known.  November 4, 2026
```
```text
 Otilia Stretcu, Research Scientist, and Leijie Wang, Student Researcher, Google Research

 Agile Deliberation addresses the challenges of building AI image classifiers for subjective categories by guiding users through an interactive deliberation workflow, from scoping sub-categories to resolving edge cases, using an LLM-driven optimization loop to automatically build an accurate, aligned classifier.

 Machine learning models learn to recognize the world around us from examples labeled by humans. Underlying this process is an assumption that the person doing the labeling has a clear and stable definition of the category in mind before they begin. This assumption holds well when training a model on objective categories, like a stop sign or a golden retriever, where boundaries are clear and universally recognized. In practice, however, real-world applications often require vision systems to navigate the subjective "gray areas" of human experience. For example, consider training a vision classifier to identify "healthy food", curate "inspiring artwork”, or assist in content moderation. In such domains, category boundaries may not be universal or static, since they can shift with cultural context, personal philosophies, or evolving operational policies. Furthermore, people rarely start with a complete specification for subjective concepts, even in their own minds. Instead, they begin with an intuitive idea of a concept and only discover the concept’s true boundaries, exceptions, and nuances as they encounter real-world examples. Traditional training workflows don’t account for this concept evolution , forcing users to provide rigid labels to an AI system even when their own mental model is still shifting.
 To bridge this gap, we introduce Agile Deliberation , a framework that treats the creation of subjective AI classifiers as an iterative conversation. Rather than requiring humans to act as static data labelers, Agile Deliberation turns the AI system into a collaborative partner that helps users "deliberate" and sharpen their own definitions. By resolving human ambiguity first, the framework systematically builds more effective, robust, and aligned AI systems. To support the wider research community, we have also open-sourced the underlying code and algorithms on GitHub .
 A key differentiator of this work is its focus on the live user experience. Because standard, static AI benchmarks can’t capture subjective concepts, we bypassed simulated testing and evaluated Agile Deliberation across 18 live, 1.5-hour sessions with human participants. This allowed us to directly observe and measure how a person's intent dynamically evolves when paired with an intelligent system. We found that Agile Deliberation drastically reduced user fatigue and anxiety by replacing manual prompt engineering with direct feedback on borderline images, which resulted in more consistent, higher-performing AI models that outperform standard baselines.

 How it works: The two stages of deliberation

 Agile Deliberation splits the complex task of defining a subjective concept into two structured stages: concept scoping and concept iteration . Together, these two phases transform a fuzzy idea into a highly precise instructional blueprint for an AI model.

 The Agile Deliberation workflow. The framework decomposes a broad target concept into in-scope (i.e., positive examples that the classifier should recognize and flag as matching the user's intent) and out-of-scope (i.e., explicit negative boundaries or "false alarms" that the user wants the classifier not to flag) definitions, retrieves borderline images to expose edge cases, and guides human feedback into an automatic prompt refinement loop to generate ready-to-use image classifiers. 

 Stage 1: Concept scoping

 When confronted with a broad topic like "Healthy Food," human intuition naturally struggles to list every rule upfront. In the concept scoping stage, the system guides the user to break down their overarching concept into a structured hierarchy of sub-concepts and explicit exclusions.
 For instance, instead of just using a single broad label, a user might decompose "Healthy Food" into positive sub-categories like "Salads," "Grain Bowls," and "Lean Proteins." Simultaneously, they might define explicit exclusions, such as "Processed Foods" or "Raw, Unprepared Ingredients." This creates an initial structured baseline that grounds the model's understanding.

 Stage 2: Concept iteration

 With the initial structure established, the framework moves from static planning to active testing. Traditional machine learning assumes the human annotator is an "oracle" with a complete set of fully defined rules already in mind. Agile Deliberation upends this premise, focusing instead on collaborative refinement.
 This stage draws inspiration from active learning , a method traditionally used to retrieve informative data points to maximize a machine's training efficiency. However, instead of selecting examples purely to minimize machine uncertainty as in active learning, Agile Deliberation uses vision-language models (VLMs) to actively mine and surface semantically borderline images that challenge the current text-based definitions.
 For instance, the system might present an image of a fruit smoothie to challenge a "healthy diet" concept, forcing the user to decide: Is this a healthy beverage because it contains raw fruit, or is it an excluded processed food due to high sugar content? 
 Confronting these ambiguous edge cases drives users to reflect on their own hidden assumptions, clarify their true intent, and update the policy rules accordingly. This human feedback is then routed directly into an automatic prompt optimization loop, ensuring the VLM's classification boundaries shift in tandem with the user’s refined definitions.

 Experiments

 Evaluating subjective visual classifiers presents a fundamental challenge: there is no static, objective ground truth to measure performance against and therefore, offline evaluation on pre-labeled datasets can’t measure how well the framework adapts as a person's mental model of a concept shifts during the deliberation process.
 To capture this dynamic, we built a functional prototype and evaluated it through a live user study. We conducted 18 live user sessions, each lasting 1.5 hours, where participants interacted with our system and alternative baselines in a randomized order to prevent learning bias.

We chose two complex, highly subjective domains to test the limits of these systems:
 Healthy Food : A domain where personal health philosophies, dietary restrictions, and cultural backgrounds can produce highly diverse, subjective viewpoints.
 Pay-to-Play : A real-world content moderation challenge that requires capturing expert-level nuance and specific context. This involves identifying clickbait images in online entertainment or gaming that promise misleading financial or digital rewards.
 We evaluated Agile Deliberation against three common distinct paradigms:
 Zero-shot classifiers : The standard "one-and-done" approach. Users write an initial prompt, but have no way to see edge cases or adapt when the model misinterprets the boundary.
 Modeling collaborator : An automated, top-down approach where an AI agent tries to decompose the concept on its own. While it generates criteria automatically, it removes the user from the loop, leaving no way to guide or correct its logic.
 Manual deliberation : The tedious, brute-force status quo process, where users examine data in spreadsheets, guess search queries to find anomalies, and rewrite raw prompts by hand.

 Results

 The live user sessions revealed that Agile Deliberation yields higher-performing classifier models, while substantially improving the user experience.

 Improving consistency and performance

 We found that study participants who went through the structured deliberation process demonstrated significantly higher labeling consistency over time. By resolving boundary ambiguities early on, they built classifiers that substantially outperformed all standard baselines. These performance gains were most dramatic on the most challenging subjective images — the exact areas where traditional classifiers typically fail because they rely on default, generic AI assumptions rather than the user's explicit, nuanced intent.

 Eliminating blind spots

 Expert participants reported that the system acted as an effective diagnostic tool. By intentionally serving up confusing, borderline images, the AI system helped them uncover "blind spots" in their initial definitions — uncovering scenarios they hadn't anticipated until presented with ambiguous real-world examples.

 Classifier performance gains across tasks . Across both "Pay-to-Play" and "Healthy Food" evaluation groups, the Agile Deliberation framework yields consistent performance gains over zero-shot baselines, whereas manual deliberation methods often fail to improve or even degrade classifier accuracy.

 A key finding of our live study was the cognitive toll of manual prompt engineering. Our study showed that users experienced pronounced cognitive fatigue when trying to predict search terms that might uncover edge cases during manual concept deliberation. Furthermore, they reported experiencing persistent anxiety that manually tweaking a text prompt to fix one mistake might unintentionally degrade performance for other parts of the classifier they had already fixed.
```

### [IBM Research] How MEMS inertial sensors can rival GPS
- url: https://research.ibm.com/blog/how-mems-inertial-sensors-can-rival-gps?utm_medium=rss&utm_source=rss
- published: 2026-11-05T13:00:00+00:00

```text
Modern navigation was revolutionized by satellite-based global positioning system (GPS) technology, but it’s not always available. GPS relies on signals from space, so it’s susceptible to anything that disrupts that journey — be it tall buildings, the deep ocean, or electronic interference.

 To address this challenge, HRL Laboratories , an IBM company, has developed a new type of inertial measurement unit (IMU) that employs an advanced algorithm to provide an uninterruptible alternative to GPS.

 “We're getting to the point where over-reliance on GPS has actually become a problem,” said David Chang, who leads the team working on HRL’s IMUs. “Inertial sensors help you deal with the scenarios where you cannot rely on GPS.”

 The heart of the IMU navigation approach is a fully self-contained device that precisely measures a vehicle’s movement in three dimensions. If you know where you started, and you know the exact path you’ve taken based on speed, orientation, and elapsed time, then you can work out your current coordinates. This approach revives a pre-GPS navigation technique called “dead reckoning” which is how some craft, such as submarines, still find their way around.

 But while a submarine’s high-performance IMU can be about the size of a dorm fridge, HRL’s IMU uses inertial sensors built using micro-electromechanical systems (MEMS) to yield a device about the size of a soup can. This small form factor makes it versatile enough to be deployed on lightweight vehicles like aerial drones.

 How do MEMS inertial sensors work?

 MEMS inertial sensors use miniaturized versions of accelerometers and gyroscopes etched into processor-sized silicon chips to track changes in velocity and angle of travel.

 Accelerometers exploit a suspended weight’s resistance to changes in motion — its inertia — to compute the difference in velocity between it and the rest of the device. Imagine holding a cup of water in a car. If the vehicle quickly comes to a stop, the water will keep moving forward and end up splashing out of the cup. The suspended weights in MEMS accelerometers will similarly lag behind as a vehicle speeds up or swing forward as the vehicle slows down, triggering a signal in the surrounding sensors that corresponds to the acceleration being applied.

 MEMS gyroscopes also measure movement based on inertia, but in their case, it’s rotation. The MEMS sensor contains a mass that vibrates back and forth. As the gyroscope spins, the inertia of the mass causes it to experience a shift in movement perpendicular to the direction it’s vibrating. Sensors that surround the mass pick up on this sideways motion to calculate the angular velocity causing it.

 A high-performance MEMS inertial sensor is designed to measure changes in one dimension to avoid unwanted cross-axis sensitivity. To account for this, the team’s IMUs contain three of each MEMS sensor aligned to the three-axis coordinate system describing the physical world.

 Versions of MEMS accelerometers and gyroscopes are found in many consumer devices — this is how a fitness tracker can tell whether you had a restless night of sleep and how a phone knows to spin its screen around when it gets flipped — but HRL’s MEMS inertial sensors are engineered to be much more accurate in order to come close to GPS for navigational accuracy.

 An IMU contains three accelerometers and three gyroscopes, each aligned to the X, Y, or Z axis to detect rotation or acceleration in any direction. 

 Solving bias drift is essential for a true GPS alternative

 For a long time, a phenomenon called “bias drift” has been limiting the use of MEMS-based IMUs for navigation. Bias drift occurs when noise from sources like vibrations and heat throw off sensors and generate a false inertial signal — in other words, bias is the signal from a sensor when it is not moving. The longer a typical MEMS-based IMU is used, the more bias drift compounds, undermining the ability to navigate for longer than a handful of minutes.

 But now, bias drift is an issue that HRL researchers have evidently solved.

 “The holy grail for these MEMS sensors is to deal with drift. You need to figure out how to calibrate it out,” said Chang. “I think we’ve finally cracked that nut.”

 The team’s solution is AutoCal, an automatic, self-calibrating system that continuously measures bias and corrects for its drift. The system works by regularly taking two simultaneous measurements for each sensor in opposite directions, capturing inertial signals with equal magnitude but different signs. Since the bias is the same nondirectional quantity contained in both measurements, it’s possible to arithmetically isolate the bias while also retaining the true core signal for navigation. The bias is then removed from subsequent measurements until the next calibration.

 Continuously correcting for drift means that these IMUs can be used indefinitely to support navigation, removing a major barrier to matching the accuracy of GPS.

 AutoCal (blue) removes bias drift (green) over an 8-hour static test. 

 How are MEMS-based IMUs optimized for cost and size?

 In addition to solving for bias drift, the researchers want to make high-performance IMUs small and cheap enough to deploy widely.

 One approach to saving space is using application-specific integrated circuits (ASICs) for custom electronics that reduce the bulk dedicated to off-the-shelf parts. Advanced packaging techniques were also developed to minimize the amount of unused space between components. This involves considerations like how the MEMS devices are assembled and the design of signal connections. Together, these efficiencies add up to a significantly leaner device.

 To keep costs down, the research team ensured its MEMS chips — which have the added challenge of moving parts like springs — could be mass-produced on silicon wafers with semiconductor manufacturing techniques, including using tools for etching precise patterns and depositing materials in exacting quantities. Partnering with established fabrication facilities provides a pathway to benefit from the same economies of scale as producing computer processors.

 What’s next for MEMS inertial sensors?

 The team aims to keep shrinking its AutoCal IMUs. The next step is to get the device down to about the size of a hockey puck.

 HRL is also looking to expand the applications that IMUs can support. While navigation is the biggest opportunity on the horizon, any use case that employs GPS could eventually benefit from MEMS-based IMUs. For example, they could help autonomous vehicles get around cities where buildings often disrupt satellite signals.

 But the researchers’ immediate focus is getting their current IMU into the hands of real-world users, with production expected to begin in 2027. “Cost, size, weight, and power — these factors are very important if you want to proliferate these devices,” said Chang. “I think at some point we're going to run into a situation where GPS is just totally unreliable for critical applications.”
```

```text
 CUDA 13.5 enhancements 

 Some notable enhancements that come with CUDA 13.5 include:

 Locality domain enhancements 

 CUDA 13.5 gives applications a choice between uniform streaming multiprocessor (SM) partitions across locality domains or partitions that include all available SMs. By default, localized green-context partitions use the same guaranteed SM count per domain, leaving supplemental SMs outside those partitions. 

 The new cudaDevSmResourceGroupLocalityDomainSupplementalSms flag, combined with cudaDevSmResourceGroupLocalityDomainId , includes these additional SMs within each selected domain. This enables applications to use all device SMs when partitioning across locality domains, although the resulting partitions may differ in size. 

 Applications can use discovery mode in the cudaDevSmResourceSplit() API to obtain each partition’s SM count and distribute work accordingly. This allows you to choose between the uniformity and predictability of uniform SM size for each locality domain, or to choose the maximum number of SMs that each locality domain has, and utilize as much of the GPU hardware as possible. For more info see the CUDA Runtime API .

 NVIDIA MPS 

 MPS v3 gives you more control over how workloads share a GPU, from scheduling individual servers to assigning resources to groups of clients.

 Weighted timeslicing

 Weighted timeslicing lets you give longer compute turns to servers hosting workloads that need them. Set a base timeslice, scale it per MPS server, and independently tune how aggressively the GPU switches between workloads. 

 SM partition load balancing

 SM partition load balancing lets workloads use capacity beyond their base partition when resources are available. Enable borrowing with --max-chunks , and allow a partition to lend its SMs while it has no attached clients with --shareable=true . These settings are independent, so a partition can borrow, lend, or do both. MPS reclaims borrowed resources before reassigning them, while applications continue to see a stable base partition size.

 Cgroup-based routing

 Cgroup-based routing connects your workload launcher’s process groupings to MPS resource policies. Map a cgroup v2 subtree to an MPS namespace, and clients connecting through the daemon’s main socket are routed to that namespace automatically. 

 SM partition assignments

 Per-namespace SM partition assignments let you choose a partition for each device once, then apply that selection to every client routed to the namespace. You no longer need to configure CUDA_MPS_SM_PARTITION separately for those clients. Namespace assignments take precedence, while devices without an assignment retain the environment-variable fallback.

 Polling-based fallback for memory accounting

 Polling-based memory accounting provides a fallback when cgroup threshold notifications are missing or unreliable. During eviction decisions, MPS can read current usage and limits directly instead of relying on cached notification state. To force polling, run nvidia-cuda-mps-control memacct set force_polling=true before memory accounting starts. This adds work per eviction decision but removes its dependence on notification delivery.

 Batched 1d copies in CUDA graphs 

 CUDA 13.5 adds CUDA Graph support for batched 1D memory copies. Applications can now include existing cudaMemcpyBatchAsync calls in stream capture without changing the batched-copy call syntax, allowing multiple transfers to be captured and replayed as part of a reusable graph workflow. Applications can also add batched-copy nodes explicitly and update compatible copy addresses and sizes without changing the batch structure.

 Windows driver modes on NVIDIA Rubin 

 Starting with the NVIDIA Rubin architecture, CUDA supports Windows Driver Display Model (WDDM) and Microsoft Compute Driver Model (MCDM), with MCDM providing the compute-only driver model. Tesla Compute Cluster (TCC) is not supported on Rubin and later GPUs. Applications and deployment tools that assume TCC mode should use the supported WDDM or MCDM configuration for their target system.

 CUDA Tile updates 

 Multi-gpu communication in CUDA Tile 

 CUDA 13.5 adds support for multi-GPU communication directly within CUDA Tile kernels . Unicast pointers let a kernel access memory on another NVLink-connected GPU, while multicast pointers and dedicated multimem operations support reductions and stores across multiple GPUs on NVIDIA NVSwitch fabrics with NVIDIA NVLink SHARP support. Applications prepare the shared-memory mappings before launch, then combine communication with computation inside the kernel, enabling workloads such as fused matrix multiplication and cross-GPU reduction.

 Tile to single instruction multi-thread (SIMT) interoperability (public preview) 

 CUDA 13.5 allows CUDA Tile kernels to call SIMT library device functions directly. Before this release, Tile and SIMT library code could only be combined across kernel boundaries, with data passing through global memory between them. With this preview, kernels written in cuTile Python or CUDA Tile C++ can call device functions from SIMT libraries in the middle of their own code, on data that is already in registers or shared memory. These libraries include NVIDIA NVSHMEM , NVIDIA CCCL Coop , NVIDIA Warp and NVIDIA MathDx , which covers NVIDIA cuFFTDx, NVIDIA cuBLASDx, NVIDIA cuSolverDx, and NVIDIA nvCOMPDx, and this interop support will be enabled by each of these libraries soon.

 A tile library (.tilelib) packages interface and implementation information for SIMT library functions. The compiler partitions each tile across threads the way the library expects, communicates any shared memory and synchronization requirements, and produces a single kernel. To enable the preview in C++, compile with nvcc --tile-preview simt and pass the tilelib to the tile compiler. In cuTile Python, use cuda.tile_preview.foreign_call , provided by the cuda.tile_preview package.

 In 13.5, the Tile-SIMT interop preview covers library functions only. Calling your own __device__ functions from tile code is planned for a future release. For more information, see the documentation .

 NVIDIA CUDA Python 

 NVIDIA CUDA Python continues to expand Pythonic access to CUDA programming. The CUDA Python core library cuda.core 1.2 introduces batched memory copies, Programmatic Dependent Launch (PDL), simpler runtime compilation, and more flexible CUDA Graph updates.

 Batched memory copies 

 The new cuda.core.utils.copy_batch() submits multiple buffer copies through a single CUDA driver call. CopyOptions provides control over source access ordering, memory-location hints, and overlap behavior, giving applications more control over data movement.
```
