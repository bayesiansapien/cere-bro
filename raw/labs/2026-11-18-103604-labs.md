```text
 Announcing AI data preparation capabilities in Amazon SageMaker: Build high-quality datasets for model development workflows

 Teams that ship generative AI to production know that a model is only as good as its data. That is why preparing high-quality training and evaluation data comes first. Fine-tuning an open-weight model, running reinforcement learning, or building an evaluation suite all depend on data that is accurate, well-labeled, and representative of your task. For narrow, well-defined tasks, a smaller model customized on clean, task-specific data can often match or exceed the accuracy of a larger general-purpose model prompted into shape, at a lower cost per inference.

 In practice, though, preparing that data is often the slowest part of the project. Labeled examples are scarce or expensive, and privacy rules limit what you can use. Quality problems such as duplicates, label noise, and answer leakage go unnoticed until a training run disappoints, and every training technique expects data in its own format. As a result, data scientists spend weeks wrangling data instead of building models.

 Today, we’re expanding Amazon SageMaker AI with new AI data preparation capabilities for model development workflows. You can generate synthetic examples, assess and improve existing datasets, and bring expert feedback into the process through Python SDK APIs and the AWS AI-ML agent skill. You work in your notebook or IDE, with specifications and code that you can inspect and change.

 Prepare data without hand-building pipelines

 With AI Data Preparation capabilities, you don’t need to stitch together labeling tools, generation scripts, and validation jobs. Each capability is a standalone building block. You can use one of them on its own or chain them together according to the workflow you want.

 Auto-labeling: Label data at scale from an unlabeled dataset, a small labeled seed set, or no labels at all. Built-in task types include classification, named entity recognition, extractive question answering, ordinal rating, and summarization, and you can define custom tasks. You describe the task in a short labeling spec, which is validated against your own examples before the full dataset is labeled. For tasks with a fixed set of possible answers, such as classification, named entity recognition, and extractive question answering, a jury of several models labels each row, and their level of agreement becomes that row’s confidence score.

 Human review: Rows below your confidence threshold go to a review queue in Amazon SageMaker Studio, which uses the open-source Label Studio Community Edition. Outside subject matter experts can access the review app through the link in the partner app box in SageMaker Studio. Reviewer corrections feed back into auto-labeling, and you can generate consensus metrics and labeling reports.

 Synthetic data generation: Generate training, evaluation, and test data from a specification. You can ground the output in your own seed data and documents, and the service generates a code-based data generation pipeline that you can review, modify, reuse, and scale.

 Data quality evaluation: Check datasets against your own business rules, built-in metrics, and LLM-as-a-judge metrics. Find duplicates and near-duplicates, and surface issues you didn’t think to check for, such as label noise or answer leakage.

 Data transformation: Clean and reshape data for your target training technique. Describe the change in plain language and have the code generated for you, use built-in operations such as dedupe, merge, split, and filter, or run your own Python at scale.

 You work wherever you already work. Use the SageMaker Python SDK directly or provide your coding agent the AI-ML skill in the agent toolkit and let your agent invoke the APIs according to established data science best practices. Describe what you need, and the agent selects and runs the right capability in SageMaker Studio JupyterLab, Kiro, or your local IDE with your coding assistant of choice.

 For teams building specialized models, the hardest part is often finding enough task-specific data. Splunk, a Cisco company, faced exactly this when building evaluation models for its Agent Observability product.

 “For Splunk Agent Observability, our ability to train robust GenAI Eval models relies on access to high-quality, diverse datasets which are hard to curate for very specific tasks. Amazon SageMaker AI data preparation capabilities for synthetic data generation is meaningfully helping us scale these capabilities. We’ve been able to generate statistically representative synthetic datasets reliably and fast, while preserving the underlying patterns our models depend on. The seamless integration with the rest of our SageMaker workflow means our data scientists and customers spend less time wrangling data and more time building models that drive real enterprise value through Splunk.” 

 — Yash Sheth, Director of Engineering, Splunk Agent Observability

 Chain capabilities from raw data to training

 The value grows when you combine the capabilities. Some common patterns:

 Build a golden evaluation dataset: Auto-label your raw data from a small seed set. High-confidence rows are accepted automatically, and low-confidence rows go to human reviewers. Their corrections improve the next labeling pass, resulting in a trusted, human-validated dataset to benchmark your models against.

 Go from raw documents to a trained model in one workflow:

 Generate data: Synthetic data generation creates task-specific examples grounded in your documents and seed data.

 Transform it: Data transformation reshapes the data into the format your training technique expects, such as supervised fine-tuning (SFT), direct preference optimization (DPO), or reinforcement learning (RL).

 Validate it: Data quality evaluation checks the dataset for duplicates, leakage, and rule violations before you spend compute on training.

 Train: Train with SageMaker AI model customization.

 How it works

 Consider a team preparing data to evaluate agentic customer support assistants. Its product guide says that a factory reset erases saved settings. The team wants to test whether the assistant preserves that warning when answering reset questions.

 One pass through the preparation workflow looks like this:

 Define the requirements: Supply the product guide as context and describe the questions and reference answers you need. Include the requirement that answers about a factory reset preserve the warning about saved settings. Review the specification produced with your coding agent.

 Generate and inspect a sample: Generate a small batch and check the records against the guide. Review the generation and check the code. Confirm that the examples cover the intended questions and that the reference answers follow the source material.

 Assess and review: Run a data quality assessment and inspect the record-level findings. Ask a subject matter expert to review ambiguous answers or disputed assessments. Use the results and annotations to request improvement recommendations.

 Apply changes and repeat: Revise the specification if the requirements need clarification or transform the dataset to address issues such as duplicates. Generate additional examples where needed, then reassess the revised dataset before using it to evaluate the assistant.

 This example workflow illustrates how the capabilities fit together.

 Keep control of your preparation workflow and data

 With the AI-ML skill, you describe the task in natural language while your coding agent helps build specifications, prepare code, and coordinate the data preparation steps. You can open those artifacts to see how the workflow is configured and make changes directly.

 If you prefer to invoke the APIs yourself, use the Python SDK APIs to call individual capabilities from your own code. The SDK APIs take a specification as input, so we recommend creating it with the help of an agent. You can add quality assessment to an existing process, generate data for a new task, or combine several operations. You choose the preparation steps your project needs and how they fit into your model customization and evaluation processes.

 AI Data Preparation runs with an AWS Identity and Access Management (IAM) execution role that you control. Your source data, generated datasets, and labels stay in your own Amazon Simple Storage Service (Amazon S3) buckets, in the AWS Region you choose.

 Get started today

 The AI data preparation capabilities are generally available in the US East (N. Virginia) and US West (Oregon) Regions.

 There are two ways to get started:

 With your coding agent –  Set up the data preparation skills in your supported notebook or IDE. Describe one training or evaluation task and review the resulting specification before generating a sample.

 With Python –  Use the SageMaker Python SDK directly to run individual data preparation capabilities from your own code. The SDK takes a specification as input, so we recommend creating your specifications with the AI-ML skill first, then using the SDK to run them in your workflow.

 For more information, see the Amazon SageMaker AI documentation.
```

```text
## Training

### [Causal Forcing++ -> FastFrames-S](https://github.com/apple-aiml-research/ml-fastframes/blob/main/docs/training.md#causal-forcing---fastframes-s)

FastFrames-S keeps the two-step frame-wise Causal Forcing++ generator frozen and trains the
networks around it.

### [Wan2.1-14B -> FastFrames-L](https://github.com/apple-aiml-research/ml-fastframes/blob/main/docs/training.md#wan21-14b---fastframes-l)

We first distill Wan2.1-14B into a two-step causal model following the Causal Forcing++ recipe,
then train its pixel decoder and KV refinement network as for FastFrames-S. We release all
checkpoints: 1) a causal teacher trained on latents generated by Wan2.1-14B; 2) the
consistency-distilled model; 3) the DMD-distilled model; 4) the final generator, pixel decoder
and KV refinement network.
```

```text
Code World Model 2.0 由上游引擎维护世界状态，通过视觉 Proxy 规定相机路径、场景布局和物体运动，再交给视频模型生成外观。

本仓库提供 **Invoker-Render 的因果流式 DiT 权重**。模型以结构 Proxy、一张外观参考图和文本为输入，配套的 [CodeWorldModel](https://github.com/inclusionAI/CodeWorldModel) 推理代码支持因果四步流式生成，基于 MiniMax-H3、SGLang 和 SGLang-Omni。

## 特点

- **长时流式生成**：固定外观锚点与有界历史窗口，支持持续输入 Proxy 帧。
- **多粒度控制**：支持语义图、稀疏 3D 框、主体掩码、带明暗的几何体，以及框加骨架。
- **交互式部署**：配套代码提供 WebSocket 会话服务、文件客户端和浏览器客户端。

## 权重说明

- **根目录：因果流式 DiT 主权重**。33.12B 参数，FP32 存储，29 个 safetensors 分片、638 个张量，约 132.5 GB，未量化，可直接加载。
- `config.json` 保留 `MiniMaxH3Transformer3DModel` 架构标识；分片索引为 `diffusion_pytorch_model.safetensors.index.json`。
- **`bidirectional_lora/teacher-live.safetensors`：双向 teacher 的 LoRA 权重**（约 2.3 GB），底座为 MiniMax-H3。它与根目录的因果主权重不是同一个模型，不要叠加到根目录权重上。
- 本仓库不包含 VAE、Qwen、因果解码器、silence tensors 或准备好的推理 bundle，需另行准备匹配资产。

## 推理

请使用配套的 [CodeWorldModel](https://github.com/inclusionAI/CodeWorldModel) 仓库，按其 `README.md` 和 `docs/INFERENCE.md` 配置环境、准备 bundle，并通过 `invoker_render.py` 启动服务或运行文件推理。默认 `production` 配置使用单机八张 NVIDIA GPU。

输入为 **1344×768 RGB 首图、24 FPS Proxy 视频和文本提示词**；文件推理要求 Proxy 帧数为 `17*N+5`，且不少于 39 帧。24 FPS 是视频时间轴帧率，不代表推理吞吐。
```

```text
## Model Introduction

**Hy4 flash** is our most cost-effective Hy model to date, featuring 220B total parameters (including 64B Engram parameters) with just 12B active parameters per token. It natively accepts text and image inputs, generates text, and supports a context window of up to 1M tokens.

Its 42-layer language backbone consists of one dense feed-forward layer and 41 MoE layers, with identity Hyper-Connections (iHC) supporting inter-layer information flow. A vision encoder (adapted from SigLIP2-So400m-Patch16-Res512) is connected to the backbone through an MLP projector. In addition to the backbone, a built-in 5-layer drafter, [DFly2](#dfly2-for-speculative-decoding) (0.85B parameters), reuses the target model's KV cache and sparse indices to support long-context speculative decoding at a low, constant cost.

Compared with Hy4, Hy4 Flash introduces three notable architectural changes:

1. **Hybrid attention.** Sparse attention (IndexPool) and sliding-window attention (SWA) are interleaved at a 1:3 ratio.
2. **LatentMoE.** Routed experts operate in a lower-dimensional latent space. Each token activates 16 of 512 routed experts, alongside one shared expert.
3. **N-gram embedding (Engram).** The backbone is augmented with learned bigram and trigram representations, retrieved via multi-head hash lookups.

## Practicality and Cost Efficiency

### Optimization Approach

Across training, evaluation, and inference, we aggressively optimized for cost efficiency while preserving intelligence:

- **Pre-training**: Hy4 flash integrates hybrid attention, LatentMoE, and Engram into its architecture—reducing KV cache size to just **1/24 of Hy3** and **1/6 of Hy4**, with extensive scaling ladder experiments ensuring performance meets expectations.
- **Post-training**: Self-distillation from Hy4 establishes strong general intelligence, while reinforcement learning cuts average end-to-end output tokens by **50%**.
```

```text
 The biggest cost lever in a generative AI system is whether you call a model at all.  Spend grows with request count, even for low-value steps.
```

```text
 Today, Amazon SageMaker AI introduces KV cache-aware routing (KV-aware routing), a new routing strategy for real-time endpoints. It uses the cache state that the model container reports. It sends each request to an instance that already holds a long cached match for its prompt and isn’t too busy. It’s for teams that serve large language models (LLMs) with multi-turn conversations, long shared prompts, or heavy load.  Here’s the problem it solves: LLM applications such as chat assistants, Retrieval Augmented Generation (RAG), and agents with long system prompts send many requests that start with the same text. A model keeps the work it did on a prompt in GPU memory, the KV cache, and skips that work when the same start reaches the same instance again. In part 1 of this series , we introduced prefix-aware routing for Amazon SageMaker AI, which sends requests that start the same way to the same instance. Prefix-aware routing infers where a prefix is cached from the request alone, so it can’t tell when an instance has evicted that cache.

 Prefix-aware routing picks an instance from the request alone. It hashes the start of the request, up to the PrefixLength you configure (bytes of the InvokeEndpoint payload, or characters of the message text for the OpenAI-compatible Chat Completions API), and sends requests that start the same way to the same instance.  The cache on an instance changes over time. An instance evicts older KV cache entries when its GPU memory fills up, but the router keeps sending matching requests there as if the cache were still warm.

 A conversation starts out short. In a multi-turn chat, each turn adds to the history.  How KV-aware routing works

 KV-aware routing has three parts: the model container reports what it has cached, SageMaker AI keeps a managed cache index of that state for the endpoint, and the endpoint uses the index to choose an instance for each request.

 When you turn events on with SM_VLLM_KV_EVENTS_CONFIG , the container publishes a KV cache event each time it stores or evicts cache entries, and SageMaker AI uses these events to keep the index current. The index holds only pointers: one-way, truncated hashes of cached content, each mapped to the instance or inference component copy that holds it. It never stores prompts, token IDs, request payloads, or KV tensors. When a request arrives, the endpoint tokenizes the prompt and looks up the tokens in the index. The index returns the instances or inference component copies that hold part of the prompt in their cache, and how much of it each one holds. For example, if instance A holds the cached start of a conversation, the next turn of that conversation goes to A. Because the index matches on tokens rather than a fixed number of bytes, a multi-turn history can match in full as it grows. A request that shares only part of its prompt still goes to the instance with the longest match.

 The endpoint then picks among these candidates by weighing how much of the prompt each one has cached against how busy it is. A candidate that is too busy is skipped, so if the instance with the longest match is busy, the request goes to the next-best one that is available. You don’t configure a concurrency threshold for this, as you do with prefix-aware routing. The index also follows the fleet. When you scale in, entries for removed instances are dropped. When you scale out or an update replaces instances, the new instances start with empty caches, so latency can be higher for a short time.
```

### [Salesforce AI Research] Forecasts That Fix Themselves: Self-Evolving Data Science Agents at Salesforce
- url: https://www.salesforce.com/blog/self-evolving-data-science-agents/
- published: 2026-11-17T22:02:11+00:00
- via: feed

```text
Share article

 Every night, our internal forecasting platform generates nearly four million forecasts that power our global infrastructure. They decide how much cloud capacity we reserve, which workloads to migrate, and whether an infrastructure budget is going to run over. Each forecast instance is defined by just a few settings: what data to use, which model to run, and how accurate it needs to be.

 That simplicity in our forecasting platform let us scale from five use cases to more than a hundred without a matching increase in data scientists. But launching a forecast is the easy part. Keeping it accurate means constantly tuning it. The metrics we forecast constantly change and models drift, so each forecast needs a data scientist to work out what changed and test a fix. 

 In order to scale our model tuning, we built an internal self-evolving data science agent that investigates forecast drift, tests candidate model fixes against recent history, and opens a pull request (proposed code change a data scientist must approve). “Evolving” here means the agent reuses lessons from past investigations and reviewer feedback. It doesn’t deploy models on its own.

 Figure 1: When a forecast drifts off target, the agent works out why and proposes a fix for a data scientist to approve. 

 To date, the agent has proposed more than 100 forecast model fixes like swapping models from Prophet to Moirai, tuning change point sensitivity, and adjusting the training window. Although results vary by forecast, we observed a 14% reduction in sMAPE error during backtests, with some forecasts showing significant improvements. More importantly, a typical agentic investigation takes 27 minutes instead of hours. This transition from reactive data scientist debugging to autonomous agentic tuning enables our platform to self-evolve with the ever-changing metrics at scale.

 From a Forecast Miss to a Tested Change

 Consider a storage forecast for a single AWS availability zone. Teams use it to decide how much capacity to reserve months ahead. Through the first half of 2026, usage grew at a steady pace. Then, in June, growth flattened as new workloads started landing in other regions. The forecast kept projecting the old trend. Left alone, it would have had us reserve, and pay for, about 100 TB of storage we’d never use. But the agent’s pull request swapped in Moirai, Salesforce’s a time-series forecasting model, which helped us avoid reserving unneeded capacity

 Figure 2: Storage growth in one availability zone slowed, but the old forecast kept the old trend. The agent’s pull request swapped in Moirai, which follows the slowdown and avoids reserving ~100 TB of unused capacity. 

 Here are the six steps of how the agent caught and fixed the forecast model.

 1. Localize. Find which forecasts are off track.

 2. Diagnose. Examine changes in the data and search Slack for relevant context.

 3. Remediate. Try new models and settings, including foundation models like Moirai 2.0 .

 4. Re-evaluate. Test the new forecasts against past data.

 5. Decide. Open a pull request for a data scientist to review if a new forecast model is more accurate.

 6. Evolve. Update the investigation playbook with the fix that worked.

 The agent can’t change a production forecast. It can only open a pull request, and only when a fix beats the current model by at least 5% on data it hasn’t seen. Each investigation has a fixed testing budget, and when the evidence is unclear, it hands the case to a data scientist.

 Architecture: One Agent, Many Workers

 Figure 3: The agent decides what to test, Kubernetes and Spark run the tests in parallel, and MLflow ranks the model results. 

 The agent doesn’t replace our ML stack. It sits on top of it. Experiments still run on the standard tools: Kubernetes and Spark do the computation, and MLflow tracks and ranks the results. What’s new is the agent between Slack and those engines, which gives data scientists one conversational interface to the whole system. A data scientist can ask a question in Slack. The agent works out why a forecast missed and which fixes to try. A single investigation can mean dozens of backtests, far too much compute for the agent to handle itself, so it sends each job to the right engine. Smaller jobs run on Kubernetes, one pod per variant, and larger ones run on Spark, where one configuration is tested across many series at once. MLflow scores every candidate and sends the top models back to the agent, which picks the winner and automatically opens a pull request for review.

 What’s Next 

 Before our self-evolving agent, data scientists had to investigate each forecast miss, with AI playing only a supporting role. Now we’ve turned that around. The self-evolving agent does the data science work, and data scientists help by reviewing its fixes and giving feedback. That feedback carries into the next investigation, so the agent keeps improving. Our team now spends its time building new forecasts instead of maintaining old ones.

 We’re extending the self-evolving agent beyond model tuning:

 Forecast pipeline health . An accurate model only helps if the job that runs it finishes. We’re extending the self-evolving agent to monitor the data pipelines behind each forecast. As with tuning, what the agent can do on its own depends on what a wrong action would cost.

 Automatic forecast onboarding . A business planner could ask for a weekly AI token forecast by model and region. The agent would identify the source data, check that it has enough usable history, and pick the best model before opening a pull request for production. 

 Multimodal intelligence . Right now the agent reacts after a forecast misses. We want it to read context like launch plans and migration announcements alongside the numbers, so it can adjust a forecast before the change lands. Recent research on text-conditioned forecasting suggests models can do this by reading numbers and plain language together.

 These steps move us toward forecasts that don’t just recover from misses but anticipate them, and an agent that keeps learning from every investigation.
```
