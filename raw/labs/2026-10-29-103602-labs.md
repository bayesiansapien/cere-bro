# Granite-Speech-5.0-2B ONNX

ONNX weights of [ibm-granite/granite-speech-5.0-2b](https://huggingface.co/ibm-granite/granite-speech-5.0-2b) for in-browser inference with [Transformers.js](https://huggingface.co/docs/transformers.js) on WebGPU. These are the weights used by the [granite-speech-webgpu](https://huggingface.co/spaces/ibm-granite/granite-speech-webgpu) demo.

| file | precision | size |
| --- | --- | --- |
| `onnx/audio_encoder_q4.onnx` | 4-bit weights, fp32 activations | 658 MB |
| `onnx/embed_tokens_q4f16.onnx` | 4-bit weights, fp16 | 119 MB |
| `onnx/decoder_model_merged_q4f16.onnx` | 4-bit weights, fp16, KV cache | 948 MB |

Weights are 4-bit, block size 32, asymmetric (`MatMulNBits` / `GatherBlockQuantized`).

## Usage (Transformers.js >= 4.3)

'''js
import { AutoProcessor, GraniteSpeechForConditionalGeneration } from '@huggingface/transformers';

const model_id = 'ibm-granite/granite-speech-5.0-2b-ONNX';
const processor = await AutoProcessor.from_pretrained(model_id);
const model = await GraniteSpeechForConditionalGeneration.from_pretrained(model_id, {
  dtype: { audio_encoder: 'q4', embed_tokens: 'q4f16', decoder_model_merged: 'q4f16' },
  device: 'webgpu',
});

const messages = [{ role: 'user', content: '<|audio|>transcribe the speech with proper punctuation and capitalization.' }];
const text = processor.tokenizer.apply_chat_template(messages, { add_generation_prompt: true, tokenize: false });
const inputs = await processor(text, audio /* Float32Array, 16 kHz mono */);
const ids = await model.generate({ ...inputs, max_new_tokens: 256 });
const output = processor.batch_decode(ids.slice(null, [inputs.input_ids.dims.at(-1), null]), { skip_special_tokens: true });
'''

Transformers.js 4.3 or newer is required for WebGPU in Safari 26.

See the [base model card](https://huggingface.co/ibm-granite/granite-speech-5.0-2b) for the supported tasks, prompts and languages.

## How it was made

granite-speech-5.0-2b has the same architecture as granite-speech-4.1-2b, except that the language model's rotary position embeddings use YaRN scaling (factor 4, up to 16384 positions). These files reuse the graphs of [onnx-community/granite-speech-4.1-2b-ONNX](https://huggingface.co/onnx-community/granite-speech-4.1-2b-ONNX) with every weight re-derived from the 5.0 checkpoint:

- direct weight copies, BatchNorm folded into the encoder depthwise convolutions, and the constant-folded Q-Former query self-attention, all recomputed from the 5.0 weights;
- the decoder's rotary cos/sin caches regenerated from the model's own YaRN rotary embedding (16384 positions, attention scaling included);
- 4-bit quantization with the same recipe as the 4.1 files (it reproduces them byte for byte when applied to the 4.1 weights).

Checks:

- **fp32 conversion:** greedy transcripts identical to `transformers` on the bundled `multilingual_sample.wav` and LibriSpeech clips.
- **4-bit files:** 2.43% WER (2.31% normalized) on the 73-utterance `hf-internal-testing/librispeech_asr_dummy` set on the onnxruntime CPU EP, vs 2.70% for the 4.1 ONNX files under the same pipeline.

The decoder's logits are 1/8 of `transformers`' logits, the same as the 4.1 ONNX files; this does not change greedy decoding.

 Architectural principles

 Tool access: A subscribed tool call succeeds, and a call to a tool outside the agent’s subscription is denied with the expected error.

 Identity: A request from another workstream’s account or identity is rejected.

 Release: The previous agent runtime version can be restored.

 Retirement: Teardown removes the agent’s runtime, memory, tool gateway, and tool grants in dependency order, and confirms nothing is left behind.

 Operating models and platform components

 Centralized: A single artificial intelligence and machine learning (AI/ML) team builds and runs every agent. Governance is consistent, but that team quickly becomes a bottleneck as the number of use cases grows.

 Decentralized: Each business unit builds and operates its own agents. Teams can move quickly, but without shared standards, controls tend to drift, effort gets duplicated, and cost visibility suffers.

 Federated: A central Platform team provides shared, governed services while domain teams retain ownership of their agents, tools, and data. This model balances team autonomy with consistent guardrails and is where most enterprises land.

Artificial Intelligence 

 Distributed training with Ray Train DLCs and EFA on EKS

 What usually stops PyTorch training from scaling out to a cluster is the container, not the model code. Every container needs the same CUDA runtime , a PyTorch build compiled against it, NCCL (NVIDIA Collective Communications Library), the Elastic Fabric Adapter (EFA) userspace libraries, the AWS OFI NCCL plugin that connects NCCL to EFA, and a Ray version the cluster operator agrees with. Building that image and rebuilding it each time one of those pieces moves is a project of its own, and it has nothing to do with the model you set out to train. The Ray Train Deep Learning Container (DLC) is that image, built by AWS. AWS assembles the stack, tests it as one unit, publishes it in Amazon Elastic Container Registry (Amazon ECR) Public and keeps it patched.

 Figure 1: One EKS cluster with a control plane managed by AWS, a CPU system node (m7i.xlarge) running the KubeRay operator and Ray head, and two EFA-enabled g6.12xlarge nodes in one Availability Zone. KubeRay builds it from one RayCluster manifest, Ray Train places eight workers, one per GPU, and inter-node collectives cross over EFA.

 Ray runs a job across machines as a single cluster with two roles. The Ray head coordinates and runs the global control store that tracks cluster state, the dashboard and job server you submit jobs to. Ray worker nodes supply the GPUs and run the training processes. Each worker joins the cluster by connecting to the head’s address when it starts. On Kubernetes, each of these is a pod. Kubernetes has no built-in idea of a Ray cluster, so something must create the head and worker pods, start Ray in the right role in each, point the workers at the head, and replace pods that fail. KubeRay does this. It’s an open source Kubernetes operator that adds a RayCluster resource: you describe a head group and a worker group in one manifest, and KubeRay builds and maintains the cluster from it.

 A single tagged image runs as both the Ray head and the Ray workers, whether KubeRay starts it on Amazon Elastic Kubernetes Service (Amazon EKS) or you start it yourself on Amazon Elastic Compute Cloud (Amazon EC2). What you add is configuration: which instances, how many GPUs each pod gets, which network transport NCCL uses, and which extra Python packages a job needs. All of it is set from outside the image.

 This post walks through a sample that uses the DLC exactly as published to fine-tune Qwen2.5-1.5B with PyTorch Fully Sharded Data Parallel (FSDP) across eight NVIDIA L4 GPUs on two g6.12xlarge instances. The training code is one function, the cluster is one RayCluster manifest plus a file of variables, and no image is built at any point. Because the DLC already carries the EFA stack, collectives between the two instances run over the EFA as soon as the pods request it. The entire solution is in this sample repository , and it uses the same KubeRay-on-EKS foundation as our multi-node Ray Serve walkthrough .

 No separate inference image family –  Ray Train shares the ray ECR repository with the Ray Serve DLC and Ray LLM DLCs , under the train-ml tag prefix.

 Figure 2: The sample’s cluster. Every pod runs the same Ray Train DLC from Amazon ECR Public. The CPU system node runs the KubeRay operator and a Ray head with no GPUs. Each EFA-enabled g6.12xlarge, both in one Availability Zone, runs a single four-GPU Ray worker pod.

 All nodes sit in private subnets of one virtual private cloud (VPC) and reach the internet only through a NAT Gateway, which is how every node pulls the DLC from Amazon ECR Public and how workers download model weights from Hugging Face. One m7i.xlarge forms the system node group, hosting kube-system add-ons, the KubeRay operator and the Ray head. The head runs the job server on port 8265 and Ray’s control store on 6379, and it advertises no GPUs, so no training work lands on it. Jobs are submitted from inside the head pod with kubectl exec , through the EKS API, so port 8265 is never exposed outside the cluster.

 Training runs on two g6.12xlarge instances, each with four NVIDIA L4 GPUs, 48 vCPUs, 192 GiB of memory, 40 Gbps of networking and one EFA interface. Each runs one Ray worker pod that claims all four GPUs and the EFA interface, and Ray Train places four workers in each pod: ranks 0–3 on one instance, 4–7 on the other. Because EFA traffic doesn’t cross Availability Zones, the scripts place both instances in a single zone that has been checked to offer g6.12xlarge.

 What Ray Train does inside the container

 The DLC provides the stack. Ray Train provides the part that would otherwise be launcher code. Multi-node PyTorch normally means starting a process per GPU on every host and giving each one its rank, the world size and a rendezvous address. With Ray Train you write the training loop as a function and pass it to TorchTrainer with a ScalingConfig . Ray starts one worker per GPU wherever the cluster has GPUs, forms the torch.distributed process group, and runs your function on each worker.

 This sample asks Ray Train for FSDP , which splits the model’s weights, gradients and optimizer state across all eight GPUs rather than copying them to each one. Qwen2.5-1.5B in bfloat16 needs about 12 GB for those four tensors. Sharded eight ways, each L4 GPU holds roughly 1.5 GB. The price is communication: FSDP gathers each layer’s weights before using it and reduce-scatters gradients afterwards, so the whole model crosses between ranks on every step. Between the two instances, that traffic is what the DLC’s EFA stack carries.

 Accelerating software delivery with agentic QA automation using Amazon Nova Act – Part 3

 As quality assurance (QA) automation adoption grows inside an organization, a new problem appears that has nothing to do with writing tests. A platform team stands up test automation, then a second team wants to join, then a dozen more. Soon hundreds of test cases belong to different products and squads, and everyone can see everyone else’s tests. No one can answer a basic question at a glance: is this application’s test coverage healthy right now? Test authoring stops being the bottleneck. Organizing tests and controlling who can touch them becomes the work.

 A second, related question follows close behind: who owns this application and its tests, and who is accountable when coverage slips? Without a clear owner, health problems have no one to land on.

 In the first post , we introduced QA Studio, a reference solution built with Amazon Nova Act . Teams use it to define tests in natural language and run them through AI-powered visual navigation. In the second post , we added test suites and a CLI for batch regression testing in continuous integration and continuous delivery (CI/CD) pipelines. In this post, we cover two capabilities that help QA Studio scale across an organization. The first, applications , organizes tests and reports health metrics. The second, team-based user management , controls who can see and change what.

 Organizing tests with applications

 An application in QA Studio represents the system under test: a website, a web app, a service front end. It’s the container that gives a collection of tests, a home, and an owner. Use cases (the individual tests from Part 1) and test suites (the regression collections from Part 2) belong to an application, and they inherit its ownership. Instead of one flat list of every test in the deployment, each team works inside the applications they own.

 Creating an application takes a name, a base URL, and an optional set of environments such as development, staging, and production. From the application page, teams create new use cases directly in context, add existing ones, and group them into test suites. This is also where QA Studio reports on the health of the tests it runs.

 Figure 1: The application detail page, showing pass rate, executions, and failures with the use cases and test suites tabs

 Understanding application health with metrics

 Tests produce results. Understanding those results over time is what tells a team whether the development lifecycle for an application is healthy, not only whether a single build is ready for release. QA Studio records the outcome of every execution as Amazon CloudWatch custom metrics, dimensioned by application and by environment. It turns these metrics into a health view on the application page.

 The top of the page answers the immediate question with three figures: the pass rate over the selected window, the total number of executions, and the current failure count. Alongside them, QA Studio computes a health score of 0–100. The score starts from the pass rate and subtracts a penalty for flaky tests. That way, an application whose tests pass but flip between pass and fail doesn’t present a falsely perfect picture. A team scanning a portfolio of applications can tell the stable ones from the ones that need attention without opening each result.

 The metrics tab moves from the current snapshot to trends. Teams choose a 7-day window with hourly granularity or a 30-day window with daily granularity, and QA Studio charts executions, successes, failures, and average duration across that period. Because the underlying metrics carry an environment dimension, teams filter the view to a single environment. For example, they can compare how staging behaves against production for the same set of tests.

 Two views target the tests that cost teams the most time. The flaky tests view ranks use cases by how often they flipped between passing and failing over the last seven days. This surfaces the intermittent failures that erode trust in a suite before they turn into a production miss. The recent failures view lists the latest failed executions for quick triage. Each one links back to the Amazon Nova Act trajectory logs and session recordings described in Part 1. That way, moving from “this test is failing” to “here is exactly what the agent saw” takes one click.

 Controlling access with teams and roles

 Metrics tell a team how their applications are doing. Team-based user management decides which applications are theirs in the first place. QA Studio organizes access around teams, and an application belongs to exactly one team. Members of that team work with its applications. Everyone else doesn’t see them.

 Every team member holds one of five roles, and each role includes the permissions of the ones below it:

 Admin : Studio-wide access to every team, application, and user, including creating teams and assigning applications. Admin is a studio-wide role rather than a per-team assignment.

 Team Lead : Manages their own team members and creates applications for the team.

 Editor : Creates and edits use cases and test suites within the team’s applications.

 Executor : Runs use cases and suites but doesn’t modify them.

 Viewer : Read-only access to the team’s applications and results.

 Because roles are cumulative, a Team Lead has everything an Editor has, and so on down to Viewer. Access to a use case or a test suite follows the application that contains it. If a member can work with the application, they can work with its tests, bounded by their role. This keeps permission management at the application level instead of on thousands of individual tests.

 An administrator sees the whole studio. The Users page lists every account with its team and role in one place.  Sharing applications between teams

 Teams rarely work in complete isolation. A platform team might own an application that a feature team needs to run against, without handing over the ability to change it. QA Studio supports this with shared access: the owning team grants another team access to an application at a view, execute, or full level.

 Shared access follows a ceiling rule. A user’s effective permission on a shared application is the lower of their own role and the level of the grant. A Viewer who is given full access to a shared application remains view-only, because their role is the ceiling. This way, an owning team can share widely without granting more than a recipient’s role allows.

 Why financial research is hard to automate 
 Financial research looks like a search problem, but it has features that break simple approaches.

 The answer lives in the layout. Take a 10-K, the annual report that US public companies file with the Securities and Exchange Commission, covering the business, its risks and its audited financial statements ( what a Form 10-K contains ). Questions do not always come in the document's language. Teams that cover several markets often ask in one language about documents written in another.

 The solution is a research assistant that answers questions about a collection of filings and shows for every claim, the page it came from. It uses four models, each with one job:
 Cohere Embed turns each page, and each question, into a vector which is a list of numbers that captures its meaning, so that pages about the same thing as the question sit close to it.  Upgrading from legacy APIs? The legacy GPU delegate and custom delegate APIs are deprecated in favor of CompiledModel GPU acceleration and the Compiler Plugin and Dispatch APIs, and NNAPI will be removed starting in 2027. Older SDKs now receive critical security fixes only. Apps you've already shipped keep working, but plan your move to the CompiledModel API now: code that uses deprecated APIs won't compile against the latest SDK, and staying on an older SDK can cause conflicts as your other dependencies move forward.
