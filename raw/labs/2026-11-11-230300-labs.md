Artificial Intelligence 

 Introducing usage-based pricing for Amazon SageMaker AI bidirectional streaming

 Usage-based metering for bidirectional streaming solves a software billing problem for real-time speech AI. Customers deploying streaming models on Amazon SageMaker AI bidirectional streaming pay for the endpoint infrastructure that hosts the model. Separately, model providers listing on AWS Marketplace need a way to charge for what customers consume during a live stream. Today, we’re announcing usage-based metering for Amazon SageMaker bidirectional (bidi) streaming inference, so model providers can report actual usage for the AWS Marketplace software charge. Amazon SageMaker AI endpoint infrastructure charges still apply.

 Deepgram , the real-time speech AI company, is the launch partner for this capability, bringing usage-based Speech-to-Text (STT) and Text-to-Speech (TTS) billing to AWS Marketplace. This post builds on a series of innovations between Deepgram and AWS. First, we introduced bidirectional streaming for real-time inference on Amazon SageMaker AI , which supports long-lived bidirectional streams between clients and model servers. Then, Deepgram enhanced Amazon SageMaker AI support with AWS Identity and Access Management (AWS IAM) temporary delegation , simplifying secure authentication for enterprise deployments, and expanded observability with enhanced metrics . Now, with usage-based metering, we further strengthen the foundation for production real-time AI, aligning billing with how customers consume streaming and real-time AI workloads.

 Why streaming broke the existing billing model

 With AWS Marketplace software metering for SageMaker AI real-time request-response inference, model providers can report a unit count in an HTTP response header. AWS Marketplace uses that quantity for the software charge. This works for request-response APIs where the billable quantity is known when the response is sent.

 Bidirectional streaming is different. A client streams audio and receives transcriptions through the SageMaker AI API using an HTTP/2 event stream. SageMaker AI connects to the model server over WebSockets. A session can last 30 seconds or 30 minutes. Usage accumulates as the session runs, and the final total isn’t known until it ends. A response header alone can’t report periodic usage during that live session.

 Hourly software pricing can charge customers while a model is available, including quiet periods. With usage-based metering, providers can align the AWS Marketplace software charge with reported usage. SageMaker AI endpoint infrastructure charges remain separate and continue to apply while the endpoint is provisioned.

 How companion metadata streaming works

 The solution introduces a second WebSocket connection alongside the existing inference stream. When a bidirectional streaming session starts, SageMaker AI establishes two connections to the model server:

 Data connection : carries inference request and response data, the existing bidirectional stream.

 Metadata connection : a companion WebSocket dedicated to metering data.

 Model servers opt in by returning one header on the WebSocket upgrade response:

 X-Amzn-SageMaker-Metadata-Stream-Supported: true 

 SageMaker AI then opens a companion WebSocket to the model server at /invocations-bidirectional-stream-metadata . Both connections carry the same X-Amzn-SageMaker-Request-Id header, which the model server uses to correlate metering records with the active inference session.

 The model server sends metering data as JSON text frames on the metadata connection. Send records at a frequency that matches the billing model: incrementally as usage accrues (recommended), either as each unit is consumed or as periodic batches of units consumed since the previous record. Send any final record as soon as the session ends. Each frame contains exactly one metering record, rather than an array of records. The metadata stream has a rate quota of one message per second per connection, with a maximum message size of 512 bytes.

 We recommend sending metering records incrementally as usage accrues. This reduces the amount of usage left unreported if a session ends unexpectedly. Transport delivery alone does not establish that usage has been billed. Validate reported units against AWS Marketplace reports and buyer charges.

 {
 "Metering": {
 "Dimension": "inference.count",
 "ConsumedUnits": 720,
 "ClientToken": "a3f2b1c0-unique-uuid"
 }
} 

 Metering messages use the inference.count dimension, and ConsumedUnits supplies the quantity for that dimension. If the product charges per second of audio, a record reporting 12 minutes of metered audio carries 720 seconds as ConsumedUnits: 720 . The dimension name doesn’t mean one unit per request. The provider defines which audio counts as metered usage, and the AWS Marketplace offer maps the unit to its price. The listing shows one price per unit, labeled per request, with up to three decimal places. The ClientToken field supports idempotency. If a duplicate token arrives on the same connection, SageMaker AI drops the duplicate message silently.

 The metadata connection runs over TCP, which provides ordered, reliable delivery at the transport layer. If it fails to establish or drops mid-session, inference continues by default because X-Amzn-SageMaker-Metadata-Stream-Required defaults to false . Set this header to true when the provider must stop inference if the metadata stream becomes unavailable. This choice trades inference availability for metering continuity. It doesn’t guarantee that malformed or dropped records are billed.

 What this means for customers

 If you deploy real-time AI models for transcription, contact centers, voice agents, or captioning, the new metering model changes how the AWS Marketplace software charge is calculated. SageMaker AI endpoint infrastructure charges still apply.

 Transparent, per-unit billing through AWS Marketplace means usage flows directly into your AWS bill. You get consolidated AWS billing, negotiated rates through private offers, and no separate billing relationship with the model provider to manage.

 Pay for audio processed according to the product’s unit definition. If the product charges per second of audio, 12 minutes of metered audio equals 720 billable seconds and ConsumedUnits: 720 . An open connection lasting 12 minutes doesn’t, by itself, define the billable audio quantity. The provider’s counting rules determine the metered usage, whereas endpoint infrastructure charges remain separate.

 Model providers can offer negotiated per-unit rates or fixed-price contracts through AWS Marketplace private offers.

 We recommend discussing directly with your AWS account representative or partner representative.

 What this means for model providers

 If you’re a model provider listing on AWS Marketplace, you can configure your model server to report usage during streaming inference sessions through companion metadata streaming.

 The SageMaker Marketplace Onboarding Agent Skill accelerates onboarding with an opt-in inference metering path. Its starter templates advertise metadata-stream support and build validated, incremental ConsumedUnits frames for the companion WebSocket. Review and production-harden the code before submission.

Artificial Intelligence 

 UAEF: A framework-agnostic system for closed-loop evaluation of AI agents

 Teams building AI agents on AWS use a range of frameworks, including LangGraph, LangChain, Strands Agents, and Amazon Bedrock AgentCore. Each framework records agent execution in its own way, so the structure of messages, tool calls, and handoffs between agents differs from one to the next. Evaluation tooling tends to follow the same boundaries: teams build metrics, scoring logic, and result storage against a single framework’s trace format, and they must rebuild them when they switch frameworks or run agents on more than one.

 This coupling makes a basic development question harder to answer: did a change to the prompt, model, or tools improve the agent? Answering it requires consistent metrics across versions of an agent and a shared record of past results to compare against. Agent quality also spans several dimensions that a single accuracy score does not capture: tool calling, response quality, responsible AI, performance, multi-turn conversation, multi-agent coordination, and reasoning.

 In this post, we introduce the Universal Agent Evaluation Framework (UAEF). Customers across 12 organizations in the telecom, healthcare, and financial services industries used UAEF to evaluate their AI agents with one consistent set of metrics and compare agent versions before release. UAEF is a framework-agnostic evaluation system: it uses adapters to convert traces from each framework into a common format, then scores those traces with 36 built-in metrics across 7 dimensions. It stores the results in Amazon DynamoDB and Amazon Simple Storage Service (Amazon S3) and generates reports and insights that inform the next iteration of the agent. This post describes how UAEF works, provides a playbook for choosing metrics and preparing datasets, and points to runnable notebooks for each supported framework.

 UAEF: One evaluation layer for agent frameworks

 UAEF is a framework-agnostic evaluation system for AI agents. It takes the agent a team already has and scores it the same way across supported frameworks and runtimes. UAEF takes two inputs: the agent under test and a dataset to run it on. The dataset provides the inputs for each test case, and it can also include ground-truth answers, the expected output for each input. Ground truth is optional, and only metrics that compare the agent’s response against a reference use it. To evaluate tool calling, the ground truth must also include the expected tool calls for each test case: which tools the agent should call, in what order, and with what arguments. Everything after that happens inside the UAEF.

 Figure 1 shows the path a single evaluation takes, from the inputs to the reports and insights. First, an adapter reads the agent’s native execution, its messages, tool calls, and agent-to-agent handoffs, and normalizes it into one canonical trace, so that the steps that follow are identical no matter which framework produced the agent. Next, UAEF screens the trace for personally identifiable information (PII), such as email addresses, phone numbers, and credit card numbers, before data is stored. The evaluation engine then scores the trace on a selection from 36 built-in metrics across 7 quality dimensions. When you persist a run, UAEF records it as an experiment in Amazon DynamoDB and Amazon S3: Amazon DynamoDB holds the per-experiment metadata used for listing and comparison, and Amazon S3 holds the full results. With runs stored, a team can compare an agent version against a baseline to detect regressions and generate reports and insights that explain what changed and why. Those reports close the loop: the team evaluates the agent, learns what regressed or improved, changes the prompt, model, or tools, and evaluates again.

 Figure 1: UAEF closed-loop evaluation data flow

 The rest of this section follows that flow in order: the adapters that make UAEF framework-agnostic, the evaluation engine and its metrics, PII detection, experiment storage and comparison, and the reports that close the loop.

 Canonical trace and adapters

 Adapters are what make UAEF framework-agnostic. An adapter reads the record of an agent’s run, including its messages, tool calls, and agent-to-agent handoffs. It converts that record into one canonical representation called the AgentTrace , which is the only thing the rest of UAEF scores. Because of that conversion, UAEF works with the agent, whatever SDK it was built with (such as LangGraph, LangChain, or Strands Agents). It can run locally, behind an HTTP endpoint, or on a managed runtime such as Amazon Bedrock AgentCore, with traces in Langfuse or not captured at all. UAEF provides an adapter for each of these, and they produce the same AgentTrace , so metrics, scores, and comparisons stay consistent across every one of them.

 A trace reaches UAEF two ways. If one already exists, from a past run, a log, or an observability store, it is handed to UAEF and the matching adapter normalizes it. If not, UAEF invokes the agent for you: given a runtime Amazon Resource Name (ARN) or an HTTP endpoint, it calls the agent on each dataset input, collects the response, and adapts it in one step. Either way, the output is the same AgentTrace .

 Because every metric, mode, and report operates on the AgentTrace rather than on a framework native format, the scoring that follows is identical no matter where the trace came from. That separation, normalization first and scoring second, is what lets a team compare an agent built on one framework against an agent built on another on a single scale.

 Evaluation engine

 The evaluation engine scores a canonical trace across 7 quality dimensions, each capturing a distinct aspect of agent behavior that a single accuracy number would hide. Tool calling measures whether the agent selected the right tools, called them in a sensible order, and passed valid arguments. Response quality measures whether the final answer is relevant, complete, accurate, and grounded in the provided context rather than hallucinated.

 Responsible AI measures safety, bias, toxicity, and resistance to prompt injection. Performance measures operational cost in latency, token use, and throughput. Multi-turn measures how well the agent sustains a conversation, including context retention, coherence, and goal completion across turns. Multi-agent measures coordination in systems of cooperating agents, such as task delegation and the division of work. Reasoning measures the internal logic of the agent’s chain of thought, including consistency and freedom from fallacies.

 Each dimension is computed by one or more of 36 built-in metrics, and every metric returns a normalized score in the interval [0, 1], where 1 is best, so dimensions and the overall result share one scale. Metrics come in two families. Deterministic metrics compute a score directly from the trace and the ground truth and reproduce exactly on repeated runs. Large language model (LLM)-as-a-judge metrics score qualities that resist a closed-form definition, such as response relevance or safety, by prompting a judge model on Amazon Bedrock. You can also add your own custom metrics or draw on the RAGAS and DeepEval integrations.

 Because judge metrics feed an agent’s own output back into a prompt, that content is treated as untrusted input: an agent that can influence its judge can influence its own scores. The rubric is sent separately from the content, and the content is escaped so it cannot break out of its delimiter and be read as instructions. Each judge response is parsed strictly and must cite a verbatim span of the content it scored. A score whose evidence is not found is rejected rather than recorded. Judge scores are evaluation signal, not a safety decision, and should not gate a security control. For runtime enforcement on the agent itself, apply Amazon Bedrock Guardrails in its own invocation path. The full model is in SECURITY.md.

Calling evaluate() or batch_evaluate() with persist=True creates a new experiment, identified by an optional name and objective, and writes it to two stores with complementary roles. Amazon DynamoDB holds one row per experiment with the metadata used for listing and comparison: evaluation count, the average score per metric, and an overall average.  The Python library also models a finer-grained structure. An experiment contains runs, and each run records the agent design under test: framework, model, tools, system prompt, and parameters. A run can also record a configuration snapshot and a Git commit. You can mark one run as the baseline for its experiment. This ties each score to the change that produced it, whether a new prompt, a different model, or an added tool.

 Comparison works on the stored per-metric averages. For each metric that two runs have in common, the comparison engine calculates the absolute and percentage change. It then classifies the metric as a regression, an improvement, or unchanged, using a configurable threshold with a default of 5 percent. It groups regressions by dimension, which shows, for example, whether a prompt change affected tool calling but not response quality.

 Key takeaways

 AWS's Tiros automated-reasoning tool can analyze the topology of a deployed AWS Cloud WAN network as often as every hour. It gives a mathematical demonstration that the network matches its isolation specifications, with no dynamic packet sampling.
 Tiros works from Cloud WAN route tables, attachments, and policy documents, which specialized software converts into logical propositions. Tiros then derives the reachable paths, and the system alerts an operator if reachability differs from the expected segmentation. 

 Was this answer helpful?

 Corporations, banks, hospitals, and academic institutions all rely on wide-area networks (WANs) to connect their local networks across geographic regions. Within a WAN, however, it’s often necessary to isolate different computational resources from each other: for example, coding environments used to test new website features should remain separate from active websites.
 Customers rely on such isolation — or segmentation — to help protect sensitive data; a single misconfiguration of segmentation rules could allow traffic to reach unintended parts of a network or allow data to cross organizational boundaries.
 Historically, validating network segmentation has involved mapping the network by sending packets through it. The size and complexity of modern networks, however, make it impractical to build a complete map this way, so organizations instead rely on a sampling process that sends packets through only portions of the network. The result is that network segmentation is rarely validated exhaustively.
 By using Tiros, Amazon Web Services’ automated-reasoning tool for analyzing network connectivity, we’re offering an alternative to dynamic sampling that is designed to validate segmentation across all modeled paths.
 Previously, Tiros had been used in customer-facing services such as Amazon Inspector, VPC Reachability Analyzer, and Network Access Analyzer. These services focus on reachability, or determining whether some sequence of valid requests leads from one network resource to another. Our key insight is that if we can determine the reachable paths in a network, then we can also identify the absence of paths between particular resources.
 Fundamentally, automated segmentation validation is a static process: it examines a network without relying on dynamic packet traffic. Using Tiros, we can analyze the topology of a deployed network as frequently as every hour. These analyses provide a mathematical demonstration that the topological description aligns with our isolation specifications.
 Automated segmentation validation 

 In modern networking, a virtual network sits on top of the physical network of servers and wires and other components. Segmentation is achieved through logical rules and routing policies rather than physical isolation of network hardware.
 We consider the case in which an Amazon Web Services (AWS) customer is using the AWS Cloud WAN service to configure and deploy a large organizational WAN. To validate network segmentation using Tiros, we first collect the customer’s Cloud WAN configuration from route tables, “attachments” (which are like a virtual cable within the network), and policy documents. Specialized software converts these configurations into logical propositions that describe network behavior. Now, we have a configuration that’s expressed logically, so that automated reasoning tools can analyze it.
 Then we ask Tiros, “Which attachments can reach which attachments with which destination IPs?” Tiros generates the satisfying assignments it can derive from the network description, each of which corresponds to a path. Our system checks that no path exists between segments that the policy declares should be off limits from each other. If actual reachability matches the expected segmentation, the validation check succeeds; if they differ, the system alerts an operator.
 Virtual private clouds and network predicates 

 Consider a global company that uses Cloud WAN to connect resources all over the world and manage a website for selling and supporting its products. When the company updates its website, it does so from a replica of the public-facing website inside the development environment within Cloud WAN. The production environment needs to be strictly contained, so that tests and changes not yet ready for deployment don’t reach the live website, which is maintained in the separate production environment. So the company’s software developers write a policy, or a collection of logical rules, that captures the need for this segmentation.

 The policy defines two segments, production and development, across two regions, us-east-1 and us-west-2, as in the figure above. Attachment policies use tags to assign Virtual Private Clouds (VPCs, logically separated networks within larger networks) to various other network segments. In this policy, VPCs are tagged such that VPC-prod-use1 and VPC-prod-usw2 join the production segment and VPC-dev-use1 joins the development segment, as in the figure.
 Observe, also, that in the figure, VPC-prod-use1 and VPC-dev-use1 are destinations within the same address space, 10.0.0.0/16. In this context, segmentation becomes critical; if the VPCs were deployed within the same segment, or segmentation was misconfigured, a packet destined for that address space would have a nondeterministic destination, VPC-prod-use1 or VPC-dev-use1. Practically speaking, such a misconfiguration could cause customer traffic to erroneously arrive in a development VPC.
 Using Tiros, we take the core network configuration above and build a logical model of the network composed of rules (conditional predicates) and facts (unconditional predicates). Once the model is built, we can query Tiros for the instances of segmentation it derives for the attachments in the model.
 When given predicates, facts, and a query, Tiros generates the assignments associated with each VPC and IP for which the query is provable within the model. If, for instance, Tiros finds no assignment where a production VPC reaches a development VPC, or a development VPC reaches a production VPC, then the results indicate that the core network’s segmentation aligns with the stated policy.
 Future work 

 Segmentation validation demonstrates how automated reasoning can provide the kind of assurance that packet-based testing cannot. By encoding network configurations as logical propositions and using Tiros to explore the possible paths in the model, we can check segmentation against the stated policy rather than just sampling it. Customers do not need to run separate reachability tests.
 This approach is not unique to Cloud WAN. Across AWS, automated reasoning is used to analyze properties of systems that are too large to test exhaustively. Using an engine called Zelkova, IAM Access Analyzer helps you identify whether a policy could grant access to a resource from outside your account and uses the same reasoning to help identify S3 buckets that are shared publicly or with other accounts. Similarly, VPC Reachability Analyzer helps determine whether one resource can reach another in your network. They all share the same foundation: translating configurations into logic and checking whether the properties you care about hold.

 IBM is building the world’s first fault-tolerant quantum computer, IBM Quantum Starling. Slated to launch in 2029, Starling will be capable of running quantum circuits comprising 100 million quantum operations on 200 qubits.

 The framework for Starling was described in a 2025 paper , which presented a path to achieve fault tolerance by creating hardware to implement the bivariate bicycle quantum low-density parity check (qLDPC) error correction codes introduced by IBM in a 2024 Nature publication . Critically, the code is implemented in a modular fashion to enable scalability beyond what could be achieved with a monolithic architecture.

 The modular architecture detailed in the paper offers an order of magnitude reduction in resource requirements compared to prior approaches. For the same logical error rate, Starling’s qLDPC architecture requires about 10x fewer physical qubits. It is constructed by assembling modules that each contain a quantum memory and logical processing unit (LPU), which allows logic operations on the memory. The modules have universal adapters that allow them to be connected using l-couplers. Additionally, sophisticated modular cryogenic and control systems house and run the modules at ultra-cold operating temperatures.

These steps forward are being delivered in parallel, though not in isolation — lessons from one component influence the progress being made on the others. Taken together, the work outlined below represents major progress toward building Starling and delivering on the promise of fault-tolerant quantum computing.

 Device physics

 IBM Quantum Loon was announced a year ago to demonstrate many of the key components needed to implement IBM’s qLDPC codes, including qubit reset circuits and “c-couplers” to link qubits across the chip, a prerequisite for establishing the six-way qubit connectivity needed to implement the qLDPC code.

 Since then, Loon was measured to have qubit relaxation times (T1) of about 200us with reset time constants of 20ns–40ns. Its gates had median error rates near 0.3%. The ultimate aim for Starling is to have T1 in the millisecond range and gate errors in the low 0.01% range. The physics of the device are designed to enable this low error rate. In fact, we routinely measure gate errors in the high 0.01% range on Heron and Nighthawk — going as low as 0.04%. Transferring coherence times from our test devices, which are currently in the single digit millisecond range, will also help facilitate lower error rates.

 It is also important to understand how much loss the c-coupler layers introduce so we can estimate gate error limits. The results here are also very promising. The resonators had quality factors above 10 million, which is beyond the goal needed for Starling. Adding to this, it was found that traversing c-coupler layers only resulted in a minimal reduction in quality factor, meaning it was possible to increase the number of c-coupler layers being used in the chip. Originally two were being used, but that has now increased to three with plans to reach four or more. Adding additional layers will enable more complex routing and can effectively shorten some of the longest connections c-couplers need to make.

 The results above verify that c-couplers are a viable approach to enabling non-local, dense connections for quantum processors.

 QPUs

 Advances have also been made in how quantum processing units (QPUs) can be put together.

 In particular, there have been two exciting developments related to overall device yield and complexity. First, improvements to the qLDPC code made it possible to have only five connections between qubits instead of six — while also delivering 20x-100x lower logical errors. Second, with further coupler innovations, we discovered ways to reduce the number of Josephson junctions. Bringing these advances together, the number of Josephson junctions needed has been more than cut in half, dropping from around 5,000 to 2,000.

 This junction reduction means that our device yield will increase. With a junction yield target of 99.95%, we find that about 1 out of 12 processors will be fully functional with 5,000 junctions, but 1 out of 3 processors will be fully functional with 2,000 junctions — a factor of 4x increase. Having fewer junctions will also help lower the spread of required critical junctions across the device.

 Lastly, the length of the c-coupler has been increased to 20mm, which helps loosen some of the strict density requirements of qubits and couplers on a quantum processor.

 This combination of exciting results demonstrating high quality factors within and across c-couplers, the improved code, and device yield improvements led us to redesign the modular processors. The new designs lower the risk and increase yield for the modular qLDPC code processors and hence will benefit Starling. A year ago, it would not have been possible to envision this, showcasing how ongoing innovation pushes us toward ever better designs.

 The strong results for c-coupler performance and the ability to reduce the number of Josephson junctions offered ways to improve future quantum processor designs.

 Modular decoders

 Decoders, classical algorithms used to identify errors in quantum circuits, are needed to achieve fault-tolerant quantum computing. IBM introduced the decoder Relay-BP in 2025 and showed that it could deliver a better logical error rate than leading alternatives while simultaneously lowering compute requirements for decoding. Now, IBM researchers have extended Relay-BP to demonstrate that errors for memory-only operations and measurement operations are nearly consistent. In fact, the performance we observe already meets the requirements for Starling.

 To run Relay-BP on Starling, IBM is creating a real-time decoder ASIC leveraging 2nm nanosheet technologies. This custom chip will deliver improved logical error rates to increase Starling’s performance.

 Inter-module connectivity

 To scale to a large number of error-corrected qubits, the processing modules for Starling need to be linked with long-range connections called l-couplers.

 IBM recently connected two Nighthawk processors using four l-couplers, as described in this paper , achieving an average 1% error rate with the best result being 0.7%. Linking multiple Nighthawk processors together is a crucial step toward scaling to larger systems that can do useful work. Relative to prior demonstrations, the raw error rates have improved by about a factor of 2x, but the key outcome is the repeatability of attaching l-couplers to processors. Everything must be assembled in a way that does not undo careful microwave engineering so that coupling strengths and dephasing rates are consistent.

 Starling will ultimately need over 100 l-couplers per module with 0.1% error rates. This is why progress on improving reliability and repeatability is an important step.
