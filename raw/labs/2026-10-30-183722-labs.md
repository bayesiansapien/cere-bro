> **One compact 4B policy that knows when to click — and when to code.**

Computer-use agents (CUAs) that confine themselves to pixels pay a heavy tax: a single screenshot consumes thousands of tokens, and re-deriving structured file edits through dozens of mouse clicks discards the fastest, most verifiable channel on the machine. Conversely, giving a frontier model naive access to both GUI and terminal tools does not automatically produce hybrid competence — without an optimized execution scaffold, even frontier teachers exhibit suboptimal channel habits that transfer directly to distilled students. Worse, existing CUA post-training pipelines rely on checkpoints already heavily specialized for GUI grounding and coding.

**Mage-VL-Cowork** bridges this gap. Trained end-to-end from an intermediate **4B [`Mage-VL`](https://huggingface.co/microsoft/Mage-VL)** checkpoint through a progressive **five-stage specialize-then-unify curriculum**, it combines screenshot-grounded GUI interaction (`computer_use`) and persistent code/terminal execution (`bash`) inside a **single vision-language policy** — with no external orchestrator. Upstream of training, we **evolve the teacher harness** (pruning redundant action routes and equipping domain libraries) and build **Mage-CUA-Forge**, a workflow-first synthesis engine that generates **293,806 tasks** across **6,915 atomic skills** while cutting recurring per-task generation cost by **82.6%**.

At **4B parameters**, **Mage-VL-Cowork** reaches **66.0% on OSWorld-Verified** under a 50-step budget — achieving the **best performance among 4B models** and demonstrating that an **efficient small VLM can excel at complex computer use**, pushing the frontier of **on-device intelligence**. Across training stages, online reinforcement learning adds **+10.16 percentage points** over Hybrid SFT while simultaneously cutting mean model calls by **13.0%** and output tokens by **25.4%**.

## ✨ Highlights

- **Best-in-class 4B hybrid computer use (66.0% OSWorld-Verified).** Achieving the highest score at the 4B scale, `Mage-VL-Cowork` proves that an efficient small VLM can master end-to-end computer use — leading on **Operating System tasks at 87.5%**, reaching **62.7% on Multi-Application Workflows**, and advancing the frontier of **on-device intelligence**.
- **Internalized turn-level channel routing.** Without an external multi-agent router, the policy dynamically selects `computer_use` for visual layouts, canvas editing, and live in-memory application state, and switches to `bash` for structured programmatic edits (spreadsheets, documents, presentations) and deterministic ground-truth verification.
- **Evolved teacher harnesses amplify student distillation (+12.5 pp).** Evolving and pruning the teacher scaffold before rollout (removing overlapping tools like `xdotool` and accessibility trees while pre-installing domain Python libraries) lifts the GPT-5.4 teacher to **92.0%** with **29.2% fewer steps**, which expands into a **+12.5 pp student gain** (37.6% vs. 25.1%) at the 4B scale.
- **Workflow-first synthesis at −82.6% recurring cost.** **Mage-CUA-Forge** authors reusable, skill-conditioned generation workflows and application-specific preparers once per skill rather than running open-ended agent loops per task — reducing token consumption by **93.3%** (1,276K → 85K tokens/task) and expenditure from **$0.906 to $0.158 per task**.
- **Specialize-then-unify five-stage curriculum (+20.44 pp).** Starting from an intermediate 4B `Mage-VL` checkpoint, the model builds standalone visual grounding (**30.6% → 56.9%** on OSWorld-G; **78.8% → 87.2%** on ScreenSpot-v2), GUI execution, and coding/terminal competence before unifying them via Hybrid SFT and asynchronous Online Hybrid RL (**45.56% → 55.84% → 66.0%**).
- **Stronger *and* more compact after Online RL.** Online GRPO with verifiable task rewards improves task accuracy by **+10.16 pp** over Hybrid SFT while compressing interaction length from **21.57 to 18.77 model calls** (−13.0%) and output tokens from **7,374 to 5,499 per task** (−25.4%).

### 1. Evolved Hybrid CUA Harness
A strong teacher model does not automatically produce clean hybrid supervision. Before large-scale trajectory collection, an authoring agent evolves the external harness $\mathcal{H} = (\mathcal{F}, \mathcal{T}, \mathcal{P}, \mathcal{E})$ — refining the execution scaffold $\mathcal{F}$, tool interfaces $\mathcal{T}$, system prompt $\mathcal{P}$, and pre-installed terminal environment $\mathcal{E}$ (equipping domain packages such as `python-pptx`, `openpyxl`, `pandas`, `pypdf`, and `pillow` while removing redundant tools like `xdotool` and verbose accessibility dumps). We instantiate specialized **GUI**, **Terminal**, and **Hybrid** harnesses to roll out the same synthesized tasks across training stages.

### 2. Workflow-First Environment Synthesis (`Mage-CUA-Forge`)
Instead of spending open-ended agent tokens to construct one task at a time, **Mage-CUA-Forge** invests authoring effort **once per atomic skill** to build reusable generation workflows and application-specific preparers. Shared specification branches coordinate input artifact creation, executable environment setup scripts, user instructions, and evaluation rubrics. For web and cross-application tasks, we pair desktop preparers with synthesized **InfiniteWeb** sites and deterministic, SQLite-backed **WebHarbor** replicas that reset cleanly before every episode. Across three student-feedback-guided rounds, the pipeline synthesizes **293,806 distinct tasks** (**38.24% multi-application**, **877,608 file references** across 278 file categories) and retains **318,837 verified hybrid trajectories** (68.19% GUI tool calls, 31.81% terminal tool calls).

### 3. Five-Stage Specialize-Then-Unify Curriculum
Rather than learning hybrid routing as a workaround for weak visual grounding, **Mage-VL-Cowork** builds two strong standalone channels first and then unifies them:

They simulate dynamic, time-evolving organizations with meeting histories, project timelines, email threads that develop over weeks, and organizational changes that unfold naturally. This temporal dimension is essential because a large class of Copilot queries are inherently time aware. Questions like “What did the team decide last Thursday?” or “What’s changed since the last quarterly review?” only produce meaningful evaluations if the underlying data has a genuine temporal structure.

 Industry specific simulation

 We generated three synthetic environments across multiple industries, each with distinct characteristics that mirror real world usage:

 A pharmaceutical environment that includes regulatory submission workflows, clinical trial discussions, and cross functional safety review meetings

 A capital markets environment featuring deal pipelines, compliance communications, and client portfolio reviews

 An IT/software company that simulates sprint planning, code review discussions, and product launch coordination

 Figure 3: Industries targeted for industry evaluation data generation 

 This industry specificity ensures that our evaluation queries test Copilot against the kinds of questions real users in those domains actually ask, rather than relying on generic test cases that may not surface domain specific failure modes.

 Automated query generation

 While synthetic environments provide the substrate for evaluation, they face a key limitation: we still need realistic evaluation queries. These are the questions that test whether Copilot can surface the right information, synthesize it correctly, and present it helpfully. Manually writing thousands of grounded, industry specific queries is prohibitively expensive and slow. That’s where our automated pipeline comes in.

 The six-stage pipeline

 Figure 4: Query customization pipeline that turns generic query templates into realistic, industry-specific queries 

 We built an automated pipeline that turns simple, generic query ideas into realistic, industry-specific questions for Copilot. It starts with a large library of common workplace tasks, narrows them down to what’s relevant for a given industry, and adapts them using domain-specific language and context. The system then uses AI to generate queries grounded in the synthetic environment’s data, rewrites them to sound more natural and human, and validates each one for accuracy and uniqueness. The result is a rich set of high-quality, lifelike queries that enable scalable and reliable evaluation of Copilot across real-world scenarios.

 Validating synthetic quality

 Of course, generating synthetic data is only part of the challenge. We also need to ensure the data is good enough to produce meaningful evaluations. We assess synthetic environment quality using our internal semantic evaluation framework which measures quality across three dimensions:

 Structural fidelity : Does the organizational structure reflect realistic reporting hierarchies, team sizes, and cross functional relationships?

 Contextual relevance : Are the queries and workflows representative of actual enterprise usage patterns?

 Behavioral realism : Do the simulated users exhibit human-like communication patterns and collaboration dynamics?

 Content safety : Is the generated content free of harmful, offensive, or personally identifiable material, and does it avoid impersonating real individuals?

 End-to-end automation

 While our synthetic environments and query pipelines provide the methodology, they face several practical limitations without proper automation, including:

 Reproducibility : Manual processes produce subtly different results each time, making it difficult to compare evaluations across releases.

 Scale : The number of industry verticals and configuration variants exceeds what any team can reasonably produce by hand.

 Iteration speed : Manual creation takes days, delaying essential feedback and slowing down development cycles.

 Cross-team consistency : Without standardized tooling, different teams produce evaluation datasets with incompatible formats and quality levels.

 This automation reduced evaluation dataset creation from a multi-day manual process to automated runs. We estimate savings of approximately $100,000 per evaluation dataset and $300,000 in total project savings. But the more important outcome is that any team can now regenerate an evaluation dataset from the same configuration and get identical results.

 Understanding coding agent success and failure 

 Coding agents execute user queries by reasoning about, editing, and running code. Understanding why these agents fail is critical if we want to build more capable and reliable coding agents. Unfortunately, existing benchmarks often make it difficult to identify which factors contribute to success or failure.

 CABRA is a framework for generating coding challenges from scratch. It lets researchers increase complexity in a controlled way and pinpoints the skills that are most difficult for agents.

 Across thousands of generated challenges, the researchers found that agents often overcame coding problems by using tools. Yet the agents still struggled when they needed to understand unfamiliar codebases. The findings suggest that understanding existing code, rather than modifying it, remains one of the biggest obstacles to developing more effective coding agents.

 Evolving agent skills with activity logs 

 Computer-use agents are AI systems that are designed to complete tasks that require clicking and typing. They can fill in forms, process requests, and navigate websites. To do this effectively, they need to learn the procedures that people use to get work done. User activity logs can offer a way to capture this knowledge. But activity logs typically don’t record the intent behind each action and often combine tasks.

 The new framework TeleTune learns reusable skills and workflows from these logs. It also infers the task goals associated with the sequences of actions.

 In evaluations across software and browser tasks, TeleTune outperformed existing approaches. By learning from existing activity, TeleTune offers a scalable way to help AI agents adapt to unfamiliar software and carry out complex, multi-step workflows

 Looking beyond similarities in AI use (opens in new tab) 

 Workers across industries may appear to be using AI in surprisingly similar ways, but a closer look reveals a different story.

 Microsoft researchers analyzed aggregated Copilot Chat activity across a broad range of customer categories and found that editing documents led all classified activities, accounting for more than 20 percent.

 But when researchers set aside the 20 most common activities, differences between customer categories became substantially more pronounced. The most common uses of AI may be hiding important differences in how organizations use it for more specialized work.
