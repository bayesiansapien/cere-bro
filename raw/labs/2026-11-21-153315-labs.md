Artificial Intelligence 

 Introducing managed cluster extensions for observability and user management in Amazon SageMaker HyperPod Slurm

 Keeping a shared Slurm cluster for foundation model development in sync entails keeping several separately maintained pieces of configuration matched to what’s running on the nodes. The cluster’s shape lives on multiple configuration files, its software in custom scripts, its network topology in files that must be edited as nodes change, and its users in a roster that an administrator must maintain and rerun. Over time these pieces drift away from what’s actually running, and nothing tells you when they do.

 We believe cluster configurations should be managed the way you manage the rest of your AWS infrastructure. You declare what you want through an API or the console, AWS validates it before it’s applied, the cluster is kept in that state continuously, and you can see whether it’s working. During 2026, Amazon SageMaker HyperPod brought that approach to Slurm clusters, with API-driven Slurm configuration, AMI-based configuration, continuous provisioning, automatic topology management, and deep health checks. Today, we launched cluster extensions, which bring the same approach to the software and settings on running nodes, with managed extensions for observability and user management. However, through all of it, you still keep full access to every node in your cluster, including the controller node. You can SSH in, configure nodes directly, and run your own lifecycle scripts. The APIs give you less to maintain, direct access gives you more control, and you choose the balance.

 In this post, we walk through the features we introduced in 2026 and explain why the software on running nodes needed a different mechanism. We then show how cluster extensions work, through both the API and the console, and follow a platform team through a quarter on a cluster that uses them.

 A declarative foundation for Slurm cluster operations

 We can think of a Slurm cluster’s configuration grouped into six layers. Five of them describe the cluster itself: its definition, node setup, capacity, network topology, and hardware health. The sixth covers the software running on its nodes, which we discuss in the next section. The following figure shows the six layers.

 Earlier in 2026, we brought declarative management to the first five layers. With API-driven Slurm configuration , administrators define node roles, partitions, and Amazon FSx for Lustre and Amazon FSx for OpenZFS mounts in CreateCluster and UpdateCluster requests, and connect an external accounting database . HyperPod updates partition settings while preserving other controller-node Slurm customizations. AMI-based configuration replaces routine setup scripts with images preconfigured with Slurm, Docker, Enroot, Pyxis, and home directories. A custom AMI or OnInitComplete script handles organization-specific software. Continuous provisioning for Slurm retries capacity requests in the background; AMI-based configuration works with it , minimum capacity requirements let teams specify MinInstanceCount, and cluster operations track scaling requests.

 Automatic topology management maintains the network layout as nodes scale or are replaced. On Slurm 25.11 or later, partition-level topology supports tree or block topology per partition. For hardware health, on-demand deep health checks stress GPUs and test NVIDIA Collective Communications Library (NCCL) connectivity, while deep health checks with continuous provisioning run as nodes are provisioned. Nodes under check stay in Slurm maintenance reservations until checks finish, keeping jobs off them.

 Introducing cluster extensions

 The five layers described so far are configurations that HyperPod can derive or apply once, when it provisions a node. The sixth layer, the software that runs on the nodes, behaves differently because it keeps changing for the life of the cluster. As researchers join and leave, a team asks for deeper GPU metrics for a week, and an exporter ships a fix. For this layer, lifecycle scripts have been the main mechanism so far, and they have drawbacks when the software keeps changing. A script runs only when a node is provisioned, so each change means editing it and then replacing nodes or rerunning it across the fleet. A mistake shows only when the script runs on a node, and nothing reports what’s installed, so nodes drift apart over time.

 We wanted the software to be declared in one place, checked when you submit it, kept consistent across nodes, and visible afterward. In November 2026, we launched cluster extensions, which are software packages managed by AWS that you install, configure, update, and remove through APIs or the Amazon SageMaker AI console, starting with observability and user management, including directory integration, as the first software extensions. Compared with scripts, extensions have these advantages:

 Validated up front: HyperPod checks an extension’s settings against its schema when you submit them, through the API or the console, so a misspelled setting is rejected before anything reaches a node.

 Consistent on every node: HyperPod applies the extension to every node, including nodes added by scale-up or replacement, and keeps the nodes consistent as the cluster scales and heals.

 Changed through the API or the console: You change a setting or upgrade a version with an API call, or from the SageMaker AI console, instead of editing scripts and replacing nodes. Both paths use the same validated configuration, and this post shows console screenshots alongside the API examples.

 Visible: Each extension reports its status and per-node health.

 Use cluster extensions when HyperPod offers a managed software capability. Use custom AMIs and lifecycle scripts for organization-specific software or initialization that the available extensions don’t cover. HyperPod supports two cluster managed extensions today:

 The observability extension (sagemaker-observability) collects node, GPU, Elastic Fabric Adapter (EFA), Slurm job, and Slurm cluster metrics and sends them to Amazon CloudWatch or Amazon Managed Service for Prometheus .

 The user management extension (sagemaker-user-management) creates users and groups with the same IDs on every node, controls who can use SSH and sudo on each node type, and registers users with Slurm accounting. It can also connect the cluster to Active Directory, for example AWS Directory Service for Microsoft Active Directory .

Artificial Intelligence 

 Introducing Amazon SageMaker HyperPod Global Inference Gateway: One endpoint across Regions and clusters

 During a traffic peak, a request can sit in a queue on a saturated HyperPod cluster while GPUs on another cluster, sometimes in another AWS Region, sit idle. You have already paid for that capacity, but your requests can’t reach it.

 In Introducing Amazon SageMaker HyperPod Inference Gateway , we showed how the Inference Gateway gives each Amazon SageMaker HyperPod cluster a single, GPU-aware endpoint. It reads real-time signals such as key-value (KV) cache utilization and queue depth to place every request on the best-suited pod. That solves routing inside one cluster, but not across clusters.

 Today, SageMaker HyperPod introduces the Global Inference Gateway. It is one SageMaker-managed gateway that routes across every cluster you register, in one Region or across Regions. The gateway picks the cluster and carries the request over the AWS backbone, with automatic failover and authentication through AWS Signature Version 4 (SigV4) and AWS Identity and Access Management (IAM). Inside each cluster, the Inference Gateway keeps picking the pod, unchanged. The Global Inference Gateway is the second tier of the architecture we described in part 1.

 The challenge: Capacity spread across clusters and Regions

 Models are getting larger, and the GPU capacity to serve them is harder to find. To get enough of it, you spread it across more clusters and more Regions.

 Consider a team that serves four models across five HyperPod clusters in two Regions. Without the Inference Gateway, clients track 20 endpoints: one per model per cluster. The Inference Gateway cuts that to five, one per cluster. But each client still picks a cluster itself.

 That choice has costs:

 Uneven load. During peaks, requests queue in one Region while GPUs in the other Region are idle.

 Manual failover. When a cluster fails, an engineer changes configuration to move traffic away from it.

 Custom plumbing. Spreading traffic across Regions means building and maintaining load balancers, DNS, and cross-Region networking yourself.

 The team needs one endpoint that sends each request to the best-suited cluster and moves traffic off a failed cluster on its own.

 Key benefits

 The Global Inference Gateway helps you get more from the GPU capacity you already have, with less to operate.

 Put idle GPUs to work. During a peak, requests overflow to clusters with available capacity in the same Region or another one, instead of queuing on a saturated cluster.

 Fail over automatically. When a cluster fails, the gateway moves its traffic to the next-best cluster. Clients don’t change anything.

 Use one endpoint for everything. Clients call a single SageMaker-managed endpoint instead of tracking one endpoint per cluster or per model.

 Skip the custom networking. You don’t build or maintain load balancers, DNS, or cross-Region networking.

 Stay private by default. Every request is authenticated with SigV4 and IAM, and it reaches your clusters only over AWS PrivateLink.

 Customer feedback

 “At Bagelcode, we run our own LLM inference service on AWS to help teams across the company, including our game teams, use AI to improve how they work. In our beta tests, the Global Inference Gateway in Amazon SageMaker HyperPod routed requests across two AWS Regions through a single endpoint and kept serving them when one cluster could no longer serve the model. That gave our small platform team cross-Region failover without having to build or maintain our own routing layer.” 

 — Jinhyung Park, VP (AI Platform), Bagelcode

 How it works

 Setting up the gateway takes two decisions: which clusters to open up for routing, and which of them to group behind one gateway.

 Publish a cluster. You do this once per cluster. You turn on the spec.globalRouting block in the cluster’s existing InferenceGatewayConfig . The HyperPod Inference controller then publishes the cluster privately from your own account.

 Create the gateway. You do this once per gateway. You call CreateGlobalInferenceGateway with the clusters to route across, and SageMaker returns one endpoint.

 A cluster is reachable only after you publish it. When you publish a cluster, the controller creates a Network Load Balancer in front of the cluster’s Inference Gateway, publishes a virtual private cloud (VPC) endpoint service on it, and uploads the listener’s certificate to your TLS bucket. These resources live in your account. If you list a cluster in a gateway before you publish it, the call fails with a message that tells you what to fix.

 How a request flows

 Figure 1 shows the path of each request: (1) your client signs the request with SigV4 and sends it to the gateway’s regional endpoint. (2) The gateway authenticates the caller and picks the best cluster. (3) AWS PrivateLink carries the request to that cluster, in the same Region or another, and (4) the cluster’s Inference Gateway routes it to a model pod, as it does today.

 Figure 1: The Global Inference Gateway receives each request at one regional endpoint and forwards it over AWS PrivateLink to the best HyperPod cluster, where the cluster’s Inference Gateway routes it to a model pod. Each cluster publishes its load back to the gateway.

 What AWS operates

 You decide which clusters to publish, which to group behind a gateway, and how to weight routing. AWS operates the rest:

 The routing fleet. SageMaker provisions and operates the fleet that terminates TLS, authenticates callers, scores clusters, and forwards each request.

 Private connectivity. SageMaker creates one private endpoint per cluster and carries traffic on the AWS backbone, in-Region and cross-Region.

 Certificates and validation. Using an execution role that you create, the service reads each cluster’s VPC endpoint service name, certificate, and Region, so you don’t copy them by hand. It checks them before routing traffic.

 Health and failover. The gateway health-checks every cluster and moves traffic off a failed cluster automatically. For details, see the Operating the gateway section.

 Authentication and rate limits. The gateway checks SigV4 signatures, IAM permissions, and rate limits, and rejects failing requests before any cluster sees them.

 On each cluster, a service-managed metrics publisher with its own IAM role sends the cluster’s load to the gateway.

 How the gateway picks a cluster

 For each request, the gateway scores every healthy cluster on four signals and sends the request to the highest-scoring cluster. Each cluster’s metrics publisher supplies the load signals.

 You control how much each signal counts with routing weights. Each weight is a value from 0.0 to 1.0, and a weight of 0 turns that signal off. If you set weights, you set all four, and they must add up to 1.0. If you omit them, the defaults in the following table apply.

 Announcing Amazon Textract Insights: Verifiable generative AI for documents

 The challenge of extracting data from mixed packets

 Many of the high-value document workloads involve diverse, mixed packets rather than clean, single-purpose files. A mortgage file, for example, typically arrives as a single scan holding a W-2, payslips, bank statements, and a page of handwritten notes. Each has its own layout and appears in no fixed order. Claims files and onboarding packages can look very similar: typed forms, dense tables, scanned receipts, and free-text letters interleaved in one file.

 Teams usually take one of two approaches, and each has trade-offs. The first is a custom pipeline that combines optical character recognition, document splitting, classification, a foundation model prompt, and a review step. The team must integrate, scale, and operate all of it. The second is a general-purpose large language model used by default. It returns fluent answers but does not reliably cite the source page or give a confidence score. Without a traceable source and a calibrated score, it is hard to know which values to accept automatically and which to review. This uncertainty often limits how far teams can automate.

 Amazon Textract Insights is built for reliable document processing, bringing this entire workflow into a single asynchronous request on Amazon Textract. Rather than assembling and operating a custom pipeline, your team works through one managed API and moves directly to the data it needs.

 How Amazon Textract Insights works

 With Amazon Textract Insights, you define what to extract in a blueprint. A blueprint is a JSON Schema in which each field carries a natural language description of what to find. Each field also has an inference type that determines whether the value is read verbatim from the page or inferred from the content of the document. You can begin with an AWS public blueprint for a common document type, such as a W-2, Form 1040, Form 1098, a passport, or a birth certificate. You can also author your own blueprint for the documents specific to your business.

 For a mixed packet, you add the blueprints for each document type you expect to the same project. Amazon Textract Insights splits the packet into logical sub-documents, matches each one to the blueprint that fits it, extracts the requested fields, and returns a confidence score and grounding for each value.

 For example, suppose you receive a mortgage application as a single 26-page PDF that contains a W-2, payslips, bank statements, and a loan officer’s handwritten notes. You create an Amazon Textract Insights project with the AWS public W-2, payslip, and bank statement blueprints, add a custom blueprint for loan officer notes, and enable splitting. You then submit the file from your Amazon S3 bucket with a single StartDocumentInsights call. Amazon Textract Insights splits the file into its individual documents, matches each one to its blueprint, and writes the results to your S3 bucket. Each value includes a confidence score and the page and bounding box it was drawn from.

 Confidence and grounding for auditable automation

 Amazon Textract Insights returns two kinds of fields: The first are explicit fields read directly from the page. The second are inferred fields derived from the document’s content. Both return with a confidence score and with grounding that identifies the page and the coordinates the value was drawn from.

 Because each value is traceable to its source, a reviewer or an auditor can confirm any result against the original document. You can extend automation to documents that would previously have gone to manual review, while keeping people in the process wherever judgment is required.

# ACE2.5-ERA5

Ai2 Climate Emulator (ACE) is a family of models designed to simulate atmospheric variability from the time scale of days to centuries.

**Disclaimer: ACE models are research tools and should not be used for operational climate predictions.**

ACE2.5-ERA5 is a stochastic successor to [ACE2-ERA5](https://huggingface.co/allenai/ACE2-ERA5) trained on the [ERA5 dataset](https://huggingface.co/buckets/allenai/ACE2.5-ERA5-reference-data). It produces calibrated ensemble predictions with realistic small-scale structure on timescales from days to centuries, at substantially lower computational cost than ACE2-ERA5. The repository containing figure reproduction scripts is located [here](https://github.com/ai2cm/ace2.5-era5-paper).

### Released checkpoints

Three configurations are released, each trained on ERA5:

| Checkpoint | Resolution | Time step | Parameters | Description |
|------------|-----------|-----------|------------|-------------|
| `ace2.5-era5.tar` | 1° | Daily | 46M | Primary model, best balance of climate skill and throughput |
| `ace2.5-era5-4deg.tar` | 4° | Daily | 14M | Comparable climate skill at target resolution, 5× throughput, 10× lower training cost |
| `ace2.5-era5-6h.tar` | 1° | 6-hourly | 46M | Competitive short-range weather skill with calibrated spread |

Each is released as seed 0. Seeds 1–3 of the 1-degree daily and 4-degree daily models are in the `seeds/` directory (e.g. `seeds/ace2.5-era5-s1.tar`). Climate skill is consistent across seeds.

The `ablations/` directory contains checkpoints for the ablation models described in the paper, intended for reproducibility of the paper's figures. See `CHECKPOINTS.md` for the provenance of each file.

### Inference quickstart

1. Download a checkpoint from this repository.

2. Install code dependencies with `pip install fme`.

3. Prepare an inference configuration YAML specifying the checkpoint path, initial condition, and forcing data. See the [docs](https://ai2-climate-emulator.readthedocs.io/en/stable/) for details.

4. Run inference with `python -m fme.ace.inference <config.yaml>`.

### Key improvements over ACE2-ERA5

- **Stochastic:** noise-conditioned layer normalization trained with CRPS + spectral energy score produces calibrated ensembles (spread matches error to within 4% from day 3)
- **Realistic precipitation structure:** retains 86% of ERA5's spectral power at wavenumbers 100–179 (ACE2-ERA5 retains 36%)
- **10× smaller:** spectral bottlenecking reduces parameters from 456M to 46M
- **3.2× faster inference:** combined effect of the daily time step and spectral bottleneck

### Strengths and weaknesses

Strengths:
- accurate atmospheric warming response to combined SST and CO2 forcing over 1940–2020
- highly accurate atmospheric response to El Niño SST variability, improved over ACE2-ERA5
- realistic tropical cyclone geographic distribution (6-hourly model)
- accurate Madden-Julian Oscillation variability
- realistic stratospheric polar vortex
- exact conservation of global dry air mass and moisture
- calibrated ensemble spread across all evaluated fields

Known weaknesses:
- the individual sensitivities to SST and CO2 are not entirely realistic

 How Standard Bank Group automates AI risk assessment for generative AI

 Having an AI policy is one thing. Proving, one use case at a time, that AI systems follow it is another. Every new generative AI application adds one more system to prove. Teams can now build one in days, but each still needs a risk committee’s approval before it reaches customers or employees. When that approval depends on reviewers reading documents and testing the system by hand, governance becomes the slowest step in the pipeline.

 Standard Bank Group chose to automate that proof. Working with AWS Professional Services, the bank deployed an automated assessment that scores each generative AI use case against international AI standards and its own policies. The assessment produces reports and a dashboard that show what is already in place, what is working well, and what still needs mitigation. This post explains how the assessment runs on AWS and what Standard Bank Group learned from its first runs.

 Governing AI with the framework you already have

 Standard Bank Group didn’t need a new AI policy. Like most large banks, it already had an established model risk practice that covers concerns such as explainability and fairness, and a change risk process that assesses each new use case according to its level of risk before it goes live.

 Generative AI increases the complexity, because models and tooling change every three to six months, yet each use case still needs to meet the same high security and compliance bar.

 “At Standard Bank, this assessment demonstrates how we are working with AWS to embed intelligent, automated risk management into our AI journey, allowing us to accelerate meaningful business value while maintaining the trust and controls that banking demands.  — Jörg Fischer, Group Chief Information and AI Officer, Standard Bank Group

 The goal was to automate evidence gathering and testing, then feed the results into the approval gates Standard Bank Group already runs. Review and approval stay with the risk committee, but the committee now bases each decision on consistent evidence, collected the same way across use cases.

 How the assessment works

 Figure 1 shows how the assessment’s components fit together in Standard Bank Group’s AWS account, from intake through evaluation to reporting.

 Figure 1: The assessment pipeline in Standard Bank Group’s AWS account, from intake through evaluation to reporting

 The assessment runs entirely in Standard Bank Group’s own AWS account. Documents, code, and test results stay in an Amazon Simple Storage Service (Amazon S3) bucket there. The AWS Well-Architected Tool handles intake, AWS Step Functions orchestrates the pipeline, and a foundation model on Amazon Bedrock evaluates the evidence. It uses a technique called LLM-as-a-judge, in which a large language model checks evidence against defined criteria.

 With Amazon Bedrock, Standard Bank Group could use a foundation model without stepping outside the controls it already runs on AWS. The bank controls access to the model through AWS Identity and Access Management (IAM), just as it does for its other AWS workloads. Amazon Bedrock doesn’t share the bank’s prompts or model outputs with model providers, and doesn’t use them to train models. Because Amazon Bedrock offers many foundation models through one API, the team can move to a newer judge model by changing a configuration setting instead of rebuilding the pipeline.

 Each assessment moves through four steps. In the first two, a pre-assessment agent collects evidence about the use case, then the pipeline examines it and tests the application directly. The third evaluates that evidence against controls. The fourth summarizes the results in a standard, predefined format and delivers them to the people who act on them.

 Step 1: A pre-assessment agent collects the evidence

 The custom lens in the Well-Architected Tool holds about 40 questions, each covering a risk event such as incomplete technical documentation or insufficient human oversight. Delivery teams no longer fill it in from scratch. A pre-assessment agent running on AWS Fargate scans the use case’s code repository and documentation. It maps relevant files to each question and pre-populates the lens with answers and links to the evidence. The delivery team then reviews those answers, corrects any mistakes, and adds the evidence the agent couldn’t find.

 Step 2: The pipeline examines the artifacts and tests the application

 The pipeline works from four kinds of evidence.

 System documentation, which describes how the application was designed, built, and evaluated.

 Policy documents, which set out roles, responsibilities, and procedures such as incident handling.

 Source code and the system prompt, which show how controls are implemented.

 Live calls to the application, which show how it behaves in practice.

 For documents and code, the pipeline checks whether each artifact contains what its mapped control requires. Each control comes from an international AI standard or framework, or from Standard Bank Group’s own policies. An incident procedure, for example, needs to describe how incidents are reported.

 For live testing, the pipeline calls the application through its AWS Lambda function or API. The delivery team supplies questions a typical user would ask. The pipeline adds a built-in set of jailbreak attempts and off-topic questions, which the application is expected to decline. It also sends the same prompt several times, in its original and reworded forms, and uses an embedding model on Amazon Bedrock to check that the answers stay consistent in meaning. Where the team provides expected answers, the pipeline measures how closely the responses match them. Every response is stored in Amazon S3, so reviewers can see exactly what the application generated.

 Step 3: LLM-as-a-judge evaluation against standards

 In this step, a foundation model on Amazon Bedrock acts as the judge. The assessment uses the model as-is with no fine-tuning or customization. (Model availability varies by AWS Region, so check the supported models by Region before you deploy.) For each question, the model checks whether specific evidence appears in the artifacts and in the application’s responses, and returns yes or no.

 Every check maps to a control in an international standard or framework for AI management, AI risk, or AI security. Standard Bank Group also customized the lens with judge questions built from its own standards, bringing the total to more than 300. The checks cover the eight AWS responsible AI dimensions in the following table:

 Veracity and robustness

 Privacy and security

 Transparency

 What toddlers can teach us about recursive self-improvement 

 Anyone who has watched a toddler build with wooden blocks has seen a hard research problem solved on a living room floor. I have spent years trying to get machines to do what a two-year-old does on instinct.

 Imagine one such child. She is stacking a tower of blocks, absorbed, and reaches for a piece that isn’t there. She pauses. She looks at the pile. She finds two smaller blocks that stack to the same height as the one she wanted, tests them, and keeps going.

 A few minutes later she hits an even harder problem and pauses again. A block has slipped into a gap at the base of the tower, too deep for her fingers to reach. Rearranging what she already has will not solve this one. So she looks around the room, picks up a wooden stick, and works the block free. Nobody handed it to her, she did this herself. 

 Four things happened in those two pauses. 

 She noticed a gap. Before she could solve anything, she had to recognize that something was missing, which requires a working model of what the finished thing should look like.

 She gave herself a capability she did not have. The two blocks were a recombination of what was already in front of her. The stick was something else: her hands could not do the job, so she extended them . 

 She got better at it. Over the following months, her improvisations got sharper. She learned which shapes bear weight, how wide a base needs to be, when a structure has gone far enough. Her towers improved because her judgment improved.

 And there was a fourth thing, which took me longer to see, because it is defined by its absence: what she didn’t do. At no point, however many towers she built, could she grow a third hand. That limit marks the boundary of learning.

 This is the era of self-evolving systems, where a machine can change what it is made of, and not just what it knows. 

 The evolution of how machines learn 

 Allow the professor in me a few minutes at the whiteboard, starting with five terms that get used loosely and interchangeably in conversations about AI research. They should not be, and knowing them makes everything that follows easier to see.

 Learning is a system improving its performance using feedback, inside a process someone else designed.

 Self-learning is a system identifying its own knowledge or performance gaps, seeking the feedback or experience it needs, and using it to improve.

 Evolution is a change to a system’s architecture or learning mechanisms that produces new capabilities.

 Self-evolution is a system identifying its own limitations and modifying its architecture, capabilities, or learning mechanisms to overcome them.

 Recursive self-improvement (the term that’s getting the most attention lately) – goes one step further: the system improves not only its capabilities but also its ability to generate future improvements. 

 Note the one word that separates each pair: “self.” It marks the point where the AI system, rather than a human, notices what is missing and acts on it.

One more term before we start. A model’s weights are the billions of numerical settings inside it, adjusted a little at a time during training. Everything the model knows lives in those numbers, and nowhere else.

 Now on to how machines learn. 

 For roughly 50 years, machine learning has worked in a particular way, and it has worked well. A model encounters a high volume of example challenges or experiences. Some of its attempts earn rewards, and others are mistakes that draw corrections. Both become a signal. The signal adjusts the model’s weights, and the model gets better at its task. We have refined this loop many times over, and its shape has held: the knowledge in those weights changes, while the architecture holds still.

 For decades, machines have learned by running the same loop. What the model knows changes; the structure holding that knowledge stays the same. 

 Human beings learn much the same way.  

 If you’ve ever practiced a new language in an app like Duolingo, you’ve felt this loop firsthand: you attempt a sentence, the app rewards you or corrects you, and the next attempt comes a little easier. Each round of practice changes connections in the brain, and it is worth being precise about what. 

 We are born with a brain of a certain structure, and across a lifetime we modify its neural circuitry through a process called neuroplasticity. That change is considerable. Experience strengthens some synaptic connections and weakens others, builds new ones and prunes away the unused, and reorganizes entire functional networks around a newly learned skill. The brain grows, too, through childhood and adolescence. What remains relatively stable underneath all of that activity is the brain’s high-level architecture. We don’t spontaneously grow a second brain, develop an entirely new sensory system, or grow a third hand as in the toddler example.  Everything we call “learning” happens inside the bounds of our biology. The parallel to traditional machine learning is close: the model becomes more capable without fundamentally changing its computational architecture. 

 Evolution operates on a different timescale and changes something deeper. Across generations, architecture itself shifts. Feathers that once kept small dinosaurs warm become the wings of a swallow, along with the neural wiring it needs to bank through a gust of wind. A patch of light-sensitive cells becomes an eye, and the brain reorganizes around everything the eye delivers. Architecture can shrink, too: vestigial structures that stop earning their keep, such as wisdom teeth in humans, become smaller or absent over time.

Evolution changes more than the strength of connections. It changes what kind of nervous system there is to connect. The organism that emerges is built differently from its ancestor.

We set a goal, and our AI system optimized for something we never specified, because the something turned out to be useful for the goal. In a simulation, that is a fascinating result. In a company, the stakes are much higher. A system that quietly optimizes for an objective nobody wrote down is how a pricing engine learns to misquote, or a claims process learns to approve what it should flag.

 All of which is why, when someone says an agent evolves, the useful question is which one they mean: 

 Is it learning, getting better within the structure it already has, or

Last year my colleagues and I published a survey of the frontiers of reasoning in large language models , and one of the clearest trends we tracked was the shift from standalone models to agentic systems.  A standalone model has one thing that can change, its weights. An agent has many: the tools it can call, the skills it can reuse, the specialists it can delegate to, the way it organizes its own work. Researchers call all of that surrounding apparatus the harness, and every part of it can learn and evolve.

Here is where the biology stops being a guide. In living systems, learning and evolution run on different clocks. Learning takes a lifetime, and evolution takes generations. A machine has no such separation. A system can refine its reasoning from this morning’s work and give itself a module it lacked by the afternoon, running in one continuous process what biology splits across two very different timespans.
