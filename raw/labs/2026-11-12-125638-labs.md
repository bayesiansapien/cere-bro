 Introducing the Web Search API on Amazon Bedrock AgentCore

 AI agents and applications that answer questions about recent events, product releases, prices, or regulations need information newer than their model’s training data. Until now, Web Search on Amazon Bedrock AgentCore delivered that information to agents through AgentCore Gateway , a capability of Amazon Bedrock AgentCore. That means creating a gateway and a web search target and calling the tool from an MCP client. The setup fits platform teams that share one search policy across many agents, but it’s more than you need when your own code only requires search results.

 Today, we’re announcing the Web Search API on Amazon Bedrock AgentCore. With it, your own code can search the web with a single API call. It returns ranked results from a web index that Amazon operates, each with a text extract and, when available, the page title, URL, and publication time. You call it from the AWS SDKs or the AWS Command Line Interface (AWS CLI), signed with the same AWS Identity and Access Management (IAM) credentials you use for your other AWS services. There are no resources to create first. Authenticate, call, and get results. Use it in an application, an agent loop you write yourself, or a data pipeline.

 Why a standalone API?

 The AgentCore Gateway is the recommended path for most agentic workloads. It gives agents one secure Model Context Protocol (MCP) endpoint that combines web search with your other tools. It also handles inbound and outbound authentication, semantic tool selection, and optional MCP sessions . But developers told us they also need a lower-level integration point for scenarios where the gateway is not the right fit:

 Custom orchestration frameworks –  Developers building their own agent loops, or using frameworks like LangChain or LlamaIndex, want to call web search directly as a tool within their orchestration logic rather than routing through a gateway.

 Non-agent use cases –  Not every application that needs web grounding is an agent. Search-powered dashboards, fact-checking pipelines, content enrichment workflows, and monitoring systems all benefit from real-time web results without requiring agent infrastructure.

 Tighter control over the request lifecycle –  Some developers want to manage retries, caching, and error handling themselves rather than delegating to the gateway.

 Simpler integration for existing applications –  Applications that already have their own API layer can call the Web Search API directly, adding web grounding without adopting the full AgentCore Gateway stack.

 The Web Search API complements the gateway. It runs on the same search infrastructure that powers Alexa+, Kiro, Quick, and other Amazon products, with the same quality and compliance posture, exposed as a direct API operation.

 How it works

 The Web Search API is the InvokeWebSearch operation on the bedrock-agentcore data plane, the same endpoint that other AgentCore tools such as AgentCore Browser , a capability of Amazon Bedrock AgentCore, use. Requests are signed with AWS Signature Version 4 (SigV4) from your standard AWS credentials, so there’s no API key or secret to manage.

 Figure 1: How a Web Search API request flows

 The numbered steps are:

 Your application calls InvokeWebSearch with the AWS SDKs or the AWS CLI, which sign the request with SigV4 using its AWS credentials. From a virtual private cloud (VPC), the call can go through an interface VPC endpoint.

 The API checks with AWS Identity and Access Management (IAM) that the caller has bedrock-agentcore:InvokeWebSearch on the AWS managed web search tool.

 The API applies the filters in the request: the domains to include or exclude and the publication time range.

 The API searches a web index that Amazon operates. Queries are served inside AWS and aren’t sent to a third-party search engine.

 The API returns up to maxResults ranked results, each with a text extract and, when available, the page title, URL, and publication time.

 The calling identity needs one IAM permission on an AWS managed resource. It’s the same action and resource that a gateway’s service role uses for web search, so one policy covers both routes. For details, see Grant permission to call the API .

 Key API features

 Domain filtering –  Include or exclude specific domains to scope search results to trusted sources (for example, only aws.amazon.com and kubernetes.io for an assistant focused on AWS). Each list holds up to 100 domain names, and a root domain also matches its subdomains.

 Date filtering –  Restrict results to a publication time range with publishedAfter and publishedBefore , given as RFC 3339 date-times in UTC such as 2026-01-01T00:00:00Z. Both bounds are inclusive.

 Configurable result count –  Request between 1 and 25 results per query. If you don’t set maxResults , the API returns up to 25. The search text, searchQuery , can be up to 200 characters.

 Results with text extracts –  Each result includes a text extract and, when available, the page title, URL, and publication time, ready to feed into your model’s context window.

## Usage

Requires `transformers>=5.15` (the first release with `muse_glimmer`); see `requirements.txt`. One 80 GB GPU holds
the model in bf16.

'''python
from modeling_metaencoder import MetaEncoder

model = MetaEncoder.from_pretrained("facebook/meta-encoder-v1")
'''

`MetaEncoder` has three calls. Callers pass content and task descriptions; the wrapper writes every prompt itself, in
the layout the encoder was trained on (see [Prompt formatting](#prompt-formatting)).

| Call | Use it to | Returns |
| :--- | :--- | :--- |
| `encode(inputs, instruction=None)` | embed inputs to store, cluster or compare | `(n, 6656)` float32 tensor, L2-normalised |
| `retrieve(query, corpus, top_k=None, query_instruction=None, corpus_instruction=None)` | rank a corpus against a query | `list[Hit]`, best first |
| `decide(state, questions, images=None, video=None)` | answer Jev-style questions about a state | Jev answers with probabilities |

### Inputs

`encode` and `retrieve` take *items*. An item is a string, a PIL image, or a dict with any of `text`, `image`,
`images`, `video` (a list of frames) and `instruction`. The instruction says what the embedding is for, e.g.
"Represent the given image." or "Find a document image that matches the given query."; the same input embeds
differently under different instructions, and queries and documents usually take different ones.

### 1. Encode

'''python
from PIL import Image

docs = model.encode([{"image": Image.open("chart.png")}, {"image": Image.open("slide.png")}],
                    instruction="Understand the content of the provided document image.")
MetaEncoder.similarity(docs, docs)   # cosine similarity matrix
'''

`inputs` is one item or a list of them; `instruction` applies to the items that carry none of their own.

### 2. Retrieve

'''python
hits = model.retrieve("Which quarter had the highest revenue?", docs, top_k=1,
                      query_instruction="Find a document image that matches the given query.")
hits[0].index, hits[0].score, hits[0].item   # position in the corpus, cosine similarity, the corpus item
'''

`corpus` is a list of items, or the tensor `encode` returned for them: encode a large corpus once and search the
tensor repeatedly.

### 3. Decide

`decide` takes a Jev decision request, a state and named questions, and answers each question:

'''python
result = model.decide(
    {"query": "used iphone 15"},
    {
        "shopping": {"type": "noul", "instructions": "Is the user shopping for a product?"},
        "topic": {"type": "choice", "instructions": "Which topic is the query about?",
                  "criteria": {"electronics": "", "food": "", "travel": "", "other": ""}},
        "intent": {"type": "score", "instructions": "How strong is the purchase intent?",
                   "criteria": ["none", "weak", "moderate", "strong"]},
    },
)
result["questions"]["shopping"]   # {"value": True, "probabilities": {"false": 0.016, "true": 0.984},
                                  #  "confidence": 0.881, "scores": {...}}
result["questions"]["topic"]["value"], result["questions"]["intent"]["value"]   # "electronics", 1.89
'''

- `state`: what the questions are about. A string, or any JSON value (an object of fields, a list of records).
- `images`, `video`: the state's media: a PIL image or a list of them, and a list of video frames.
- `questions`: `{name: {"type", "instructions", "criteria"}}`, with `instructions` the question itself:

| `type` | `criteria` | `value` | `probabilities` keys |
| :--- | :--- | :--- | :--- |
| `noul` | optional `{"true": ..., "false": ...}` descriptions | `True` / `False` | `"false"`, `"true"` |
| `choice` | `{option: description}`, 2 to 26 options; descriptions may be empty | the chosen option | the options |
| `score` | the ordered list of level labels, e.g. `["none", "weak", "strong"]` | expected level index (float) | `"0"` .. `"n-1"` |

Each answer also has `confidence` (1 minus the normalised entropy of `probabilities`) and `scores` (the raw cosine
similarities). Questions are answered independently; for a question that only applies given another's answer,
decide the first and ignore the second as needed.

`decide_batch(states, questions, images=None, video=None)` answers the same questions for many states (one
`images` / `video` entry per state).

Probabilities are `softmax(score / 0.02)`, the contrastive training temperature. To fit the temperature to your
data, decide a labelled set and call `model.calibrate(answers, labels)` with the per-question answers
(`result["questions"][name]`) and their correct keys (the option, `True`/`False`, or the level index); later
`decide` calls use the fitted temperature.


## Prompt formatting

The wrapper formats every input as in training, so callers never write prompts:

- **System turn** (`chat_template.jinja`): the fixed header ending in "Represent the user's input.", then the item's
  instruction after a blank line when it has one. The date line is fixed, so an input embeds the same on any day.
- **User turn**: images and video frames first, then the text. Images keep their native resolution, snapped to a
  28-pixel grid, up to 4096 merged tokens. Video is encoded frame by frame; more than 8 frames are subsampled
  uniformly to 8, as in training.
- **Pooling**: the last position, the user turn's `<|eot|>`, with left padding. Inputs are never truncated (that
  would drop the pooled token); training sequences were at most 16,384 tokens.

`decide` turns each question into a closed-set decision row of training, scored as retrieval over its options:

| Part | Rendered as |
| :--- | :--- |
| query text | the state, a blank line, `Task: {instructions}`, then the options: `Options: a, b, c`, or one `- option` per line when an option is long or punctuated |
| state | a string as is; a JSON value with `json.dumps` |
| query instruction | "Read the task definition and select the option it calls for." for a string state; "Answer the question about the scenario by selecting the correct option." for a JSON state |
| options | `noul`: `No, Yes`; `choice`: the criteria keys; `score`: the level labels |
| candidates | one per option: the option, then its description (if any) on the next line |
| candidate instruction | `Option for the task: {instructions}` when every option is a short label (at most 5 words), else none |

Option descriptions are optional. The yes/no, choice and score rows of training used bare option labels; candidate
descriptions were trained only as records of the entities that options name.

 What makes a system an agent

 A chat completion call can generate text, but it can’t decide what to do next, reach into external systems, or remember what happened yesterday. An agent can, because it unites three capabilities:

 Planning – Given a goal, the model breaks it into steps, prioritizes them, and revises the plan as new information arrives.

 Tool use – Beyond generating text, the model can select and invoke external functions such as APIs, databases, and code interpreters to act in the world.

 Memory – Context carries across turns (short-term) and across sessions (long-term), so each decision builds on what came before.

 A Retrieval Augmented Generation (RAG) application has limited tool use (retrieval) but no planning loop. An agent has all three, operating in a goal-directed loop until the task is complete or it determines it cannot proceed.

 Semantic diffing of formal policies with anti-unification

 When reviewing code, you start with a diff. You wouldn’t compare two 3,000-line files by eye and hope to spot every change. Formal policies can be even harder to compare because a textual diff often highlights syntactic changes that don’t affect meaning. Reorder two conjuncts, swap the arguments of an equality, or use an equivalent predicate, and much of the file might appear changed. A real change in behavior, such as an Or where the requirement says and , can get lost in that noise.

 A semantic diff shows what two policies have in common and where they disagree. The open source engine used in this post computes this diff using anti-unification , which finds a most specific common pattern for two expressions. Plotkin’s 1970 paper gives the classical formulation. The engine works over an e-graph, which keeps track of expressions known to be equal. We supply the algebraic laws and domain rules that justify those equalities, such as equating an external destination with one that isn’t internal. The result shows the shared parts once and keeps both versions of each differing part for review. If no differences remain, the policies are equivalent under those laws and rules. When the rules or the search are incomplete, a remaining difference might reflect an equivalence the engine has not found.

 One use case is autoformalization. Autoformalization translates natural language into a formal language. Suppose you want to turn requirements into SMT-LIB , the standard input language for satisfiability modulo theories (SMT) solvers such as Z3 and cvc5, or into Cedar or Dogwood to control authorization in your software system. A large language model (LLM) generates the formal artifact from the prose. The model writes the artifact. It plays no part in computing the diff.  Silent data corruption (SDC) happens when hardware, such as a GPU, returns a wrong but plausible number and raises no error. In distributed training, the wrong number can flow into the gradients and weights of every replica. Loss can still look normal for hours, and by the time a team notices an unexplained divergence or a weaker model, the compute is spent. It happens at scale: during a 54-day period of Llama 3 405B pre-training on up to 16K H100 GPUs, Meta attributed 6 of 419 unexpected job interruptions to silent data corruption, and those were only the cases that interrupted the job and were traced to SDC.

 Amazon SageMaker HyperPod already replaces nodes that report a fault: the health-monitoring agent watches for GPU errors, deep health checks stress-test nodes, and automatic node recovery swaps out bad hardware. SDC slips past all of these features, because the hardware never reports anything. Detection has to come from the training job itself.

 In this post, we add three checks to a PyTorch DistributedDataParallel (DDP) training loop to detect SDC. When a check fires, we map the suspect rank to its node, contain the corruption, and have SageMaker HyperPod replace the node. Each check covers a different place where a fault can land:

 A non-finite gradient check catches NaN, Inf, and overflow in a GPU’s forward or backward pass, on the step it happens, and NaN or Inf that the gradient all-reduce introduces.

 A ring replay audit catches finite wrong values. On audit steps, every GPU recomputes a micro-batch from another node and compares the loss bit for bit and the gradients by fingerprint.

 Heart disease, kidney conditions, and metabolic disorders like type 2 diabetes aren't isolated, they form an interconnected web known as cardiovascular-kidney-metabolic (CKM) syndrome . CKM progression often begins silently years before symptoms appear, shaped by everyday habits like movement, sleep, and cardiovascular activity. Catching these subtle shifts early offers the best chance to reverse the trend . Yet while smartwatches easily track what we did yesterday, moving from passive tracking to meaningful action is much harder: How do my daily habits affect my CKM right now? And if I sleep 30 minutes longer or add a brisk walk to my routine, how much will my health improve over the next three months? 
 Age is often seen as playing a part in answering these questions, but chronological age alone isn’t enough because two people born in the same year can have vastly different physiological health. While researchers have developed “ biological clocks ” from blood tests or wearable sensors to estimate whether someone's body is aging faster or slower than their calendar age, most existing clocks aren't built for everyday coaching. Many are trained simply to estimate the birth year, latching onto traits you can't easily change, or act as black boxes that can't show how modifying a specific habit will shift your future health.
 In “ Personalized health coaching via coachable health age and counterfactual wearable trajectories ” and our companion study, “ Cardiovascular-Kidney-Metabolic Health Age Using Wearables and Blood Biomarkers ”, we introduce an investigational framework designed to close the loop between tracking a person’s health and actively improving it. The framework provides the following:
 A coachable health age model: An interpretable health-age metric built entirely from modifiable daily behaviors and physiology captured passively by consumer wearables.
 A sensor world model and counterfactual coaching system: A machine learning world model (SensorWM) trained on over 2.2 million person-weeks of wearable data that simulates personalized 12-week "what-if" health trajectories, paired with a language model agent that turns those simulations into realistic, clinician-vetted coaching plans.
 Expansion to multi-organ CKM health: When routine blood tests are available, our framework can be expanded to combine wearable streams with lab biomarkers to detect early, subclinical strain across the heart, kidney, and metabolic systems.

 Overview of our framework, from estimating coachable health age and predicting long-term disease risk to simulating 12-week "what-if" habit trajectories for personalized coaching. 

 A health age metric you can actually move
 To make a health metric useful for coaching, every input should be something that can be tracked continuously and influenced through daily choices. Rather than training a model to guess a person’s birth year, we grounded our coachable health age (CHA) model in published epidemiological studies linking everyday behaviors to cardio-metabolic disease risk. CHA integrates four core signals passively measured by consumer wearables — resting heart rate , daily step count , sleep duration , and weekly Active Zone Minutes — alongside optional markers like VO2max, sleep schedule regularity , and insulin resistance , when available. Because active people often have lower resting heart rates and better sleep, we mathematically adjust for overlap across these signals so each habit contributes its distinct share to your health age delta , the difference between your CHA and chronological age. A negative delta (say, −3 years) means an individual's physiological profile appears younger than their chronological age, while a positive delta signals accelerated aging.
 We validated this model across three independent cohorts:
 Predicting future disease ( All of Us research program , n = 22,748): Across more than 68,000 person-years of consenting Fitbit and electronic health record follow-up, healthy participants who had a health age older than their calendar age at baseline were significantly more likely to develop hypertension, cardiovascular disease, or type 2 diabetes over the next eight years. Adding CHA to standard clinical metrics (age, sex, and BMI) significantly improved disease risk prediction, especially among adults under 50.
 Improvement over time (longitudinal Fitbit cohort, n = 1,464): Tracking users across consecutive 3-month windows over two years showed that among users with a sustained change in habits, the CHA decreased.
 Alignment with clinical health ( WEAR-ME study ): Unlike wearable aging clocks trained to predict chronological age, CHA aligned better with the modified American Heart Association's Life's Essential 8 cardiovascular score and metabolic syndrome severity score , as well as participants' own self-reported health.

 Across 18,423 disease-free participants in the All of Us cohort, those with a health age younger than or equal to their calendar age had significantly higher disease-free survival over 8 years ( left ), while 2-year longitudinal tracking shows that individuals can meaningfully lower their health age over 3-month windows ( right ). 

 Playing out "what-if" futures with a sensor world model
 Knowing your health age tells you where you stand today. Turning that number into a personalized plan requires answering a "what-if" (or counterfactual) question: What will happen to my body over the next 12 weeks if I change specific habits, and which plan can I realistically stick with? 
 Simply plugging new step or sleep targets into a static calculator misses how the body adapts as a connected system. When you consistently move more and sleep better over several weeks, your resting heart rate and heart rate variability gradually improve too, creating extra health benefits downstream.
 To capture these dynamics, we developed Sensor World Model (SensorWM), an action-conditioned world model pre-trained on 2.28 million person-weeks of de-identified data from roughly 100,000 consenting Fitbit users. Given two weeks of baseline wearable data, SensorWM forecasts how 20 physiological markers will evolve over the next 12 weeks under different daily steps, sleep, and cardio routines, outperforming general-purpose time-series foundation models like TimesFM while preserving the clinical patterns associated with diabetes, hypertension, and insulin resistance.
 We paired SensorWM with a feasibility-constrained optimizer and a language model coaching agent to do three things:
 Simulate: SensorWM rolls out 125 candidate 12-week habit combinations for each person, comparing them against a "status-quo" projection if habits stay the same.
 Filter for realism and safety: The most aggressive workout plan doesn't help if it causes burnout in week two. Our optimizer weighs projected health-age reductions against each person's historical habit flexibility and clinical safety bounds, picking a more ambitious target (−2.3 years) for someone with high baseline flexibility, and a gentler ramp (−1.3 years) for someone whose routine is more constrained.
 Coach: The language model translates the top-ranked pathways into a supportive, progressive 12-week coaching plan.
