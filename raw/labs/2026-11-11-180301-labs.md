# Sing VL S1

Sing VL S1 is a multimodal decision model built on Qwen3.5. It answers named questions over text or JSON and up to four images. Each question uses a single Transformers forward pass to score the supplied options.

- **Choice** selects an option and returns a probability for each candidate.
- **Noul** returns the probability that a yes/no proposition is true.
- **Score** rates the input against 2–10 levels ordered from low to high. It returns the probability of each level and the expected level, computed as the sum of each zero-based level index times its probability.

## Usage

Use Python 3.12 and hardware-compatible PyTorch and torchvision builds. From the model repository root, enter `inference/` before running the examples. If you have a standalone copy of the inference code, run the examples from that directory and replace `..` with the checkpoint path.

'''bash
cd inference
python -m pip install -r requirements.txt
'''

### Python

'''python
from PIL import Image

from model import SingVLS1

model = SingVLS1("..", device="cuda:0")

# Text
text, _ = model.predict(
    state="The color is red. ",
    questions={
        "color": {
            "type": "choice",
            "instructions": "Which color is named?",
            "criteria": {"red": "Red", "blue": "Blue"},
        },
        "yesno": {"type": "noul", "instructions": "Is the named color red?"},
        "redness": {
            "type": "score",
            "instructions": "How clearly does the text identify the color as red?",
            "criteria": ["Not red", "Possibly red", "Clearly red"],
        },
    },
)
print(text["answers"])

# Images in blue-then-red order. Both state values work.
questions = {
    "which": {
        "type": "choice",
        "instructions": "Which image is red?",
        "criteria": {"first": "The first image", "second": "The second image"},
    }
}
with Image.open("examples/blue.png") as blue, Image.open("examples/red.png") as red:
    for state in ({}, "<image>\n<image>\n"):
        vision, _ = model.predict(state=state, questions=questions, images=[blue, red])
        print(vision["answers"])
'''

With no `<image>` markers, the model inserts them before the state text. With explicit markers, use one per image. The markers match the images in list order.

Use the same `score` question format with images. The answer includes `probabilities` and a `legend`, both keyed by the zero-based level number as a string. For example, probabilities of `0.1`, `0.3`, and `0.6` on three levels give `0 × 0.1 + 1 × 0.3 + 2 × 0.6 = 1.5`.

### HTTP API

Start the FastAPI server. Send requests to `POST http://127.0.0.1:8173/v1/systemone` from another terminal on the same machine. Interactive API docs are at `http://127.0.0.1:8173/docs`.

'''bash
python serve.py --model .. --port 8173 --image-root ./examples
'''

Send a text request with an inline JSON body.

'''bash
curl -fsS http://127.0.0.1:8173/v1/systemone \
  -H 'Content-Type: application/json' -d '{
  "model": "sing-vl-s1",
  "state": "The color is red. ",
  "questions": {
    "color": {
      "type": "choice",
      "instructions": "Which color is named?",
      "criteria": {"red": "Red", "blue": "Blue"}
    },
    "yesno": {"type": "noul", "instructions": "Is the named color red?"},
    "redness": {
      "type": "score",
      "instructions": "How clearly does the text identify the color as red?",
      "criteria": ["Not red", "Possibly red", "Clearly red"]
    }
  }
}'
'''

For a Vision request, add an ordered `images` array. Its entries can be Base64 data URLs (`data_url`), raw Base64 strings (`base64`), or server-side file paths (`path`). Paths are relative to `--image-root` or absolute paths inside that directory. With the server command above, send the example filenames directly.

'''bash
curl -fsS http://127.0.0.1:8173/v1/systemone \
  -H 'Content-Type: application/json' -d '{
  "model": "sing-vl-s1",
  "state": {},
  "images": ["blue.png", "red.png"],
  "questions": {
    "which": {
      "type": "choice",
      "instructions": "Which image is red?",
      "criteria": {"first": "The first image", "second": "The second image"}
    }
  }
}'
'''

For the same request with explicit image markers, use `"state": "<image>\n<image>\n"`.

The response puts results under `answers` using the supplied question IDs. The text example selects `red` and returns `answers.redness.score` on a 0–2 scale. The Vision example selects `second`.

**ZoomGain** builds questions about a full image from visual details that become clear when you zoom in. We use this global-to-zoom perception gap to construct supervision for vision-language models. In the paper, the best of 28 models scored **61.08** on ZoomGainBench, and ZoomGain-9B reached superior performance on multiple fine-grained perception and general perception benchmarks. ## 🔬 How ZoomGain Works

<p align="center">
  <img src="docs/figures/zoomgain-pipeline.png" width="920" alt="Three stages of ZoomGain data construction: anchor grounding, global-to-zoom evidence mining, and answer verification with multiple-choice distractors." />
</p>

1. **Ground the target.** Multiple models independently locate a target described in the full scene. Their agreement identifies a region to crop.
2. **Mine evidence.** Compare captions of the same region at both scales, then turn details revealed by the crop into questions about the full image.
3. **Verify questions and answers.** Cross-check answers on the crop, filter ambiguous questions and questions answerable without the image, and build plausible distractors for multiple-choice items.

## 📊 Evaluate on ZoomGainBench

### 📦 Download the benchmark

ZoomGainBench contains **1,000 questions over 941 images** covering attribute recognition, counting, and OCR. Each annotation includes English and Chinese question text, a reference answer, scoring rules, and an evidence bounding box in image pixel coordinates.

'''bash
BENCH_DIR="$ASSET_DIR/data/ZoomGainBench"
hf download inclusionAI/ZoomGainBench annotations.jsonl images.zip \
  --repo-type dataset --local-dir "$BENCH_DIR"
unzip -q "$BENCH_DIR/images.zip" -d "$BENCH_DIR"

Keep `images/` next to `annotations.jsonl`. The evaluator loads the full image from each annotation's relative `image_path` and uses `evidence_bbox` to validate the evidence location.

### 🚀 Run evaluation

Install the dependencies from the model section and run the benchmark from the repository root. Replace the example `MODEL_PATH` with the path to a local checkpoint directory for any compatible model.

'''bash
MODEL_PATH="local/path/to/Qwen3.5-4B" \
ANNOTATIONS="$BENCH_DIR/annotations.jsonl" \
OUTPUT_DIR="outputs/qwen3.5-4b-bench" \
GPUS=0 PORT=18811 LANGUAGE=all \
bash eval_ZoomGainBench/eval.sh
'''

- `LANGUAGE=all` evaluates both languages for **2,000 tasks**. Use `LANGUAGE=en` for English or `LANGUAGE=cn` for Chinese.
- `GPUS=0,1` with `TP=1` runs two independent replicas. Set `TP=2` to use both GPUs for one replica.
- Append `--dry-run` to validate the model and dataset or `--limit 10` for a short GPU run. Evaluation defaults to temperature `0` with Qwen3.5 thinking disabled.

Read `report.md` for the evaluation scores, `summary.json` for aggregate metrics, and `results.json` for per-question results. `responses.jsonl` contains the raw model responses.

**ZoomGain** builds questions about a full image from visual details that become clear when you zoom in. We use this global-to-zoom perception gap to construct supervision for vision-language models. ## 🔬 How ZoomGain Works

<p align="center">
  <img src="docs/figures/zoomgain-pipeline.png" width="920" alt="Three stages of ZoomGain data construction: anchor grounding, global-to-zoom evidence mining, and answer verification with multiple-choice distractors." />
</p>

1. **Ground the target.** Multiple models independently locate a target described in the full scene. Their agreement identifies a region to crop.
2. **Mine evidence.** Compare captions of the same region at both scales, then turn details revealed by the crop into questions about the full image.
3. **Verify questions and answers.** Cross-check answers on the crop, filter ambiguous questions and questions answerable without the image, and build plausible distractors for multiple-choice items.

 IBM is building the world’s first fault-tolerant quantum computer, IBM Quantum Starling. Slated to launch in 2029, Starling will be capable of running quantum circuits comprising 100 million quantum operations on 200 qubits.

 The framework for Starling was described in a 2025 paper , which presented a path to achieve fault tolerance by creating hardware to implement the bivariate bicycle quantum low-density parity check (qLDPC) error correction codes introduced by IBM in a 2024 Nature publication . Critically, the code is implemented in a modular fashion to enable scalability beyond what could be achieved with a monolithic architecture.

 The modular architecture detailed in the paper offers an order of magnitude reduction in resource requirements compared to prior approaches. For the same logical error rate, Starling’s qLDPC architecture requires about 10x fewer physical qubits. It is constructed by assembling modules that each contain a quantum memory and logical processing unit (LPU), which allows logic operations on the memory. The modules have universal adapters that allow them to be connected using l-couplers. Additionally, sophisticated modular cryogenic and control systems house and run the modules at ultra-cold operating temperatures.

 This diagram shows the components that will need to come together for IBM Quantum Starling. 

 Below, we provide an update on significant technical advances toward Starling, broken down into six categories. These steps forward are being delivered in parallel, though not in isolation — lessons from one component influence the progress being made on the others. Taken together, the work outlined below represents major progress toward building Starling and delivering on the promise of fault-tolerant quantum computing.

 Device physics

 IBM Quantum Loon was announced a year ago to demonstrate many of the key components needed to implement IBM’s qLDPC codes, including qubit reset circuits and “c-couplers” to link qubits across the chip, a prerequisite for establishing the six-way qubit connectivity needed to implement the qLDPC code.

 Since then, Loon was measured to have qubit relaxation times (T1) of about 200us with reset time constants of 20ns–40ns. Its gates had median error rates near 0.3%. The ultimate aim for Starling is to have T1 in the millisecond range and gate errors in the low 0.01% range. The physics of the device are designed to enable this low error rate. In fact, we routinely measure gate errors in the high 0.01% range on Heron and Nighthawk — going as low as 0.04%. Transferring coherence times from our test devices, which are currently in the single digit millisecond range, will also help facilitate lower error rates.

 It is also important to understand how much loss the c-coupler layers introduce so we can estimate gate error limits. The results here are also very promising. The resonators had quality factors above 10 million, which is beyond the goal needed for Starling. Adding to this, it was found that traversing c-coupler layers only resulted in a minimal reduction in quality factor, meaning it was possible to increase the number of c-coupler layers being used in the chip. Originally two were being used, but that has now increased to three with plans to reach four or more. Adding additional layers will enable more complex routing and can effectively shorten some of the longest connections c-couplers need to make.

 The results above verify that c-couplers are a viable approach to enabling non-local, dense connections for quantum processors.

 QPUs

 Advances have also been made in how quantum processing units (QPUs) can be put together.

 In particular, there have been two exciting developments related to overall device yield and complexity. First, improvements to the qLDPC code made it possible to have only five connections between qubits instead of six — while also delivering 20x-100x lower logical errors. Second, with further coupler innovations, we discovered ways to reduce the number of Josephson junctions. Bringing these advances together, the number of Josephson junctions needed has been more than cut in half, dropping from around 5,000 to 2,000.

 This junction reduction means that our device yield will increase. With a junction yield target of 99.95%, we find that about 1 out of 12 processors will be fully functional with 5,000 junctions, but 1 out of 3 processors will be fully functional with 2,000 junctions — a factor of 4x increase. Having fewer junctions will also help lower the spread of required critical junctions across the device.

 Lastly, the length of the c-coupler has been increased to 20mm, which helps loosen some of the strict density requirements of qubits and couplers on a quantum processor.

 This combination of exciting results demonstrating high quality factors within and across c-couplers, the improved code, and device yield improvements led us to redesign the modular processors. The new designs lower the risk and increase yield for the modular qLDPC code processors and hence will benefit Starling. A year ago, it would not have been possible to envision this, showcasing how ongoing innovation pushes us toward ever better designs.

 The strong results for c-coupler performance and the ability to reduce the number of Josephson junctions offered ways to improve future quantum processor designs. 

 Modular decoders

 Decoders, classical algorithms used to identify errors in quantum circuits, are needed to achieve fault-tolerant quantum computing. IBM introduced the decoder Relay-BP in 2025 and showed that it could deliver a better logical error rate than leading alternatives while simultaneously lowering compute requirements for decoding. Now, IBM researchers have extended Relay-BP to demonstrate that errors for memory-only operations and measurement operations are nearly consistent. In fact, the performance we observe already meets the requirements for Starling.

 To run Relay-BP on Starling, IBM is creating a real-time decoder ASIC leveraging 2nm nanosheet technologies. This custom chip will deliver improved logical error rates to increase Starling’s performance.

 Inter-module connectivity

 To scale to a large number of error-corrected qubits, the processing modules for Starling need to be linked with long-range connections called l-couplers.

Relative to prior demonstrations, the raw error rates have improved by about a factor of 2x, but the key outcome is the repeatability of attaching l-couplers to processors. We learned that magnetic shielding is important but also that the usual concerns related to thermalization and vibrations matter. Everything must be assembled in a way that does not undo careful microwave engineering so that coupling strengths and dephasing rates are consistent.

 Taken together, these advances show that speed is more than a specification. It is an essential capability that makes frontier circuits cost-efficient and turns Nighthawk into a proving ground for the error correction to come.

 The path to Starling

 Reaching quantum circuits at the scale of 100 million operations will require a fault-tolerant quantum computer—one that runs valuable circuits in minutes, not months. The first such computer will be IBM Quantum Starling , targeted for 2029. Get a more detailed breakdown of this year's progress towards IBM Quantum Starling in our Path to Starling blog post. 

 Building a first-of-its-kind system means co-designing its components in parallel, where a lesson learned on one component reshapes the design of another. For Starling, that co-design effort is taking place across six essential areas: device physics, QPUs, modular decoders, inter-module connectivity, modular cryogenics and wiring, and modular control electronics.

 No matter how we go about the journey, however, our destination remains the same: modular logical memories paired with logical processing units, joined by l-couplers and incorporating magic states to realize design that needs roughly 10x fewer physical qubits than other fault-tolerant architectures.

 Let’s start with the memory that will store Starling’s logical qubits. Our IBM Quantum Loon processor, first showcased at QDC 2025, now brings the ingredients of an error-correcting qLDPC processor together on a single chip, with measured performance comparable to Nighthawk r2.

 Design improvements cut Loon’s hardest-to-yield elements—its Josephson junctions—by more than half, from about 5,000 to 2,000. The decrease was enabled by an improved qLDPC code that needs only five qubit connections instead of six, as well as new coupler innovations. Fewer components mean a simpler chip that is easier to build and less prone to error, thanks in large part to denser on-chip connections known as c-couplers.  Pulse-level capabilities

 Error-correction research demands fine-grained control over what the hardware does and when. IBM Quantum Platform and the Qiskit software stack expose that control directly, rather than hiding it behind a black box. Three groups of capabilities do the heavy lifting:

 Real-time measurement and feedback. Dynamic circuits let researchers measure qubits mid-circuit and branch on the outcome in real time — the basis of syndrome extraction and feedback — using low-overhead instructions like MidCircuitMeasure .

 Precise timing control. You can set exactly when signals fire to protect idle qubits from noise, building custom dynamical decoupling sequences and shaping circuit timing through the transpiler's scheduling passes .

 Custom calibration. Beyond IBM's default calibrations, you can request instructions calibrated for a specific workload — including qec_experimental , the experimental default for the for_loop instruction behind the repetition-code experiment in the next section — or trigger a fresh calibration inside a session to counter drift during long runs.

 For teams exploring soft decoders, raw IQ readout data — useful for leakage detection and confidence scoring — is also available by setting the measurement level .

 Why it matters: Real codes only run when these capabilities work together, on hardware fast and large enough to exercise them.
