Artificial Intelligence 

 SageMaker Inference now supports Multi-Instance GPU to maximize GPU utilization for model endpoints

 When you deploy a model to a GPU endpoint, the smallest unit of GPU you can request is one whole accelerator.

 This constraint can cost you twice. First, you can’t host more models on an instance than it has accelerators. An ml.p4d.24xlarge has eight A100s, so it holds eight models, whether each one needs 40 GB or 14 GB. Second, and less obvious, it makes every deployment come down to a choice of which full GPU to deploy to. As your concurrency and prompt lengths grow, a full GPU on an older instance stops being enough, but a full GPU on a newer one is more than your model can use. You end up either under-served or paying for capability you never reach.

 Today, Amazon SageMaker Inference supports GPU partitioning, which uses NVIDIA Multi-Instance GPU (MIG) to divide a physical GPU into independent partitions. Each partition receives a fixed share of the GPU’s compute units and a dedicated block of its memory, with isolation enforced in hardware. That changes both constraints: you can place a different model in each partition, and you can choose a fraction of a newer accelerator instead of a whole one of either generation.

 This post covers both. The first part is the direct benefit: deploy more models than you have GPUs, with isolation between them. The second is the one customers ask about when the question turns to cost: how the granularity of partitioning helps you pick the right-sized unit, and what we measured when we did.

 One thing to know before you read further: GPU partitioning works on endpoints that use inference components , the construct you use to deploy several models to one endpoint and set the compute each model gets. Partitioning builds directly on it. A partition is a resource a component asks for, in the same place it already asks for CPU and memory. If you haven’t used inference components, this post introduces them. Single-model endpoints, serverless endpoints, and heterogeneous instance pools cannot be partitioned.

 What customers do today, and why each option falls short

 If you have more models than accelerators, you have had three choices.

 Run fewer, larger endpoints and batch harder – This raises utilization, but only when the models are interchangeable. A portfolio of fine-tuned variants or per-tenant models is not.

 Use multi-model endpoints –  These load and unload models from a shared GPU on demand, which fits sparse, bursty traffic. But models share the device without isolation, so a heavy request for one model affects the others. A model that isn’t loaded also pays a load penalty on first use.

 Move to self-managed Kubernetes –  This is where customers who need real GPU partitioning have gone. MIG works there, but you take on driver versioning, partition configuration, a device plugin, scheduling, and keeping it all consistent across a fleet. That’s a lot of work for a hardware capability your instances already have.

 Why MIG

 NVIDIA Multi-Instance GPU (MIG) splits one GPU into as many as seven instances, depending on the GPU. Each instance has its own compute, cache, memory and memory bandwidth. Because the split is in hardware rather than software, you get guarantees that other sharing methods can’t give:

 Predictable latency –  Each partition has dedicated memory bandwidth, so one model’s traffic spike doesn’t show up in another model’s p99.

 Fault isolation –  A crash or memory error stays inside its partition instead of taking down every model on the GPU.

 Right-sized capacity –  Small and mid-sized models get a slice that fits them instead of a whole GPU. You can mix slice sizes on one device.

 No cold starts –  Every model keeps its own partition and stays loaded, with no load penalty and no eviction.

 Tenant isolation –  Memory protection between partitions is enforced in hardware, which makes security and compliance reviews simpler.

 Reliable planning and chargeback –  A partition performs the same way regardless of its neighbors, so load tests predict production. GPU cost also maps cleanly to a model, team or tenant.

 Partitioning has boundaries worth knowing up front. The maximum number of partitions depends on the accelerator and never exceeds seven. MIG itself only allows a layout to change while its partitions are idle, and on SageMaker AI that means choosing a layout when you create the endpoint. A model that needs more than one GPU still needs whole devices. Within those boundaries, you get the isolation of separate GPUs without dedicating one to each model.

 Partitioning without the platform work

 Until now, getting MIG meant running the Kubernetes stack yourself. GPU partitioning on Amazon SageMaker AI removes that step: you pick a partition profile for your model, and SageMaker AI handles GPU configuration, placement and scaling. You get hardware-isolated GPU sharing on a managed endpoint, without having to run the platform underneath it.

 Salesforce has been part of this work from the start, helping define the requirements and validating the initial implementation.

 “NVIDIA MIG partitions a single GPU into multiple isolated instances, each with dedicated compute and memory resources. Salesforce sees this as an important capability because many inference workloads do not require an entire GPU. MIG would allow us to consolidate workloads safely, significantly improve GPU utilization, reduce inference costs, and maintain predictable performance and strong isolation. 

 This capability would help us scale AI Inference more efficiently across different use cases. Salesforce has helped define requirements, validated the initial solution.  How it works

 GPU partitioning adds two optional fields to API calls you already make. There are no new API operations, no new resource types, and no new AWS Identity and Access Management (IAM) actions, and an endpoint that omits both fields behaves exactly as it does today.

 AcceleratorPartitionLayouts goes on a production variant in CreateEndpointConfig and declares how each accelerator is divided:

 {
 "EndpointConfigName": "multi-model-partitioned",
 "ExecutionRoleArn": "<execution-role-arn>",
 "ProductionVariants": [
 {
 "VariantName": "AllTraffic",
 "InstanceType": "ml.p4d.24xlarge",
 "InitialInstanceCount": 1,
 "AcceleratorPartitionLayouts": [
 { "AcceleratorPartitionTypes": ["mig-4g.20gb", "mig-2g.10gb", "mig-1g.5gb"] }
 ]
 }
 ]
} 

 An A100 has seven compute slices to divide. The preceding layout uses all seven, so each of the eight A100s on the p4d instance carries three partitions and the endpoint provides 24, eight of each type.

 The carve applies uniformly. One layout entry describes how one accelerator is divided, and every accelerator on every instance in the variant is divided the same way. The list isn’t positional, so an entry doesn’t map to a specific GPU.

 AcceleratorPartitionType goes on an inference component and selects which partition the model runs on:

 "EndpointName": "multi-model-partitioned",

 "Specification": {
 "ModelName": "summarizer-model",

 "AcceleratorPartitionType": "mig-4g.20gb",
 "NumberOfAcceleratorDevicesRequired": 1,

 "MinMemoryRequiredInMb": 2048
 }
 },
 "RuntimeConfig": { "CopyCount": 1 }
} 

 Each component copy occupies one partition of the requested type. With eight partitions of each type on the instance, raising CopyCount places additional copies on free partitions. This is useful for a small model serving high concurrency, where a single process leaves the GPU waiting on requests.

 NumberOfAcceleratorDevicesRequired is always 1 here. With a partition type set it means one partition rather than one accelerator. NumberOfCpuCoresRequired and MinMemoryRequiredInMb still describe host CPU and host memory, because GPU memory comes from the partition type.

 Invocation doesn’t change. InvokeEndpoint addresses a model by inference component name, and the partition it occupies never appears in the request.

 Partitioning happens while the endpoint is provisioned. When it reaches InService every accelerator is carved and the partitions are empty, which is a valid state as components land on them afterward. In our testing, carving accelerators added roughly 17 seconds to provisioning. The rest of the time is the usual instance launch and container pull.

Artificial Intelligence 

 Taxonomy of agentic primitives in Amazon Quick

 Over the past year, as we built Amazon Quick, our agents went from answering questions to taking actions: scheduling meetings, running research, generating reports. As the system evolved, one problem kept resurfacing: there was no shared definition of the primitives that agentic work is built from. The same few ideas kept getting rebuilt under different names: an actor that does the work, a signal that starts it, a packaged procedure, and a memory that carries lessons forward. This repetition leaked into product design and onto the user.

 Take the user who says “ monitor my Slack channel and send me a daily digest ”. Is that a new agent, a scheduled instruction to an existing one, a workflow, or a skill? These are different questions, but without a shared vocabulary they collapse into one confusing choice.

 This post shares the taxonomy we converged on: one set of primitives found by decomposing agentic work into four plain questions: When? , What? , Who? , and How? Most of the framework stays invisible to end users by design, but a shared vocabulary makes the system easier to reason about for anyone building beneath it.

 The framework at a glance

 Figure 1: How triggers, agents, and capabilities relate, with learning feeding back from the session runtime

 A trigger starts the work and carries the task ( When and What ), an agent takes it on ( Who ) and uses its capabilities (tools, skills, and workflows) to perform the task ( How ). This post describes these primitives and how they relate to one another. It’s the first post in a series, and upcoming posts cover our agentic operating system, background learning, proactive feeds, and much more.

 Triggers: What causes work to begin

 Triggers are the activation mechanism for getting work done, but they also carry instructions: a human message is both the moment of activation and the description of what to do. They are both the When? and the What? of a task.

 Human-initiated: A person opens a conversation and asks the agent to do something. Interactive, synchronous, conversational.

 Agent-delegated: One agent, mid-task, invokes another to handle a sub-problem. Programmatic, composable, potentially recursive.

 Scheduled: Time-based activation, like “run financial research every Monday at 9am.” Deterministic, with the same standing instructions applied across runs.

 Event-driven: A signal from an external system, such as a new email, a Slack mention, a file change, or a webhook.

 The type of trigger conditions the execution: a scheduled background task might stay conservative (for example, do nothing if uncertain), while a human-initiated one would be responsive (for example, ask rather than stop).

 Agents

 We define an agent as a persistent, learning actor . It’s the Who? in any execution, and the anchor against which learning accrues. Two agents given identical input can differ, because they carry different instructions, capabilities, and histories. The agent isn’t the instructions it follows. It’s the entity that interprets them. It consists of three things:

 Instructions:  Standing guidance defining persona, role, context files, and operating principles. A Finance Agent behaves differently from a general assistant primarily because of this.

 Capabilities:  The tools, skills, workflows, and sub-agents available for use, updated dynamically. A charting library can be added in one session and removed the next.

 Learned context:  Memory that accumulates through use: the queries that work for a tool, the formatting users prefer, the edge cases they care about. This is how the tenth execution beats the first without anyone changing the instructions.

 Everything else is extrinsic: the large language model (LLM) underlying the agent is a swappable model parameter, conversation history is per-session state, and triggers belong to the platform.

 A consequence of this definition is that a user request “ I want an agent that monitors my Slack and sends a digest every morning ” is usually a trigger added to an existing agent , not a new agent or workflow. With this framing, we can merge chat, scheduled, and “autonomous” agents into one actor that you can converse with, schedule, and that can orchestrate and inspect its own past work.

 Capabilities

 Capabilities are How an agent acts, spanning a spectrum from fully agentic to fully deterministic. That axis is really a confidence contract : how much latitude the agent keeps versus how much the user fixes in advance.

 Tools are atomic operations with a typed schema: send an email, query a database, read a file. Whether a local function, a Model Context Protocol (MCP) server, or another agent behind a protocol boundary, the caller sees the same interface: name, description, parameters, result.

 Skills are structured guidance with room for judgment: instructions bundled with resources (templates, scripts, examples) that describe an approach rather than a rigid sequence. They load through progressive disclosure , so the agent sees only names and short descriptions until one becomes relevant, then reads the full instructions in. A skill can therefore bundle arbitrary depth of expertise without a constant cost.

 Workflows are deterministic coordination: declared steps, control flow, branching, and error handling that execute in fixed order, with decision logic in code rather than model inference. Think of a purchase-approval route: budget check, manager sign-off, then finance, each recorded. The route is fixed, but the judgment inside a step is still the agent’s.

 Figure 2: Skills versus workflows, which differ in whether the agent or the code decides the step order

 Why skills and workflows outlast model improvements

 A natural question arises: if models keep improving, won’t skills and workflows become unnecessary? We don’t think so, because each holds value independent of model capability. Skills are the unit for capturing, versioning, and sharing institutional expertise, while workflows deliver auditability, step-wise visibility, and deterministic multi-service coordination. Nor are they fixed: a well-understood skill can tighten into a workflow ( crystallization ), a workflow that keeps hitting edge cases can loosen back into a skill ( dissolution ). This is done in Quick through our continuous learning framework, which we will describe in a future post.

 What this means in practice

 Return to “ monitor my Slack channel and send me a daily digest ”. Because these primitives compose, the same request can be met several valid ways:

 A scheduled task with a one-line instruction, leaving the agent to figure out the rest.

 The same task backed by a skill with explicit formatting rules and channel priorities.

 The same task invoking a workflow with deterministic steps and error handling.

 All three produce a daily digest on a schedule. What differs is the confidence contract. A user who trusts the agent wants the first, one burned by inconsistency the second, one running a compliance-sensitive process the third.

 Learning shifts that trajectory over time. A task that starts as one sentence (“ check my email for urgent items ”) accumulates domain-bound learnings: effective queries, preferred formatting, and which senders matter. The tenth run is markedly better, with no one encoding that by hand. The right design is the simplest option that meets the user’s confidence requirement, with a path to graduate through autonomous learning when they need more.

 Conclusion

 The value of this agentic primitive taxonomy is that four plain questions, When , What , Who , and How , are enough to place any piece of agentic work, from a one-line chat request to a scheduled, compliance-grade process. Sharing one vocabulary lets builders reason about the system and lets the product hide complexity. Best of all, the user never has to learn any of it. They say what they want, and the system assembles the appropriate primitives to do their job.

Artificial Intelligence 

 Serverless MCP server for AI agent data lake access on Amazon ECS Fargate

 Organizations building applications powered by artificial intelligence (AI) face a recurring challenge: giving large language model (LLM) agents access to enterprise data lakes without duplicating integration logic across every agent and application. Most teams begin by wiring agents directly to databases and APIs, with no shared gateway such as a Model Context Protocol (MCP) server in between. Each new dataset demands custom code, and each agent reimplements its own access control. As the number of datasets or agents grows, permission enforcement drifts, and onboarding a new data source becomes a multi-day engineering effort.

 Our team supports Amazon’s North America Sort Center (NASC) network, where planning teams rely on operational data to manage capacity, labor, and package flow. To give those teams conversational access to that data, we built a serverless Model Context Protocol (MCP) server on Amazon Elastic Container Service (Amazon ECS) with AWS Fargate to address this problem for planning teams in NASC. The server acts as a centralized, agent-agnostic gateway between AI agents and our enterprise data lake. Exposing a new dataset requires only a JSON metadata file that the server discovers automatically on the next pipeline sync.

 In this post, we describe the architecture, show how a metadata-driven approach removes the need for per-dataset integration code, and explain how the serverless infrastructure supports multiple agents and applications in a multi-tenant environment.

 Problem statement and design goals

 Two interrelated challenges shaped how we designed this system: fragmented data access patterns and an unsustainable onboarding model.

 Integration challenge at scale

 Our data lake contains thousands of datasets spanning operational metrics, business analytics, and domain-specific data. Multiple teams wanted AI assistants that could query this data conversationally, but each built its own integration from scratch. Each agent embedded its own SQL generation logic, schema knowledge, and connection handling, so a schema change meant patching every agent individually. Access control was fragmented, with no single audit point for data access decisions. Onboarding a new dataset required custom tool code, query validation, and redeployment, typically a multi-day effort per table.

 Design goals

 We established four requirements:

 Configuration-driven data lake access. Adding a dataset requires only a metadata file, not code.

 Agent-agnostic tool interfaces. Any MCP-compatible client can invoke the same tools.

 Centralized permission enforcement. Access control is enforced at the MCP server layer.

 Elastic infrastructure. The system scales with bursty AI workload patterns.

 Solution overview

 The architecture separates concerns into four layers (client, MCP server, tools, and knowledge-base refresh), each independently scalable and deployable. A metadata catalog underpins the tools layer, storing schema descriptions, column-level semantics, and table relationships that the AI agent references when generating SQL. Because the agent derives schema knowledge from the catalog at query time, there is no need to hardcode table structures or redeploy when schemas change. The knowledge-base refresh layer keeps that catalog current, indexing new dataset metadata as it arrives. The following sections describe each layer in detail.

 Architecture walkthrough

 The following diagram shows the request flow from user query to data layer across all four layers. A user submits a query from a client application (web chat, Slack, an IDE plugin, or an external agent). The request resolves through Amazon Route 53 for DNS and reaches an Application Load Balancer in a public subnet, configured with HTTPS and AWS WAF. The load balancer routes to Amazon Cognito, which authenticates the user and enriches the request. Authenticated traffic then enters the private subnet, where the client layer runs on Amazon ECS Fargate. This layer handles session state in Amazon DynamoDB and forwards requests through an internal Application Load Balancer to the MCP server layer, also on Amazon ECS Fargate. In the MCP server layer, an AI agent powered by Amazon Bedrock orchestrates tools built with FastMCP (a Python framework for building MCP servers). Amazon Bedrock Guardrails is applied to every model interaction. On the right, the data layer holds the tool backends. Amazon Athena and Amazon Redshift run SQL queries against the data lake, and Amazon Bedrock Knowledge Bases, the fully managed Retrieval Augmented Generation (RAG) capability, handles semantic search. Data ingestion into Amazon Simple Storage Service (Amazon S3) and the knowledge bases is handled by AWS Lambda. Each layer is described in detail in the sections that follow.

 MCP server layer: Stateless execution with conversation state

 The MCP server runs on its own ECS Fargate cluster, isolated from the client layer. Requests reach it through Amazon Route 53 and an internal Application Load Balancer in a private subnet. When a request arrives, the agent retrieves session history, analyzes user intent using Amazon Bedrock, discovers and invokes appropriate tools, and streams results back to the user.

 How ToyBlocks works
