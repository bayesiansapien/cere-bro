# SingVL-4B GGUF

SingVL-4B GGUF is the GGUF release of Sing VL S1, a 4B-parameter multimodal decision model built on Qwen3.5. It answers named questions over text or JSON and up to four images. Each question uses one complete forward pass to score the supplied options.

- **Choice** selects an option and returns a probability for each candidate.
- **Noul** returns the probability that a yes/no proposition is true.
- **Score** rates the input against 2–10 levels ordered from low to high. It returns the probability of each level and the expected level, computed as the sum of each zero-based level index times its probability.

Full-attention layers use bidirectional attention over the complete input. GDN layers keep causal recurrence. Each question starts with cleared KV and recurrent state, and reads candidate logits at the last valid input position. The included llama.cpp adapter applies this attention contract automatically.

## Usage

The included backend uses llama.cpp on Linux x86_64 CPU. Use Python 3.12 and compatible PyTorch and torchvision builds for input processing. Build the adapter once using the pinned llama.cpp commit, then run the Python or HTTP examples from this repository's root directory. The default context capacity is 4096 tokens, including image tokens. [Build instructions](docs/build.md)

### Python

'''python
import os
from PIL import Image
from examples.llama_cpp.model import SingVLS1

os.environ["JEV_GGUF_MODEL"] = "models/SingVL-4B-Q8_0.gguf"
os.environ["JEV_GGUF_MMPROJ"] = "models/mmproj-SingVL-4B-F16.gguf"
os.environ["JEV_CPU_CONTEXT"] = "4096"
os.environ["JEV_CPU_THREADS"] = "8"

model = SingVLS1("config", device="cpu")
try:
    text, _ = model.predict(
        state="The color is red. ",
        questions={
            "color": {
                "type": "choice",
                "instructions": "Which color is named?",
                "criteria": {"red": "Red", "blue": "Blue"},
            },
            "yesno": {"type": "noul", "instructions": "Is the named color red?"},
            "redness": {
                "type": "score",
                "instructions": "How clearly does the text identify the color as red?",
                "criteria": ["Not red", "Possibly red", "Clearly red"],
            },
        },
    )
    print(text["answers"])

    questions = {
        "which": {
            "type": "choice",
            "instructions": "Which image is red?",
            "criteria": {"first": "The first image", "second": "The second image"},
        }
    }
    with Image.open("examples/images/blue.png") as blue, Image.open("examples/images/red.png") as red:
        for state in ({}, "<image>\n<image>\n"):
            vision, _ = model.predict(state=state, questions=questions, images=[blue, red])
            print(vision["answers"])
finally:
    model.close()
'''

With implicit image placement, the processor inserts image markers before the state text. Explicit `<image>` markers match the images in list order, with one marker per image. State and question instructions are concatenated, so retain a trailing space or newline in a text state when a separator is needed.

Score questions use the same format for text and images. The response includes `score`, `probabilities` and `legend`. Probabilities of `0.1`, `0.3` and `0.6` on three levels give `0 × 0.1 + 1 × 0.3 + 2 × 0.6 = 1.5`.

 Where inference cost comes from

 Every Amazon Bedrock response carries usage metadata. Input and output tokens bill at the rate for the model and tier that served the request. Cache reads and writes use separate token counters, and reasoning tokens count as output tokens.

 Prompt cache duration

 Repeated system instructions, tool definitions, or reference context can be processed again when the cache expires before the next request. The Prompt caching for faster model inference guide lists 5-minute and 1-hour time-to-live (TTL) values for supported Anthropic models.  For supported models, Amazon Bedrock also offers implicit prompt caching , which attempts to reuse eligible prompt prefixes without cache controls in your request. Because implicit caching is best effort and doesn’t guarantee a cache hit, the duration choices in this section apply to explicit caching.

 { "cachePoint": { "type": "default", "ttl": "1h" } }

 Cost per task, not cost per token

 Price per token invites quick comparison, but it doesn’t reflect what you actually pay. The published rate reflects the cost of a single token. Your bill reflects the cost of completing a task. A task is one complete unit of work your application asks a model to do: resolve one support email, extract fields from one invoice, or answer one user question. A task runs from the request through to a usable result, however many model calls it takes.

 The lower-priced model might not be the cheaper one to run. A cheaper model might fragment your text into more tokens, pad responses with filler, misread your tool schema and loop through corrections, or burn thousands of reasoning tokens before answering. None of these costs appear on the Bedrock pricing page .

 The four hidden cost drivers

 Four model characteristics determine what that published rate actually costs you on your workload.

 Tokenizer efficiency

 A token isn’t a word, and it is not equal across models. Every model family uses a different tokenizer and vocabulary. The same text, code, or JSON payload splits into different token counts. If Model A’s list price is 15 percent lower but its tokenizer needs 40 percent more tokens for your data (common with structured schemas and numerical arrays), Model B is cheaper. The gap widens for non-English text: many tokenizers fragment non-Latin scripts into two to three times more tokens than the equivalent English.

 Output alignment and verbosity

 Output tokens commonly cost 3–5x more than input tokens (the ratio varies by family. Refer to the Bedrock pricing page ). A model that ignores formatting constraints like “return only raw JSON” makes you pay that output premium for filler words. A model that follows formatting instructions closely saves money by generating fewer of these more expensive output tokens.

 Agentic loop efficiency

 Agentic workflows change the cost math entirely. Tool use (function calling) lets a model invoke external functions, requiring a multi-turn loop: analyze the prompt, decide to call a tool, wait for the observation, generate an answer. Each turn re-sends the full conversation history and tool results as input tokens. A model that takes four turns (each one re-sending a larger context payload) costs far more than one that finishes in a single pass.

 Reasoning overhead

 Many models support extended thinking , working through a chain of thought before the visible answer. Reasoning tokens bill as output tokens, so a model that thinks for 2,000 tokens before a 200-token answer bills you for 2,200. Some models redact the reasoning while still charging for it. Start with reasoning turned off and enable it only when benchmarks show a quality gap that justifies the cost.

When an agent searches on behalf of a user, can you make sure that it uses only the information that user is allowed to see?

 I help lead Google's agent skills program , currently with 175 agent skills that supplement community collections like go-skills . To keep that many skill files consistent, I wrote skill-lint, a standalone Go CLI that checks SKILL.md files and applies LLM-generated line edits before they ship. Even with skill-lint's own unit and fuzz test suite, a small slice or line-number mistake inside its Markdown parsers or edit applier can sit dormant until an unusual file or edit range triggers a runtime panic in the linter.
 In Go, every slice or index operation that can panic at runtime compiles down to an explicit bounds-check trap in machine code, after the compiler's optimizer strips out the checks it can already rule out. To hunt for crashes, I compiled key functions from my code to see which panic traps survived optimization, and Gemini 4 Argon translated the path to each trap into rules for the Z3 constraint solver . An LLM-written solver model isn't a sound proof system, but it gives the agent an independent way to reason about control flow and synthesize concrete Go reproducers, and every crash it finds is real because go test runs the offending bytes directly. That workflow caught all three bugs I planted in test parsers and turned up three latent bugs in skill-lint.
 In this post, I'll walk through how the Gemini and Z3 pipeline works, why go test -fuzz missed two of those crashes (and the one-line change that fixes it), and where this approach fits in a day-to-day Go workflow.
 How the solver pipeline works
 A recent post from Anthropic showed how formal verification catches latent bugs in C and C++ by having frontier AI models write machine-checked Rocq proofs across OSS-Fuzz libraries. Instead of sampling random inputs like a fuzzer, a formal tool works backward from each failure condition to solve for the exact input that triggers it. Full theorem proving is still too heavy for most day-to-day Go projects, so I wanted to see how much of that bug-hunting power an agent can get from an LLM and a constraint solver in about a minute per function.
 In C and C++, reading or writing past the end of a buffer corrupts memory. Go catches out-of-bounds access at runtime instead, compiling every slice or index operation it can't prove safe into an explicit branch to runtime.panicBounds that panics, crashing the process unless recovered.
 Before generating machine code, Go's SSA prove pass already eliminates most of those checks by tracking slice lengths and loop variables. That optimization pass leaves behind only the runtime.panicBounds traps the compiler couldn't rule out on its own, giving the solver a short list of candidate crash sites to target.
 I compiled each target with GOOS=linux GOARCH=riscv64 go build -gcflags="-S -d=ssa/check_bce/debug=1" ( -S prints the assembly listing and ssa/check_bce/debug=1 logs every surviving bounds check) and passed both the Go source and the disassembly to the model. Looking at Go source alone, you can't see which bounds checks the compiler already removed or where a register gets truncated to 8 bits; in the disassembly, both show up. I targeted RISC-V because it's the instruction set Anthropic's post targets for its Rocq proofs, and Go cross-compiles to it out of the box.
 From there, Argon read the Go source and disassembly and returned a Z3 script modeling the path to each surviving trap, along with a patched function whenever it flagged a bug. Z3 then checked whether those constraints could be satisfied, and whenever it found a crashing input, go test replayed those bytes against the real function. Using an LLM saved me from translating assembly into solver constraints by hand. Argon's translation dominated the runtime, at about a minute per function, while Z3 itself finished in milliseconds.

 Go's SSA compiler strips out provably safe bounds checks first. Gemini 4 Argon then models the remaining traps for Z3 to check.

 When to trust the solver 
 Anthropic's approach relies on interactive theorem proving , where experts model machine semantics and Rocq checks LLM-generated proofs against those rules. In contrast, my workflow uses a constraint solver based on satisfiability modulo theories (SMT) , relying on Argon to translate assembly directly into Z3 constraints. While a constraint solver doesn't provide a complete correctness proof without a semantic model, it is highly effective for finding bugs. Z3's check-sat command returns sat when input constraints can be satisfied and unsat when they cannot.
 A sat answer ("definitely buggy") comes with concrete bytes aimed at the trap, and go test runs them against the real function. Once go test panics, you have a concrete bug reproducer regardless of whether Argon's model was sound. Like a Bloom filter for bugs, an unsat answer only means "maybe correct." Trading away a correctness proof is what makes the approach so practical: you get most of the bug-finding value of formal methods for a tiny fraction of the effort.
 Anthropic's setup proved no-crash properties on whole binaries under a 64 MB budget; I checked individual functions on fresh 64-byte slices where cap(buf) == len(buf) , so any slice past len(buf) panics. (If you want the full-binary Rocq setup for Go, theorem-labs/oss-verify includes a Go 1.27 runtime overlay that makes the runtime single-threaded and deterministic.)
 For the fuzzing baseline, I ran unseeded go test -fuzz on Go 1.27.3 against each planted bug: one 3-second run and three 60-second runs, each with a fresh fuzz cache so a short time budget wouldn't explain a miss.

 Never read : no tool returned the instruction, so the agent never saw it.
 Resisted : the agent read the instruction but didn't follow it. This includes an agent that tried and failed.

 Report attempts that the agent resisted, at a lower severity, so you can see when someone is probing your agent.
 Catch small actions that reach an untrusted destination, such as a single visit to an unknown web page.
 Tell normal use of high-impact tools apart from misuse.
 Give new agents full coverage sooner.
 Detect instructions planted in long-term memory more reliably.

However, building a machine capable of realizing this promise has long proved challenging. Today, several architectures have emerged offering different routes to running quantum algorithms at scale.

 The core unit of quantum computing is the quantum bit, or qubit. These are physical objects like atoms, electrons, or superconducting circuits whose innate properties are quantized, meaning they assume discrete (rather than continuous) values onto which we can encode the zeros and ones of computation. Being quantum mechanical, these values can also enter superposition — a linear combination of zero and one — and entangle with one another, so the information is distributed across multiple qubits at once. A quantum computer must prepare and manipulate the qubit states, and at the end of the computation, measure the array to a final bit string.

 IBM currently researches two hardware architectures for quantum computing. The first and more mature of the two is based on the superconducting transmon qubit, which is made from superconducting electrical circuits — circuits that transmit electrical current without resistance and can assume discrete energy states. The second and newer approach is based on spin qubits, which encode and manipulate information stored in the spin state of individual electrons. HRL Laboratories, an IBM company, has been pursuing spin qubits.

 What is spin? 
 How can spin represent qubits? 
 What are the comparative advantages of spin qubits? 

 What is spin?

 Spin is an intrinsic quantum property with no classical analogue, although some of its mathematics look similar to those of a spinning ball. Electron spins can either point up or down, taking values of positive one-half or negative one-half. When measured, quantum spins can never take values other than those options, breaking the direct analogy to a spinning ball, which might go faster or slower, or rotate about a different axis than the one you’re measuring. Spin can present in many ways in atoms, molecules, and materials: Multiple electrons working together can take on higher spin states, or even exhibit spin from the absence of an electron (a “ hole ”). A spin-based quantum computer encodes information in selected states of one or more spins.

 Using a spin qubit first requires trapping one or more individual electrons in structures called quantum dots. HRL’s quantum dots utilize a layer of silicon sandwiched between layers of silicon-germanium, which confine the electron in that silicon layer in a two-dimensional plane. We then apply a voltage to a microscopic metal gate fabricated on top of this “heterostructure,” trapping an electron directly below the gate. There are other ways to trap electrons, using different quantum dot structures or even using implanted atoms.

 How can spin represent qubits?

 There are several types of spin qubit architectures. These are the two most popular:

 In the Loss-DiVincenzo spin qubit, a single quantum dot traps a single electron whose state is controlled by microwave pulses. The direction that the spin points (up or down) stores the value of the qubit. Neighboring qubits are entangled by causing the electrons’ quantum wavefunctions to briefly overlap using voltage pulses on the gates, producing an “exchange” interaction.
 Exchange-only qubits use three quantum dots (and therefore three electrons) to represent a single qubit. This type of qubit can be controlled entirely through electron-electron exchange interactions (no microwaves), with baseband voltage pulses similar to those of conventional electronics, though many of them.

 HRL has developed a spin qubit architecture based on the exchange-only qubit, most recently demonstrating a complete system with 54 quantum dots, configurable to host as many as 18 qubits, on which we implemented a simple quantum-error-detecting code. Like superconducting quantum processors, spin qubits must be kept cold in a dilution refrigerator.

 What are the comparative advantages of spin qubits?

 Spin qubits have several properties that make them promising candidates for quantum computing. They have high gate fidelities, and can be fabricated using advanced semiconductor processes, making them amenable to scaling toward the large qubit counts required by many quantum use cases. Spin qubits are relatively fast — certainly faster than ion traps or neutral atoms. Considering measurement speed, though, they are not as fast as superconducting quantum processors.

 Perhaps most importantly, since exchange-only qubits rely on only voltage pulses for applying gate operations, these qubits only require relatively simple control signals. In the same paper where HRL showed basic error correction, the quantum processing unit was controlled entirely with a custom CMOS chip operating at 4 K, near the coldest plate of the dilution refrigerator. This greatly reduced the number of necessary connections from room temperature, enabling future systems to grow larger more quickly. This will be a greater challenge for qubits that rely on microwaves for control, since that hardware generally has to stay at room temperature and be connected to qubits with long coaxial cables.

 Spin qubit-based quantum computers don’t have as many qubits as superconducting ones at present, and there are still challenges to scaling. We are working to make our qubits more uniform and improve their fabrication yield using the facilities at Anderon. We also must reduce the amount of power required by our controller and further consolidate the wiring required as we scale up. We have research underway to tackle these challenges and more.

 There are comparative advantages of pursuing spin qubits and superconducting qubits in tandem. Both are based on semiconductor fabrication technology, so advances on fabricating one platform could potentially benefit the other. Additionally, given the similarities of their underlying hardware platform, we are excited for the potential to explore hybrid systems employing both flavors of qubit architecture.

 Ultimately, we expect that superconducting qubits will take us into the era of fault tolerance before spin qubits do, beginning with IBM Quantum Starling and continuing with IBM Quantum Blue Jay. However, IBM is also pushing forward with spin qubits to better understand how they might contribute to future, larger or less expensive systems. We are excited to have spin qubits as part of our portfolio as we work to bring useful quantum computing to the world.

 Solving a 31-year-old mathematics challenge  

 For the last 31 years, the KLS conjecture has been one of the central open problems in high-dimensional geometry. But not anymore.

 New research has resolved the conjecture. This removes a major theoretical obstacle to understanding the efficiency of randomized algorithms used across science and computing. 

 The breakthrough establishes a universal principle for log-concave distributions: simple flat cuts can identify their narrowest bottlenecks within a fixed factor, regardless of dimension. The results have been independently validated, and the proof has also been formally verified using computer-assisted methods. 

 Learn more about this breakthrough on the Microsoft Research blog.

 Making AI coding agents more efficient 

 Coding agents can help when writing and modifying code, but long sessions can max out the amount of information an AI model can process at once. As a result, coding agents will summarize earlier interactions in a resource-intensive process known as context compaction.

 A new study looked at 13.5 million coding sessions and found fewer than 8% required context compaction. Yet those sessions accounted for 44% of total AI processing costs. 

 To address this challenge, researchers developed COMPACTIONBENCH.

 COMPACTIONBENCH is a benchmark for evaluating context compaction during long-running coding tasks. They also introduced APEC, a method that prepares summaries in the background instead of interrupting an agent’s work. 

 In evaluations, APEC improved coding performance while reducing costs by up to 25.4% and execution time by 9.6%. 

 [TRANSITION MUSIC]

 Improving AI tokenization across 104 languages 

 Before AI models can process text, they break it into smaller units called tokens. How that text is divided can affect both efficiency and performance, especially across different languages. 

 Most tokenizers are designed to compress text as efficiently as possible. But a new study suggests that compression alone isn’t enough. 

 Researchers introduced the Latent Core Tokenizer, or LCT, which identifies reusable components of words before building a shared vocabulary across languages. 

 In evaluations spanning 104 languages, LCT produced more linguistically meaningful tokens than leading alternatives while maintaining comparable efficiency across languages. It also improved model performance across four multilingual benchmarks. 

 The findings suggest that better tokenization depends not just on how much text can be compressed, but on how well the underlying structure of language is preserved.
