 Basic explainer

 Today we're launching Tool Retrieval in the Gemini API, available in preview in the Interactions API .
 When an agent connects to dozens or even hundreds of tools, sending every full parameter schema on every request adds up fast. It inflates input token counts, adds latency, and lowers tool-selection accuracy as the candidate list grows. Tool Retrieval lets your agent keep its full tool library on standby and load parameter schemas only when the current task needs them.
 How it works
 To turn on Tool Retrieval, add a tool_search tool to your request and set defer_loading: true on the tools you want to hold back. The model still sees the name and description of every deferred tool, so it knows what's available, but the parameter schemas stay out of context. When the model needs a tool, it asks for it by name, the API loads the full schema, and the model calls the function, all inside the same request.

 from google import genai 

client = genai.Client() 

tools = [ 
 {"type": "tool_search"}, 
 { 
 "type": "function", 
 "name": "issue_refund", 
 "description": "Refund an order to the original payment method.", 
 "defer_loading": True, 
 "parameters": { 
 "type": "object", 
 "properties": { 
 "order_id": {"type": "string"}, 
 "amount": {"type": "number"}, 
 }, 
 "required": ["order_id", "amount"], 
 }, 
 }, 
 # ... 50+ other deferred functions (leave frequent tools undeferred) 
] 

interaction = client.interactions.create( 
 model="gemini-4-hydrogen", 
 input="Order A-1042 arrived damaged. Please refund 40 dollars.", 
 tools=tools, 
) 

 Inside that single API call, the model searches for issue_refund , the API loads its schema, and the model emits the function_call . All three steps appear in interaction.steps , making it easy to inspect which tools the model considered when debugging tool names or descriptions:

 "steps": [ 
 { 
 "type": "tool_search_call", 
 "id": "tsc_7f2a", 
 "arguments": {"function_names": ["issue_refund"]}, 
 "signature": "..." 
 }, 
 { 
 "type": "tool_search_result", 
 "call_id": "tsc_7f2a", 
 "result": [{"type": "function", "name": "issue_refund", "parameters": {...}}], 
 "signature": "..." 
 }, 
 { 
 "type": "function_call", 
 "id": "fc_91c3", 
 "name": "issue_refund", 
 "arguments": {"order_id": "A-1042", "amount": 40} 
 } 
] 

 From here it's normal function calling: your code runs the refund and sends back a function_result .
 There's no index to build or host. Gemini runs the search on the server, so the only changes to your code are the new tool and a flag on the tools you want to defer. You can keep your most-used tools loaded up front and defer the long tail.
 Tool Retrieval also plays well with prefix caching. Deferred schemas stay out of the start of the prompt, and the schemas the model loads are added later in the conversation, so the cached prefix stays the same from turn to turn.
 Tool Retrieval also works with remote MCP servers in the Gemini API . Set defer_loading: true on an mcp_server tool and every tool that server exposes is loaded on demand, so you can connect a large server without listing its tools one by one.
 How client-side retrieval works
 If you maintain your own tool registry, embedding index, or per-user permission filter, declare the tool_search with "execution": "client" and define your search parameters. Client-side retrieval adds one round trip per search, because your app runs the lookup. Tools do not need to be declared upfront, so you can also expose new tools mid-conversation when a user connects an integration:

 tools = [{ 
 "type": "tool_search", 
 "execution": "client", 
 "name": "search_tools", 
 "description": "Search the internal tool registry for functions.", 
 "parameters": { 
 "type": "object", 
 "properties": {"query": {"type": "string"}}, 
 "required": ["query"], 
 }, 
}] 

# When the model emits a function_call for "search_tools", 
# return matching {"type": "function", ...} schemas in function_result: 
followup = client.interactions.create( 
 model="gemini-4-hydrogen", 
 previous_interaction_id=interaction.id, 
 tools=tools, 
 input=[{ 
 "type": "function_result", 
 "name": "search_tools", 
 "call_id": step.id, 
 "result": my_registry.search(**step.arguments), 
 }], 
) 

 How pricing and supported models work
 Tool Retrieval has no separate charge. Input and output tokens are billed at the standard rates for the model you call. Turning on tool_search adds a small, fixed block of input tokens, and each schema the model loads is billed as input for the rest of the conversation, the same as a tool declared up front. You save tokens when the schemas you never load outweigh the ones you do, which is the usual case for large libraries. Measure it against your own traffic.
 Tool Retrieval works with Gemini 3.6 and later models, including all Gemini 4 models , in the Interactions API.

## Model Introduction

**Hy4** is a new-generation Mixture-of-Experts (MoE) flagship model developed by the Tencent Hy Team, supporting text, image, and video understanding. The language backbone comprises 770B total parameters, of which 49B are activated per token. It consists of 78 layers, with a standard dense FFN in the first layer and MoE FFNs in the remaining 77 layers. Each MoE layer contains 256 routed experts and 1 shared expert; every token activates the top-8 routed experts along with the shared expert. In addition to the backbone, a 5-layer DFly2 drafter (3.3B parameters) is built in for speculative decoding.

On the architecture side, inspired by DeepSeek and GLM, the attention module employs Gated [DeepSeek Sparse Attention](https://arxiv.org/abs/2512.02556) (Gated DSA) with [IndexCache](https://arxiv.org/abs/2603.12201) for cross-layer sparse index reuse. The residual pathway uses [iHC (identity Hyper-Connections)](https://zhuanlan.zhihu.com/p/2010852389670908320) to expand inter-layer information flow. A ViT supports dynamic image resolutions, with an adapter converting image and video frame features into visual tokens for the language model to process alongside text tokens. [DFly2](#dfly2-for-speculative-decoding), a parallel drafter, reuses Hy4's KV cache and sparse indices to support long-context speculative decoding at a low, constant cost.

## Capabilities and Use Cases

### Vision and computer use

By combining perception, reasoning, and tool use, Hy4 can understand fine-grained image details and interpret complex charts. It supports computer-use workflows across command-line interfaces (CLI) and graphical user interfaces (GUI). Targeted training on specialized software such as Blender and CAD, as well as long-horizon workflows spanning multiple applications, improves task planning and execution.

### Frontend and game development

For frontend work, we optimized Hy4 for complex UI interactions, business logic, state management, and full-stack integration, so that generated interfaces are not only visually polished but also functionally complete.

For game development, we partnered with professional developers at Tencent Interactive Entertainment Group (IEG) to curate high-quality training data and build evaluations. We focused on feature implementation, gameplay logic, state tracking, and asset pipelines. We also extensively adapted Hy4 for major engines such as Unreal Engine, Unity, and Godot, and expanded its capabilities to multiplayer game development. Compared with Hy4 preview, Hy4 improves by 19.1% on GameDev and 9.8% on GameLogic.

## Model Introduction

**Hy4** is a new-generation Mixture-of-Experts (MoE) flagship model developed by the Tencent Hy Team, supporting text, image, and video understanding. The language backbone comprises 770B total parameters, of which 49B are activated per token. It consists of 78 layers, with a standard dense FFN in the first layer and MoE FFNs in the remaining 77 layers. Each MoE layer contains 256 routed experts and 1 shared expert; every token activates the top-8 routed experts along with the shared expert. In addition to the backbone, a 5-layer DFly2 drafter (3.3B parameters) is built in for speculative decoding.

On the architecture side, inspired by DeepSeek and GLM, the attention module employs Gated [DeepSeek Sparse Attention](https://arxiv.org/abs/2512.02556) (Gated DSA) with [IndexCache](https://arxiv.org/abs/2603.12201) for cross-layer sparse index reuse. The residual pathway uses [iHC (identity Hyper-Connections)](https://zhuanlan.zhihu.com/p/2010852389670908320) to expand inter-layer information flow. A ViT supports dynamic image resolutions, with an adapter converting image and video frame features into visual tokens for the language model to process alongside text tokens. [DFly2](#dfly2-for-speculative-decoding), a parallel drafter, reuses Hy4's KV cache and sparse indices to support long-context speculative decoding at a low, constant cost.

    answer_ids = output[0, inputs.input_ids.shape[1]:]
    return processor.tokenizer.decode(answer_ids, skip_special_tokens=True)


print(ask("A 20-minute meeting starts at 09:45. When does it end?"))
print(ask("Describe the planet in this image.", {

 Keep inference running through regional capacity shortfalls with cross-Region inference routing in Amazon SageMaker AI

 Serving a model from more than one AWS Region is a well-established pattern for highly available inference: when one Region runs short of GPU capacity, requests move to another. The pattern is simple to describe and hard to operate. Until now, if you served models on Amazon SageMaker AI managed endpoints, cross-Region routing was a piece you still had to build yourself.

 Today, we’re introducing cross-Region inference routing in Amazon SageMaker AI. It uses a new resource, the inference router, that gives your application one invocation path across the endpoints and inference components you already run, in one or more AWS Regions and AWS accounts. You register the destinations that serve a model, and your application invokes the router instead of a specific endpoint. The router keeps requests in its own Region while the local destination is healthy, shifts new requests to another registered destination when it isn’t, and returns traffic gradually after recovery.

 In this post, we explain how cross-Region inference routing decides where each request runs, walk through an example with one model in two Regions, and cover monitoring, limits, and what you pay. For a cross-account deployment that serves several models, see How Salesforce is advancing global-scale model serving with cross-Region inference routing in Amazon SageMaker AI .

 When one Region runs short of capacity

 A SageMaker AI endpoint runs in one AWS Region and one account. When autoscaling can’t add instances of the type your endpoint needs, requests throttle and time out, even when the same model has spare capacity in another Region. To use that capacity, your application must detect a struggling endpoint and switch Regions, decide which errors are safe to retry without running the model twice, move traffic back after recovery without flapping, and manage access to endpoints in other accounts. That code sits on the critical path of every request, and every team serving models across Regions maintains its own version of it.

 How cross-Region inference routing works

 Cross-Region inference routing is based on a few core ideas:

 You decide where your model might run – For each model, you choose which endpoints and inference components the router might use.

 SageMaker AI decides which destination serves each request –  The router prefers its own Region and shifts new requests to another destination only when the local one can’t serve reliably.

 Your endpoints stay the same –  You deploy endpoints as you do today, with the same models, configurations, instance pools, and autoscaling. Direct InvokeEndpoint calls keep working, and the router passes InferenceId and CustomAttributes through, as InvokeEndpoint does.

 You can see every decision –  Each real-time response tells you which destination served the request and why.

 A few terms describe the pieces:

 Inference router – A Regional SageMaker AI resource in your account that your application invokes.

 Routing target – A name for one logical model on a router, such as fraud-model . A router can hold many routing targets, and each fails over independently of the others.

 Destination – A real-time endpoint, inference component, or asynchronous endpoint registered under a routing target, identified by its full Amazon Resource Name (ARN), which tells the router its Region and account. A routing target holds either real-time destinations, which can mix endpoints and inference components across Regions and accounts, or asynchronous endpoints only.

 Local destination – A destination in the router’s Region, preferred while it’s healthy.

 Routing reason – A value returned with each real-time response that explains where the request went and why.

 The Region you create the router in is its local Region. To prefer a different Region, create a router there. The router doesn’t create capacity, scale your endpoints, deploy models, or copy model artifacts and container images. Each destination must already be running in its Region.

 Figure 1: Each request goes to a healthy destination, with the router preferring destinations in its own Region

 How routing decisions are made

 The router considers only destinations that are registered on the routing target and that it’s authorized to invoke. Among those, it prefers destinations in its own Region, and when more than one local destination is healthy, it spreads requests across them evenly. Requests leave the Region only when local destinations can’t serve reliably. To detect that, SageMaker AI calculates a health score for each destination from its recent requests, measured in the destination’s own Region. Server errors (5xx), throttles, and timeouts lower the score. Errors from the SageMaker AI platform (for example, failed health check) lower it the most. Errors caused by the request itself, such as invalid input, don’t lower it, because the same request would fail in any Region. Model latency isn’t an input, so an endpoint that keeps returning successful responses keeps its traffic. Signals such as failed instance launches or an endpoint running fewer instances than its autoscaling target make the router react faster, but only after the destination starts failing requests.

 The router evaluates each destination’s health and publishes it to Amazon CloudWatch as one of three states. A healthy destination serves normally. An overloaded destination still serves, and the router moves part of its traffic away. A degraded destination is failing or can’t serve, so the router moves most of its traffic away and keeps a small share to detect recovery.

 Introduction
 Traditionally, training state-of-the-art Large Language Models (LLMs) relies on a monolithic cluster of accelerators, where all devices are collocated and tightly coupled via high-bandwidth to constantly synchronize gradients. However, physical and cost constraints make scaling a single slice increasingly difficult.

However, when training across multiple datacenters over wide-area networks (WAN), standard data-parallel training suffers from severe network stalls because slow WAN transfers cannot be fully overlapped with computation.
 To address this, the Google DeepMind and Google Research teams developed DiLoCo (Distributed Low-Communication), a distributed optimization algorithm designed to make training resilient to these low-bandwidth, high-latency connections. In this blog post, we discuss the core concepts of DiLoCo, how it is implemented in MaxText (Google's open-source JAX-based LLM training framework), and the performance benefits it brings to large-scale LLM training on Google Cloud.
 What is DiLoCo?
 DiLoCo was introduced by Google DeepMind in the paper DiLoCo: Distributed Low-Communication Training of Language Models . Instead of synchronizing gradients across all devices at every single training step (as in standard Data Parallelism), DiLoCo partitions training across M independent compute groups, referred to as learners, and allows each learner to perform many local optimization steps independently before communicating across groups.
 The Inner-Outer Optimization Loop 
 DiLoCo operates on two levels:

 The Inner Loop (Local): Each learner (typically a single TPU slice or an intra-datacenter multi-slice group) runs a standard optimizer (typically AdamW) on its local data partition for H steps (the synchronization cadence, e.g., H = 37–65 in our experiments). During these steps, no communication occurs between different DiLoCo groups. Standard intra-replica communication (such as ICI, or intra-replica DCN if the learner itself is a multi-slice group) continues at every step as usual.
 The Outer Loop (Global): Every H steps, the M learners compute the difference (delta) between their current weights and the global weights at the start of the interval. The learners average these deltas across the network via a distributed all-reduce and apply an outer optimizer (typically SGD with Nesterov momentum) to update the global weights, which then serve as the starting point for the next inner-loop interval.

 Despite communicating significantly less frequently (by a factor of H, e.g., 1-2 orders of magnitude less) than standard synchronous training, DiLoCo has been shown to achieve comparable convergence and model quality .
 The Vanilla DiLoCo described above reduces total communication volume by a factor of H, however, all learners still transmit their weight deltas for the entire model all at once at every H-th step. On a thin network pipe, that full-model transfer creates a large periodic stall every H steps. This issue is alleviated by Streaming DiLoCo, which is described in the next section.
 Why Streaming DiLoCo Shines in Low-Bandwidth Regimes
 In multi-slice training, communication within a single slice is handled by high-speed Inter-Chip Interconnects (ICI). When scaling to multiple slices, synchronization across slices must traverse the Data Center Network (DCN) or, if the slices are geographically distributed, wide-area networks (WAN).
 Within a single datacenter, DCN bandwidth is high enough that JAX and XLA can often hide standard Data Parallel all-reduce collectives by overlapping gradient communication with backward-pass computation. Across datacenters or congested links, however, bandwidth drops and latency rises sharply. Standard DP stalls at every step waiting for global gradient synchronization, collapsing Model FLOPS Utilization (MFU).
 Streaming DiLoCo eliminates this synchronization stall by partitioning the model's parameters into P disjoint fragments . Over the course of H steps, every single fragment in the model is synchronized exactly once, achieving the exact same outer-loop cadence as vanilla DiLoCo without spiky bandwidth utilization.

 Fragmentation: MaxText partitions the model into P = N LAYERS + 1 fragments: one fragment for all non-scanned parameters (token embeddings, final layer norm, and output head) and Nlayers fragments, one for each scanned Transformer decoder layer.
 Staggered Per-Step Streaming: Instead of pausing every H steps to exchange the entire model, MaxText synchronizes a single fragment every Δh=max⁡(1,round(H/P)) steps. Setting H=P (Δh=1) synchronizes one fragment per step , spreading the exact same reduced communication volume across all H steps so the network sees a nearly uniform, tiny stream (once large embedding matrices are load-balanced across the layer fragments, as described next) rather than a massive periodic spike. Rather than synchronizing adjacent layers consecutively, the selection of which fragment syncs at each interval is interleaved across the depth of the network (e.g., Fragment 0, then Layer k, then Layer 2k, etc.). This ensures every round of synchronization touches different depths of the network rather than leaving an entire section of the model stale while another section updates.
 Embedding Load Balancing : Since Fragment 0 holds all parameters outside the scanned layers: the token embeddings, pre-logits layer norm, and unembedding/output head, its size depends on the vocabulary dimension, and it can be much larger than the other fragments. Without mitigation, the step that synchronizes Fragment 0 would produce a massive spike in network traffic compared to the other layer fragments. To this end, while some non-scanned vectors remain in Fragment 0, large matrices from this fragment are evenly split and merged with the other Nlayers fragments.

To achieve zero communication stalls, we overlap the reduce-scatter of the gradients with the backward pass, which produces them and takes tbwd time. Therefore, the peak required bandwidth is Bdp ≈ 2∣Θ∣b / tbwd.

 Here is a Sunday paper-style puzzle you can try right now. Draw a 3×3 grid. Fill every cell with either +1 or −1, subject to two rules: each row must multiply to +1, and each column must multiply to −1.
 Go ahead. We’ll wait…
 You didn’t manage it, right? There is an elegant reason for that. For a row to multiply to +1, it needs an even number of −1s. For a column to multiply to −1, it needs an odd number. Add up the rows and you learn the grid contains an even number of −1s. Add up the columns and you learn it contains an odd number. Well…That’s impossible!
 The grid would have to be two contradictory things at once. No such table exists; it is a paradox.
 Now turn the puzzle into a game: Each round, Alice is handed a row and Bob a column. Without talking, Alice fills her row by the row rule and Bob fills his column by the column rule. They win if they put the same number in the square where their row and column intersect. Any plan made in advance is just a pre-written table, meaning at best they will win 8 out of 9 rounds. This changes if they use a quantum computer. It won't fill in the impossible grid, but in principle, it lets them win every round.
 The reason is a property called quantum contextuality , arguably the strangest feature of quantum mechanics. Einstein once famously asked whether the moon is there when nobody looks, his way of insisting that physical properties ought to exist whether or not anyone measures them. For quantum systems, contextuality is the precise, experimentally testable statement that the answer can be no: you cannot assign fixed, pre-existing values to everything you might measure.
 What a measurement yields can depend on which other compatible measurements you make alongside it (i.e., on its context ). This is not only a deep philosophical statement, but more so, cutting-edge science and the basis of a new technology. And in the game above, Alice and Bob can use it to engineer a solution. Their answers are not looked up in a hidden table written in advance; the table does not exist. Their answers come into being as they measure, and quantum correlations stitch them together more tightly than any classical rulebook permits.
 Entanglement usually gets top billing as the “magic ingredient” of quantum computing. But a growing body of theory suggests contextuality is the deeper resource, the thing that actually powers certain quantum algorithms past their classical counterparts. The catch is that, until recently, contextuality had been demonstrated almost exclusively in small systems of a few particles. Whether it survives, and stays useful, in the many-body systems that real quantum computers are made of was an open question.
 That is the question we set out to answer. In " Quantum-classical separation in bounded-resource tasks arising from measurement contextuality ," published in Science , we demonstrate and measure contextuality on our superconducting quantum processors. Our qubits win the magic square game 98.3% of the time, exceed the classical limit on a contextuality test, and outperform classical strategies in tasks spanning up to 105 qubits. Along the way, these tasks proved to be a sensitive new benchmark for quantum hardware, catching subtle errors that random-circuit tests miss.

 Beating the classical bound
 We ran what is commonly called the magic square game on our Willow quantum processor. Alice and Bob each hold two qubits, sharing two entangled Bell pairs instead of a pre-written table, and measure them using preset settings for their assigned row or column to get their ±1 entries.
 The best conceivable classical strategy loses at least one round in nine, winning at most 88.89% of the time. When we played all nine versions of the game 100,000 times apiece, our qubits lost roughly one in sixty, winning 98.30% of them (0.9830 ± 0.0001).
 The gap is meaningful and statistically significant: our qubits coordinated better than any pre-written table allows. That's because no cell has a value fixed in advance. Each answer takes shape only when it is measured alongside the rest of its row or column (its context), and shared entanglement makes Alice's and Bob's answers for the shared cell agree.

 With shared entanglement and a prearranged measurement plan, Alice and Bob can in principle agree at the intersection in every round. On our hardware, noise causes about one loss in 60.

 Reinforcement learning (RL) uses rewards to train models to solve problems and complete tasks more successfully. 

 Inference drives this process. Workers generate rollouts: sequences of model outputs, actions, and environment interactions. The RL framework scores the results, updates model weights, and sends those weights back to the workers for the next round.

 As RL training scales, redundant compute work, slow rollouts, weight updates, and worker failures can waste GPU capacity and delay training. 

 NVIDIA Dynamo provides the serving layer to address these constraints, helping teams generate more accepted training samples and complete training iterations faster. 

 This blog post explains the rollout bottlenecks that slow RL training and how Dynamo addresses them through routing, ModelExpress weight updates, and recovery.

 Figure 1. The RL loop generates rollouts, assigns rewards, and updates model weights before repeating 

 1. Why RL needs distributed rollout infrastructure 

 A reasoning rollout may contain one response. A coding-agent rollout can involve repository exploration, edits, tool calls, and tests. These differences create an uneven workload across inference workers.

 Three constraints determine how effectively that workload supports training.

 Rollout completion time. When training requires a group of samples, the slowest required rollout can delay the next step. Distributing request counts evenly across GPUs does not necessarily distribute work evenly.

 Repeated context. Multiple attempts often begin with identical instructions, task descriptions, or coding repository context. Recomputing those prefixes consumes GPU capacity before new output is generated.

 Weight freshness. Training produces new model weights throughout the run. Workers must receive them according to the algorithm’s requirements for sampling and acceptable staleness.

 Addressing these constraints can let teams complete more iterations within a fixed compute budget. The right optimization depends on which constraint limits the workload.

 Figure 2. The three constraints on RL training: slow rollouts, redundant prompt processing, and timely weight updates 

 2. The Dynamo architecture for RL 

 Dynamo sits between rollout orchestration and inference workers. The RL framework submits generation requests; Dynamo routes them to eligible capacity; inference engines execute the model.

 Figure 3. Dynamo coordinates rollout serving, the RL framework controls training and ModelExpress distributes weights

 Component Role

 3. How Dynamo accelerates routing, weight distribution, and recovery 

 KV-aware routing: Reduce repeated prompt computation 

 RL often generates several solutions to the same task using a shared prompt. Sending these requests to a worker that has cached the prompt avoids repeated processing, saving GPU compute. But sending every request to that worker can create a queue, delaying rollouts and the next training step. 

 Dynamo’s router balances KV cache reuse and worker load to reduce redundant computation and waiting. The objective is earlier completion of the samples needed for training.

 ModelExpress: Reduce recurring weight-distribution overhead 

 RL training repeatedly updates the model. Sending a full checkpoint to every rollout worker takes time and can interrupt generation.

 ModelExpress reduces this overhead by reusing weights already available in the cluster instead of loading from remote storage. Compatible workers can copy weights directly from another GPU over NIXL.

 Delta weight transfer reduces the data sent between updates. Instead of moving the full model, it sends a compressed representation of what changed. Workers reconstruct the new weights from the matching base version, reducing transfer time and network traffic.

 This also helps recovery. A replacement worker can load a checkpoint and apply subsequent deltas to catch up with the training run. Healthy workers can continue generating rollouts while capacity is restored.

 Dynamo detects worker loss, directs new requests toward eligible workers and adds replacement workers to routing once ready, keeping rollout generation moving when a worker fails.
