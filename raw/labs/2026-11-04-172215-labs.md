 Per-token API prices keep falling, yet engineering bills for autonomous coding agents keep climbing. Price per million tokens isn't the metric that actually governs production economics anymore. The dominating metric is now cost per successful task: total spend across every loop iteration, tool call, retry and internal thinking pass divided by the number of tasks that pass verification.
 When an agent calls a high-thinking reasoning configuration for every micro-decision in its harness, you're paying deep-reasoning prices for questions a lightweight configuration already answers accurately. To prevent this unnecessary overhead, consider adding a lightweight routing layer that can intercept routine decisions before they ever reach an expensive reasoning model.

That is the premise behind wiring TypeSafe's Jev classifier in front of Google Antigravity's model calls. Rather than generating text token by token, Jev—a specialized structured-output classifier designed for high-throughput decision pipelines—evaluates structured classification primitives in a single forward pass: a Choice from a list, a numeric Score or a Noul, which returns a 0 to 1 probability for a binary statement.
 For full disclosure, Google has no partnership with TypeSafe, and this article is not an endorsement of TypeSafe or its products. Jev is used here as one example of a lightweight classifier, and the same routing pattern can be built with other classifiers, including Google-native ones. The Getting started with discriminative models codelab, for example, runs the same kind of classifier on DiffusionGemma, Google DeepMind's open-weights model, in your own Google Cloud project.
 We ran a 50-question, auto-graded, coding-agent benchmark against live Gemini and Jev APIs to test whether a near-free classifier can route each task to the cheapest model that still gets it right. Here's what we learned:
 1. Regex and token-length harness routers collapse on unseen agent tasks 
 The naive way to ask Jev to route a coding task is a single broad Choice question: simple or complex . When we tested that first on 16 coding-agent tasks, Jev routed nearly everything to simple , even tasks requiring an LRU cache trace or modular exponentiation. TypeSafe's documentation warns against this exact anti-pattern. If a question weighs multiple factors or requires a meta-judgment, decompose it into an atomic check.
 When we replaced the broad Choice question with one atomic Noul question, it fixed the separation immediately. The question was: does answering this require performing more than one sequential calculation, simulation step or logical deduction, rather than a single direct lookup, format check or one-step classification?

 On those initial 16 tasks, Jev routed 13 of 16 in agreement with our hand-labeled difficulty on the first run and 14 of 16 on the second pass. Many engineering teams ask whether they even need a classifier API when they can write a zero-cost regex and prompt-length heuristic in Python, matching words like sequence , modulo and race condition or escalating any prompt over 35 words.
 On the 16 development questions used to write those exact rules, the local heuristic scored 15 of 16, or 93.8%. To test whether that heuristic survived contact with realistic coding-agent traffic, we froze its code without changing a character and added 34 unseen held-out tasks across seven coding-agent buckets: fact extraction, schema validation, short classification, single-hop code checks, state simulation traces, math or logic chains and subtle language-semantics bugs.

 On the 34 held-out questions, the frozen heuristic dropped 23.2 percentage points to 70.6%. Realistic simple tasks such as extracting a port from a Kubernetes YAML manifest, a file path from a unified git diff header or a line number from a Python traceback exceeded 35 words and triggered false escalations. Conversely, concise multi-step code traces such as mutable default arguments across calls, Python dictionary key hashing on {1: "a", True: "b", 1.0: "c"} and C short-circuit evaluation lacked the heuristic's hardcoded puzzle words and were falsely routed to the simple path. Jev classified all 34 unseen tasks with 100.0% agreement, 34 of 34, reaching 48 of 50, or 96.0%, across the full suite.

 A common mistake when building a fast-path router is assuming that setting a low maxOutputTokens cap on a reasoning model will make it spend less on easy tasks. Our 50-question data shows why that assumption fails.

 Capping the model's output at 300 tokens didn't save any money on easy tasks. The cap is only a ceiling, and easy answers never came close to it. On the easy tasks, the capped version actually cost slightly more than the uncapped one. All the cap did was break 7 of the 25 hard tasks. On six of them, the model ran out of room while still reasoning and never gave an answer. On the seventh, it squeezed its reasoning to fit, finished on time and got the answer wrong.
 So a Jev router that sends easy tasks to the capped model and hard ones to normal Flash got all 50 right. It still cost slightly more than skipping the router and using normal Flash for everything, and it was slower. If your cheap option doesn't actually make the model think less on easy tasks, no router can save you money. Not even a perfect one that costs nothing.

 Salesforce AI Research doubled Agentforce memory performance by creating a framework that tracks what an AI agent remembers. 

 Imagine the following scenario: In March, a customer tells an agent that their office is in Bangalore. In June, they mention the office has moved to Pune. In July, they ask a question that depends on where they are, but the agent answers as though the office were still in Bangalore. The culprit is the agent’s memory.

 Keeping details current when a customer updates it months later is one of the harder problems in AI agent memory. Even today’s most advanced agents can miss them, because a reply built on an older fact reads exactly like a reply built on a current one. At best, this means a customer has to enter information twice. At worst, an employee asks the agent to arrange catering for tomorrow’s meeting and it books delivery to the old office. Either way, an agent’s “forgetfulness” translates to friction in the experience – with potential for real business consequences.

Salesforce AI Research built an evaluation framework that answers a question that is difficult to answer any other way: how much does an agent actually remember? Our framework generates long, multi-session conversations with specific facts planted along the way, runs them through the live Agentforce system, and then asks the agent questions that depend on those facts. Testing the entire path, from the moment a customer mentions something to the moment an agent acts on it, is what makes the result trustworthy. The conversations come from ConvoMem , a public benchmark we released in 2025.

 That framework was used to improve Agentforce Memory, the capability that keeps agents current on what customers tell them, which became generally available in September.

 The improvement came from our updated memory policy, the rules that decide what an agent keeps about a customer and what it does when that information changes. The updated policy holds on to more of what a customer says, and it treats an update as a correction to something the agent already knows rather than an additional fact filed next to the first. What’s significant about this methodology is that nothing underneath the policy changed. Agentforce Memory still runs on the architecture it launched with.

 On that evaluation, run on the live Agentforce system, the updated policy recalls 1.8 times as many of the facts customers state outright as the policy it replaced, and 2.2 times as many of the facts that change over time. The memory of the end-to-end conversation is essentially doubled in quality. 

 “An agent’s answer can’t tell you whether it failed to save something or failed to use what it saved,” said Erik Nijkamp, director of research at Salesforce AI Research. “Testing the whole path is what separates those, and once you can see which one is failing, you can improve it by changing a policy instead of rebuilding the system.”

 Doing that evaluation in production matters, because memory only behaves like memory under real conditions: months of conversation, live data, and a human waiting on the answer.

 Silvio Savarese, EVP and chief scientist at Salesforce, said: “In a research lab, you choose a problem and then go find data for it. In a product organization, the problem is already running, with customers on it, and the discipline is to measure it honestly before you change anything. That is what this work gives us, on a capability our customers depend on every day.” 

 The problem is already running, with customers on it, and the discipline is to measure it honestly before you change anything.

 One Salesforce customer, a travel platform, recently used Agentforce to create an employee-facing agent that answers team questions, summarizes cases, drafts emails, and updates CRM records. With its improved Agentforce Memory, the agent carries the context that matters into every conversation, so sales and service reps get personalized, relevant answers without starting from scratch each time.

Agent memory is becoming something enterprise businesses will hold to a standard, the way they hold any other part of their systems. Testing what an agent remembers across a full conversation is how that standard gets set.
