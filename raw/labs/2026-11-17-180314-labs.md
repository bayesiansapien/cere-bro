```text
# Qwen3.8-Flash-Next-NVFP4-QAD

This is an experimental mixed-precision QAD checkpoint of
[Qwen3.8-Flash-Next](https://huggingface.co/Qwen/Qwen3.8-Flash-Next), exported after
100 optimizer updates using NVIDIA Model Optimizer and NeMo AutoModel with FSDP2.
It contains the full multimodal model, including the frozen vision encoder,
PLE n-gram embedding, and MTP module. Weight files occupy approximately 129.7 GB
(120.8 GiB).

**This checkpoint uses a more aggressive quantization recipe than
[Qwen3.8-Flash-Next-NVFP4](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4).**
In addition to routed experts, it quantizes shared experts to NVFP4 and selected
GDN, QSA, and indexer projections to MXFP8. The repository name's `-QAD` suffix
identifies the training method; it does not mean the original NVFP4 recipe was
kept unchanged. Task accuracy gains from QAD are not statistically established.

Weight shards were consolidated for distribution. Every source file was verified
against its export SHA256, and consolidated files passed a complete readback.
Tensor names, shapes, dtypes, and stored values are unchanged.

## Quantization recipe

| Component | Stored precision | QAD treatment |
|---|---|---|
| Main LM routed experts, 48 MoE groups | NVFP4, block size 16 | Trained |
| Main LM shared experts, 144 linear matrices | NVFP4, block size 16 | Trained |
| GDN projections, 180 linear matrices | MXFP8, block size 32 | Trained |
| QSA q/k/v/o projections, 48 linear matrices | MXFP8, block size 32 | Trained |
| QSA indexer projections, 12 linear matrices | MXFP8, block size 32 | Frozen |
| PLE n-gram embedding | Per-tensor FP8 E4M3, BF16 scale | Frozen |
| MTP routed experts | FP8 E4M3, 128 x 128 block scales | Frozen |
| MTP shared experts and attention | BF16 | Frozen |
| Vision encoder, routers, gates, convolutions, output head, other excluded tensors | Original precision | Frozen |

The main model uses native NVFP4 and MXFP8 computation in the validated serving
configuration. Selected excluded operations retain their original FP32 contracts.
The KV cache was BF16 during evaluation; KV-cache quantization is not part of
this recipe. See `hf_quant_config.json`, `config.json`, and
`quantization_recipe.json` for machine-readable metadata.

The main LM was quantized from the original BF16 model. The preserved MTP and
PLE state derives from the released NVIDIA mixed-precision checkpoint. QAD did
not further quantize or train MTP. All benchmark measurements below disabled MTP.

## QAD training

The student used fake-quantized computation with floating master weights and a
frozen BF16 teacher. Training used text inputs; the vision encoder stayed frozen.

| Setting | Value |
|---|---|
| Completed optimizer updates | 100 |
| Maximum training sequence length | 16,384 tokens |
| Global batch size | 512 sequences |
| Consumed sequence examples | 51,200, including any repeated samples |
| Microbatch size | 1 sequence per rank |
| FSDP2 world size | 64 |
| Optimizer | Adam, betas (0.9, 0.95), epsilon 1e-8, weight decay 0 |
| Peak / minimum learning rate | 1e-5 / 1e-6 |
| Warmup / scheduler horizon | 50 / 500 updates; this export stops at update 100 |

16,384 is a sequence-length ceiling. It does not mean every example contained
16,384 non-padding tokens. The exact training data files are not distributed in
this repository. This is an inference checkpoint; optimizer state is not included.

Export validation compared native training-reference and exported-model
log probabilities at input lengths 256, 4,096, 8,192, and 16,384. Across 28,924
scored positions, mean absolute log-probability error was 1.21e-6, maximum error
was 1.00e-5, and top-1 agreement was 99.25%. This establishes export parity within
the tested limits, not parity with BF16 model accuracy.

## Experimental evaluation

The baseline is the original
[Qwen3.8-Flash-Next](https://huggingface.co/Qwen/Qwen3.8-Flash-Next) model in BF16.
All entries are our measurements on a 0–100 scale. Benchmark metrics and
evaluation protocols can differ from published model-card results.

Validation scope: checkpoint identity, native quantization kernels, score
coverage, and task-specific grading were checked. Historical full-run request
retry, timeout, and output-termination accounting is incomplete, particularly
for Terminal-Bench. The numbers are descriptive; unresolved limit effects
prevent a clean attribution of differences to quantization or training.

| Benchmark / metric | Original model (BF16) | QAD update 100 |
|---|---:|---:|
| GPQA-Diamond accuracy | 92.05 | 91.60 |
| IFBench instruction-following score | 79.60 | 79.93 |
| SciCode subtask success | 50.22 | 51.11 |
| AA-LCR accuracy | 77.81 | 77.13 |
| MMMU-Pro accuracy | 77.75 | 77.34 |
| Terminal-Bench 2.1 native pass@1, qualified | 85.96 | 85.96 |

SciCode reports mean subtask success over eight operational runs per model,
with 338 scored subtasks per run (2,704 per model). Repeats used the same configured
request seed and are not independently reseeded trials. A confidence interval
against BF16 is not reported here. SciCode subtask success must not be compared
with published main-problem scores.

Terminal-Bench retains all 712 outcomes per model, including protocol-defined
runtime failures scored as zero: 6/712 for BF16 and 4/712 for QAD. Both models
scored 612/712. The exploratory task-cluster bootstrap 95% interval for QAD minus
BF16 is [-2.95, +3.23] percentage points. Historical allocation-wide timeout/retry
and output-cap rates remain unknown; later two-task logging diagnostics do not
retroactively fill those gaps.

These measurements do not establish an overall task-accuracy improvement over
the BF16 baseline.

## Serving

Validated hardware was NVIDIA GB300, using native Blackwell kernels, vLLM 0.30.0,
four-way tensor parallelism, and expert parallelism. This recipe additionally
needs the compatibility helpers in [`serving/`](serving/README.md): narrow
MXFP8 output padding/cropping and the canonical sparse-indexer policy used for
training/export validation. The helpers check the ModelOpt runtime source hash
and refuse an unvalidated build.

Follow [`serving/README.md`](serving/README.md) for the tested settings and
compatibility requirements. Generic `transformers.from_pretrained()` loading
and arbitrary vLLM versions have not been validated for this mixed format.
The model configuration preserves the base model's context settings; QAD export
parity was checked through 16K, and task-serving configurations used up to 262,144.
This release does not establish accuracy at the base model's maximum context.

MTP is preserved for completeness. MTP-enabled accuracy, acceptance rates, and
performance were not validated for this QAD checkpoint. With standard exact
speculative rejection sampling, draft quantization primarily changes acceptance
and speed; approximate verification can change the output distribution.

## Architecture and intended use

The upstream model combines a vision encoder, Gated DeltaNet, Qwen Sparse
Attention, MoE layers, gated residual streams, and n-gram embeddings. Inputs may
contain text, images, or video, and outputs are text. Refer to the
[base model card](https://huggingface.co/Qwen/Qwen3.8-Flash-Next) for its
architecture, training information, intended uses, and limitations. This release
is intended for quantization and QAD research and deployment validation.
```

### [IBM Research] How low-SWaP radar is making sophisticated sensing smarter
- url: https://research.ibm.com/blog/how-low-sWaP-radar-is-making-sensing-smarter?utm_medium=rss&utm_source=rss
- published: 2026-11-17T12:00:00+00:00
- via: feed

```text
Radar systems have traditionally faced a straightforward engineering tradeoff: Better performance requires more hardware, more power, and more money. But emerging applications including drones, autonomous vehicles, and distributed sensing networks require capable radar on platforms where space, weight, battery power, and computing resources are limited. These needs are driving researchers at HRL Laboratories, an IBM company, to rethink how radar systems are designed.

 Enter low-SWaP radar. SWaP stands for size, weight, and power, although cost is increasingly treated as a central constraint. The goal of low-SWaP radar, beyond making a system smaller, is to preserve as much of its useful capability as possible while shrinking the hardware, reducing its energy demands, and dramatically lowering its cost. For HRL lab leader Seong-Hwoon Kim and his colleagues, the target is radar systems costing in the tens of thousands of dollars range rather than hundreds of thousands or even millions. “For this industry, that cost difference is a paradigm shift,” he said.

 Achieving that goal means rethinking radar as an integrated system, including the semiconductor devices producing and receiving radio-frequency signals as well as the algorithms interpreting those signals in real time.

 What does a radar actually measure?

 The word “radar” is an acronym for radio detection and ranging. At its simplest, radar works by transmitting radio-frequency (RF) signals and examining what comes back after those signals encounter objects in the environment and return to a sensing antenna. Based on how the returning pulse’s phase and amplitude differ from what was transmitted, information about nearby objects can be interpreted. The Doppler shift of a returning pulse describes how its wavelength is stretched or compressed based on whether an object of interest is moving farther or closer from the radar source. This information contributes to the overall picture provided by radar equipment.

 Unlike a camera, a radar sensor doesn't produce an immediately recognizable picture. Instead, engineers design a radar system's operating mode and its waveform, determining how its RF signal is conditioned and transmitted so that useful information — like how far away an object is and how fast it is moving — can be extracted when the signal bounces back to the source. A radar mode is a particular way of operating the radar, with its waveform and other parameters configured for a specific sensing task. Frequency and modulation can be selected for a particular application, but the radar's hardware must also be capable of supporting that mode. Designing increasingly specialized hardware around increasingly sophisticated modes is one reason high-performance radar systems can become so expensive.

 Kim’s team approaches that problem through co-design, considering the waveform, hardware, and signal-processing software together rather than treating each as a separate engineering problem.

 “I’m a strong believer that software and algorithms will make excellent sensors even smarter,” he said. “But if you can make the excellent sensor a little bit smarter, then work on the hardware in conjunction with the software, now you've got something that will really work.”

 Getting more from commercial hardware

 One of the keys to lowering radar’s cost is avoiding custom hardware when existing components can do much of the job. Commercial off-the-shelf, or COTS, electronics offer enormous economies of scale. But components designed for mass markets don’t necessarily support everything a specialized radar requires, according to Kim.

 He described his team’s approach as “customized off the shelf.” Instead of developing every component from scratch, researchers can start with comparatively inexpensive commercial components, modify them where necessary, and add surrounding electronics or software to give them capabilities their original designers hadn’t anticipated.

 The important point is to avoid customizing away the economic advantage.

 “If you buy a $50 chip, you don’t want to make that chip cost you $5,000,” Kim said. “You want to just add some more capability to it,” while keeping it close to that original cost category.

 That philosophy extends throughout low-SWaP design: Spend resources where they materially improve performance, rather than optimizing every component to its theoretical limit.

 Bringing intelligence to the edge

 Radar’s SWaP problem doesn’t end with the RF hardware. The sensor also needs enough computing power to turn the signals it receives into useful information, increasingly in real time.

 A basic radar data product is a range-Doppler map. One dimension contains information about an object’s range from the sensor, while another captures its relative motion via the Doppler effect. The result can help determine where something is and how quickly it is moving relative to the radar. But interpreting a range-Doppler map is very different from picking out a recognizable object in a photograph. A stronger signal isn’t necessarily a more important signal. Useful information may emerge from patterns across the data.

 Kim and his colleagues are exploring how machine learning can act as a first-line filter for that information directly at the edge. Depending on the scene, Kim estimates that 80% to 90% of radar data may ultimately be irrelevant to the higher-level task. If an efficient machine-learning model can identify the potentially useful portion earlier, the rest of the computing system has much less information to process.

 The approach isn’t about putting the largest possible AI model onto a radar. Rather, it’s the opposite: finding efficient algorithms running on efficient hardware that can perform a tightly defined task within severe power and computing constraints.

 Co-designing AI with radar

 Applying AI to radar creates another challenge: Radar data is highly specialized.

 A machine-learning researcher working with photographs knows intuitively what an image of a face, vehicle, or building represents. It’s easy to annotate data for model training in that case. A radar return, on the other hand, is an electrical representation of the environment. Understanding it requires knowing something about how the waveform was generated, how the radar operates, and how the returning signal was processed.

 Kim’s team therefore wants machine-learning researchers to understand radar waveform and mode design while radar engineers understand what the algorithms need from the hardware. That creates a feedback loop in which algorithm requirements can influence hardware design and knowledge of the sensor can influence how machine learning systems interpret its output.

 That loop could become an important source of innovation, according to Kim. Rather than simply giving an AI system a collection of labeled radar data and asking it to discover patterns, researchers can incorporate knowledge of how those measurements were created in the first place. The aim is both better results and systems that can be deployed more quickly.
Building efficiency into the RF hardware

 Ultimately, low-SWaP radar is constrained by physics. A sensor on a battery-powered platform like a self-driving car or a drone has a finite energy budget, meaning improvements in software can’t compensate indefinitely for inefficient electronics. That makes semiconductor technology another important part of the equation. Expertise in designing and fabricating efficient RF devices is one way to make the necessary tradeoffs closer to the fundamental hardware level rather than adding more hardware around an inefficient component, said Kim.

 One important technology is gallium nitride, or GaN, a semiconductor used in radar and other high-performance RF systems. Kim and his colleagues work on GaN devices and fabrication, and their foundry also makes the technology available to other organizations in the U.S. defense industrial base.

 That semiconductor expertise complements the broader low-SWaP philosophy: Optimize the technology stack as a system, including the underlying devices as well as RF components, signal processing, and software.

 What’s next for low-SWaP radar?

 The next step may be pushing the same approach into still higher frequencies.

 Kim’s team is investigating high-millimeter-wave devices, an area with relevance beyond radar to emerging communications technologies such as 5G and 6G. HRL researchers are now examining how technologies developed in that frequency range could support a new generation of low-cost, high-millimeter-wave radars.

 Ultimately, low-SWaP radar is less about miniaturizing a conventional radar than it is about deciding what capability actually needs to live inside the sensor and designing the entire system accordingly. That could make sophisticated sensing practical on platforms where the cost, weight, or energy demands of conventional systems have made it difficult before.

 And increasingly, the determining factor won’t be any one breakthrough component. It will be how effectively the hardware, RF electronics, sensing modes, and intelligent software are designed to work together.
```
