 Announcing SOCI-indexed images for faster SageMaker AI jobs

 Every minute your deep learning container image spends downloading is a minute you pay for and a minute your team waits. Container image download is pure overhead: billable job time that produces no model progress. For modern deep learning images, that overhead is several minutes on every single job. Today, we’re excited to announce Seekable OCI (SOCI) indexing for Amazon SageMaker AI Training and Amazon SageMaker AI processing jobs , which takes full container image download off the critical path of every job.

 With SOCI indexing, SageMaker AI lazy-loads your container image. It fetches only the files needed to start the container and streams the rest in the background as your code runs, so your job begins in seconds instead of minutes. You adopt it by pointing to a pre-indexed AWS Deep Learning Container (DLC) or adding an index to your own image. Neither approach requires changes to your job definition, entry point, or data channels. The result is faster job starts, lower job cost, and more time spent building models rather than waiting on infrastructure.

 SOCI-indexed images start Amazon SageMaker AI training containers in seconds, with no impact on training performance. As we show in the What we measured section, this reduced GPU idle time during image pulls by up to 90 percent in our benchmarks.

 This post shows how to adopt SOCI indexing: what it is, the results we measured, and how to turn it on for your own jobs.

 The challenge

 SageMaker AI training and processing jobs run inside container images stored in Amazon Elastic Container Registry (Amazon ECR). Before a job can execute your code, the service downloads the entire image to the instance. It decompresses and writes every layer to disk.

 For small images this takes seconds. But deep learning images routinely exceed 10 GB or more. That download adds minutes to every job, and you pay for it as job time. The impact is largest exactly where iteration speed matters most: hyperparameter tuning sweeps for hundreds of jobs, quick experiments, and short processing jobs, where image download can dominate total runtime.

 How SOCI indexing works

 Seekable OCI (SOCI) is an open source technology that lazy loads container images. Instead of downloading the whole image before starting, the runtime uses a SOCI index to fetch only the files needed to launch the container immediately. It then streams the rest in the background as your code accesses it.

 A SOCI index is metadata that maps every file inside your image. You store it in Amazon ECR as an OCI-compliant artifact linked to your original image. Because the index is a separate artifact, your image digest and any existing signatures remain valid.

 SageMaker AI checks for an index automatically

 When you create a training or processing job, SageMaker AI checks whether the image you specified has a SOCI index and behaves accordingly:

 Scenario 
 What happens 

 The image includes a SOCI index 
 SageMaker AI lazy-loads the image and starts your container before the full download completes 

 The image has no SOCI index 
 Standard download, no change in behavior 

 The index can’t be read, or lazy loading doesn’t succeed 
 The job falls back to a standard download and continues running 

 Because jobs always fall back to a standard download when needed, adding a SOCI index never prevents your job from running. You only gain faster startup. You never risk breaking an existing workflow.

 Getting started

 You can adopt SOCI indexing two ways: use a pre-indexed AWS Deep Learning Container or create an index for your own custom image.

 Option 1: Use a pre-indexed AWS Deep Learning Container

 AWS publishes SOCI-indexed variants of several popular Deep Learning Containers, identified by the -soci suffix on the image tag:

 763104351884.dkr.ecr.us-east-1.amazonaws.com/pytorch-training:2.9-gpu-py312-cu130-ubuntu22.04-sagemaker-v1-soci 

 Pre-indexed variants are available for PyTorch Training, TensorFlow Training, vLLM, and SGLang, including arm64 variants for some frameworks. To adopt lazy loading, update the image tag in your job definition to the -soci variant. Browse the full list in the AWS Deep Learning Containers Gallery .

 Note: If you build your own image FROM a DLC base image, you must create a SOCI index for your final image. The index from the base image does not carry forward to derived images.

 Option 2: Create a SOCI index for your own image

 To index a custom image, you need a Linux host (such as an Amazon Elastic Compute Cloud (Amazon EC2) instance running Amazon Linux 2023) with containerd , the SOCI snapshotter , and either Finch or nerdctl installed.

 Set your environment variables . 

 ACCOUNT_ID="111122223333"
REGION="us-east-1"
REPOSITORY_NAME="my-training-image"
ORIGINAL_IMAGE_TAG="v1.0"
SOCI_IMAGE_TAG="v1.0-soci"
REGISTRY="$ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com" 

 Install the required tools . 

 sudo dnf install -y containerd fuse soci-snapshotter runfinch-finch
sudo systemctl start soci-snapshotter
sudo systemctl restart containerd 

 Authenticate to Amazon ECR . 

 aws ecr get-login-password --region "$REGION" \
 | sudo nerdctl login -u AWS --password-stdin "$REGISTRY" 

 Pull your original image . 

 sudo nerdctl pull "$REGISTRY/$REPOSITORY_NAME:$ORIGINAL_IMA

# LFM3-Audio-2B-GGUF

GGUF version of [LFM3-Audio-2B](https://huggingface.co/LiquidAI/LFM3-Audio-2B) for local inference on CPUs and GPUs.

LFM3-Audio-2B is a compact audio model that runs locally on laptops and edge devices. It takes text or audio as input and responds with text, speech, or both.

Find architecture and usage details in the [original model card](https://huggingface.co/LiquidAI/LFM3-Audio-2B).

## Use with llama.cpp
<hr style="margin: -0.7em 0 1.2em 0; border: 0; border-top: 1px solid rgba(127, 127, 127, 0.3);" />

> [!WARNING]
> Support for LFM3-Audio and LFM3-Omni in [llama.cpp](https://github.com/ggml-org/llama.cpp) is pending the merge of [ggml-org/llama.cpp#31257](https://github.com/ggml-org/llama.cpp/pull/31257). Until it is merged and released, build llama.cpp from that pull request.

> [!NOTE]
> Support for the `/v1/realtime` API (real-time voice conversations over WebSocket) in `llama-server` is coming soon.

Add a quantization tag to pick a file. With `-hf`, llama.cpp also downloads the audio projector.

Speech recognition: use the system prompt `Perform ASR in <language>.`, or `Perform ASR.` to let the model infer the language.

'''bash
llama-mtmd-cli -hf LiquidAI/LFM3-Audio-2B-GGUF:Q4_K_M \
  --audio speech.wav -sys "Perform ASR in English." -p "<__media__>" --temp 0
'''

Speech synthesis: `--tts-lang` takes a language code (default `en`) and `--tts-voice` is `female` (default) or `male`. The audio sampling parameters of the original model card are stored in the GGUF.

'''bash
llama-tts -m LFM3-Audio-2B-Q4_K_M.gguf -mm mmproj-LFM3-Audio-2B-Q8_0.gguf \
  -p "Hello world" --tts-voice male -o out.wav
'''

More options in the [llama.cpp guide](https://docs.liquid.ai/deployment/on-device/llama-cpp).

# LFM3-Audio-2B-MLX-4bit

4-bit MLX version of [LFM3-Audio-2B](https://huggingface.co/LiquidAI/LFM3-Audio-2B) for Apple Silicon. The weights take 1.58 GB, plus 0.15 GB for the audio codec in `audio_tokenizer/`.

The language backbone uses 4-bit affine quantization with groups of 64, except for the token embedding (also the output layer) and the value and feed-forward down projections in the layers that llama.cpp's Q4_K_M upgrades, which use 6 bits. The audio encoder, audio projector, depth decoder and codebook embedding stay in BF16. The audio codec is the original one. It is the smallest variant and loses some accuracy, so [8-bit](https://huggingface.co/LiquidAI/LFM3-Audio-2B-MLX-8bit) is the recommended trade-off.

Find architecture and usage details in the [original model card](https://huggingface.co/LiquidAI/LFM3-Audio-2B).

# Text to speech
python -m mlx_vlm.generate --model LiquidAI/LFM3-Audio-2B-MLX-4bit \

# d1-2B-MLX-4bit

4-bit MLX version of [d1-2B](https://huggingface.co/LiquidAI/d1-2B) for Apple Silicon. The weights take 1.35 GB.

d1-2B is a decision model for text, pictures, and video. It answers named, typed questions over a state with calibrated probabilities in one forward pass, without generating tokens.

The language model uses 4-bit affine quantization with groups of 64. The vision tower, projector and norms stay in FP16. Against the original checkpoint run in float32, it changed 3 of 52 test answers and moved probabilities by up to 0.25. Prefer [FP16](https://huggingface.co/LiquidAI/d1-2B-MLX-fp16) or [8-bit](https://huggingface.co/LiquidAI/d1-2B-MLX-8bit) where calibration matters.

Find architecture and usage details in the [original model card](https://huggingface.co/LiquidAI/d1-2B).

## Use with MLX-VLM
<hr style="margin: -0.7em 0 1.2em 0; border: 0; border-top: 1px solid rgba(127, 127, 127, 0.3);" />

Support for d1 in [MLX-VLM](https://github.com/Blaizzy/mlx-vlm) is in progress. We will update this card when an MLX-VLM release supports it.

'''python
from mlx_vlm import load
from mlx_vlm.utils import load_image

model, processor = load("LiquidAI/d1-2B-MLX-4bit")

# Text: several named questions over one state, answered in one pass
ticket = "I was charged twice and my parcel never arrived. Please refund one charge."
out = model.system_one(ticket, {
    "refund": {"type": "noul", "instructions": "Is the customer asking for a refund?"},
    "team": {"type": "choice", "instructions": "Which team should handle this?",
             "criteria": {"billing": "Charges, refunds, invoices",
                          "shipping": "Delivery and parcels",
                          "technical": "App or site faults"}},
    "topics": {"type": "choice", "multiple": True,
               "instructions": "Which topics does the message raise?",
               "criteria": {"billing": "Payments and charges",
                            "delivery": "Shipping and parcels",
                            "login": "Signing in to the account"}},
    "urgency": {"type": "score", "instructions": "How urgent is this ticket?",
                "criteria": ["low", "medium", "high"]},
})
a = out["answers"]
print(round(a["refund"]["noul"], 2), a["team"]["choice"], a["topics"]["choices"],
      a["urgency"]["legend"][str(int(a["urgency"]["score"]))])
# 1.0 billing ['billing', 'delivery'] medium
print(out["usage"])
# {'input_tokens': 189, 'output_tokens': 0}

# Picture: the photo is the whole state
image = load_image("http://images.cocodataset.org/val2017/000000039769.jpg")
out = model.system_one(None, {
    "cats": {"type": "number", "instructions": "How many cats are there?", "range": [0, 10], "step": 1},
    "remote": {"type": "box", "instructions": "Where is the remote control on the left?"},
}, media=[image])
a = out["answers"]
print(a["cats"]["number"], {k: round(v, 2) for k, v in a["remote"]["box"].items()})
# 2.0 {'top': 0.16, 'bottom': 0.24, 'left': 0.06, 'right': 0.28}

## Use with ONNX Runtime
<hr style="margin: -0.7em 0 1.2em 0; border: 0; border-top: 1px solid rgba(127, 127, 127, 0.3);" />

The vision encoder maps each image, or each temporal patch of a video, to projected features, and the audio encoder maps the log-mel features of 16 kHz audio to audio features. The decoder answers a state and up to 16 questions, written or spoken, packed into one row without padding, in a single forward pass with no cache. It takes `input_ids`, `attention_mask`, `position_ids`, the features at the `<|image|>`, `<|video|>` and `<|audio|>` placeholders (`image_features`, `video_features`, `audio_features`), `question_ids` (-1 on the state, k on question k) and the flat positions of the answer slots (`slot_positions`). It returns `logits` at the answer slots and the final-norm `hidden_states`.

The checkpoint's Python code in this repository builds the rows and turns these outputs into typed answers. For audio, image and video preprocessing, use the values in `processor_config.json`.

On GPU, use fp16, q4f16 or q8f16. The CUDA execution provider has no fp32 GroupQueryAttention kernel, so the other graphs run the sliding-window layers on the CPU.

In the browser, use `import * as ort from 'onnxruntime-web/webgpu'`: the default `onnxruntime-web` import cannot run these graphs. On WebGPU, pair `decoder_q4f16` with the float32 side graphs of the q4 bundle (`vision_encoder_q8`, `audio_encoder`), and keep each packed row under about 8,000 tokens for q4.

d1-Omni-2B reads its answers from a single forward pass, so there are no sampling parameters to set. More options in the [ONNX guide](https://docs.liquid.ai/deployment/on-device/onnx).

# d1-Omni-2B-MLX-8bit

8-bit MLX version of [d1-Omni-2B](https://huggingface.co/LiquidAI/d1-Omni-2B) for Apple Silicon. The weights take 2.71 GB.

d1-Omni-2B is a decision model for text, pictures, video, and audio. It answers named, typed questions over a state with calibrated probabilities in one forward pass, without generating tokens. Questions can be written or spoken.

The language model uses 8-bit affine quantization with groups of 64. The vision tower, audio encoder, projectors and norms stay in FP16. Against the original checkpoint run in float32, it kept all 59 test answers and moved probabilities by at most 0.008.

 Introduction: From Blueprint to Working Prototype 
 Imagine ordering your weekly groceries as naturally as texting a friend: "Hey, we're out of milk and eggs. Can you also add some snacks for Friday movie night?" 
 In our previous post, Building Conversational Commerce with Multi-Agent Swarms on GCP , we shared the architectural blueprint for conversational commerce—proposing a 3-layer decoupled design (Ingress, Memory, and Cognition) to solve messaging timeouts, state tracking, and response reliability.
 While blueprints establish the architecture on paper, production readiness demands working software. In this post, we take that blueprint and bring it to life with a functional prototype called HappyDelivery .
 Using LangGraph , Gemini , FastAPI , and Google Cloud , we'll walk through the code, the state machine, deterministic financial tools, and an automated verification suite that demonstrates how this multi-agent swarm operates in practice.
 1. The Prototype Stack: 3 Layers, 3 Diagrams 
 To build a reliable commerce swarm, we implemented three decoupled layers that handle the journey of every customer text message:

 Let's examine how each layer functions in code with its own dedicated architecture.

 Layer 1: Ingress Layer (Omni-Channel Webhook Gateway on GKE/Cloud Run + Cloud Pub/Sub) 
 A frequent question when designing conversational commerce is: how does a message sent by a customer on their smartphone actually land in Layer 1, and can this architecture support messaging platforms beyond WhatsApp? 
 How Client Devices Connect to Layer 1 
 End users do not communicate directly with your Google Cloud servers. Instead, customer messages traverse an operator ecosystem before landing on your webhook:

 Supporting Multiple Messaging Channels: WhatsApp, RCS, Apple Messages, and SMS 
 Every major consumer messaging platform operates on the exact same fundamental contract: an asynchronous HTTPS POST webhook delivery with a strict HTTP acknowledgement timeout :
 WhatsApp (Meta Cloud API) : Requires a prompt HTTP 200 OK acknowledgement and validating the X-Hub-Signature-256 header against your Meta App Secret using HMAC-SHA256. If your server times out or returns a non-200 status, Meta marks delivery as failed and initiates exponential backoff retries (for up to 7 days), which can trigger duplicate order deliveries.
 Google RCS Business Messaging (RBM) : Delivered via Google Cloud Pub/Sub push or HTTPS webhooks authenticated via OAuth2 / Service Account JWT bearer tokens or payload HMAC signature verification ( X-Goog-Signature ). Requires returning HTTP 200 promptly to avoid webhook delivery retries.
 Apple Messages for Business (AMB) : Delivered through an Apple-approved Messaging Service Provider (MSP). Authenticated via provider webhook signatures, JSON Web Signatures (JWS), or Mutual TLS (mTLS) with prompt HTTP 200 OK acknowledgement expectations.
 SMS / MMS ( Twilio , Sinch , Infobip ): Standard form-encoded or JSON POST webhooks signed with vendor-specific HMAC tokens (e.g., X-Twilio-Signature ).
 While the payload schemas and cryptographic headers differ slightly between platforms, Layer 1 abstracts away all client differences :

 Layer 2: Session & Cart Layer (Cloud Memorystore Redis) 
 Messaging platforms are completely stateless: every text message arrives as an isolated webhook event. To provide a coherent shopping experience, the system must instantly reconstruct the customer's full context without having to re-read or re-parse days of chat logs on every turn.
 We use Cloud Memorystore (Redis) keyed by the customer's verified phone number (session:{phone_number}) to store active state:

 Real-World Customer Journeys (CUJs) Powered by this Layer 

 The Asynchronous Shopping Trip (Pause & Resume): In real life, people don't complete an order in one sitting. A customer might text at 9:00 AM: "Add a gallon of milk to my cart" , close WhatsApp to catch a train, and reply at 2:00 PM: "Also add bread and eggs, and what's my total?" Because session state is cached in Redis, the system instantly restores their active cart ([Milk]) and recalculates totals without losing a beat.
 Contextual Guardrails (Dietary Preferences & Addresses): If a user's profile specifies dietary_preferences: ["Nut-Free"] , the Inventory Agent automatically respects that preference when recommending movie night snacks—without the user having to re-declare their allergy in every text message.
 Safe, Tokenized Checkout: The customer profile holds tokenized payment references ( customer_id: "cust_9821", payment_ref: "Visa ending in 4242" ). The LLM only ever reads the friendly masked label, while the transaction tools pass the tokenized customer ID to Stripe. Raw credit card numbers never touch chat prompts or logs.
 💡 Scale & Performance: What QPS Can the Base Infrastructure Handle? 
 A common question in conversational commerce is whether state lookups will introduce latency. Here is what the baseline infrastructure supports:
 Raw Throughput: A single, baseline Google Cloud Memorystore for Redis instance (Basic Tier, 1–5 GB memory) easily delivers 10,000 to 50,000+ QPS with sub-millisecond (< 1ms) read/write latencies.
 Conversational QPS: Each chat turn requires 2–3 Redis operations (session fetch, cart mutation, state commit). This means a single standard Redis instance comfortably handles 3,000 to 15,000 active conversational turns per second before needing Redis Cluster horizontal sharding or read replicas.
 Memory Capacity: An active session payload (profile + active cart + preferences) takes ~2 KB to 5 KB of serialized JSON. A modest 5 GB Redis instance can hold over 1,000,000 concurrent active shopping carts in memory simultaneously.
 Key Takeaway: In practice, the Session & Cart Layer will never be the bottleneck —it easily outpaces upstream webhook inference and downstream LLM inference.

 Layer 3: Agent Swarm Layer (Multi-Agent Orchestration with Gemini) 
 Rather than relying on a single monolithic prompt to handle every task, we separate reasoning into a swarm of specialized agents:

 Supervisor (Gemini Flash): Acts as a low-latency router, classifying the customer's request and delegating it to the right specialist.
 Profile Specialist: Retrieves personal preferences and issues secure single-use auth links for new buyers.
 Inventory Specialist (Gemini Pro): Bound to warehouse tools; queries stock, recommends pairing items, and mutates the cart.
 Transaction Specialist (Gemini Pro): Bound to payment tools; calculates totals deterministically and initiates charges.

 Ali Behrouz, Staff Research Scientist, and Vahab Mirrokni, VP and Google Fellow, Google Research

 We introduce a sleep phase in continual learning, enabling large language models to continuously integrate new facts and enhance reasoning while mitigating catastrophic forgetting or static knowledge cutoffs.

 Modern LLMs achieve impressive performance via pre-training and in-context learning (ICL). However, once deployed, they remain largely static, operating with a fixed knowledge cutoff date that leaves them unable to acquire long-term capabilities or adapt to new information.
 While updating models with new data seems like the obvious solution, continual parameter updates often trigger catastrophic forgetting , a fundamental issue where learning new tasks severely degrades performance on previously learned ones. Alternatively, relying strictly on ICL limits knowledge retention to the immediate context window: once the context session ends, the acquired short-term information is forgotten.
 Inspired by how the human brain processes and stabilizes memory during rest, we introduce a sleep framework in continual learning: a learning paradigm that equips large language models (LLMs) with a continuous periodic lifecycle, enabling them to continually learn, consolidate fragile short-term context into stable long-term parameters. With this framework, we demonstrate that alternating between active interaction and offline memory consolidation allows LLMs to continuously acquire new facts, retain long-context knowledge up to 10M tokens, and improve complex reasoning.

 Rethinking machine learning: Active (wake) vs. sleep phases
 Traditional machine learning relies on a strict separation between training and inference. In a continual learning framework, this distinction becomes artificial; an intelligent agent must constantly learn, adapt, and process information.
 Under the sleep paradigm, an LLM operates across two primary states:
 Active (wake) phase : The model actively receives, processes, and interacts with inputs, storing temporary information in fast, short-term memory components.
 Sleep phase : The model pauses processing new inputs and redirects its internal computations toward memory consolidation and self-improvement.
 While terms like "sleep," "dreaming," and "self-improvement" borrow from neuroscience, our framework operates entirely within a fixed model architecture and human-defined training rules. During the offline sleep phase, the model unlocks pre-allocated Mixture-of-Experts (MoE) memory blocks and updates its numerical weights using self-generated practice examples. This automated post-training cycle helps a deployed model absorb new facts and sharpen its reasoning accuracy while keeping its core codebase and design unchanged.

 Key components of the sleep process
 The sleep paradigm addresses catastrophic forgetting and continuous adaptation through two stages: memory consolidation and dreaming.
 1. Memory consolidation
 In the human brain, non-rapid eye movement (NREM) slow-wave sleep consolidates fragile memories into long-term structures via abstraction and distillation. Our proposed sleep framework mirrors this natural phenomenon through two key technical mechanisms:
 Parameter expansion & continuum memory hierarchy: To prevent catastrophic forgetting, the model dynamically scales its capacity during sleep. Using a Mixture of Experts (MoE) and Hope architecture , newly unlocked, low-rank experts are integrated into stable, lower-frequency memory blocks to store incoming knowledge without disrupting older parameters.
 Knowledge seeding (upward distillation): Fragile short-term memories stored in high-frequency layers (e.g., in-context memory) are transferred into the newly expanded long-term parameters. This is achieved through Generalized Knowledge Distillation (GKD) combined with reinforcement learning (RL)-based imitation learning : On-policy distillation: The expanded student model learns token-specific feedback from teacher distributions generated on self-sampled sequences.
 Learning to imitate (LTI): The student model is rewarded based on semantic and absolute similarity ( Levenshtein distance ) when completing prefixes of teacher-generated text.

 Synaptic pruning: Once the memory consolidation into lower-frequency modules is complete, the high-frequency temporary parameters are reset, freeing up capacity for future active sessions.

 Overview of our sleep framework: Input streams from the active phase are stored in short-term memory before entering the sleep cycle, which bifurcates into Consolidation (transferring fragile short-term tokens into expanded long-term parametric memory using low-rank structures and MoE) and Dreaming (autonomous self-improvement via synthetic routing with random experts and RL refinement). 

 2. Dreaming for self-improvement
 During REM sleep , the human brain actively simulates scenarios, consolidates emotional/semantic connections, and explores novel neural pathways. Mirroring this, during the “dreaming stage”, the sleep framework implements an autonomous self-improvement loop:
 Random expert selection: During synthetic data generation, the MoE router randomly activates non-standard experts. This forces the model to mix disparate domains of knowledge and uncover latent patterns.
 Curated rehearsal: The model generates synthetic training samples ("dreams") and filters them using gradient-based data selection to prioritize samples with the highest potential to boost overall model capability.
 RL refinement: The model performs supervised fine-tuning on top-rated dream samples and evaluates whether the generation improves performance on downstream tasks.

 Theoretical foundations
 Beyond the empirical results, our sleep paradigm is grounded in a theory that clarifies why its two stages (memory consolidation and dreaming) can support continual learning without simply trading new knowledge for old capabilities.
 For memory consolidation, the analysis shows that knowledge seeding can be understood as a structured, low-rank compression problem. The model is not asked to copy every detail of its short-term traces into its parameters. Instead, it identifies a compact set of directions that best preserve both the model’s own on-policy behavior and the semantic qualities rewarded by the learning objective.
 This perspective explains the complementary roles of the two signals: on-policy distillation aligns consolidation with the trajectories the model will actually produce at inference time, reducing the mismatch that can arise when training only on teacher-generated distributions; meanwhile, the semantic reward changes what is worth retaining, prioritizing directions that preserve meaning and task-relevant behavior rather than merely matching token probabilities. Parameter expansion then provides the capacity needed to write these selected memories without overwriting previously consolidated knowledge.
 For dreaming, the theory characterizes random expert activation and reward-based sample selection as mechanisms for improving the geometry of learning. Injecting different MoEs broadens the set of gradient directions explored during synthetic generation, exposing the model to a richer collection of updates than those induced by its ordinary wake-time data alone. Gradient-based filtering then emphasizes the synthetic experiences that carry the most useful learning signal, strengthening informative directions while preserving the structure of the underlying gradient space.
 Together, these steps yield a more balanced optimization landscape: learning is less dominated by a small number of directions, gradients are better conditioned, and the model can make more stable progress when refining its capabilities. In this view, dreaming is not simply self-generated data augmentation; it is a deliberate process for diversifying, selecting, and consolidating the updates through which the model improves itself.

By Sai Nagabhairava , Hannes Roth , Na Chen , Peter Prelich , Jonathan Bergeron 

 This latest deep dive into Meta’s Privacy Aware Infrastructure (PAI) takes a look at PrivacyLib.  

 A privacy requirement must hold as data moves through Meta’s diverse data and processing systems. Historically, supporting a new requirement meant implementing the same enforcement logic separately in each system. PrivacyLib replaces this with a common library that runs inside the clients of Meta’s data and processing systems. 

 A system integrates with PrivacyLib once, and new privacy capabilities plug in as modules that reuse that integration. PrivacyLib performs billions of checks every second, and changes are simulated and rolled out per module.  

 For internal AI agents, whose data access paths may not be known in advance, tool calls on supported paths carry agent context to PrivacyLib. The propagated context links each access to its session, so modules can observe data use and block operations that are not allowed. 

 At Meta, many privacy requirements ultimately come down to the same question: Can we prove that a piece of data goes only where it is allowed? At Meta’s scale, rather than relying solely on manual privacy audits, which can go out of sync as systems change, we have developed Privacy Aware Infrastructure (PAI) to answer this question within the infrastructure itself. PAI offers efficient and reliable first-class privacy constructs embedded in Meta’s infrastructure so that products can keep evolving quickly. 

 In previous posts, we have covered how data understanding , data lineage , and Policy Zones (our information flow control technology) play a role in PAI. Now, we are diving deep into PrivacyLib , a common library that runs inside the clients of hundreds of our data and processing systems at the point of data access. 

 PrivacyLib plays an important role in the final stage of the broader PAI workflow: continuously enforcing and monitoring data flows. 

 This blog post focuses on PrivacyLib’s role in the final stage of the PAI workflow. 
 Before PrivacyLib, we integrated privacy enforcement separately into the clients of each data and processing system for each requirement. With this approach, implementing a new requirement across systems could take months. Each new requirement, whether purpose limitation or data flow discovery, needed the same set of capabilities: covering a wide range of systems; deploying in weeks rather than months; running on every data access without becoming a latency problem; and rolling out enforcement changes without taking the fleet down. Over time, this approach became harder to scale as requirements and systems evolved. 

 PrivacyLib separates system integration from requirement implementation. We integrate each system once. When a requirement can be met at the point of data access, we implement it as a PrivacyLib module shared across the systems already integrated, so a new requirement no longer needs a separate implementation in each system.  

 There are two kinds of modules:  

 Enforcing modules can block a data access. For example, Policy Zones enforces purpose limitation . 

 Observing modules only record a data access. For example, Privacy Probes collects the runtime signals used to discover data flows.  

 As internal AI agents became a new way of accessing data, we also added the Agent Observability module to observe agent-related data access events and help safeguard the data that agents can reach. Systems already integrated with PrivacyLib picked it up without new integration work, which is what integrating once buys: each new privacy capability arrives as a module, not as a project. 

 PrivacyLib replaces repeated implementations across systems.

 More than a hundred libraries used to access data services, from key/value stores to AI features.

 Millions of assets being accessed daily.

 Coverage:  Systems can have multiple client libraries and legacy integrations, accept direct network calls, and offer direct database access to backing stores. All of them need to be handled to ensure requirements hold no matter the access path.

 Generating tokens faster starts with identifying what limits inference performance. In the batch-size-1 evaluation of Ling-3.0-flash from Inclusion AI on NVIDIA DGX Spark, profiling showed that decoding was memory-bound: reading model weights drove execution time. Two operations stood out—the mixture-of-experts (MoE) computation and the output-layer projection that produces scores across the model’s vocabulary.

 Those findings pointed to two ways to improve performance: reduce the weight traffic in each decode step and generate more tokens per verification round. This post examines three techniques that address those costs:

 Humming MXFP4 MoE kernels to improve execution of the routed-expert computation.

 Online FP8 quantization of the output layer, or LM head, to reduce its weight-read volume.

 Multi-token prediction (MTP) speculative decoding with NEXTN to draft and verify multiple tokens together.

 This post explains how each optimization works, measures its effect, and examines an integration issue that can make the combined configuration slower than the baseline. Ling-3.0-flash serves as the implementation example, with code and deployment instructions in the Ling cookbook .

 Model and baseline configuration 

 The evaluation used Ling-3.0-flash-fp4, a mixture-of-experts model with 124 billion total parameters and 5.1 billion active parameters per token. The model has 42 layers: 35 Kimi Delta Attention (KDA) linear-attention layers and seven multi-head latent attention (MLA) layers. Each MoE layer routes each token to eight of 512 routed experts, alongside one shared expert.

 For agentic workflows, Ling-3.0-flash provides a native 256K-token context window, expandable to 1M tokens. Compared with the previous Ling flash model, it improves long-horizon task stability, tool-calling accuracy, and harness compatibility. Developers can enable reasoning for complex agent tasks or disable it for latency-sensitive interactions. Improved spatial understanding supports constructing physical-scene grids and reasoning about relative positions in coding tasks.

 The baseline followed the official cookbook’s W4A8 configuration: FlashInfer MXFP4 MoE kernels, NVIDIA CUTLASS dense GEMM, and the –enable-fp32-lm-head option. The LM head projects a hidden dimension of 2,560 to a vocabulary of 157,184 tokens.

 For standard MXFP4 deployment instructions, follow the MXFP4 deployment notebook .

 Optimization 1: Humming MXFP4 MoE backend 

 The first optimization replaces the flashinfer_mxfp4 MoE execution backend with humming. Humming is an independent kernel library available through the humming-kernels pip package.

 Unlike the FlashInfer CUTLASS path, Humming uses NVIDIA CUDA Runtime Compilation (NVRTC) to generate and compile CUBINs at runtime for the actual M/N/K dimensions, data types, and GPU architecture. It caches compiled binaries in ~/.humming/cache. This specializes kernels for Ling-3.0-flash shapes, including its relatively narrow moe_intermediate_size of 768. It also compiles at a finer granularity: an individual kernel completes in seconds, whereas the FlashInfer CUTLASS path uses ninja to compile 97 targets and takes on the order of tens of minutes. Performance is reported as time per output token (TPOT) and decode throughput in tokens per second.

 Optimization 2: Online FP8 LM head quantization 

 In the checkpoint, the LM head is stored in BF16 and listed in modules_to_not_convert, so it is not quantized during loading. Its vocabulary GEMM is 157,184 × 2,560, and the entire weight block must be read for each generated token. Under a bandwidth bottleneck, it is therefore a high-value target for compression.

 The optimization applies a dynamic FP8 quantization configuration only when constructing the LM head. The rest of the model continues to load with the checkpoint’s FP8/MXFP4 configuration. Moving the LM-head weights from BF16 to FP8 halves the read volume for this layer. The configuration is enabled with SGLANG_ENABLE_FP8_LM_HEAD=1.

 This setting is mutually exclusive with the baseline –enable-fp32-lm-head option, which outputs logits in FP32 and uses a slower vocabulary-GEMM path.

 Optimization 3: MTP speculative decoding with NEXTN 

 The first two optimizations reduce the cost of each decode step. Speculative decoding follows a different path: it reduces the number of decode steps.

 Ling-3.0-flash includes a NEXTN prediction layer (num_nextn_predict_layers: 1), which can be used directly as a draft model without additional training or downloads. The configuration uses three draft steps and a four-token verification window. In each round, the draft predicts three tokens in sequence, and the target verifies four positions at once, accepting the correct prefix.

 The benefit depends on two quantities: accept length, the average number of accepted tokens per round, and the verification-cost ratio, the cost of one verification step relative to a normal decode step. The measured ratio was approximately 2.26. The principal source of verification cost was not attention computation; at batch size 1, KV reads were small relative to weight reads. Instead, the cost came from MoE expert activation: a normal decode activates eight experts for one token, while verification processes four tokens and can activate up to 32 experts.

 Note: 

 When online FP8 LM-head quantization and MTP are enabled together, the draft model must share the entire LM-head module with the target, rather than only its weight tensor. The original Ling NEXTN implementation didn’t expose this interface. Without it, the framework silently falls back: the draft receives FP8 weights but interprets them as BF16, accept length drops to 1.00, and throughput becomes lower than a configuration with no optimizations.
