 The test
 Tornado is an open-source Python web framework. Its repository holds about 340 files of code, tests and docs. That fits in Qwen4 Max's context window, and it's far more than anyone would paste into a prompt by hand. We picked a fix the maintainers committed on November 18, 2026, two days after Qwen4 Max was released, and tested against the repository as it was just before that commit.
 This is one example, chosen to show what a single call can do and what it costs.
 The bug is in Tornado's websocket code. When a connection closed with messages still unsent, every write_message() call that wasn't awaited logged an error, even though awaiting it is optional. We sent every text file in that checkout as one prompt, with a bug report that describes only the symptom:
 write_message logs "Task exception was never retrieved" when the connection closes 

When a websocket connection closes while messages are still unsent (for example, the client sends its messages and a FIN, or resets the connection, without reading the replies), every write_message() call whose result was not awaited logs "Task exception was never retrieved" at ERROR level.

Awaiting the Future returned by write_message is optional, so an unawaited call should not log anything. A caller that does await it should still get WebSocketClosedError. We asked for the cause and a patch. This is the request, replayed:

 What came back
 The first token arrived after 54 seconds, and the reply was complete at 72. Qwen4 Max traced the error to WebSocketProtocol13.write_message in tornado/websocket.py . That method wraps each write in a task. When the connection closes, the task fails with an exception that nobody is required to collect, and Python logs that as "Task exception was never retrieved."
 The model's patch marks the exception as retrieved. Nothing is logged, and a caller who does await the write still gets the error:
 - return asyncio.ensure_future(wrapper())
+ task = asyncio.ensure_future(wrapper())
+
+ # Awaiting the returned Future is optional, so an error nobody looks
+ # at must not be reported as "Task exception was never retrieved".
+ # Retrieving it here leaves it in place for callers that do await.
+ def _mark_retrieved(t: "asyncio.Task[None]") -> None:
+ if not t.cancelled():
+ t.exception()
+
+ task.add_done_callback(_mark_retrieved)
+ return task 
 The precedent is what makes the patch read like it belongs in the project. The model's explanation says the fix should do what BaseIOStream.write already does for its own futures. That method is in tornado/iostream.py , one layer below the websocket code, and it solves the same problem the same way. The maintainers' commit makes the same comparison.

With the model's patch applied, both pass. We then ran Tornado's full suite, 1,673 tests, with the patch in place, and none failed.

 We are notifying customers about a security incident involving a subset of prompts submitted to Together AI’s serverless inference service in June and July 2026. An unauthorized party downloaded stored prompt samples after a credential for a private repository was exposed in a public code repository.
 We apologize for this incident. We are reviewing the affected data to determine what information was exposed and which customers require direct notification.

 What happened
 As part of routine software testing, we collected prompt samples authorized for that use and stored them in a private Hugging Face repository. The samples came from requests to the MiniMax M3, GLM-5.2, and Kimi K2.6 models, primarily on June 24, July 4, July 8, and July 14, 2026.
 During development of our public GitHub repository, xorl, an AI coding agent committed a credential that provided access to the private Hugging Face repository. Our automated scanning detected the exposed credential, and we reverted the commit.
 During the exposure window, an unauthorized party obtained the credential and used it to download the stored prompt samples. The party subsequently searched those samples for credentials to other services and tested whether those credentials were valid. Five of the credentials tested were canary credentials associated with a Dragos security experiment.
 We have no reason to believe the unauthorized party has leaked this data further and understand that it has now been deleted.
 Investigation and scope
 We have worked with an external forensic investigation firm and law enforcement to investigate the incident.
 Based on our review, we have not identified evidence of additional prompt leakage beyond this incident. Our review of the affected prompt contents is ongoing to determine whether sensitive personal information or other customer data was exposed. We will contact affected customers directly as needed with the findings relevant to them.
 Changes we have made
 Following the incident, we strengthened controls around development workflows, credentials, and customer data. These changes include:
 Using scoped or short-lived credentials, and keyless access where supported, to reduce the potential impact of credential exposure.
 Checking all pull requests for credentials.
 Making zero data retention (ZDR) the default setting for new accounts.
 Updating our development processes governing the use of AI coding agents.
 What customers can do
 Customers handling sensitive prompt data should enable ZDR in their account settings.
 If you have questions about this incident or its potential impact on your organization, contact security@together.ai.
