This is a standalone **draft sidecar**: it carries only the drafter (5 attention layers, rank-256 Markov head, confidence head, block size 9). Token embeddings and the LM head are shared from the target model at load time, so it must be paired with a [`LFM2.5-24B-A2B-GGUF`](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B-GGUF) target file.

Find more information about LFM2.5-DSpark in our [blog post](https://www.liquid.ai/blog/lfm2.5-dspark).

'''bash
llama-server -hf LiquidAI/LFM2.5-24B-A2B-GGUF:F16 \
  -hfd LiquidAI/LFM2.5-24B-A2B-DSpark-GGUF:F16 \
  --spec-type draft-dspark --spec-draft-n-max 9 --spec-draft-n-min 0 \
  -ngl 99 -ngld 99 -fa on

Requires a recent SGLang build with LFM2-MoE DSpark support
([PR #31041](https://github.com/sgl-project/sglang/pull/31041)) and native Hugging Face configuration support
([PR #43939](https://github.com/sgl-project/sglang/pull/43939)). Launch the target with the draft attached:

'''bash
python -m sglang.launch_server \
  --model-path LiquidAI/LFM2.5-24B-A2B-FP8 \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path LiquidAI/LFM2.5-24B-A2B-DSpark \
  --speculative-draft-attention-backend flashinfer \
  --speculative-dspark-block-size 9 \
  --speculative-num-draft-tokens 10 \
  --mem-fraction-static 0.8 --port 30000
'''

Then query the OpenAI-compatible endpoint at `http://localhost:30000/v1`. The baseline is the same command without the `--speculative-*` flags.

Artificial Intelligence 

 Beyond the KV cache: Training and serving i14’s Laplace 3B linear attention model on AWS Trainium2 with native PyTorch

 Most large language models (LLMs) use transformer architectures with softmax attention. During inference, their key-value (KV) cache grows with the conversation or document context. This can reduce concurrency, increase serving cost, and force agentic applications to discard useful history.

 i14 designed Laplace 3B as a linear attention alternative. Its recurrent state stays at 29.5 MB per sequence, independent of context length. Working with AWS, i14 used native PyTorch support through TorchNeuron Native to bring this custom architecture to AWS Trainium2 . This preserved its Gated Linear Attention (GLA) design and Muon optimizer.

 On one trn2.48xlarge instance, Laplace 3B trained at about 120,000 tokens per second. The model served 11,544 output tokens per second across 1,280 concurrent sequences. This post explains the model design, the changes i14 made for Trainium2, and the training and inference results.

 About i14

 i14 is an AI research and technology company that develops model architectures, components, and runtimes. Its work draws on AI, computational cognitive science, and research into how biological systems learn over time. i14 applies these ideas to models that can retain long-range context without allowing serving state to grow with every token.

 Why linear attention models?

 Transformer softmax attention compares tokens across the context. During training, this computation grows quadratically with sequence length. During inference, the KV cache grows as the model processes more tokens.

 Linear attention reorganizes the computation around a recurrent state that is updated for each token. Laplace 3B uses GLA to compress prior context into a fixed-size matrix state. This changes training attention from O( T 2) to O( T ) and keeps inference state fixed at 29.5 MB per sequence.

 Linear attention compresses history rather than retaining every key and value. You must therefore evaluate retrieval quality for your workloads. The fixed state can benefit long-running agents, large-document analysis, and applications that need persistent memory with predictable serving requirements.

 How i14 adapted Laplace 3B for AWS Trainium2

 The original implementation of Laplace 3B used GPU-optimized Triton kernels. The AWS Generative AI Innovation Center (GenAIIC) team first rewrote the GLA kernel with standard PyTorch operators for Trainium2. After comparing both approaches, the team chose the beta version of TorchNeuron Native, the native PyTorch backend for AWS Trainium , because it performed better.

 The implementation required three changes:

 Using native PyTorch for the GLA attention kernel. The team replaced the GPU-specific fused_chunk_simple_gla Triton kernel with standard PyTorch operators, using 16 chunks of 128 tokens to match the 128 partitions of the NeuronCore on-chip buffer.

 Redesigning how Muon communicates. Two all_to_all collectives in MuonFSDP2 cut per-rank traffic by 24 times and raised throughput by 1.63 times.

 Compiling the sequential backward pass. The team statically unrolled the 16 chunk steps of the GLA recurrence to fit the graph-size and on-chip memory limits of the compiler.

 The engineering challenges section describes each change in detail.

 Why AWS Trainium accelerators?

 AWS Trainium is a family of AWS machine learning (ML) accelerators designed for model training and inference. A trn2.48xlarge instance combines 16 Trainium2 chips, 64 logical NeuronCores, high-bandwidth memory, and NeuronLink-v3 connectivity. These resources support the distributed training and inference configurations described in this post.

 Three properties of Trainium2 shaped the implementation: software-managed on-chip memory (Challenge 1), a fast chip-to-chip interconnect (Challenge 2), and a static compiler (Challenge 3). The compiler traces the GLA recurrence as a fixed graph.

 Software-managed on-chip memory. Each NeuronCore has a 28 MiB State Buffer (SBUF) with 128 partitions and a 2 MiB partial-sum buffer (PSUM). The PSUM is wired to a 128×128 systolic Tensor Engine, alongside separate vector and scalar units. The SBUF is not a cache: the compiler schedules every HBM-to-SBUF transfer ahead of time, so the data is in place with no evictions or misses (Figure 1).

 Making data available without risking inadvertent disclosure. Complaint records, CAPAs, standard operating procedures (SOPs), and audit findings belong to one tenant and must be unreachable by another. Not even an errant AI query could cross. Vector store, retrieval logic, and generation context all had to be scoped to a single tenant.

 Executing agents in isolation. The permissions governing an agent’s tools, data stores, and model endpoints had to be scoped to the requesting user rather than a shared service role, available only during execution, and respectful of that user’s access rights.  Reading content that cannot be trusted. Agents here ingest complaints, email attachments, scanned PDFs, and images from outside the organization. Hidden instructions in an attached PDF are not hypothetical at this volume.

 Embedding 2 billion documents without a quarter-long wait. Reliance hosts more than 2 billion documents, with individual tenants storing millions of Word files, PDFs, scanned forms, spreadsheets, images, and email. The team committed to onboarding even the largest tenant within a single working day. Because these documents inform regulatory decisions, quality could not be traded for throughput. A missed complaint erodes trust in the whole system.

 Where the architecture landed

 Holding four tensions at once narrowed the options considerably. Amazon Bedrock addressed them as one platform: multi-model access through a single API, the AWS Region residency and AWS Identity and Access Management (IAM) governance the AWS account already enforces, and Guardrails as production content controls rather than something to build.

 The foundation resolves into three layers, shown in Figure 1. Data preparation embeds quality documents with Cohere Embed v4 on Amazon Bedrock and writes them to a per-tenant vector store on Amazon OpenSearch Service . Secure execution passes a user request through AgentCore Gateway , a capability of Amazon Bedrock AgentCore , which applies authentication and policy before handing it to an isolated microVM session that calls an Anthropic Claude model on Amazon Bedrock. Wrapping both, content protection applies Amazon Bedrock Guardrails twice: input filtering on the way in, output filtering before anything reaches the handler. Retrieval, execution, and screening stay in separate stages, so each can be enforced and evidenced on its own.

 Choosing how to represent the data

 Nothing else worked until the documents were retrievable. That meant accurately, across languages and formats, and not across a tenant boundary. The team evaluated embedding models against its own corpus rather than public leaderboards. The deciding questions were specific to this data: what a photo of a cracked housing has to do with the paragraph describing it, and a German complaint with an English CAPA.

 Cohere Embed v4 on Amazon Bedrock won on five counts and they weren’t independent of each other. What was decided first was how much of the pipeline was made unnecessary. Quality records carry photos of defective products, scanned inspection forms, and annotated diagrams alongside text. Embed v4 places both modalities in one vector space. A photo of a cracked housing and the paragraph describing that defect are retrievable from a single query, with no separate pipeline per modality. Native multilingual support does the same work along the other axis: documents arrive in multiple languages, often inside one tenant’s corpus, and need no translation preprocessing. Two pipelines the team never had to build, and two fewer places for a document to fall out of retrieval.

 The remaining three counts settled where the vectors could live and what they would cost. Customer data can’t leave its AWS Region, even for inference, so in-Region model availability on Amazon Bedrock was a precondition rather than a convenience. Embed v4 supports in-Region inference in the US East (N. Virginia) Region (us-east-1), Europe (Ireland) Region (eu-west-1), and Asia Pacific (Tokyo) Region (ap-northeast-1), covering three of Octave’s regional compliance requirements. Model and feature availability varies by Region and changes over time. For current coverage, see Regional availability by models in the Amazon Bedrock User Guide. Within each Region, Amazon OpenSearch Service costs scale linearly with dimension count. That made Embed v4’s configurable output dimensions of 256–1,536 worth testing rather than accepting by default. Testing against representative production queries showed 512 dimensions holding target accuracy while cutting storage roughly 66 percent against the 1,536 default. The 128K token context window paid off elsewhere entirely: chunks of roughly 4K tokens pack many to a request, which is where the onboarding throughput came from.

 Keeping tenants apart at runtime

 The harder question was where to enforce tenant separation. Application code would have worked, but it would have meant every future feature team getting it right on every code path, where one missed check risks inadvertent cross-tenant disclosure. The team pushed isolation into the runtime instead. AgentCore runtime, a capability of Amazon Bedrock AgentCore, enforces separation below the application layer, and because it stays framework- and model-independent, the agent framework and models chosen for the Complaint Triage Assistant were not constrained by the isolation decision.

 Each user session runs in a dedicated microVM with its own CPU, memory, and filesystem, stopped and sanitized when the session ends. That is hardware-level separation designed to hold regardless of how the agent behaves. AgentCore carries the authenticated user’s identity through the whole execution chain: per-user OAuth token vaults verify the agent acts for that specific user rather than a shared service identity, and credentials are scoped per-agent and live only during the session. AgentCore Gateway authorizes at the tool, operation, and parameter level. Automated reasoning provides formal verification against the defined rules.  A core principle of robust quality assurance is that even rigorous internal processes are strengthened by external scrutiny. That's why we partnered with AVERI (AI Verification and Evaluation Research Institute), an independent nonprofit dedicated to third-party evaluation of AI systems, to conduct an independent review of our internal safety evaluation datasets.
 AVERI’s mandate wasn’t just to test model outputs but to examine the quality and rigor of our tests themselves — asking whether our evaluations stress-test safety boundaries.

 How the collaboration worked

 We provided AVERI with a random sample of prompts drawn from our internal safety-evaluation suite. AVERI's team — led by executive director Miles Brundage and including researchers Sean McGregor, A. Feder Cooper, and George Balston — examined the evaluation prompts for diversity, difficulty calibration, and methodological soundness.
 AVERI assessed the sample independently without input from our evaluation team, ensuring their findings reflected a genuine external perspective.

 What the review confirmed

 AVERI’s review validated several strengths of our evaluation process:

 Comprehensive topical coverage — aligned with publicly documented safety categories including self-harm, cybersecurity, and other risk areas;
 Diversity of testing approaches — variation in writing style (professional vs. informal), single-turn and multiturn conversations, and original content;
 Low contamination risk — content that appeared to be original rather than sourced from publicly available datasets, reducing risk of evaluation leakage through pretraining.
 Opportunities for improvement

 With any fresh review comes the opportunity to identify areas that internal teams — deeply familiar with their own work — may overlook. AVERI's external perspective surfaced several opportunities to further strengthen an already comprehensive suite:

 Expanding linguistic and stylistic diversity — While our evaluations include multilingual prompts, AVERI recommended extending multilingual coverage more evenly across risk categories and further varying prompt structures to broaden the range of scenarios tested;
 Calibrating attack sophistication — AVERI recommended adding more multistep, adversarial prompts to our existing set, so evaluations probe deeper model reasoning and better reflect sophisticated real-world misuse attempts;
 Maintaining evaluation freshness — AVERI identified a small number of prompts with time-limited references and a few edge cases where grading criteria could be made clearer;
 Ensuring evaluation signal quality — In some cases, models may refuse based on superficial cues in a prompt, so passing those tests doesn’t necessarily indicate reliable safety behavior in new situations.
 How we incorporated the feedback

 Concrete improvements made:

 Test set refresh : Updated evaluation datasets to address specific issues identified, removing redundant prompts and adding more-challenging adversarial scenarios
 Difficulty calibration framework : Introduced tiered difficulty levels to ensure that evaluations include prompts that genuinely push model safety limits, not just straightforward cases
 Quarterly review cadence : Established a regular evaluation maintenance process to catch staleness, reduce repetition, and incorporate emerging attack patterns
 Broader language coverage : Expanded multilingual prompts across all risk categories rather than concentrating them in specific areas

 This collaboration represents what we believe is an emerging best practice: engaging independent third parties to evaluate not just model outputs , but the quality of the evaluation process itself . As the AI safety field matures, we expect this kind of meta-evaluation to become an important complement to traditional red-teaming and benchmarking.

Support has to track those customers through the incident, then make sure each gets the right answer when it is resolved.

It provides us with AI teammates that take ownership of operational jobs, particularly repetitive workflows that otherwise fall between people and systems. As we shared in a recent blog , the SpaceXSI customer support team uses Support Bot in Grok Bot to handle customer-facing communication.
 Now we’ve added two more AI teammates that we call on specifically for incidents. The first, IncidentWatch, monitors the support queue for spikes in similar tickets and alerts our team when it sees one.  Detecting incidents through customer reports 
 Customers often notice problems before our internal alerts fire. When several customers report the same issue at once, those tickets can be an early signal of an incident.
 IncidentWatch is a Grok Bot teammate we built to detect that signal. Every five minutes, it reviews the previous 15 minutes of tickets for spikes around the same problem. If the pattern does not match a known incident, IncidentWatch alerts the support engineer on call with the apparent issue, number of matching tickets, and examples to investigate.

 A support engineer decides whether the reports point to an incident and works with engineering to investigate. In the meantime, IncidentWatch holds tickets that clearly match the issue.
 Once the team confirms the incident, we post it to our public status page. Support Bot, our primary customer-facing Bot, returns to the held tickets, checks them against the incident, and responds to customers whose reports match. As the incident progresses, it can return with updates.
 Clearing the incident backlog 
 Once an incident is resolved, there may still be hundreds of related tickets in the queue, and each needs a final response. Traditionally, support teams have had two ways to clear them, and both have drawbacks. They can respond to each ticket individually, which can take hours, or use a bulk action, which is fast but leaves little room to catch a ticket that should not receive the message.
 We built IncidentSweep to combine the control of the first approach with the speed of the second.
 A support engineer starts by telling IncidentSweep which tickets to consider, which to exclude, and exactly what message to send. IncidentSweep finds the matching tickets, reviews each one, and sets aside any it cannot confidently connect to the incident.
 Before sending anything, IncidentSweep shows the engineer the proposed batch, the tickets it included, and the exact message they will receive. The engineer can spot-check the tickets and make changes before approving the send.
 IncidentSweep then sends the approved message in small batches and records each action. It never adds tickets after approval, and if anything fails, it stops and reports what happened.
