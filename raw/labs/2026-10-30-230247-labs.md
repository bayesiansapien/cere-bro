 Configure the ChatGPT desktop app with Amazon Bedrock in AWS GovCloud (US)

 The ChatGPT desktop app is now available on Amazon Bedrock in AWS GovCloud (US) , providing access to OpenAI’s frontier models through two components. Work completes complex, multi-step tasks and delivers review-ready results, and Codex is a coding agent for developing, testing, and reviewing software.

 This walkthrough is intended for organizations whose security architecture requires model inference to use AWS GovCloud (US) identities, endpoints, and Regional controls. It configures Codex to route model requests through Amazon Bedrock Mantle in us-gov-west-1 , where access can be governed using AWS Identity and Access Management (IAM) and existing AWS GovCloud (US) network controls.

 Codex is the OpenAI coding agent for AI-powered software development. With GPT models powering inference, Codex introduces a new class of intelligence optimized for complex, long-horizon developer workflows. You can use the ChatGPT desktop app, the Codex CLI, and IDE integrations with Visual Studio Code, JetBrains, and Xcode. Model inference is routed through the Responses API on Amazon Bedrock.

 For customers with data residency requirements, processing stays within the Amazon Bedrock AWS Region that you select. You pay per token with no seat licenses and no per-developer commitments. Zero data retention (ZDR) is also supported. In this configurable mode, prompts and responses are processed without being written to durable storage by AWS or shared with model providers. This helps you protect sensitive information and meet stringent data-governance, privacy, and security requirements.

 This post walks through a controlled local deployment of the ChatGPT desktop app that sends model inference to Amazon Bedrock in AWS GovCloud (US-West). The configuration uses API-mode sign-in, a managed device policy, a named AWS profile, and network restrictions. These restrictions allow access only to the approved Amazon Bedrock endpoint while disabling other external connections and network-enabled capabilities. The result is a deployment that an agency security team can test and document before approving broader use.

 Using AWS GovCloud (US) and following this guide do not, by themselves, authorize your workload. Your organization remains responsible for reviewing the selected model, AWS services, Region, endpoint, workstation controls, repositories, credentials, and data flows against its system security plan and authorization process.

 Solution overview

 You can use the ChatGPT desktop app in two ways:

 Work for larger tasks that need planning, research, files, and a finished result.

 Codex for technical work such as editing code, running tests, and reviewing pull requests.

 The ChatGPT desktop app runs on an organization-managed computer through the desktop app or CLI. It uses the configured AWS credentials to securely send requests to the Amazon Bedrock Mantle endpoint in us-gov-west-1 . Because this setup uses AWS directly, ChatGPT workspace rules and user roles don’t control it. The main security controls are the computer’s policies and the AWS identity and permissions being used.

 Walkthrough

 The configuration has three main steps: set up authentication, set up the ChatGPT desktop app configuration files, and then launch, initialize, and verify the deployment.

 Prerequisites

 Before setting up the ChatGPT desktop app with AWS GovCloud (US), make sure your version of the ChatGPT desktop app supports Amazon Bedrock in AWS GovCloud (US). You need an approved AWS GovCloud (US) account, an IAM identity and approved credentials, access to the approved model, AWS Region, and endpoint, and permission to use them. You also need to set up the requirements.toml and config.toml files.

 Step 1: Set up authentication

 Select the approved AWS GovCloud (US) account and IAM identity or role with access to the approved model in us-gov-west-1 . Obtain credentials through your organization’s approved mechanism. This walkthrough uses the named profile codex-il5 . Keep credentials, bearer tokens, session tokens, and other secrets out of TOML files.

 Protect the profile configuration, credential source, SSO token cache, and any credential helper from ChatGPT desktop app task writes, while allowing approved authentication tools to maintain and refresh credentials.

 The ChatGPT desktop app supports two Amazon Bedrock authentication pathways: an Amazon Bedrock API key or the AWS SDK credential chain . AWS SSO through AWS IAM Identity Center is supported within the credential-chain pathway.

 The app first checks for AWS_BEARER_TOKEN_BEDROCK in its environment. For desktop use, this variable can be supplied through %USERPROFILE%\.codex\.env on Windows or ~/.codex/.env on Linux and macOS. When present, the bearer token takes precedence over profile-based authentication.

 If no bearer token is available, the app falls back to the standard AWS SDK credential chain. The chain can read AWS credentials from ~/.aws/credentials and related profile settings from ~/.aws/config . On Windows, the corresponding default paths are %USERPROFILE%\.aws\credentials and %USERPROFILE%\.aws\config . The chain also supports SSO profiles. For SSO, it uses the profile settings in the AWS config file and the cached SSO session to obtain temporary role credentials. These credentials don’t need to be manually stored in the AWS credentials file. See OpenAI’s Bedrock authentication documentation and the AWS IAM Identity Center credential provider documentation .

While science fiction lore tells us that humans will meet extraterrestrial life in the form of little green men, the detail that should raise hairs this Halloween is this: the search for extraterrestrial intelligence took a major leap forward with AI, and it increasingly focuses on AI agents built by humans listening for AI agents built by aliens. 

 Some scientists have suggested that extraterrestrial civilizations, if they exist, could be billions of years older than humanity. Such civilizations might have developed technologies far beyond humanity’s, including forms of AI. 

 Breakthrough Listen and the SETI Institute are bringing agentic AI into the daily search for extraterrestrial intelligence. At the Allen Telescope Array in Northern California, agents can now steer the instrument, enhance and correct incoming data, and apply AI models to the incoming stream — all from a single natural language request. The NVIDIA Holoscan platform processes the massive streams of sensor data, giving agents live data to act on. 

 The result is a faster, more adaptable search for potential signals from extraterrestrial life and technologies.

 Terabits a Second, Processed in Flight 

 Radio telescopes generate enormous volumes of data, creating a challenge for scientists who need to identify potentially interesting signals as observations unfold. 

 At the Allen Telescope Array, DAQIRI , a Holoscan platform library, enables the telescope to pull terabits per second of sensor data straight into GPU memory so observations are processed in flight rather than filling hard drives. CyberEther , a signal-processing framework developed at the SETI Institute, does the math using NVIDIA CUDA-X libraries including cuFFT and cuBLAS . 

 Nexus , a web-based observatory orchestrator, acts as the agent harness. The system can handle 2.4 terabits per second on NVIDIA RTX PRO 6000 Blackwell GPUs, with inference running on premises, next to the instrument. 

 Put together, the system enables an agent to steer a telescope’s antennae, calibrate and focus the instrument for a clean signal, catch and fix data errors and plot the result. Agents compress what would take humans weeks or years into hours. 

 Science Fact, Not Fiction 

 The pipeline has already proven itself, achieving the first real-time AI detection of a pulsar — a rapidly spinning stellar remnant that pulses like a cosmic lighthouse — in the Crab Nebula.

 Building an autonomous agent requires a model, a harness, and domain-specific tools. To deploy an agent more securely, developers need a runtime that enforces policies, along with optimization and observability tools for reliable execution.

 For production agents, the challenge lies in making these agents capable and safe to operate with access to real enterprise systems and data.

 This post explains how these components work together, with a focus on how NVIDIA NemoClaw open blueprints enable developers to build specialized agents on a stack they can own, customize, and run. This post provides criteria to help developers integrate NemoClaw with a harness they already use: OpenClaw, Hermes Agent, or LangChain Deep Agents.

 What an agent harness provides 

 An agent requires four things:

 A model that reasons .

 A harness that defines how the agent operates.

 Tools and skills that extend its capabilities.

 A runtime that governs what the agent can access and do in production.

 NemoClaw works with agent harnesses 

 NemoClaw open blueprints currently support three harnesses:

 OpenClaw can access files and applications, write code, spawn sub-agents, and maintain context across sessions. It runs on your own machine or server and supports long-running sessions, memory, and scheduled tasks.

 Hermes Agent , from Nous Research, is designed to get better with use. As teams correct the agents’ approach and repeat workflows, Hermes captures those patterns as durable skills that can be reused in future work.

 LangChain Deep Agents provides a customizable harness for complex, multistep tasks. It combines planning, file-based context management, memory, and delegation to specialized subagents.

 Each harness gives an agent skills, tools, orchestration, and memory.

 Using NemoClaw for full-stack production agents 

 NemoClaw is not a competing harness, and it is not a runtime. It is a collection of blueprints that assembles an open agent stack on top of the harness selected by the developer. The stack combines model and harness optimization with runtime governance.

 Each NemoClaw blueprint brings together four components:

 A tuned open harness, such as Hermes Agent, LangChain Deep Agents, or OpenClaw, optimized to work with NVIDIA Nemotron.

 Nemotron open models .

 NVIDIA NeMo tools for optimization, including NVIDIA NeMo Relay for observing and improving agent execution, plus routing capabilities that can help improve throughput, cost, and reliability.

 NVIDIA OpenShell is the secure runtime that governs agent access to files, networks, credentials, and tools.

 If you are already building with OpenClaw, Hermes Agent, or LangChain Deep Agents, a NemoClaw blueprint can assemble the surrounding stack without requiring you to rewrite the agent.

 Figure 1. NemoClaw is an open blueprint that works with several agent harnesses 

 Why co-optimizing the model and harness matters 

 An agent combines a model and a harness. The model thinks, while the harness provides the environment in which it operates. When the two are matched, the model can focus on the task. When they aren’t, it may ask for context again, stop early, or loop without progress.

 For example, LangChain tuned its Deep Agents harness for Nemotron 3 Ultra by adjusting prompts, tools, and middleware without retraining the model. Starting from an already strong baseline, the harness tuning brought Nemotron 3 Ultra to near-frontier performance at approximately 10x lower cost per run compared with leading closed models.

 The NemoClaw blueprint for LangChain Deep Agents packages these optimizations directly. Every developer using LangChain Deep Agents with Nemotron 3 Ultra can access these optimizations without reproducing the tuning work. The tuned Nemotron 3 Ultra model profile is available through LangChain on GitHub .

 Use a harness such as OpenClaw, Hermes Agent, or LangChain Deep Agents to build and experiment with the agent’s skills, tools, memory, and orchestration logic.

 Example: A memory-driven Chief of Staff, built on Hermes 

 The NemoClaw community repository includes a memory-driven Chief of Staff recipe. The agent maintains a persistent, human-readable model of the people, projects, priorities, and working patterns it encounters, so it doesn’t have to reconstruct context from scratch on every task. It is built as a deployable Hermes profile for NemoClaw, as outlined in the technical design walkthrough.

 The recipe shows the stack working together rather than in isolation. OpenShell governs the agent’s file system, process, and network access, and keeps credentials for managed inference and Model Context Protocol (MCP) connections outside the sandbox. This helps keep the agent bound by policy even when its memory or retrieved context leads it toward an unintended action. NeMo Relay is integrated natively into the Hermes session.  Importance of agent governance

The OpenShell tutorial covers how to create your first policy to prevent data exfiltration to GitHub. NemoClaw references include more sophisticated OpenShell policies that govern agent connections across many different internal tools, sites, and communication channels.

 Deploy across cloud, data center, and local systems

 Configuring NVIDIA GPUDirect Storage starts with understanding your environment. Which settings and storage paths are appropriate for your platform and workload?  The gds-diag tool was developed by the GPUDirect Storage team to simplify optimization and configuration of GPUDirect Storage. gds-diag is a simple, open-source command-line utility that assesses environments, identifies problems, and suggests improvements to help you make the most of your GDS deployment.

 It is also bundled with an optional agent skill that adds a natural-language interface and orchestration layer. The skill interprets your intent, selects and invokes the appropriate subcommands, and coordinates multi-step diagnostic workflows.  Download and installation 

 To use gds-diag , you need a Linux system with Python 3.8 or newer. GPUDirect Storage requires an NVIDIA datacenter-class GPU and NVIDIA CUDA Toolkit 12.2 or newer, but these are not dependencies of gds-diag itself.

 gds-diag is distributed as part of the NVIDIA Magnum IO GitHub repository with no other dependencies to install. Clone the repository on the machine where you plan to run it with git clone https://github.com/NVIDIA/MagnumIO.git and select one of the following usage models:

 Command-line tool: This provides a deterministic, minimal-dependency path to diagnose GDS deployments. Go to the gds-diag directory, run gds-diag.py --help , and follow the Command-line usage guidance.

 Quick tip: The AI agent mode is recommended if this option is available in your environment. gds-diag is validated with both Claude and Codex, though it may work with other tools as well. 

 Command-line usage 

 The gds-diag command-line tool is a single Python script with multiple subcommands to focus on different diagnostic tasks. You can browse available subcommands by running ./gds-diag.py --help .

 For more information about a specific subcommand, run ./gds-diag.py <subcommand> --help .

 Quick tip: Not sure where to start? Just run ./gds-diag.py all /path/to/check , and gds-diag will automatically run a complete sequence of diagnostics for that path. This works in bare-metal, virtual machine, and container environments. 

 Figure 2 groups the available subcommands into four categories.

 Figure 2. Table of gds-diag subcommands, grouped into categories 

 Choose a diagnostic category based on your stage of deployment or the problem you need to investigate.

 End-to-end checks: Use all to automatically select appropriate diagnostics for your environment and run them in sequence.

 Preparing for installation: Use pre-install to check GPU support and CUDA Toolkit installation. Use support-matrix to view supported storage targets and plan your deployment.

 Validating an installation: Use post-install to check whether GDS is installed correctly and identify blockers. Use config-audit to review configuration files and environment variables that influence GDS behavior.

 Deep diagnostics: Use container-check to assess GDS support in container environments, including containerd, Docker, Enroot, and Kubernetes. Use mount-check to diagnose a specific mount point or directory.

 The anatomy of a gds-diag finding 

 The output of most gds-diag subcommands is presented as a set of findings grouped into sections, as Figure 3 shows.

 Figure 3. Screenshot of an example gds-diag finding with annotations 

 Each finding and each section has a status badge.

 “FAIL” indicates a hard blocker.

 “WARN” indicates a potential blocker.

 “INFO” communicates notable information.

 “PASS” indicates a nominal finding and is shown only when you use the --verbose option.

 Each finding includes an explanation followed by a mitigation plan. gds-diag will not implement the mitigation plan or otherwise modify the system on its own . Its role is to identify problems and optimization opportunities and help you or your administrator make improvements. Multiple sections (and findings within those sections) may be shown.

 Quick tip: You can also emit all diagnostic reports as structured JSON data with the --json command-line option. This could be useful if you plan to ingest findings into another tool or archive them for future reference.
