Artificial Intelligence 

 Route coding agent requests to the right model on Amazon Bedrock with NVIDIA NeMo Switchyard

 Coding agents such as Claude Code and OpenAI Codex CLI work in tasks. A developer asks for a change, and the agent reads files, edits code, and runs tests until the work is done. One task can take a few model calls or dozens. What the developer pays for is the task, not one call.

 The price per token alone doesn’t tell you what a whole task costs. The total depends on how many turns a model needs, how much history each turn replays, and how often a task has to be retried or never finishes. You pay for every attempt, including attempts on tasks that never finish. So when you route a coding agent’s requests between models, judge the routing by cost per solved task: the total cost of your runs divided by the number of runs whose tests pass.

 NVIDIA NeMo Switchyard is an open source library that helps an AI agent choose which model handles each request. You define the models that it can use and the strategy that it follows. Its LiteLLM integration supports two strategies. Stage routing reads the recent tool activity and results in the request history, and then picks one of two candidate models. Random routing picks from the configured models, with optional weights, for traffic splits and A/B comparisons. Another option you can explore is LiteLLM, who also recently shipped a native built-in Switchyard stage router as an auto-router strategy.

 In this post, you use the AWS Cloud Development Kit (AWS CDK) to deploy LiteLLM, an open source gateway for large language models (LLMs), with the Switchyard routing plugin in your AWS account. LiteLLM calls the models on Amazon Bedrock . You then use the sample’s benchmark runners to measure cost per solved task for a routed model group and for single-model baseline groups, so that you can evaluate routing against your own workloads.

 Note: The sample installs switchyard-server 0.3.0 from crates.io and runs the published LiteLLM v1.102.0 image. NVIDIA documents switchyard-server 0.3.0 as a demo and evaluation component, and its configuration can change between releases. This sample uses the experimental Switchyard LiteLLM integration and its configuration and APIs may change between releases. This is sample code, for non-production usage. Work with your security and legal teams to meet your organizational security, regulatory, and compliance requirements before deployment. Deploy the sample in a non-production account and test it before relying on it.

The endpoint is your hostname over HTTPS, with an AWS Certificate Manager (ACM) certificate on the load balancer, and only the IPv4 CIDR range that you allow can reach it. With a hosted zone in Amazon Route 53 , Route 53 resolves the hostname to the load balancer.

 AWS WAF filters the request with IP reputation, known bad input, and per-IP rate-limit rules. The Application Load Balancer forwards only /v1/chat/completions , /v1/models , and /health/liveliness to the ECS task in a private subnet, and answers every other path with 404.

 The task runs one container: LiteLLM with the embedded Switchyard plugin. LiteLLM validates the gateway key and calls the plugin to pick a model. Stage chooses between a capable model and a lower-cost efficient model. It reads the tool activity and results in the request history, so the agent must send the full conversation history. Random chooses from a weighted pool. Neither strategy calls a judge model.

 LiteLLM calls the selected model through the Amazon Bedrock Converse or ConverseStream API, with the task’s AWS Identity and Access Management (IAM) role for credentials. The call goes through an Amazon Bedrock Runtime interface endpoint in the Amazon Virtual Private Cloud (Amazon VPC) , so inference traffic stays on the AWS network.

 The response or token stream returns through LiteLLM and the load balancer. The x-litellm-model-name response header names the model that answered. The response body’s model field stays switchyard .

 LiteLLM listens on port 4000 in the container and is the load balancer’s target, and the task’s security group admits only the load balancer. The path allowlist keeps the LiteLLM admin UI, API docs, and key management routes unreachable. Amazon Elastic Container Registry (Amazon ECR) holds the gateway image. AWS Secrets Manager generates the secret behind the gateway key, and the container adds the sk- prefix when it starts. The task definition passes the profile files in LITELLM_CONFIG_TEXT and SWITCHYARD_CONFIG_TEXT , and the startup script writes them to /tmp before it starts LiteLLM. Logs go to one Amazon CloudWatch log group, /<stack name>/litellm , which keeps them for 30 days, and Container Insights collects metrics. The VPC spans two Availability Zones, and one NAT gateway provides outbound access for image pulls and other AWS services.

 The plugin supports Stage routing, which needs exactly two candidates, and Random routing, which needs at least two and splits traffic by weight for A/B tests. Classifier-backed strategies, such as Task and Composite routing, need intermediate model calls that this integration doesn’t support. See the Switchyard routing overview for the full catalog.

 Architecture patterns for fast session startup on Amazon Bedrock AgentCore runtime

 Agents today review code, process claims, and run unattended for hours. Many also sit behind interactive experiences where a person waits for the first response. Amazon Bedrock AgentCore runtime gives these agents a fully managed, serverless environment: each session runs in its own isolated microVM, the platform scales to zero when there’s no work, and you only pay for the resources your sessions consume.

 AgentCore runtime with platformVersion set to “V2” changes how sessions start. Instead of initializing your container for every session, it prepares your environment once, snapshots it, and restores that snapshot for each new session. Session start times are faster and more consistent. V2 also reclaims memory your sessions don’t use, so your bill tracks what your agent uses.

 For most agents, switching to V2 is all it takes. Some agents need restructuring to get the full benefit, and for chat and voice experiences even 2 seconds is too slow. This post explains how V2 starts a session, how to measure session start time, and how to keep work off the first request, including build hooks, which AgentCore runtime now supports.  How V2 starts a session

 AgentCore runtime runs each session in a new microVM. On V1, AgentCore pulls your container image from Amazon Elastic Container Registry (Amazon ECR), starts the container, and runs your initialization code before it can process the first request. The image pull dominates, so cold start grows with image size.

 V2 does that work once. When you create or update a runtime, AgentCore runtime starts your container in a fresh microVM and waits for the first healthy ping ( GET /ping ), which must arrive within 120 seconds. It then clears the operating system’s file cache, to keep the snapshot small, freezes the microVM, and stores its memory and disk as a snapshot.

 This is a change from V1: Every create or update now takes a few minutes while the snapshot is built.

 In this post, init means everything your agent does before /ping reports healthy. With the AgentCore Python SDK, that’s everything before app.run() . If you run your own HTTP server, in Node.js or another language, report healthy only after your initialization finishes.

 Figure 1: Build, once per create or update

 When a new session arrives, AgentCore restores the snapshot into a new microVM. Your process resumes exactly where it was frozen, with its imports, objects, and clients in place. Files from your image are loaded lazily: each block is fetched the first time a session reads it.

 Figure 2: Invoke, every new session

 Three facts follow from these flows, and the rest of this post builds on them:

 Memory comes back whole. Anything your process held at snapshot time, and anything in a RAM-backed file system such as /dev/shm , is available at memory speed from the first access.

 File reads don’t carry over. The file cache is cleared before the freeze, so reading a file during init doesn’t make it fast in a restored session.

 Image files are fetched on first read. The first read of a block comes from snapshot storage and is then cached closer to the host.

 Why OpenFold3 uses asynchronous inference

 Most JumpStart models, such as large language models and embedding models, deploy to real-time endpoints. A real-time endpoint returns its response within a single request, and that request is capped at 60 seconds. Structure prediction works differently. Folding time grows with the number and length of the chains in a query, and real-world proteins and complexes often take several minutes.

 For this reason, OpenFold3 on JumpStart runs on SageMaker Asynchronous Inference :

 You upload the request to Amazon S3 and call InvokeEndpointAsync , which returns immediately.

 The endpoint queues the request and processes it, with an invocation timeout of up to 1 hour.

 The endpoint writes the result, or the error details, to an S3 location you choose. You can poll for it or get a notification through Amazon Simple Notification Service (Amazon SNS).

 Two properties of asynchronous endpoints suit scientific workloads especially well. First, they queue bursts of requests internally, so you can submit a large batch of sequences without building your own job queue. Second, they can scale to zero instances when the queue is empty, which helps you avoid paying for idle instances between experiments.

01 Safety first 

 Safety evaluations inform some of the most consequential decisions we make about an AI model, including whether it’s ready to deploy, which safeguards ship alongside it, and what our next round of safety training and research should focus on. When we say a model is “safer than its predecessor,” we mean that it scored better on a set of evals someone built. But a safety claim is only as sound as the eval behind it, and good ones are hard to build.
 A safety eval measures a model’s propensity to cause or contribute to harm, whether its response to a request makes harm more or less likely, and how severe that harm would be, rather than measuring specific capabilities. It can cover different types of harm. For example, a user may actively request harmful outputs (such as seeking instructions on how to harm themselves), or they may request outputs that are intended to be harmless, but that come with high risk of unintended harm (such as seeking information on the appropriate dose of a drug). Essentially, a safety eval asks, “Given a specific input, did the model do the right thing?”
 Like other types of evals, these can be tricky to get right: researchers have repeatedly found that AI evals are easy to game , don’t always measure what they claim to measure, and aren’t documented well enough to reproduce . The results can change depending on whether the questions are multiple-choice or open-ended , or even based on how answer options are ordered .
 Psychology faced similar issues a decade ago, when large-scale replication projects found that many published findings didn’t hold up, likely at least in part because many original studies relied on small samples and journals favored statistically significant results. In response, the field instituted reforms such as preregistration (writing down hypotheses and analysis plans before collecting or analyzing data), better measurement, and more rigorous statistics, which made measurements more trustworthy and results easier to replicate. Drawing on those reforms, and from our experience building evals at Anthropic , 1 this post shares recommendations for anyone who builds or relies on AI safety evaluations, using examples from our system cards .

 Safety first
 Build a team with the right skills
 Building a strong safety eval requires multiple perspectives, including from subject-matter and technical experts. Methods experts, for example, help decide how to sample, grade, and analyze the model’s responses. Domain experts such as psychologists, biologists, or political scientists help ensure evals cover realistic and diverse test cases. They will also decide what counts as harm, which cases are borderline, and what a good response looks like.
 When one of these perspectives is missing, eval quality can suffer. Failure modes include evals that are technically rigorous but don’t capture the most relevant factors in a specific harm area or, conversely, evals that reflect deep expertise in a subject area but test only a subset of behaviors, making it difficult to draw valid conclusions about the domain as a whole. Having domain and methods experts involved from the beginning of the process can mitigate against both.
 Run evals safely

For this reason, evals should be run in a sandbox with no internet access, and monitored in real time so you can stop a run immediately if a model is acting in ways that could result in real-world harm. In recent months, in response to our own incidents , we have hardened our evaluation environments , temporarily stopped running many evaluations that give models internet access, and implemented real-time monitoring for web search evaluations that require giving models internet access. We continue to work to make these environments both realistic and safe.
 Design
 Match the design to the question
 The first thing to ask when building an eval is: what is the question you’re trying to answer? This should guide the way you design the evaluation, as it will determine how you can interpret the results.
 Most evals are observational: they tell you that one model obtained a different score than another, but not why. Causal claims (for example, “This intervention made the model safer”) need a design that varies one variable at a time, such as evaluating the same model with and without a specific intervention in place. For example, the question “Is the model responding safely to requests for content that might promote eating disorders?” is observational, whereas the question “Does altering the system prompt change whether the model responds safely to requests for content that may promote eating disorders?” is causal. An observational design is the right choice for understanding a model’s behavior; a causal design is the right choice when you want to understand whether a specific change can influence that behavior.
 Measure what you mean to measure

 For safety evals, the obvious construct is refusal, or how often the model declines to respond. This makes sense in many cases—we don’t want models to help a user launch a scam or a phishing scheme. But for conversations related to suicide and self-harm, refusal is often the wrong construct. When a user is in crisis, simply declining to engage is, itself, a failure; the ideal response engages the user with empathy and points them toward human support .  Many scientific simulations, from molecular chemistry to materials science, spend the majority of their execution time computing high-precision dense general matrix multiplications (GEMM). These operations are called DGEMM for real 64-bit floating-point numbers and ZGEMM for complex 64-bit floating-point numbers. cuBLAS is widely used by HPC and AI applications to accelerate GEMM and other Basic Linear Algebra Subprograms (BLAS) on NVIDIA GPUs. Rapid advances in lower-precision hardware have motivated exploration of a new class of algorithms that deliver full double-precision results on the faster integer Tensor Cores.  

 With CUDA Toolkit 13.4.2, cuBLAS no longer has to choose between accuracy and speed. cuBLAS breaks each double-precision number into integer pieces, multiplies them on the GPU’s Tensor Cores, and reassembles the exact result. The answers keep full double-precision accuracy, but the work runs on faster hardware. 

 Two new algorithms make this more efficient: Ozaki-II needs fewer integer multiplications than the earlier Ozaki-I approach, and the 2M method cuts a complex matrix multiplication from four real multiplications to two. This builds on the Automatic Dynamic Precision (ADP) framework introduced in Unlocking Tensor Core Performance with Floating Point Emulation in cuBLAS , which delivers higher double-precision (FP64) matrix-multiplication performance by mapping FP64 arithmetic onto integer Tensor Cores while preserving native FP64 accuracy.

 cuBLAS delivers automatic acceleration of DGEMM and ZGEMM with no application code changes.  From Ozaki-I to Ozaki-II 

 Ozaki-I and Ozaki-II schemes share a common first step, but differ in how the big integer multiplication is performed. Both the schemes align the exponents of the input matrices and convert them to a shared-exponent, variable-length integer representation so that products accumulate exactly on integer Tensor Cores. cuBLAS uses heuristics to automatically choose between Ozaki-I and Ozaki-II for best performance. The integer width is chosen by ADP at runtime or can also be set explicitly by the user.

 Ozaki-I breaks each big integer into 8-bit slices and multiplies slices of A against slices of B in a triangular pattern, so the number of Tensor Core GEMMs grows with the square of the slice count. 

 Ozaki-II uses a faster big-integer multiplication algorithm based on the Chinese Remainder Theorem (CRT). It reduces each quantized operand modulo a set of small pairwise-coprime integers, performs exactly one integer GEMM per modulus, and reconstructs the exact product from the residues. With Ozaki-II, the GEMM count is linear in the number of moduli, whereas Ozaki-I grows with the square of the slice count, so the advantage widens as the accuracy target rises. At the accuracy required to match FP64, Ozaki-I needs roughly twice as many Tensor Core GEMMs as Ozaki-II.

 Because Ozaki-II materializes one residue pair per modulus, a naive implementation would carry a much larger workspace than Ozaki-I. However, cuBLAS already applies the memory-parsimonious tiling introduced for Ozaki-I in CTK 13.3 to Ozaki-II scheme as well, discarding each residue pair immediately after its GEMM. This results in a more manageable workspace size.

 cuBLAS ADP framework is designed to provide accuracy guarantees comparable to, or better than, standard floating-point GEMM algorithms. More information on the accuracy of fixed-point methods can be found in the references. If at run-time, the number of mantissa bits required to preserve FP64-equivalent accuracy exceeds the library default or a user-supplied maximum, cuBLAS falls-back to a code path that utilizes the native FP64 MMA instructions. So, applications can safely use cuBLAS in their production deployments without worrying about numerical accuracy.  What cuPhoton.xBeam computes 

 cuPhoton.xBeam is the FX correlator in the cuPhoton toolkit. It restructures the recordings so they can be read in parallel, builds a .vdix index so later reads jump straight to each frame, and loads the voltages into GPU memory. Then it does the FX work, like DiFX (CPU-based, open-source software correlator): it Fourier-transforms each station’s voltage into frequency channels (F) and cross-multiplies the station and polarization pairs at each frequency channel requested by the job (X). Those steps run on the GPU. In order, xBeam does five things:

 1. Ingest . Read the VDIF frames and place each one at its correct time. xBeam builds a small index file, the .vdix sidecar, that records where every frame is without copying the data, so later reads jump straight to the right place.

 xBeam indexes VDIF frames by timestamp, thread, and physical location. Its .vdix sidecars let subsequent reads locate the required data without rewriting the recording. Missing or invalid data remain explicitly tracked.

 2. Delay and fringe . Shift each station’s samples by the delay in the job’s model, so the same wavefront lines up at every station, and remove the phase drift caused by Earth’s motion. Delay correction spans both sides of the fast Fourier transform (FFT). Integer-sample alignment and fringe rotation occur before channelization; a frequency-dependent phase correction handles the remaining fractional-sample delay afterward.

 3. Channelize. Run an FFT on each station’s voltage stream to split it into frequency channels.

 4. Cross-multiply and accumulate . For every pair of stations, multiply each channel’s spectrum from one station by the complex conjugate of the corresponding spectrum from the other station and sum the products over the integration time. Invalid input is masked, and the accumulated products are normalized using validity-derived exposure weights. The selected processing profile controls additional admission and reported-weight conventions.

 5. Write visibilities . Save the result in DiFX’s SWIN format or in xBeam’s own xbeam-v1 format, whichever the job asks for.

 The delay xBeam applies comes from the job file. It is a sum of different delays: the geometric delay, which is parameterized as a polynomial in time around a reference time t 0, plus a delay resulting from the offset and linear drift of each station’s clock, and a fixed clock offset for each frequency band:

 τ ( t ) = ∑ k a k ( t − t 0 ) k + τ clock ( t ) + τ band \tau(t)=\sum_k a_k(t-t_0)^k+\tau_{\mathrm{clock}}(t)+\tau_{\mathrm{band}} 

 Within one FFT, xBeam either holds the delay constant or approximates it with a straight line or parabola, which is order 0, 1, or 2 in the setting fringe_approximation_order . The phase correction applied to the samples is

 φ ( t ) = 2 π ( − ν ref τ ( t ) + ν LO t ) \varphi(t)=2\pi(-\nu_{\mathrm{ref}}\tau(t)+\nu_{\mathrm{LO}}t) 

 where ν ref is the band’s reference frequency, and ν LO is the local-oscillator frequency term. For stations a and b at frequency ν , the product that is summed is the spectrum of station a times the complex conjugate of the spectrum of station b :

 S a b ( ν ) = V ~ a ( ν ) V ~ b * ( ν ) S_{ab}(\nu)=\widetilde V_a(\nu)\widetilde V_b^*(\nu) 

 xBeam does not compute delays from station positions. It uses the delays given in the job. It also does not trace light paths around a black hole. DiFX is the CPU correlator used as the reference for validating xBeam results. Tools such as HOPS, rPICARD, and eht-imaging take the visibilities from there for calibration and imaging.

 Data moves from disk into GPU memory in one of two ways: standard POSIX reads through pinned host memory, or reads through cuFile, the GPUDirect Storage API. Whether cuFile uses a direct storage-to-GPU path depends on the configuration and runtime conditions. The phase correction, the FFT, and the cross-multiply all run on the GPU.
