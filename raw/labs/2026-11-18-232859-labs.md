## Quantization Details

| Component | Scheme |
|---|---|
| Linear layers (attention q/k/v/o, MLP gate/up/down) | 4-bit symmetric block-wise weights (`MatMulNBits`, block size 32), exported from a quantization-aware-trained (QAT) checkpoint |
| Token embedding / tied LM head | 4-bit block-wise weights (`GatherBlockQuantized` / `MatMulNBits`, block size 64) |
| Activations, norms, logits | FP16 |
| KV cache | FP16 |
| Attention | `GroupQueryAttention` with fused RoPE; 21 sliding-window layers (window 2048) + 7 full-attention layers |

The model is a single ONNX decoder graph (opset 21 + `com.microsoft` contrib ops) with an FP16 KV cache, so it runs on any ONNX Runtime build that provides the WebGPU execution provider, including ONNX Runtime Web in the browser.

## Usage

Run with [ONNX Runtime GenAI](https://github.com/microsoft/onnxruntime-genai) using the WebGPU execution provider. `onnxruntime-genai` is installed with `--no-deps` so that it uses the WebGPU build of ONNX Runtime instead of the default CPU build:

'''bash
hf download microsoft/Aion-1.0-Instruct-2.3B-ONNX-WebGPU --local-dir Aion-Instruct-v1-ONNX-WebGPU
pip install numpy onnxruntime-webgpu==1.27.0
pip install --no-deps onnxruntime-genai==0.14.1
'''

'''python
import onnxruntime_genai as og

model_dir = "Aion-Instruct-v1-ONNX-WebGPU"
config = og.Config(model_dir)
config.clear_providers()
config.append_provider("webgpu")
model = og.Model(config)
tokenizer = og.Tokenizer(model)

chat_template = open(f"{model_dir}/chat_template.jinja", encoding="utf-8").read()
messages = '[{"role": "user", "content": "Give me a short introduction to large language models."}]'
prompt = tokenizer.apply_chat_template(messages, template_str=chat_template, add_generation_prompt=True)

params = og.GeneratorParams(model)
params.set_search_options(max_length=4096)
generator = og.Generator(model, params)
generator.append_tokens(tokenizer.encode(prompt))

stream = tokenizer.create_stream()
while not generator.is_done():
    generator.generate_next_token()
    print(stream.decode(generator.get_next_tokens()[0]), end="", flush=True)
'''

`max_length` (prompt + generated tokens) defaults to 4,096 in `genai_config.json`; it can be raised up to the model's 32,768-token context, at the cost of a larger pre-allocated KV cache. To run on CPU instead, omit the `clear_providers` / `append_provider` calls.

## Model Description

Aion Instruct serves as the foundational Small Language Model (SLM) in the Windows ecosystem, specifically optimized for on-device AI, text and operating system use cases. ## Bias, Risks, and Limitations

With 2.3 billion parameters, Aion Instruct is a rather small language model. While this means the model is taking up less disk space and can be quite fast, it also comes with trade-offs.

In comparison to large language models, whose size enables storing vast amounts of factual knowledge and grasping subtle context, logic, and nuance, small language models such as Aion Instruct can miss fine details, provide misstatements, or show inability to follow complex multi-step reasoning. Larger models also have larger context and the memory needed to remember facts accurately, as well as the reasoning to see through trick questions. Smaller models lack the storage and reasoning depth to consistently do both.

While Microsoft’s best practices were followed while training and safety alignment was conducted, anyone using the model should bear in mind that Aion Instruct does not have the complex reasoning needed to understand all the nuances of safety, including attempts to induce unsafe behavior. Aion Instruct may be susceptible to adversarial attacks.

XPIA, DIC, and ECI are amongst the key metrics to improve in future releases:

*Scores are direction-normalized so higher is better (0–100).*

While we continue to work towards closing performance gaps across languages and supporting more languages, output quality may differ depending on the language.

We also remain committed to improving the groundedness and safety of Aion Instruct. One way of limiting harmful output generation are content moderation models – a local model from that group will be used alongside Aion Instruct when the model becomes available in Windows (General Availability coming by end of Jan 2027).

### Recommendations

The model was not trained to excel at world knowledge. Users should take note of recommended uses (see section: Uses), use their best judgement, and follow laws and regulations when interacting with the model.

## Quickstart

'''python

    model_id,
    dtype="auto",
    device_map="auto",

]

    add_generation_prompt=True,
    return_dict=True,
    return_tensors="pt",
).to(model.device)

## Chat Format

Conversations are formatted with the included [chat template](./chat_template.jinja):

'''
<|system|>You are Aion Instruct, a large language model trained by Microsoft.
Knowledge cutoff: 2025-12
Current date: YYYY-MM-DD<|end|><|user|>Hello!<|end|><|assistant|>Hi! How can I help?<|end|>
'''

- Every turn ends with `<|end|>`, which is also the EOS token.
- A leading `system` message is appended to the default system preamble.
- Optional template variables: `model_identity`, `knowledge_cutoff`, and `current_date`.

### Tool Calling

Pass tools via `apply_chat_template(..., tools=tools)`. The tool schemas are injected into the system prompt between `<|tool|>` and `<|/tool|>`, and the model emits calls as:

'''
<|tool_call|>{"name": "<function-name>", "arguments": {...}}<|/tool_call|>
'''

Tool results (`role: "tool"` messages) are returned to the model inside a user turn prefixed with `<|tool_response|>`.

01 Introduction 

 Summary: Claude has solved two open problems in theoretical physics. Both concern black holes and the search for a theory of quantum gravity. In the first, it completed a calculation that physicists set up more than 20 years ago, but which had never been solved. Claude’s result showed that a sudden transition associated with the formation of black holes persists even where spacetime no longer has a definite shape. In the second, Claude found the exact limit of the simplest version of a technique used to test candidate theories of quantum gravity. This post explains both findings, first in plain terms and then in more technical detail. The preprints are available here and here . 
 Introduction
 Modern physics rests on two frameworks: general relativity and quantum mechanics. General relativity describes very large things, like stars; quantum mechanics describes very small things, such as atoms. Both are astonishingly good at predicting how the universe behaves, but they’re mathematically incompatible. Finding a theory that unites them—“quantum gravity”—is one of the field’s biggest goals. Black holes are a natural testing ground, because they’re one of the few areas where both relativity and quantum mechanics matter—they pack immense mass into a very small space. 
 One of the most useful tools for studying quantum gravity is called holographic duality . The real universe has three dimensions of space and one of time, which relativity combines into four-dimensional spacetime. But physicists studying quantum gravity often work with simpler model universes that they can understand in more detail. 
 The basic idea of holographic duality is that some of these theoretical universes can be described in two ways: as a complete universe with gravity and spacetime, and in quantum terms, with no gravity at all, “written” on the universe’s outer boundary. Just as a real hologram encodes a 3D image on a 2D plane, the quantum model encodes all the information of the universe in one dimension fewer (a universe with four dimensions of space, for instance, can be fully described by a quantum theory with three). This lets physicists turn hard questions about gravity into questions about quantum physics, which are sometimes easier to answer. 
 The first problem Claude solved concerns what happens when you heat up one of these theoretical universes. At low temperatures, the universe fills up with a gas of particles. Above a certain temperature, a black hole forms instead. In 1983, Stephen Hawking and Don Page showed that this switch is abrupt: it’s a phase transition, similar to how water suddenly boils at 100°C. But Hawking and Page’s calculation relies on general relativity, which holds only when the universe is vast, compared with the tiny scale at which that description breaks down. As the theoretical universe shrinks toward that smaller scale, spacetime loses any definite shape and becomes blurry, and nobody knows how to do the calculation on the gravity side of the duality. On the quantum side, though, the same situation can be calculated, at least in principle.
 In 1999, physicists found that there was a phase transition in that regime as well. But they didn’t know whether it was abrupt, like Hawking and Page’s, or smooth. In 2003, a group of physicists set out the calculation that would settle the question , but it was extremely complex and was never completed. Claude did it by running a small research group of copies of itself, in which it worked out almost every piece of the calculation independently and checked its math against known results. It showed that the phase transition is abrupt. The same sudden switch appears at both extremes, suggesting that black hole formation isn’t just a feature of relativity but is actually built into the underlying quantum theory.
 The second problem concerns a simplified theoretical universe with two dimensions of space instead of three. This universe is straightforward enough to study in detail, but still has black holes and other mysteries similar to those of our own universe. Even in this simpler universe, physicists don’t know how to create a full theory of quantum gravity, so they approach it from the other direction: rather than building a single, correct theory, they try to rule out wrong ones by showing that they are internally inconsistent. This method is called bootstrapping .
 Since 2009, physicists have used a version of this method to set a ceiling on how heavy the lightest black hole in such a universe could be. Any theory that breaks the ceiling is ruled out, and each lowering of the ceiling narrows the search. Results from numerical calculations hinted at where the best possible ceiling lay, but they couldn’t prove it, and the best proven ceiling was well short of what the numerical results suggested. 
 Claude Fable 5.2 noticed a pattern in the numerical results that physicists had missed and borrowed a method from elsewhere in math and physics to calculate the precise ceiling for the simplest version of this technique and prove that it could not be lowered. It doesn’t identify the correct theory, but it may point physicists in the right direction.
 Neither result describes our own universe directly, and neither has practical applications, but both contribute to a long-running theoretical effort to understand how quantum mechanics and relativity fit together. 
 In the rest of this post, we explain in more detail what each problem was and what Claude did to solve them.
 A note about Claude’s methods
 In August, an Anthropic researcher, Hongbin Chen, was testing Claude’s capabilities as a side project. He asked Claude to draw up a list of interesting open problems in theoretical physics, specifically focusing on black holes and the bootstrap method. Claude came back hours later with 22 candidates, and Hongbin set up separate agents to work on each one; they could read each other’s progress posts and collaborate when working on related problems. The agents ran in the background, with no special setup, for about six weeks.
 The agents solved the two problems in this post. One was the Hawking-Page phase transition, the question of when a hot gas turns into a black hole. Weeks after one of the agents reached a solution, a physicist, who had independently used Claude to tackle the same problem, shared his result, and a colleague realized that Hongbin’s agent had reached the same answer earlier. The two solutions used different methods, so they were a useful check on each other. 
 The modular bootstrap result came from several agents. The one that was assigned the problem spotted the pattern in the numerical results when surveying the bootstrap literature, and another one—which was working on a mathematically related problem about how tightly spheres can be packed into a high-dimensional space—turned that pattern into a method. It found that this method reproduced a sphere-packing result recently proved by an OpenAI model . Claude then applied the same method to the bootstrap problem, which an earlier Claude agent had tried, and failed, to solve in 61 parallel attempts. Two other agents also independently arrived at the same answer. One half of the final proof, showing that the ceiling can’t be lowered, follows the strategy of the OpenAI proof. In September, the results were formally verified in Lean, a computerized proof checker. Claude then wrote the paper with minimal guidance, and a physicist checked every main result.
 The Hawking-Page transition
 To understand the first problem, we need to start with something much more familiar: a walk through New York City.
 Two equally good routes from Penn Station (A) to the High Line entrance (B). In theory, a quantum particle can take both simultaneously.

 Imagine that you’re heading from Penn Station to the High Line entrance on West 30th Street and 10th Avenue, and there are two equally good routes.  Training a next-generation machine learning interatomic potential (MLIP) requires ground truth: tens to hundreds of millions of density functional theory (DFT) calculations of energies, forces, and stresses across diverse structures and chemistries.

 Plane-wave DFT, with VASP as its dominant implementation, is the gold standard for generating that data. It is accurate, well-validated across materials classes, and ubiquitous at the national labs and research institutions running these calculations at scale. 

 As MLIP training datasets have grown, so has the pressure to generate DFT data faster and cheaper. But the small unit cells and dense k-point grids common in MLIP data generation can leave significant GPU performance unused. VASP’s OpenACC implementation has delivered meaningful speedups, especially for large-system calculations. However, for smaller systems, sequential k-point processing limits GPU utilization. At the same time, AI workloads are reshaping GPU hardware development toward lower-precision data types, creating a growing gap between what modern NVIDIA GPUs can deliver and what FP64-only HPC codes are optimized for.

 This post introduces two new NVIDIA capabilities that address these bottlenecks. The first, Daviator, resolves the small-system GPU performance problem through k-point and spin-batched GPU kernels. In particular, a batched Davidson solver delivers significant performance gains. The second, a new mixed precision execution layer, enables further performance gains, especially on inference-class GPUs with a high FP32:FP64 throughput ratio.

 For a projected reference dataset workload, the results show up to 22x faster time-to-solution and up to 75% lower cost compared to CPU execution, depending on hardware and configuration.

 The GPU bottleneck in plane-wave DFT 

 In periodic systems, electronic wavefunctions are parameterized by crystal momentum, a discrete set of k-points that samples the Brillouin zone. For periodic structures with small unit cells, hundreds to thousands of irreducible k-points are required to achieve well-converged results.

 Each k-point solve is largely independent; for instance, no inter-k-point communication is required during the Davidson eigensolver step. Despite this independence, VASP’s OpenACC GPU port processes k-points sequentially. For large systems, the work per k-point can fully saturate a GPU, but for small systems with dense k-point grids, the hundreds of small GPU dispatches per step causes kernel launch overhead to dominate compute time. The result: a single-atom iron system with 752 k-points ran 8x slower on the more expensive GPU hardware than on CPU. Thus, researchers working at this scale were left with a manual routing decision based on the size of the job.

 Additionally, plane-wave DFT traditionally runs in FP64, a conservative default that guarantees accuracy throughout the solver pipeline. But GPU hardware is no longer symmetric in this regard. On data center GPUs, FP64 throughput has held flat across NVIDIA Hopper, Blackwell, and Rubin GPUs, while FP32 throughput has continued to increase. Inference-class and workstation GPUs like the RTX PRO 6000 push this further, with a 64:1 FP32:FP64 ratio (Figure 1). As AI workloads drive hardware development toward lower-precision data types, the fraction of peak GPU throughput available to FP64-only codes is stagnating.

 Figure 1. A comparison of FP64 and FP32 throughput across different NVIDIA GPUs 

 Daviator: Batching k-points for GPU saturation 

 Daviator is a library of GPU kernels developed by NVIDIA that replaces sequential per-k-point processing in plane-wave DFT inner loops with batched GPU operations. At the core of the transformation lies a batched Davidson eigensolver that replaces sequential loops that cause latency with batched FFTs, GEMMs, and custom kernels. This drops the number of GPU kernel launches drastically, enabling SM occupancy to go from a fraction of capacity to near saturation. Data stays resident in GPU memory throughout. VASP retains full ownership of the SCF loop, mixing, symmetry, and I/O; Daviator integrates at well-defined call boundaries over data already on device.
