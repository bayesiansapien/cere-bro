01 Why migrate? 

 Many problems have a generator–verifier gap: it’s often far easier to verify that a solution is correct than to come up with one. Sudoku is a classic example. It’s simple to check the solution (just count the numbers in each row, column, and box), but finding that solution can take a long time. Many ambitious Claude projects have relied on this gap: formalizing proofs in mathematics or migrating large, well-tested codebases are tasks Claude can take on as long as it has a reliable way to verify its work.
 But as Claude has become more capable, it’s begun to take on projects in live systems, where generating the work is easier than verifying it. In these systems, users often rely on edge cases and quirks that fall outside the test suite , and it’s hard to write a definition of “correct” that covers everything . Without a reliable way to check Claude’s work, the migration of a live system is hard to trust—however quickly Claude can generate the code for it.
 We ran into this problem when we migrated our Messages API from Python to Rust. This API is the primary way that customers—as well as our own apps, like Claude Code and Cowork—reach Claude. From early 2024 to fall 2026, API traffic grew roughly 1,800 times. Rust would allow us to use far less CPU per request. Claude wrote a first version of the API’s core request path in about a week. But building trust in the migration required us to find a way to verify that our Rust API was at parity with our production API. This proved hard for several reasons, including that the Python API continued changing throughout the migration, so parity was a moving target; Claude can reply nondeterministically to the same request, so a difference between two outputs didn’t necessarily mean a bug; and we couldn't read customer requests, so we weren't able to easily see where the two versions diverged.
 In this post, we share how we turned the production Messages API itself into a verifier—and how that helped us test the new Rust version on production traffic, find where it differed, and automatically dispatch agents to fix those differences. This allowed us to ship an API on Rust that uses about 70% less CPU per request and cuts median time to first token by about 20% without ever taking the service offline or freezing feature development.
 Why migrate?
 We built the Messages API in 2023 and wrote it in Python, which was widely used internally for much of our research code. At first, it was simple. The Messages API passed requests to the model and sent back what the model wrote. (One engineer at the time called it “basically a request forwarder.”) But as the Messages API became more capable and deeply integrated with our codebases, it also developed shared dependencies with Python libraries that were owned by our research and inference teams, which made it hard to move. If we ever wanted to move to another language, it would mean building logging, metrics, and tools all over again.
 This calculus gradually began to change. By late 2025, every Messages API request had to be validated, converted into the prompt, tokenized, and screened by our safety classifiers. As each reply arrived, the stream of tokens had to be sorted into text, thinking, and tool calls, and Python added overhead to every one of those steps each time it created an object, freed memory, or handed its work to the next task. Traffic eventually grew far beyond what the initial Python service was built for (Figure 1), and we quickly needed to find a way to make the service much more efficient.
 The monthly average of API requests per day on our own platform, including our own use.

 Incremental or all at once?
 Full rewrites of large production systems are often approached cautiously, for at least two reasons. First, there is no guarantee that test suites cover 100% of production code behavior, and rewriting it is risky. Second, the sheer effort required often makes such work intractable. (In 2024, after one of our engineers suggested migrating to Go or Rust, another temporarily settled the question: “ We are not rewriting the API in go or rust! ”)
 The standard advice if you’re looking for performance gains is thus to rewrite only the parts that are slowing the system down, so that’s where we started. In Rust, we rewrote the code that parses a model’s output and called it from Python. This reduced the API’s CPU usage by about 8% to 10%. However, incremental solutions often incur added complexity, and it’s important to make sure that incremental improvements justify those costs. In our case, the gains didn’t justify the added complexity. Each token now crossed between Python and Rust three times (Figure 2), creating new sources of overhead.
 After the incremental rewrite, each token of a reply crossed between Python and Rust three times.

 As Claude became increasingly capable, we began to question whether the usual reasons to avoid a full migration still held. The effort required to undertake the project was dropping fast: by May 2026, Claude was writing more than 80% of the code Anthropic merged . We wondered if Claude could now help us write code that would empirically capture every behavior and fix in the production system. But the question became: how could we verify that the behavior of our migration was correct? Verification, not generation, had become the bottleneck.
 How we verified the migration
 General approaches
 To verify the migration, we first needed to define what “correct” meant. You can do this in a few ways (Figure 3). If you’re lucky, you can simply write a rule. A theorem in mathematics is a precise statement, and a proof assistant (like Lean) can check each step of a proof against a fixed set of rules. Other times—and more frequently in software engineering—you define “correct” with a set of examples, like tests. For instance, when Bun moved from Zig to Rust, its test suite was written in TypeScript, so the same tests could judge both versions. In our case, neither approach was sufficient, so we used the existing system as an oracle to test parity during the migration. In this case, our existing system (the Messages API) kept changing. We were releasing new models and shipping new features regularly, which made the definition of “correct” a moving target.
 Three common sources of “correctness.”

 Tests
 Tests were the easiest place for us to start, since we already had an existing set of about 700 integration tests. However, two problems limited our ability to trust them to verify the correctness of a migration as high stakes as this (Figure 4).
 The tests were coupled to the Python implementation. An integration test sends a request, then checks the reply and what was sent to other services. Our tests ran the Python API inside the test’s process and mocked services, like billing and rate limiting, in Python’s memory. The tests had to change along with the code, and Claude helped with both. Now, a “pass” could mean that the code was right, or that the test had been changed in a way that let wrong code through. We saw this happen: when we audited the ported tests, we found more than 100 weakened assertions.
 The tests were incomplete. The Messages API has dozens of features, and there are far too many configurations to test them exhaustively. Just 20 binary options make over a million combinations—that translates to 12 days of tests at a second each, for one model, before we even vary the prompts inside them. In practice, engineers test a subset that tries to approximate production, but that process inevitably misses cases. Some projects, like Bun, have an independent suite that’s extensive enough to judge a rewrite. Many production services don’t; what counts as correct depends as much on how they behave as on what’s in their tests or documentation.
 A ported test may check less than the original (dashed), and tests cover only the combinations someone thought of.

 Detecting parity with production
 Production data is sometimes “ the only true test ” that new code behaves like the old code. Running requests through old and new code and comparing the results is often called shadowing . To understand what we needed to compare, it helps to walk through what happens to a single request on the Messages API (Figure 5). The API validates each request, converts it into a prompt a model can read (the prompt for inference), tokenizes it, and runs it through safety classifiers. A model then writes a reply, one token at a time. On the output side, the API sorts those tokens into text, thinking, and tool calls, streams them to the customer, and counts usage for limits and billing.
 The Messages API’s input and output paths. Filled dots are examples of differences we found between Python and Rust. The hollow dot is a risk we had to prevent.

 The migration covered both the input and output paths. Some differences were obvious, such as when the Rust API rejected a request that Python had accepted. But many were subtle. For instance, if the Rust API left out part of a prompt, the request would still succeed and the model would still answer, though sometimes with minor differences.
 Our Rust API passed about 98% of its tests in April, yet only about a quarter of inputs matched on production traffic (Figure 6). The gap came partly from cases in production traffic that our tests didn’t cover. For example, when Python writes JSON tool calls, it escapes certain characters (e.g., an emoji) by replacing them with text codes. Rust wrote those characters as is, so the two prompts differed by a few bytes. Production also weighted bugs differently. In a test suite, each case counts once, but in live traffic, a bug will show up in each request where it’s triggered, which means a single common bug can cause many mismatches.

 Built in collaboration with analytical chemists and using community-developed tools, Mass Spec Skills empowers scientists using Google Antigravity to interpret tandem mass spectra, lay out chemical evidence, and match frontier-level retrieval accuracy even with a lightweight model.
 Every sample of blood, soil or plant tissue contains a vast array of small molecules, such as nutrients, hormones, drugs and their breakdown products, pollutants, or bioactive compounds with therapeutic potential. A modern mass spectrometer can detect tens of thousands of these molecular signals in a single drop of sample extract, measuring the masses of charged molecules and, in tandem mass spectrometry (MS/MS), the fragments they break into.
 These measurements, however, do not directly reveal the molecular structure. Researchers cannot immediately tell which compound produced a signal and relate it to its biological role or downstream use cases.
 To fully map the diversity of small molecules, which remains largely uncharted, researchers need ways to translate mass spectra to molecular structures at scale. The standard approach is to match each spectrum against reference spectra from previously measured molecules. Yet even after a decade of expanding reference libraries, spectral searches annotate on average only about 5% of measured spectra, and 10% for human samples; the rest has been called the "dark matter" of mass spectrometry.
 Many of the molecules producing these unannotated signals are already listed in public chemical databases, but their spectra have not been recorded, so there is no reference spectrum to compare against. Elucidating them instead requires inferring the structure directly from the observed fragment ions.
 Analytical chemists have a well-tested, step-by-step workflow for narrowing down candidate structures from tandem (MS/MS) spectra: check spectral reference libraries, find the molecular formula and retrieve candidate structures from chemical databases, and then test every candidate against observed fragment peaks.
 The tools for each step exist and are openly available, but running the full workflow would take a domain expert a significant amount of time for every single spectrum. Because a single study can produce thousands of spectra, manual analysis cannot keep up, leaving most of these signals unannotated.
 Today, we are sharing Mass Spec Skills for Google Antigravity , a suite of domain skills that pair Gemini's chemical reasoning with the ability to run established mass spectrometry tools and query public chemical databases on the user's behalf to fulfil their request. Antigravity runs these skills, combines their results, and reasons about the chemistry, laying out the evidence for a chemist to review.
 For molecules that are already catalogued in a database, identification is much faster. For undiscovered molecules, the agent still helps: it narrows down the formula and the parts of the structure supported by the fragments to guide full structure elucidation. A language model cannot do this on its own, since matching fragments to a structure takes precise mass calculations, searches across databases of millions of compounds, and simulations of how bonds break. Pairing Gemini’s reasoning with dedicated chemistry tools brings those steps into one workflow.

 Antigravity and the Mass Spec Skills have the potential to transform our natural product-based drug discovery workflows by substantially accelerating the identification of bioactive compounds from complex plant extracts. Their remarkable accuracy in predicting even highly complex molecular structures (>90% in most of our evaluations), coupled with detailed interpretation of MS/MS fragmentation patterns, could significantly reduce the time required for compound annotation and enable us to prioritise promising bioactive candidates more rapidly and confidently.
 Dr Phanankosi Moyo
 University of Pretoria

Verifiable Social Reasoning for LLM Assistants

 November 25, 2026
 Zorik Gekhman, Senior Research Scientist; Amir Taubenfeld, Staff Research Engineer; Google Research

 We introduce an evaluation framework based on multi-agent social simulations that quantifies how well AI assistants understand social situations from users' subjective narratives. In our framework, a target agent with a hidden motive interacts with other agents including one representing the user, who then consults the evaluated assistant to infer the target’s motive, providing verifiable ground truth by construction.

 Large Language Models (LLMs) are widely used for everyday personal support and advice, yet evaluating their social reasoning in such consultation settings remains challenging since (1) it requires setups where the assistant learns about social situations from subjective user narratives, and (2) social properties, such as others’ intentions, typically lack verifiable ground truth.
 Designed to address both of these challenges, we introduce an evaluation framework for social reasoning based on multi-agent simulations. In our framework, a target agent is assigned a hidden motive and interacts with other agents, including one representing the user. The user then consults with the evaluated assistant, which must infer the target's hidden motive. Evaluating a diverse range of LLMs through our framework reveals that relying on subjective user mediation substantially complicates social reasoning. Furthermore, models are sensitive to user framing, require more detail than humans need to reach correct predictions, and fail to fully leverage clarification questions. We open-source the framework and dataset to encourage future research on user-mediated social reasoning.

 AI assistants operate within a user-mediated reality: the assistant hears about social events only through the subjective lens of the user, making it challenging to reason objectively about the true motive of an actor in the user’s circle. 

 User-mediated reality
 When evaluating LLMs’ social reasoning, it’s important to recognize that deployed assistants operate within a user-mediated reality . In classical reasoning tasks like math and code, LLMs operate over objective, complete information. However, when an LLM acts as a conversational assistant and is asked for personal support and advice, it does not observe the actual social interactions firsthand; its only source of information is the subjective, potentially biased lens of the user.
 This information asymmetry can be challenging, as users may omit crucial context or provide a distorted narrative due to personal bias (e.g., projecting their insecurities onto their recounting of events). When models adopt the user's premise, they may amplify one-sided assumptions rather than offer objective assessment. This can result in an undesired failure mode, such as dispensing harsh advice against a colleague who was actually trying to help.

 An example from our study: the evaluated model offers potentially harsh counsel despite the user describing a clearly helpful peer. 

 Evaluating everyday social interactions
 Existing evaluations often constrain their scope to edge-cases and overt anomalies, like testing whether models endorse absurd claims such as a human claiming to have supernatural powers , largely overlooking more nuanced everyday social interactions. These everyday interactions represent a massive share of real-world usage, translating to hundreds of millions of daily conversations where users seek personal support, relationship advice, and companionship.

 The challenge of verifiable ground-truth
 Evaluating everyday scenarios is inherently more challenging due to a lack of verifiable ground truth. In extreme cases, ground truth labels come “for free”; a claim of having supernatural powers, for instance, is trivially false. In contrast, establishing a verifiable ground truth for nuanced, day-to-day interactions, such as inferring human motives, is far less trivial.

 Our approach
 To systematically evaluate LLM-based assistants’ social reasoning, we propose an evaluation framework based on multi-agent simulations that produces rich interpersonal dynamics between generative characters with three core principles:
 User-mediated reality: As illustrated in the figure below, the evaluated model, which acts as an assistant, does not participate in the main social interaction and cannot observe the events firsthand. Instead it interacts exclusively with a single user persona.
 Verifiable signals: To establish a verifiable ground truth, the evaluation framework starts each simulation with a controllable entity that has a hidden motivation. This motivation shapes the entity's behavior throughout the simulation, and the goal of the evaluated assistant is to predict it.
 Controllable axes: To evaluate how user perspective influences the assistant's social reasoning, the framework parameterizes the user persona's cognitive filters along distinct axes, such as toggling a user between being confident or insecure.
 Based on these principles, our framework tests social capabilities across diverse scenarios.

 Bird's-eye view of our framework. 

 Our framework programmatically generates scenarios and evaluates them using a five-step pipeline:
 Ground in social topics: We start with a definition of a set of social reasoning categories (e.g., desires, knowledge) that determine the scope of the evaluation. Grounding the evaluation around some principled set of categories ensures that it covers a range of social aspects.
 Generate scenario templates: The framework generates the scaffolding for each simulation, including: a multi-scene structure, a user persona, any background personas, and a target persona whose hidden motive is controlled by the framework. Every scenario is built around a reasoning question. The diagram below illustrates an example scenario within the desire category, requiring the model to deduce the romantic motives of the target persona.
 Run the main simulation: The simulated user, the target entity, and any auxiliary agents interact naturally across the scenes to generate a concrete, emergent social narrative. The multi-agent simulations are implemented by extending the Concordia open-source library developed by Google.
 Conduct the assistant debrief: The user agent is extracted from the simulation and turns to the assistant for social advice, privately recounting the events in a partial and perhaps biased manner.
 Assess the assistant decision: The assistant is prompted to predict the underlying hidden motive based solely on the user-mediated conversation. We then use an LLM-as-a-judge to determine if the assistant successfully deduced the ground truth.

 A simplified illustration of a scenario template (step 2 above). Each simulation instantiates one of the hidden motives (right panel) that shapes the target persona’s behavior. This motive serves as the ground truth that the evaluated assistant must predict. 

 Importantly, the simulation and the debrief are separated in our framework, allowing simulations to be reused efficiently across any number of evaluated models, and enabling the creation of static evaluation datasets. We open-source the framework and a dataset with over 20K generated examples for running experiments.

 Key findings
 Our framework makes it possible to systematically study what makes user-mediated social reasoning challenging, offering insights into how better assistants can be developed and evaluated. We apply it to 12 LLMs and isolate several key factors:
 The assistant-observer gap: When we show an LLM the objective, unmediated events of a simulation directly as a "fly on the wall" observer, the model is significantly more accurate at predicting the verifiable ground truth than when the same model acts as an assistant talking strictly to the user. This gap isolates the cost of reasoning through the user's subjective lens.
 Sensitivity to user framing: The gap intensifies when we inject explicit biases into the simulated user. Rather than offering an objective perspective, the evaluated models often adopt the user’s subjective framing. For instance, in some cases where the user expresses unfounded suspicion, the assistant validated those assumptions rather than reasoning from the underlying facts.
 The effect of narrative detail: Models improve with more detailed user narratives, even when the additional detail is not necessary for a correct prediction. This suggests that models often require more evidence than is actually needed before committing to certain predictions.
 Multi-turn dynamics: Longer conversations do not always improve social reasoning accuracy. While additional turns provide opportunities to ask clarifying questions, models preserve conversational coherence, often causing models to anchor to prior exchanges, reinforcing the user’s subjective framing across successive turns.
 We are currently using the framework and dataset to help inform our own model development. We are also releasing both publicly, to be transparent about our research and to encourage the community to make progress on this important topic.

 Conclusion
 Our previous work on behavioral alignment explored how AI assistants match human preferences in everyday social scenarios. In this work , we expand the focus from measuring general behavioral tendencies to evaluating social reasoning .
 By incorporating verifiable signals within simulated environments, we chart a scalable, empirical path toward developing reliable AI. Future work can build on this foundation by modeling longer-term, evolving relationships and multi-party group dynamics, bringing simulated benchmarks even closer to the nuances of real-world human interactions.
