 Meta’s Muse Spark Open now available in Amazon SageMaker JumpStart

 Muse Spark Open, Meta’s coding-optimized open-weight model, is now available in Amazon SageMaker JumpStart , the machine learning (ML) hub of Amazon SageMaker AI . The model was trained on real developer workflows, such as multi-file refactors and long debugging sessions, and it supports a context window of 1 million tokens. You can deploy it to a SageMaker AI endpoint in your own AWS account in a few steps, without managing the serving infrastructure yourself. SageMaker JumpStart offers two variants: BF16 ( Muse-Spark-Open-816B-A42B ) and NVFP4 quantized ( Muse-Spark-Open-816B-A42B-NVFP4 ).

 In this post, we introduce Muse Spark Open and show you how to deploy the model with Amazon SageMaker Studio and the SageMaker Python SDK , send it a first inference request, and clean up.

 Overview of Muse Spark Open

 Meta describes Muse Spark Open as a coding-optimized model trained for agentic coding workflows, with a focus on first-attempt accuracy, tool calling, and understanding of large codebases. It’s a reasoning model, and it accepts text, images, documents, audio, and audio-video as input and returns text.

 Muse Spark Open uses a mixture-of-experts (MoE) architecture with 816 billion total parameters, of which 42 billion are active for each token. The model holds the capacity of a very large network, while the compute it spends on each token is closer to that of a much smaller dense model. Meta releases the weights under the Muse Model License, which includes the Muse Spark Usage Policy.

 Built for long-running coding agents

 Meta trained Muse Spark Open on the way developers work in real repositories: code generation, debugging, multi-file refactors, and tasks that run for a long time. With the 1 million-token context window, the model can take in a whole project, including its dependencies, legacy code, and thousands of files. You don’t need to split a task into smaller pieces to fit the context.

 Meta also designed Muse Spark Open as an agentic model from the start. Meta says the model plans, acts, observes the result, and corrects itself over long horizons, rather than making single tool calls. As a reasoning model, it works through a task before it acts, and the SageMaker AI endpoint returns that reasoning alongside the answer, so you can follow what an agent is doing and why. Meta trained the model to browse the web, coordinate subagents for work that can be split up, and operate computers across desktop, mobile, and browser environments. These are capabilities of the model. On SageMaker AI, your application or agent framework provides the tools, browser, and computer-use environment that the model calls. Beyond code, Meta reports that Muse Spark Open reasons across images, documents, audio, and video.

 Two properties of the model shape how you serve it. First, sparse activation keeps per-token compute low, but serving still requires enough GPU memory to hold all 816 billion parameters, so the instance choice comes down to memory capacity. Second, the NVFP4 variant stores weights in NVIDIA’s 4-bit floating point format, which needs roughly a quarter of the memory of the BF16 weights. On SageMaker AI, that difference decides the instance: the NVFP4 variant runs on ml.p5e.48xlarge , and the BF16 variant runs on ml.p6-b300.48xlarge . That makes NVFP4 the variant to try first when you size for cost. Evaluate it on your own workloads to confirm the quality fits your use case.

 With open weights on SageMaker AI, you also control the deployment. The endpoint runs in your AWS account, so your source code and prompts are processed on infrastructure that you configure and control. You can attach the endpoint to your own Amazon Virtual Private Cloud (Amazon VPC) , encrypt its storage volume with a key from AWS Key Management Service (AWS KMS) , and turn on network isolation for the container. You also choose the instance type and scaling limits, and you pin the model version, so the model only changes when you redeploy.

 Use cases

 You can use Muse Spark Open for a wide range of applications. Meta’s focus on coding and agentic workflows suits it to the following use cases:

 Coding assistants over private repositories : Answer questions about large codebases, refactor them, and debug them with the full project in context, while the code is processed on an endpoint in your account.

 Long-running coding agents : Run agents that plan a change, edit across multiple files, run tests in your own sandbox, and correct course based on the results.

 Multimodal engineering workflows : Turn screenshots, design documents, or a recorded bug report with audio and video into a reproduction plan or a draft fix.

 Announcing DPoP Support for Google OAuth: Securing Refresh Tokens

 OCT. 15, 2026

 Sergei Akulich

 Traditional OAuth bearer tokens operate on a "finders-keepers" model, making them vulnerable to Infostealer malware (e.g. RedLine, NodeStealer) and Adversary-in-the-Middle (AiTM) attacks.
 DPoP (Demonstrating Proof-of-Possession) is an application-layer OAuth 2.0 security profile ( RFC 9449 ) that neutralizes token theft and replay attacks by cryptographically binding tokens to a client-generated asymmetric keypair at the application layer, ensuring that even if a token is stolen, it cannot be replayed without the corresponding private key.
 This article is meant to inform you on where and how to adopt DPoP and describes Google's specific DPoP implementation. A DPoP adoption SKILL.md is also available to help implement DPoP.
 Some optional features and implementation decisions in RFC 9449 are delegated to Google as an authorization provider. Google Identity , and its OAuth Platform , function as a developer-facing service where engineers implement OAuth 2.0 and cryptographic security controls like DPoP to protect API integrations. Separately, Google Workspace Context-Aware Access (CAA) leverages DPoP to secure enterprise AI workloads on the Gemini Enterprise Agent Platform by cryptographically validating agent identities at the Agent Gateway.
 Google's OAuth Platform supports DPoP binding specifically for refresh tokens. This design choice reflects a pragmatic engineering tradeoff: by sender-constraining the long-lived refresh token, we neutralize the primary vector for persistent offline impersonation. Meanwhile, short-lived access tokens remain standard Bearer tokens, ensuring that high-QPS resource APIs do not incur the per-request asymmetric cryptographic verification overhead of DPoP. This approach delivers robust protection for your most sensitive credentials while maintaining the high performance and low latency of Google API integrations.
 Unlike standard Bearer token flows, DPoP requires client-side cryptographic key generation, strict timestamp and nonce handling, specific claim computation (htm, htu, iat, jti), exact header construction, and DPoP proof JWT construction. These changes may introduce additional system constraints to support secure computation, handling, and storage.
 Architectural considerations 
 The IETF’s Best Current Practice for OAuth 2.0 Security ( RFC 9700 ) discusses sender-constrained refresh tokens. Additionally, the OAuth 2.0 for Browser-Based Applications IETF draft discusses three models: Backend-for-Frontend (BFF), Token-Mediating Backend, and Browser-based OAuth Client.
 Following this guidance, Google recommends using DPoP to sender-contrain refresh tokens in these models.
 Unlike transport-layer token binding (e.g., mTLS/RFC 8705) which often breaks or terminates at modern cloud proxies and load balancers, DPoP operates at the HTTP header level. This makes it highly resilient for complex, multi-hop environments, including emerging Model Context Protocol (MCP) and autonomous agent architectures.
 Architectural Deep-Dive: The Performance-vs-Security Tradeoff 
 A common question from security architects is: If DPoP is designed to sender-constrain tokens, why are Google's access tokens still standard Bearer tokens?
 The answer lies in operational scaling and performance at Google's scale. Verifying asymmetric cryptographic signatures (such as ES256) requires significant CPU cycles. If every API call to high-throughput Google resource servers (like Gmail, Calendar, or Drive APIs) required verifying a DPoP proof, the compute overhead at the API Gateway layer would be massive, introducing measurable latency and scaling costs.
 By constraining DPoP binding strictly to the refresh token, Google's architecture achieves a balance:

 Long-Lived Credentials Protected: The highly sensitive, long-lived refresh token (which can be used to obtain new access tokens indefinitely) is cryptographically bound to the client's key pair. If exfiltrated, it is useless to an attacker.
 High-Performance Serving: Short-lived access tokens (typically valid for 1 hour or less) remain standard Bearer tokens. This ensures that the vast majority of API requests incur zero cryptographic verification overhead, maintaining the high performance and low latency developers expect from Google APIs.

 Complementary Protections: DPoP and DBSC 
 DPoP is a powerful tool for securing OAuth 2.0 tokens, but it is important to understand its boundaries.
 DPoP does not protect standard web application session cookies, which remain a primary target for Infostealer malware. To address cookie theft, Google and the Web Incubator Community Group (WICG) are actively developing Device Bound Session Credentials (DBSC) . While DPoP operates at the application layer to secure API tokens for public and confidential clients, DBSC operates at the browser and network layer to cryptographically bind browser session cookies to the device's hardware (such as TPM). Together, DPoP and DBSC form a comprehensive defense-in-depth strategy against credential theft across both API and web-based user sessions.
 Multi-Agent Delegation & Model Context Protocol (MCP) 
 As autonomous AI agents and Model Context Protocol (MCP) architectures emerge, securing tool-use tokens becomes critical. While DPoP is highly resilient in single-hop client-to-server connections, multi-agent workflows (where Agent A delegates a task to Agent B, which calls Resource C) introduce delegation challenges.
 In a multi-agent chain, Agent B cannot sign a DPoP proof on behalf of Agent A without access to Agent A's private key—and sharing private keys violates the core security principles of DPoP. Because Google's core consumer OAuth endpoint (oauth2.googleapis.com) does not support OAuth 2.0 Token Exchange (RFC 8693) , developers building multi-agent or federated cloud workloads should consider Google Cloud Secure Token Service (STS) . By routing delegation through STS, the intermediate agent can exchange the upstream token for a new, short-lived federated token cryptographically bound to its own local key pair, preserving the sender-constrained security model across the entire agent chain without key exposure.

## DFlash 2 Speculative Decoding
This model is ready for inference in DFlash 2 speculative decoding mode. DFlash 2 drafts a block of candidate tokens in a single non-causal forward pass, then uses a pairwise path selector over each position’s top-k candidates. The target model verifies the proposed path so that more than one token can be accepted per generation step. The mean number of tokens emitted per step is the acceptance length.

 Trust in Depth: Giving agents more autonomy without losing control

 In every conversation I have with enterprise leaders, they say the same thing. They want agents to do more, but they don’t trust them to do it right all the time.

 That’s fair. The same creativity and autonomy that makes agents useful makes them hard to trust. Give an agent a task and it finds its own path to finish it, picking tools and sequencing steps no developer scripted. Run the same task twice and it might take a different route each time. A test that passes today tells you little about what the agent does tomorrow.

 The usual answer is a person in the loop, approving everything the agent does. That works at small scale, but as agents take on more work, human approvals pile up and review fatigue sets in. People asked to check everything stop catching the things that matter. Caution becomes a bottleneck, and agents capable of far more sit idle on the valuable work that could be making more of an impact.

 The fix is to let the agent act on its own when its actions can be verified, and reserve human judgment for the decisions that need it. As agents take on higher stakes work, like financial transactions, a wrong action becomes increasingly harmful. Organizations need the confidence to hand an AI agent important work, knowing it will stay within the limits set, even when no one is watching. That confidence must be built.

 Content filtering, testing, and monitoring each serve an important purpose, but none of these capabilities alone can promise an agent will behave correctly the next time it runs. Trust comes from independent layers that reinforce one another, the same layered discipline the industry has practiced for two decades as Defense in Depth, turned to a new purpose. Where Defense in Depth limits what can go wrong, this expands what you can safely allow. AWS calls it Trust in Depth. 

 Trust in Depth: Trust you can verify 

 You build trust by answering a set of questions at different moments in the agent’s lifecycle:

 Scope, before it runs: What is this agent for, what capabilities does the job require, and what must it never do?

 Know, at deployment: Who authorized it, what identity does it carry, and can you account for every agent acting on your behalf?

 Bound, while it runs: Do its actions stay within the limits you set, and can it still do the job?

 Observe, after each run: Can you reconstruct what the agent did and why, and learn from it?

 Across these questions, some requirements can be expressed as precise rules, while others call for judgment. A company might require that only a manager can approve access, or that an employee’s sign-in must be blocked before their mailbox can be shared. Other expectations, such as keeping a friendly tone or handling a sensitive situation appropriately, depend on context and human judgment.

 For precisely defined rules, testing shows whether the controls work in the cases you anticipate, but an agent takes paths you didn’t. The technology that goes further is automated reasoning, the mathematical logic that checks whether a rule holds in every possible case. It can establish that a rule holds on every path covered by a precise description of the system and its assumptions, or uncover the exact case where it fails.  AWS has run automated reasoning in production for more than a decade , from Identity and Access Management (IAM) at more than 2.1 billion requests per second to critical systems like the AWS Nitro Hypervisor, Amazon S3 Block Public Access, and VPC Reachability Analyzer. Now we are bringing it to agents. Wherever an agent’s rules can be stated precisely, automated reasoning can check them.

Where proof does not apply, limit the agent’s access and actions, evaluate its behavior, and send genuine ambiguity to a person to apply judgment. Grant more autonomy as you establish that the relevant rules are enforced, the agent performs reliably on the task, and failures can be detected and handled.

 Scope your agent to only what the job requires

 Trust begins before an agent runs, and this is where to invest the most effort. Problems caught here are cheap to fix. Scoping means deciding what work the agent owns, which tools, data, and services it may reach, the rules it must follow, and which decisions stay with a person.

 “Resolve the customer’s issue” says what to achieve, not how the agent may act to achieve it. The agent still needs limits on what it may see, what it may do, and when it must stop and ask. Give it only the access its job requires, and no more. Watch for capabilities no one granted on purpose, the ones bundled with a tool or a role.  You can’t govern what you can’t see. Teams are creating agents faster than anyone can track them, and an agent no one knows about is an agent no one controls. Every agent needs its own identity, checked every time it acts. No action should be orphaned. When something goes wrong, you can tell which agent did what, and who authorized it.

Once the agents are known, AgentCore issues each agent its own identity and checks it on every request, so every action traces back to a specific agent operating under a known authority.  Bound what your agent says and does, within the limits you set

Too tight, and it can’t do its job at all. So let the agent choose how to pursue its task but never rely on it to enforce its own limits. Those limits define the agent’s boundaries and belong in the environment around the agent, enforced deterministically and evaluated across the full sequence of actions, not one step at a time.

 A new form of computing

 Every result a computer produces comes with an implicit question: did the program run as claimed and produce correct outputs? Today, answering that question often requires a degree of trust alongside verification. We trust the operator, the vendor, the counterparty, or the agent, and we rely on contracts, audits, and logs to establish that trust.

A program runs, and along with its output it produces a short proof, a cryptographic certificate that this program, on these inputs, produced this output. The proof is small and fast to check. The 1M token context window holds an entire project, including complex dependencies, legacy code, and thousands of files without breaking a task into pieces.  

 As a reasoning model, Muse Spark Open adds audio and video perception alongside image and document understanding, working natively and reliably across what it sees, hears, and reads. NVFP4 checkpoints generated by Meta and optimized for NVIDIA Blackwell Ultra shrink the memory footprint of all 816B parameters with native FP4 Tensor Core acceleration. Fewer bytes moved per token to increase tokens per second per user, and the freed-up memory supports larger KV cache for concurrent long context sessions, delivering higher throughput, a lower cost per token. 

 Custom-built for agentic coding multimodal understanding across text, image, video, and audio  

 General coding models are optimized for single-shot completions such as generating a function, writing a unit test, or suggesting an inline fix. They excel at discrete, well-scoped tasks where the context is small, and the answer is immediate. Agentic coding demands something fundamentally different. Planning a multifile refactor, navigating thousands of files, recovering from failing tests, and coordinating subagents over long horizons requires a model built for sustained, multistep work.  

 Muse Spark Open is built for exactly these workloads, delivering higher first-attempt accuracy, reliable tool calling, and deep codebase understanding across repositories. It plans, acts, observes, and self corrects. It supports multistep task execution with tool use, output evaluation, and iterative refinement. The model uses goal conditioning to hold direction and context compaction to retain the knowledge needed to sustain progress across long-running sessions. With a 1M token context window, it holds an entire project, including complex dependencies, legacy code, and thousands of files without breaking tasks into pieces. 

 Beyond coding, it searches the web (including multimodal browsing), spawns and coordinates subagents for decomposable tasks, and leverages computer use capabilities unified across desktop, mobile, and browser. It generates separate commentary before each action, so developers know what the agent is doing and why.  

 The model’s 1.8B perception encoder natively processes interleaved text, images, video frames, and audio without separate pipelines per modality. This means that the model reasons over what it sees, hears, and reads in a single unified pass. This suits developer workflows spanning screenshots, diagrams, error logs, and video walkthroughs within the same agent session. Sparse MoE routing activates only 42B of 816B total parameters per token, delivering frontier agentic capability at a fraction of the serving cost of dense models at equivalent scale.

 Muse Spark Open optimized performance on GB300 NVL72  

 The NVIDIA GB300 NVL72 features a rack scale architecture that integrates 72 NVIDIA Blackwell Ultra GPUs into a single platform. Its large, 72-GPU NVIDIA NVLink domain enables efficient communication at 130 TB/s, eliminating bottlenecks that appear when expert traffic must cross traditional off-the-shelf networks. For a sparse MoE model like Muse Spark Open, which routes each token to eight of 256 experts, that bandwidth directly determines how much of the theoretical throughput a deployment realizes. 

 Agentic workloads turn static single-turn interactions into multistep workflows that reason, invoke tools, coordinate subagents, and carry growing context from one turn to the next. Out of the box, Muse Spark Open running agentic workloads on NVIDIA GB300 NVL72 delivers up to 50K per second per GPU and up to 600 tokens per second per user, enabling AI factories to run large parameter models in production at high throughput and low latency.

 Flexible deployment options for Muse Spark Open  

 NVIDIA supports multiple inference stacks to meet a variety of developer needs. SGLang, vLLM , and TensorRT LLM give developers direct control over serving configuration, parallelism, and batching on the NVIDIA accelerated computing platform. TensorRT LLM adds compiled engines tuned for NVIDIA GPUs. NVIDIA Dynamo publishes deployment recipes for all three, and separates prefill from decode across dedicated GPU pools, so compute bound prompt processing doesn’t slow token generation. Its KV cache-aware routing sends each request to the worker already holding the relevant prefix, avoiding precomputation as context accumulates across long agentic sessions. 

 Post-train Muse Spark Open with NeMo AutoModel and Megatron Bridge  

 Developers can post-train Muse Spark Open on domain specific datasets using NVIDIA NeMo AutoModel , a PyTorch native training library with native Hugging Face checkpoint support and no model conversion required. It enables full SFT and LoRA fine tuning out of the box, optimized for rapid experimentation over a wide variety of industry specific cases. 

 Developers can also leverage NVIDIA Megatron Bridge  to convert Hugging Face checkpoints to Megatron format when they are ready for large production-scale training to take advantage of the optimizations.

 Get started with GPU-accelerated Muse Spark Open  

 To get started, download Muse Spark Open NVFP4 weights from Hugging Face. For production deployments, try the downloadable NVIDIA NIM . The NIM reduces setup to a single command, replacing benchmarking and tuning cycles with a container that automatically selects the best serving backend and precision for the detected hardware.
