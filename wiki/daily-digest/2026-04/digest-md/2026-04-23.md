## The Big Picture

The week of April 21–23 will likely be remembered as the week the industry stopped talking about chat interfaces. Kimi K2.6 ran for five days. OpenAI's Agent Studio targets persistent agents living inside Slack. Anthropic's Conway containerizes always-on execution environments. Three separate teams arrived at the same architectural bet — AI as infrastructure rather than tool — without coordinating on it. When three major players independently converge on the same paradigm in the same week, the paradigm is no longer speculative.

But the convergence reveals a gap more than it resolves one. The technical capability exists. A 1.7B model can run a 10-hour post-training loop (ml-intern, 04-22). A swarm of 300 sub-agents can coordinate 4,000 steps over five days. What doesn't exist is the trust infrastructure to deploy these systems on problems that matter. Four peer-reviewed medical studies in a single week reached the same conclusion: current LLMs, deployed without structured interaction protocols, fail at clinical reasoning in ways that would get a human clinician fired. That's the baseline the industry is asking to run autonomously for five days.

The permission system analysis adds a systems-engineering dimension to this. Claude Code's classifier approach is adaptive but carries unknown false-negative rates on novel inputs. Hermes' regex approach is auditable but brittle. Both were designed for single tool calls. Neither has been stress-tested at Kimi K2.6's coordination scale. The approval bottleneck — in Claude Code's coordinator mode or Hermes' threading lock — could become the throughput ceiling for multi-day agents.

The Anthropic Mythos breach closes the loop with uncomfortable symmetry: the model specifically designed for cyber defense was accessed through a third-party environment. If Mythos can be breached through a container-equivalent, Hermes' "container bypass = trust" assumption is exactly wrong at the attack surface that matters most.

### Persistent Agent Infrastructure: Kimi K2.6, Agent Studio, Conway

> Five days, 300 sub-agents, 4,000 steps — and nobody has benchmarked what happens when one sub-agent fails mid-task.

**Source:** VentureBeat / TestingCatalog  
**Links:** [VentureBeat](https://venturebeat.com/orchestration/kimi-k2-6-runs-agents-for-days-and-exposes-the-limits-of-enterprise-orchestration) · [TestingCatalog](https://www.testingcatalog.com/anthropics-works-on-its-always-on-agent-with-new-ui-extensions/) · [Wiki](../../agentic-systems/2026-04-23-persistent-agent-infrastructure.md)  
**Tier:** 2 — Agents / Agentic Reasoning (Tier 1 intersection: agent trajectory routing)

```
Three architectures for the same problem:

Kimi K2.6:        [Central Orchestrator] → 300 sub-agents → 4,000 steps over 5 days
                   Distributes state management across sub-agents
                   Built a compiler in 10 hours (est. 2 months / 4-person team)

OpenAI Chronicle: [Agent] ← screen activity → [Markdown summaries]
                   Context grounded in user's actual work history
                   Slack-native scheduled workflows via Agent Studio (Hermes)

Anthropic Conway: [Agent] ← containerized env → [versioned Live Artifacts]
                   State managed like software (version history, auto-update)
                   Live Artifacts: dashboards pulling real-time external app data
```

These three architectural bets reflect different diagnoses of the persistent agent problem. Kimi K2.6 bets that distribution solves coherence — each sub-agent manages local state, the orchestrator coordinates globally. OpenAI bets that grounding context in observable user activity reduces hallucinated state — if the agent knows what you actually did (via screen capture), it doesn't need to invent a mental model of your context. Anthropic bets that containerization plus versioning treats agent state the way software engineers treat code — inspectable, rollback-able, isolated.

None of these approaches is obviously right. Kimi K2.6's distributed state has a coordination problem: what happens when two sub-agents modify the same resource? Chronicle's Markdown summaries become their own long-context problem after days of operation. Conway's container isolation is directly tested by the Mythos breach — container boundaries are not impenetrable.

What all three reveal is that current agent orchestration frameworks were not designed for this. LangGraph, DSPy, and CrewAI are request-response systems. Multi-day stateful execution requires session state management, checkpointing, rollback capabilities, and distributed coordination primitives. The infrastructure doesn't exist yet. Kimi K2.6, Agent Studio, and Conway are all building it from scratch — which explains why they're all arriving at slightly different answers.

The specific Kimi K2.6 claim that matters most for the wiki: 4,000 coordinated steps over five days means roughly one decision every 100 seconds. At that rate, any permission pipeline that requires human confirmation becomes a throughput bottleneck immediately. The permission system analysis (Ken Huang, 04-23) shows that neither Claude Code nor Hermes was designed for this scale.

**Why it matters:** The request-response paradigm for AI agents is ending. The infrastructure layer that fills the gap — state management, fault tolerance, coordinated permissions — is what the next 12-18 months of AI infrastructure work will be about.

**Research angle:** The missing benchmark is a multi-day agent reliability evaluation. SWE-Bench measures single-task code generation. We need a "SWE-Marathon" that measures correctness with realistic failure modes across long-horizon tasks. Without it, "5 days, 300 agents, 4,000 steps" is a demo, not a validated capability claim.

### Claude Code vs. Hermes: Two Safety Philosophies

> One uses a classifier that can reason about novel inputs. The other uses patterns that are always auditable. Both fail differently.

**Source:** Ken Huang Substack  
**Links:** [Post](https://kenhuangus.substack.com/p/chapter-4-permission-systems-and) · [Wiki](../../agentic-systems/2026-04-23-claude-code-vs-hermes-permissions.md)  
**Tier:** 2 — Agents / Agent Safety (Tier 1 intersection: agent trajectory routing)

```
Claude Code:           Hermes:
canUseTool pipeline:   DANGEROUS_PATTERNS:
  1. Static rules        1. Normalize (strip ANSI, fullwidth Unicode)
     deny always wins    2. Regex match (30+ patterns)
  2. ML classifier       3. Approval dialog
     2-sec timeout          scope: once / session / always
  3. Interactive dialog     threading lock (concurrent sub-agents)

Multi-agent:           Container bypass:
  coordinator mode       Docker/Singularity/Modal skip approval
  bubble (inherit)       container = trust boundary
```

The core architectural difference: Claude Code's classifier can reason about commands it has never seen. Hermes' patterns cannot. Claude Code will correctly classify a novel jailbreak if it's similar enough to training examples; Hermes will miss it if it doesn't match a pattern. On the flip side, Hermes' pattern list is fully auditable — a security team can read it and reason about coverage. Claude Code's classifier behavior is a black box.

The container bypass in Hermes is the most consequential design choice. It assumes that if you're running inside Docker or Modal, the environment provides sufficient isolation and the tool doesn't need to inspect the commands. That's an architectural bet on the container boundary as a trust primitive. The Mythos breach (04-23) — unauthorized access through a third-party environment — is a direct challenge to this bet. "Third-party environment" is functionally a container-equivalent. If Mythos can be accessed through it, container isolation is not a sufficient trust boundary for high-stakes agent execution.

This analysis directly extends the Claude Code Architecture page (04-19), which documented the overall permission system structure. Ken Huang's deep dive adds the specific classifier racing logic (speculative bash classifier with 2-second timeout), the organizational rule priority ordering, and the threading lock details that weren't in the prior summary.

**Why it matters:** Permission architecture is the last line of defense between a capable agent and a costly mistake. Both systems will face novel attack surfaces at Kimi K2.6-scale deployment. The failure modes are different — knowing which one you're running is a prerequisite for knowing how to audit it.

### Medical LLM Reliability: Four Studies, One Conclusion

> The models have the knowledge. The problem is that they don't know how to ask the right questions.

**Source:** Gary Marcus Substack  
**Links:** [Post](https://garymarcus.substack.com/p/please-dont-trust-your-chatbot-for)  
**Tier:** 2 — LLM Capabilities / Reliability / Evaluation

Four independent peer-reviewed studies — BMJ, JAMA Network Open, two Nature Medicine — landed within the same period and reached the same core finding: LLMs fail at clinical reasoning when deployed without structured interaction protocols, but *not* because the knowledge is absent.

The BMJ study tested five chatbots on 10 medical questions. Nearly half the responses were highly problematic, delivered with confidence and fabricated citations. The JAMA study evaluated 21 models across 29 clinical reasoning questions: "cannot yet be relied on for unsupervised patient-facing clinical decision-making." The first Nature Medicine study found models identified relevant conditions in fewer than 34.5% of cases — no better than a control group. But the same models performed significantly better when guided by trained physicians. The second Nature Medicine study found ChatGPT Health undertriaged 52% of gold-standard emergencies.

The physician-guided finding is the most analytically useful result in this batch. The same model, same knowledge, better outcomes when a doctor structures the interaction. This isolates the problem: LLMs do not know how to conduct a clinical interview. They cannot adaptively probe for the information they need. They don't know what they don't know in a medical context.

This is not a capability gap — it's an interaction design problem. The solution is not a smarter model. It's a structured agent loop that follows a clinical protocol before generating any diagnostic suggestion. The connection to agent infrastructure (04-23) is direct: if we cannot trust current LLMs to ask the right follow-up questions in a single medical consultation, we certainly cannot trust persistent agents to make correct judgment calls over multi-day autonomous operation.

The 52% undertriage rate for emergencies is the most consequential individual number. Overtriage wastes resources; undertriage costs lives. Any deployed medical AI system needs explicit safeguards against false negatives — a systematic bias toward caution rather than confidence.

**Why it matters:** Four journals, four research groups, one conclusion. The confluence makes this unusually strong evidence for a specific mechanism: LLM confidence is decorrelated from accuracy when the model lacks structured probing protocols.

### Distributed Systems Thinking Meets AI Infrastructure

> Kleppmann's second edition arrives just as persistent agents need everything it teaches.

**Source:** Pragmatic Engineer Podcast  
**Links:** [Post](https://newsletter.pragmaticengineer.com/p/designing-data-intensive-applications)  
**Tier:** 2 — Infrastructure / Agent Systems

Martin Kleppmann's interview on DDIA second edition is not obviously an AI story. It's framed around databases and distributed systems. But every principle he names maps directly to persistent agent infrastructure.

Three specific observations that land differently when read against Kimi K2.6 and Conway:

**Replication beats sharding now**: modern machines are large enough that most workloads fit on a single node. The distributed systems problem has shifted from "how do you shard data across machines" to "how do you replicate state for fault tolerance." A multi-day agent that fails at step 3,800 needs its state replicated somewhere it can restart, not just a faster machine.

**Serverless for scale-down**: bursty AI traffic makes scale-down as important as scale-up. A persistent agent that's idle for four hours between tasks should not hold compute at idle cost. Serverless architectures handle this. The Conway container approach maps naturally to serverless container-based execution.

**LLM-powered formal verification**: two trends are converging — LLMs generate too much code for human review, and LLMs are getting good at writing formal proofs. Together, this could make formal verification mainstream. Applied to agents: if Kimi K2.6 builds a compiler in 10 hours, who verifies the output? An agent that generates code + an agent that verifies it against a formal spec is the only path to scalable quality assurance.

Kleppmann doesn't mention AI agents directly. He doesn't need to. DDIA was written for databases and message queues. Its principles — replication for fault tolerance, consistency guarantees, design for failure — apply unchanged to persistent agent state.

**Why it matters:** The Kleppmann interview is a useful forcing function: if you cannot describe your persistent agent's consistency model, failure mode, and state replication strategy, you don't understand your own system.

## Worth Watching

- **Multi-day agent reliability benchmark** — "SWE-Marathon" doesn't exist yet. Kimi K2.6's five-day compiler demo is not a validated benchmark — it's a demo. Watch for a serious multi-day, multi-step correctness evaluation with realistic failure modes. This is the most important missing piece in the persistent agent story.

- **Trainium2 actual performance numbers** — Anthropic committed $100B to AWS with Trainium2 as the training substrate. The competitive performance of Trainium2 against H100s for transformer workloads is unverified at scale. If it delivers, the inference serving economics for anyone using Claude API change materially. Watch for Anthropic infrastructure cost benchmarks in Q3 2026.

- **Hermes container bypass in multi-day agents** — Kimi K2.6 and Conway both rely on container-based isolation. The Mythos breach demonstrates that container-equivalent boundaries can be compromised. Will Hermes update its container trust assumption, or will they add an additional verification layer for long-running agents? Watch for a v2 of the Hermes permission architecture.

- **LLM-powered formal verification** — Kleppmann flagged this as the emerging solution to AI-generated code review. Two prerequisites: LLMs that can write formal proofs reliably, and proof checkers that can verify them automatically. The first prerequisite is borderline met (o3 and Claude Sonnet 4.6 can write Lean proofs for constrained problems). The second is mature (Lean 4, Isabelle). Watch for a serious production deployment of verify-then-merge in a major codebase.
