## The Big Picture

The routing question is getting answered at three levels simultaneously, and this week makes the convergence visible. At the **step level**: the step-level optimization paper builds an event-driven cascade inside a computer-use agent — a small model runs by default, learned monitors escalate to the frontier model at exactly the steps that need it. At the **turn level**: Ken Huang Ch 14 maps how Claude Code and Hermes handle provider selection, fallback chains, and per-turn cheap-model routing in production harnesses. At the **product level**: Anthropic shipped a `/model` flag in Claude Code so users can dynamically route tasks across models by latency, cost, or capability. Three layers, one week, one convergent answer: adaptive, context-sensitive routing is how AI systems will manage inference cost at every granularity.

The May 1 digest's Worth Watching item — "trajectory-aware multi-model router crossing 70% on Claw-Eval-Live (90 days)" — already has a candidate mechanism. The step-level optimization paper is precisely that: it uses the agent's execution trajectory (reasoning-action sequences) to decide which model to invoke per step. It hasn't been tested on Claw-Eval-Live yet, but the plumbing is in place. The 90-day clock is ticking.

The second thread is safety as an unstable lifecycle property. Safety Drift shows that benign fine-tuning produces large, contradictory changes in safety across 100 models — improvement on one benchmark while degrading on another, simultaneously, from the same fine-tuning run. The implication: every organization deploying a fine-tuned variant of a safe base model is running an experiment they haven't evaluated. Pair this with FlashRT (today), which democratizes optimization-based red-teaming from 264GB/1 hour down to 65GB/10 minutes, and the picture is clear: the attack-defense gap is closing from both ends. The offense tooling is getting cheaper; the safety guarantee is already weaker than assumed.

### Step-Level Optimization for Efficient Computer-Use Agents

> Frontier agents call large multimodal models at nearly every GUI step. Most steps are routine. Two failure modes cluster at specific junctures: progress stalls and silent semantic drift. A learned cascade catches both — without retraining anything.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2604.27151) · [Wiki](../../ai-routing/2026-05-02-step-level-optimization-computer-use-agents.md)
**Tier:** 1 — agent trajectory routing

```
GUI agent trajectory:
  Step 1–2: routine → small model (cheap)
  Step 3: [Stuck Monitor: loop detected] → escalate to frontier model
  Step 4–6: routine → small model
  Step 7: [Milestone Monitor: objective checkpoint] → escalate to frontier model
  Step 8–N: routine → small model
  
Result: frontier model invoked only at high-risk junctures
        no architectural changes, no retraining required
```

The key insight is that computer-use agents don't fail uniformly. Progress stalls happen when the agent loops or fails to advance — the Stuck Monitor tracks degraded progress from reasoning-action sequences. Silent semantic drift is subtler: the agent continues taking contextually plausible actions after diverging from the user's actual objective — the Milestone Monitor catches this by flagging semantically significant checkpoints for verification. Two learned systems, two failure modes, one cascade.

The "modular, no-retraining required" claim is the practical lever. You don't need to rebuild the underlying agent — you bolt the monitors on top. This means the framework can wrap existing Claude Code, Hermes, or any other harness. The immediate follow-up experiment writes itself: evaluate this cascade on Claw-Eval-Live (May 1), where no single frontier model reaches 70% on real workflow tasks. The task-family discrimination that Claw-Eval-Live exposes is exactly the calibration data the Milestone Monitor would use.

This fills the gap the May 1 agent-eval cluster opened. Six benchmarks (OccuBench, GTA-2, DR3-Eval, PRL-Bench, Claw-Eval-Live, InteractWeb-Bench) all reported frontier-agent failure rates above 30%. The bottleneck was identified as trajectory-aware routing. This paper is the first concrete mechanism for it in computer-use agents.

**Why it matters:** If this cascade can push a computer-use agent past the 70% threshold no single model reaches, it's the architecture pattern for the next generation of reliable agents — not a better base model, but smarter allocation of expensive compute.

**Research angle:** Two open questions. (1) Monitor reliability over long horizons — Stuck Monitor tracks reasoning-action sequences; how does it hold up at step 50+ when context is large? (2) KV cache composition — if escalated frontier-model calls reuse prefix KV cache from earlier small-model steps, escalation cost drops significantly. No paper has measured this interaction.

### Ken Huang Ch 14: Model Routing and Provider Abstraction

> Claude Code bakes routing into TypeScript at compile time — four providers, one fallback model, static selection rules. Hermes treats routing as a runtime concern — API format auto-detection, ordered fallback chains, live context-window discovery, per-turn cheap-model routing. `stripSignatureBlocks` is the subtle production detail most hand-rolled implementations miss.

**Source:** Ken Huang / Agentic AI Substack
**Links:** [Post](https://kenhuangus.substack.com/p/chapter-14-model-routing-and-provider) · [Wiki](../../ai-routing/2026-05-01-ken-huang-ch14-routing-provider-abstraction.md)
**Tier:** 1 — LLM routing, production harness architecture

```
Claude Code (compile-time):          Hermes (runtime):
  4 providers resolved at startup      API format auto-detected from URL
  getRuntimeMainLoopModel():           Ordered fallback chain (list)
    plan mode → lighter model          fetch_model_metadata():
    context >200K → larger model         OpenRouter, 1hr TTL cache
  Single fallback model                switch_model(): in-place, live
  FallbackTriggeredError →             choose_cheap_model_route():
    stripSignatureBlocks()               per-turn, conservative
    retry with fallback                  160 char / 28 word limits
```

The `stripSignatureBlocks` detail is load-bearing. Extended thinking produces cryptographically signed blocks that are model-specific — replaying a conversation with signed blocks to a different model triggers API rejections. Claude Code strips them automatically before the fallback retry. Most hand-rolled fallback implementations never handle this, causing cryptic errors when switching providers mid-conversation.

Hermes's smart routing function is intentionally conservative. It routes a query to a cheaper model only if it's under 160 characters, under 28 words, has no code blocks, no URLs, and no complexity-signal keywords (debug, implement, analyze, docker). The design principle: a false negative (simple query → expensive model) costs cents; a false positive (complex query → cheap model) costs analyst time. Asymmetric cost means conservative routing is always correct.

This is the third chapter in Ken Huang's cross-harness series (Ch 8: memory, Ch 13: MCP, Ch 14: routing). The pattern across all three is now fully legible: Claude Code is minimal-by-design with safety delegated to humans; Hermes is first-class runtime subsystems with safety delegated to scanners and sanitizers. Both are internally coherent threat models for different deployment contexts.

The MCP server selection gap surfaces explicitly in Ch 14: when 10 servers expose overlapping capabilities, today the agent picks "whichever first." That's a routing problem — latency-aware, cost-aware, capability-coverage-aware. Ch 13 was about session management; Ch 14 names MCP routing as the next open thread.

**Why it matters:** This is the most detailed public map of production routing infrastructure available. New harnesses can pick which tradeoffs to inherit from each design. The two-level composition — turn-level smart routing (Hermes) + step-level cascade (step optimization paper above) — has never been measured together.

**Research angle:** Two-level routing composition: Hermes routes at the turn level (query complexity), the step-level paper routes within the trajectory (execution state). Stacked on the same agent, the interaction effects could be nonlinear — a query that passes the cheap-model threshold might still trigger a Milestone Monitor escalation mid-trajectory. The cross-level interference is uncharacterized.

### Compliance vs Sensibility: Reasoning Controllability in LLMs

> Force a model to use "wrong" reasoning for a task. It ignores you — and still gets the right answer, using internalized parametric memory. The bigger surprise: reasoning types are linearly encoded in middle-to-late layers, and mechanistic interventions increase compliance by 29%.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2604.27251) · [Wiki](../../llms-foundation-models/2026-05-02-compliance-vs-sensibility-reasoning-controllability.md)
**Tier:** 2 — LLM mechanistic interpretability, reasoning

Models have internalized reasoning patterns (inductive, deductive, abductive) so deeply during pre-training that instruction-level override mostly fails. When you force a model to use an unnatural reasoning type for a task, it continues using the task-appropriate pattern — and still performs well, because the output comes from parametric memory, not instruction-following. The pattern scales with model size: larger models are *more* likely to override the instruction.

The practical implication is uncomfortable: prompts that mandate a specific reasoning approach ("reason deductively," "use first principles") may be silently ignored. The model produces a convincing output using a different internal path. This matters for RAG pipelines and structured prompting workflows that assume reasoning-type compliance.

The linear encoding finding is the research hook. Reasoning types are cleanly separable in the residual stream at middle-to-late layers (approximately layers 16–24 in the tested models). This means targeted mechanistic interventions can boost compliance by 29% — not by changing prompts, but by steering the representation directly. It's the same family of finding as emotion directions and factuality directions in interpretability research, now extended to reasoning mode.

**Why it matters:** Any fine-tuning or alignment approach that only optimizes output behavior is fighting the wrong layer. The reasoning-type representation is upstream.

### Safety Drift After Fine-Tuning

> 100 deployed models analyzed. Benign domain-specific fine-tuning causes large, heterogeneous, contradictory safety changes — improving on some benchmarks while degrading on others, simultaneously, from the same run. Base-model safety evaluations predict nothing about the fine-tuned variant.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2604.24902) · [Wiki](../../llms-foundation-models/2026-05-02-safety-drift-fine-tuning-high-stakes.md)
**Tier:** 2 — safety, deployment risk

The finding is stark: safety is not a stable property. A model that passes every safety benchmark at the base can degrade on specific safety dimensions after benign medical or legal fine-tuning — not because of adversarial intent, but because the fine-tuning distribution shifts the model's internal representations in ways that happen to trade off safety properties against each other.

The "contradictory" framing is the key word. This isn't just degradation — it's improvement on some metrics *simultaneously with* degradation on others from the same fine-tuning run. That means there's no single "safer fine-tuning" recipe; the changes are domain-specific and unpredictable without direct evaluation of the fine-tuned variant.

**Why it matters:** The current deployment norm — evaluate the base model, approve all derivatives — is empirically broken. Every fine-tuned medical, legal, or financial variant in production carries an uncharacterized safety profile. This pairs directly with FlashRT's democratization of red-teaming tooling: the attack tools are now cheap enough that post-fine-tuning red-teaming should be the default, not the exception.

## Connecting the Dots

```
THREE-LEVEL ROUTING CONVERGENCE THIS WEEK:
─────────────────────────────────────────
Step level:   Step-level optimization (trajectory history → escalate)
Turn level:   Ken Huang Ch 14 (query complexity → cheap model)
Product level: Claude Code /model flag (user-directed task routing)

All three answer: "when should the system use cheap vs expensive compute?"
None have been composed in a single agent yet.
```

The routing convergence is the headline. The step-level paper provides an intra-trajectory mechanism (escalate when monitors fire). Ch 14 provides a per-turn mechanism (route cheap when query is simple). Anthropic's `/model` flag provides a user-directed mechanism (choose per task explicitly). Stacked on the same agent, these three layers could compose multiplicatively — or interfere. The paper that measures all three on a single benchmark sets the new baseline.

**Safety cluster forming:** Three sources this week establish that the safety lifecycle is broken at the deployment layer. Safety Drift shows benign fine-tuning causes unpredictable safety regressions. GPT-5.5 shows frontier offensive capability is now broadly available (not gated like Mythos). FlashRT makes optimization-based red-teaming affordable for academic researchers. The natural composition: post-fine-tuning red-teaming with FlashRT should be the default practice for any organization deploying a fine-tuned variant, but almost nobody does it today.

**ViPO + Semi-DPO: same root cause, different cures.** Both papers published the same day diagnosing multi-dimensional preferences collapsed to binary labels as the root of conflicting DPO gradients. ViPO solves it by collecting better-quality data (1M pairs, balanced distributions). Semi-DPO solves it by treating conflicting pairs as noisy unlabeled data and pseudo-labeling them. The long-run fixed point is the same: clean, multi-dimensional preference data trains to the same result as standard DPO. The more interesting question they raise together: what does "high quality preference data" look like for reasoning tasks (not just visual quality), and does the same n-of-2 convergence hold there?

**Ken Huang routing series now complete:** Ch 8 (memory), Ch 13 (MCP session management), Ch 14 (model routing). The three chapters together constitute the most complete public map of production agent harness design. The cross-chapter pattern is clear: Claude Code trades runtime flexibility for predictability (compile-time resolution, static rules, TypeScript safety guarantees); Hermes trades simplicity for runtime power (live metadata, in-place model switching, fallback chains). A third harness that takes Claude Code's safety model but Hermes's routing flexibility has not been built yet.
