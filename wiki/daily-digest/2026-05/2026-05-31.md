## The Big Picture

Strip out the carryover and today is small, but the new papers rhyme. Two of them are about not discarding work that is already partly correct. RePoT keeps the verified prefix of a failed plan and asks the model to fix only the tail; In-Writing keeps the reasoning intact by refusing to impose output structure until the model signals it is ready. Both are reactions against the same wastefulness: one-shot Program-of-Thought throws away every correct step before the first bad one, and constrained-from-the-start decoding throws away reasoning quality to guarantee a parseable format. The fix in both cases is sequencing rather than all-or-nothing, recover from the last good state, or commit to structure only after thinking is done.

The second rhyme is LLM systems improving LLM systems through structured diagnosis. RPT has an LLM optimizer call a diagnostic function over the whole evaluation set, summarize recurring failure modes, and edit the prompt against that failure history. "Discovering Cooperative Pipelines" pushes the same idea up a level: an outer-loop researcher agent reads and rewrites the inner pipeline's prompts and feedback functions, and, tellingly, only injects an explicit fairness mechanism when the welfare objective is Rawlsian maximin, a mechanism absent from its own instructions. Both replace human intuition with a structured, memory-grounded diagnostic loop, and both are early evidence that the interesting unit of optimization is moving from the prompt to the pipeline.

The third thread is older and showed up again in CoHyDE: stop freezing one half of a system while tuning the other. Standard tool retrieval either fine-tunes a dense encoder (great on surface-matching queries, useless on vague ones) or bolts a frozen LLM onto it for query expansion (robust to vague queries, harmful to well-formed ones). CoHyDE co-trains both so they cooperate, which is the same move PANDO made on 05-30 (a skill library updated during the rollout it is evaluated on) and that CollectionLoRA makes today (distilling 50 teacher LoRAs into one with dual-stream routing instead of stacking adapters). The pattern worth naming: the cheap component and the expensive component do better trained as one co-evolving system than wired together after the fact.

## Deep Dives

### RePoT: recover a failed plan from the last verified step

> When a Program-of-Thought plan hits one bad action, the usual move is to throw the whole trajectory away. RePoT keeps the verified prefix and fixes only the tail, for at most one extra LLM call, and routes between repair and retry because the right move depends on how strong the model is.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2605.30052) · [Wiki summary](../../agentic-systems/2026-05-31-repot-recoverable-program-of-thought.md)

```
PoT (brittle):  LLM ─► Python plan ─► run ─► first invalid action ─► whole trajectory dead ✗
RePoT:          LLM ─► plan ─► deterministic replay → verified prefix [step1..K ✓ | K+1 ✗]
                          ─► ONE LLM call resumes from verified prefix ─► success
                          (cost ≤ 1 extra call, only on the ~14% where PoT fails)
Adaptive RePoT: long verified prefix ─► SUFFIX REPAIR ; short prefix ─► FRESH RETRY
```

**What is it about?**
Program-of-Thought (PoT) has an LLM emit a Python program that prints a plan of primitive actions. One invalid action silently kills the whole plan. RePoT adds a deterministic environment replay that walks the plan to its first invalid step, then makes one LLM call to resume from that verified prefix.

**What problem does it solve?**
One-shot PoT has no graceful failure: a single bad action discards every correct step before it, and a naive retry re-pays for the whole trajectory. The field's default recovery signal has been an error string ("that failed, try again"), which the paper's controlled Derail-550 benchmark shows is almost useless (recovery ≤3.1%).

**What is the core novelty?**
Separating *deterministic verified replay* (a non-LLM environment walk that localizes the exact first failure) from *one LLM repair call* (resume from the verified prefix). Derail-550 proves the load-bearing signal is the checkpoint *state*, not the specific suffix text. Adaptive RePoT then routes between suffix-repair and fresh-retry on verified-prefix length, because the right recovery move is capability-dependent.

**Key takeaways**
- **+3 to +11 pp over PoT** across four closed-model configs on PuzzleZoo-775; peak **96.9% vs 86.3%** on gpt-5.4-mini-medium.
- Cost is **at most one extra LLM call**, only on the ~14% of problems where PoT fails.
- vs matched-budget retry: wins decisively on Gemini, ties GPT-medium/Claude, **loses on GPT-mini**, a clear capability-scaling pattern.
- Derail-550: checkpoint-information conditions clear ≥30% (GPT-medium) / ≥70% (Gemini) vs ≤3.1% for error-only feedback.

**Gaps in the study**
The capability-dependence is reported but not solved: Adaptive RePoT is preliminary and rule-based, and because RePoT *hurts* the weakest model the dispatcher is required, not optional. Evaluation is on planning/puzzle environments with crisply-defined valid actions; transfer to open-ended tool-use agents, where transitions are not cleanly verifiable, is untested.

**Industrial implication**
For agent stacks that emit executable plans, deterministic checkpoint replay is a near-free reliability layer, one repair call on the small fraction of runs that fail. But it has to be gated by a capability-aware dispatcher, because applying repair to a weak model makes things worse, which turns "which recovery strategy" into a real routing decision rather than an always-on feature.

### In-Writing: think first, constrain later

> Constrained decoding guarantees a parseable format but, applied from token one, it interrupts reasoning. In-Writing reasons free-form first and only switches on the grammar after a trigger token, gaining up to 27% over naive generation in a single call.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2601.07525) · [Wiki summary](../../llms-foundation-models/2026-05-31-in-writing-think-before-constraining.md)

```
Constrained-from-start (bad): [CONSTRAIN ▓▓▓▓▓▓▓] ← grammar clamps token 1, reasoning crippled
Free-form (unverifiable):     [ reason freely ........ ] ← no structure, hard to parse
In-Writing (one call):        [ free-form reasoning ... ] ⟨TRIGGER⟩ [ CONSTRAINED output ]
                                  trigger-token strategy prevents PREMATURE triggering
```

**What is it about?**
A hybrid decoding framework. The model reasons in free-form text, then a trigger token flips it into structured (grammar- or schema-constrained) decoding, decoupling the reasoning phase from the formatting phase inside one generation call.

**What problem does it solve?**
Production needs machine-parseable output but also needs the model's full reasoning to get the answer right, and the two have been in conflict. Turn the grammar on early and reasoning degrades; leave it off and you need brittle post-hoc extraction. In-Writing sequences the two instead of forcing them at once.

**What is the core novelty?**
Trigger-token strategies that "virtually eradicate" premature triggering, the failure where constrained decoding clamps down while reasoning is still in progress. Prior hybrids either made two separate calls or accepted that early constraints hurt reasoning; In-Writing makes the phase transition a triggered event inside a single decode.

**Key takeaways**
- Single-call hybrid: free-form reasoning then constrained decoding after a trigger token.
- Trigger strategies **virtually eliminate premature triggering**.
- Up to **+27% accuracy over natural generation** across classification and reasoning tasks.
- Code released (Nokia Bell Labs).

**Gaps in the study**
The +27% is measured against unstructured free-form output, not against a strong two-call reason-then-format pipeline, so the gain over good engineering is less clear. Evaluation uses relatively simple structured targets; whether the single switch holds for deeply nested schemas (where premature triggering has more chances to fire) is untested.

**Industrial implication**
Structured output without sacrificing reasoning, in one call, is directly useful for any agent that must emit JSON or a fixed label set while still reasoning hard. It is a cleaner alternative to the tool-use-forcing mechanism that Claude Code and Hermes both rely on (Ken Huang Ch 15, 05-02), and it removes a class of post-hoc parsing failures.

### CoHyDE: co-train the rewriter and the encoder for tool retrieval

> Tool retrieval breaks on the gap between colloquial queries and technical API names. Fine-tuned encoders nail well-formed queries and collapse on vague ones; frozen-LLM expansion does the opposite. CoHyDE trains both as one loop so they cooperate.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2605.29271) · [Wiki summary](../../agentic-systems/2026-05-31-cohyde-cotrain-rewriter-encoder-tool-retrieval.md)

```
Encoder fine-tune : great on surface-matching queries, COLLAPSES on vague ones
Frozen-LLM HyDE   : robust to vague queries, HURTS well-formed ones (catalog-unaware)
CoHyDE (co-evolve, both warm-started on the catalog):
   rewriter ─► catalog-style hypothetical desc ─► encoder retrains (InfoNCE)
        ▲                                              │
        └──── DPO against retrieval scores ◄───────────┘   × 3 rounds
```

**What is it about?**
Tool retrieval (picking the right API from a large catalog for an agent query) over a ~10k-tool ToolBench subset. CoHyDE trains a dense encoder and an LLM query rewriter together: the encoder learns on the rewriter's catalog-style hypothetical descriptions, the rewriter is DPO-aligned against the encoder's retrieval scores.

**What problem does it solve?**
Users write vague, colloquial queries; catalogs use technical API vocabulary; no fixed encoder bridges both. The two standard fixes each fix one half of the query distribution and break the other. CoHyDE makes the halves cooperate.

**What is the core novelty?**
Treating the rewriter and encoder as one jointly-trained, co-evolving system with a closed feedback loop, rather than bolting a frozen LLM onto a fixed encoder. Warm-starting both on the catalog before the loop keeps the co-evolution from drifting.

**Key takeaways**
- **+2.5 pp NDCG@5 on standard queries, +6.3 pp on held-out vague queries** over the strongest single-component baseline.
- Up to **+8 pp on the hardest vague tier**.
- Ablations: either component alone loses by up to 8 pp on vague queries, **co-training is the ingredient**.
- Three rounds; encoder InfoNCE on rewriter output, rewriter DPO on retrieval scores.

**Gaps in the study**
Tested on one ~10k-tool subset; stability on catalogs 10x larger (where the rewriter could drift faster than the encoder adapts) is untested, and convergence-versus-oscillation over rounds is not analyzed. Training cost versus a one-shot encoder fine-tune is not reported.

**Industrial implication**
As agent tool catalogs grow into the thousands, retrieval decides whether the agent even sees the right tool, so this is upstream of every tool-selection router. The unanswered cost question (co-training is more expensive than a single fine-tune) is what decides whether it ships.

### RPT: optimize the prompt against the whole failure history

> Most auto-prompting reacts to one example at a time and never sees the systematic failure. RPT diagnoses recurring failure modes across the entire evaluation set, keeps a memory of prior reports, and edits the prompt against that history, up to +12.9 points.

**Source:** HuggingFace Daily Papers
**Links:** [Paper](https://arxiv.org/abs/2605.21781) · [Wiki summary](../../llms-foundation-models/2026-05-31-reflective-prompt-tuning-function-calling.md)

```
Prior auto-prompting: react to one example / small batch ─► local critique (misses patterns)
RPT (function-calling reflective loop):
   LLM optimizer ─► diagnostic_fn(prompt) over the WHOLE set ─► structured failure report
        ▲                                 │
   revise prompt ◄── memory of prior reports ◄──┘   (+ calibration-aware selection)
```

**What is it about?**
Automated prompt optimization that mimics a human prompt engineer. An LLM optimizer calls a diagnostic function that evaluates the target model over the entire optimization set, summarizes recurring failure modes into a structured report, and revises the prompt using that report plus an accumulated memory of prior reports.

**What problem does it solve?**
Prompt design is brittle and labor-intensive, and existing automated methods optimize myopically (candidate search or per-example critique), so they fix the example in front of them without noticing that the prompt systematically mishandles, say, multi-hop questions. RPT targets the recurring pattern instead.

**What is the core novelty?**
Using LLM function-calling to run the whole-set-diagnostic-plus-memory workflow, and a confidence-aware variant that folds calibration signals into both the diagnostics and the final prompt selection, which is why RPT improves calibration and not just accuracy.

**Key takeaways**
- Diagnostic function aggregates failures over the **entire optimization set** into structured reports, not per-example critiques.
- **Accumulated memory of prior reports** grounds each revision in failure history.
- Up to **+12.9 points** over the initial prompt across three reasoning tasks; competitive with SOTA.
- **Improves confidence calibration**; largest gains on multi-hop and mathematical reasoning.

**Gaps in the study**
Evaluating the full set every iteration is expensive and the compute cost versus candidate-search or small-batch critique is not reported, so the gain's price is unclear. Three reasoning tasks is a narrow base, and gains concentrate where failures are systematic and nameable.

**Industrial implication**
For teams hand-tuning prompts, a diagnostic-driven optimizer that also improves calibration is directly useful, and the calibration gain makes it composable with confidence-based routing (escalate only when the tuned prompt's calibrated confidence is low). Whether it beats cheap candidate search at matched compute is the deciding question.

## Connecting the Dots

The clearest pattern among today's genuinely new papers is "don't destroy partially-correct work," and two papers express it at different layers. RePoT (recover a failed Program-of-Thought plan from its last verified checkpoint, one repair call) protects a partially-correct *trajectory*; In-Writing (reason free-form, then constrain only after a trigger token) protects partially-complete *reasoning* from being clamped by an early format constraint. Both reject the all-or-nothing default, one-shot PoT discards every correct step before the first error, and constrained-from-start decoding discards reasoning quality for a parseable format, in favor of sequencing. It is the same instinct that runs through the wiki's KV-eviction work (keep the tokens that matter, evict the rest) and the on-policy-distillation thread (the Extrapolation Cliff's verified-prefix warm-start): preserve the verified part, spend effort only on what is actually broken.

A second connection runs from RPT to "Discovering Cooperative Pipelines," and it is about LLMs improving LLM systems through structured diagnosis. RPT's optimizer calls a diagnostic function over the whole set, builds a failure-mode report, and edits the prompt against an accumulated memory. The cooperative-pipelines paper does the same thing one level up: an outer-loop researcher agent rewrites the inner pipeline's prompts, feedback functions, and helper code, and only injects a fairness mechanism under the Rawlsian-maximin objective, a mechanism that appears nowhere in its own instructions. Both are versions of a structured, memory-grounded loop standing in for human engineering intuition, and together they suggest the optimization target is migrating from the prompt to the pipeline. RPT's calibration-awareness also ties into the confidence-as-signal thread the wiki has been building (Conf-KV's confidence-driven cache budget, BeliefTrack's belief-state rewards, both 05-30): confidence is increasingly something to optimize, not a byproduct.

The third thread is "co-train, don't freeze," and CoHyDE is its newest instance. Standard tool retrieval freezes either the encoder or the LLM and tunes the other, and each choice breaks half the query distribution; CoHyDE co-trains them so the rewriter learns to produce hypotheticals the encoder can use and the encoder learns to embed them. This is the same architectural move as PANDO (05-30, a skill library updated during the rollout it is evaluated on) and CollectionLoRA (today, 50 teacher LoRAs distilled into one with probabilistic dual-stream routing rather than stacked adapters). Three papers in two days choosing joint co-evolution over after-the-fact wiring is enough to call it a pattern: the cheap component and the expensive component do better as one system.

## Worth Watching

- **A learned RePoT dispatcher appears within 90 days** — Adaptive RePoT routes repair-vs-retry on a hand-tuned prefix-length rule, and because repair *hurts* weak models the routing decision has real downside. Expect a learned router (features: prefix length, model identity, difficulty estimate) that recovers the per-model optimum. Falsifies if checkpoint-repair is shown to be uniformly safe across model strengths, removing the need to route.
- **CoHyDE-style co-training transfers across catalogs within 6 months** — if a rewriter co-trained on ToolBench works zero-shot on a fresh API catalog, tool retrieval becomes a solve-once problem; if it must be re-run per catalog, the unreported training cost decides its fate.
