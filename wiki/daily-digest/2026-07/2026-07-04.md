## Deep Dives

### Leanstral 1.5: Mistral's 6B theorem prover swaps scaffolds for test-time compute

> Every prior Lean theorem-proving model wrapped the LLM in a complicated scaffold: search procedures, premise selectors, proof-tree managers. Mistral removed all of it. Leanstral 1.5 is a 6B active-parameter model behind a simple coding agent interface, and it scales by spending more inference compute with periodic context compaction every 200K tokens.

**Source:** Twitter / Mistral blog
**Links:** [Blog](https://mistral.ai/news/leanstral-1-5/) . [Tech Report](https://github.com/mistralai/LeanstralSafeVerify/blob/main/LeanstralReport.pdf)

**What is it about?**
Leanstral 1.5 is an open-weight (Apache 2.0) 6B-parameter language model fine-tuned for automated theorem proving in Lean. It achieves state-of-the-art on graduate-level algebra benchmarks (FATE-H, FATE-X), scores 587 on PutnamBench, and saturates miniF2F, a benchmark of high-school math competition problems. The architecture is simplified relative to prior systems: a mid-training phase on Lean tokens, supervised fine-tuning on 50% Lean proof traces, then reinforcement learning with CISPO.

**What problem does it solve?**
Prior theorem provers like earlier versions of Leanstral and DeepSeek-Prover relied on elaborate scaffolding: search heuristics, premise selection systems, and hand-tuned proof-tree managers. These scaffolds were brittle, domain-specific, and hard to maintain. Leanstral 1.5 shows that a simple coding agent loop with test-time compute scaling does the same job more robustly.

**What's the core novelty?**
The elimination of the scaffold. Instead of engineering a proof search procedure, the model acts as a coding agent: it writes Lean code, the Lean compiler checks it, and the model iterates. Test-time compute scales through context compaction every 200K tokens, keeping the proof search in memory without blowing the context window. The interesting finding from the tech report is that the compaction step is surprisingly transparent: the log curves show no visible discontinuity at compaction boundaries, suggesting the model recovers state cleanly.

**Key takeaways**
- Apache 2.0 license for a theorem prover that competes with closed frontier models. This matters for reproducible science.
- 6B active parameters means this runs on consumer hardware, unlike the 70B+ math models that dominated earlier.
- Saturating miniF2F means the benchmark is effectively solved at the high-school level. Graduate algebra (FATE-H/X) is where the remaining signal lives.
- The accompanying LeanstralSafeVerify tool checks code properties and catches bugs in Rust repos, showing the proof capability transfers to practical software verification.

**Gaps in the study**
The compaction technique's limits are unexplored. The team mentions it runs to 4M tokens but does not publish what happens after that. The RL phase uses CISPO, a contrastive preference optimization variant, but there is no ablation comparing CISPO to standard DPO or PPO. The transfer from Lean proofs to Rust code verification is demonstrated qualitatively but not benchmarked against dedicated static analysis tools.

**Industrial implication**
A 6B theorem prover under Apache 2.0 that verifies Rust code means formal verification can become a CI pipeline step, not a specialist consultant engagement. The scaffold-free approach also suggests a general lesson for agent-building: inference-time compute plus a tight verification loop (Lean compiler, Rust compiler, test suite) often beats hand-engineered agent scaffolds. This is the same pattern that coding agents like Claude Code already use, extended to formal proof.

### Kilo Code Auto Efficient: model routing as table stakes

> Every engineering leader is asking for a router that cuts AI spend without tanking code quality, and The Pragmatic Engineer just declared routing table stakes. Kilo Code's answer is Auto Efficient: a prompt-aware router that reads your coding task, checks a benchmark, and selects the cheapest model proven for that task type. It also learns per-session, optimizing model selection as it observes what works.

**Source:** Twitter (@kilocode)
**Links:** [Kilo Gateway](https://kilo.ai/gateway)

**What is it about?**
Auto Efficient is a model router integrated into Kilo Gateway, a universal inference API that fronts 500+ models. For each incoming coding prompt, the router classifies the task type, references KiloBench (an internal coding benchmark that maps task categories to model performance), and routes to the cheapest model proven to handle that category. Over a session, it learns which models perform well for the specific user's coding patterns and shifts allocations accordingly.

**What problem does it solve?**
The standard approach of routing everything to Claude Opus or GPT-5.5 Pro wastes money: many tasks (boilerplate, refactoring, simple CRUD) are handled just as well by smaller or open-weight models. The alternative of manually configuring routing rules per task type is brittle and does not adapt to model releases. Auto Efficient automates this cost-quality tradeoff per prompt without manual intervention.

**What's the core novelty?**
Session-aware routing. Most model routers make independent decisions per request. Auto Efficient treats the session as a learning problem: it observes which models produce good code for the specific user's repo and coding style, then shifts future allocations toward those models. The benchmark-grounded initial routing provides a cold-start prior; session learning provides personalization.

**Key takeaways**
- The Pragmatic Engineer's coverage of routing as "table stakes" signals the market has crossed an adoption threshold: routing is no longer a research curiosity, it is infrastructure every AI platform is expected to ship.
- 500+ models available through a single API endpoint means the routing layer is downstream of model diversity, not upstream of it. More models make routing more valuable, and better routing makes more models viable.
- Session-awareness is the feature that separates a router from a static rule engine. It closes the gap between an org's one-size-fits-all benchmark and the specific user's actual task distribution.

**Gaps in the study**
KiloBench is proprietary, so third-party evaluation of the routing accuracy is impossible. The session-learning mechanism is described in high-level terms without published data on convergence rate or regret. No A/B test results comparing Auto Efficient against static routing (e.g., "always use Opus for code, always use Haiku for chat") are publicly available.

**Industrial implication**
If routing is table stakes, the winner is the platform with the most model-provider integrations and the most benchmark data. Kilo's 500+ models give it breadth. The question is depth: can session-level learning produce enough per-user signal to justify auto-routing over a simple static tier (cheap model first, escalate on failure)? The enterprise use case where this matters most is CI/CD pipelines that fire thousands of coding prompts daily: a 30% cost reduction on boilerplate tasks alone pays for the routing infrastructure.

This is the second routing product shipped this quarter (after SciOrch's offline orchestrator on 06-18). Both share the same insight: routing decisions are too expensive to make at inference time with frontier models. The answer is to learn a cheap proxy offline (SciOrch) or from benchmark priors plus session data (Kilo). A routing ecosystem is forming.

### Scaling Monosemanticity: Anthropic extracts interpretable features from Claude 3 Sonnet

> Anthropic researchers extracted millions of interpretable features from a production-scale frontier model, not a toy network. The scale jump from earlier dictionary-learning work (small models, toy domains) to Claude 3 Sonnet is what makes this paper land differently: interpretability is no longer a proof of concept, it is a tool applied to real deployed systems.

**Source:** Kurate cs.AI #13
**Links:** [Paper](http://arxiv.org/abs/2605.29358v1)

**What is it about?**
The paper scales sparse autoencoder (SAE) based dictionary learning to Claude 3 Sonnet, a mid-sized Anthropic model. The authors extract millions of monosemantic features (individual neurons or neuron groups that activate for a single human-interpretable concept) and demonstrate that these features are causally relevant: activating or suppressing them changes model behavior in predictable ways. This is the largest-scale demonstration of dictionary learning applied to a frontier-class model.

**What problem does it solve?**
Previous SAE work operated on models small enough that scaling questions were unanswerable: do interpretable features survive at production scale, or does superposition overwhelm them? This paper answers yes. The features exist, they are extractable, and they remain causally meaningful at the scale of a model that ships to users. This also validates the core premise of Anthropic's interpretability-as-safety strategy: you can peer inside a model you actually deploy.

**What's the core novelty?**
The primary contribution is the scale-up itself, from toy models to a frontier production model, and the engineering discipline required to make SAE training tractable at that scale. The paper also introduces improved feature visualization techniques and a causal intervention framework for validating that extracted features are not artifacts.

**Key takeaways**
- Features extracted from Claude 3 Sonnet include safety-relevant concepts: deception, sycophancy, power-seeking. These features can be causally manipulated.
- The feature dictionary covers a substantial fraction of the model's internal representations, reducing the "dark matter" problem where SAEs miss most of what the model is doing.
- Compute cost for full-feature extraction at Sonnet scale is extremely high. The paper does not hide this; it frames the cost as the central scaling challenge for interpretability.

**Gaps in the study**
The 06-18 digest covered a paper showing SAE interventions are unreliable: clamping an "unsafe" feature blocks one route but behavior reroutes through the unexplained portion of the model (95.8% recovery on refusal). This paper does not engage with that finding. The features are interpretable and causally relevant, but whether they provide robust control (rather than just probes) is the open question. Also, the extraction is post-hoc: it tells you what the model was doing after training, not during.

**Industrial implication**
This is a research milestone for Anthropic's safety narrative. In the same week that Anthropic removed steganography-detection code and launched a "Cyber Jailbreak Severity" framework (see Industry Pulse), this paper is the underlying research that makes those safety interventions credible. The tension is that causal manipulation of features is still unreliable, as the 06-18 SAE-intervention paper showed. The safety infrastructure claims more confidence than the interpretability research yet supports.

This paper also received a 9.0/10 ai_rating on Kurate, the highest among all cs.AI papers this week. The LLM judges are treating interpretability at scale as a landmark.

### How to Scale Mixture-of-Experts: from muP to the maximally scale-stable parameterization

> When you scale a Mixture-of-Experts model (where each token routes through a small subset of specialized sub-networks instead of the full model) from 100M to 100B parameters, the optimal hyperparameters shift in ways that cause training to silently diverge. This paper extends muP (the maximal update parameterization that makes hyperparameters transfer across scale) to MoE architectures, giving a recipe for stable scaling that works from the first small-scale experiment to the final frontier run.

**Source:** Kurate cs.LG #12
**Links:** [Paper](http://arxiv.org/abs/2605.14200v1)

**What is it about?**
The paper derives the maximally scale-stable parameterization for MoE transformers. muP, introduced by Yang et al., ensures that the optimal learning rate, initialization scale, and other hyperparameters found at small model sizes transfer directly to large model sizes for dense transformers. This paper extends that framework to the routing mechanism, expert networks, and load-balancing loss of MoE models, providing a unified initialization and learning-rate scaling rule that is provably stable across model width.

**What problem does it solve?**
Training MoE models at scale requires expensive hyperparameter sweeps at each target size because the standard muP does not account for the interaction between the routing function and expert networks. Practitioners routinely waste millions of dollars in compute on tuning runs that would be unnecessary if the scaling were stable. This paper gives the recipe that makes those tuning runs unnecessary.

**What's the core novelty?**
The key technical result is an analysis of how the router's output distribution interacts with expert initialization as width scales. The authors show that the router's softmax must be temperature-scaled with width, and expert initialization must account for the fact that each expert sees only a fraction of tokens. The resulting parameterization, which they call MoE-muP, is derived from first principles rather than found empirically.

**Key takeaways**
- MoE-muP is provably stable: a 1.3B MoE trained with hyperparameters found on a 125M proxy transfers without adjustment.
- The router temperature scaling rule is the critical piece that naive muP misses. Get it wrong and training diverges silently.
- The paper validates on both vision (ViT-MoE) and language (LLM-MoE) architectures, showing the parameterization is architecture-agnostic within the transformer family.
- Kurate ai_rating: 9.0/10, the second highest in cs.LG this week after the virtual patient paper.

**Gaps in the study**
Validation is limited to language modeling loss and downstream perplexity. The paper does not test whether MoE-muP also stabilizes more complex training regimes like reinforcement learning from human feedback (RLHF) or on-policy distillation, where MoE routing dynamics interact with the reward signal.

**Industrial implication**
Every lab training MoE models (Mistral, DeepSeek, Google with Gemini's MoE architecture) benefits directly. A lab that adopts MoE-muP saves millions in hyperparameter tuning compute on each scaling step. For the open-weight community, this is the difference between "we trained a 7B MoE that mostly works" and "we trained a 70B MoE that proves the scaling recipe transfers." This parameterization is also likely to appear in the next generation of open-weight MoE releases from DeepSeek, Mistral, and Qwen.

### Solve the Loop: attractor models as an alternative to autoregressive generation

> Autoregressive language models produce text one token at a time, left to right. Attractor models iterate the entire sequence through a fixed point: they converge to an answer, not generate word by word. This paper proposes that reasoning is better modeled as finding an attractor in a dynamical system, not as sequential token prediction.

**Source:** Kurate cs.LG #6
**Links:** [Paper](http://arxiv.org/abs/2605.12466v1)

**What is it about?**
The paper introduces "attractor models" for language and reasoning. Instead of generating tokens left to right, the model iteratively refines a full sequence representation until it converges to a fixed point (an attractor) that represents the answer. For reasoning tasks, this means the model can revise earlier steps based on later insights, a capability that autoregressive models can only approximate through chain-of-thought prompting.

**What problem does it solve?**
Autoregressive models cannot revise earlier tokens once generated, which makes reasoning errors compound. Chain-of-thought partially addresses this by letting the model "think aloud," but the thinking is still left-to-right: a mistake in step 3 cannot be corrected unless the model writes a step 7 that says "step 3 was wrong." Attractor models eliminate this constraint by treating the entire output as a joint optimization problem.

**What's the core novelty?**
The architecture iterates a sequence representation through a recurrent block until convergence (detected by a halting condition). At convergence, the representation is decoded into tokens. The number of iterations is adaptive: simple completions converge in a few steps, hard reasoning problems iterate longer. This is conceptually related to diffusion language models but uses deterministic dynamics rather than stochastic denoising.

**Key takeaways**
- The model demonstrates emergent revision behavior: later iterations can change decisions made in earlier iterations without explicit chain-of-thought.
- Performance on reasoning benchmarks (MATH, GSM8K) is competitive with autoregressive models of similar parameter count.
- The iteration count serves as a natural measure of problem difficulty: more iterations for harder problems.

**Gaps in the study**
The model is a proof of concept at modest scale. Scaling behavior (does the attractor property hold at 70B+ parameters?), training stability across many iterations, and inference latency are all unaddressed. The convergence guarantee is empirical, not proven, and there may be inputs with no stable attractor.

**Industrial implication**
If attractor models scale, they could replace chain-of-thought prompting with a model-native revision loop. This would be a meaningful efficiency gain because chain-of-thought tokens are expensive (they increase context length and inference cost) and are often wrong in ways the model cannot fix. A model that can revise its own reasoning without generating tokens for the revision process reduces inference cost and improves correctness. This is far-term; near-term, the idea informs how we think about test-time compute scaling (the attractor iterations are a form of test-time compute that is more structured than beam search).

## Global View

**Routing infrastructure is consolidating right as model dependency risk peaks.** On the same day The Pragmatic Engineer declares routing "table stakes" and Kilo Code ships a session-aware auto-router, 67% of enterprises report they already built hedges against Fable 5 dependency during its weeks-long outage. These are two sides of the same coin. Routing was originally sold as cost optimization: use the cheapest model that works for each task. The Fable 5 outage exposed a second, larger use case: routing as business continuity. If your critical workflows are routed through multiple model providers, no single model's removal (by export control, safety downgrade, or pricing change) can halt your operations. Kilo Gateway's 500+ models and session-aware routing make the continuity case just as strong as the cost case. The enterprise lesson from the Fable 5 outage is not "don't depend on frontier models." It is "depend on all of them simultaneously, with a routing layer that switches faster than your procurement team can negotiate a new contract."

**Fable 5's qualitative leap exposes an evaluation gap.** The developer testimonials Sholto Douglas amplified are unusually consistent: Fable 5 eliminates boilerplate, stops hedge-language, makes judgment calls instead of sanding every edge off, and produces code that developers describe as "the most direct 1:1 translation of thought to reality." Yet the benchmark delta over Sonnet 5 is modest on paper. This is not new (CEO-Bench on 06-18 showed Opus 4.8 and GPT-5.5 staying solvent for 500 simulated startup days, a benchmark that no one had built before), but Fable 5 makes the gap undeniable. The evaluation community is measuring models on tasks where the gap between competent and excellent is a few percentage points, while users report an order-of-magnitude difference in their actual work. The benchmarks that would capture Fable 5's qualitative edge (sustained multi-file codebase changes, system design judgment, proactive "here's context you didn't know you needed" behavior) do not yet exist. When 67% of enterprises build hedges against a model they describe as qualitatively transformative, the signal is not that the model is overrated. It is that our evaluation tools are underpowered.

**Scaffold removal is a pattern, not a coincidence.** Leanstral 1.5 removed the theorem-proving scaffold. Fable 5 works better with 80% fewer system prompt instructions. Claude Code's whole product is "remove the scaffold between you and the code." Three independent decisions in one week, all making the same architectural move: the model is now good enough that hand-crafted intermediate structure is a tax, not a support. This is the same insight that drove the shift from symbolic AI to neural nets: when the model is weak, you scaffold. When the model is strong, the scaffold becomes friction. The implication for builders: if you are still designing agent systems with elaborate hand-tuned prompt chains, decision trees, and routing logic, Fable 5 class models are about to make your scaffold the bottleneck, not the enabler.
