<span class="mz-card-badge">Kernels · state cache · NVIDIA + Dao AI Lab</span>
<h4>ReplaySSM: store the inputs, not the state</h4>
<p>Hybrid models mix attention with SSM layers (state-space layers that compress history into a fixed-size state). During decoding, reading and writing that state every step is the memory bottleneck. ReplaySSM keeps a checkpoint of the state plus a short buffer of recent inputs, and replays the inputs to compute outputs. That roughly halves state memory traffic: 1.46-1.80x faster SSM decode kernels at batch 256 on Blackwell Ultra B300. Speculative decoding gets simpler too, since rejecting a draft just drops buffered inputs instead of restoring a snapshot, for 1.85-2.10x speculative throughput on 120B-class models. A high-precision checkpoint with a low-precision read copy keeps most models within ~2 points of FP32 on GPQA-Diamond. Already wired into TensorRT-LLM.</p>

### Agent memory: what it costs, what it buys

<div class="mz-feed">

<div class="mz-card">
<div class="mz-card-body">
<span class="mz-card-badge">Paper · KV cache · DAIR pick</span>
<h4>Persistent memory in multi-agent inference adds cost, not accuracy</h4>
<p>UCLA and colleagues measure a three-tier chain-of-agents system on long-context tasks. Splitting the work across agents works: peak KV cache (the stored attention state that grows with context) drops to 14.3 MiB per query versus about 35 MiB for single-pass and RAG, and latency falls from 52-67 s to 29 s. The persistent tier that stores and recalls reasoning traces does not pay off: +0.368 MiB of cache and +0.015 accuracy with a confidence interval crossing zero. The authors argue the null is structural, since single-question benchmarks give each item its own evidence, so there is nothing useful to recall. They also report four measurement corrections, three of which had inflated the benefit. A useful check on the many viral "agents with memory" claims.</p>

### Training memory: RL that fits

<div class="mz-feed">

<div class="mz-card">
<div class="mz-card-body">
<span class="mz-card-badge">Paper · NVIDIA · DAIR pick + X (cross-source)</span>
<h4>LoGRA: full-weight RL with less memory than LoRA</h4>
<p>RL post-training usually runs out of GPU memory on gradients and optimizer state before it runs out of compute. LoGRA never builds the full gradient: as microbatches accumulate, each weight gradient is compressed by a random rank-256 projection that is redrawn every step, and the update is rebuilt from two small matrices. Before each step it predicts how much the policy will move and scales the step to a KL budget. At 1.5B it uses 7.2 GiB vs 13.2 GiB for rank-256 LoRA at the same Pass@4; at 7B average memory drops 45.7%; and it trains a 27B model on one 8-GPU node where dense Adam runs out of memory.</p>

<div class="mz-card-body">
<span class="mz-card-badge">Paper · Alibaba</span>
<h4>QwenGyre: stop GPUs idling during agent rollouts</h4>
<p>Agentic RL rollouts can run for hours and 700K+ tokens while GPUs wait on browsers and test runs. ## LLMs, agents, safety

### Self-improvement gets measured

Five papers on agents that improve from their own experience landed in one US day. The common move: stop asking "how good is the agent" and ask "how efficiently does it get better, and who checks."

<div class="mz-feed">

<div class="mz-card">
<div class="mz-card-body">
<span class="mz-card-badge">Paper · Meta and others</span>
<h4>Agent Plasticity: how well does an agent learn?</h4>
<p>Weights stay frozen. The agent may only edit its memory, skills, strategy and Python tools after successes and failures, and is then tested on new held-out tasks. Agent plasticity measures held-out gain per unit of learning cost. Across Chess, Go, Hex and NetHack, frontier models with similar feedback show very different curves: one reaches the highest final skill, another learns more efficiently, and some stay flat or get worse. A common failure is that weak agents store the right skill and then never retrieve it. That echoes today's memory null result from the other direction.</p>
<div class="mz-card-foot"><a href="https://arxiv.org/abs/2610.08902">Paper →</a> · <a href="https://x.com/Xudong07452910/status/2109487471730032943">Post →</a></div>

<div class="mz-card">
<div class="mz-card-body">
<span class="mz-card-badge">Paper · AWS + HSBC</span>
<h4>Double Ratchet: the grader evolves with the agent</h4>
<p>Self-improving agents usually need a human-written grader. Here the grader is built from small, mostly rule-based checks, one per failure type, and evolves alongside the agent's skills. A grader version is chosen only for agreeing with 10 labeled examples, never for raising the agent's score, which blocks the obvious reward hack. It kept 88-110% of the gain that ground truth or a rubric gave, across code, SQL and reports. Oddly, with safeguards removed the grader passed 97-100% of outputs yet still trained skills well, which deserves a closer look.</p>

<div class="mz-card-body">
<span class="mz-card-badge">Paper · test-time search</span>
<h4>Fork-and-Flush: escaping "idea basins"</h4>
<p>Dimitris Papailiopoulos and Microsoft collaborators found that long-running research agents develop tunnel vision, polishing one family of ideas like gradient descent stuck in a local minimum. They map these "idea basins" by having an LLM compare thousands of experiment pairs and embedding the result in 2D. The fix is basin hopping: periodically fork the agent into several copies in the same workspace with empty context, let them run, and continue from the best. At equal compute it beats single runs and best-of-N on 12 of 13 long-horizon tasks, some running 4+ days. It is a cheap, harness-level fix.</p>

<h4>RSI-Anything and Sakana's MASS</h4>
<p>RSI-Anything uses a predictive world model (JEPA-Anything) to pick which actions and training data to try, then keeps policy updates only if they pass compatibility checks. Code repair rises from 26.3% to 31.2% with the coder fixed; lab planning more than doubles over five policy versions. Sakana and Berkeley's MASS has one base model propose, run and grade multi-agent workflows, then fine-tunes on the best trajectories; two cycles on Qwen3.6-27B give 1.2-1.6x more performance per output token. Both are claims on their own benchmarks.</p>

<h4>Fan out, then combine: 66 of 70 bugs, every run</h4>
<p>Anthropic's docs for dynamic workflows report a test with 70 planted bugs in a 116K-line codebase. A single agent found 14, 15 and 27 across three runs; a multi-agent workflow found 66 every time. <h4>Benchmarks that look like real work: SWE-TaskFlow and MiniCorp</h4>
<p>JetBrains studied 4,782 real coding-agent sessions: features and bug fixes were well under half of requests, versus 93.8% of SWE-Bench Pro. <span class="mz-card-badge">Paper · Microsoft · DAIR pick</span>
<h4>DUET: train the grader alongside the agent</h4>
<p>An LLM grader that stays fixed gets out of date, because the agent's failure modes change as it improves. DUET alternates: each round runs the solver, has the grader score and critique the trajectories, then a tool-using updater revises either the grader or the solver while the other stays fixed. The solver reaches 96.5% on the Finance Agent Benchmark (GEPA 94.4%), and grader agreement on GDPval rises from 68.4% to 78.5%. Training the grader with the solver frozen barely moves it, which is the interesting result: graders learn from the agent's new mistakes, not in isolation.</p>
