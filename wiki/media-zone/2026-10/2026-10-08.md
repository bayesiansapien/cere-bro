<h4>Unsloth: train your own Jev-style decision model locally</h4>
<p>Jev (yesterday's decision model, which scores bounded choices from token logits instead of generating text) now has an open training recipe. <h4>Jev-Mem: memory decisions without an LLM writing sentences</h4>
<p>Mem0 applies the same idea to agent memory. Every memory system makes many small calls: store this, update that, drop the old fact. <h4>SanDisk's data-center bet rides on KV-cache offload</h4>
<p>A market analyst projects SanDisk data-center revenue growing about 30x to roughly $8B a quarter by 2028, citing agents pushing KV cache (the saved attention state a model reuses instead of recomputing) onto enterprise SSDs. <span class="mz-card-badge">Explainer thread · serving fundamentals</span>
<h4>Inference engineering is the underrated skill</h4>
<p>A clear primer on why serving is its own field. Prefill (processing the prompt) is compute-heavy and parallel; decode (one token per step) is bound by memory bandwidth because it rereads weights and a growing KV cache each step. Batching, KV capacity, scheduling, kernel choice and tail latency all follow from that split. Nothing new to a specialist, but it is a good one-page map of where serving cost actually comes from.</p>

### Search harnesses: split the planner from the proposer

<div class="dg-title">The planner never sees the code, and the code never sees the grader</div>
<div class="dg-sub">The claimed savings come from resetting sessions and keeping state in a graph, not in context.</div>

```mermaid
flowchart LR
  G["Idea graph<br/><small>lineage, scores, lessons</small>"] --> D["Search director<br/><small>Opus 5.5 plans next step</small>"]
  D --> P["Proposer<br/><small>GPT-6.1 Sol writes variants</small>"]
  P --> S["Sandbox<br/><small>isolated execution</small>"]
  S --> E["Evaluator<br/><small>walled off from candidates</small>"]
  E -->|scores| G
  M["Meta pass<br/><small>distills verified lessons</small>"] -->|guidance| G
  classDef input fill:#d0ebff,stroke:#1971c2,color:#1b1b1b,stroke-width:2px
  classDef core fill:#e5dbff,stroke:#6741d9,color:#1b1b1b,stroke-width:2px
  classDef loop fill:#fff3bf,stroke:#f08c00,color:#1b1b1b,stroke-width:2px
  classDef exit fill:#d3f9d8,stroke:#2f9e44,color:#1b1b1b,stroke-width:2px
  class G input
  class D,P core
  class S,M loop
  class E exit
```

<div class="dg-legend">Blue is persistent state, purple are the two models, amber is execution and learning, green is the isolated scorer.</div>

<h4>Two frontier models, one idea graph, 3.2x lower spend</h4>
<p>A viral thread credits a Stanford group with a code-search harness where Opus 5.5 plans, GPT-6.1 Sol proposes code, and a persistent graph database holds lineage, so each session resets and context never bloats. Claimed results: 3.2x lower model spend than fixed evolutionary loops, first place in 7 AtCoder heuristic contests, and SOTA on Anthropic's kernel-builder task. The thread links no paper, so the numbers are unverified; the design idea (state in a graph, not in tokens) is the takeaway.</p>

### The math drop gets graded

<div class="mz-feed">

<div class="mz-card">
<div class="mz-card-body">
<span class="mz-card-badge">Essay · Marcus and Tao</span>
<h4>"The real news isn't the result, it's what we weren't told"</h4>
<p>Gary Marcus argues OpenAI's 722 AI-written manuscripts came from an unreleased model with an undisclosed procedure: no failure rate, no architecture, no word on whether Lean verification was iterative.
