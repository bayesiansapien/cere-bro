### The KV cache moves to disk, and agents start editing it

Two posts, one idea: recomputing prefill is the expensive part of long-context serving, so the winning move is keeping KV states alive longer and touching them less.

<div class="dg-title">A cache hit is a disk read, not a GPU recompute</div>

<h4>DeepSeek open-sources DeepInfer: prefix cache on SSD</h4>
<p>DeepInfer is the serving stack behind DeepSeek's API cache hits. Conventional engines keep the KV cache (the stored attention keys and values for every past token) in GPU memory, where it gets evicted fast. DeepSeek stores it on SSDs instead. That works only because MLA (multi-head latent attention, which stores one compressed vector per token per layer) shrank the cache about 93% versus their older 67B model, and because their 3FS file system stripes reads across thousands of drives. Cached prefixes live 3 days for agent traffic and 7 for chat, and 56% of input tokens on one production day came from disk. The cost face is blunt: a hit is 50x cheaper than a miss on deepseek-flash, so put system prompts, tools and documents first.</p>

<h4>Cache engineering: edit the KV cache, not the prompt</h4>
<p>Agents that trim or summarize old messages break prefix reuse, so they pay to recompute the cache. A Tsinghua and CUHK team keeps the text history intact and instead adds two cache operations: "drop" hides selected KV entries from future attention, and "repos" fixes the positions of the keys that remain. Their AKV serving engine tracks these edits in an extended radix tree and rebuilds missing states in one batched prefill. Dropping old tool responses gave 27.7% lower cost, +1.7 benchmark points, 1.18x throughput and 1.51x faster P95 latency; letting agents tune their own drop policy saved another 7.1%. Quietly posted, low engagement, but squarely on KV eviction research.</p>

<h4>CUDA Graph padding: paying for tokens that do not exist</h4>
<p>CUDA Graphs record a fixed sequence of GPU kernels once and replay it, which removes the CPU launch cost on every decode step. The catch is that a graph has a fixed shape, while continuous batching changes the batch size every step. Engines like vLLM capture graphs for a few sizes and pad up to the next one, so a 121-token batch runs the 128-token graph and pays for 7 phantom slots. Adding one token past a capture size makes cost jump in a step, which vLLM's Adaptive Verification work hits directly with speculative decoding. A small account, high engagement rate, and a clean explanation of a cost most serving dashboards hide.</p>

<h4>Inference engineering in one page</h4>
<p>A dense primer on why serving is its own discipline. Prefill (processing the prompt and building the KV cache) is compute-heavy and parallel; decode (one token at a time) is bound by memory bandwidth because it rereads weights and KV state every step. Almost every known trick maps to one side of that split: FlashAttention and GQA cut memory traffic, PagedAttention cuts fragmentation, chunked prefill lets long prompts share the GPU with decode, prefix caching skips repeated prefill but does not speed decode. <h4>Are self-evolving agents actually continual learners?</h4>
<p>Many self-improvement methods leave weights frozen and rewrite the agent's own prompts, memory or code from feedback. This paper tests ReasoningBank, GEPA and Meta-Harness on task streams that drift in topic, workflow or domain (built from BIRD, BFCL and ScienceWorld). Self-evolution helps on average, but more plasticity always costs stability. Global prompt edits overwrite what worked on earlier tasks, and similarity-based memory pulls in the wrong memories when similar queries need different workflows.</p>

<h4>EMMA: scoped edits fix the forgetting problem</h4>
<p>An Amazon-led paper reads like a direct answer to the card above. EMMA treats a multi-agent system's configuration as episodic memory with three parts: the controller's routing memory (which sub-agent handles which step), specialist prompts that inherit a generalist prompt, and short procedural skills. After a failure, a reflector assigns the fix to exactly one of the three and proposes one bounded edit, so a change cannot sprawl across the system. It beats ACE, GEPA, EvoMAS and ADAS on KramaBench, AppWorld and BBEH by up to 32.5%, with 17 to 38% fewer training runs.</p>
