## Routing, KV cache, compression, GPU

### Inference engineering, revisited: vLLM internals, CUTLASS, speculative decoding

- **The vLLM anatomy (cost optimization).** A saved deep-read of "Inside vLLM," the long walkthrough of a high-throughput serving stack, lays out the machinery that actually moves serving cost: paged attention (managing the KV cache, the stored attention keys and values, like operating-system virtual-memory pages), chunked prefill, prefix caching, guided decoding, speculative decoding, and disaggregated prefill/decode. It is the concrete "how" behind every latency and throughput number. A genuinely worthwhile full read for anyone tuning a serving path.
- **CUTLASS for custom kernels (cost optimization).** NVIDIA's CUTLASS, its open-source CUDA templates plus Python DSLs for high-performance linear algebra, resurfaced as the entry point for writing your own fast GEMM and attention kernels instead of waiting on vendor libraries. Kernel-level control is where the last 2x usually hides.
- **EAGLE speculative decoding (cost optimization).** Part of the same inference-engineering reading, EAGLE drafts candidate tokens from feature-level extrapolation so the big model only verifies. Speculative decoding keeps showing up as the highest-leverage latency win that needs no change to the model itself.

## LLMs, agents, safety

### The harness, not the model, is the optimization surface (two papers, one thesis)

- **Prompt wording changes *where* effort goes, not just how much.** A preregistered benchmark of 4,644 valid runs across 24 deterministic coding tasks, 7 reasoning models, and 2 real agent harnesses. The same requested change producing the same correct patch can drive radically different work. "Try multiple approaches" phrasing inflates reasoning 2.4x to 7.4x and spawns about three elaborated-then-discarded solution branches for one implemented fix, with no gain in success rate. "Maximum certainty" instead triggers repeated verification: extra test runs, tool calls, turns, latency, and context growth. The takeaway is uncomfortable and practical. Your prompt is a cost dial, and most people turn it blindly.
- **LongHorizon-Harness: keep the state outside the context.** Alibaba's AutoNavi team reframes long-horizon execution (tasks needing sustained reasoning across many interdependent steps) as a task-state management problem. Existing harnesses keep execution, state, and completion-assessment inside one growing context, so the state becomes hard to track and wrong self-assessments propagate into later steps. Their Manage-Execute-Audit loop splits the roles: a manager holds explicit state outside the context and picks the next subtask, a fresh-context executor performs it, and a read-only auditor verifies the actual environment state before the next round. State updates only on facts independently verified from the environment.
- **Why this is one story, and where it connects.** Both papers land on the claim the wiki has been circling since the 05-23 "code as agent harness" summary (which argued the scaffold, not the weights, is the real artifact) and the 05-27 "scaling the harness" page. The 08-08 weekly review's HarnessOpt-Bench (which made "can a model optimize its own harness" measurable) is the benchmark for this idea; these two papers are the mechanism. If the harness is where behavior is decided, it is also where cost is decided, which ties it straight to the inference-engineering thread above.

**Sources:** [Harness prompt-wording study (arXiv 2608.01347)](https://arxiv.org/abs/2608.01347) · [LongHorizon-Harness (arXiv 2608.01964)](https://arxiv.org/abs/2608.01964)

### Context engineering and self-improving loops: delete the prompt, keep the skill

- **"Delete 80% of the system prompt" (token optimization).** A heavily-saved claim that Anthropic, Cloudflare, and Karpathy independently cut most of their agent system prompts, moving instructions into on-demand skills and tools instead of a bloated always-on preamble. If it holds up, it is the token-optimization face of the harness thesis: the win is in what you *stop* keeping in context.
- **Agent skills are becoming a supply chain, and most of it is noise.** A parsed corpus of 7,944 public Claude Code skills reportedly found roughly a third make the agent *worse* than using no skill at all. The practical read: as skills proliferate, curation quality matters more than skill count. Related saves point to Nous Research's Hermes Agent, which pitches persistent memory that auto-generates skills as "the agent that grows with you."
- **Self-improving loops as the live frontier.** Several saves cluster on Anthropic's self-improving agentic loops and "70% of our engineers use them" claims. Treat the percentages as marketing, but the direction, agents that rewrite their own harness and skills, is exactly what the HarnessOpt-Bench thread predicted would matter.

**Sources:** [Hermes Agent (Nous Research)](https://hermes-agent.nousresearch.com)

### Agent memory keeps trying to move inside the model

- **"What if memory were a capability of the LLM itself?"** A saved thread arguing for making memory native to the model rather than an external store. This is the same pull the wiki's long agent-memory cluster keeps recording: SuperLocalMemory (04-17), EvolveMem (05-15), MemForest (05-26), MemTrain (06-04). The field keeps trying to internalize memory instead of bolting on a vector database (an external index of past context the agent queries). The open question worth tracking: does "native memory" actually beat retrieval, or just hide it inside the weights?
