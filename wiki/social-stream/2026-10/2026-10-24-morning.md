- **Cheap models do the cheap work (cluster of 4)** ([@rohanpaul_ai](https://x.com/rohanpaul_ai/status/2113789709097091338), [@dair_ai](https://x.com/dair_ai/status/2113638581818556920), [@undefinedKi](https://x.com/undefinedKi/status/2113689331412156666), [@Xudong07452910](https://x.com/Xudong07452910/status/2113800139005460534); [paper](https://arxiv.org/abs/2610.31483), [Anthropic post](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)). Meta and Carnegie Mellon train small Qwen3 models to pick tools from more than 10,000 options: split the instruction into substeps, retrieve candidates for each, commit one tool per substep. After SFT on about 20,000 ToolBench instructions and RL that rewards covering the right tools, the 8B model reaches 41.5% on ToolBench G3, above a prompted 402B Llama-4-Maverick, and it transfers to new retrievers and tool sets. Shopify's agent reads about 40 tokens for every one it writes, so reading goes to small task-trained open models and only results return to the frontier planner: reported 7x faster and about 90% fewer tokens, with a judge tuned to 74.5 agreement with human experts and nightly reruns that repair 69% of failed conversations. Anthropic's guidance runs the other way on structure: fold subagents back into one main loop with skills, since every handoff loses detail, but check end-to-end evals because one merge broke a task that used to pass. - **Caching, explained properly** ([@akshay_pachaar](https://x.com/akshay_pachaar/status/2113617883456766031)). Four caches cut repeated work at different points. The KV cache stores keys and values (the vectors attention reads from earlier tokens) so each new token reuses them. Prefix caching reuses saved attention state across requests that start the same way; in vLLM each block's ID includes everything before it, so identical text after a changed prefix does not hit. Prompt caching is the provider-managed, discounted version of prefix caching, so put stable instructions first and the changing question last. Semantic caching matches the meaning of a new prompt against stored ones and returns a saved answer without calling the model at all.

- **Why the same GPU is slow at batch 1 and fast at batch 64** ([@techNmak](https://x.com/techNmak/status/2113498978742583578)). At low batch, decoding is memory-bound: moving weights and KV cache costs more than the arithmetic. Bigger batches reuse each weight load across more tokens, which raises arithmetic intensity and moves the bottleneck toward compute. So a model's FLOP count does not tell you its speed. Memory access patterns matter too: 32 threads reading contiguous 4-byte values touch four 32-byte sectors, but a 32-byte stride touches 32 sectors for the same useful data. Tiling into registers and shared memory is how matmul kernels avoid repeated trips to device memory.
